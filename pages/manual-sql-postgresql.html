Capítulo 01

Introdução: o modelo relacional e o porquê do PostgreSQL

Antes de qualquer sintaxe, vale entender o que um banco de dados relacional realmente é e por que ele venceu como forma padrão de guardar dados estruturados. Este capítulo constrói o modelo mental: o problema que o banco resolve, a teoria relacional de Codd traduzida para a prática, a diferença entre pensar de forma declarativa e imperativa, o posicionamento do PostgreSQL frente a MySQL, SQLite e NoSQL, e a anatomia interna de um SGBD. Ao final, apresentamos o schema de e-commerce que vai acompanhar todo o volume.

# O problema que o banco de dados resolve

Imagine guardar os pedidos de uma loja em um arquivo JSON ou numa planilha. No começo funciona. Aí surgem as perguntas reais: quais clientes compraram mais de R$ 500 no último mês? Quantos pedidos ainda não foram pagos? O estoque deste produto bate com a soma dos itens vendidos? Cada pergunta vira um loop manual, e cada escrita simultânea de dois processos vira corrupção silenciosa.

Um Sistema de Gerenciamento de Banco de Dados (SGBD) existe para resolver quatro problemas que arquivos não resolvem bem: consultas arbitrárias eficientes sobre grandes volumes, integridade (os dados não podem ficar inconsistentes), concorrência (milhares de clientes lendo e escrevendo ao mesmo tempo sem se atropelar) e durabilidade (o que foi confirmado não se perde, nem com queda de energia). O modelo relacional é a estrutura matemática que torna os dois primeiros tratáveis; transações e o motor de armazenamento cuidam dos dois últimos.

Nota
"SQL" é a linguagem (Structured Query Language, padronizada pela ISO). "PostgreSQL" é um SGBD que implementa SQL e adiciona extensões próprias. Você aprende SQL uma vez e usa em vários bancos; aprende PostgreSQL para extrair o máximo de um deles em produção.

# O modelo relacional

Em 1970, Edgar F. Codd propôs organizar dados como relações: conjuntos de tuplas, onde cada tupla tem os mesmos atributos. Na prática isso é uma tabela — linhas (tuplas/registros) e colunas (atributos), cada coluna com um tipo bem definido. A genialidade não é a tabela em si; é que toda operação sobre relações produz outra relação. Filtrar uma tabela devolve uma tabela. Juntar duas tabelas devolve uma tabela. Isso torna as operações compostáveis — a base de toda a expressividade de SQL.

Três ideias sustentam o modelo:

  • Relações são conjuntos: não há ordem inerente entre as linhas e, conceitualmente, não há duplicatas (na prática SQL permite duplicatas, mas o ideal é uma chave que as previna).
  • Acesso por valor, não por posição: você não pega "a terceira linha"; você pega "as linhas onde email = 'ana@x.com'". Não existem ponteiros entre registros — relacionamentos são expressos por valores em comum (chaves).
  • Esquema explícito: a estrutura (colunas, tipos, restrições) é declarada e o banco a impõe. Dado inválido é rejeitado na porta de entrada, não descoberto meses depois.

# Álgebra relacional na prática

SQL é, na essência, uma camada amigável sobre a álgebra relacional — um pequeno conjunto de operadores que recebem relações e devolvem relações. Conhecer os operadores ajuda a "ver" o que uma query faz internamente:

A pergunta "quais e-mails de clientes que fizeram algum pedido?" é, na álgebra, uma projeção sobre uma seleção sobre uma junção. Em SQL você escreve o resultado desejado e deixa o banco escolher a ordem das operações:

algebra_na_pratica.sql
-- π(email) ∘ σ(status='pago') ∘ (users ⋈ orders)
-- "projete o email, das linhas onde o pedido está pago,
--  da junção de users com orders pelo id do usuário"
SELECT DISTINCT u.email
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.status = 'pago';

# Declarativo, não imperativo

Esta é a mudança mental mais importante do volume inteiro. Em JavaScript, Python ou Go você descreve como obter o resultado: itere a lista, abra um laço aninhado, acumule num array. Em SQL você descreve o que quer; o query planner decide o "como" — qual índice usar, em que ordem juntar as tabelas, se vale a pena paralelizar.

imperativo_vs_declarativo.txt
// Imperativo (JS): você dita o algoritmo, a ordem, os laços
const resultado = [];
for (const u of users) {
  for (const o of orders) {
    if (o.userId === u.id && o.status === 'pago') {
      resultado.push(u.email);
    }
  }
}

-- Declarativo (SQL): você descreve o resultado; o planner
-- escolhe usar índice, hash join ou nested loop por conta própria
SELECT DISTINCT u.email
FROM users u JOIN orders o ON o.user_id = u.id
WHERE o.status = 'pago';

A consequência é libertadora e perigosa ao mesmo tempo: o banco pode executar a mesma query de mil formas, e duas queries logicamente idênticas podem ter desempenho radicalmente diferente. Por isso o Capítulo 20 (Performance e EXPLAIN) existe — você aprende a ler o plano que o banco escolheu, sem nunca ditá-lo manualmente.

Performance & custo
Pensar declarativamente não significa ignorar desempenho — significa que você influencia o plano por meios indiretos: índices certos, estatísticas atualizadas (ANALYZE) e queries que o planner consegue otimizar. "Brigar" com o planner reescrevendo SQL às cegas costuma piorar; medir com EXPLAIN (ANALYZE, BUFFERS) é o caminho.

# Anatomia de um SGBD

Saber o caminho de uma query por dentro do PostgreSQL evita boa parte das confusões futuras. Quando você envia SELECT ..., ela passa por quatro estágios:

  • Parser: valida a sintaxe e transforma o texto numa árvore de consulta.
  • Planner/Optimizer: gera planos de execução alternativos e escolhe o de menor custo estimado, usando estatísticas das tabelas e os índices disponíveis. É aqui que o "como" é decidido.
  • Executor: roda o plano escolhido, pedindo dados ao motor de armazenamento.
  • Storage: páginas em disco e em cache (shared buffers), com o WAL (Write-Ahead Log) garantindo durabilidade e o MVCC (Multi-Version Concurrency Control) permitindo que leitores não bloqueiem escritores.

Dois conceitos desta lista voltarão muitas vezes. O MVCC é a razão de leituras concorrentes serem rápidas no PostgreSQL — cada transação enxerga um "instantâneo" coerente dos dados (detalhe no Capítulo 11). O WAL é a razão de um COMMIT ser durável mesmo com queda de energia logo depois — a mudança vai para o log antes de ir para os arquivos de dados.

# O schema que usaremos no manual

Todo o volume usa um mesmo domínio — uma loja de e-commerce — para que os exemplos se acumulem de forma didática. Não precisa entender cada cláusula agora; ela será explicada nos capítulos próprios. Veja como um modelo mental do que vamos manipular:

schema_ecommerce.sql
-- Clientes da loja
CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text NOT NULL UNIQUE,
  nome        text NOT NULL,
  criado_em   timestamptz NOT NULL DEFAULT now()
);

-- Categorias de produto
CREATE TABLE categories (
  id     int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome   text NOT NULL UNIQUE
);

-- Produtos do catálogo
CREATE TABLE products (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  categoria_id  int REFERENCES categories(id),
  nome          text NOT NULL,
  preco         numeric(10,2) NOT NULL CHECK (preco >= 0),
  estoque       int NOT NULL DEFAULT 0
);

-- Pedidos feitos pelos clientes
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users(id),
  status     text NOT NULL DEFAULT 'pendente',
  criado_em  timestamptz NOT NULL DEFAULT now()
);

-- Itens de cada pedido (tabela de junção pedido↔produto)
CREATE TABLE order_items (
  order_id     bigint NOT NULL REFERENCES orders(id),
  product_id   bigint NOT NULL REFERENCES products(id),
  quantidade   int NOT NULL CHECK (quantidade > 0),
  preco_unit   numeric(10,2) NOT NULL,
  PRIMARY KEY (order_id, product_id)
);

Cinco tabelas, todas conectadas por valor: orders.user_id aponta para users.id, order_items liga pedidos a produtos numa relação muitos-para-muitos. Esse é o modelo relacional em ação — e cada conceito desse schema (tipos, IDENTITY, REFERENCES, CHECK, chave composta) ganha um capítulo dedicado adiante.

Dica
Não decore a sintaxe deste schema agora. O objetivo do Capítulo 1 é o modelo mental: dados como relações, operações que compõem, SQL declarativo, o planner decidindo o "como". Com isso firme, os 21 capítulos seguintes deixam de ser regras soltas e passam a ser consequências de um único modelo coerente.

# psql — o cliente essencial

O psql é um REPL poderoso. Os meta-comandos começam com \ e são processados pelo cliente (não pelo servidor). Conhecê-los bem vale mais do que qualquer GUI para entender o banco em profundidade.

Conexão e navegação

psql
-- Conectar interativamente
\c loja              -- troca para o banco "loja" (mesmas credenciais)
\c loja dev localhost -- banco, usuário, host
\conninfo            -- exibe a conexão atual

-- Listar objetos do banco
\l                   -- lista todos os bancos de dados
\l+                  -- com tamanho, encoding e owner
\dn                  -- lista schemas
\du                  -- lista roles/usuários

Inspecionar tabelas e objetos

psql
\dt                  -- lista tabelas do schema público
\dt *.*              -- tabelas de todos os schemas
\d  orders           -- descreve a tabela: colunas, tipos, índices, FK
\d+ orders           -- idem + tamanho, storage e comentários
\di                  -- lista índices
\df                  -- lista funções
\dv                  -- lista views
\dm                  -- lista materialized views
\ds                  -- lista sequences

Exibição e formatação

psql
\x                   -- alterna modo expandido (uma coluna por linha)
\x auto              -- expande só quando a linha for larga demais
\timing              -- mostra o tempo de execução de cada query
\pset pager off      -- não pagina resultados longos
\pset format csv     -- saída em CSV (útil para copiar p/ planilha)
\pset format aligned -- volta ao formato padrão

Arquivos e histórico

psql

\e                   -- abre o editor ($EDITOR) com a última query
\s                   -- exibe o histórico de comandos
\s ~/psql_history.sql -- salva o histórico num arquivo

Variáveis e saída

psql

\echo :schema         -- exibe o valor da variável

\copy products TO '/tmp/products.csv' CSV HEADER

\q                    -- sai do psql (Ctrl+D também funciona)
Nota
\copy (barra invertida) roda no lado do cliente e não exige permissões especiais no servidor. O comando COPY (sem barra) roda no lado do servidor e exige a role pg_read_server_files. Para uso cotidiano prefira \copy.

Capítulo 03

Tipos de dados

Escolher o tipo certo de cada coluna não é detalhe de sintaxe — é design. Um text onde deveria haver numeric impede cálculos; um timestamp sem fuso horário guarda silenciosamente dados ambíguos; um serial legado pode surpreender em operações de cópia. Este capítulo percorre os tipos mais usados do PostgreSQL: numéricos, texto, booleano, data e hora, UUID, bytea e os mecanismos de conversão (casting), com as armadilhas de cada família.

Dica
Prefira bigint para chaves primárias desde o início — é comum subestimar o crescimento de uma tabela e esgotar o intervalo de int em produção. O custo de espaço extra (4 bytes por linha) raramente justifica a migração posterior.

Ponto fixo — numeric / decimal

tipos_numeric.sql
-- numeric(precisão, escala): precisão = total de dígitos, escala = casas decimais
CREATE TABLE demo_numeric (
  preco      numeric(10, 2),  -- até 99.999.999,99 com 2 casas
  taxa       numeric(5,  4),  -- ex.: 0,1525 (taxa de 15,25%)
  arbitrario numeric          -- precisão ilimitada — evite em colunas indexadas
);

-- numeric é EXATO: 0,1 + 0,2 = 0,3 (sem surpresas de ponto flutuante)
SELECT 0.1::numeric + 0.2::numeric;  -- → 0.3
SELECT 0.1::float8  + 0.2::float8;   -- → 0.30000000000000004
Atenção
Nunca use real ou double precision (ponto flutuante) para valores monetários. Use numeric(10,2). Ponto flutuante é adequado para ciência/engenharia onde aproximação é aceitável, não para dinheiro.

Sequências automáticas — IDENTITY vs serial

identity_vs_serial.sql
-- IDENTITY (SQL standard, preferido desde PG 10)
CREATE TABLE products (
  id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome text
);
-- GENERATED ALWAYS: rejeita INSERT com valor explícito (mais seguro)
-- GENERATED BY DEFAULT: aceita valor explícito (útil em migrações/seeds)

-- serial (legado — ainda funciona, mas não é SQL padrão)
CREATE TABLE legado (
  id  serial PRIMARY KEY  -- açúcar para: integer DEFAULT nextval('legado_id_seq')
);

-- Forçar valor em IDENTITY BY DEFAULT (útil em pg_restore)
INSERT INTO products (id, nome) OVERRIDING SYSTEM VALUE
VALUES (99, 'produto importado');

tipos_texto.sql

# Data e hora

Esta família é onde mais erros sutis acontecem em produção — especialmente a confusão entre timestamp e timestamptz.

Atenção
Sempre prefira timestamptz. O PostgreSQL armazena o valor em UTC e converte automaticamente para o fuso configurado na sessão (SET timezone = 'America/Sao_Paulo'). Com timestamp (sem tz), o banco guarda o valor bruto sem qualquer contexto — o mesmo número pode significar horas diferentes dependendo de onde o sistema roda.
tipos_datetime.sql
-- Funções de data/hora mais usadas
SELECT now();                        -- timestamptz atual da transação
SELECT current_timestamp;             -- alias de now()
SELECT current_date;                  -- apenas a data de hoje
SELECT clock_timestamp();             -- atualiza a cada chamada (≠ now() em transações)

-- Aritmética com interval
SELECT now() + '7 days'::interval;   -- daqui a 7 dias
SELECT now() - '30 minutes'::interval;
SELECT age(now(), criado_em) FROM orders; -- duração desde a criação

-- Extraindo partes
SELECT extract(year  FROM now());     -- ano
SELECT extract(month FROM now());     -- mês
SELECT extract(dow   FROM now());     -- dia da semana (0=domingo)
SELECT date_trunc('month', now());     -- início do mês atual

-- Configurar fuso da sessão
SET timezone = 'America/Sao_Paulo';
SELECT now();  -- exibido no fuso correto, armazenado em UTC

-- Pedidos dos últimos 30 dias
SELECT * FROM orders
WHERE criado_em >= now() - '30 days'::interval;

-- UUID como chave primária: bom para IDs públicos / APIs

  user_id     bigint REFERENCES users(id),

Performance & custo
UUID v4 (aleatório) como chave primária fragmenta o índice B-tree — cada insert vai para uma posição aleatória, causando muitas page-splits e bloat. Para tabelas com alto volume de escrita, prefira UUIDs ordenáveis por tempo (v7) ou simplesmente bigint IDENTITY como PK e exponha o UUID como coluna separada apenas para a API.

# Casting — conversão de tipos

O PostgreSQL tem dois mecanismos de cast: o operador :: (específico do PG, conciso) e a função CAST() (SQL padrão, portável).

casting.sql
-- Operador :: (forma preferida no PostgreSQL)
SELECT '42'::integer;                      -- text → integer
SELECT '3.14'::numeric;                    -- text → numeric
SELECT '2025-01-15'::date;                 -- text → date
SELECT '2025-01-15 10:30:00-03'::timestamptz;

-- CAST() — SQL padrão
SELECT CAST('42' AS integer);
SELECT CAST(3.99 AS integer);             -- → 3 (trunca, não arredonda)

-- round() para arredondar antes de converter
SELECT round(3.99::numeric)::integer;      -- → 4

-- Casts implícitos: o PostgreSQL converte automaticamente em alguns contextos
SELECT 1 + 2.5;          -- integer + numeric → numeric (3.5)
SELECT 1::float8 + 2;    -- float8 domina → 3.0

-- Conversão de preco (numeric) para texto formatado
SELECT 'R$ ' || preco::text FROM products;
-- Melhor: usar to_char para formatação localizada
SELECT to_char(preco, 'FM"R$ "999G990D00') FROM products;
PostgreSQL 16/17
O PostgreSQL 17 introduziu melhorias no tipo pg_lsn e na representação interna de interval. Mais relevante para o dia a dia: gen_random_uuid() agora está disponível sem precisar habilitar pgcrypto, e as funções de data/hora ganharam melhor suporte a ICU para collation por locale.

Capítulo 04

DDL — schemas e tabelas

DDL (Data Definition Language) é a parte de SQL que define a estrutura do banco: cria, modifica e remove objetos como tabelas, schemas e sequences. Um bom schema de banco é escrito com a mesma disciplina que código de produção — com convenções claras, constraints explícitas e alterações incrementais via migrations. Este capítulo cobre CREATE / ALTER / DROP TABLE, schemas como namespace, valores padrão, colunas geradas, colunas de identidade, comentários e as convenções de nomenclatura que tornam o schema autodocumentado.

# Schemas como namespace

Um schema no PostgreSQL é um namespace dentro do banco de dados — análogo a um "pacote" ou "diretório". O schema padrão se chama public. Vários schemas no mesmo banco permitem separar contextos (multi-tenant, domínios de negócio, versões de API) sem precisar de bancos separados.

schemas.sql
-- Criar schemas
CREATE SCHEMA vendas;
CREATE SCHEMA estoque;
CREATE SCHEMA IF NOT EXISTS relatorios;

-- Criar tabela em schema específico
CREATE TABLE vendas.orders ( ... );
CREATE TABLE estoque.products ( ... );

-- search_path: lista de schemas onde o PG procura objetos sem prefixo
SET search_path = vendas, public;
SELECT * FROM orders;  -- resolve para vendas.orders

-- Definir search_path padrão para um usuário
ALTER ROLE dev SET search_path = vendas, public;

-- Listar schemas e seus donos
SELECT schema_name, schema_owner
FROM   information_schema.schemata
ORDER BY schema_name;

-- Remover schema (precisa estar vazio, ou usar CASCADE)
DROP SCHEMA relatorios;
DROP SCHEMA relatorios CASCADE;  -- remove também todos os objetos dentro
Dica
Em produção, evite usar o schema public para tudo — ele é acessível a qualquer role por padrão no PG 14 e anteriores. A partir do PG 15 o CREATE no schema public foi restrito ao owner. Crie schemas com nomes de domínio (app, auth, audit) e conceda permissões explícitas.

# Colunas GENERATED

Colunas geradas têm o valor calculado automaticamente a partir de outras colunas — nunca precisam ser informadas em INSERT ou UPDATE.

generated_columns.sql
-- GENERATED ALWAYS AS ... STORED: calculada e armazenada em disco
CREATE TABLE order_items (
  order_id    bigint         NOT NULL,
  product_id  bigint         NOT NULL,
  quantidade  int            NOT NULL,
  preco_unit  numeric(10,2) NOT NULL,

  -- Coluna gerada: total é sempre quantidade * preco_unit
  total       numeric(12,2)
              GENERATED ALWAYS AS (quantidade * preco_unit) STORED,

  PRIMARY KEY (order_id, product_id)
);

-- Inserir: total é calculado automaticamente
INSERT INTO order_items (order_id, product_id, quantidade, preco_unit)
VALUES (1, 42, 3, 29.90);

SELECT total FROM order_items;  -- → 89.70

-- Coluna gerada para full-text search (padrão comum)
CREATE TABLE products (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome     text   NOT NULL,
  descricao text,
  busca    tsvector
            GENERATED ALWAYS AS (
              to_tsvector('portuguese', coalesce(nome, '') || ' ' ||
              coalesce(descricao, ''))
            ) STORED
);
Nota
O PostgreSQL suporta apenas colunas geradas STORED (armazenadas em disco). Colunas geradas VIRTUAL (calculadas na leitura, sem ocupar espaço) ainda não são suportadas — esse é um ponto onde MySQL e SQL Server estão à frente.

# ALTER TABLE

alter_table.sql
-- Adicionar coluna (leve — não bloqueia leitura)
ALTER TABLE products ADD COLUMN peso_kg numeric(8,3);
ALTER TABLE products ADD COLUMN IF NOT EXISTS peso_kg numeric(8,3);

-- Remover coluna
ALTER TABLE products DROP COLUMN peso_kg;
ALTER TABLE products DROP COLUMN IF EXISTS peso_kg CASCADE;  -- remove dependentes

-- Renomear coluna
ALTER TABLE products RENAME COLUMN nome TO titulo;

-- Renomear tabela
ALTER TABLE products RENAME TO catalogo;

-- Alterar tipo da coluna
ALTER TABLE products ALTER COLUMN estoque TYPE bigint;

-- Alterar DEFAULT
ALTER TABLE products ALTER COLUMN ativo SET DEFAULT false;
ALTER TABLE products ALTER COLUMN ativo DROP DEFAULT;

-- Adicionar / remover NOT NULL
ALTER TABLE products ALTER COLUMN slug SET NOT NULL;
ALTER TABLE products ALTER COLUMN slug DROP NOT NULL;

-- Adicionar constraint com nome
ALTER TABLE products
  ADD CONSTRAINT preco_positivo CHECK (preco >= 0);

-- Remover constraint por nome
ALTER TABLE products
  DROP CONSTRAINT preco_positivo;

-- Mover tabela para outro schema
ALTER TABLE products SET SCHEMA estoque;
Performance & custo
ADD COLUMN com DEFAULT volátil (como now() ou gen_random_uuid()) reescreve toda a tabela no PG 10 e anteriores — operação lenta e blocante. A partir do PG 11, ADD COLUMN com DEFAULT de valor constante é instantâneo (metadado); com valor não constante ainda reescreve. Planeje com EXPLAIN e faça em janela de manutenção se a tabela for grande.

Capítulo 05

SELECT fundamental

O SELECT é o coração de SQL — a operação que extrai dados de uma ou mais tabelas e devolve uma relação. Este capítulo cobre os blocos essenciais: projeção de colunas, filtragem com WHERE, ordenação, paginação com LIMIT/OFFSET, remoção de duplicatas com DISTINCT, aliases e expressões inline. O encerramento mais importante é a ordem lógica de execução — entendê-la resolve a maioria das confusões sobre "por que não posso usar o alias aqui?".

# Projeção — escolher colunas

projecao.sql
-- Todas as colunas (evite em produção — frágil e ineficiente)
SELECT * FROM products;

-- Colunas específicas (preferido sempre)
SELECT id, nome, preco
FROM   products;

-- Expressão direta — sem tabela
SELECT 2 + 2;          -- → 4
SELECT now();           -- → timestamp atual
SELECT version();       -- → string de versão do PostgreSQL

-- Prefixar com nome da tabela (evita ambiguidade em queries com JOIN)
SELECT products.nome, products.preco
FROM   products;
Dica
SELECT * é problemático em código de produção: se a tabela ganhar uma coluna nova, a query começa a retornar dados inesperados. Em aplicações, liste sempre as colunas explicitamente. SELECT * é aceitável no psql para exploração interativa.

# Aliases — AS

aliases.sql
-- Alias de coluna
SELECT
  nome                          AS titulo,
  preco                         AS preco_brl,
  preco * 1.1                   AS preco_com_frete,
  upper(nome)                   AS nome_maiusculo
FROM products;

-- O AS é opcional (mas deixe explícito para clareza)

-- Alias de tabela (muito usado em JOINs)

FROM   products p;   -- p é o alias de products

SELECT p.nome
FROM   products AS p;

FROM products;

# WHERE — filtragem básica

O WHERE filtra linhas antes da projeção. Operadores de comparação e lógicos são cobertos em detalhe no Capítulo 6; aqui o foco é entender onde o WHERE se encaixa.

where_basico.sql
-- Filtragem simples
SELECT id, nome, preco
FROM   products
WHERE  preco < 100;

-- Múltiplas condições
SELECT *
FROM   products
WHERE  ativo AND estoque > 0 AND preco <= 500;

-- Filtrando por texto exato
SELECT *
FROM   orders
WHERE  status = 'pago';

-- IMPORTANTE: alias do SELECT não está disponível no WHERE
-- Esta query é inválida:
SELECT preco * 0.9 AS preco_desconto
FROM   products
WHERE  preco_desconto < 50;  -- ERRO: preco_desconto não existe aqui

-- Correto: repetir a expressão no WHERE
SELECT preco * 0.9 AS preco_desconto
FROM   products
WHERE  preco * 0.9 < 50;

# ORDER BY — ordenação

order_by.sql
-- Crescente (padrão) e decrescente
SELECT nome, preco
FROM   products
ORDER BY preco ASC;    -- ASC é o padrão — pode omitir

SELECT nome, preco
FROM   products
ORDER BY preco DESC;   -- mais caros primeiro

-- Múltiplas colunas: ordena pela 1ª, desempata pela 2ª
SELECT categoria_id, nome, preco
FROM   products
ORDER BY categoria_id ASC, preco DESC;

-- Ordenar por expressão
SELECT nome, preco, estoque
FROM   products
ORDER BY (preco * estoque) DESC;  -- valor total em estoque

-- ORDER BY pode referenciar alias do SELECT (exceção à regra geral)
SELECT nome, preco * 0.9 AS preco_desconto
FROM   products
ORDER BY preco_desconto DESC;   -- válido! ORDER BY é avaliado após SELECT

-- Controle de NULLs na ordenação
SELECT nome, categoria_id
FROM   products
ORDER BY categoria_id ASC NULLS LAST;    -- NULLs vão para o fim

SELECT nome, categoria_id
FROM   products
ORDER BY categoria_id DESC NULLS FIRST;  -- NULLs vão para o início

-- Padrão do PostgreSQL sem NULLS FIRST/LAST:
-- ASC → NULLs no final; DESC → NULLs no início

# LIMIT e OFFSET — paginação

limit_offset.sql
-- LIMIT: retorna no máximo N linhas
SELECT nome, preco
FROM   products
ORDER BY preco DESC
LIMIT  10;   -- top 10 mais caros

-- OFFSET: pula N linhas (paginação por página)
-- Página 1: LIMIT 10 OFFSET 0
-- Página 2: LIMIT 10 OFFSET 10
-- Página N: LIMIT 10 OFFSET (N-1) * 10
SELECT nome, preco
FROM   products
ORDER BY id
LIMIT  10 OFFSET 20;   -- página 3

-- Contar o total sem trazer as linhas (para informar "X resultados")
SELECT count(*) FROM products WHERE ativo;
Atenção
OFFSET em páginas grandes é lento. Para chegar na página 1000 de resultados, o banco ainda precisa varrer e descartar 9.990 linhas. Para paginação de alta performance, use cursor-based pagination: guarde o último id (ou outra coluna ordenada) visto e filtre com WHERE id > :ultimo_id ORDER BY id LIMIT 10.

# DISTINCT e DISTINCT ON

distinct.sql
-- DISTINCT: remove linhas duplicadas do resultado
SELECT DISTINCT status
FROM   orders;   -- lista de status únicos existentes

SELECT DISTINCT categoria_id
FROM   products
WHERE  ativo;

-- DISTINCT ON (expr): extensão PostgreSQL — retorna uma linha por grupo
-- "O produto mais caro de cada categoria"
SELECT DISTINCT ON (categoria_id)
  categoria_id,
  nome,
  preco
FROM   products
ORDER BY categoria_id, preco DESC;
-- Regra: a expressão do DISTINCT ON deve ser o prefixo do ORDER BY

-- "O pedido mais recente de cada cliente"
SELECT DISTINCT ON (user_id)
  user_id,
  id   AS pedido_id,
  criado_em
FROM   orders
ORDER BY user_id, criado_em DESC;
Nota
DISTINCT ON é uma extensão do PostgreSQL sem equivalente direto no SQL padrão. Para portabilidade, o mesmo resultado pode ser obtido com ROW_NUMBER() (window function do Capítulo 8) ou subquery. Em PostgreSQL, DISTINCT ON costuma ser mais legível e igualmente eficiente.

# Ordem lógica de execução

Esta é a peça mais importante do capítulo. O PostgreSQL processa os blocos de uma query em uma ordem diferente da que você os escreve. Entender isso explica erros como "column does not exist" ao usar alias no WHERE e por que HAVING filtra depois do GROUP BY.

ordem_logica.sql
-- Você ESCREVE nesta ordem:
SELECT   ...          -- 6. projeção e cálculo de expressões/aliases
FROM     ...          -- 1. identifica as tabelas (e aplica JOINs)
WHERE    ...          -- 2. filtra linhas individuais
GROUP BY ...          -- 3. agrupa linhas
HAVING   ...          -- 4. filtra grupos
ORDER BY ...          -- 7. ordena o resultado (já pode usar alias do SELECT)
LIMIT/OFFSET ...     -- 8. pagina o resultado

-- O banco EXECUTA nesta ordem:
-- 1. FROM (+ JOINs)  → todas as linhas candidatas
-- 2. WHERE           → filtra linhas (sem agregação)
-- 3. GROUP BY        → forma grupos
-- 4. HAVING          → filtra grupos (pode usar agregações)
-- 5. SELECT (WINDOW) → avalia window functions
-- 6. SELECT          → projeta colunas e calcula aliases
-- 7. DISTINCT        → remove duplicatas
-- 8. ORDER BY        → ordena (pode referenciar alias do SELECT)
-- 9. LIMIT/OFFSET    → pagina
ordem_logica_exemplos.sql
-- Por que alias NÃO funciona no WHERE: WHERE é avaliado antes do SELECT
SELECT preco * 0.9 AS desconto
FROM   products
WHERE  desconto < 50;     -- ERRO: "desconto" ainda não existe

-- Por que alias FUNCIONA no ORDER BY: ORDER BY é avaliado depois do SELECT
SELECT preco * 0.9 AS desconto
FROM   products
ORDER BY desconto;         -- OK

-- Por que HAVING pode usar COUNT mas WHERE não
SELECT   user_id, count(*) AS total_pedidos
FROM     orders
WHERE    status = 'pago'         -- filtra linhas (antes do GROUP BY)
GROUP BY user_id
HAVING   count(*) >= 3;          -- filtra grupos (depois do GROUP BY)

Capítulo 06

Filtragem e operadores

Um bom WHERE faz o banco trabalhar menos — traz só os dados necessários, permite usar índices e evita processamento desnecessário na aplicação. Este capítulo cataloga os operadores de comparação, lógicos e de conjunto (IN, BETWEEN, LIKE/ILIKE), os operadores de nulidade (IS NULL), as funções de tratamento de NULL (COALESCE, NULLIF) e o CASE. O fio condutor é a lógica de três valores do SQL — sem entendê-la, resultados com NULL surpreendem constantemente.

# Lógica de três valores e NULL

Em SQL, toda comparação produz um de três resultados: TRUE, FALSE ou NULL (desconhecido). O WHERE só inclui linhas onde a condição é TRUE — linhas onde ela resulta em NULL são silenciosamente excluídas. Essa é a raiz da maioria das surpresas com NULL.

three_valued_logic.sql
-- NULL em comparações: resultado é sempre NULL (não TRUE nem FALSE)
SELECT NULL =  NULL;   -- → NULL (não TRUE!)
SELECT NULL <> NULL;   -- → NULL
SELECT NULL =  1;      -- → NULL
SELECT NULL >  0;      -- → NULL

-- Tabela verdade do AND com NULL
-- TRUE  AND NULL → NULL   (poderia ser true, não sabemos)
-- FALSE AND NULL → FALSE  (false domina)
-- NULL  AND NULL → NULL

-- Tabela verdade do OR com NULL
-- TRUE  OR NULL  → TRUE   (true domina)
-- FALSE OR NULL  → NULL
-- NULL  OR NULL  → NULL

-- Consequência prática: esta query NÃO retorna produtos sem categoria
SELECT * FROM products WHERE categoria_id <> 3;
-- Linhas onde categoria_id IS NULL são excluídas silenciosamente!

-- Correto: incluir o caso NULL explicitamente
SELECT * FROM products
WHERE categoria_id <> 3 OR categoria_id IS NULL;

# Operadores de comparação

comparacao.sql
-- Igualdade e diferença
SELECT * FROM orders  WHERE status =  'pago';
SELECT * FROM orders  WHERE status <> 'cancelado';   -- padrão SQL
SELECT * FROM orders  WHERE status != 'cancelado';   -- alias, funciona no PG

-- Comparações numéricas e de data
SELECT * FROM products WHERE preco     >  100;
SELECT * FROM products WHERE preco     >= 100;
SELECT * FROM products WHERE preco     <  50;
SELECT * FROM products WHERE preco     <= 50;
SELECT * FROM orders  WHERE criado_em >  '2025-01-01'::timestamptz;

-- IS DISTINCT FROM / IS NOT DISTINCT FROM: compara com suporte a NULL
SELECT * FROM products
WHERE categoria_id IS DISTINCT FROM 3;
-- Equivale a: categoria_id <> 3 OR categoria_id IS NULL
-- O operador mais seguro para "diferente" quando NULLs importam

# Operadores lógicos — AND, OR, NOT

logicos.sql
-- AND: todas as condições devem ser TRUE
SELECT * FROM products
WHERE ativo AND estoque > 0 AND preco <= 200;

-- OR: pelo menos uma condição deve ser TRUE
SELECT * FROM orders
WHERE status = 'pendente' OR status = 'pago';

-- NOT: inverte o resultado (TRUE → FALSE, FALSE → TRUE, NULL → NULL)
SELECT * FROM products WHERE NOT ativo;

-- Parênteses mudam a precedência: AND tem precedência sobre OR
-- Esta query é ambígua sem parênteses:
SELECT * FROM orders
WHERE user_id = 1 AND status = 'pago'
   OR user_id = 2 AND status = 'pago';  -- AND agrupa primeiro

-- Parênteses explícitos — sempre mais claro:
SELECT * FROM orders
WHERE (user_id = 1 OR user_id = 2)
  AND status = 'pago';

# IN e NOT IN

in_notin.sql
-- IN: equivale a uma série de ORs — muito mais legível
SELECT * FROM orders
WHERE status IN ('pendente', 'pago', 'enviado');

SELECT * FROM products
WHERE categoria_id IN (1, 3, 7);

-- NOT IN: todos os valores da lista devem ser diferentes
SELECT * FROM orders
WHERE status NOT IN ('cancelado', 'devolvido');

-- ARMADILHA: NOT IN com NULL na lista → resultado vazio!
-- Se a subquery retornar NULL, NOT IN falha silenciosamente
SELECT * FROM products
WHERE categoria_id NOT IN (1, NULL);
-- Retorna 0 linhas! NULL contamina o NOT IN inteiro.
-- Use NOT EXISTS ou filtre NULLs antes (Capítulo 9)

-- IN com subquery
SELECT * FROM products
WHERE categoria_id IN (
  SELECT id FROM categories WHERE nome ILIKE '%eletro%'
);
Atenção
NOT IN com uma lista que pode conter NULL (especialmente quando vem de uma subquery) retorna zero resultados. Prefira NOT EXISTS para subqueries (Capítulo 9) ou use <> ALL(ARRAY[...]) quando a lista é fixa e não contém NULL.

# BETWEEN

between.sql
-- BETWEEN: inclusive nas duas extremidades
SELECT * FROM products
WHERE preco BETWEEN 50 AND 200;
-- Equivale a: preco >= 50 AND preco <= 200

-- Com datas: padrão para janelas de tempo
SELECT * FROM orders
WHERE criado_em BETWEEN '2025-01-01' AND '2025-01-31 23:59:59';

-- Preferível com datas: usar >= e < para evitar problemas de inclusão de horário
SELECT * FROM orders
WHERE  criado_em >= '2025-01-01'::timestamptz
  AND  criado_em <  '2025-02-01'::timestamptz;

-- NOT BETWEEN
SELECT * FROM products
WHERE preco NOT BETWEEN 50 AND 200;   -- preco < 50 OR preco > 200

-- BETWEEN SYMMETRIC: não importa a ordem dos limites (PG extension)
SELECT 5 BETWEEN SYMMETRIC 10 AND 1;   -- → TRUE (normaliza a ordem)

# LIKE, ILIKE e pattern matching

like_ilike.sql
-- LIKE: case-sensitive, padrões com % (qualquer sequência) e _ (um char)
SELECT * FROM products WHERE nome LIKE  'Camiseta%';  -- começa com "Camiseta"
SELECT * FROM products WHERE nome LIKE  '%preta%';    -- contém "preta"
SELECT * FROM products WHERE nome LIKE  '%_M';        -- termina com qualquer char + "M"

-- ILIKE: case-insensitive (extensão PostgreSQL — não existe no SQL padrão)
SELECT * FROM products WHERE nome ILIKE '%camiseta%';  -- encontra "Camiseta", "CAMISETA"
SELECT * FROM users    WHERE email ILIKE '%@gmail.com';

-- NOT LIKE / NOT ILIKE
SELECT * FROM products WHERE nome NOT ILIKE '%teste%';

-- Escapar os metacaracteres % e _ com ESCAPE
SELECT * FROM products
WHERE nome LIKE '100\%' ESCAPE '\';   -- busca literalmente "100%"

-- SIMILAR TO: padrões estilo POSIX ERE (mais poderoso que LIKE, menos que regexp)
SELECT * FROM products
WHERE nome SIMILAR TO '(Camiseta|Calça)%';

-- Regexp: operadores ~ e ~* (case-insensitive)
SELECT * FROM users
WHERE email ~  '^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$';  -- valida e-mail
WHERE nome  ~* 'silva|santos';                              -- case-insensitive
Performance & custo
LIKE 'prefixo%' pode usar índice B-tree (busca por prefixo). LIKE '%sufixo' ou LIKE '%meio%' não usam índice B-tree — fazem seq scan. Para busca por qualquer parte do texto, use Full-Text Search com índice GIN (Capítulo 19) ou pg_trgm com índice GIN/GiST. ILIKE também não usa índice B-tree padrão — precisa de índice lower(coluna) ou pg_trgm.

# IS NULL e IS NOT NULL

is_null.sql
-- A ÚNICA forma correta de testar NULL — nunca use = NULL
SELECT * FROM products WHERE categoria_id IS NULL;      -- sem categoria
SELECT * FROM products WHERE categoria_id IS NOT NULL;  -- com categoria

-- = NULL nunca funciona (retorna NULL, não TRUE)
SELECT * FROM products WHERE categoria_id = NULL;  -- NUNCA retorna linhas

-- Padrão: buscar e também incluir NULLs
SELECT * FROM products
WHERE categoria_id = 5 OR categoria_id IS NULL;

-- IS TRUE / IS FALSE / IS UNKNOWN: testa booleano com suporte a NULL
SELECT * FROM products WHERE ativo IS TRUE;
SELECT * FROM products WHERE ativo IS NOT FALSE;  -- inclui NULL

# COALESCE e NULLIF

coalesce_nullif.sql
-- COALESCE(a, b, c, ...): retorna o primeiro valor não-NULL da lista
SELECT
  nome,
  coalesce(descricao, 'Sem descrição')     AS descricao,
  coalesce(categoria_id::text, 'N/A')        AS categoria
FROM products;

-- COALESCE em cálculos: evita NULL se propagar
SELECT
  nome,
  coalesce(desconto_pct, 0) AS desconto,
  preco * (1 - coalesce(desconto_pct, 0) / 100.0) AS preco_final
FROM products;

-- NULLIF(a, b): retorna NULL se a = b, senão retorna a
-- Útil para evitar divisão por zero
SELECT
  total_vendas / nullif(quantidade_dias, 0)  AS media_diaria
FROM relatorio;
-- Se quantidade_dias = 0, NULLIF retorna NULL e a divisão vira NULL
-- em vez de gerar "division by zero" e abortar a query

-- Converter string vazia em NULL
SELECT nullif(trim(campo_texto), '') FROM importacao;

-- GREATEST e LEAST: mínimo/máximo entre valores (ignoram NULL)
SELECT greatest(10, 20, 5);    -- → 20
SELECT least(10, 20, 5);       -- → 5
SELECT greatest(preco, 10) FROM products;  -- preço mínimo garantido de 10

Capítulo 07

JOINs — o modelo mental da junção

JOIN é onde o modelo relacional revela seu poder — e onde mais gente se perde. A confusão quase sempre vem de tentar memorizar diagramas de Venn em vez de entender o que uma junção realmente faz linha a linha. Este capítulo constrói o modelo mental correto: junção como produto cartesiano filtrado, depois cada tipo (INNER, LEFT, RIGHT, FULL, CROSS), o papel exato dos NULLs, self-joins, a diferença real entre ON e USING, semi/anti-joins e por que a ordem em que você escreve as tabelas raramente importa.

# O que uma junção realmente faz

Esqueça os diagramas de Venn por um momento. A definição operacional de qualquer JOIN é mecânica e exata: combine cada linha da tabela A com cada linha da tabela B, depois mantenha apenas as combinações que satisfazem a condição. Isso é literalmente um produto cartesiano seguido de um filtro.

modelo_mental.sql
-- Estas duas queries são logicamente IDÊNTICAS:

-- 1. JOIN explícito (forma moderna, sempre prefira esta)
SELECT u.nome, o.id
FROM   users u
JOIN   orders o ON o.user_id = u.id;

-- 2. Produto cartesiano + filtro (a "verdade" por baixo do JOIN)
SELECT u.nome, o.id
FROM   users u, orders o      -- vírgula = CROSS JOIN (todas as combinações)
WHERE  o.user_id = u.id;       -- o filtro que dá sentido à combinação

-- Se users tem 1.000 linhas e orders tem 5.000:
--   produto cartesiano   = 5.000.000 combinações conceituais
--   após o filtro ON     = ~5.000 linhas (as que casam)
-- O planner NÃO materializa os 5 milhões — usa hash/merge/nested loop.
-- Mas o RESULTADO é o mesmo que se materializasse. Esse é o modelo.

Com esse modelo na cabeça, todo tipo de JOIN se resume a uma única pergunta: "o que acontece com as linhas de A que não encontraram par em B?". INNER as descarta. LEFT as preserva preenchendo as colunas de B com NULL. RIGHT faz o espelho. FULL preserva os órfãos dos dois lados. É só isso — o resto é consequência.

# INNER JOIN — só o que casa

O INNER JOIN mantém apenas as linhas onde a condição é TRUE em ambos os lados. Linhas sem par desaparecem do resultado. É o join padrão — escrever apenas JOIN significa INNER JOIN.

inner_join.sql
-- Pedidos com o nome do cliente. Pedidos sem cliente válido somem;
-- clientes sem nenhum pedido também não aparecem.
SELECT
  o.id          AS pedido,
  u.nome        AS cliente,
  o.status,
  o.criado_em
FROM   orders o
INNER JOIN users u ON u.id = o.user_id
ORDER BY o.criado_em DESC;

-- Múltiplos JOINs: o resultado de um JOIN vira entrada do próximo.
-- "Itens vendidos com cliente, produto e categoria"
SELECT
  u.nome        AS cliente,
  p.nome        AS produto,
  c.nome        AS categoria,
  oi.quantidade,
  oi.preco_unit
FROM   order_items oi
JOIN   orders     o ON o.id          = oi.order_id
JOIN   users      u ON u.id          = o.user_id
JOIN   products   p ON p.id          = oi.product_id
JOIN   categories c ON c.id          = p.categoria_id;
Nota
Numa cadeia de INNER JOINs, uma linha só sobrevive se casar em todos os joins. Se um produto tem categoria_id NULL, o JOIN categories elimina aquela linha inteira do resultado — mesmo que cliente e pedido estivessem corretos. Esse efeito cascata é a causa #1 de "sumiram linhas que eu esperava".

# LEFT JOIN — preservar a tabela da esquerda

O LEFT JOIN (ou LEFT OUTER JOIN) mantém todas as linhas da tabela à esquerda. Quando não há par à direita, as colunas da direita vêm como NULL. É o join mais útil na prática — sempre que a pergunta é "todos os X, com seus Y se houver".

left_join.sql
-- TODOS os clientes, mesmo os que nunca compraram
SELECT
  u.id,
  u.nome,
  o.id AS pedido_id,   -- NULL para quem nunca comprou
  o.status
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
ORDER BY u.id;

-- Contar pedidos por cliente, incluindo zero (padrão muito comum)
SELECT
  u.nome,
  count(o.id) AS total_pedidos   -- count(o.id) ignora NULL → 0 para sem pedidos
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.nome
ORDER BY total_pedidos DESC;

A armadilha: filtro da tabela direita no WHERE vs no ON

Esta é a sutileza mais importante do capítulo inteiro. Colocar uma condição da tabela direita no WHERE de um LEFT JOIN silenciosamente o transforma em INNER JOIN — porque NULL = 'pago' é NULL (falso), e o WHERE descarta essas linhas.

left_join_armadilha.sql
-- ❌ ERRADO: vira INNER JOIN sem você perceber
-- Clientes sem pedidos têm o.status = NULL; NULL = 'pago' é falso;
-- o WHERE então os elimina. Resultado: só clientes COM pedidos pagos.
SELECT u.nome, o.id
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.status = 'pago';       -- mata o LEFT JOIN

-- ✅ CORRETO (intenção A): a condição faz parte da junção
-- "Todos os clientes; ao lado, apenas os pedidos pagos (ou NULL)"
SELECT u.nome, o.id
FROM   users u
LEFT JOIN orders o
       ON o.user_id = u.id AND o.status = 'pago';

-- ✅ CORRETO (intenção B): quero de fato só quem tem pedido pago
-- Então um INNER JOIN expressa a intenção honestamente
SELECT u.nome, o.id
FROM   users u
JOIN   orders o ON o.user_id = u.id
WHERE  o.status = 'pago';
Atenção
Regra prática: condições sobre a tabela preservada (a da esquerda, num LEFT JOIN) podem ir no WHERE. Condições sobre a tabela opcional (a da direita) que devem permitir NULL precisam ir no ON. Se a condição da tabela opcional vai no WHERE, você está pedindo, na prática, um INNER JOIN — então escreva INNER JOIN e deixe a intenção explícita.

# RIGHT JOIN e FULL JOIN

RIGHT JOIN é o espelho do LEFT: preserva a tabela da direita. Na prática quase ninguém usa RIGHT JOIN — basta inverter a ordem das tabelas e usar LEFT, que é mais legível. FULL JOIN preserva os órfãos dos dois lados.

right_full_join.sql
-- RIGHT JOIN: todos os pedidos, mesmo os com user_id inválido
-- (raro — só faz sentido se a FK puder estar quebrada)
SELECT u.nome, o.id
FROM   users u
RIGHT JOIN orders o ON o.user_id = u.id;
-- Idêntico, mas mais legível, como LEFT JOIN invertendo as tabelas:
SELECT u.nome, o.id
FROM   orders o
LEFT JOIN users u ON u.id = o.user_id;

-- FULL OUTER JOIN: preserva linhas sem par dos dois lados
-- Ótimo para reconciliação: o que existe num lado e não no outro
SELECT
  c.id   AS categoria_id,
  c.nome AS categoria,
  p.id   AS produto_id,
  p.nome AS produto
FROM   categories c
FULL OUTER JOIN products p ON p.categoria_id = c.id
WHERE  c.id IS NULL OR p.id IS NULL;
-- c.id IS NULL → produtos órfãos (categoria inexistente)
-- p.id IS NULL → categorias sem nenhum produto

# CROSS JOIN — produto cartesiano explícito

cross_join.sql
-- Todas as combinações — sem condição. Use com intenção, não por acidente.
-- "Grade de tamanhos × cores para gerar SKUs"
SELECT t.tamanho, c.cor
FROM   (VALUES ('P'), ('M'), ('G')) AS t(tamanho)
CROSS JOIN (VALUES ('preto'), ('branco')) AS c(cor);
-- 3 × 2 = 6 linhas: (P,preto) (P,branco) (M,preto) ...

-- Gerar série de datas para um relatório (todos os dias do mês)
SELECT d::date
FROM   generate_series(
         '2025-01-01'::date,
         '2025-01-31'::date,
         '1 day'::interval
       ) AS d;
-- Combinado com CROSS JOIN: gera "todo cliente × todo dia" para
-- relatórios densos sem buracos (Capítulo 8)
Performance & custo
Um CROSS JOIN acidental (esquecer a condição, ou um ON que nunca casa) gera uma explosão combinatória: duas tabelas de 100 mil linhas viram 10 bilhões. Sintoma clássico: query que "trava" e EXPLAIN mostrando Nested Loop sem condição de junção. Sempre verifique no EXPLAIN (Capítulo 20) se o número de linhas estimado faz sentido.

# ON vs USING vs NATURAL

on_using_natural.sql
-- ON: condição explícita, qualquer expressão — sempre a forma segura
SELECT *
FROM   orders o
JOIN   users u ON u.id = o.user_id;

-- USING: atalho quando as colunas têm o MESMO nome nas duas tabelas
-- Colapsa a coluna comum em uma só (não vem duplicada no SELECT *)
SELECT *
FROM   order_items oi
JOIN   orders o USING (order_id);   -- exige order_id nas duas tabelas
-- Com USING, referencie a coluna comum SEM prefixo: order_id (não o.order_id)

-- NATURAL JOIN: junta automaticamente por TODAS as colunas de mesmo nome
-- PERIGOSO: se alguém adicionar uma coluna "criado_em" nas duas tabelas,
-- o join muda silenciosamente. Evite NATURAL JOIN em produção.
SELECT * FROM orders NATURAL JOIN users;   -- frágil — não use

# Self-join — uma tabela consigo mesma

Nada impede juntar uma tabela com ela mesma — basta usar dois aliases diferentes. É a técnica para hierarquias (gerente/subordinado), comparações entre linhas e relações de mesmo tipo.

self_join.sql
-- Suponha users com coluna indicado_por (FK para o próprio users.id)
-- "Cada cliente e quem o indicou"
SELECT
  u.nome      AS cliente,
  indicador.nome AS indicado_por
FROM   users u
LEFT JOIN users indicador ON indicador.id = u.indicado_por;
-- LEFT JOIN: clientes sem indicador ainda aparecem (indicado_por NULL)

-- Pares de produtos da mesma categoria (sem repetir o par invertido)
SELECT
  a.nome AS produto_a,
  b.nome AS produto_b,
  a.categoria_id
FROM   products a
JOIN   products b
       ON b.categoria_id = a.categoria_id
      AND b.id > a.id;   -- b.id > a.id evita (X,Y) e (Y,X) duplicados e (X,X)

# Semi-join e anti-join

Às vezes você quer saber apenas se existe correspondência, sem trazer os dados do outro lado. Trazer via JOIN e depois DISTINCT funciona, mas EXISTS/NOT EXISTS expressa a intenção com mais clareza e costuma ser mais eficiente.

semi_anti_join.sql
-- SEMI-JOIN: "clientes que TÊM pelo menos um pedido"
-- (sem multiplicar linhas nem precisar de DISTINCT)
SELECT u.id, u.nome
FROM   users u
WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- ANTI-JOIN: "clientes que NUNCA compraram"
SELECT u.id, u.nome
FROM   users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- Anti-join alternativo via LEFT JOIN + IS NULL (mesmo resultado)
SELECT u.id, u.nome
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.id IS NULL;   -- nenhum par encontrado → órfão
-- O planner do PostgreSQL costuma gerar o MESMO plano (Anti Join)
-- para ambas as formas. Prefira NOT EXISTS pela clareza e por ser
-- imune à armadilha do NOT IN com NULL (Capítulo 6).

# Ordem de junção e o planner

Uma dúvida comum: "importa em que ordem eu escrevo as tabelas no JOIN?". Para INNER JOIN, logicamente não — o resultado é idêntico independentemente da ordem. O planner do PostgreSQL reordena livremente as junções internas buscando o plano mais barato; ele decide qual tabela varrer primeiro, qual algoritmo de junção usar e quando aplicar cada filtro.

join_order.sql
-- Estas três produzem o MESMO resultado e, frequentemente, o MESMO plano:
FROM orders o JOIN users u ON ... JOIN order_items oi ON ...
FROM users u JOIN orders o ON ... JOIN order_items oi ON ...
FROM order_items oi JOIN orders o ON ... JOIN users u ON ...

-- Exceções importantes:
-- 1. OUTER JOINs (LEFT/RIGHT/FULL) NÃO são livremente reordenáveis —
--    a ordem afeta o resultado (qual lado é preservado).
-- 2. Com muitas tabelas (> geqo_threshold, padrão 12) o planner usa
--    busca genética e pode não achar o ótimo global.

-- Diagnosticar a ordem real escolhida pelo planner:
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.nome, count(*)
FROM   users u
JOIN   orders o ON o.user_id = u.id
GROUP BY u.nome;
-- Procure: Hash Join / Merge Join / Nested Loop e a ordem das tabelas
Performance & custo
Os três algoritmos de junção do PostgreSQL têm perfis distintos: Nested Loop brilha quando um lado é pequeno e o outro tem índice na coluna de junção; Hash Join é o cavalo de batalha para juntar conjuntos grandes sem ordenação útil; Merge Join ganha quando ambos os lados já vêm ordenados (ex.: por índice). Você não escolhe o algoritmo — garante boas condições (índices nas FKs, estatísticas atualizadas) e lê a escolha no EXPLAIN.
Dica
Quase toda coluna usada em JOIN ... ON deveria ter um índice — tipicamente as chaves estrangeiras. O PostgreSQL cria índice automático para PRIMARY KEY e UNIQUE, mas não para FOREIGN KEY. Indexar orders.user_id, order_items.order_id e order_items.product_id costuma transformar joins lentos em instantâneos (detalhe no Capítulo 15).

Capítulo 08

Agregação, GROUP BY e window functions

Agregação é como SQL responde "quantos?", "qual o total?", "qual a média?". O conceito é simples, mas duas confusões persistem: a relação exata entre GROUP BY e as colunas do SELECT, e a diferença entre agregar (colapsar linhas) e usar window functions (calcular sobre vizinhas sem colapsar). Este capítulo desenvolve o modelo mental de "dobrar linhas em grupos", percorre as funções de agregação, HAVING, FILTER, os agregados multidimensionais (ROLLUP/CUBE) e fecha com window functions — talvez a ferramenta mais subutilizada do SQL.

# O modelo mental: dobrar linhas em grupos

Uma função de agregação recebe muitas linhas e devolve uma. GROUP BY particiona as linhas em grupos pela(s) coluna(s) indicada(s); cada grupo então colapsa em uma única linha de saída, e as funções de agregação são calculadas dentro de cada grupo. Visualize como dobrar uma folha: cada dobra junta um conjunto de linhas em uma só.

modelo_agregacao.sql
-- Sem GROUP BY: a tabela INTEIRA é um único grupo → uma linha de saída
SELECT count(*), avg(preco), max(preco) FROM products;
-- → 1 linha: (qtd_total, preço_médio, preço_máximo)

-- Com GROUP BY: um grupo por categoria → uma linha POR categoria
SELECT
  categoria_id,
  count(*)       AS qtd_produtos,
  avg(preco)     AS preco_medio,
  max(preco)     AS mais_caro
FROM   products
GROUP BY categoria_id;
-- → N linhas: uma por valor distinto de categoria_id

Disso decorre a regra que mais gera erros: toda coluna no SELECT precisa ou estar no GROUP BY, ou estar dentro de uma função de agregação. O motivo é lógico, não arbitrário: depois de colapsar um grupo de 50 produtos numa linha, qual dos 50 nomes o banco deveria mostrar? A pergunta não tem resposta — então o PostgreSQL recusa a query.

regra_group_by.sql
-- ❌ ERRO: column "products.nome" must appear in the GROUP BY clause
SELECT categoria_id, nome, count(*)
FROM   products
GROUP BY categoria_id;
-- "nome" não está no GROUP BY nem agregado. Qual nome mostrar do grupo?

-- ✅ Opção A: agregue o nome (ex.: liste todos)
SELECT categoria_id, string_agg(nome, ', ') AS produtos, count(*)
FROM   products
GROUP BY categoria_id;

-- ✅ Opção B: adicione nome ao GROUP BY (grupos mais finos)
SELECT categoria_id, nome, count(*)
FROM   products
GROUP BY categoria_id, nome;

-- Exceção: colunas funcionalmente dependentes da PK no GROUP BY
-- são permitidas (PG deduz que são únicas por grupo)
SELECT u.id, u.nome, count(o.id)
FROM   users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;   -- u.nome OK: depende de u.id (PK)

# As funções de agregação

funcoes_agregacao.sql
-- count(*)    → conta TODAS as linhas do grupo (inclui NULLs)
-- count(col)  → conta linhas onde col NÃO é NULL
-- count(DISTINCT col) → valores distintos não-NULL
SELECT
  count(*)                      AS total_linhas,
  count(categoria_id)           AS com_categoria,
  count(DISTINCT categoria_id)  AS categorias_distintas
FROM products;

-- sum / avg / min / max — ignoram NULL automaticamente
SELECT
  sum(quantidade * preco_unit) AS receita_total,
  avg(preco_unit)              AS ticket_medio,
  min(preco_unit)              AS menor_preco,
  max(preco_unit)              AS maior_preco
FROM order_items;

-- Agregados de coleção: juntar valores de um grupo
SELECT
  categoria_id,
  string_agg(nome, ', ' ORDER BY nome) AS lista,
  array_agg(id ORDER BY preco DESC)     AS ids_por_preco,
  jsonb_agg(jsonb_build_object('id', id, 'nome', nome)) AS json
FROM   products
GROUP BY categoria_id;

-- Agregados estatísticos
SELECT
  stddev(preco)                              AS desvio_padrao,
  percentile_cont(0.5) WITHIN GROUP (ORDER BY preco) AS mediana,
  mode() WITHIN GROUP (ORDER BY categoria_id)        AS categoria_mais_comum
FROM products;
Atenção
count(*) e count(coluna) não são equivalentes. count(*) conta linhas; count(coluna) conta valores não-NULL daquela coluna. Num LEFT JOIN, use count(tabela_direita.id) — não count(*) — para que clientes sem pedidos contem 0 em vez de 1 (a linha existe por causa do LEFT JOIN, mas o id do pedido é NULL).

# HAVING — filtrar grupos

WHERE filtra linhas antes de agrupar; HAVING filtra grupos depois de agregar. Essa ordem (revista no Capítulo 5) explica por que HAVING pode usar count() e WHERE não.

having.sql
-- "Clientes com 3+ pedidos pagos e receita acima de R$ 1000"
SELECT
  o.user_id,
  count(*)                        AS qtd_pedidos,
  sum(o.total)                     AS receita
FROM   orders o
WHERE  o.status = 'pago'            -- filtra LINHAS antes de agrupar
GROUP BY o.user_id
HAVING count(*) >= 3              -- filtra GRUPOS após agregar
   AND sum(o.total) > 1000
ORDER BY receita DESC;

-- Erro comum: tentar usar HAVING onde WHERE bastaria (menos eficiente)
-- Se o filtro é sobre uma coluna NÃO agregada, use WHERE — ele reduz
-- o volume ANTES de agrupar (mais rápido).

# FILTER — agregação condicional

A cláusula FILTER permite aplicar diferentes condições a diferentes agregados na mesma query — eliminando a velha gambiarra de SUM(CASE WHEN ... THEN 1 ELSE 0 END).

filter.sql
-- "Por cliente: total de pedidos, quantos pagos, quantos cancelados,
--  e a receita só dos pagos" — tudo em uma passada
SELECT
  user_id,
  count(*)                                  AS total,
  count(*) FILTER (WHERE status = 'pago')      AS pagos,
  count(*) FILTER (WHERE status = 'cancelado') AS cancelados,
  sum(total) FILTER (WHERE status = 'pago')    AS receita_paga
FROM   orders
GROUP BY user_id;

-- Equivalente antigo com CASE (ainda válido, mas FILTER é mais limpo):
-- count(*) FILTER (WHERE status='pago')
--   ≡  sum(CASE WHEN status='pago' THEN 1 ELSE 0 END)

-- Pivot manual: contagem por status em colunas
SELECT
  date_trunc('month', criado_em)                  AS mes,
  count(*) FILTER (WHERE status = 'pago')      AS pagos,
  count(*) FILTER (WHERE status = 'pendente')  AS pendentes
FROM   orders
GROUP BY date_trunc('month', criado_em)
ORDER BY mes;

# GROUPING SETS, ROLLUP e CUBE

Às vezes você precisa de subtotais e totais gerais junto com os agrupamentos detalhados — um relatório com "total por categoria" e "total geral" na mesma saída. Em vez de várias queries com UNION ALL, o PostgreSQL oferece agrupamentos multidimensionais.

grouping_sets.sql
-- ROLLUP: hierarquia com subtotais — (cat,status), (cat), ()
SELECT
  categoria_id,
  status,
  sum(total) AS receita
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.id
JOIN   products p    ON p.id = oi.product_id
GROUP BY ROLLUP (categoria_id, status);
-- Linhas com status=NULL = subtotal da categoria
-- Linha com categoria_id=NULL e status=NULL = total geral

-- CUBE: TODAS as combinações de subtotais
-- (cat,status), (cat), (status), ()
SELECT categoria_id, status, sum(total)
FROM   orders o JOIN order_items oi ON oi.order_id = o.id
                JOIN products p ON p.id = oi.product_id
GROUP BY CUBE (categoria_id, status);

-- GROUPING SETS: você escolhe EXATAMENTE quais agrupamentos quer
SELECT categoria_id, status, sum(total)
FROM   orders o JOIN order_items oi ON oi.order_id = o.id
                JOIN products p ON p.id = oi.product_id
GROUP BY GROUPING SETS (
  (categoria_id, status),  -- detalhe
  (categoria_id),          -- subtotal por categoria
  ()                       -- total geral
);

-- GROUPING() distingue "NULL de subtotal" de "NULL de dado real"
SELECT
  CASE WHEN grouping(categoria_id) = 1 THEN 'TOTAL'
       ELSE categoria_id::text END AS categoria,
  sum(total)
FROM   orders o JOIN order_items oi ON oi.order_id = o.id
                JOIN products p ON p.id = oi.product_id
GROUP BY ROLLUP (categoria_id);

# Window functions — agregar sem colapsar

Aqui está a virada de chave conceitual. Uma função de agregação com GROUP BY colapsa o grupo numa linha. Uma window function calcula um valor "olhando" para um conjunto de linhas relacionadas, mas mantém todas as linhas individuais. A diferença é a cláusula OVER: ela diz "calcule este agregado, mas não dobre as linhas — anexe o resultado a cada uma".

window_conceito.sql
-- GROUP BY: 1 linha por categoria (linhas colapsadas)
SELECT categoria_id, avg(preco)
FROM   products
GROUP BY categoria_id;

-- OVER: TODAS as linhas + a média da categoria ao lado de cada uma
SELECT
  id,
  nome,
  categoria_id,
  preco,
  avg(preco) OVER (PARTITION BY categoria_id) AS media_categoria,
  preco - avg(preco) OVER (PARTITION BY categoria_id)
                                          AS diff_da_media
FROM   products;
-- Cada produto continua visível, agora COM a média da sua categoria
-- e quanto ele desvia dela. Impossível de fazer com GROUP BY puro.

PARTITION BY e ORDER BY dentro do OVER

window_ranking.sql
-- Ranking de produtos por preço DENTRO de cada categoria
SELECT
  categoria_id,
  nome,
  preco,
  row_number() OVER (PARTITION BY categoria_id ORDER BY preco DESC) AS posicao,
  rank()       OVER (PARTITION BY categoria_id ORDER BY preco DESC) AS rank_com_gaps,
  dense_rank() OVER (PARTITION BY categoria_id ORDER BY preco DESC) AS rank_sem_gaps,
  ntile(4)   OVER (PARTITION BY categoria_id ORDER BY preco DESC) AS quartil
FROM   products;
-- row_number: 1,2,3,4...  sempre único
-- rank:       1,1,3,4...  empates compartilham, pula posições
-- dense_rank: 1,1,2,3...  empates compartilham, sem pular

-- "Top 3 produtos mais caros por categoria" (padrão clássico)
SELECT * FROM (
  SELECT
    categoria_id, nome, preco,
    row_number() OVER (PARTITION BY categoria_id
                          ORDER BY preco DESC) AS rn
  FROM products
) ranked
WHERE rn <= 3;
-- O filtro precisa ser numa subquery: window functions são
-- avaliadas APÓS o WHERE (ordem lógica do Capítulo 5).

LAG, LEAD e somas acumuladas (frames)

window_frames.sql
-- LAG/LEAD: acessar a linha anterior/seguinte (sem self-join!)
-- "Receita mensal e variação vs o mês anterior"
WITH mensal AS (
  SELECT
    date_trunc('month', criado_em) AS mes,
    sum(total)                     AS receita
  FROM orders
  WHERE status = 'pago'
  GROUP BY 1
)
SELECT
  mes,
  receita,
  lag(receita) OVER (ORDER BY mes)              AS receita_mes_anterior,
  receita - lag(receita) OVER (ORDER BY mes)  AS variacao,
  round(100.0 * (receita - lag(receita) OVER (ORDER BY mes))
        / nullif(lag(receita) OVER (ORDER BY mes), 0), 1)
                                                  AS variacao_pct
FROM mensal
ORDER BY mes;

-- Soma acumulada (running total) via frame de janela
SELECT
  mes,
  receita,
  sum(receita) OVER (
    ORDER BY mes
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS receita_acumulada,
  avg(receita) OVER (
    ORDER BY mes
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
  ) AS media_movel_3m
FROM mensal;
-- O "frame" define QUAIS linhas entram no cálculo daquela linha:
-- UNBOUNDED PRECEDING..CURRENT ROW = tudo até aqui (acumulado)
-- 2 PRECEDING..CURRENT ROW = janela deslizante de 3 linhas

-- WINDOW nomeada: reutilizar a mesma janela em vários cálculos
SELECT
  nome, preco,
  rank()       OVER w,
  percent_rank() OVER w
FROM   products
WINDOW w AS (PARTITION BY categoria_id ORDER BY preco DESC);
PostgreSQL 16/17
O PostgreSQL 16 trouxe melhorias importantes de paralelização para agregações (Parallel Hash Aggregate mais agressivo) e para string_agg/array_agg em modo paralelo. O 16 também adicionou os agregados any_value() — útil quando você precisa de "qualquer valor do grupo" sem se importar qual, evitando colocar a coluna desnecessariamente no GROUP BY.
Dica
Regra para escolher: se a saída deve ter uma linha por grupo, use GROUP BY. Se deve manter todas as linhas e apenas anexar um cálculo contextual (ranking, média do grupo, total acumulado, valor da linha anterior), use uma window function. Tentar resolver "top-N por grupo" ou "comparar com a linha anterior" só com GROUP BY e self-joins é o caminho longo e lento.

Capítulo 09

Subqueries e CTEs

Toda subquery é uma query dentro de outra — mas onde ela aparece e se ela "enxerga" a query externa muda completamente seu comportamento. Este capítulo organiza o assunto pelo modelo mental certo: subquery como valor escalar, como conjunto, como tabela; correlacionada vs não-correlacionada; EXISTS/IN/ANY/ALL e suas armadilhas com NULL; CTEs (WITH) como blocos nomeados e legíveis; recursão para hierarquias e grafos; LATERAL para "para cada linha, rode esta query"; e a barreira de materialização que afeta o planner.

# Três formas de subquery, pelo formato do resultado

A pergunta que organiza tudo: quantas linhas e colunas a subquery devolve? A resposta determina onde ela pode aparecer.

formas_subquery.sql
-- 1. ESCALAR: 1 linha, 1 coluna → usável como um valor qualquer
SELECT
  nome,
  preco,
  preco - (SELECT avg(preco) FROM products) AS diff_media
FROM   products;
-- A subquery escalar pode ir no SELECT, WHERE, ORDER BY...
-- Se ela retornar mais de 1 linha: ERRO em tempo de execução.

-- 2. CONJUNTO (coluna): N linhas, 1 coluna → usável com IN/ANY/ALL
SELECT * FROM products
WHERE categoria_id IN (
  SELECT id FROM categories WHERE nome ILIKE '%eletro%'
);

-- 3. TABELA (derivada): N linhas, M colunas → usável no FROM
SELECT sub.categoria_id, sub.receita
FROM   (
  SELECT p.categoria_id, sum(oi.quantidade * oi.preco_unit) AS receita
  FROM   order_items oi
  JOIN   products p ON p.id = oi.product_id
  GROUP BY p.categoria_id
) AS sub                       -- toda subquery no FROM PRECISA de alias
WHERE  sub.receita > 10000;

# Correlacionada vs não-correlacionada

Esta distinção é o coração do desempenho de subqueries. Uma subquery não-correlacionada não menciona a query externa — pode ser executada uma única vez. Uma subquery correlacionada referencia colunas da query externa — conceitualmente, é reavaliada para cada linha externa.

correlacionada.sql
-- NÃO-correlacionada: independe da linha externa, roda 1 vez
SELECT nome, preco
FROM   products
WHERE  preco > (SELECT avg(preco) FROM products);
-- A média é calculada uma vez e reutilizada para todas as linhas.

-- CORRELACIONADA: a subquery usa p2.categoria_id da linha externa
-- "produtos acima da média da SUA PRÓPRIA categoria"
SELECT p1.nome, p1.preco, p1.categoria_id
FROM   products p1
WHERE  p1.preco > (
  SELECT avg(p2.preco)
  FROM   products p2
  WHERE  p2.categoria_id = p1.categoria_id   -- ← correlação
);
-- Modelo mental: "para cada p1, calcule a média da categoria dele".
-- O planner frequentemente reescreve isso para um JOIN/agregado
-- eficiente — mas o MODELO conceitual é "uma vez por linha externa".

-- A mesma intenção, muitas vezes mais eficiente, com window function:
SELECT nome, preco, categoria_id FROM (
  SELECT *, avg(preco) OVER (PARTITION BY categoria_id) AS m
  FROM products
) t
WHERE preco > m;
Performance & custo
Subqueries correlacionadas no SELECT são a fonte clássica do problema N+1 dentro do próprio banco: uma subquery escalar correlacionada na lista de seleção é avaliada por linha do resultado externo. Quase sempre dá para reescrever como JOIN + agregação ou window function, que o planner executa numa única varredura. Cheque no EXPLAIN (Capítulo 20): um SubPlan repetido milhares de vezes é o sintoma.

# EXISTS, IN, ANY e ALL

Os quatro testam pertencimento/existência, mas têm semânticas diferentes — sobretudo diante de NULL.

exists_in_any_all.sql
-- EXISTS: TRUE se a subquery retorna AO MENOS uma linha
-- (o SELECT interno é irrelevante; use SELECT 1 por convenção)
SELECT u.nome
FROM   users u
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id AND o.status = 'pago'
);
-- EXISTS para de varrer no primeiro acerto (short-circuit) e é imune
-- a NULL — o teste é "existe linha?", não "valor está na lista?".

-- IN: valor pertence ao conjunto retornado
SELECT * FROM products
WHERE categoria_id IN (SELECT id FROM categories WHERE ativa);

-- = ANY (...) é equivalente a IN
SELECT * FROM products
WHERE categoria_id = ANY(SELECT id FROM categories WHERE ativa);

-- ANY/ALL com outros operadores (impossível com IN)
-- "produtos mais caros que TODOS os da categoria 3"
SELECT * FROM products
WHERE preco > ALL(SELECT preco FROM products WHERE categoria_id = 3);

-- "produtos mais caros que ALGUM da categoria 3"
SELECT * FROM products
WHERE preco > ANY(SELECT preco FROM products WHERE categoria_id = 3);
Atenção
A armadilha do NOT IN com NULL (Capítulo 6) é ainda mais perigosa com subqueries: se a subquery de um NOT IN retornar uma única linha NULL, a expressão inteira vira NULL e a query retorna zero linhas, silenciosamente. Use sempre NOT EXISTS para anti-joins — ele tem a semântica correta e o planner gera um plano Anti Join eficiente.
not_in_vs_not_exists.sql
-- ❌ PERIGOSO: se algum user_id em orders for NULL, retorna 0 linhas
SELECT * FROM users u
WHERE u.id NOT IN (SELECT user_id FROM orders);

-- ✅ CORRETO: NOT EXISTS é imune a NULL e expressa a intenção
SELECT * FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);

# CTEs — WITH como bloco nomeado

Uma CTE (Common Table Expression) é uma subquery batizada com nome, declarada antes da query principal com WITH. Não muda o que é possível — muda a legibilidade: queries complexas viram uma sequência de passos nomeados, lidos de cima para baixo como um pipeline.

cte_basico.sql
-- Pipeline legível: cada CTE é um passo com nome de domínio
WITH receita_por_cliente AS (
  SELECT
    o.user_id,
    sum(oi.quantidade * oi.preco_unit) AS receita
  FROM   orders o
  JOIN   order_items oi ON oi.order_id = o.id
  WHERE  o.status = 'pago'
  GROUP BY o.user_id
),
classificados AS (
  SELECT
    user_id,
    receita,
    CASE
      WHEN receita >= 5000 THEN 'VIP'
      WHEN receita >= 1000 THEN 'Recorrente'
      ELSE                     'Eventual'
    END AS segmento
  FROM receita_por_cliente
)
SELECT
  c.segmento,
  count(*)        AS qtd_clientes,
  sum(c.receita) AS receita_total
FROM   classificados c
JOIN   users u ON u.id = c.user_id
GROUP BY c.segmento
ORDER BY receita_total DESC;

-- CTE de escrita: data-modifying CTE com RETURNING (Capítulo 10)
WITH arquivados AS (
  DELETE FROM orders
  WHERE  status = 'cancelado' AND criado_em < now() - '1 year'::interval
  RETURNING *
)
INSERT INTO orders_arquivo SELECT * FROM arquivados;

# WITH RECURSIVE — hierarquias e grafos

A recursão de CTEs resolve a classe de problemas que SQL plano não alcança: percorrer árvores e grafos de profundidade desconhecida — organogramas, categorias aninhadas, listas de materiais, "amigos de amigos". A estrutura é sempre a mesma: um termo âncora (ponto de partida) UNION ALL um termo recursivo que se refere à própria CTE.

with_recursive.sql
-- Categorias com auto-referência: categories(id, nome, parent_id)
-- "Toda a subárvore a partir da categoria raiz 1"
WITH RECURSIVE arvore AS (
  -- ÂNCORA: o ponto de partida (nível 0)
  SELECT id, nome, parent_id, 0 AS nivel
  FROM   categories
  WHERE  id = 1

  UNION ALL

  -- RECURSIVO: filhos do que já está em "arvore"
  SELECT c.id, c.nome, c.parent_id, a.nivel + 1
  FROM   categories c
  JOIN   arvore a ON c.parent_id = a.id
)
SELECT repeat('  ', nivel) || nome AS arvore_indentada, nivel
FROM   arvore
ORDER BY nivel, nome;

-- Caminho até a raiz (subir a hierarquia) + proteção contra ciclos
WITH RECURSIVE caminho AS (
  SELECT id, nome, parent_id,
         ARRAY[id]          AS visitados,
         nome::text             AS trilha
  FROM   categories WHERE id = 42

  UNION ALL

  SELECT p.id, p.nome, p.parent_id,
         c.visitados || p.id,
         p.nome || ' > ' || c.trilha
  FROM   categories p
  JOIN   caminho c ON p.id = c.parent_id
  WHERE  NOT p.id = ANY(c.visitados)   -- ← interrompe ciclos
)
SELECT trilha FROM caminho ORDER BY array_length(visitados, 1) DESC LIMIT 1;
Atenção
Uma WITH RECURSIVE sobre dados com ciclos roda para sempre (ou até estourar memória). Sempre carregue um array de nós visitados e filtre WHERE NOT id = ANY(visitados), ou use a cláusula CYCLE (PG 14+): ... CYCLE id SET eh_ciclo USING caminho. Em produção, considere também o tipo ltree ou a tabela de fechamento transitivo (Capítulo 14) para árvores lidas com frequência.

# LATERAL — "para cada linha, rode esta query"

LATERAL permite que uma subquery no FROM referencie colunas das tabelas que vêm antes dela — algo que subqueries normais no FROM não podem fazer. O modelo mental é um for sobre a tabela esquerda, executando a subquery uma vez por linha. É a forma idiomática para "top-N por grupo" e para desempacotar funções que retornam conjuntos.

lateral.sql
-- "Os 3 pedidos mais recentes de CADA cliente" — top-N por grupo
SELECT u.nome, p.id AS pedido, p.criado_em
FROM   users u
CROSS JOIN LATERAL (
  SELECT o.id, o.criado_em
  FROM   orders o
  WHERE  o.user_id = u.id          -- ← enxerga u (LATERAL)
  ORDER BY o.criado_em DESC
  LIMIT  3
) AS p;
-- Use LEFT JOIN LATERAL ... ON true para manter clientes sem pedidos.

-- Desempacotar função que retorna conjunto, por linha
SELECT p.nome, tag
FROM   products p
CROSS JOIN LATERAL unnest(p.tags) AS tag;   -- p.tags é text[]

-- Cálculo derivado reaproveitado (evita repetir a expressão)
SELECT oi.order_id, calc.subtotal, calc.com_imposto
FROM   order_items oi
CROSS JOIN LATERAL (
  SELECT oi.quantidade * oi.preco_unit           AS subtotal,
         oi.quantidade * oi.preco_unit * 1.1     AS com_imposto
) AS calc;

# Materialização: a barreira de otimização

Historicamente, CTEs no PostgreSQL eram sempre materializadas: a CTE era computada por inteiro e armazenada num resultado temporário antes da query principal — uma "barreira de otimização" que o planner não atravessava. A partir do PG 12 o comportamento mudou: CTEs não recursivas, referenciadas uma vez e sem efeitos colaterais passam a ser inlined (fundidas na query externa) por padrão, como uma subquery comum. Você pode forçar qualquer um dos dois lados.

materialized.sql
-- NOT MATERIALIZED: força inline — o planner pode empurrar filtros
-- para DENTRO da CTE (push-down), muitas vezes muito mais rápido
WITH caros AS NOT MATERIALIZED (
  SELECT * FROM products WHERE preco > 100
)
SELECT * FROM caros WHERE categoria_id = 3;
-- Inlined: o planner pode usar índice em (categoria_id, preco)

-- MATERIALIZED: força o cálculo único e o "cache"
-- Útil quando a CTE é cara E referenciada várias vezes,
-- ou quando contém uma função volátil/com efeito colateral
WITH base AS MATERIALIZED (
  SELECT p.categoria_id, sum(oi.quantidade) AS vendidos
  FROM   order_items oi
  JOIN   products p ON p.id = oi.product_id
  GROUP BY p.categoria_id
)
SELECT * FROM base b1
JOIN   base b2 ON b2.vendidos < b1.vendidos;  -- base usada 2x → materializar evita recomputar
PostgreSQL 16/17
O PG 16 melhorou a estimativa de custo de CTEs inlined e a paralelização dentro de WITH RECURSIVE em mais cenários. Decisão prática que continua valendo: deixe o padrão (auto) na maioria dos casos; use NOT MATERIALIZED quando a CTE é um simples filtro e você quer push-down de predicados/índices; use MATERIALIZED quando ela é cara e reaproveitada várias vezes na mesma query.

INSERT, UPDATE, DELETE — DML completo

DML (Data Manipulation Language) é o SQL que muda dados: insere, atualiza e remove linhas. O PostgreSQL vai além do padrão em várias frentes — RETURNING para obter os dados afetados sem uma query extra, INSERT ... ON CONFLICT para upserts idiomáticos, MERGE para sincronização de tabelas e extensões como UPDATE ... FROM e DELETE ... USING para operações baseadas em outras tabelas. Este capítulo percorre cada operação do básico ao avançado, com os padrões de produção mais usados.

# INSERT

insert.sql
-- Inserção simples com colunas explícitas (sempre prefira listar colunas)
INSERT INTO users (email, nome)
VALUES ('ana@exemplo.com', 'Ana Lima');

-- Múltiplas linhas em um único INSERT (mais eficiente que N inserts)
INSERT INTO categories (nome) VALUES
  ('Eletrônicos'),
  ('Roupas'),
  ('Livros'),
  ('Casa');

-- INSERT ... SELECT: inserir a partir de uma query
INSERT INTO products_backup (id, nome, preco)
SELECT id, nome, preco
FROM   products
WHERE  ativo AND estoque > 0;

-- DEFAULT VALUES: insere uma linha só com valores padrão
INSERT INTO orders (user_id) VALUES (1);
-- status = 'pendente' e criado_em = now() serão aplicados pelos DEFAULTs

# RETURNING — obter dados do DML

RETURNING é uma das extensões mais úteis do PostgreSQL: devolve as linhas afetadas (antes ou depois da mutação, dependendo da operação) sem necessidade de um SELECT extra. Essencial em aplicações que precisam do id gerado ou do estado final da linha.

returning.sql
-- Obter o id gerado após INSERT (padrão clássico em APIs)
INSERT INTO orders (user_id)
VALUES (1)
RETURNING id, status, criado_em;

-- RETURNING * → devolve a linha inteira como inserida/atualizada
INSERT INTO users (email, nome)
VALUES ('joao@exemplo.com', 'João Silva')
RETURNING *;

-- RETURNING em UPDATE: ver o estado pós-atualização
UPDATE orders
SET    status = 'pago', atualizado_em = now()
WHERE  id = 42
RETURNING id, status, atualizado_em;

-- RETURNING em DELETE: ver o que foi removido
DELETE FROM order_items
WHERE  order_id = 42
RETURNING *;

-- Usar RETURNING numa CTE (data-modifying CTE)
WITH novo_pedido AS (
  INSERT INTO orders (user_id) VALUES (1) RETURNING id
)
INSERT INTO order_items (order_id, product_id, quantidade, preco_unit)
SELECT novo_pedido.id, 101, 2, 49.90
FROM   novo_pedido;
-- Cria pedido e insere itens em uma transação, sem precisar do id em memória

# INSERT … ON CONFLICT — upsert idiomático

Upsert — "insert ou update" — é uma das operações mais comuns em sistemas reais: tente inserir; se a linha já existir (conflito de chave), faça algo. A forma idiomática do PostgreSQL é INSERT ... ON CONFLICT, atômica e eficiente.

upsert_on_conflict.sql
-- ON CONFLICT DO NOTHING: ignora o erro e segue em frente
INSERT INTO categories (nome)
VALUES ('Eletrônicos')
ON CONFLICT (nome) DO NOTHING;   -- nome tem constraint UNIQUE

-- ON CONFLICT DO UPDATE: atualiza a linha existente
-- "EXCLUDED" referencia os valores que foram TENTADOS de inserir
INSERT INTO products (id, nome, preco, estoque)
VALUES (101, 'Teclado Mecânico', 349.90, 15)
ON CONFLICT (id) DO UPDATE SET
  nome          = EXCLUDED.nome,
  preco         = EXCLUDED.preco,
  estoque       = EXCLUDED.estoque,
  atualizado_em = now()
RETURNING *;

-- Upsert acumulativo: somar ao invés de sobrescrever
INSERT INTO products (id, nome, preco, estoque)
VALUES (101, 'Teclado Mecânico', 349.90, 5)
ON CONFLICT (id) DO UPDATE SET
  estoque = products.estoque + EXCLUDED.estoque;
-- products.estoque → valor atual na tabela
-- EXCLUDED.estoque → valor que chegou no INSERT (5 unidades novas)

-- ON CONFLICT ON CONSTRAINT: especificar pelo nome da constraint
INSERT INTO users (email, nome)
VALUES ('ana@exemplo.com', 'Ana Lima 2')
ON CONFLICT ON CONSTRAINT users_email_key DO UPDATE SET
  nome = EXCLUDED.nome;
Dica
ON CONFLICT DO UPDATE sempre reescreve a linha (gera nova versão no MVCC), mesmo que os valores não mudem. Se a operação mais comum for "já existe, não faça nada", prefira DO NOTHING. Se você quiser atualizar só quando realmente mudou, adicione um WHERE no DO UPDATE: ON CONFLICT (id) DO UPDATE SET preco = EXCLUDED.preco WHERE products.preco <> EXCLUDED.preco.

# MERGE — sincronização de tabelas

MERGE é o upsert do padrão SQL (desde a versão 15 no PostgreSQL) — mais expressivo que ON CONFLICT quando você precisa de múltiplas ações condicionais em uma operação: inserir se não existe, atualizar se existe com certos valores, deletar se existe com outros.

merge.sql
-- Sincronizar tabela de staging com a tabela principal
-- products_staging: dados vindos de uma importação/API
MERGE INTO products AS destino
USING products_staging AS origem
  ON destino.id = origem.id

WHEN MATCHED AND origem.ativo = false THEN
  DELETE

WHEN MATCHED THEN
  UPDATE SET
    nome          = origem.nome,
    preco         = origem.preco,
    estoque       = origem.estoque,
    atualizado_em = now()

WHEN NOT MATCHED THEN
  INSERT (id, nome, preco, estoque, categoria_id)
  VALUES (origem.id, origem.nome, origem.preco,
           origem.estoque, origem.categoria_id);

-- MERGE também aceita RETURNING (PG 17)
MERGE INTO products AS destino
USING products_staging AS origem ON destino.id = origem.id
WHEN MATCHED THEN
  UPDATE SET preco = origem.preco
WHEN NOT MATCHED THEN
  INSERT (id, nome, preco) VALUES (origem.id, origem.nome, origem.preco)
RETURNING merge_action(), destino.*;
-- merge_action() retorna 'INSERT', 'UPDATE' ou 'DELETE'
PostgreSQL 16/17
MERGE foi introduzido no PG 15 (padrão SQL:2003). O PG 17 adicionou RETURNING ao MERGE e a função merge_action() para identificar qual ação foi executada por linha. O PG 16 adicionou suporte a WHEN NOT MATCHED BY SOURCE — lidar com linhas na tabela destino que não existem na origem (análogo a um DELETE condicional).

# UPDATE

update.sql
-- UPDATE simples
UPDATE products
SET    preco = preco * 1.1             -- reajuste de 10%
WHERE  categoria_id = 1;

-- Atualizar várias colunas
UPDATE orders
SET    status        = 'enviado',
       atualizado_em = now()
WHERE  id = 42 AND status = 'pago';    -- só se já estiver pago

-- UPDATE ... FROM: atualizar baseado em outra tabela (extensão PG)
-- "Ajustar preço_unit dos itens ao preço atual do produto"
UPDATE order_items oi
SET    preco_unit = p.preco
FROM   products p
WHERE  oi.product_id = p.id
  AND  oi.preco_unit <> p.preco;

-- UPDATE com subquery no SET
UPDATE products
SET    estoque = estoque - (
  SELECT sum(quantidade)
  FROM   order_items oi
  WHERE  oi.product_id = products.id
    AND  oi.order_id = 42
)
WHERE  id IN (
  SELECT product_id FROM order_items WHERE order_id = 42
);

-- UPDATE sem WHERE: afeta TODAS as linhas — use com muita cautela
-- Para tabelas grandes em produção, rode em lotes (Capítulo 22)
UPDATE products SET atualizado_em = now();  -- afeta TUDO
Atenção
Um UPDATE sem WHERE afeta todas as linhas. Em produção, antes de um UPDATE de risco, rode um SELECT com o mesmo WHERE para confirmar o escopo. Dentro de uma transação, BEGIN; SELECT count(*) ...; UPDATE ...; -- confira RETURNING; ROLLBACK; é uma técnica segura de validação antes do COMMIT.

# DELETE

delete.sql
-- DELETE simples
DELETE FROM orders
WHERE  status = 'cancelado'
  AND  criado_em < now() - '2 years'::interval;

-- DELETE ... USING: deletar baseado em outra tabela (extensão PG)
-- "Remover itens de pedidos cancelados"
DELETE FROM order_items oi
USING  orders o
WHERE  oi.order_id = o.id
  AND  o.status = 'cancelado';

-- DELETE com subquery
DELETE FROM products
WHERE  id NOT IN (
  SELECT DISTINCT product_id FROM order_items
);
-- Cuidado: NOT IN com NULL (Capítulo 6). Prefira NOT EXISTS:
DELETE FROM products p
WHERE NOT EXISTS (
  SELECT 1 FROM order_items oi WHERE oi.product_id = p.id
);

-- Soft delete: "deletar" sem remover a linha
UPDATE products
SET    deletado_em = now()
WHERE  id = 101;
-- Queries de leitura excluem deletados: WHERE deletado_em IS NULL

-- Para tabelas novas: a estratégia mais rápida é
-- 1. Criar a tabela SEM índices
-- 2. Carregar todos os dados (COPY ou INSERT ... SELECT)
-- 3. Criar os índices ao final (mais rápido que atualizar por linha)

Performance & custo
COPY é tipicamente 5–10× mais rápido que INSERT linha a linha para grandes volumes. Para cargas intermediárias, agrupar INSERTs em lotes de 500–1000 linhas por transação é o equilíbrio certo — lotes menores geram overhead de commit; lotes maiores seguram locks por mais tempo. Drivers modernos como node-postgres e psycopg3 suportam COPY via stream diretamente.

padroes_dml.sql
-- "Criar pedido e seus itens em uma CTE atômica"
WITH pedido AS (
  INSERT INTO orders (user_id) VALUES (7) RETURNING id
)
INSERT INTO order_items (order_id, product_id, quantidade, preco_unit)
SELECT p.id, product_id, quantidade, preco_unit
FROM   pedido p
CROSS JOIN (VALUES
  (10, 2, 49.90),
  (11, 1, 99.00)
) AS itens(product_id, quantidade, preco_unit);

-- "Decrementar estoque ao confirmar pedido — só se houver saldo"
UPDATE products p
SET    estoque = p.estoque - oi.quantidade
FROM   order_items oi
WHERE  oi.product_id = p.id
  AND  oi.order_id   = 42
  AND  p.estoque     >= oi.quantidade    -- guarda: não vai a negativo
RETURNING p.id, p.estoque;
-- Verifica na aplicação: se count(RETURNING) < count(itens), houve produto sem estoque

-- "Arquivar e deletar em uma operação" (data-modifying CTE)
WITH para_arquivar AS (
  DELETE FROM orders
  WHERE  status = 'cancelado'
    AND  criado_em < now() - '1 year'::interval
  RETURNING *
)
INSERT INTO orders_arquivo
SELECT * FROM para_arquivar;

Transações e ACID

Transações são o que separa um banco de dados sério de um arquivo glorificado. Elas garantem que "transferir saldo" ou "confirmar pedido e baixar estoque" aconteça por inteiro ou não aconteça — nunca pela metade, nem mesmo com queda de energia ou mil clientes simultâneos. Este capítulo constrói o modelo mental de ACID, mostra como o PostgreSQL implementa isolamento via MVCC, demonstra cada anomalia de concorrência com cenários concretos, e cobre SAVEPOINT, locking explícito, deadlocks e advisory locks.

# O que ACID realmente garante

ACID não é um conceito acadêmico abstrato — cada letra resolve um modo específico pelo qual dados se corrompem. O modelo mental: uma transação é uma fronteira dentro da qual mudanças são tentativas, e fora da qual elas são fatos.

LetraGarantiaO desastre que evita
AtomicidadeTudo ou nadaSaldo debitado mas crédito nunca aplicado (pedido criado, estoque não baixado)
ConsistênciaInvariantes preservadasEstoque negativo, FK órfã, soma de itens ≠ total do pedido
IsolamentoTransações não se enxergam pela metadeUma transação lê dados que outra ainda não confirmou (ou já desfez)
DurabilidadeO confirmado sobreviveCOMMIT bem-sucedido perdido por queda de energia logo depois

No PostgreSQL, a durabilidade vem do WAL (Capítulo 1): a mudança vai para o log de escrita antes dos arquivos de dados, então um COMMIT que retornou sucesso é recuperável. A atomicidade e o isolamento vêm do MVCC. A consistência é responsabilidade compartilhada: o banco impõe as constraints (Capítulo 12), e você impõe as regras de negócio dentro de transações.

# Delimitando transações

transacao_basica.sql
-- Transferência de "saldo" entre dois clientes: precisa ser atômica
BEGIN;

UPDATE contas SET saldo = saldo - 100 WHERE user_id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE user_id = 2;

-- Se algo falhar aqui, NADA foi aplicado de verdade ainda
COMMIT;   -- agora as duas mudanças são fatos, juntas

-- Em caso de erro/decisão de abortar:
BEGIN;
UPDATE products SET estoque = estoque - 5 WHERE id = 1;
-- ops, regra de negócio violada na aplicação
ROLLBACK;   -- desfaz tudo desde o BEGIN; é como se nada tivesse acontecido

-- Autocommit: fora de um BEGIN explícito, CADA statement é sua
-- própria transação. Isto são DUAS transações independentes:
UPDATE contas SET saldo = saldo - 100 WHERE user_id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE user_id = 2;
-- Se a 2ª falhar, a 1ª JÁ FOI COMMITADA → dinheiro sumiu. Use BEGIN.
Atenção
Se um erro ocorrer dentro de uma transação no PostgreSQL, ela entra em estado abortado: todo comando seguinte falha com "current transaction is aborted" até um ROLLBACK (ou ROLLBACK TO SAVEPOINT). Isso é proposital — impede que você continue operando sobre um estado inconsistente. Frameworks/ORMs geralmente gerenciam isso, mas em scripts manuais é uma pegadinha frequente.

# SAVEPOINT — rollback parcial

savepoint.sql
BEGIN;

INSERT INTO orders (user_id) VALUES (1);

SAVEPOINT antes_itens;

INSERT INTO order_items (order_id, product_id, quantidade, preco_unit)
VALUES (currval('orders_id_seq'), 999, 1, 10);  -- produto 999 não existe → erro de FK

-- Volta só até o savepoint; o INSERT em orders permanece
ROLLBACK TO SAVEPOINT antes_itens;

-- Tenta de novo com um produto válido
INSERT INTO order_items (order_id, product_id, quantidade, preco_unit)
VALUES (currval('orders_id_seq'), 10, 1, 49.90);

RELEASE SAVEPOINT antes_itens;   -- opcional: descarta o savepoint
COMMIT;
-- Savepoints são a base de "nested transactions" em ORMs/frameworks

# MVCC: como o PostgreSQL isola sem travar leituras

Aqui está o mecanismo central. Em muitos bancos, ler uma linha que outra transação está alterando exige esperar (lock de leitura). O PostgreSQL usa MVCC (Multi-Version Concurrency Control): cada UPDATE não sobrescreve a linha — cria uma nova versão. Cada transação enxerga um snapshot coerente dos dados conforme as regras do seu nível de isolamento. A consequência prática define a filosofia do PostgreSQL: leitores nunca bloqueiam escritores, e escritores nunca bloqueiam leitores. Apenas escritor-vs-escritor na mesma linha contende.

Nota
As versões antigas de linhas (chamadas "dead tuples") não somem sozinhas — ficam até o VACUUM recuperá-las (Capítulo 20). Por isso transações muito longas são problemáticas: enquanto uma transação está aberta, o banco não pode limpar versões que ela poderia precisar enxergar, e a tabela incha (bloat). Mantenha transações curtas.

# As anomalias de concorrência

Sem isolamento, transações concorrentes produzem quatro tipos de corrupção. Os níveis de isolamento são definidos exatamente por quais dessas anomalias eles impedem — então é preciso conhecê-las primeiro.

anomalias.sql
-- ── DIRTY READ: ler dado não confirmado de outra transação ──
-- T1: BEGIN; UPDATE products SET preco = 9999 WHERE id = 1;  (sem commit)
-- T2: SELECT preco FROM products WHERE id = 1;  → veria 9999?
-- No PostgreSQL: IMPOSSÍVEL. Nem em Read Committed dirty read ocorre.

-- ── NON-REPEATABLE READ: mesma linha, valores diferentes na mesma tx ──
-- T1: BEGIN; SELECT preco FROM products WHERE id=1;  → 100
-- T2:        UPDATE products SET preco=150 WHERE id=1; COMMIT;
-- T1:        SELECT preco FROM products WHERE id=1;  → 150 (mudou!)
-- Ocorre em Read Committed; prevenido em Repeatable Read.

-- ── PHANTOM READ: mesma condição, conjunto de linhas diferente ──
-- T1: BEGIN; SELECT count(*) FROM products WHERE preco<100;  → 8
-- T2:        INSERT INTO products (...preco 50...); COMMIT;
-- T1:        SELECT count(*) FROM products WHERE preco<100;  → 9 (fantasma!)
-- Ocorre em Read Committed; prevenido em Repeatable Read (no PG).

-- ── WRITE SKEW: cada tx lê algo válido, juntas violam invariante ──
-- Regra: ao menos 1 médico de plantão. Há 2 (Ana, Bruno).
-- T1: vê 2 de plantão → Ana sai de plantão
-- T2: vê 2 de plantão → Bruno sai de plantão
-- Resultado: 0 de plantão. Cada tx estava "certa" isoladamente.
-- Só Serializable previne write skew.

# Os três níveis de isolamento do PostgreSQL

O SQL padrão define quatro níveis; o PostgreSQL implementa três (Read Uncommitted se comporta como Read Committed — dirty reads simplesmente não acontecem). O nível é um dial: mais isolamento = mais correção sob concorrência, porém mais conflitos de serialização para sua aplicação tratar.

NívelDirty readNon-repeatablePhantomWrite skew
Read Committed (padrão)NãoPodePodePode
Repeatable ReadNãoNãoNão*Pode
SerializableNãoNãoNãoNão

* O PostgreSQL é mais forte que o padrão SQL: Repeatable Read também previne phantom reads via snapshot isolation.

isolation_levels.sql
-- Read Committed (padrão): cada COMANDO vê um snapshot fresco.
-- Adequado para a maioria das aplicações web/CRUD.
BEGIN;  -- implicitamente READ COMMITTED
SELECT estoque FROM products WHERE id = 1;
COMMIT;

-- Repeatable Read: a TRANSAÇÃO INTEIRA vê o mesmo snapshot
-- (o do primeiro comando). Ideal para relatórios consistentes.
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT sum(total) FROM orders;          -- "foto" consistente
SELECT count(*) FROM orders;           -- mesma foto, mesmo se houve commits
COMMIT;

-- Serializable: como se as transações rodassem uma de cada vez.
-- Pode abortar com erro 40001 (serialization failure) → RETENTAR.
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ... lógica que depende de invariantes globais ...
COMMIT;   -- se falhar com 40001, a aplicação deve repetir a transação
Dica
Regra prática de escolha: Read Committed para CRUD web típico; Repeatable Read para relatórios que precisam de uma foto consistente do banco; Serializable quando há invariantes que cruzam múltiplas linhas/tabelas (estoque, reservas, regras de negócio críticas) — e nesse caso sua aplicação precisa de uma camada de retry para o erro 40001.

# Lost update e locking explícito

O cenário mais comum em e-commerce: dois clientes compram o último item simultaneamente. O padrão "ler-modificar-escrever" sem proteção causa lost update.

lost_update.sql
-- ❌ LOST UPDATE: padrão read-modify-write ingênuo
-- T1: SELECT estoque FROM products WHERE id=1;   → 1
-- T2: SELECT estoque FROM products WHERE id=1;   → 1 (também vê 1!)
-- T1: UPDATE products SET estoque=0 WHERE id=1;   → vende
-- T2: UPDATE products SET estoque=0 WHERE id=1;   → vende DE NOVO
-- Vendeu 2 unidades de 1 item em estoque.

-- ✅ SOLUÇÃO 1: UPDATE atômico (deixe o banco fazer a aritmética)
UPDATE products
SET    estoque = estoque - 1
WHERE  id = 1 AND estoque >= 1
RETURNING estoque;
-- Se RETURNING vier vazio: não havia estoque. Sem race condition.

-- ✅ SOLUÇÃO 2: SELECT ... FOR UPDATE (lock pessimista de linha)
BEGIN;
SELECT estoque FROM products
WHERE  id = 1
FOR UPDATE;   -- trava a linha; outras tx esperam aqui
-- ... lógica de negócio na aplicação ...
UPDATE products SET estoque = estoque - 1 WHERE id = 1;
COMMIT;   -- libera o lock

-- Variações de locking de linha:
-- FOR UPDATE         → lock exclusivo (vou alterar)
-- FOR NO KEY UPDATE  → mais leve; não bloqueia FKs que referenciam
-- FOR SHARE          → lock compartilhado (vou ler, não deixe alterar)
-- FOR KEY SHARE      → o mais leve dos shares

-- Evitar espera: pular linhas travadas (filas de trabalho!)
SELECT * FROM fila_jobs
WHERE  status = 'pendente'
ORDER BY criado_em
LIMIT  1
FOR UPDATE SKIP LOCKED;   -- cada worker pega um job diferente

-- Falhar rápido em vez de esperar:
SELECT * FROM products WHERE id = 1 FOR UPDATE NOWAIT;
-- erro imediato se a linha já estiver travada
Performance & custo
FOR UPDATE SKIP LOCKED transforma uma tabela em uma fila de trabalho concorrente eficiente — múltiplos workers consomem jobs sem contenção e sem pegar o mesmo item. É a base de muitos sistemas de filas em PostgreSQL. Já o lock pessimista de longa duração (FOR UPDATE + lógica lenta na aplicação antes do COMMIT) serializa o acesso e vira gargalo: mantenha a janela entre o lock e o COMMIT a mais curta possível.

# Deadlocks

Um deadlock acontece quando duas transações travam recursos em ordens opostas e cada uma espera a outra. O PostgreSQL detecta automaticamente o ciclo e aborta uma das transações com erro 40P01 — mas a prevenção é responsabilidade do design da aplicação.

deadlock.sql
-- ❌ Receita de deadlock: ordens de lock opostas
-- T1: BEGIN; UPDATE products WHERE id=1;  (trava linha 1)
-- T2: BEGIN; UPDATE products WHERE id=2;  (trava linha 2)
-- T1:        UPDATE products WHERE id=2;  (espera T2 soltar a 2)
-- T2:        UPDATE products WHERE id=1;  (espera T1 soltar a 1)
-- → DEADLOCK. O PG aborta uma com: "deadlock detected" (40P01)

-- ✅ Prevenção 1: SEMPRE travar recursos na MESMA ordem
-- Convenção: ordenar pelos ids ascendentes antes de atualizar
BEGIN;
SELECT id FROM products
WHERE  id IN (1, 2)
ORDER BY id          -- ordem determinística de aquisição
FOR UPDATE;
-- ... agora atualize ambas; nenhuma outra tx que siga a mesma
--     convenção poderá formar um ciclo ...
COMMIT;

-- ✅ Prevenção 2: transações curtas; tocar menos linhas; índices
-- bons (locks de linha precisos em vez de varreduras amplas).

-- Aplicação DEVE ter retry para 40P01 e 40001 (serialization):
-- pseudo: try { tx() } catch (e) { if e in (40P01,40001) retry() }

# Advisory locks — coordenação no nível da aplicação

Às vezes você precisa de um mutex que não está atrelado a nenhuma linha — "só um processo pode rodar este job agendado por vez", "só uma instância recalcula o ranking". Advisory locks são travas nomeadas (por um inteiro) que o PostgreSQL gerencia mas cuja semântica é definida pela sua aplicação.

advisory_locks.sql
-- Lock de sessão: vive até unlock explícito ou fim da conexão
SELECT pg_advisory_lock(42);          -- bloqueia até obter o lock 42
-- ... seção crítica: só um processo executa isto por vez ...
SELECT pg_advisory_unlock(42);

-- Tentar sem bloquear: ideal para "se já está rodando, pule"
SELECT pg_try_advisory_lock(42);   -- → true se conseguiu, false se já em uso
-- if (false) { log('job já em execução por outra instância'); exit }

-- Lock de transação: liberado automaticamente no COMMIT/ROLLBACK
-- (mais seguro — impossível "esquecer" de soltar)
BEGIN;
SELECT pg_advisory_xact_lock(hashtext('recalcular_ranking'));
-- ... trabalho protegido ...
COMMIT;   -- lock liberado aqui, sem chamada explícita de unlock
PostgreSQL 16/17
O PG 16/17 trouxe ganhos de desempenho em cargas de alta concorrência (melhor escalabilidade de locks internos e do subsistema de WAL) e diagnósticos mais ricos: pg_stat_activity e a view pg_locks ajudam a identificar bloqueios; log_lock_waits = on registra esperas longas por lock. A função pg_blocking_pids(pid) mostra quais sessões estão bloqueando uma transação travada — essencial para diagnosticar contenção em produção.

Constraints e integridade referencial

Constraints são a camada de defesa do banco contra dados inválidos. Elas garantem que nenhuma aplicação bugada, script ad-hoc ou operação direta no psql consiga colocar o banco num estado inconsistente. Este capítulo cobre todas as constraints do PostgreSQL — PRIMARY KEY, FOREIGN KEY com suas ações de cascata, UNIQUE, CHECK, NOT NULL, EXCLUDE — e o mecanismo de deferimento que permite atrasar a verificação para o COMMIT, essencial para operações em lote e referências circulares.

# PRIMARY KEY

A chave primária identifica unicamente cada linha de uma tabela. Implica automaticamente NOT NULL e UNIQUE, e o PostgreSQL cria um índice B-tree para ela. Só pode haver uma por tabela.

primary_key.sql
-- Constraint inline na coluna (mais comum)
CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text   NOT NULL
);

-- Constraint de tabela (obrigatório para PKs compostas)
CREATE TABLE order_items (
  order_id   bigint NOT NULL,
  product_id bigint NOT NULL,
  quantidade int    NOT NULL,
  CONSTRAINT order_items_pkey PRIMARY KEY (order_id, product_id)
);

-- Adicionar PK após criação da tabela
ALTER TABLE legado ADD PRIMARY KEY (id);

-- Remover e recriar (ex: alterar tipo da PK)
ALTER TABLE products DROP CONSTRAINT products_pkey;
ALTER TABLE products ADD PRIMARY KEY (id);

# FOREIGN KEY — integridade referencial

A FK garante que o valor referenciado existe na tabela-pai. O PostgreSQL verifica tanto na escrita (inserção/atualização do filho) quanto na deleção/atualização do pai — e a cláusula de ação define o que fazer quando o pai é removido ou alterado.

foreign_key.sql
-- Sintaxe básica: coluna REFERENCES tabela(coluna)
CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL
    REFERENCES users(id)
    ON DELETE RESTRICT         -- padrão: impede deletar usuário com pedidos
    ON UPDATE CASCADE          -- se o id do user mudar, propaga
);

-- FK de tabela (multi-coluna ou nomeada)
CREATE TABLE order_items (
  order_id   bigint NOT NULL,
  product_id bigint NOT NULL,
  CONSTRAINT fk_order   FOREIGN KEY (order_id)   REFERENCES orders(id),
  CONSTRAINT fk_product FOREIGN KEY (product_id) REFERENCES products(id)
);

ALTER TABLE orders

SELECT conname, confupdtype, confdeltype

Atenção
O PostgreSQL não cria índice automaticamente na coluna de FK (ao contrário da PK e UNIQUE). Sempre crie um índice na coluna filha: CREATE INDEX ON orders(user_id). Sem ele, deletar ou atualizar o pai dispara um seq scan em toda a tabela filha — um gargalo silencioso que só aparece com volume.

# UNIQUE

unique.sql
-- Inline: coluna única
CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text   NOT NULL UNIQUE
);

-- UNIQUE de tabela: combinação de colunas deve ser única
CREATE TABLE memberships (
  user_id bigint,
  team_id bigint,
  CONSTRAINT uq_membership UNIQUE (user_id, team_id)
);

-- NULL e UNIQUE: múltiplos NULLs são PERMITIDOS (NULL ≠ NULL)
-- Isso é correto pelo padrão SQL — NULLs não se contradizem
INSERT INTO products (nome, slug, categoria_id) VALUES
  ('A', 'a', NULL),   -- OK
  ('B', 'b', NULL);   -- OK — dois NULLs em coluna UNIQUE são aceitos

-- UNIQUE NULLS NOT DISTINCT (PG 15+): NULLs também colidem
CREATE TABLE configuracoes (
  user_id  bigint,
  chave    text,
  valor    text,
  UNIQUE NULLS NOT DISTINCT (user_id, chave)
  -- user_id=NULL e chave='tema' só pode existir uma vez
);

-- Índice único parcial: unicidade condicional
-- "Só um email ativo por vez, mas pode ter histórico inativo"
CREATE UNIQUE INDEX uq_email_ativo
  ON users(email)
  WHERE deletado_em IS NULL;

# CHECK

check.sql
-- CHECK inline: expressão booleana sobre colunas da linha
CREATE TABLE products (
  id       bigint         GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  preco    numeric(10,2) NOT NULL CHECK (preco >= 0),
  estoque  int            NOT NULL CHECK (estoque >= 0),
  nome     text           NOT NULL CHECK (length(nome) BETWEEN 2 AND 200),
  status   text           NOT NULL CHECK (status IN ('rascunho','ativo','inativo'))
);

-- CHECK de tabela: expressão pode cruzar colunas
CREATE TABLE promocoes (
  id           bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  inicio       timestamptz NOT NULL,
  fim          timestamptz NOT NULL,
  desconto_pct numeric(5,2) NOT NULL,
  CONSTRAINT datas_validas   CHECK (fim > inicio),
  CONSTRAINT desconto_valido CHECK (desconto_pct BETWEEN 1 AND 100)
);

-- Adicionar CHECK a tabela existente
ALTER TABLE orders
  ADD CONSTRAINT status_valido
  CHECK (status IN ('pendente', 'pago', 'enviado', 'cancelado', 'devolvido'));

-- CHECK com NOT VALID: adicionar sem validar linhas existentes
-- (rápido em produção; valide depois com VALIDATE CONSTRAINT)
ALTER TABLE orders
  ADD CONSTRAINT status_valido
  CHECK (status IN ('pendente', 'pago', 'enviado', 'cancelado'))
  NOT VALID;

ALTER TABLE orders VALIDATE CONSTRAINT status_valido;
-- VALIDATE usa lock mais leve que ADD CONSTRAINT em tabelas grandes
Nota
Um CHECK que referencia uma função marcada como IMMUTABLE funciona bem. Se a função for STABLE ou VOLATILE (como now()), o PostgreSQL aceita o CHECK mas ele não é avaliado em UPDATE de colunas não mencionadas — uma armadilha sutil. Para validar invariantes que dependem do tempo, use triggers (Capítulo 18).

# NOT NULL

not_null.sql
-- NOT NULL inline — a constraint mais comum e importante
CREATE TABLE users (
  id        bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email     text        NOT NULL,   -- obrigatório
  telefone  text,                   -- nullable: pode ser desconhecido
  criado_em timestamptz NOT NULL DEFAULT now()
);

-- Adicionar NOT NULL a coluna existente
-- Estratégia segura em produção (evita lock longo em tabelas grandes):
-- 1. Adicionar coluna nullable
ALTER TABLE products ADD COLUMN sku text;
-- 2. Preencher valor default em lotes
UPDATE products SET sku = 'SKU-' || id::text WHERE sku IS NULL;
-- 3. Adicionar NOT VALID CHECK + VALIDATE (lock leve)
ALTER TABLE products
  ADD CONSTRAINT sku_not_null CHECK (sku IS NOT NULL) NOT VALID;
ALTER TABLE products VALIDATE CONSTRAINT sku_not_null;
-- 4. Finalmente, SET NOT NULL (PG 12+: usa o CHECK já validado, sem rescan)
ALTER TABLE products ALTER COLUMN sku SET NOT NULL;
ALTER TABLE products DROP CONSTRAINT sku_not_null;
Performance & custo
No PG 12+, ALTER COLUMN SET NOT NULL detecta automaticamente que um CHECK (col IS NOT NULL) já validado existe e pula o rescan da tabela — tornando a operação praticamente instantânea mesmo em tabelas com centenas de milhões de linhas. O padrão de 4 passos acima é a migração zero-downtime recomendada para adicionar NOT NULL a colunas em produção.

# EXCLUDE — exclusão de sobreposição

EXCLUDE é uma generalização de UNIQUE: enquanto UNIQUE usa apenas igualdade, EXCLUDE permite qualquer operador, sendo a ferramenta certa para garantir que intervalos de tempo, faixas de preço ou reservas de salas não se sobreponham.

exclude.sql
-- Reservas de sala: não pode haver sobreposição de horário para a mesma sala
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- necessária para EXCLUDE com GiST

CREATE TABLE reservas (
  id       bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sala_id  int         NOT NULL,
  periodo  tstzrange   NOT NULL,
  CONSTRAINT sem_sobreposicao
    EXCLUDE USING GiST (sala_id WITH =, periodo WITH &&)
  -- = : mesma sala
  -- && : períodos que se sobrepõem
  -- Juntos: rejeita nova reserva que sobreponha outra da mesma sala
);

-- Inserção válida: sala 1, sexta 14h–16h e sala 1, sexta 16h–18h (sem sobreposição)
INSERT INTO reservas (sala_id, periodo) VALUES
  (1, '[2025-01-10 14:00, 2025-01-10 16:00)'),
  (1, '[2025-01-10 16:00, 2025-01-10 18:00)');

-- Inserção inválida: sobreposição → erro de constraint
INSERT INTO reservas (sala_id, periodo) VALUES
  (1, '[2025-01-10 15:00, 2025-01-10 17:00)');
-- ERROR: conflicting key value violates exclusion constraint

# Constraints deferríveis

Por padrão, constraints são verificadas após cada statement. Deferrable constraints podem ser adiadas até o COMMIT — indispensável em duas situações: referências circulares (A referencia B, B referencia A) e operações em lote onde a ordem de inserção viola temporariamente a integridade.

deferrable.sql
-- Criar FK deferível: verificada no COMMIT por padrão, não por statement
CREATE TABLE nodes (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome    text   NOT NULL,
  next_id bigint
    REFERENCES nodes(id)
    DEFERRABLE INITIALLY DEFERRED   -- adiada até o COMMIT por padrão
);

-- Com INITIALLY DEFERRED: podemos criar referências circulares numa tx
BEGIN;
INSERT INTO nodes (nome, next_id) OVERRIDING SYSTEM VALUE
VALUES (1, 'A', 2), (2, 'B', 1);  -- A→B e B→A, impossível sem deferimento
COMMIT;   -- verificação ocorre aqui

-- DEFERRABLE INITIALLY IMMEDIATE: verificada por statement por padrão,
-- mas pode ser adiada quando necessário:
SET CONSTRAINTS fk_orders_user DEFERRED;     -- adia para esta transação
SET CONSTRAINTS ALL DEFERRED;               -- adia todas as deferráveis
SET CONSTRAINTS ALL IMMEDIATE;              -- volta ao imediato

-- Quais constraints suportam deferimento? Apenas FK, UNIQUE e EXCLUDE.
-- CHECK e NOT NULL são sempre IMMEDIATE (não deferráveis).
Dica
Em aplicações com ORM, um padrão comum é declarar todas as FKs como DEFERRABLE INITIALLY DEFERRED. Isso permite inserir entidades pai e filho em qualquer ordem dentro de uma transação sem orquestrar a sequência de inserts. O preço é que erros de integridade só aparecem no COMMIT — mais difícil de depurar. Prefira INITIALLY IMMEDIATE e use SET CONSTRAINTS DEFERRED cirurgicamente quando necessário.

Capítulo 13

Design e normalização

Um schema é a codificação das regras de negócio na própria estrutura dos dados. Decisões de design tomadas no dia um determinam quais bugs são impossíveis e quais serão eternos. Este capítulo desenvolve o raciocínio por trás da modelagem: pensar em entidades e relacionamentos, entender as anomalias que a normalização elimina, percorrer as formas normais (1NF→BCNF) como remoção progressiva de redundância, decidir conscientemente quando desnormalizar, escolher entre chaves naturais e substitutas, e reconhecer os anti-padrões que parecem atalhos mas viram dívida técnica.

# O modelo mental: redundância gera anomalias

A normalização não é um conjunto de regras a decorar — é a consequência lógica de uma observação simples: quando o mesmo fato é armazenado em mais de um lugar, eles podem discordar. Toda a teoria existe para eliminar essa possibilidade. Considere uma tabela "desenhada errado de propósito":

tabela_nao_normalizada.sql
-- Tudo numa tabela só: pedido + cliente + produto + categoria
CREATE TABLE pedidos_flat (
  pedido_id       bigint,
  cliente_email   text,        -- repetido em todo pedido do cliente
  cliente_nome    text,        -- idem
  produto_nome    text,        -- repetido em todo pedido do produto
  produto_preco   numeric,     -- idem
  categoria_nome  text,        -- repetido ainda mais vezes
  quantidade      int
);

Esse design sofre de três anomalias clássicas — e elas são o "porquê" de todo o resto do capítulo:

  • Anomalia de atualização: o cliente troca de e-mail. Você precisa atualizar todas as linhas dos pedidos dele. Esquecer uma deixa o banco contradizendo a si mesmo.
  • Anomalia de inserção: não dá para cadastrar um produto novo sem que ele tenha pelo menos um pedido — a existência do produto está acoplada à existência de um pedido.
  • Anomalia de deleção: apagar o último pedido de um cliente apaga também a única cópia dos dados desse cliente. Você perde informação que queria manter.

Normalizar é decompor tabelas até que cada fato viva em exatamente um lugar. As formas normais são níveis crescentes dessa garantia.

# Modelagem entidade-relacionamento

Antes das formas normais vem o modelo conceitual. ER pensa em três blocos: entidades (substantivos do domínio: cliente, produto, pedido), atributos (propriedades das entidades: nome, preço) e relacionamentos (verbos que conectam entidades: cliente faz pedido; pedido contém produtos). A pergunta-guia para identificar entidades: "sobre o que eu preciso guardar fatos independentes?".

modelo_er.txt
// O domínio de e-commerce em prosa, antes de virar SQL:

// Entidades (fatos independentes que valem por si):
//   users        — uma pessoa que pode comprar
//   products     — um item do catálogo
//   categories   — um agrupamento de produtos
//   orders       — uma compra realizada por um user

// Relacionamentos (com cardinalidade):
//   user 1 ── N orders          (um cliente faz vários pedidos)
//   category 1 ── N products    (uma categoria tem vários produtos)
//   order N ── N products       (muitos-para-muitos)
//     → resolvido por uma ENTIDADE ASSOCIATIVA: order_items

// Regra de ouro: todo relacionamento N:N vira uma tabela própria.
// order_items existe porque um pedido tem vários produtos E
// um produto aparece em vários pedidos — com atributos próprios
// do relacionamento (quantidade, preco_unit no momento da compra).
Nota
A tabela order_items guarda preco_unit — uma cópia deliberada do preço do produto no instante da compra. Isso parece redundância, mas não é: o preço do produto muda com o tempo; o preço cobrado naquele pedido é um fato histórico imutável. A regra é: copiar um valor que muda é redundância; copiar um valor congelado no tempo é um fato novo e legítimo.

# Dependências funcionais

A ferramenta formal por trás das formas normais é a dependência funcional: dizemos que A → B ("A determina B") quando, conhecido o valor de A, o valor de B fica univocamente determinado. cpf → nome (um CPF identifica uma pessoa, logo seu nome). cep → cidade (um CEP determina a cidade). As formas normais são, no fundo, regras sobre quais dependências funcionais podem coexistir numa mesma tabela.

# 1NF — valores atômicos

A Primeira Forma Normal exige que cada célula contenha um valor atômico — nada de listas, conjuntos ou grupos repetidos numa coluna. Uma tabela viola 1NF quando um campo guarda "vários valores de uma vez".

primeira_forma_normal.sql
-- ❌ Viola 1NF: telefones numa string separada por vírgula
CREATE TABLE users_ruim (
  id        bigint,
  nome      text,
  telefones text   -- '11999990000, 1133334444' — não atômico!
);
-- Consequência: "buscar quem tem o telefone X" vira LIKE frágil;
-- impossível ter constraint, índice útil ou contar telefones.

-- ✅ 1NF: cada telefone é uma linha em sua própria tabela
CREATE TABLE users (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome text   NOT NULL
);
CREATE TABLE user_telefones (
  user_id  bigint REFERENCES users(id) ON DELETE CASCADE,
  telefone text   NOT NULL,
  tipo     text   NOT NULL DEFAULT 'celular',
  PRIMARY KEY (user_id, telefone)
);
Dica
No PostgreSQL há uma nuance: tipos array e jsonb tecnicamente "violam" a 1NF clássica, mas são cidadãos de primeira classe e às vezes a modelagem certa (tags de um produto, atributos flexíveis). A pergunta não é "é atômico?", e sim "preciso consultar/restringir/indexar os elementos individualmente, ou eles só fazem sentido como um bloco?". Se for o primeiro caso, normalize em tabela; se for o segundo, jsonb/array são legítimos (Capítulos 16 e 17).

# 2NF — sem dependência parcial da chave

A Segunda Forma Normal só é relevante quando a chave primária é composta. Ela exige que todo atributo não-chave dependa da chave inteira, não de apenas parte dela.

segunda_forma_normal.sql
-- ❌ Viola 2NF: PK = (order_id, product_id), mas produto_nome
--    depende SÓ de product_id (parte da chave)
CREATE TABLE order_items_ruim (
  order_id     bigint,
  product_id   bigint,
  produto_nome text,     -- product_id → produto_nome (dependência parcial)
  quantidade   int,
  PRIMARY KEY (order_id, product_id)
);
-- produto_nome se repete em todo pedido daquele produto → anomalias

-- ✅ 2NF: o que depende só de product_id mora em products
CREATE TABLE products (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome text   NOT NULL
);
CREATE TABLE order_items (
  order_id   bigint REFERENCES orders(id),
  product_id bigint REFERENCES products(id),
  quantidade int    NOT NULL,
  preco_unit numeric(10,2) NOT NULL,  -- depende da chave inteira: OK
  PRIMARY KEY (order_id, product_id)
);

# 3NF — sem dependência transitiva

A Terceira Forma Normal elimina dependências transitivas: um atributo não-chave não pode depender de outro atributo não-chave. Se chave → A e A → B, então B não pertence a esta tabela.

terceira_forma_normal.sql
-- ❌ Viola 3NF: id → categoria_id → categoria_nome (transitiva)
CREATE TABLE products_ruim (
  id             bigint PRIMARY KEY,
  nome           text,
  categoria_id   int,
  categoria_nome text   -- depende de categoria_id, não de id → 3NF violada
);
-- Renomear uma categoria exigiria varrer todos os produtos dela.

-- ✅ 3NF: o nome da categoria mora na entidade categoria
CREATE TABLE categories (
  id   int  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome text NOT NULL UNIQUE
);
CREATE TABLE products (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome         text   NOT NULL,
  categoria_id int    REFERENCES categories(id)
);
-- Renomear categoria = 1 UPDATE numa linha. Sem anomalias.
Nota
Para a vasta maioria dos sistemas, 3NF é o destino. Uma heurística informal e útil: cada coluna não-chave deve depender "da chave, de toda a chave e de nada além da chave" (the key, the whole key, and nothing but the key). 1NF cuida do "ser uma coluna de verdade", 2NF do "de toda a chave", 3NF do "nada além da chave".

# BCNF — a forma normal de Boyce-Codd

BCNF é um reforço da 3NF: exige que todo determinante seja uma chave candidata. Casos que violam BCNF mas satisfazem 3NF são raros — surgem quando há múltiplas chaves candidatas sobrepostas. Na prática diária você raramente precisa pensar em BCNF explicitamente; chegar a uma 3NF bem-feita com chaves candidatas claras quase sempre já entrega BCNF.

bcnf.txt
// Exemplo clássico de violação de BCNF satisfazendo 3NF:
// Tabela aula(aluno, materia, professor) com regras:
//   - cada professor leciona UMA única matéria
//   - cada (aluno, matéria) tem UM professor
// Dependências: {aluno,materia} → professor   E   professor → materia
// "professor" é determinante mas NÃO é chave candidata → fere BCNF.
// Solução: decompor em professor_materia(professor, materia)
//          e aula(aluno, professor).

# Desnormalização consciente

Normalizar elimina anomalias mas multiplica JOINs. Em pontos quentes de leitura, manter uma cópia controlada de um dado pode ser a decisão certa — desde que feita com os olhos abertos e com um mecanismo que mantenha a cópia coerente. Desnormalização não é "errar a modelagem"; é uma otimização explícita com um custo conhecido.

desnormalizacao.sql
-- Caso legítimo: cachear o total do pedido (evita SUM em toda leitura)
ALTER TABLE orders ADD COLUMN total_cache numeric(12,2);

-- A coerência precisa ser GARANTIDA, não esperada. Opções:
-- 1. Coluna gerada (se a fórmula for da mesma linha — não é o caso aqui)
-- 2. Trigger que recalcula ao mudar order_items (Capítulo 18)
-- 3. Materialized view para agregados de leitura intensa (Capítulo 18)

-- Contraexemplo de desnormalização RUIM: copiar dado mutável sem
-- mecanismo de sincronização (cliente_email em orders) — volta a
-- ter as três anomalias. A regra: copiou? prove que mantém coerente.

-- Antes de desnormalizar, MEÇA. Muitas vezes um índice resolve
-- (Capítulo 15) sem o custo de manter cópias coerentes.
Performance & custo
A ordem correta de otimização é: (1) normalize e modele bem; (2) adicione índices apropriados; (3) meça com EXPLAIN (ANALYZE); (4) só então considere desnormalizar o gargalo específico que sobrou. Desnormalizar preventivamente "porque JOIN é lento" quase sempre adiciona complexidade e bugs de inconsistência para resolver um problema que um índice resolveria de graça.

# Chaves naturais vs substitutas

Uma chave natural é um identificador que já existe no domínio (CPF, ISBN, e-mail). Uma chave substituta (surrogate) é um identificador artificial sem significado de negócio (id bigint IDENTITY, uuid). A escolha tem consequências de longo prazo.

Padrão recomendado para a maioria dos sistemas: use uma chave substituta como PK (id bigint GENERATED ALWAYS AS IDENTITY) e adicione a chave natural como coluna UNIQUE separada (email text NOT NULL UNIQUE). Você ganha estabilidade e FKs compactas, sem perder a integridade do identificador de negócio. Para IDs expostos publicamente em APIs, considere um uuid adicional para não vazar volume/sequência (Capítulo 3).

# Anti-padrões de schema

antipadroes.sql
-- ❌ ANTI-PADRÃO 1: EAV (Entity-Attribute-Value) genérico demais
-- "tabela que guarda qualquer atributo de qualquer coisa"
CREATE TABLE eav (entidade text, atributo text, valor text);
-- Perde tipos, constraints, FKs e performance. Quase sempre é melhor
-- modelar colunas reais; se precisa de flexibilidade, use jsonb (cap 16).

-- ❌ ANTI-PADRÃO 2: valores múltiplos em string (revisita 1NF)
tags text  -- 'oferta,novo,premium' → impossível indexar/constrangir bem
-- Use text[] (cap 17), jsonb, ou tabela de junção conforme o caso.

-- ❌ ANTI-PADRÃO 3: FK polimórfica sem integridade
CREATE TABLE comentarios_ruim (
  alvo_tipo text,   -- 'produto' | 'pedido' | ...
  alvo_id   bigint  -- FK "para qualquer tabela" — o banco não consegue garantir
);
-- Não há FK real possível. Alternativas: tabela por tipo, ou
-- supertipo com FK + colunas de subtipo (herança por tabela, cap 14).

-- ❌ ANTI-PADRÃO 4: "god table" com dezenas de colunas opcionais
-- products com 80 colunas, 60 quase sempre NULL → na verdade são
-- várias entidades disfarçadas. Decomponha por subtipo/uso.

-- ❌ ANTI-PADRÃO 5: nullable como flag de estado
-- "se data_envio IS NULL então não foi enviado" funciona, mas
-- estados complexos pedem uma coluna status explícita + CHECK.
Atenção
O anti-padrão mais sedutor é o EAV, porque promete "nunca mais alterar o schema". Na prática você troca ALTER TABLE (rápido, seguro, validado) por queries de auto-junção ilegíveis, ausência de tipos e constraints, e planos de execução péssimos. Quando você realmente precisa de atributos dinâmicos, jsonb com índice GIN (Capítulo 16) entrega flexibilidade com indexação e operadores ricos — sem destruir o resto do schema.

Relacionamentos e modelagem de árvores

Se entidades são os substantivos do domínio, relacionamentos são os verbos que os conectam — e a decisão central de cada um é a cardinalidade. Este capítulo trata os três tipos fundamentais (1:1, 1:N, N:N) pelo modelo mental "onde vai a chave estrangeira?", o caso especial de tabelas auto-referenciadas, como fazer polimorfismo relacional sem cair no anti-padrão do capítulo anterior, herança de tabelas no PostgreSQL, e — o tema mais rico — as quatro estratégias de modelar árvores e grafos, cada uma com seu trade-off de leitura vs escrita.

# A pergunta que resolve tudo: onde vai a FK?

Todo relacionamento, no fundo, é resolvido decidindo em qual tabela mora a chave estrangeira. A regra mecânica: a FK fica no lado "muitos" da relação, porque uma coluna só pode guardar um valor — e é o lado "muitos" que aponta para o único pai.

onde_vai_a_fk.txt
// 1:N → FK no lado "N"
//   user 1 ── N orders   →   orders.user_id REFERENCES users(id)
//   (cada order tem 1 user; um user tem N orders)

// N:N → nenhuma das duas tabelas; nasce uma TERCEIRA
//   order N ── N product →   order_items(order_id, product_id)

// 1:1 → FK em qualquer um dos lados, com UNIQUE para travar o "1"
//   user 1 ── 1 perfil   →   perfis.user_id UNIQUE REFERENCES users

// Pergunte sempre: "uma linha de A se relaciona com QUANTAS de B,
// e uma de B com quantas de A?" — a resposta dita a estrutura.

# 1:N — o relacionamento padrão

É o relacionamento mais comum: um cliente tem vários pedidos, uma categoria tem vários produtos. A FK vai no lado "muitos", e a ação de cascata (Capítulo 12) codifica a regra de negócio sobre o que acontece quando o pai some.

um_para_n.sql
CREATE TABLE users (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome text   NOT NULL
);

CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL           -- NOT NULL → relacionamento obrigatório
    REFERENCES users(id) ON DELETE RESTRICT
);
-- Sempre indexe a FK (o PG não cria sozinho!):
CREATE INDEX ON orders(user_id);

-- Relacionamento OPCIONAL: FK nullable + ON DELETE SET NULL
CREATE TABLE products (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  categoria_id int             -- nullable → produto pode não ter categoria
    REFERENCES categories(id) ON DELETE SET NULL
);
Nota
A nulabilidade da FK é a modelagem da obrigatoriedade. user_id bigint NOT NULL REFERENCES users diz "todo pedido tem dono". categoria_id int REFERENCES categories (nullable) diz "produto pode existir sem categoria". Não é detalhe — é regra de negócio expressa em DDL, imposta pelo banco.

# 1:1 — e por que ele costuma ser um sinal de alerta

Um 1:1 verdadeiro significa que cada linha de A corresponde a no máximo uma de B. Antes de modelá-lo, vale a pergunta: "por que isto não é uma só tabela?". Há três justificativas legítimas: colunas opcionais volumosas, separação por sensibilidade/segurança, ou particionamento de acesso. Fora isso, é frequentemente duas metades da mesma entidade.

um_para_um.sql
-- Padrão 1: PK compartilhada (a FK É a PK) — o mais limpo
CREATE TABLE user_perfis (
  user_id bigint PRIMARY KEY            -- PK e FK na mesma coluna
    REFERENCES users(id) ON DELETE CASCADE,
  bio          text,
  avatar_url   text,
  preferencias jsonb
);
-- A PK garante no máximo 1 perfil por user, sem coluna extra.

-- Padrão 2: FK separada com UNIQUE (quando precisa de id próprio)
CREATE TABLE user_credenciais (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL UNIQUE     -- UNIQUE é o que força o "1"
    REFERENCES users(id) ON DELETE CASCADE,
  senha_hash text NOT NULL
);
-- Justificativa válida aqui: separar credenciais sensíveis de users,
-- permitindo GRANT diferente e reduzindo superfície de exposição.

# N:N — sempre uma tabela de junção

Um relacionamento muitos-para-muitos nunca é resolvido com colunas — ele sempre nasce como uma terceira tabela (associativa/junção). E essa tabela frequentemente tem atributos próprios: dados que pertencem ao relacionamento, não a nenhuma das pontas.

n_para_n.sql
-- order_items: a junção pedido ↔ produto, COM atributos próprios
CREATE TABLE order_items (
  order_id   bigint NOT NULL REFERENCES orders(id)   ON DELETE CASCADE,
  product_id bigint NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
  -- Atributos DO RELACIONAMENTO (não do pedido, nem do produto):
  quantidade int            NOT NULL CHECK (quantidade > 0),
  preco_unit numeric(10,2) NOT NULL,
  -- PK composta = par único + impede duplicar produto no mesmo pedido
  PRIMARY KEY (order_id, product_id)
);
-- Indexe a "outra direção" da junção para queries que partem do produto:
CREATE INDEX ON order_items(product_id);
-- (a PK já cobre buscas que começam por order_id)

-- Atravessar a junção: "produtos comprados pelo cliente 7"
SELECT DISTINCT p.nome
FROM   orders o
JOIN   order_items oi ON oi.order_id   = o.id
JOIN   products p     ON p.id         = oi.product_id
WHERE  o.user_id = 7;
Performance & custo
A ordem das colunas na PK composta da tabela de junção importa para indexação. PRIMARY KEY (order_id, product_id) cria um índice eficiente para "itens de um pedido" (prefixo order_id), mas não para "pedidos com um produto". Por isso o índice extra em (product_id): ele cobre a travessia na direção oposta. Decida a ordem da PK pela query mais frequente e adicione índice para a direção secundária (Capítulo 15).

# Auto-referência

Uma tabela pode ter FK para si mesma — a base de hierarquias (categorias com subcategorias), grafos (usuário indica usuário) e estruturas recursivas. É um 1:N (ou N:N) onde as duas pontas são a mesma tabela.

auto_referencia.sql
-- 1:N auto-referenciado: categoria tem subcategorias (uma árvore)
CREATE TABLE categories (
  id        int  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome      text NOT NULL,
  parent_id int  REFERENCES categories(id) ON DELETE RESTRICT
  -- parent_id NULL = nó raiz; senão aponta para o pai
);
CREATE INDEX ON categories(parent_id);

-- N:N auto-referenciado: "amizade" / "seguir" entre usuários
CREATE TABLE follows (
  seguidor_id bigint REFERENCES users(id) ON DELETE CASCADE,
  seguido_id  bigint REFERENCES users(id) ON DELETE CASCADE,
  criado_em   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (seguidor_id, seguido_id),
  CONSTRAINT nao_seguir_a_si_mesmo CHECK (seguidor_id <> seguido_id)
);

# Polimorfismo relacional, do jeito certo

O Capítulo 13 mostrou o anti-padrão: alvo_tipo text, alvo_id bigint apontando para "qualquer tabela", sem FK possível. Quando você realmente precisa que uma entidade se relacione com tipos diferentes (um comentário sobre produto ou sobre pedido), há três soluções íntegras.

polimorfismo_correto.sql
-- SOLUÇÃO A: arco exclusivo (exclusive arc) — uma FK por tipo,
-- CHECK garante que exatamente UMA está preenchida
CREATE TABLE comentarios (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  texto      text   NOT NULL,
  product_id bigint REFERENCES products(id) ON DELETE CASCADE,
  order_id   bigint REFERENCES orders(id)   ON DELETE CASCADE,
  CONSTRAINT exatamente_um_alvo CHECK (
    (product_id IS NOT NULL)::int +
    (order_id   IS NOT NULL)::int = 1
  )
);
-- Vantagem: FKs reais, integridade garantida. Limita-se a poucos tipos.

-- SOLUÇÃO B: tabela de junção por tipo (a mais escalável)
CREATE TABLE comentarios (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  texto text   NOT NULL
);
CREATE TABLE comentario_produto (
  comentario_id bigint REFERENCES comentarios(id) ON DELETE CASCADE,
  product_id    bigint REFERENCES products(id)    ON DELETE CASCADE,
  PRIMARY KEY (comentario_id)
);
-- Cada novo tipo = nova tabela de junção, todas com FK íntegra.

-- SOLUÇÃO C: supertipo/subtipo (herança de entidade)
-- Uma tabela "comentavel" como supertipo, FK aponta para ela,
-- products/orders referenciam a mesma identidade do supertipo.

# Herança de tabelas no PostgreSQL

O PostgreSQL tem herança nativa via INHERITS — uma tabela filha herda as colunas da pai e queries na pai podem incluir as filhas. É um recurso poderoso, porém com ressalvas importantes que limitam seu uso geral.

table_inheritance.sql
CREATE TABLE pagamentos (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id  bigint NOT NULL,
  valor     numeric(12,2) NOT NULL,
  criado_em timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE pagamentos_cartao (
  bandeira    text NOT NULL,
  ultimos_4   char(4) NOT NULL
) INHERITS (pagamentos);   -- herda id, order_id, valor, criado_em

-- SELECT na pai inclui as filhas por padrão
SELECT * FROM pagamentos;            -- inclui pagamentos_cartao
SELECT * FROM ONLY pagamentos;       -- só a pai, exclui filhas
Atenção
Herança de tabelas tem uma armadilha séria: constraints UNIQUE e FOREIGN KEY não são herdadas e não funcionam entre pai e filhas. Uma FK que aponta para a tabela-pai não encontra linhas que estão fisicamente nas filhas. Por isso, hoje, INHERITS é raramente usado para modelar subtipos de domínio — seu uso prático principal é como base do particionamento (que no PG moderno tem sintaxe declarativa própria, PARTITION BY, vista no Capítulo 22). Para subtipos, prefira o padrão supertipo/subtipo com FKs explícitas.

# Modelando árvores: quatro estratégias

Hierarquias — categorias aninhadas, organogramas, threads de comentários — admitem várias modelagens, e a escolha é um trade-off explícito entre custo de leitura e de escrita. Não existe "a melhor"; existe a certa para o seu padrão de acesso.

1. Adjacency list — só o pai

arvore_adjacency.sql
-- Cada nó guarda apenas o id do pai. Escrita trivial, leitura recursiva.
CREATE TABLE categories (
  id        int  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome      text NOT NULL,
  parent_id int  REFERENCES categories(id)
);
-- Subárvore inteira → WITH RECURSIVE (Capítulo 9)
WITH RECURSIVE sub AS (
  SELECT id, nome, parent_id FROM categories WHERE id = 1
  UNION ALL
  SELECT c.id, c.nome, c.parent_id
  FROM categories c JOIN sub ON c.parent_id = sub.id
)
SELECT * FROM sub;
-- ✅ Escrita O(1), mover subárvore = 1 UPDATE
-- ❌ "todos os ancestrais/descendentes" custa recursão

2. Materialized path / ltree

arvore_ltree.sql
-- Cada nó guarda o caminho completo até a raiz. ltree é o tipo nativo.
CREATE EXTENSION IF NOT EXISTS ltree;

CREATE TABLE categories (
  id   int   GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome text  NOT NULL,
  path ltree NOT NULL      -- ex.: 'eletronicos.computadores.notebooks'
);
CREATE INDEX ON categories USING GiST (path);

-- Descendentes: operador @> ("é ancestral de")
SELECT * FROM categories WHERE path <@ 'eletronicos';
-- Ancestrais de um nó
SELECT * FROM categories WHERE path @> 'eletronicos.computadores.notebooks';
-- Filhos diretos via padrão lquery
SELECT * FROM categories WHERE path ~ 'eletronicos.*{1}';
-- ✅ Leitura de subárvore/ancestrais rápida (índice GiST)
-- ❌ Mover subárvore exige reescrever o path de todos os descendentes

3. Closure table — todas as relações ancestrais

arvore_closure.sql
-- Tabela auxiliar: uma linha para CADA par (ancestral, descendente),
-- incluindo o próprio nó (profundidade 0).
CREATE TABLE categories (
  id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, nome text
);
CREATE TABLE categoria_closure (
  ancestral_id   int REFERENCES categories(id) ON DELETE CASCADE,
  descendente_id int REFERENCES categories(id) ON DELETE CASCADE,
  profundidade   int NOT NULL,
  PRIMARY KEY (ancestral_id, descendente_id)
);
-- Descendentes = 1 JOIN simples, SEM recursão:
SELECT c.* FROM categoria_closure cc
JOIN categories c ON c.id = cc.descendente_id
WHERE cc.ancestral_id = 1;
-- ✅ Qualquer consulta hierárquica = JOIN O(1), sem WITH RECURSIVE
-- ❌ Escrita custosa: inserir/mover nó atualiza N linhas de closure

4. Nested set

Cada nó guarda dois números (left/right) que codificam sua posição numa varredura em profundidade. Leitura de subárvore vira um simples BETWEEN, mas qualquer inserção renumera grande parte da árvore. Hoje é raramente recomendado: a closure table entrega leituras igualmente rápidas com escrita muito menos dolorosa.

Índices

Um índice é a diferença entre uma query que responde em 2 milissegundos e a mesma query que demora 8 segundos. Mas índice não é mágica gratuita — é uma estrutura de dados paralela que troca custo de escrita e espaço por velocidade de leitura. Este capítulo constrói o modelo mental certo: o que um índice realmente é, por que cada um deles desacelera escritas, como o B-tree funciona e o que ele não consegue fazer, a regra do prefixo em índices compostos, índices parciais/de expressão/covering, e quando os tipos especializados (GIN, GiST, BRIN, Hash, SP-GiST) ganham.

# O modelo mental: o índice de um livro

A analogia é literal e exata. Sem índice, encontrar "onde o livro fala de MVCC" exige ler o livro inteiro página por página — um sequential scan. Com o índice remissivo no fim do livro, você vai direto: "MVCC … p. 142". O índice é uma cópia ordenada de uma informação (o termo) apontando para onde o dado completo está (a página). Três consequências decorrem dessa analogia e governam tudo:

  • O índice ocupa espaço próprio. O índice remissivo são páginas extras no livro. Em um banco, cada índice é uma estrutura em disco, separada da tabela.
  • Toda escrita atualiza o índice também. Se você adiciona um parágrafo sobre MVCC numa nova página, o índice remissivo precisa ser corrigido. Cada INSERT/UPDATE/DELETE precisa manter todos os índices da tabela coerentes.
  • O índice só ajuda se a busca casar com a ordem dele. Um índice por termo não ajuda a achar "a 3ª palavra mais longa do livro". A estrutura do índice tem que se alinhar ao padrão da query.
Performance & custo
A regra econômica fundamental: índices aceleram leitura e desaceleram escrita. Uma tabela com 6 índices paga, em cada INSERT, a inserção na heap mais 6 manutenções de índice. Tabelas de escrita intensa com índices de leitura raramente usados são um anti-padrão comum e caro. A pergunta antes de criar um índice nunca é "isso pode ajudar alguma query?" e sim "o ganho de leitura justifica o custo permanente de escrita e espaço?".

# B-tree: o índice padrão

Quando você escreve CREATE INDEX sem especificar tipo, ganha um B-tree — uma árvore balanceada que mantém as chaves ordenadas. Essa ordenação é o que ele sabe fazer, e define exatamente suas capacidades.

btree.sql
-- O B-tree atende, eficientemente:
CREATE INDEX ON orders(user_id);

SELECT * FROM orders WHERE user_id = 7;          -- igualdade ✅
SELECT * FROM orders WHERE user_id > 100;        -- faixa ✅
SELECT * FROM orders WHERE user_id BETWEEN 10 AND 20; -- faixa ✅
SELECT * FROM orders ORDER BY user_id;            -- ordenação ✅ (sem sort)
SELECT * FROM products WHERE nome LIKE 'Camis%';   -- prefixo ✅
SELECT * FROM orders WHERE user_id IS NULL;       -- IS NULL ✅

-- O B-tree NÃO ajuda em:
SELECT * FROM products WHERE nome LIKE '%camiseta%'; -- contém ❌ (sem prefixo)
SELECT * FROM products WHERE nome ILIKE 'camis%';  -- ILIKE ❌ (case difere da ordem)
SELECT * FROM products WHERE lower(nome) = 'x'; -- função ❌ (índice é de nome, não de lower(nome))
-- Para esses casos: índice de expressão, ou GIN/pg_trgm (adiante)

# Índices compostos e a regra do prefixo

Um índice em várias colunas, (a, b, c), ordena primeiro por a, depois por b dentro de cada a, depois por c. A consequência — a regra mais importante de indexação composta — é o leftmost prefix: o índice serve para predicados que usam um prefixo das colunas, da esquerda para a direita.

indice_composto.sql
CREATE INDEX idx_oi ON order_items(order_id, product_id, quantidade);

-- ✅ USA o índice (prefixo da esquerda):
WHERE order_id = 42                                  -- (order_id)
WHERE order_id = 42 AND product_id = 10           -- (order_id, product_id)
WHERE order_id = 42 AND product_id = 10 AND quantidade > 1

-- ❌ NÃO usa eficientemente (pula a 1ª coluna do índice):
WHERE product_id = 10                                -- sem order_id, o índice não ordena por product_id
WHERE quantidade > 1                                  -- idem

-- Analogia: lista telefônica ordenada por (sobrenome, nome).
-- Achar "Silva" → rápido. Achar "Silva, João" → rápido.
-- Achar todos os "João" (qualquer sobrenome) → varre tudo.

-- Regra de ORDENAÇÃO das colunas no índice composto:
-- 1º colunas de IGUALDADE, depois a coluna de FAIXA/ORDER BY.
-- Para: WHERE status='pago' AND criado_em > X ORDER BY criado_em
CREATE INDEX ON orders(status, criado_em);
-- status (igualdade) primeiro; criado_em (faixa+ordenação) depois.
Nota
A direção (ASC/DESC) só importa em índices compostos quando o ORDER BY mistura direções. Para ORDER BY a ASC, b DESC, um índice (a ASC, b ASC) não evita o sort — você precisa de (a ASC, b DESC). Para um único ORDER BY col, o B-tree é lido para frente ou para trás sem custo, então a direção é irrelevante.

# Covering index e index-only scan

Normalmente, o índice diz "a linha está aqui" e o banco vai à tabela buscar as colunas pedidas (um heap fetch). Se todas as colunas necessárias já estão no índice, o banco responde sem tocar na tabela — um index-only scan, drasticamente mais rápido. A cláusula INCLUDE adiciona colunas ao índice sem fazê-las parte da chave de ordenação.

covering_index.sql
-- Query frequente: dado o user, listar status e data dos pedidos
SELECT status, criado_em FROM orders WHERE user_id = 7;

-- Índice covering: chave = user_id; payload = status, criado_em
CREATE INDEX idx_orders_user_cover
  ON orders(user_id) INCLUDE (status, criado_em);
-- Agora a query é respondida SÓ pelo índice (index-only scan):
-- não há ida à tabela para buscar status/criado_em.

-- Diferença sutil mas importante:
--   ON orders(user_id, status)    → status faz parte da ORDENAÇÃO
--   ON orders(user_id) INCLUDE(status) → status só "viaja junto"
-- Use INCLUDE quando a coluna não é usada em WHERE/ORDER BY,
-- apenas retornada — mantém o índice menor e mais eficiente.

# Índices parciais

Um índice parcial indexa apenas as linhas que satisfazem uma condição WHERE. Quando as queries sempre filtram por um subconjunto pequeno, isso produz um índice muito menor (mais rápido, menos manutenção) e ainda pode impor unicidade condicional.

indice_parcial.sql
-- Só 2% dos pedidos estão 'pendente', mas é o que mais se consulta
CREATE INDEX idx_orders_pendentes
  ON orders(criado_em)
  WHERE status = 'pendente';
-- Índice ~50x menor que um índice total; cobre exatamente as
-- queries "fila de pendentes ordenada por data".

-- Excluir soft-deleted do índice (linhas mortas não ocupam o índice)
CREATE INDEX ON products(categoria_id)
  WHERE deletado_em IS NULL;

-- Unicidade condicional (revisita Capítulo 12):
-- "só um email ATIVO, mas histórico de inativos pode repetir"
CREATE UNIQUE INDEX ON users(email)
  WHERE deletado_em IS NULL;

-- O predicado da query precisa "casar" com o do índice para usá-lo:
SELECT * FROM orders
WHERE status = 'pendente' AND criado_em > now() - '1 day'::interval;
-- ✅ usa idx_orders_pendentes (status='pendente' bate com o WHERE do índice)

# Índices de expressão

Um índice comum em email não ajuda WHERE lower(email) = 'x' — o índice guarda email, não lower(email). A solução é indexar a expressão em si.

indice_expressao.sql
-- Busca case-insensitive eficiente
CREATE INDEX idx_users_email_lower ON users(lower(email));
SELECT * FROM users WHERE lower(email) = lower('Ana@X.com');
-- A query DEVE usar a MESMA expressão do índice para ele ser usado.

-- Indexar um campo extraído de JSONB (Capítulo 16)
CREATE INDEX ON products((metadata->>'sku'));
SELECT * FROM products WHERE metadata->>'sku' = 'ABC-123';

-- Indexar resultado de cálculo recorrente
CREATE INDEX ON order_items((quantidade * preco_unit));
-- A expressão é avaliada na escrita e armazenada no índice.

CREATE INDEX ON reservas USING GiST (periodo);
-- GiST também faz busca por vizinho mais próximo (KNN):
SELECT * FROM lojas ORDER BY localizacao <-> point(-23.5,-46.6) LIMIT 5;

-- BRIN: tabela gigante (bilhões) com criado_em sempre crescente.
-- Índice minúsculo (KBs) que guarda só min/max por bloco de páginas.
CREATE INDEX ON eventos USING BRIN (criado_em);
-- Só funciona bem se a ordem física ≈ ordem da coluna (append-only).

-- Hash: apenas igualdade. Raramente melhor que B-tree;
-- útil só quando o índice B-tree ficaria grande demais.
CREATE INDEX ON sessoes USING HASH (token);

O PG 16 acelerou a construção de índices B-tree e melhorou a paralelização de CREATE INDEX. Mais relevante no dia a dia: CREATE INDEX CONCURRENTLY constrói o índice sem bloquear escritas na tabela — essencial em produção (a versão sem CONCURRENTLY trava a tabela inteira). O PG 17 trouxe melhorias de desempenho em buscas com IN/ANY em índices B-tree e otimizações no GIN para cargas mistas.

# Quando NÃO criar um índice

Saber não indexar é tão importante quanto saber indexar. Um índice é desperdício (ou prejuízo) quando:

  • A coluna tem baixa cardinalidade. Indexar boolean ativo onde 95% é true raramente ajuda — o planner prefere seq scan, e você paga o custo de manutenção à toa. (Um índice parcial WHERE ativo = false sobre os 5% pode fazer sentido.)
  • A tabela é pequena. Em uma tabela de 200 linhas, o seq scan é mais rápido que navegar um índice. O planner sabe disso e ignora o índice — ele só pesa nas escritas.
  • A tabela é de escrita intensa e a leitura é rara. Tabela de log/eventos com milhares de inserts/s e consulta esporádica: cada índice multiplica o custo de escrita.
  • Já existe um índice que cobre o caso pelo prefixo. Ter (a, b) torna um índice só em (a) redundante para muitas queries.

  pg_size_pretty(pg_relation_size(indexrelid)) AS tamanho

WHERE  idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

FROM   pg_indexes WHERE tablename = 'orders';

CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);

REINDEX INDEX CONCURRENTLY idx_orders_user_id;
Dica
Fluxo prático de indexação: (1) não crie índices "por garantia"; (2) deixe a aplicação rodar e use pg_stat_statements para achar as queries lentas reais; (3) rode EXPLAIN (ANALYZE, BUFFERS) nelas; (4) crie o índice mínimo que transforma Seq Scan em Index Scan — geralmente um composto bem ordenado ou um parcial; (5) revisite periodicamente pg_stat_user_indexes e remova os com idx_scan = 0. Índice é dívida com juros: só contraia o que paga.

# Operadores de navegação

operadores_jsonb.sql
-- -> : navega por chave/índice, retorna jsonb
SELECT metadata->'marca'           FROM products;  -- → "Acme" (jsonb com aspas)
SELECT metadata->'dimensoes'->'altura' FROM products;  -- → 20 (jsonb)
SELECT metadata->'tags'->0        FROM products;  -- → "oferta" (jsonb, índice de array)

-- ->> : navega, retorna TEXT (sem aspas — para comparar com strings)
SELECT metadata->>'marca'          FROM products;  -- → Acme (text)
SELECT * FROM products WHERE metadata->>'marca' = 'Acme';

-- #> : caminho como array de chaves, retorna jsonb
SELECT metadata #> '{dimensoes,altura}'  FROM products;  -- → 20
SELECT metadata #> '{tags,0}'            FROM products;  -- → "oferta"

-- #>> : caminho como array, retorna TEXT
SELECT metadata #>> '{dimensoes,largura}' FROM products;  -- → 30 (text)

-- @> : o lado esquerdo CONTÉM o lado direito (teste de inclusão)
SELECT * FROM products
WHERE metadata @> '{"marca": "Acme"}';         -- marca é Acme
WHERE metadata @> '{"tags": ["oferta"]}';      -- tem a tag "oferta"

-- <@ : o lado esquerdo está CONTIDO no lado direito
SELECT '{"marca":"Acme"}'::jsonb <@ metadata FROM products;

-- ? : chave de primeiro nível existe?
SELECT * FROM products WHERE metadata ? 'cor';

-- ?| : qualquer uma das chaves existe?
SELECT * FROM products WHERE metadata ?| ARRAY['cor', 'tamanho'];

-- ?& : todas as chaves existem?
SELECT * FROM products WHERE metadata ?& ARRAY['marca', 'cor'];
Nota
-> retorna jsonb (strings vêm com aspas: "Acme"); ->> retorna text (sem aspas: Acme). Use -> para navegar em profundidade e ->> na folha quando for comparar com uma string SQL. Comparar com -> requer cast: metadata->'ativo' = 'true'::jsonb.

  jsonb_build_object('id', id, 'nome', nome, 'preco', preco)
  ORDER BY preco DESC
) AS produtos
FROM products
WHERE ativo;

-- Objetos agrupados: {categoria: [produtos]}
SELECT
  c.nome AS categoria,
  jsonb_agg(jsonb_build_object('id', p.id, 'nome', p.nome)) AS produtos
FROM   categories c
JOIN   products p ON p.categoria_id = c.id
GROUP BY c.id, c.nome;

manipulacao_jsonb.sql

WHERE  id = 1;

WHERE  id = 1;

-- #- : remover pelo caminho

WHERE  id = 1;

-- jsonb_set: definir valor num caminho
UPDATE products
SET    metadata = jsonb_set(
  metadata,
  '{dimensoes,altura}',
  '25',             -- novo valor (deve ser jsonb válido)
  true              -- criar chave se não existir
)
WHERE  id = 1;

UPDATE products
SET    metadata = jsonb_insert(
  metadata,
  '{tags,0}',        -- posição (antes do índice 0)

  false              -- false=antes, true=depois
)
WHERE  id = 1;

# SQL/JSON — construtores do padrão (PG 16/17)

PostgreSQL 16/17
O PG 16 implementou os construtores SQL/JSON do padrão SQL:2016 (JSON_OBJECT, JSON_ARRAY, JSON_ARRAYAGG, JSON_OBJECTAGG) e o PG 17 completou a implementação com JSON_TABLE, JSON_EXISTS, JSON_VALUE e JSON_QUERY — uma API padrão portável equivalente aos operadores proprietários do PostgreSQL.
sql_json_standard.sql
-- JSON_OBJECT (padrão SQL, PG 16+): equivale a jsonb_build_object
SELECT JSON_OBJECT('id' VALUE id, 'nome' VALUE nome
                   RETURNING jsonb)
FROM products;

-- JSON_ARRAYAGG (padrão SQL, PG 16+): equivale a jsonb_agg
SELECT JSON_ARRAYAGG(nome ORDER BY preco RETURNING jsonb)
FROM   products;

-- JSON_EXISTS: testar caminho (PG 17+)
SELECT * FROM products
WHERE  JSON_EXISTS(metadata, '$.tags[*] ? (@ == "oferta")');

-- JSON_VALUE: extrair valor escalar com tipo (PG 17+)
SELECT JSON_VALUE(metadata, '$.marca' RETURNING text)
FROM   products;

-- JSON_TABLE: converter JSON em tabela relacional (PG 17+)
SELECT jt.*
FROM   products,
       JSON_TABLE(metadata, '$.tags[*]' COLUMNS (
         tag text PATH '$'
       )) AS jt
WHERE  id = 1;
-- → "oferta" / "novo" como linhas relacionais com FK implícita

# Indexação GIN

gin_jsonb.sql
-- GIN padrão: indexa TODAS as chaves e valores aninhados
-- Suporta: @>, <@, ?, ?|, ?&
CREATE INDEX idx_products_meta_gin
  ON products USING GIN (metadata);

-- jsonb_path_ops: índice menor, só suporta @> (suficiente na maioria)
CREATE INDEX idx_products_meta_path
  ON products USING GIN (metadata jsonb_path_ops);

-- Query que usa o índice GIN:
SELECT * FROM products
WHERE  metadata @> '{"marca":"Acme"}';       -- ✅ usa GIN

-- Query que NÃO usa GIN (usa ->>): precisa de índice de expressão
SELECT * FROM products
WHERE  metadata->>'marca' = 'Acme';          -- ❌ GIN não ajuda

-- Para ->> com filtro, crie índice de expressão B-tree:
CREATE INDEX ON products((metadata->>'marca'));    -- ✅ usa este
Performance & custo
GIN padrão é maior e suporta mais operadores; jsonb_path_ops é ~30% menor e mais rápido para @>, mas só suporta esse operador. Escolha: use jsonb_path_ops quando a única operação é "contém", e o GIN padrão quando precisa de ?/?|/?&. Para buscar por valor de chave específica com muito filtro (->>'marca' = 'Acme'), um índice B-tree de expressão é mais seletivo que o GIN.

# JSONB vs relacional — quando usar cada um

jsonb_vs_relacional.txt
// Use JSONB quando:
// - Os atributos variam por linha (catálogo de produtos com specs diferentes:
//   notebook tem RAM/SSD, camisa tem cor/tamanho/tecido)
// - O schema muda frequentemente e você quer evitar migrations
// - Os dados chegam como JSON de APIs externas e você quer guardar o payload
// - Poucos atributos precisam de filtro indexado

// Use RELACIONAL quando:
// - Todos os atributos aparecem em quase todas as linhas
// - Você filtra/ordena/agrega por esses atributos frequentemente
// - Precisa de FK, CHECK, NOT NULL sobre esses atributos
// - Joins com outras tabelas a partir desses valores

// Padrão híbrido (o mais comum na prática):
// Colunas relacionais para atributos ESTÁVEIS + jsonb para extras VARIÁVEIS
// products: id, nome, preco, estoque (colunas) + metadata jsonb (flexível)
// Nunca: tudo em jsonb e queries ->> para tudo — perde constraints e performance.

# Arrays

Arrays são listas homogêneas de valores do mesmo tipo, armazenadas numa coluna. Ao contrário do anti-padrão de CSV em string (Capítulo 13), arrays têm tipo, operadores, indexação GIN e a função unnest para "explodir" em linhas.

arrays.sql
-- Declarar coluna de array
ALTER TABLE products ADD COLUMN tags text[];        -- array de texto
ALTER TABLE orders   ADD COLUMN notificados bigint[]; -- array de ids

-- Inserir e atualizar
UPDATE products
SET    tags = ARRAY['oferta', 'novo', 'destaque']
WHERE  id = 1;

-- Acessar elementos (índice começa em 1 no PostgreSQL!)
SELECT tags[1]          FROM products;  -- primeiro elemento
SELECT tags[2:3]        FROM products;  -- slice: elementos 2 e 3
SELECT array_length(tags, 1) FROM products;  -- tamanho da 1ª dimensão
SELECT cardinality(tags)   FROM products;  -- total de elementos

-- Operadores de conjunto
SELECT * FROM products WHERE tags @> ARRAY['oferta'];     -- contém 'oferta'
SELECT * FROM products WHERE tags && ARRAY['novo','oferta']; -- tem ao menos uma
SELECT * FROM products WHERE 'destaque' = ANY(tags);        -- contém (alternativa)

-- Manipulação
SELECT tags || ARRAY['premium']     FROM products;  -- concatenar (|| append)
SELECT array_append(tags, 'premium') FROM products;  -- equivalente
SELECT array_prepend('urgente', tags)FROM products;  -- prepend
SELECT array_remove(tags, 'novo')   FROM products;  -- remover valor

-- array_cat: concatenar dois arrays
SELECT array_cat(ARRAY[1,2], ARRAY[3,4]);  -- → {1,2,3,4}

-- unnest: "explodir" array em linhas (para JOIN, filtro, agregação)
SELECT p.id, p.nome, unnest(p.tags) AS tag
FROM   products p;
-- Cada produto aparece N vezes, uma por tag

-- "Contar quantos produtos por tag"
SELECT unnest(tags) AS tag, count(*)
FROM   products
GROUP BY 1
ORDER BY 2 DESC;

-- Indexar com GIN para @> e &&
CREATE INDEX ON products USING GIN(tags);
Dica
O índice começa em 1, não em 0 — diferente de todas as linguagens modernas. tags[0] retorna NULL silenciosamente. Use tags[1] para o primeiro elemento. Também note que = ANY(tags) funciona como um "contém" legível e pode usar o índice GIN, enquanto tags[1] = 'x' não usa GIN (compara só o primeiro elemento).

# Enum

Um tipo ENUM é uma lista estática de valores texto nomeados. Compacto (4 bytes como inteiro internamente), seguro (o banco rejeita valores fora da lista) e ordenável (respeita a ordem de declaração).

enum.sql
-- Criar o tipo enum
CREATE TYPE status_pedido AS ENUM (
  'pendente', 'pago', 'enviado', 'entregue', 'cancelado'
);

-- Usar na tabela
ALTER TABLE orders
  ALTER COLUMN status TYPE status_pedido
  USING status::status_pedido;

-- Ordenação segue a ordem de declaração (não alfabética!)
SELECT * FROM orders ORDER BY status;
-- → pendente, pago, enviado, entregue, cancelado

-- Adicionar valor ao enum (sempre ao final ou em posição específica)
ALTER TYPE status_pedido ADD VALUE 'devolvido' AFTER 'entregue';

-- Listar valores de um enum
SELECT unnest(enum_range(NULL::status_pedido));

-- Renomear valor (PG 10+)
ALTER TYPE status_pedido RENAME VALUE 'cancelado' TO 'cancelado_cliente';

-- Remover enum só funciona se nenhuma coluna o usa
DROP TYPE status_pedido;  -- falha se orders.status ainda usar
Atenção
ADD VALUE ao enum não pode ser revertido com ROLLBACK dentro de uma transação — ele é automaticamente confirmado. Para adicionar valores e usá-los na mesma transação é preciso confirmar o ADD VALUE antes. Em migrações, separe o ADD VALUE num passo anterior à alteração de tabelas que dependem do novo valor. Uma alternativa mais flexível é text + CHECK, que permite alterar facilmente via migration padrão.

# Range — intervalos com semântica

Tipos range representam intervalos com inclusão/exclusão de limites — perfeitos para períodos de validade, faixas de preço, janelas de tempo. O PostgreSQL impõe a semântica de intervalo (limites, sobreposição, contenção) nativamente.

range_types.sql
-- Tipos de range embutidos
-- int4range, int8range, numrange, daterange, tsrange, tstzrange

-- Notação: [a,b] ambos incluídos | (a,b) ambos excluídos | [a,b) misto
SELECT '[2025-01-01, 2025-12-31]'::daterange;
SELECT '[2025-01-15 10:00, 2025-01-15 12:00)'::tstzrange;

-- Criar coluna de período de validade de promoção
ALTER TABLE promocoes ADD COLUMN periodo tstzrange NOT NULL;

INSERT INTO promocoes (nome, periodo)
VALUES ('Black Friday', '[2025-11-28 00:00, 2025-11-29 00:00)');

-- Operadores de range
SELECT * FROM promocoes
WHERE  periodo @> now();          -- promoção ativa agora (now() está dentro)

SELECT * FROM promocoes
WHERE  periodo &&                    -- sobreposição com um período
       '[2025-11-01, 2025-12-01)'::tstzrange;

-- Extrair limites
SELECT
  lower(periodo)              AS inicio,
  upper(periodo)              AS fim,
  lower_inc(periodo)          AS inicio_incluso,
  upper_inf(periodo)          AS sem_fim
FROM promocoes;

-- Construir range dinamicamente
SELECT tstzrange(now(), now() + '7 days'::interval, '[)');

-- Prevenção de sobreposição via EXCLUDE (Capítulo 12)
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE reservas
  ADD CONSTRAINT sem_sobreposicao
  EXCLUDE USING GiST (sala_id WITH =, periodo WITH &&);
Nota
Para ranges de números inteiros, use int4range/int8range em vez de dois campos inicio/fim. O PostgreSQL normaliza automaticamente: [1,5) e [1,4] são representados igual internamente. Isso evita a ambiguidade clássica de "o limite superior é incluso ou excluso?" e torna as queries de sobreposição sempre corretas.

# Domain — tipo com restrição reutilizável

Um DOMAIN é um alias de tipo com constraints embutidas, reusável em múltiplas colunas/tabelas. Centraliza a validação num lugar só.

domain.sql
-- Criar domínios reutilizáveis
CREATE DOMAIN email_valido AS text
  CHECK (VALUE ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$');

CREATE DOMAIN preco_positivo AS numeric(10,2)
  NOT NULL
  CHECK (VALUE >= 0);

CREATE DOMAIN cep_br AS text
  CHECK (VALUE ~ '^[0-9]{5}-?[0-9]{3}$');

-- Usar em colunas — a constraint é herdada automaticamente
CREATE TABLE users (
  id    bigint        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email email_valido  NOT NULL UNIQUE,
  cep   cep_br
);

CREATE TABLE products (
  id    bigint        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  preco preco_positivo  -- já inclui NOT NULL e CHECK >= 0
);

-- Alterar domínio afeta TODAS as colunas que o usam
ALTER DOMAIN email_valido
  ADD CONSTRAINT tamanho_maximo CHECK (length(VALUE) <= 254);

-- Listar domínios do banco
SELECT typname, pg_get_constraintdef(oid)
FROM   pg_type t
JOIN   pg_constraint c ON c.contypid = t.oid
WHERE  t.typtype = 'd';

# Tipos compostos

Um tipo composto agrupa campos em uma estrutura — como uma struct. Útil para funções que retornam múltiplas colunas e para representar sub-objetos que aparecem em várias tabelas.

composite.sql
-- Criar tipo composto
CREATE TYPE endereco AS (
  rua     text,
  numero  text,
  cidade  text,
  uf      char(2),
  cep     text
);

-- Usar na tabela
ALTER TABLE orders ADD COLUMN entrega endereco;

-- Inserir e acessar campos
UPDATE orders
SET    entrega = ROW('Av. Paulista', '1000', 'São Paulo', 'SP', '01310-100')
WHERE  id = 1;

-- Acessar campo com notação de ponto (alias necessário)
SELECT (entrega).cidade, (entrega).uf
FROM   orders
WHERE  (entrega).uf = 'SP';

-- Função que retorna tipo composto
CREATE FUNCTION buscar_endereco(order_id bigint)
RETURNS endereco AS $$
  SELECT entrega FROM orders WHERE id = order_id;
$$ LANGUAGE SQL STABLE;

# hstore — chave-valor dentro de uma coluna

hstore é o precursor do jsonb para atributos chave-valor simples (sem aninhamento, sem arrays). Menor e mais rápido para casos simples; hoje a maioria prefere jsonb pela riqueza de operadores.

hstore.sql
CREATE EXTENSION IF NOT EXISTS hstore;

ALTER TABLE products ADD COLUMN attrs hstore;

UPDATE products
SET    attrs = 'cor => preto, tamanho => M, material => algodão'
WHERE  id = 1;

-- Acessar valor por chave
SELECT attrs->'cor'      FROM products;  -- → 'preto'

-- Filtrar por chave/valor
SELECT * FROM products WHERE attrs @> 'cor => preto';
SELECT * FROM products WHERE attrs ?  'cor';   -- chave existe

-- Converter hstore em pares de linhas
SELECT (each(attrs)).* FROM products;

-- GIN para @> e ? rápidos
CREATE INDEX ON products USING GIN(attrs);

# ltree — caminhos hierárquicos

Revisitado do Capítulo 14: ltree representa caminhos em forma de strings de rótulos separadas por ponto — otimizado para queries de árvore com índice GiST.

ltree_ref.sql
CREATE EXTENSION IF NOT EXISTS ltree;

-- Exemplos de valores ltree
SELECT 'eletronicos.computadores.notebooks'::ltree;
SELECT nlevel('a.b.c'::ltree);   -- → 3
SELECT subpath('a.b.c.d'::ltree, 0, 2);  -- → a.b

-- Operadores (com índice GiST)
-- @> "é ancestral ou igual"  / <@ "é descendente ou igual"
-- ~ lquery (padrão simples)  / @ ltxtquery (full-text sobre labels)
SELECT * FROM categories WHERE path <@ 'eletronicos';     -- subárvore
SELECT * FROM categories WHERE path @> 'eletronicos.computadores.notebooks';
SELECT * FROM categories WHERE path ~ 'eletronicos.*{1}';  -- filhos diretos

CREATE INDEX ON categories USING GiST(path);

# generate_series — séries e relatórios densos

generate_series produz um conjunto de valores em uma sequência — essencial para preencher "buracos" em relatórios por data quando nenhum evento ocorreu naquele dia.

generate_series.sql
-- Série de inteiros
SELECT generate_series(1, 10);               -- 1 a 10
SELECT generate_series(0, 100, 10);          -- 0, 10, 20 ... 100

-- Série de datas/timestamps
SELECT d::date
FROM   generate_series(
         '2025-01-01'::date,
         '2025-12-31'::date,
         '1 day'::interval
       ) AS d;

-- Relatório de pedidos por dia — SEM buracos (dias sem pedido aparecem com 0)
WITH dias AS (
  SELECT d::date AS dia
  FROM   generate_series(
           '2025-01-01',
           '2025-01-31',
           '1 day'::interval
         ) d
)
SELECT
  dias.dia,
  count(o.id)    AS qtd_pedidos,
  coalesce(sum(o.total), 0) AS receita
FROM   dias
LEFT JOIN orders o
       ON o.criado_em::date = dias.dia
      AND o.status = 'pago'
GROUP BY dias.dia
ORDER BY dias.dia;

-- Série mensal para relatório de receita por mês
SELECT date_trunc('month', d)::date AS mes
FROM   generate_series(
         '2025-01-01',
         '2025-12-01',
         '1 month'::interval
       ) d;

-- Gerar dados de teste: 1.000 produtos fictícios
INSERT INTO products (nome, preco, estoque)
SELECT
  'Produto ' || i,
  round((random() * 999 + 1)::numeric, 2),
  (random() * 100)::int
FROM   generate_series(1, 1000) AS i;
Performance & custo
generate_series é um Set Returning Function (SRF) e não materializa o resultado em memória antes de produzir — é streamada. Para séries muito grandes (milhões de pontos) em relatórios, a estratégia mais eficiente é generate_series + LEFT JOIN (como no exemplo acima), não um loop na aplicação. O planner consegue usar índices nas tabelas joinadas normalmente.

Capítulo 18

Funções, triggers e views

Este capítulo trata da pergunta mais política da engenharia de dados: quanta lógica deve viver dentro do banco?. Funções encapsulam computação reutilizável; triggers reagem automaticamente a mudanças; views abstraem queries complexas; materialized views trocam frescor por velocidade. Cada ferramenta é poderosa e perigosa na mesma medida — usá-las bem exige entender não só a sintaxe, mas o critério de quando a lógica pertence ao banco e quando ela vira complexidade escondida.

# O modelo mental: lógica perto do dado

O argumento a favor de lógica no banco é a proximidade e a garantia: uma regra que vive numa CHECK, num trigger ou numa constraint vale para toda escrita — pela aplicação, por um script ad-hoc, por uma migração, por um DBA no psql. O argumento contra é a opacidade: lógica em triggers é invisível para quem lê só o código da aplicação, difícil de versionar, testar e depurar. A regra de ouro deste capítulo: integridade e invariantes pertencem ao banco; regras de negócio que mudam com frequência e fluxos de orquestração pertencem à aplicação.

# Funções: SQL vs PL/pgSQL

O PostgreSQL tem duas linguagens principais para funções. SQL é declarativa, simples, e o planner consegue "inline-á-la". PL/pgSQL é procedural — tem variáveis, loops, condicionais, tratamento de exceção — necessária quando há lógica que SQL puro não expressa.

funcoes_sql.sql
-- Função SQL: corpo é uma única expressão/query. Preferível quando dá.
CREATE FUNCTION total_pedido(p_order_id bigint)
RETURNS numeric AS $$
  SELECT coalesce(sum(quantidade * preco_unit), 0)
  FROM   order_items
  WHERE  order_id = p_order_id;
$$ LANGUAGE SQL STABLE;

SELECT total_pedido(42);
SELECT id, total_pedido(id) FROM orders;  -- usável como coluna

-- Nova sintaxe SQL-standard (PG 14+): corpo sem $$ e mais segura
CREATE FUNCTION preco_com_imposto(p_preco numeric, p_taxa numeric)
RETURNS numeric
RETURN p_preco * (1 + p_taxa);   -- corpo de expressão única, sem $$
funcoes_plpgsql.sql
-- PL/pgSQL: necessário quando há lógica procedural
CREATE FUNCTION aplicar_desconto(
  p_product_id bigint,
  p_pct        numeric
)
RETURNS numeric AS $$
DECLARE
  v_preco_atual numeric;
  v_novo_preco  numeric;
BEGIN
  SELECT preco INTO v_preco_atual
  FROM   products WHERE id = p_product_id;

  IF v_preco_atual IS NULL THEN
    RAISE EXCEPTION 'Produto % não encontrado', p_product_id;
  END IF;

  IF p_pct < 0 OR p_pct > 100 THEN
    RAISE EXCEPTION 'Desconto inválido: %', p_pct
      USING ERRCODE = 'check_violation';
  END IF;

  v_novo_preco := v_preco_atual * (1 - p_pct / 100.0);

  UPDATE products
  SET    preco = v_novo_preco, atualizado_em = now()
  WHERE  id = p_product_id;

  RETURN v_novo_preco;
END;
$$ LANGUAGE plpgsql;

Categorias de volatilidade — não é detalhe, é performance

Toda função declara sua volatilidade, e o planner usa isso agressivamente para otimizar. Errar essa marcação causa bugs sutis ou perda de desempenho.

CategoriaSignificaExemplo
IMMUTABLEMesma entrada → sempre mesma saída; sem acesso ao bancolower(text), x * 2
STABLEConstante dentro de uma query; pode ler o banconow(), lookups por id
VOLATILE (padrão)Pode mudar a cada chamada; pode ter efeitosrandom(), INSERT/UPDATE
Atenção
A volatilidade tem consequências reais: só funções IMMUTABLE podem ser usadas em índices de expressão (Capítulo 15) e o planner só pré-avalia constantes de funções IMMUTABLE. Marcar uma função que lê o banco como IMMUTABLE "para ela ser indexável" produz índices corrompidos silenciosamente — o índice não reflete mudanças. Quando em dúvida, deixe o padrão VOLATILE; só promova a STABLE/IMMUTABLE quando a semântica realmente garantir.

returns_table.sql
-- RETURNS TABLE: função que se comporta como uma tabela/view parametrizada
CREATE FUNCTION pedidos_do_cliente(p_user_id bigint)
RETURNS TABLE (
  pedido_id bigint,
  status    text,
  total     numeric,
  criado_em timestamptz
) AS $$
  SELECT
    o.id,
    o.status,
    total_pedido(o.id),
    o.criado_em
  FROM   orders o
  WHERE  o.user_id = p_user_id

SELECT * FROM pedidos_do_cliente(7);

-- RETURNS SETOF tipo_existente: retorna linhas de uma tabela existente
CREATE FUNCTION produtos_ativos()
RETURNS SETOF products AS $$
  SELECT * FROM products WHERE ativo AND deletado_em IS NULL;
$$ LANGUAGE SQL STABLE;

# Triggers: efeitos colaterais automáticos

Um trigger é uma função executada automaticamente quando um evento (INSERT/UPDATE/DELETE) ocorre numa tabela. O modelo mental crucial: é um efeito colateral invisível. Quem escreve UPDATE products SET preco = 10 pode não saber que isso dispara três triggers. Esse é o seu poder (garantia) e seu perigo (opacidade).

trigger_updated_at.sql
-- Caso clássico e legítimo: manter atualizado_em sempre coerente
CREATE FUNCTION set_atualizado_em()
RETURNS trigger AS $$
BEGIN
  NEW.atualizado_em := now();
  RETURN NEW;          -- BEFORE: o NEW retornado é o que será gravado
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_products_atualizado
  BEFORE UPDATE ON products
  FOR EACH ROW
  EXECUTE FUNCTION set_atualizado_em();
-- Agora QUALQUER UPDATE em products mantém atualizado_em correto,
-- mesmo um UPDATE manual no psql. Garantia que CHECK não dá.
trigger_auditoria.sql
-- BEFORE vs AFTER vs INSTEAD OF — o modelo mental:
--   BEFORE     : roda ANTES de gravar; pode alterar/cancelar NEW
--   AFTER      : roda DEPOIS de gravar; ideal para side-effects
--   INSTEAD OF : substitui a operação (só em views)
-- FOR EACH ROW (uma vez por linha) vs FOR EACH STATEMENT (uma vez)

-- AFTER para auditoria: registrar mudanças de preço numa tabela de log
CREATE TABLE products_audit (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  product_id  bigint,
  preco_antigo numeric,
  preco_novo  numeric,
  mudou_em    timestamptz NOT NULL DEFAULT now()
);

CREATE FUNCTION audit_preco()
RETURNS trigger AS $$
BEGIN
  IF NEW.preco IS DISTINCT FROM OLD.preco THEN
    INSERT INTO products_audit (product_id, preco_antigo, preco_novo)
    VALUES (OLD.id, OLD.preco, NEW.preco);
  END IF;
  RETURN NEW;        -- em AFTER, o retorno é ignorado (convenção: NEW)
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_audit_preco
  AFTER UPDATE OF preco ON products   -- só dispara se 'preco' mudou
  FOR EACH ROW
  EXECUTE FUNCTION audit_preco();

-- Variáveis especiais no trigger: NEW, OLD, TG_OP, TG_TABLE_NAME...
-- TG_OP é 'INSERT' | 'UPDATE' | 'DELETE' — para triggers genéricos
Performance & custo
Triggers FOR EACH ROW rodam uma vez por linha afetada — um UPDATE que toca 1 milhão de linhas executa a função 1 milhão de vezes. Para lógica que pode ser agregada, um trigger FOR EACH STATEMENT com as tabelas de transição (REFERENCING NEW TABLE AS ..., PG 10+) processa tudo num único INSERT ... SELECT — ordens de magnitude mais rápido. Triggers também são invisíveis no plano: uma carga lenta misteriosa frequentemente é um trigger esquecido.

# Views — abstração de queries

Uma view é uma query salva com nome. Não armazena dados — é reescrita na query que a referencia. Serve para encapsular complexidade, criar uma camada estável sobre o schema e restringir acesso (uma view pode expor só certas colunas/linhas).

views.sql
-- View: a "interface pública" de uma query complexa
CREATE VIEW vw_pedidos_resumo AS
SELECT
  o.id,
  u.nome      AS cliente,
  o.status,
  count(oi.product_id) AS qtd_itens,
  coalesce(sum(oi.quantidade * oi.preco_unit), 0) AS total,
  o.criado_em
FROM   orders o
JOIN   users u ON u.id = o.user_id
LEFT JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, u.nome, o.status, o.criado_em;

-- Consultada como uma tabela qualquer
SELECT * FROM vw_pedidos_resumo WHERE total > 500;

-- View com segurança: expõe só dados não-sensíveis
CREATE VIEW vw_users_publico AS
SELECT id, nome FROM users;  -- esconde email, telefone, etc.

-- Views simples são ATUALIZÁVEIS automaticamente (1 tabela, sem agg)
CREATE VIEW vw_produtos_ativos AS
SELECT id, nome, preco FROM products WHERE ativo;

UPDATE vw_produtos_ativos SET preco = 99 WHERE id = 1;
-- Funciona! Reescrito como UPDATE em products. Para views complexas,
-- use um trigger INSTEAD OF para definir a semântica de escrita.

-- WITH CHECK OPTION: impede gravar linha que sairia da view
CREATE VIEW vw_caros AS
SELECT * FROM products WHERE preco > 100
WITH CHECK OPTION;  -- UPDATE que põe preco<=100 é rejeitado

# Materialized views — snapshot pré-computado

Uma view comum recalcula a query toda vez. Uma materialized view armazena o resultado fisicamente — leitura instantânea, ao custo de os dados ficarem "congelados" até um REFRESH. É a ferramenta certa para agregações caras consultadas com muito mais frequência do que mudam (dashboards, relatórios analíticos).

materialized_view.sql
CREATE MATERIALIZED VIEW mv_receita_mensal AS
SELECT
  date_trunc('month', o.criado_em)::date  AS mes,
  count(DISTINCT o.id)                  AS pedidos,
  sum(oi.quantidade * oi.preco_unit)   AS receita
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.id
WHERE  o.status = 'pago'
GROUP BY 1
WITH DATA;

-- Leitura é instantânea — não recomputa o agregado
SELECT * FROM mv_receita_mensal ORDER BY mes;

-- REFRESH simples: BLOQUEIA leituras enquanto recomputa
REFRESH MATERIALIZED VIEW mv_receita_mensal;

-- REFRESH CONCURRENTLY: NÃO bloqueia leitores (requer índice UNIQUE)
CREATE UNIQUE INDEX ON mv_receita_mensal (mes);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_receita_mensal;
-- CONCURRENTLY é mais lento de rodar, mas a app continua lendo.

-- Estratégias de refresh:
-- 1. Agendado (pg_cron / cron externo): a cada hora/noite
-- 2. Sob demanda após carga de dados (ETL chama o REFRESH)
-- 3. Trigger (raro — refrescar a cada escrita anula o ganho)
PostgreSQL 16/17
O PG 16/17 melhorou o planejamento de queries sobre materialized views e a paralelização do REFRESH. Para "materialized view incremental" de verdade (refrescar só o que mudou), o ecossistema usa a extensão pg_ivm ou se modela manualmente com tabelas-resumo mantidas por trigger. O PostgreSQL nativo ainda só oferece refresh completo — planeje o agendamento de acordo com a janela de frescor que o negócio tolera.

Dica
Use o banco para: invariantes de integridade (constraints, triggers de validação que devem valer sempre), auditoria/temporização (atualizado_em, logs de mudança que não podem ser burlados), e abstração de leitura (views, materialized views para relatórios). Capítulo 19

Full-text search

O PostgreSQL tem um mecanismo de busca textual completo, sem extensões externas: índice invertido (GIN), stemming por idioma, ranking de relevância e sintaxe de busca amigável. É adequado para buscas em catálogos de produtos, bases de documentos e campos de texto médios — substituindo muitos casos de uso de Elasticsearch para volumes de até dezenas de milhões de documentos. Este capítulo cobre os dois tipos fundamentais (tsvector/tsquery), as funções de conversão, ranking com ts_rank, configurações de idioma e o padrão de produção com coluna gerada e índice GIN.

# O modelo mental: tokens e lexemas

tsvector é o documento processado: as palavras são normalizadas em lexemas (forma raiz), as stopwords são removidas e cada lexema recebe a posição onde ocorreu. tsquery é a consulta: uma expressão booleana de lexemas que o banco compara contra o vetor.

fts_conceito.sql
-- to_tsvector: transforma texto em vetor de lexemas
SELECT to_tsvector('portuguese', 'Camisetas listradas de algodão para crianças');
-- → 'algodão':5 'camis':1 'criança':7 'listrad':2
-- Removeu 'de' e 'para' (stopwords); stemming: camisetas→camis, listradas→listrad

-- to_tsquery: converte termo de busca em tsquery
SELECT to_tsquery('portuguese', 'camiseta & algodão');
-- → 'camis' & 'algodão'  (aplicou o mesmo stemming)

-- Operador @@: verifica se o documento contém a query
SELECT
  to_tsvector('portuguese', 'Camiseta de algodão listrada')
    @@
  to_tsquery('portuguese', 'camiseta & algodão');
-- → true

# Funções de conversão de query

Há quatro funções para criar tsquery, cada uma com um nível diferente de poder e tolerância a entrada do usuário:

tsquery_funcoes.sql
-- to_tsquery: requer sintaxe de operadores (&, |, !, ") — uso interno
SELECT to_tsquery('portuguese', 'camiseta & (algodão | poliéster) & !sintético');

-- plainto_tsquery: trata entrada como AND implícito — tolerante
SELECT plainto_tsquery('portuguese', 'camiseta algodão listrada');
-- → 'camis' & 'algodão' & 'listrad'  (AND de todos os termos)

-- phraseto_tsquery: termos devem aparecer em sequência
SELECT phraseto_tsquery('portuguese', 'camiseta algodão');
-- → 'camis' <-> 'algodão'  (adjacentes, nesta ordem)

-- websearch_to_tsquery: sintaxe amigável ao usuário (recomendado p/ inputs externos)
-- "frase exata", -palavra (NOT), OR explícito
SELECT websearch_to_tsquery('portuguese', 'camiseta algodão -sintético');
-- → 'camis' & 'algodão' & !'sintét'
SELECT websearch_to_tsquery('portuguese', '"camiseta algodão" OR "camisa linho"');

-- Operadores de tsquery: & (AND), | (OR), ! (NOT), <-> (adjacente)
SELECT to_tsquery('portuguese', 'camiseta <2> algodão');
-- <N> : separação de até N posições entre termos
Dica
Para campos de busca onde o usuário digita livremente, use sempre websearch_to_tsquery — ela não lança erro com entrada malformada (como faria to_tsquery) e entende aspas para frase exata e hífen para exclusão. É a função mais segura e natural para inputs de busca de usuário.

# Busca no e-commerce — aplicação básica

busca_basica.sql
-- Busca simples diretamente na coluna (sem índice — só para demo)
SELECT id, nome, preco
FROM   products
WHERE  to_tsvector('portuguese', nome || ' ' || coalesce(descricao, ''))
         @@ websearch_to_tsquery('portuguese', 'camiseta algodão');
-- Problema: recalcula o tsvector em todo SELECT → lento sem índice

-- Múltiplas colunas com pesos diferentes (A=mais relevante, D=menos)
SELECT id, nome
FROM   products
WHERE (
  setweight(to_tsvector('portuguese', nome), 'A') ||
  setweight(to_tsvector('portuguese', coalesce(descricao, '')), 'C')
) @@ websearch_to_tsquery('portuguese', 'algodão');

# O padrão de produção: coluna gerada + índice GIN

Recalcular o tsvector em cada query é lento para tabelas grandes. A solução idiomática é armazená-lo como coluna gerada (Capítulo 4) e indexá-la com GIN — assim o vetor é calculado na escrita (uma vez) e a busca usa o índice diretamente.

fts_producao.sql
-- 1. Adicionar coluna gerada tsvector à tabela de produtos
ALTER TABLE products
  ADD COLUMN busca tsvector
    GENERATED ALWAYS AS (
      setweight(to_tsvector('portuguese',
        coalesce(nome, '')), 'A')
      ||
      setweight(to_tsvector('portuguese',
        coalesce(descricao, '')), 'C')
    ) STORED;

-- 2. Indexar a coluna com GIN
CREATE INDEX idx_products_busca ON products USING GIN(busca);

-- 3. Buscar — o planner usa o índice GIN automaticamente
SELECT id, nome, preco
FROM   products
WHERE  busca @@ websearch_to_tsquery('portuguese', 'camiseta algodão')
ORDER BY busca <-> websearch_to_tsquery('portuguese', 'camiseta algodão')
LIMIT 20;
-- O INSERT/UPDATE mantém busca atualizada automaticamente (coluna STORED)

# Ranking com ts_rank

ts_rank.sql
-- ts_rank: relevância básica (normalizada por tamanho do documento por padrão)
SELECT
  nome,
  ts_rank(busca, websearch_to_tsquery('portuguese', 'algodão premium')) AS rank
FROM   products
WHERE  busca @@ websearch_to_tsquery('portuguese', 'algodão premium')
ORDER BY rank DESC
LIMIT 10;

-- ts_rank_cd: considera distância entre termos (cover density)
-- Penaliza documentos muito longos — boa para textos curtos como produto
SELECT
  nome,
  ts_rank_cd(busca, websearch_to_tsquery('portuguese', 'camiseta algodão'),
             32)  -- 32 = normaliza pelo tamanho único de palavras
    AS rank
FROM   products
WHERE  busca @@ websearch_to_tsquery('portuguese', 'camiseta algodão')
ORDER BY rank DESC;

-- ts_headline: retorna trecho do texto com termos destacados (para snippet)
SELECT
  nome,
  ts_headline(
    'portuguese',
    descricao,
    websearch_to_tsquery('portuguese', 'algodão premium'),
    'StartSel=<strong>, StopSel=</strong>, MaxWords=20, MinWords=10'
  ) AS trecho
FROM   products
WHERE  busca @@ websearch_to_tsquery('portuguese', 'algodão premium');
Nota
ts_headline não usa o índice GIN — ela reparseia o documento para encontrar o trecho. Use-a só nos resultados finais (os 10–20 exibidos), nunca na cláusula WHERE. O padrão é: WHERE busca @@ query (usa o índice), ORDER BY ts_rank ... DESC (ordena) e ts_headline apenas para os N resultados do LIMIT.

# pg_trgm — busca por similaridade e prefixo

Para autocompletar e tolerância a erros ortográficos, a extensão pg_trgm complementa o FTS — ela usa trigramas (sequências de 3 caracteres) para busca por similaridade e habilita o índice GIN para LIKE '%texto%' e ILIKE.

pg_trgm.sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- Índice GIN ou GiST de trigramas — habilita LIKE/ILIKE com índice!
CREATE INDEX idx_products_nome_trgm
  ON products USING GIN(nome gin_trgm_ops);

-- ILIKE agora usa o índice (antes, era seq scan)
SELECT * FROM products WHERE nome ILIKE '%camiseta%';

-- Similaridade: 0.0 (diferente) a 1.0 (igual)
SELECT nome, similarity(nome, 'camiseta') AS sim
FROM   products
WHERE  similarity(nome, 'camiseta') > 0.3
ORDER BY sim DESC;

-- Operador % : true se similarity > pg_trgm.similarity_threshold (0.3)
SELECT * FROM products WHERE nome % 'camiseta';

-- Busca por palavra mais próxima (autocompletar)
SELECT nome, word_similarity('camis', nome) AS sim
FROM   products
WHERE  'camis' <% nome         -- 'camis' está parcialmente contido
ORDER BY sim DESC
LIMIT  10;
Performance & custo
FTS com GIN e pg_trgm com GIN são complementares: FTS encontra documentos que contêm o conceito (com stemming e stopwords), pg_trgm encontra strings parecidas ou por prefixo (para autocomplete e typos). A combinação típica em produção: campo de busca principal com FTS (coluna gerada + GIN), mais autocomplete de nome com pg_trgm + GIN. Só crie os dois índices se ambos os padrões de query existem — cada índice tem custo de escrita.

Capítulo 20

Performance e EXPLAIN

Este é o capítulo onde tudo se junta. SQL é declarativo (Capítulo 1): você descreve o resultado, o query planner decide o algoritmo. Otimizar não é "escrever SQL mais rápido" — é entender o que o planner escolheu, por que escolheu, e dar a ele as condições (índices, estatísticas) para escolher melhor. Este capítulo ensina a ler EXPLAIN como quem lê um raio-X, distinguir scans, entender o papel das estatísticas, diagnosticar N+1 e bloat, e seguir uma metodologia sistemática em vez de tentativa e erro.

# O modelo mental: o planner é um estimador de custo

Para cada query, o planner gera vários planos de execução possíveis (qual índice usar, em que ordem juntar tabelas, qual algoritmo de junção) e estima um custo abstrato para cada um, escolhendo o mais barato. Esse custo não é tempo — é uma unidade relativa baseada em leituras de página e processamento de linha. A consequência prática mais importante: o planner só é tão bom quanto suas estimativas, e as estimativas dependem de estatísticas atualizadas sobre os dados. Plano ruim quase sempre significa estatística desatualizada ou índice ausente — raramente "o planner é burro".

# Lendo o EXPLAIN

EXPLAIN mostra o plano estimado. EXPLAIN ANALYZE executa a query e mostra o plano com números reais. BUFFERS adiciona quantas páginas foram lidas do cache vs disco — informação decisiva.

explain_basico.sql
-- O comando que você vai usar 90% das vezes:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT u.nome, count(*)
FROM   users u
JOIN   orders o ON o.user_id = u.id
WHERE  o.status = 'pago'
GROUP BY u.nome;

-- Saída (lida de DENTRO para FORA, de baixo para cima):
--
-- HashAggregate  (cost=215.50..230.10 rows=120 width=40)
--   (actual time=2.103..2.350 rows=118 loops=1)
--   Group Key: u.nome
--   ->  Hash Join  (cost=33.50..200.00 rows=2400 width=32)
--         (actual time=0.412..1.890 rows=2380 loops=1)
--         Hash Cond: (o.user_id = u.id)
--         ->  Seq Scan on orders o  (cost=0..120 rows=2400 ...)
--               Filter: (status = 'pago')
--               Rows Removed by Filter: 7600
--         ->  Hash  (cost=20..20 rows=1000 ...)
--               ->  Seq Scan on users u  ...
-- Planning Time: 0.350 ms
-- Execution Time: 2.480 ms

O que ler nessa saída, em ordem de importância:

  • Estimado vs real: rows=2400 (estimado) vs rows=2380 (actual) — próximos, ótimo. Discrepância grande (estimado 100, real 1.000.000) é o sinal #1 de estatística desatualizada e planos ruins.
  • Rows Removed by Filter: ler 10.000 linhas para devolver 2.400 significa que o filtro não usou índice — candidato a índice.
  • O tipo de nó: Seq Scan, Index Scan, Hash Join etc. — cada um conta uma história (a seguir).
  • loops=N: um nó com loops=5000 foi executado 5.000 vezes — sinal clássico de N+1 ou subquery correlacionada cara.
  • Execution Time vs Planning Time: se planejar demora mais que executar, a query é trivial; foque onde o tempo realmente está.
Dica
Use EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) e cole em uma ferramenta visual de plano para queries complexas — a árvore fica navegável e os nós-problema ficam destacados. Para o dia a dia, o formato TEXT lido de dentro para fora resolve. Atenção: EXPLAIN ANALYZE executa a query — para um UPDATE/DELETE, envolva em BEGIN; ... ROLLBACK; para não alterar dados de verdade.

# Seq Scan vs Index Scan — nem sempre o índice ganha

O instinto é "Seq Scan é ruim, Index Scan é bom". Errado. O planner escolhe Seq Scan quando ele é genuinamente mais rápido — e frequentemente é.

scans.sql
-- Seq Scan: lê a tabela inteira sequencialmente.
-- CORRETO quando: tabela pequena, OU a query retorna grande % das linhas.
-- Ler 80% da tabela via índice (pulando por toda parte) é MAIS LENTO
-- que ler tudo sequencialmente. O planner sabe disso.
EXPLAIN SELECT * FROM products WHERE ativo = true;
-- Se 95% é ativo=true → Seq Scan é a escolha CERTA

-- Index Scan: usa o índice p/ achar linhas, depois vai à heap buscar.
-- CORRETO quando: a query é seletiva (retorna poucas linhas).
EXPLAIN SELECT * FROM orders WHERE id = 42;
-- → Index Scan using orders_pkey (1 linha — perfeito)

-- Index Only Scan: responde SÓ pelo índice (covering, Capítulo 15)
-- Não toca a heap → o mais rápido de todos.
EXPLAIN SELECT user_id FROM orders WHERE user_id = 7;
-- → Index Only Scan (se houver índice em user_id)

-- Bitmap Heap Scan: meio-termo. Coleta os ponteiros pelo índice,
-- ordena por posição física, depois lê a heap em ordem.
-- CORRETO quando: seletividade média (não 1 linha, não 80%).
EXPLAIN SELECT * FROM orders WHERE status = 'pendente';

-- Forçar para EXPERIMENTAR (NUNCA deixar em produção):
SET enable_seqscan = off;   -- só para comparar planos no EXPLAIN
-- ... EXPLAIN ANALYZE ... compara tempo real ...
RESET enable_seqscan;
-- Se o "índice forçado" for mais lento, o planner ESTAVA certo.

# Estatísticas e ANALYZE

O planner decide entre Seq Scan e Index Scan estimando quantas linhas o predicado vai retornar. Essa estimativa vem de estatísticas amostradas: histogramas de distribuição, valores mais comuns, fração de NULLs. Quando os dados mudam muito e as estatísticas não acompanham, o planner estima errado e escolhe o plano errado.

estatisticas.sql
-- Atualizar estatísticas de uma tabela manualmente
ANALYZE orders;
ANALYZE;   -- todas as tabelas do banco

-- O autovacuum daemon roda ANALYZE automaticamente — mas após
-- uma carga MASSIVA, rode ANALYZE manualmente antes de consultar.

-- Ver estatísticas que o planner usa
SELECT attname, n_distinct, most_common_vals, null_frac
FROM   pg_stats
WHERE  tablename = 'orders' AND attname = 'status';

-- Aumentar a precisão das estatísticas de uma coluna problemática
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;   -- aplica o novo alvo de amostragem

-- Estatísticas estendidas: correlação entre colunas (PG 10+)
-- Útil quando o planner subestima por achar colunas independentes
CREATE STATISTICS st_orders (dependencies)
  ON user_id, status FROM orders;
ANALYZE orders;
Atenção
O sintoma definitivo de estatística ruim no EXPLAIN ANALYZE: a linha estimada e a real divergem por ordens de magnitude (rows=10 estimado, rows=2000000 real). Quando você vê isso, não comece a criar índices ao acaso — rode ANALYZE na tabela primeiro e refaça o EXPLAIN. Muitas "queries misteriosamente lentas" após uma carga grande são só estatísticas que o autovacuum ainda não atualizou.

# O problema N+1

O anti-padrão de performance mais comum em aplicações — e ele tem duas formas, uma na aplicação e outra dentro do próprio SQL.

n_mais_1.sql
-- N+1 NA APLICAÇÃO (o clássico de ORM):
--   1 query:  SELECT * FROM orders LIMIT 100;
--   N queries: para cada pedido, SELECT * FROM users WHERE id = ?
-- Total: 101 round-trips ao banco. Latência mata.
-- Solução: 1 query com JOIN (ou eager loading no ORM):
SELECT o.*, u.nome
FROM   orders o
JOIN   users u ON u.id = o.user_id
LIMIT  100;

-- N+1 DENTRO DO SQL: subquery escalar correlacionada no SELECT
-- (Capítulo 9). No EXPLAIN aparece como SubPlan com loops=N alto.
SELECT u.nome,
  (SELECT count(*) FROM orders o WHERE o.user_id = u.id)
FROM users u;          -- subquery roda 1x POR usuário

-- Reescrita eficiente: 1 agregação, 1 varredura
SELECT u.nome, count(o.id)
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.nome;
-- Como diagnosticar: procure 'loops=' alto e 'SubPlan' no EXPLAIN.

# MVCC, dead tuples, VACUUM e bloat

Revisitando o MVCC do Capítulo 11 sob a ótica de performance: cada UPDATE cria uma nova versão da linha e marca a antiga como morta (dead tuple). Essas versões mortas continuam ocupando espaço até o VACUUM recuperá-las. Acúmulo de dead tuples é o bloat: a tabela ocupa muito mais disco do que os dados vivos justificam, e varreduras ficam lentas porque leem páginas cheias de lixo.

vacuum_bloat.sql
-- Ver dead tuples e quando foi o último vacuum/analyze
SELECT
  relname,
  n_live_tup,
  n_dead_tup,
  round(n_dead_tup * 100.0 / nullif(n_live_tup + n_dead_tup, 0), 1) AS pct_dead,
  last_autovacuum,
  last_autoanalyze
FROM   pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- VACUUM: recupera espaço de dead tuples para REUSO (não devolve ao SO)
VACUUM orders;
VACUUM (ANALYZE, VERBOSE) orders;   -- + atualiza estatísticas

-- VACUUM FULL: reescreve a tabela e DEVOLVE espaço ao SO
-- ⚠ Bloqueia a tabela inteiro (ACCESS EXCLUSIVE) — janela de manutenção
VACUUM FULL orders;
-- Alternativa sem downtime: pg_repack (extensão externa)

-- O autovacuum daemon faz isso automaticamente. Ajuste por tabela
-- quente (muitas atualizações) para rodar com mais frequência:
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.05,   -- vacuum aos 5% de dead
  autovacuum_analyze_scale_factor = 0.02
);
PostgreSQL 16/17
O PG 16/17 trouxe melhorias substanciais no VACUUM: paralelização mais agressiva, menor amplificação de I/O e melhor manejo do transaction ID wraparound (o mecanismo que, se negligenciado por anos sem vacuum, pode forçar o banco a parar para se proteger). O PG 17 também adicionou estatísticas de progresso de vacuum mais detalhadas em pg_stat_progress_vacuum. A regra continua: não desligue o autovacuum — ajuste-o.

# Encontrando as queries lentas

pg_stat_statements.sql
-- pg_stat_statements: a ferramenta #1 para achar o que otimizar.
-- Habilite em postgresql.conf: shared_preload_libraries = 'pg_stat_statements'
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- As 10 queries que mais consomem tempo TOTAL (não média!)
-- Uma query de 5ms rodada 1M de vezes pesa mais que uma de 2s rodada 1x.
SELECT
  substring(query, 1, 80)        AS query,
  calls,
  round(total_exec_time)         AS tempo_total_ms,
  round(mean_exec_time::numeric, 2) AS media_ms,
  rows
FROM   pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT  10;

-- log de queries lentas no postgresql.conf:
--   log_min_duration_statement = 500   (loga queries > 500ms)
--   auto_explain.log_min_duration = 500 (+ plano no log)

-- Conexões e queries em execução agora (e bloqueios)
SELECT pid, state, now() - query_start AS duracao, query
FROM   pg_stat_activity
WHERE  state != 'idle'
ORDER BY query_start;

# Metodologia: do sintoma à solução

Performance & custo
A ordem que resolve a maioria dos casos sem chutar: (1) pg_stat_statements ordenado por total_exec_time — ache a query que realmente importa, não a que "parece" lenta. (2) EXPLAIN (ANALYZE, BUFFERS) nela — compare estimado vs real. (3) Se estimado ≠ real por ordens de magnitude → ANALYZE a tabela e repita. (4) Se há Seq Scan sobre filtro seletivo ou Rows Removed by Filter alto → índice (composto/parcial, Capítulo 15). (5) Se há loops= alto/SubPlan → reescreva o N+1 como JOIN/agregação. (6) Se a tabela está inchada (n_dead_tup alto) → VACUUM e ajuste o autovacuum. Só depois disso considere desnormalizar (Capítulo 13) ou cachear.

# O que o planner não conserta

  • Função sobre a coluna no WHERE: WHERE lower(email) = 'x' não usa índice de email — precisa de índice de expressão (Capítulo 15).
  • Tipo incompatível: WHERE user_id = '7' (texto vs bigint) pode impedir o uso do índice por cast implícito. Mantenha os tipos coerentes.
  • LIKE '%termo%': nenhum B-tree ajuda — use FTS ou pg_trgm (Capítulo 19).
  • OR entre colunas diferentes: WHERE a = 1 OR b = 2 raramente usa índice eficientemente — às vezes UNION de duas queries indexadas é mais rápido.
  • OFFSET gigante: paginação profunda relê e descarta tudo até o offset — use keyset pagination (Capítulo 5).

Segurança e administração

Segurança em PostgreSQL é uma camada: autenticação (quem pode conectar), autorização (o que cada um pode fazer dentro do banco) e Row-Level Security (quais linhas cada sessão enxerga). Administração envolve backups confiáveis, restauração testada e monitoramento. Este capítulo percorre o sistema de roles e privilégios do PostgreSQL, GRANT/REVOKE, SET ROLE, Row-Level Security, pg_dump/pg_restore e as views de monitoramento mais úteis — tudo com o princípio de privilégio mínimo como fio condutor.

# Roles — usuários e grupos

No PostgreSQL não há distinção entre "usuário" e "grupo" — ambos são roles. Uma role com LOGIN é o que chamamos de usuário; sem LOGIN, é um grupo de permissões que outras roles herdam.

roles.sql
-- Criar role de login (usuário de aplicação)
CREATE ROLE app_loja LOGIN PASSWORD 'senha_forte_aqui';

-- Criar role de grupo (sem login — apenas agrupa permissões)
CREATE ROLE leitura_readonly;    -- role de leitura
CREATE ROLE app_backend;         -- role da aplicação
CREATE ROLE admin_dados;         -- role administrativa

-- Adicionar login a uma role de grupo
GRANT leitura_readonly TO analista1, analista2;
GRANT app_backend TO app_loja;

-- Atributos de role
ALTER ROLE app_loja CONNECTION LIMIT 50;           -- limita conexões simultâneas
ALTER ROLE app_loja VALID UNTIL '2026-12-31';    -- expiração da senha
ALTER ROLE analista1 NOLOGIN;                       -- suspender acesso

-- Superusuário — evite em aplicações
CREATE ROLE dba_emergencia LOGIN SUPERUSER;

-- Listar roles
\du                      -- psql
SELECT rolname, rolsuper, rolcanlogin, rolconnlimit
FROM   pg_roles WHERE rolname NOT LIKE 'pg_%';

# GRANT e REVOKE — privilégios

Privilégios controlam o que cada role pode fazer com objetos específicos. O princípio de privilégio mínimo: conceda apenas o necessário para a função, nunca mais.

grant_revoke.sql
-- Privilégios em banco (nível de DATABASE)
GRANT CONNECT ON DATABASE loja TO app_loja;
GRANT CONNECT ON DATABASE loja TO leitura_readonly;

-- Privilégios em schema
GRANT USAGE ON SCHEMA public TO app_loja, leitura_readonly;

-- Privilégios em tabelas
GRANT SELECT ON ALL TABLES IN SCHEMA public TO leitura_readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_backend;

-- Estender automaticamente p/ tabelas futuras (DEFAULT PRIVILEGES)
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO leitura_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_backend;

-- Privilégios em sequences (necessário p/ IDENTITY/SERIAL)
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_backend;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO app_backend;

-- Privilégios em funções
GRANT EXECUTE ON FUNCTION total_pedido(bigint) TO leitura_readonly;

-- Revogar
REVOKE INSERT, UPDATE, DELETE ON users FROM app_backend;
REVOKE ALL ON DATABASE loja FROM analista_demitido;

-- Ver quem tem o quê (via information_schema)
SELECT grantee, table_name, privilege_type
FROM   information_schema.role_table_grants
WHERE  table_schema = 'public'
ORDER BY 1, 2;
Atenção
Até o PG 14, o schema public tinha CREATE concedido a PUBLIC por padrão — qualquer usuário logado podia criar tabelas. No PG 15+ esse default mudou. Em bancos antigos migrados, revogue isso explicitamente: REVOKE CREATE ON SCHEMA public FROM PUBLIC; e conceda apenas às roles que precisam. É uma das misconfigurações mais comuns encontradas em auditorias.

set_role.sql
-- SET ROLE: assume temporariamente outra role (deve ser membro dela)

-- A sessão agora opera com os privilégios de app_backend

-- Voltar à role original

-- O app conecta como um usuário de pool genérico,
-- depois SET ROLE para a role do tenant antes de cada operação.
-- O RLS (próxima seção) usa SET ROLE + variável de sessão.

-- SET LOCAL: muda só para a transação atual

-- ... operações com privilégio admin ...

# Row-Level Security (RLS)

RLS filtra linhas automaticamente em toda query — sem nenhuma cláusula WHERE na aplicação. Perfeito para multi-tenant (cada usuário só vê seus dados) e contextos onde a segurança não pode depender da aplicação lembrar de filtrar.

rls.sql
-- 1. Habilitar RLS na tabela
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Com RLS habilitado e sem policy: NINGUÉM lê nada (exceto superuser/owner)
-- Adicione sempre pelo menos uma policy.

-- 2. Criar policies
CREATE POLICY orders_proprio_cliente
  ON orders
  FOR ALL             -- SELECT, INSERT, UPDATE, DELETE
  TO app_backend
  USING (user_id = current_setting('app.user_id')::bigint);

-- USING: filtro para SELECT/UPDATE/DELETE (linhas existentes)
-- WITH CHECK: filtro para INSERT/UPDATE (linhas novas)
CREATE POLICY orders_insert_proprio
  ON orders
  FOR INSERT
  TO app_backend
  WITH CHECK (user_id = current_setting('app.user_id')::bigint);

-- Policy para admins verem tudo
CREATE POLICY orders_admin_tudo
  ON orders
  FOR ALL
  TO admin_dados
  USING (true);         -- true = sem restrição

-- 3. No início de cada request: setar o contexto do usuário corrente
BEGIN;
SET LOCAL app.user_id = '42';  -- id do usuário autenticado
SELECT * FROM orders;          -- automaticamente filtrado por user_id=42
COMMIT;

-- O dono da tabela ignora RLS por padrão. Para aplicar ao dono também:
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

-- Desabilitar temporariamente (para relatórios administrativos)
SET LOCAL row_security = off;  -- requer BYPASSRLS ou superuser
Performance & custo
A policy do RLS é adicionada automaticamente a cada query como predicado extra — o planner a vê como um filtro normal e pode usar índices. Para multi-tenant com RLS, indexar a coluna do tenant (user_id, tenant_id) é essencial. Um índice parcial por tenant (WHERE tenant_id = X) pode ser relevante para os tenants maiores, mas o índice geral na coluna já resolve bem na maioria dos casos.

# pg_dump e pg_restore — backups

backup_restore.sql
-- pg_dump: faz backup de um banco (não bloqueia leituras/escritas)

-- Formato plain (SQL legível) — simples mas limitado
pg_dump -U dev -d loja -f loja_backup.sql

-- Formato custom (comprimido, paralelizável) — RECOMENDADO
pg_dump -U dev -d loja -Fc -f loja_backup.dump

-- Formato directory (paralelo) — o mais rápido para bancos grandes
pg_dump -U dev -d loja -Fd -j 8 -f backup_dir/

-- Dump só de schema (sem dados) — útil para comparar estruturas
pg_dump -U dev -d loja --schema-only -f schema.sql

-- Dump só de dados de uma tabela
pg_dump -U dev -d loja -t orders --data-only -Fc -f orders.dump

-- pg_restore: restaura a partir de formato custom ou directory
pg_restore -U dev -d loja_restaurado -Fc loja_backup.dump

-- Restaurar em paralelo (muito mais rápido em bancos grandes)
pg_restore -U dev -d loja_restaurado -Fd -j 8 backup_dir/

-- Restaurar apenas uma tabela específica
pg_restore -U dev -d loja -t orders loja_backup.dump

-- pg_dumpall: faz backup de TODOS os bancos + roles globais
pg_dumpall -U postgres -f cluster_backup.sql

-- Restaurar plain SQL (pg_dump -f .sql ou pg_dumpall)
psql -U postgres -f cluster_backup.sql
Dica
A regra de ouro de backup: um backup não testado não é um backup. Automatize restaurações periódicas num banco de teste e valide a integridade (pg_restore --list, queries de contagem de linhas) antes de confiar. Formato custom (-Fc) é o mais flexível: permite restaurar objetos individuais, é paralelizável e comprimido. Nunca use plain SQL para bancos grandes — a restauração não é paralelizável.

# Monitoramento — views essenciais

monitoramento.sql
-- Conexões ativas e estado (diagnóstico de tráfego e bloqueios)
SELECT datname, usename, state, count(*)
FROM   pg_stat_activity
GROUP BY 1, 2, 3
ORDER BY 4 DESC;

-- Locks e quem está bloqueando quem
SELECT
  blocked.pid      AS pid_bloqueado,
  blocked.query    AS query_bloqueada,
  blocker.pid      AS pid_bloqueador,
  blocker.query    AS query_bloqueadora
FROM   pg_stat_activity blocked
JOIN   pg_stat_activity blocker
       ON blocker.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE  cardinality(pg_blocking_pids(blocked.pid)) > 0;

-- Tamanho de tabelas e índices
SELECT
  relname,
  pg_size_pretty(pg_total_relation_size(oid)) AS tamanho_total,
  pg_size_pretty(pg_relation_size(oid))       AS so_tabela,
  pg_size_pretty(pg_indexes_size(oid))        AS so_indices
FROM   pg_class
WHERE  relkind = 'r'
ORDER BY pg_total_relation_size(oid) DESC
LIMIT  20;

-- Cache hit ratio (ideal: acima de 99%)
SELECT
  round(heap_blks_hit * 100.0 /
    nullif(heap_blks_hit + heap_blks_read, 0), 2) AS cache_hit_pct,
  relname
FROM   pg_statio_user_tables
ORDER BY heap_blks_read DESC
LIMIT  10;

-- Replication lag (se tiver réplica de leitura)
SELECT client_addr, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn)) AS lag
FROM   pg_stat_replication;

-- Template completo: privilégio mínimo para um banco de aplicação

-- 1. Criar roles estruturais
CREATE ROLE readonly  NOLOGIN;
CREATE ROLE readwrite NOLOGIN;
CREATE ROLE owner_loja NOLOGIN;

-- 2. Criar usuários de aplicação e vinculá-los a roles
CREATE ROLE app_api    LOGIN PASSWORD '...'; GRANT readwrite  TO app_api;
CREATE ROLE app_relat  LOGIN PASSWORD '...'; GRANT readonly   TO app_relat;
CREATE ROLE app_migrate LOGIN PASSWORD '...'; GRANT owner_loja TO app_migrate;

GRANT USAGE ON SCHEMA  public TO readonly, readwrite;
GRANT CREATE ON SCHEMA public TO owner_loja;

-- 4. Privilégios de operação por role
GRANT SELECT                         ON ALL TABLES IN SCHEMA public TO readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO readwrite;
GRANT USAGE                          ON ALL SEQUENCES IN SCHEMA public TO readwrite;

ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO readwrite;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO readwrite;

-- 6. app_migrate cria/altera o schema (migrations)
-- app_api faz DML (a operação normal da API)
-- app_relat só lê (dashboards, relatórios)

# Migrations — o schema é código versionado

A regra inegociável de produção: nenhuma mudança de schema é feita manualmente no banco. Toda alteração — criar tabela, adicionar coluna, criar índice — é uma migration: um arquivo versionado, revisado, aplicado de forma determinística e reversível. O banco de produção deve ser reconstruível do zero apenas rodando as migrations em ordem.

migration_principios.sql
-- Estrutura típica: arquivos numerados, imutáveis após aplicados
--   migrations/0001_init_schema.sql
--   migrations/0002_add_products_slug.sql
--   migrations/0003_index_orders_user_id.sql

-- Princípios:
-- 1. Cada migration é atômica e idempotente quando possível
-- 2. Migration JÁ APLICADA é imutável — corrija com uma NOVA migration
-- 3. Toda migration "up" deveria ter uma "down" (reversão)
-- 4. Mudanças destrutivas (DROP COLUMN) são separadas e deliberadas

-- Migration expand/contract (zero-downtime) — adicionar coluna NOT NULL:
-- Migration A (expand): adicionar coluna NULLABLE + backfill em lote
ALTER TABLE products ADD COLUMN slug text;
-- ... deploy do código que escreve slug ...
-- ... backfill: UPDATE products SET slug=... WHERE slug IS NULL (em lotes) ...

-- Migration B (contract): tornar NOT NULL após backfill completo
ALTER TABLE products
  ADD CONSTRAINT slug_nn CHECK (slug IS NOT NULL) NOT VALID;
ALTER TABLE products VALIDATE CONSTRAINT slug_nn;
ALTER TABLE products ALTER COLUMN slug SET NOT NULL;
ALTER TABLE products DROP CONSTRAINT slug_nn;
Atenção
A migration mais perigosa é a que parece inofensiva. ALTER TABLE ADD COLUMN ... DEFAULT volátil, criar índice sem CONCURRENTLY, ou ALTER COLUMN TYPE em tabela grande adquirem um lock ACCESS EXCLUSIVE e travam a tabela inteira durante a reescrita — derrubando a aplicação. Toda migration em tabela grande precisa ser avaliada pela ótica de "que lock isso adquire e por quanto tempo" (Capítulos 4, 12 e 15). Em produção: CREATE INDEX CONCURRENTLY, NOT VALID + VALIDATE, e mudanças destrutivas só após o código parar de usar a coluna.

# Connection pooling

Cada conexão PostgreSQL é um processo do sistema operacional com overhead de memória significativo. Abrir uma conexão por request não escala — uma API com mil requests concorrentes não pode ter mil conexões diretas. O pooler mantém um conjunto pequeno de conexões reais reutilizadas por muitos clientes.

pgbouncer.txt
// Sem pooler: 1000 clientes → 1000 conexões → servidor sufoca
// Com pgbouncer: 1000 clientes → pool de ~25 conexões reais
//
// Modos do pgbouncer (do menos ao mais agressivo):
//
// session  : conexão do pool fica presa ao cliente até ele desconectar
//            (compatível com tudo; menor ganho)
// transaction : conexão é devolvida ao pool no fim de cada transação
//            (melhor equilíbrio; o modo mais usado em produção)
// statement: devolvida a cada statement (máximo throughput;
//            proíbe transações multi-statement)
//
// pgbouncer.ini essencial:
//   pool_mode = transaction
//   max_client_conn = 1000     # clientes que podem conectar AO bouncer
//   default_pool_size = 25     # conexões reais ao Postgres por database
//
// Regra de dimensionamento (ponto de partida):
//   pool_size ≈ (núcleos de CPU * 2) + nº de discos efetivos
// Mais conexões NÃO é mais rápido — após o ponto ótimo, contenção piora.
Performance & custo
No modo transaction (o recomendado), recursos atrelados à sessão deixam de funcionar de forma confiável: prepared statements nomeados, SET de sessão, advisory locks de sessão, LISTEN/NOTIFY, cursores WITH HOLD e tabelas temporárias entre transações. Para advisory locks com pooler, use a variante _xact_ (Capítulo 11), liberada no fim da transação. Configure o driver para usar prepared statements no protocolo extended de forma compatível, ou desative o cache de prepared statements do ORM quando atrás de um pooler em modo transaction.

# Particionamento declarativo

Quando uma tabela cresce para centenas de milhões de linhas — tipicamente tabelas de eventos, logs, pedidos históricos — operações de manutenção (VACUUM, índices, DELETE de dados antigos) ficam caras e os planos degradam. Particionamento divide a tabela em pedaços físicos menores que o planner pode podar (partition pruning) e manter independentemente.

particionamento.sql
-- Particionamento por RANGE de data (o caso mais comum)
CREATE TABLE eventos (
  id        bigint GENERATED ALWAYS AS IDENTITY,
  tipo      text   NOT NULL,
  payload   jsonb,
  criado_em timestamptz NOT NULL
) PARTITION BY RANGE (criado_em);

-- Partições mensais
CREATE TABLE eventos_2025_01 PARTITION OF eventos
  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
CREATE TABLE eventos_2025_02 PARTITION OF eventos
  FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');

-- Índice declarado na tabela-pai propaga para todas as partições
CREATE INDEX ON eventos (tipo, criado_em);

-- Partition pruning: a query só toca a partição relevante
EXPLAIN SELECT * FROM eventos
WHERE  criado_em >= '2025-02-10' AND criado_em < '2025-02-20';
-- → varre só eventos_2025_02; as outras partições são podadas

-- A grande vantagem operacional: dropar dados antigos é instantâneo
DROP TABLE eventos_2025_01;   -- vs DELETE de milhões de linhas + VACUUM

-- Outras estratégias: PARTITION BY LIST (por região/tenant),
-- PARTITION BY HASH (distribuição uniforme por id).
-- Automação de criação de partições: pg_partman.
PostgreSQL 16/17
O PG 16/17 amadureceu o particionamento declarativo: melhor pruning em tempo de execução (com parâmetros e prepared statements), JOIN partition-wise mais agressivo, e melhorias no comportamento de chaves estrangeiras e UNIQUE que referenciam tabelas particionadas. A regra de adoção continua: particione quando a tabela for genuinamente grande e houver uma chave de partição natural (quase sempre tempo); particionar cedo demais adiciona complexidade sem retorno.

# Monitoramento como hábito, não como pânico

Monitoramento não é algo que se faz quando o site cai — é um painel olhado regularmente que mostra tendências antes de virarem incidentes. Os sinais que importam, todos disponíveis nas views pg_stat_* (Capítulos 20 e 21):

  • Cache hit ratio abaixo de ~99% sustentado: working set não cabe na RAM — hora de aumentar memória ou revisar queries que varrem demais.
  • Crescimento de n_dead_tup mais rápido que o autovacuum recupera: bloat se acumulando — ajustar autovacuum por tabela.
  • Queries no topo de pg_stat_statements por tempo total mudando: uma query nova entrou no caminho crítico.
  • Conexões em idle in transaction: transações abertas e esquecidas — seguram locks e impedem o vacuum (Capítulo 11).
  • Replication lag crescente: réplica não acompanha — leituras servidas por ela ficam obsoletas.
  • Idade da transação mais antiga aproximando-se do limite de wraparound: emergência silenciosa que o vacuum previne.
