Zod

A biblioteca TypeScript-first de declaração de schemas e validação de runtime — parse, don't validate. Zod fecha o loop de type-safety que Drizzle deixou aberto: enquanto Drizzle garante o tipo do que está armazenado e do que é lido do banco, Zod estabelece o contrato de tudo que cruza a fronteira da aplicação — requisições HTTP, variáveis de ambiente, mensagens de fila, JSONB. Este manual cobre Zod 4.4+ — dos schemas primitivos e composição, passando por refinamentos, transforms e erros, até a integração com Drizzle, Hono e React Hook Form que dá continuidade ao Volume XI.

Capítulo 1

Introdução: parse, don't validate

Zod resolve um problema que TypeScript sozinho não resolve: TypeScript desaparece em runtime. O tsc confere que o código trata User como User, mas o JSON que chega numa rota HTTP, a string em process.env.DATABASE_URL, o JSONB lido de uma coluna metadata — nada disso passou pelo compilador. Este capítulo estabelece o modelo mental: um schema declarativo em TS que define a forma esperada do dado, infere o tipo TypeScript correspondente, e produz uma função de parse que valida em runtime e devolve um valor tipado. O argumento filosófico vem de Alexis King — parse, don't validate. O argumento prático fecha o loop aberto no Volume XI: Drizzle garante o tipo do que está no banco em compilação; Zod garante o tipo do que cruza a fronteira em runtime.

# O buraco entre compilação e execução

O TypeScript é um sistema de tipos estrutural sobre JavaScript. O tsc roda em build, emite JS sem tipos, e termina seu trabalho. Em runtime, tudo é JavaScript dinâmico. Isso significa que três operações típicas de qualquer aplicação têm um buraco onde a garantia de tipo simplesmente não existe: ler o corpo de uma requisição HTTP (req.json() retorna unknown — ou pior, any em frameworks antigos), ler uma variável de ambiente (process.env.X é sempre string | undefined, independente do que o .env declara) e desserializar uma mensagem de fila, webhook ou JSONB (JSON.parse retorna any). O padrão comum é declarar uma type assertion e seguir o jogo:

rota-sem-validacao.ts
// fronteira HTTP sem validação — TypeScript acredita em palavra
interface CorpoCriarUsuario {
  email: string;
  nome: string;
}

app.post('/users', async (req, res) => {
  const corpo = await req.json() as CorpoCriarUsuario;
  // corpo.email é "string". Mas e se o cliente mandar { email: 42 }?
  // nada disparou. o erro vai aparecer 50 linhas adiante, em outro arquivo,
  // quando email.toLowerCase() falhar com "is not a function".
  await criarUsuario(corpo);
});
Armadilha
A type assertion (as CorpoCriarUsuario) é uma promessa unilateral feita ao compilador. Nenhuma verificação real acontece. Bugs nessa categoria sempre se manifestam longe do ponto onde nasceram, o que torna o stack trace inútil para localizar a fronteira que falhou.

# Parse, don't validate

Em 2019, Alexis King publicou o ensaio Parse, don't validate. A distinção é simples mas estruturante. Validar é checar se um dado obedece a uma condição e devolver um booleano — o dado continua com seu tipo opaco original. Fazer parse é transformar um dado de tipo amplo (geralmente unknown) em um dado de tipo restrito; se o parse falha, é erro; se sucede, o output carrega como evidência o tipo refinado.

parse-vs-validate.ts
// VALIDAÇÃO: o tipo não evolui. Você confiou na função, mas o compilador não.
function ehEmail(s: unknown): boolean {
  return typeof s === 'string' && s.includes('@');
}

const entrada: unknown = obterEntrada();
if (ehEmail(entrada)) {
  // entrada continua "unknown" — TS não acompanha sem type predicate
  // (com type predicate funciona, mas o ônus de manter é do programador)
}

// PARSE: o output é uma nova variável com tipo refinado, derivado do schema.
const Email = z.email();
const email = Email.parse(entrada);
// email: string  (tipo de saída do schema, garantido pelo parse)
// se parse falhar, lança ZodError — não chega na próxima linha.

Em Zod, o schema é simultaneamente três coisas: uma declaração de tipo (TS o usa para inferência), uma função de parse (runtime) e uma especificação de validação (mensagens de erro, refinamentos). Os três são objetos diferentes em Joi e em Yup; em Zod são o mesmo valor.

# Schema declarativo, tipo inferido

O fluxo de trabalho com Zod tem três passos. Você declara o schema. Você extrai o tipo via z.infer. Você chama .parse nas fronteiras. O tipo nunca é escrito à mão; é derivado.

schema-usuario.ts
import * as z from 'zod';

// 1. schema declarado (o mesmo schema da tabela users do Vol XI)
const Usuario = z.object({
  id: z.number().int().positive(),
  email: z.email(),
  nome: z.string().min(1),
  criado_em: z.iso.datetime(),
});

// 2. tipo TypeScript derivado por inferência — uma única fonte da verdade
type Usuario = z.infer<typeof Usuario>;
// type Usuario = {
//   id: number;
//   email: string;
//   nome: string;
//   criado_em: string;
// }

// 3. parse na fronteira — input unknown, output Usuario tipado
const bruto: unknown = await fetch('/api/users/1').then(r => r.json());
const usuario = Usuario.parse(bruto);
// usuario: Usuario — daqui para frente, TypeScript trabalha com tipo seguro
Princípio
O schema vive em código TypeScript comum, sem geração de código, sem decorators, sem arquivo separado .zod ou .proto. O tsc derruba qualquer erro de uso na hora — se usuario.cpf não existe no schema, a linha não compila. Em Joi e Yup esse acoplamento é parcial; em Zod é total.

# As quatro fronteiras

Zod ganha valor onde existe dado não-confiável entrando no sistema. Em uma aplicação fullstack típica, há quatro pontos canônicos onde isso acontece — todos cobertos com a mesma API:

fronteiras.ts
// 1) HTTP — corpo, query, params, headers
const CriarPedido = z.object({
  user_id: z.number().int().positive(),
  itens: z.array(z.object({
    product_id: z.number().int(),
    quantidade: z.number().int().positive(),
  })).min(1),
});
const pedido = CriarPedido.parse(await req.json());

// 2) Variáveis de ambiente — string | undefined precisa virar config tipada
const Env = z.object({
  DATABASE_URL: z.url(),
  PORT: z.coerce.number().int().positive(),
  NODE_ENV: z.enum(['development', 'production', 'test']),
});
const env = Env.parse(process.env);

// 3) Mensagem de fila / webhook — payload externo opaco
const WebhookStripe = z.object({
  id: z.string().startsWith('evt_'),
  type: z.string(),
  data: z.object({ object: z.unknown() }),
});
const evento = WebhookStripe.parse(JSON.parse(corpo));

// 4) JSONB no banco — escrito por outra app, ou por versão anterior do código
const ProductMetadata = z.object({
  garantia_meses: z.number().int().optional(),
  marca: z.string().optional(),
});
const meta = ProductMetadata.parse(produto.metadata);

A regra geral: todo dado que não foi escrito por código TypeScript do mesmo build atravessou uma fronteira. Banco escrito por migration de outra versão. Header HTTP. Resposta de API externa. Arquivo de configuração. JWT decodificado. Mensagem de queue. Em todos esses pontos, Zod é o substituto idiomático do as.

# Comparação com Joi, Yup, io-ts

Zod não foi a primeira biblioteca de validação no ecossistema JavaScript. Conhecer as alternativas ajuda a entender o que Zod escolheu e o que abriu mão.

Joi (de @hapi/joi, 2012) é o avô do espaço. JavaScript-first, sem inferência TypeScript nativa — você declara o schema em runtime e redeclara o tipo na mão. A API é matura, com forte suporte a regras de negócio cruzadas, mas sente a idade: dois objetos paralelos (schema e tipo) que precisam ser mantidos sincronizados manualmente.

Yup (2014) foi a opção dominante para forms React entre 2017 e 2021. Tem inferência TS, mas é mais frágil em casos complexos: unions, schemas recursivos e refinamentos condicionais quebram o tipo derivado. A API encadeada inspirou a de Zod, mas o motor de tipos foi adicionado depois do projeto existir — não é um design TypeScript-first.

io-ts (2017, do ecossistema fp-ts) levou validação no TypeScript a sério antes de Zod existir. Usa o pattern codec (decode/encode), retorna Either<Errors, A> em vez de lançar, e tem inferência sólida. O custo é cognitivo: a sintaxe é funcional pura, exige familiaridade com fp-ts, e a ergonomia é hostil para quem não vive nesse paradigma. t.type({ name: t.string }) é menos legível que z.object({ name: z.string() }).

Zod (2020, de Colin McDonnell) é TypeScript-first desde o primeiro commit. A inferência é o ponto central do design — o resto da API foi construído para que z.infer sempre produza o tipo correto, mesmo em unions discriminados, schemas recursivos e transforms. A sintaxe encadeada herda de Yup; a robustez de tipos herda de io-ts; o resultado é a opção dominante em backends e forms TypeScript modernos.

# Continuidade com o Volume XI

O Volume XI (Drizzle ORM) resolveu metade do problema de type-safety. O schema da tabela em schema.ts é fonte da verdade para o tipo do que está armazenado e do que retorna de db.select(). Mas Drizzle opera em compilação; quando o dado chega na aplicação por uma rota HTTP ou sai dela para outro serviço, Drizzle não pode ajudar — não está mais no fluxo.

drizzle-vs-zod.ts
// Vol XI (Drizzle): tipo correto em COMPILAÇÃO, no caminho banco ↔ código
const usuarios = await db.select().from(users);
// usuarios: User[] — Drizzle infere de pgTable('users', { ... })

// Vol XII (Zod): tipo correto em RUNTIME, nas fronteiras da aplicação
const corpo = CriarUsuario.parse(await req.json());
// corpo: CriarUsuario — Zod valida em runtime

// Cap 18 deste volume une os dois: drizzle-zod gera Zod a partir de Drizzle.
import { createInsertSchema } from 'drizzle-zod';
const CriarUsuario = createInsertSchema(users);
// schema Zod derivado da definição Drizzle — fonte da verdade única

O eixo é o tempo. Drizzle responde "esse dado tem o formato certo agora, em tempo de compilação?". Zod responde "esse dado tem o formato certo agora, em tempo de execução?". O Cap 18 mostra como obter ambas as garantias a partir de uma única declaração.

# Zod 4: o pacote, o subpath e a versão

Este volume cobre Zod 4. A versão atual no npm é a 4.4.3 (publicada em maio de 2026). Zod 3 foi lançado em maio de 2021; Zod 4 estabilizou em 2025 depois de um ciclo longo de desenvolvimento, trazendo até 14× mais performance de parsing e um conjunto de novas APIs (formats top-level, z.iso.*, z.codec, novo modelo de erros). A maioria das mudanças é incremental, mas há quebras pontuais relevantes — os capítulos de strings e de erros marcam as principais.

Um detalhe de packaging importante: Zod 4 introduziu subpath versioning. Aplicações importam direto do root:

imports.ts
// aplicação — este é o import idiomático em código de usuário final
import * as z from 'zod';

// biblioteca que precisa suportar Zod 3 E Zod 4 simultaneamente
import * as z3 from 'zod/v3';
import * as z4 from 'zod/v4';
Zod 4
O root 'zod' agora exporta Zod 4. Os subpaths 'zod/v3' e 'zod/v4' continuam disponíveis permanentemente para autores de bibliotecas que precisam aceitar schemas de qualquer versão. Em código de aplicação, importe sempre do root.
Performance & custo
Zod 4 reescreveu o motor de parsing e é até 14× mais rápido que Zod 3 em benchmarks de schemas grandes. Em runtime de produção, o custo de um .parse em payload típico de HTTP (algumas dezenas de campos) está em microssegundos. O Cap 22 mede o impacto real e mostra quando safeParse vence parse, e quando faz sentido cachear schemas compostos.

# Requisitos: Node, TypeScript, strict mode

Zod 4 exige TypeScript 5.0+ para a inferência funcionar corretamente — versões anteriores não suportam recursos de tipo usados internamente (template literal types, conditional types com inferência de tuplas). Node 18 ou superior é o piso recomendado, com 20+ ideal para alinhamento com o Vol VIII.

O ponto não-negociável é o strict no tsconfig.json. Sem ele, unknown e any colapsam para o mesmo tipo do ponto de vista do compilador, e a inferência de z.infer produz tipos amplos demais ou silenciosamente errados.

tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  }
}
Armadilha
Com strict: false, um schema como z.object({ id: z.number() }) infere { id: number }, mas o parser ainda funciona em runtime — o problema é que TypeScript deixa de cobrar a forma do input, e schema.parse(qualquerCoisa) compila sem reclamar. O sintoma típico é bug silencioso em chamadas internas; o stack trace some.

# Primeiro schema

O hello world de Zod usa z.object, declara campos com tipos primitivos, e chama .parse num input unknown. O retorno é o valor tipado com a forma do schema:

primeiro-schema.ts
import * as z from 'zod';

// schema da tabela users do Vol XI, em sua forma mínima
const Usuario = z.object({
  id: z.number().int().positive(),
  email: z.email(),
  nome: z.string().min(1),
});

// .parse — lança ZodError se input não bate
const ok = Usuario.parse({
  id: 1,
  email: 'ana@example.com',
  nome: 'Ana',
});
// ok: { id: number; email: string; nome: string }

// .safeParse — devolve discriminated union sem lançar
const resultado = Usuario.safeParse({ id: '1', email: 'x', nome: '' });
if (resultado.success) {
  // resultado.data: Usuario
} else {
  // resultado.error: ZodError — issues estruturados (Cap 13)
  console.log(resultado.error.issues);
}

A diferença entre .parse e .safeParse é só o canal de erro: a primeira lança, a segunda devolve um objeto discriminado por success. O comportamento de validação é idêntico. O Cap 13 cobre o modelo de erros em profundidade; o Cap 22 mostra quando cada um vence em performance.

# Estrutura de projeto

Não há convenção oficial para onde colocar schemas. Duas organizações funcionam bem na prática:

estrutura-centralizada
# schemas em diretório dedicado — bom para apps pequenas e médias
src/
├── schemas/
│   ├── usuario.ts        # UsuarioSchema, CriarUsuario, AtualizarUsuario
│   ├── produto.ts
│   ├── pedido.ts
│   └── env.ts            # variáveis de ambiente (Cap 21)
├── routes/
│   ├── users.ts
│   └── products.ts
├── db/
│   └── schema.ts         # Drizzle (Vol XI)
└── index.ts
estrutura-por-dominio
# schemas colocalizados ao lado do domínio — bom para apps grandes
src/
├── usuarios/
│   ├── schema.ts         # Zod
│   ├── repository.ts     # Drizzle
│   ├── service.ts
│   └── routes.ts
├── produtos/
│   └── ...
└── config/
    └── env.ts
Boa prática
Exporte tanto o schema quanto o tipo inferido do mesmo arquivo. O consumidor importa apenas o que precisa: import { Usuario, type UsuarioType }. Isso evita o erro comum de redeclarar tipos manualmente em interfaces TypeScript paralelas que saem do ar quando o schema muda.

# Variáveis de ambiente (preview do Cap 21)

O Cap 2 do Volume XI abriu uma rota com process.env.DATABASE_URL! e prometeu resolver o ! mais tarde. O bang é o jeito do TypeScript dizer "confie em mim, não é undefined" — e propaga essa confiança não-verificada por todo o código que depende da variável. Zod resolve isso na inicialização, antes que qualquer rota seja registrada:

env.ts
import * as z from 'zod';

const Env = z.object({
  DATABASE_URL: z.url(),
  PORT: z.coerce.number().int().positive().default(3000),
  NODE_ENV: z.enum(['development', 'production', 'test']),
});

// se .env estiver incompleto, o processo falha aqui — antes de servir tráfego
export const env = Env.parse(process.env);
// env.DATABASE_URL: string  (não string | undefined)
// env.PORT: number          (não string)
// env.NODE_ENV: 'development' | 'production' | 'test'

O Cap 21 cobre o padrão completo, incluindo t3-env para projetos Next.js que separam variáveis de servidor das expostas ao cliente.

migracao.ts
// código existente em Zod 3 — mantém comportamento ao trocar import
import { z } from 'zod/v3';

// código novo em Zod 4 — root do pacote

A migração mais visível é nos formats de string: z.string().email() ainda funciona mas está deprecated em favor de z.email() top-level (mesma mudança para url, uuid, ipv4, jwt, base64). O Cap 11 lista todos. Erros também mudaram: error.issues é o caminho idiomático em vez de error.errors (Cap 13).

Capítulo 3

Tipos primitivos

Zod mapeia cada primitivo do TypeScript/JavaScript em um schema correspondente. Esses schemas são os blocos atômicos de qualquer composição — objects, arrays e unions dos capítulos seguintes são todos construídos sobre eles. Este capítulo é o catálogo completo: doze tipos, suas opções de validação imediata e os casos em que o comportamento padrão surpreende.

# Visão geral

Cada schema de tipo primitivo é uma chamada sem argumentos que retorna um validador. O nome da função bate com o tipo TypeScript que infere:

primitivos.ts
import * as z from 'zod';

z.string();     // type: string
z.number();     // type: number
z.boolean();    // type: boolean
z.bigint();     // type: bigint
z.date();       // type: Date     — aceita objeto Date, não string
z.symbol();     // type: symbol
z.undefined(); // type: undefined — o valor literal
z.null();       // type: null      — o valor literal
z.void();       // type: void      — semanticamente "sem retorno"
z.any();        // type: any       — sem validação
z.unknown();    // type: unknown   — passa tudo, tipo opaco
z.never();      // type: never     — sempre falha

# z.string

Aceita apenas strings. Qualquer outro tipo — number, null, boolean — lança ZodError. Os métodos de comprimento e transformação se encadeiam sobre o schema base:

string.ts
// comprimento
z.string().min(1);              // ao menos 1 caractere
z.string().max(255);            // no máximo 255
z.string().length(6);           // exatamente 6 (código OTP, CEP sem hífen)

// transformações (executadas após a validação)
z.string().trim();               // remove espaços nas pontas
z.string().toLowerCase();        // normaliza para minúsculas
z.string().toUpperCase();        // normaliza para maiúsculas

// prefixo / sufixo
z.string().startsWith('evt_');   // IDs de webhook Stripe
z.string().endsWith('.br');     // sufixo de domínio
z.string().includes('@');       // verificação básica de presença

// para formatos (email, url, uuid, ipv4...) ver Cap 11
// z.email(), z.url(), z.uuid() são top-level em Zod 4
Zod 4
Em Zod 3, z.string().email() era o caminho padrão. Em Zod 4, validações de formato viraram schemas top-level: z.email(), z.url(), z.uuid(), z.ipv4(), z.base64(), z.jwt(). A API encadeada ainda funciona mas está deprecated. O Cap 11 cobre todos com exemplos.

# z.number

z.number() aceita qualquer valor para o qual typeof v === 'number' retorne true — inclusive NaN e Infinity. Esse comportamento surpreende na primeira vez. Use .finite() para rejeitar ambos:

number.ts
// NaN é typeof 'number' em JS — z.number() passa por padrão
z.number().parse(NaN);              // OK! use .finite() para rejeitar

// restrições
z.number().int();                    // apenas inteiros (rejeita 1.5)
z.number().positive();               // > 0
z.number().nonnegative();            // >= 0
z.number().negative();               // < 0
z.number().nonpositive();            // <= 0
z.number().min(1).max(100);          // intervalo fechado
z.number().multipleOf(5);            // divisível por 5
z.number().finite();                 // rejeita NaN e Infinity
z.number().safe();                   // MIN_SAFE_INTEGER a MAX_SAFE_INTEGER

// campo preco da tabela products do Vol XI
const Preco = z.number().positive().finite();
// type: number
Armadilha
z.number() não coerce strings para números. z.number().parse('42') lança ZodError. Para aceitar strings numéricas vindas de formulários HTML ou de process.env, use z.coerce.number() (Cap 15).

# z.boolean, z.bigint, z.date, z.symbol

z.boolean() é o mais simples do grupo: aceita true ou false, sem coerção (a string "true" falha). z.bigint() replica para o tipo bigint os mesmos métodos de restrição de z.number. z.date() aceita exclusivamente objetos Date válidos, não strings ISO. z.symbol() raramente aparece em schemas de dados de rede, mas faz parte da especificação completa:

outros-primitivos.ts
// boolean — sem coerção
z.boolean().parse(true);            // true
z.boolean().parse('true');           // ZodError — string não é boolean

// bigint — mesmas restrições que number
z.bigint().positive();
z.bigint().min(0n).max(1000n);

// date — apenas objeto Date, não string
z.date().parse(new Date());          // OK
z.date().parse('2025-01-01');        // ZodError — use z.coerce.date() (Cap 15)
z.date().min(new Date('2020-01-01'));// data mínima permitida
z.date().max(new Date());            // até hoje

// symbol
const sym = Symbol('id');
z.symbol().parse(sym);               // OK
Observação
Para datas chegando como strings ISO em requisições HTTP, o caminho idiomático em Zod 4 é z.iso.datetime() (retorna string validada) ou z.coerce.date() (converte string para objeto Date). Ambos ficam no Cap 12 e Cap 15.

# z.undefined, z.null, z.void

Os três tipos de "ausência" têm usos distintos. z.null() e z.undefined() validam os valores literais correspondentes — e rejeita um o que o outro aceita. z.void() é pensado para tipar retorno de funções que não devolvem nada; em runtime se comporta como undefined, mas a semântica declarada é diferente. Na prática esses schemas raramente aparecem sozinhos — quase sempre entram em composição via .nullable(), .optional() ou .nullish() (Cap 14):

ausencia.ts
// z.null — aceita exatamente null, rejeita undefined
z.null().parse(null);               // null
z.null().parse(undefined);           // ZodError

// z.undefined — aceita exatamente undefined, rejeita null
z.undefined().parse(undefined);     // undefined
z.undefined().parse(null);           // ZodError

// z.void — undefined em runtime; marcador semântico de "sem retorno"
z.void().parse(undefined);           // undefined

// composição prática — campo parent_id da tabela categories (Vol XI)
const ParentId = z.number().int().positive().nullable();
// type: number | null

# z.any, z.unknown, z.never

z.any() desliga a validação — qualquer input passa e o tipo inferido é any, propagando opacidade para todo o código que usa o valor. z.unknown() também aceita qualquer input, mas infere unknown: o valor precisa ser narrowed antes de qualquer operação. z.never() sempre falha — é o schema impossível, útil em unions para garantir cobertura exaustiva:

especiais.ts
// z.any — escape hatch; use com parcimônia
z.any().parse(42);                   // 42 (type: any)
z.any().parse({ tudo: true });       // { tudo: true } (type: any)

// z.unknown — passa tudo, mas força narrowing antes de usar
const Payload = z.object({ data: z.unknown() });
const p = Payload.parse({ data: { id: 1 } });
// p.data: unknown — TS não deixa usar sem checar o tipo antes
// bom candidato: campo metadata jsonb de products (Vol XI)

// z.never — sempre falha; type: never
z.never().parse('qualquer coisa');   // ZodError sempre

// uso idiomático: exaustividade de union (Cap 7)
function assertNever(x: never): never {
  throw new Error('caso não coberto: ' + x);
}
Boa prática
Prefira z.unknown() a z.any() em campos com conteúdo genuinamente variável — JSONB de terceiros, respostas de APIs externas ainda não modeladas. unknown obriga a validar ou fazer narrowing antes de usar; any silencia o compilador e propaga a opacidade para fora do ponto de entrada.

Capítulo 4

Inferência de tipos

Um schema Zod existe em dois mundos ao mesmo tempo: como valor em runtime (o objeto retornado por z.object, z.string etc.) e como fonte de tipo em compilação (via z.infer). O mesmo artefato que valida os dados define o tipo TypeScript dos dados validados — sem declaração manual de interface. Este capítulo cobre z.infer, a distinção entre z.input e z.output que emerge quando schemas usam .default() ou .transform(), e branded types como ferramenta de tipagem nominal sobre o sistema estrutural do TypeScript.

# z.infer

z.infer<typeof Schema> é uma utility type TypeScript que extrai o tipo de saída de um schema — o tipo do valor retornado por .parse() quando bem-sucedido. Equivale a z.output<typeof Schema> e não tem custo em runtime: some completamente após a compilação.

inferencia-basica.ts
import * as z from 'zod';

// schema da tabela users do Vol XI
const Usuario = z.object({
  id:        z.number().int().positive(),
  email:     z.email(),
  nome:      z.string().min(1),
  criado_em: z.iso.datetime(),
});

// z.infer extrai o tipo de saída — idêntico ao que .parse() retorna
type Usuario = z.infer<typeof Usuario>;
// type Usuario = {
//   id: number;
//   email: string;
//   nome: string;
//   criado_em: string;
// }

// dualidade: o mesmo identificador é valor (runtime) e tipo (compilação)
const dados: unknown = await req.json();
const usuario = Usuario.parse(dados);   // valor: valida em runtime
let u: Usuario;                          // tipo: anotação em compilação

Quando o schema muda — um campo novo, um tipo diferente — o tipo TypeScript derivado atualiza junto, sem nenhuma edição adicional. Interfaces declaradas manualmente ficam desatualizadas silenciosamente; schemas Zod, não.

Boa prática
Exporte sempre o schema e o tipo com o mesmo nome. export const Usuario = z.object({...}) e export type Usuario = z.infer<typeof Usuario> no mesmo arquivo. O consumidor importa o schema quando precisa validar e importa o tipo quando precisa anotar — mesma origem, zero desincronização.

# z.input vs z.output

A maioria dos schemas tem input e output idênticos — z.string() recebe string e devolve string. Mas quando um schema aplica .default(), o campo se torna opcional no input (pode não estar presente) e obrigatório no output (o default foi preenchido). Aí z.infer — que sempre extrai o output — não basta para descrever o que o chamador precisa enviar:

input-vs-output.ts
const CriarProduto = z.object({
  nome:         z.string().min(1),
  preco:        z.number().positive(),
  ativo:        z.boolean().default(true),        // default → muda input
  categoria_id: z.number().int().optional(),
});

type Input  = z.input<typeof CriarProduto>;
// {
//   nome: string;
//   preco: number;
//   ativo?: boolean | undefined;   ← opcional (tem default)
//   categoria_id?: number | undefined;
// }

type Output = z.output<typeof CriarProduto>;
// equivalente a z.infer<typeof CriarProduto>
// {
//   nome: string;
//   preco: number;
//   ativo: boolean;                ← obrigatório (default aplicado)
//   categoria_id?: number | undefined;
// }
Observação
z.infer é um alias de z.output — sempre extrai o tipo pós-parse. Use z.input explicitamente apenas quando precisar tipar o dado bruto antes de passar para .parse(), por exemplo ao anotar o parâmetro de uma função que recebe o body de uma requisição antes da validação.

# Divergência com .transform()

.transform() é a causa mais drástica de divergência: input e output podem ter tipos completamente diferentes. O caso clássico são query strings que chegam como texto e precisam ser convertidas:

transform-diverge.ts
// query string 'ids=1,2,3' precisa virar number[]
const CsvIds = z.string().transform(s => s.split(',').map(Number));

type CsvInput  = z.input<typeof CsvIds>;   // string
type CsvOutput = z.output<typeof CsvIds>;  // number[]
// z.infer<typeof CsvIds> === number[]  (sempre o output)

// em uso: o tipo após parse já é number[]
const Filtro = z.object({ ids: CsvIds });
const filtro = Filtro.parse({ ids: '1,2,3' });
// filtro.ids: number[]  (não string)

# Branded types

TypeScript usa tipagem estrutural: dois tipos com a mesma forma são intercambiáveis, independente do nome. Isso significa que UserId e OrderId, se ambos forem string, são o mesmo tipo para o compilador — nada impede passar um no lugar do outro. Branded types adicionam uma marca phantômica que torna os tipos nominalmente distintos:

branded-types.ts
// sem brand: UserId e OrderId são apenas string — TS aceita a mistura
type UserId  = string;
type OrderId = string;

// com .brand(): a marca torna os tipos nominalmente distintos
const UserId  = z.string().uuid().brand<'UserId'>();
const OrderId = z.string().uuid().brand<'OrderId'>();

type UserId  = z.infer<typeof UserId>;
// type UserId = string & z.BRAND<'UserId'>

type OrderId = z.infer<typeof OrderId>;
// type OrderId = string & z.BRAND<'OrderId'>

// o parse produz o tipo marcado
const uid = UserId.parse('123e4567-e89b-12d3-a456-426614174000');
const oid = OrderId.parse('123e4567-e89b-12d3-a456-426614174001');

// TypeScript rejeita a mistura de marcas em compilação
function cancelarPedido(id: OrderId): void { /* ... */ }
cancelarPedido(oid); // OK
cancelarPedido(uid); // ERRO de compilação — UserId não é OrderId
Boa prática
Use branded types para IDs primários das tabelas do banco. Em vez de receber id: string em uma função, receba id: UserId — o compilador garante que ninguém passe um OrderId por acidente. O schema já valida o UUID em runtime; o brand garante a identidade semântica em compilação.

# Convenções de exportação

Dois padrões funcionam bem na prática. O idiomático usa o mesmo nome para schema e tipo; o alternativo sufixo o schema com Schema para clareza em codebases com muitos arquivos:

exportacao.ts
// padrão 1 — mesmo nome (idiomático, curto)
export const Usuario = z.object({ /* campos */ });
export type Usuario  = z.infer<typeof Usuario>;

// padrão 2 — sufixo Schema (explícito, bom em codebases grandes)
export const UsuarioSchema = z.object({ /* campos */ });
export type Usuario       = z.infer<typeof UsuarioSchema>;

// quando input e output divergem — exporte ambos
const CriarUsuario = z.object({
  email: z.email(),
  nome:  z.string().min(1),
  ativo: z.boolean().default(true),
});
export type CriarUsuarioInput  = z.input<typeof CriarUsuario>;
export type CriarUsuarioOutput = z.infer<typeof CriarUsuario>;

Capítulo 5

Objects: composição e transformação

z.object é o schema mais usado no dia a dia — qualquer corpo de requisição, registro de banco ou configuração é modelado com ele. Além de definir campos, o schema de objeto expõe métodos de composição que permitem derivar variantes sem duplicar código: subconjuntos via .pick e .omit, schemas de atualização via .partial, extensões via .extend e .merge. Este capítulo cobre o catálogo completo, incluindo o comportamento com campos extras (strip, strict, passthrough) que define o que o parser faz com chaves não declaradas no schema.

# z.object e .shape

O argumento de z.object é um mapa de campo → schema. Cada valor pode ser qualquer schema Zod — primitivo, outro objeto, array, union. O método .shape expõe o mapa original para introspecção ou reuso de campos individuais:

object-basico.ts
import * as z from 'zod';

// schema da tabela products do Vol XI
const Produto = z.object({
  id:           z.number().int().positive(),
  nome:         z.string().min(1).max(200),
  preco:        z.number().positive().finite(),
  categoria_id: z.number().int().positive().optional(),
  ativo:        z.boolean().default(true),
  metadata:     z.unknown(),
});

type Produto = z.infer<typeof Produto>;

// .shape acessa os schemas individuais de cada campo
Produto.shape.nome;   // ZodString — o schema do campo nome
Produto.shape.preco;  // ZodNumber
Produto.shape.ativo;  // ZodDefault — porque tem .default()
Observação
.shape é útil para construir schemas derivados sem redeclará-los: z.object({ id: Produto.shape.id }) reutiliza o schema do campo id em vez de duplicá-lo. Em especial, drizzle-zod usa essa propriedade internamente para compor schemas de insert e select (Cap 18).

# .pick e .omit

Derivam um sub-schema mantendo ou excluindo campos específicos. O argumento é um objeto máscara com os campos desejados marcados como true. O tipo inferido reflete exatamente os campos selecionados:

pick-omit.ts
// .pick — manter apenas os campos listados
const ProdutoResumido = Produto.pick({
  id:    true,
  nome:  true,
  preco: true,
});
type ProdutoResumido = z.infer<typeof ProdutoResumido>;
// { id: number; nome: string; preco: number }

// .omit — excluir campos específicos
const ProdutoSemMeta = Produto.omit({ id: true, metadata: true });
type ProdutoSemMeta = z.infer<typeof ProdutoSemMeta>;
// { nome: string; preco: number; categoria_id?: number; ativo: boolean }

// padrão de CRUD: schema de criação = schema sem id (gerado pelo banco)
const CriarProduto = Produto.omit({ id: true });
const produto = CriarProduto.parse(await req.json());

# .partial e .required

.partial() torna todos os campos opcionais — é o padrão idiomático para schemas de atualização (PATCH), onde o cliente envia apenas os campos que quer mudar. Sem argumento, afeta todos os campos; com uma máscara, afeta apenas os especificados. .required() é o inverso:

partial-required.ts
// schema de atualização: todos os campos opcionais exceto id
const AtualizarProduto = Produto.omit({ id: true }).partial();
type AtualizarProduto = z.infer<typeof AtualizarProduto>;
// {
//   nome?: string;
//   preco?: number;
//   categoria_id?: number;
//   ativo?: boolean;
//   metadata?: unknown;
// }

// .partial com máscara — só os campos listados viram opcionais
const ParcialNomePreco = Produto.partial({ nome: true, preco: true });
// nome e preco opcionais; restantes mantém optionalidade original

// .required — torna todos os campos obrigatórios
const ProdutoCompleto = Produto.partial().required();
// todos os campos voltam a ser required
Boa prática
Para endpoints REST, derive os três schemas a partir de um único objeto base: Produto para respostas (select), Produto.omit({ id: true }) para criação (insert), e Produto.omit({ id: true }).partial() para atualização (update/patch). Uma única declaração, três schemas sem duplicação de campos.

# .extend e .merge

.extend adiciona campos a um schema existente — ou sobrescreve um campo se a chave já existir. .merge combina dois schemas de objeto inteiros, equivalendo a chamar .extend com o .shape do segundo schema. Em caso de conflito de chave, o schema do argumento prevalece:

extend-merge.ts
// .extend — adiciona campos ao schema base
const ProdutoComTimestamp = Produto.extend({
  criado_em:     z.iso.datetime(),
  atualizado_em: z.iso.datetime().optional(),
});

// .extend sobrescreve o campo se a chave já existir
const ProdutoPrecoExato = Produto.extend({
  preco: z.number().positive().multipleOf(0.01), // sobrescreve preco
});

// .merge — combina dois schemas de objeto (B prevalece em conflito)
const Auditoria = z.object({
  criado_em:    z.iso.datetime(),
  criado_por:   z.number().int(),
  atualizado_em: z.iso.datetime().optional(),
});
const ProdutoAuditado = Produto.merge(Auditoria);
// equivalente a Produto.extend(Auditoria.shape)
Armadilha
.extend e .merge aceitam apenas schemas z.object — não funcionam com unions, intersections ou schemas arbitrários. Para combinar um objeto com uma union, use z.intersection ou reestruture como discriminated union (Cap 7).

# .keyof

.keyof() retorna um schema z.enum com os nomes dos campos do objeto. É útil para validar parâmetros que referenciam campos — como o campo de ordenação de uma query string:

keyof.ts
const ProdutoKey = Produto.keyof();
type ProdutoKey = z.infer<typeof ProdutoKey>;
// type ProdutoKey = 'id' | 'nome' | 'preco' | 'categoria_id' | 'ativo' | 'metadata'

// uso prático: validar parâmetros de ordenação
const QueryProdutos = z.object({
  ordenar_por: Produto.keyof().optional(),
  direcao:     z.enum(['asc', 'desc']).default('asc'),
  pagina:      z.coerce.number().int().positive().default(1),
});

const query = QueryProdutos.parse({ ordenar_por: 'preco', direcao: 'desc' });
// query.ordenar_por: 'id' | 'nome' | 'preco' | ... | undefined
// query.direcao: 'asc' | 'desc'

# strip, strict e passthrough

Por padrão, z.object usa o modo strip: campos não declarados no schema são removidos silenciosamente do output. Esse comportamento pode ser alterado por schema:

modos-extras.ts
const Schema = z.object({ nome: z.string() });
const input  = { nome: 'Ana', extra: 'dado_nao_declarado' };

// strip (padrão) — remove campos extras silenciosamente
Schema.parse(input);
// { nome: 'Ana' }  ← campo extra removido

// .strict() — lança ZodError se houver chaves extras
Schema.strict().parse(input);
// ZodError: unrecognized key(s) in object: 'extra'

// .passthrough() — mantém campos extras no output sem validá-los
Schema.passthrough().parse(input);
// { nome: 'Ana', extra: 'dado_nao_declarado' }  ← extra preservado

// .strip() — reverte para o padrão a partir de .strict() ou .passthrough()
Schema.strict().strip();   // volta a ser strip
Boa prática
Use .strict() em schemas de configuração interna e variáveis de ambiente, onde campos extras provavelmente indicam um typo. Use .passthrough() ao receber e repassar payloads de terceiros sem precisar modelar todos os campos. O padrão strip é o mais seguro para dados de usuário — evita que campos extras vazem para o banco ou para respostas da API.

Capítulo 6

Arrays e tuples

z.array e z.tuple são as duas estruturas de coleção ordenada do Zod, com garantias distintas. z.array é homogêneo e de tamanho variável: todos os elementos compartilham o mesmo schema. z.tuple é heterogêneo e de tamanho fixo: cada posição tem seu próprio schema, e posições a mais ou a menos lançam erro. Este capítulo cobre os dois, os métodos de restrição de tamanho, o acesso ao schema do elemento via .element e o rest element de tuples para caudas variáveis.

# z.array

z.array(schema) recebe o schema do item e valida que o input é um array cujos elementos batem com esse schema. O tipo inferido é T[], onde T é o tipo inferido do schema do elemento:

array-basico.ts
import * as z from 'zod';

// arrays de primitivos
const Ids    = z.array(z.number().int().positive());  // number[]
const Tags   = z.array(z.string().min(1));           // string[]
const Flags  = z.array(z.boolean());               // boolean[]

// array de objetos — order_items do Vol XI
const OrderItems = z.array(z.object({
  product_id: z.number().int().positive(),
  quantidade: z.number().int().positive(),
  preco_unit: z.number().positive().finite(),
}));
type OrderItems = z.infer<typeof OrderItems>;
// { product_id: number; quantidade: number; preco_unit: number }[]

const itens = OrderItems.parse(await req.json());

# Validações de tamanho

.min, .max e .length restringem o número de elementos. .nonempty() é um atalho para .min(1), mas com uma diferença importante no tipo inferido — o TypeScript consegue representar que o array tem pelo menos um elemento:

array-tamanho.ts
// restrições de tamanho
z.array(z.string()).min(1);        // ao menos 1 item     — infere string[]
z.array(z.string()).max(100);      // no máximo 100 itens — infere string[]
z.array(z.string()).length(5);     // exatamente 5 itens  — infere string[]

// .nonempty() — atalho para .min(1), com tipo mais preciso
const Tags = z.array(z.string()).nonempty();
type Tags = z.infer<typeof Tags>;
// [string, ...string[]] — tuple com pelo menos 1 item (não string[])
// Tags[0] é acessível sem checar undefined

// encadeamento — itens de pedido: ao menos 1, no máximo 50
const Itens = z.array(z.object({
  product_id: z.number().int(),
  quantidade: z.number().int().positive(),
})).min(1).max(50);
Observação
A diferença de tipo entre .min(1) e .nonempty() importa quando o array é destruturado ou quando o primeiro elemento é acessado diretamente. Com .nonempty(), arr[0] infere T; com .min(1) e noUncheckedIndexedAccess ativo no tsconfig, infere T | undefined.

# .element

.element expõe o schema do item do array. É útil para validar um elemento isolado sem redeclarar o schema, e para introspecção em schemas compostos — a mesma técnica de .shape em objetos:

array-element.ts
const ProdutoSchema = z.object({
  id:    z.number().int().positive(),
  nome:  z.string(),
  preco: z.number().positive(),
});
const Produtos = z.array(ProdutoSchema);

// .element acessa o schema do item
Produtos.element;                // ZodObject — o ProdutoSchema
Produtos.element.shape.preco;    // ZodNumber

// reutiliza o schema do item sem redeclará-lo
const item  = Produtos.element.parse(req.body);  // valida um único item
const lista = Produtos.parse(req.body);          // valida o array inteiro

# z.tuple

z.tuple recebe um array de schemas, um por posição. O tamanho é fixo: elementos a mais ou a menos lançam ZodError. O tipo inferido é uma tupla TypeScript — cada posição tem seu próprio tipo. É o schema natural para pares de coordenadas, resultados de funções que retornam múltiplos valores ou entradas de formulários com estrutura posicional:

tuple-basico.ts
// par de coordenadas [latitude, longitude]
const Coordenada = z.tuple([z.number(), z.number()]);
type Coordenada = z.infer<typeof Coordenada>;
// [number, number]

Coordenada.parse([-23.5, -46.6]);             // OK
Coordenada.parse([-23.5]);                    // ZodError — falta posição 1
Coordenada.parse([-23.5, -46.6, 0]);          // ZodError — posição 2 inesperada

// tuple heterogênea — [id, label, ativo]
const OpcaoSelect = z.tuple([
  z.number().int(),  // valor
  z.string(),       // label
  z.boolean(),      // habilitado
]);
type OpcaoSelect = z.infer<typeof OpcaoSelect>;
// [number, string, boolean]

# rest element

.rest(schema) adiciona um rest element à tuple — posições fixas tipadas individualmente seguidas de uma cauda de tamanho variável com tipo uniforme. O tipo inferido usa a sintaxe de tupla rest do TypeScript:

tuple-rest.ts
// log entry: [timestamp, nível, ...argumentos variáveis]
const LogEntry = z.tuple([
  z.iso.datetime(),  // posição 0 — obrigatório, string ISO
  z.enum(['debug', 'info', 'warn', 'error']),  // posição 1 — obrigatório
]).rest(z.unknown());                           // posições 2+ — variáveis

type LogEntry = z.infer<typeof LogEntry>;
// [string, 'debug' | 'info' | 'warn' | 'error', ...unknown[]]

LogEntry.parse(['2025-01-01T00:00:00Z', 'info']);              // OK
LogEntry.parse(['2025-01-01T00:00:00Z', 'info', 'user criado']); // OK
LogEntry.parse(['2025-01-01T00:00:00Z', 'info', 42, true]);     // OK
LogEntry.parse(['2025-01-01T00:00:00Z']);                       // ZodError — falta posição 1
Boa prática
Prefira z.tuple quando a semântica posicional importa: coordenadas, configurações de cor [R, G, B], resultados de spread de funções. Prefira z.array quando os elementos são semanticamente equivalentes e o tamanho é desconhecido. Para arrays com pelo menos um item obrigatório, use .nonempty() em vez de .min(1) — o tipo inferido é mais preciso.

Capítulo 7

Unions e discriminated unions

Uniões representam o "isto OU aquilo" no sistema de tipos — um valor que pode ter mais de uma forma. Zod oferece duas implementações com trade-offs muito diferentes: z.union é a forma geral que tenta cada schema em ordem até um bater, e z.discriminatedUnion é a forma especializada para objetos com um campo discriminador comum. A diferença não é cosmética: discriminated union faz um lookup direto pelo discriminador, custa O(1) em vez de O(N) tentativas, produz mensagens de erro precisas, e habilita narrowing exhaustivo no TypeScript. Este capítulo cobre as duas, o modelo mental por trás da escolha, e z.intersection como complemento para combinar requisitos.

# z.union: tentativa em ordem

z.union([A, B, C]) recebe um array de schemas e devolve um schema que aceita qualquer um deles. O algoritmo é direto: tenta cada schema na ordem, retorna o primeiro que bate. Se nenhum bate, lança um ZodError com a lista de todas as falhas:

union-basico.ts
import * as z from 'zod';

// um id que pode ser string (uuid) ou number (auto-increment) — APIs mistas
const Id = z.union([
  z.string().uuid(),
  z.number().int().positive(),
]);
type Id = z.infer<typeof Id>;
// string | number

Id.parse('123e4567-e89b-12d3-a456-426614174000');  // OK (bate no primeiro)
Id.parse(42);                                      // OK (bate no segundo)
Id.parse(true);                                    // ZodError — nenhum bateu

// atalho equivalente: .or()
const Id2 = z.string().uuid().or(z.number().int().positive());

Esse modelo funciona bem quando os schemas são bem distintos — um primitivo e um objeto, dois primitivos incompatíveis, schemas com formatos óbvios. O problema aparece quando os schemas se sobrepõem ou são complexos:

union-limitacoes.ts
// PROBLEMA 1: ordem importa quando há sobreposição
const Ambiguo = z.union([
  z.string(),         // aceita qualquer string
  z.string().uuid(), // aceita só uuid — NUNCA ALCANÇADO
]);
Ambiguo.parse('não é uuid'); // passa! z.string() pegou antes

// PROBLEMA 2: mensagens de erro confusas em objetos similares
const PedidoStatus = z.union([
  z.object({ tipo: z.literal('pendente'),  criado_em: z.iso.datetime() }),
  z.object({ tipo: z.literal('pago'),      pago_em: z.iso.datetime() }),
  z.object({ tipo: z.literal('cancelado'), motivo: z.string() }),
]);

PedidoStatus.parse({ tipo: 'pago', pago_em: 'data invalida' });
// ZodError lista TRÊS falhas, uma por schema tentado:
//   "esperava 'pendente' em tipo"     ← do primeiro schema
//   "data inválida em pago_em"        ← do segundo (a verdadeira)
//   "esperava 'cancelado' em tipo"    ← do terceiro
// — só uma é o erro real, mas o usuário vê todas
Armadilha
Em z.union com objetos parecidos, o erro retornado é uma união de tentativas falhadas. Mostrar isso direto para o usuário final ou para um cliente da API gera ruído. Sempre que houver um campo comum que discrimine as alternativas (status, tipo, kind, type), prefira z.discriminatedUnion.

# z.discriminatedUnion: lookup direto

Quando os objetos da união compartilham um campo com valor literal único por variante — um discriminador — z.discriminatedUnion usa esse campo como índice. Em vez de tentar todos os schemas, lê o discriminador uma vez e vai direto ao schema correspondente. Sintaxe e semântica:

discriminated-union.ts
// mesma união acima, agora discriminada pelo campo 'tipo'
const PedidoStatus = z.discriminatedUnion('tipo', [
  z.object({
    tipo:      z.literal('pendente'),
    criado_em: z.iso.datetime(),
  }),
  z.object({
    tipo:    z.literal('pago'),
    pago_em: z.iso.datetime(),
    valor:   z.number().positive(),
  }),
  z.object({
    tipo:         z.literal('cancelado'),
    cancelado_em: z.iso.datetime(),
    motivo:       z.string().min(1),
  }),
]);

type PedidoStatus = z.infer<typeof PedidoStatus>;
// type PedidoStatus =
//   | { tipo: 'pendente';  criado_em: string }
//   | { tipo: 'pago';      pago_em: string; valor: number }
//   | { tipo: 'cancelado'; cancelado_em: string; motivo: string }

// agora o parse lê 'tipo' primeiro e vai DIRETO no schema correto
PedidoStatus.parse({ tipo: 'pago', pago_em: 'data invalida' });
// ZodError: "data inválida em pago_em" — uma única falha, na variante certa
Performance & custo
Em z.union com N variantes, no pior caso (input que falha em todas) Zod tenta cada schema completo — N parses. Em z.discriminatedUnion, Zod faz um lookup pelo discriminador (O(1) em um map interno) e executa exatamente um parse. Em payloads de webhook com 30+ tipos de evento (Stripe, GitHub) a diferença é visível em benchmarks. Zod 4 melhorou também o custo do z.union via short-circuit em campos posicionais, mas discriminated continua sendo várias vezes mais rápido.

# Narrowing exhaustivo

Discriminated unions casam com o sistema de narrowing do TypeScript. Quando você usa switch sobre o discriminador, o compilador estreita o tipo dentro de cada case. Combinando com o tipo never num branch default, garante-se em compilação que toda variante foi tratada — se uma nova for adicionada ao schema, o código deixa de compilar até ser atualizada:

narrowing.ts
function processar(pedido: PedidoStatus) {
  switch (pedido.tipo) {
    case 'pendente':
      // pedido: { tipo: 'pendente'; criado_em: string }
      console.log('aguardando pagamento desde', pedido.criado_em);
      break;

    case 'pago':
      // pedido: { tipo: 'pago'; pago_em: string; valor: number }
      console.log('R$', pedido.valor, 'pago em', pedido.pago_em);
      break;

    case 'cancelado':
      // pedido: { tipo: 'cancelado'; cancelado_em: string; motivo: string }
      console.log('cancelado:', pedido.motivo);
      break;

    default:
      // pedido: never — todas as variantes foram cobertas
      // se uma nova variante for adicionada, esta linha deixa de compilar
      assertNever(pedido);
  }
}

function assertNever(x: never): never {
  throw new Error(`caso não coberto: ${JSON.stringify(x)}`);
}
Boa prática
O par discriminated union + assertNever é o padrão idiomático para máquinas de estado em TypeScript — pedidos, assinaturas, deploys, qualquer entidade com estados que carregam dados diferentes. O compilador serve como teste de cobertura: novo estado adicionado ao schema = erro de compilação em cada switch que não foi atualizado.

# Caso real: webhooks

Webhooks de serviços externos (Stripe, GitHub, Sentry) são o ambiente nativo de discriminated unions. Todos seguem o mesmo padrão: um campo type ou event com valor literal por tipo de evento, e um payload data cuja forma depende do tipo:

webhook-stripe.ts
const WebhookStripe = z.discriminatedUnion('type', [
  z.object({
    type: z.literal('invoice.paid'),
    data: z.object({
      object: z.object({
        id:          z.string().startsWith('in_'),
        amount_paid: z.number().int().positive(),
        customer:    z.string().startsWith('cus_'),
      }),
    }),
  }),
  z.object({
    type: z.literal('charge.refunded'),
    data: z.object({
      object: z.object({
        id:              z.string().startsWith('ch_'),
        amount_refunded: z.number().int().positive(),
        reason:          z.enum(['fraudulent', 'duplicate', 'requested_by_customer']),
      }),
    }),
  }),
  z.object({
    type: z.literal('customer.created'),
    data: z.object({
      object: z.object({
        id:    z.string().startsWith('cus_'),
        email: z.email(),
      }),
    }),
  }),
]);

const evento = WebhookStripe.parse(await req.json());

switch (evento.type) {
  case 'invoice.paid':
    await creditarConta(evento.data.object.customer, evento.data.object.amount_paid);
    break;
  case 'charge.refunded':
    await registrarEstorno(evento.data.object.id, evento.data.object.reason);
    break;
  case 'customer.created':
    await enviarBoasVindas(evento.data.object.email);
    break;
}
Zod 4
Zod 4 permite aninhar discriminated unions — uma variante de uma discriminated union pode ser ela mesma uma discriminated union. Em Zod 3, isso exigia gambiarra com z.union envolvente. Útil para webhooks com sub-tipos: type: 'invoice.*' com um discriminador secundário subtype dentro de data.

# z.intersection

Enquanto union é "isto OU aquilo", intersection é "isto E aquilo" — o input precisa satisfazer todos os schemas combinados. O tipo inferido é a interseção TypeScript (A & B). Para objetos puros, .merge e .extend do Cap 5 fazem o mesmo de forma mais ergonômica; z.intersection é necessário quando ao menos um dos lados não é um z.object simples:

intersection.ts
const Pessoa     = z.object({ nome: z.string(), idade: z.number().int() });
const Funcionario = z.object({ empresa: z.string(), cargo: z.string() });

// z.intersection — input precisa satisfazer ambos
const PessoaFuncionario = z.intersection(Pessoa, Funcionario);
type PessoaFuncionario = z.infer<typeof PessoaFuncionario>;
// { nome: string; idade: number } & { empresa: string; cargo: string }
// equivalente a { nome: string; idade: number; empresa: string; cargo: string }

// atalho .and()
const Combo = Pessoa.and(Funcionario);

// para z.object, prefira .merge — mesmo resultado, sem perder métodos de object
const Melhor = Pessoa.merge(Funcionario);
// Melhor é ZodObject — tem .pick, .omit, .partial, .keyof, etc
// PessoaFuncionario é ZodIntersection — perde os métodos de object
Observação
z.intersection é raro na prática. Os casos legítimos são interseções com unions, com schemas transformados (.transform), ou com schemas vindos de libs externas que não expõem .merge. Para qualquer composição de z.object com z.object, use .merge ou .extend.

# Quando usar cada um

Situação API Justificativa
Primitivos diferentes (string ou number) z.union Sem campo discriminador; sobreposição rara
Objetos com campo discriminador comum z.discriminatedUnion Performance + erros melhores + narrowing
Webhooks de serviços externos z.discriminatedUnion Caso canônico — sempre tem type/event
Máquina de estados z.discriminatedUnion + assertNever Cobertura exaustiva garantida em compilação

Enums e literals

Literais e enums representam conjuntos fechados de valores conhecidos em tempo de design. z.literal aceita um valor específico — uma string, número ou booleano exato. z.enum aceita um conjunto fixo de strings, equivalente a uma union de literais string. z.nativeEnum ponte para enums declarados com a sintaxe nativa do TypeScript. Este capítulo cobre as três APIs, os métodos que manipulam o conjunto de valores (.options, .extract, .exclude) e quando preferir cada forma.

# z.literal

z.literal(valor) aceita exclusivamente o valor passado — verifica igualdade estrita (===). O tipo inferido é o tipo literal correspondente, não o tipo amplo:

literal.ts
import * as z from 'zod';

// literal string
const Pendente = z.literal('pendente');
type Pendente = z.infer<typeof Pendente>;
// type Pendente = 'pendente'  (não string)

Pendente.parse('pendente');  // OK
Pendente.parse('pago');      // ZodError

// literal de outros tipos primitivos
z.literal(42);       // type: 42
z.literal(true);     // type: true
z.literal(null);     // type: null

// uso canônico: discriminador em discriminated unions (Cap 7)
const Pago = z.object({
  tipo:    z.literal('pago'),    // trava o valor do campo
  pago_em: z.iso.datetime(),
});

# z.enum

z.enum aceita um array (declarado com as const implicitamente) e devolve um schema que valida qualquer string do conjunto. O tipo inferido é a union de literais correspondente:

enum.ts
// status da tabela orders do Vol XI
const StatusPedido = z.enum(['pendente', 'pago', 'cancelado']);
type StatusPedido = z.infer<typeof StatusPedido>;
// type StatusPedido = 'pendente' | 'pago' | 'cancelado'

StatusPedido.parse('pago');     // OK
StatusPedido.parse('PAGO');     // ZodError — case-sensitive
StatusPedido.parse('enviado');  // ZodError — não está no conjunto

// também aceita objeto de chaves nomeadas (Zod 4)
const Papel = z.enum({
  ADMIN:    'admin',
  CLIENTE:  'cliente',
  CONVIDADO:'convidado',
});
type Papel = z.infer<typeof Papel>;
// type Papel = 'admin' | 'cliente' | 'convidado'
Zod 4
Em Zod 4, z.enum também aceita um objeto além do array. A forma de array (z.enum(['a', 'b'])) continua sendo a mais idiomática e infere o tipo corretamente. A forma de objeto é útil para mapear chaves descritivas a valores (constantes nomeadas) sem precisar declarar um enum TypeScript separado.

# z.nativeEnum

z.nativeEnum integra com enums declarados via a sintaxe enum do TypeScript — incluindo enums numéricos, string enums, e const enum. É o caminho quando o schema precisa coexistir com código TS que já usa enum tradicional:

native-enum.ts
// enum string TypeScript
enum PapelEnum {
  Admin    = 'ADMIN',
  Cliente  = 'CLIENTE',
  Convidado= 'CONVIDADO',
}

const Papel = z.nativeEnum(PapelEnum);
type Papel = z.infer<typeof Papel>;
// type Papel = PapelEnum  ('ADMIN' | 'CLIENTE' | 'CONVIDADO')

Papel.parse(PapelEnum.Admin);  // OK
Papel.parse('ADMIN');          // OK — o valor literal também passa
Papel.parse('admin');          // ZodError — case errado

// enum numérico
enum Prioridade {
  Baixa  = 1,
  Media  = 2,
  Alta   = 3,
}
const P = z.nativeEnum(Prioridade);
P.parse(2);                        // OK — Prioridade.Media
P.parse(Prioridade.Alta);            // OK
Observação
Em projetos novos, prefira z.enum com array de strings em vez de enum TypeScript + z.nativeEnum. enum tem peculiaridades históricas (geração de objeto runtime, comportamento diferente para enums numéricos vs string) que z.enum evita. Reserve z.nativeEnum para integrar com código existente que já usa enum.

# .options, .extract, .exclude

Schemas de enum têm métodos para introspecção e derivação de subconjuntos. .options expõe a lista de valores como array; .extract e .exclude criam novos enums com subconjuntos do original:

enum-metodos.ts
const StatusPedido = z.enum(['pendente', 'pago', 'cancelado', 'reembolsado']);

// .options — lista de valores como array readonly
StatusPedido.options;
// readonly ['pendente', 'pago', 'cancelado', 'reembolsado']

// uso prático: gerar opções de <select> HTML a partir do schema
const opcoes = StatusPedido.options.map(s => ({ valor: s, label: s }));

// .extract — subconjunto explícito
const Finalizados = StatusPedido.extract(['pago', 'reembolsado']);
type Finalizados = z.infer<typeof Finalizados>;
// type Finalizados = 'pago' | 'reembolsado'

// .exclude — complemento (todos exceto os listados)
const Ativos = StatusPedido.exclude(['cancelado', 'reembolsado']);
type Ativos = z.infer<typeof Ativos>;
// type Ativos = 'pendente' | 'pago'

# Union de literals vs z.enum

Os dois caminhos produzem o mesmo tipo TypeScript final. A diferença é ergonômica e funcional:

union-vs-enum.ts
// forma 1: union de z.literal — equivale a z.enum, mas mais verboso
const A = z.union([
  z.literal('pendente'),
  z.literal('pago'),
  z.literal('cancelado'),
]);
type A = z.infer<typeof A>;
// type A = 'pendente' | 'pago' | 'cancelado'

// forma 2: z.enum — idiomática, mais curta, expõe .options/.extract/.exclude
const B = z.enum(['pendente', 'pago', 'cancelado']);
type B = z.infer<typeof B>;
// type B = 'pendente' | 'pago' | 'cancelado'  (idêntico a A)

// quando usar union de literals?
// - misturar tipos: z.union([z.literal('auto'), z.literal(0), z.literal(false)])
// - z.enum aceita só strings
const Tema = z.union([
  z.literal('claro'),
  z.literal('escuro'),
  z.literal('auto'),
  z.literal(null), // null não é string — z.enum não aceitaria
]);
Boa prática
Para conjuntos de strings, sempre z.enum — é mais curto, tem métodos úteis e mensagens de erro mais limpas ("expected one of: 'a' | 'b' | 'c'"). Reserve union de literals para conjuntos com tipos mistos (string + number + null) ou para discriminadores em discriminated union, onde cada variante carrega um z.literal distinto.

Capítulo 9

Records, maps e sets

z.record, z.map e z.set cobrem as três estruturas de coleção chave-valor e conjunto do JavaScript que não são arrays simples. z.record valida objetos plain com chaves homogêneas — dicionários, caches, configurações por ambiente. z.map valida instâncias de Map. z.set valida instâncias de Set com garantia de unicidade. A diferença central entre z.record e z.object é a natureza das chaves: em z.object, as chaves são conhecidas em design e cada uma tem seu próprio schema; em z.record, as chaves são dinâmicas e todos os valores compartilham o mesmo schema.

# z.record

z.record(keySchema, valueSchema) valida um objeto cujas chaves e valores seguem schemas homogêneos. Se chamado com apenas um argumento, assume chaves do tipo string:

record-basico.ts
import * as z from 'zod';

// dicionário sku → preço
const PrecosPorSku = z.record(z.string(), z.number().positive());
type PrecosPorSku = z.infer<typeof PrecosPorSku>;
// Record<string, number>

PrecosPorSku.parse({ 'sku-001': 29.90, 'sku-002': 149.00 });  // OK
PrecosPorSku.parse({ 'sku-001': 'gratis' });  // ZodError — valor não é number

// cache de produtos: chave = id string, valor = objeto
const CacheProdutos = z.record(
  z.string(),
  z.object({
    id:    z.number().int(),
    nome:  z.string(),
    preco: z.number().positive(),
  })
);
type CacheProdutos = z.infer<typeof CacheProdutos>;
// Record<string, { id: number; nome: string; preco: number }>
Observação
z.record não garante que o objeto tenha ao menos uma chave — um objeto vazio {} passa. Para exigir ao menos uma entrada, combine com .refine: z.record(...).refine(r => Object.keys(r).length > 0) (refinamentos no Cap 10).

# Chaves tipadas com z.enum

O primeiro argumento de z.record pode ser qualquer schema de chave — não apenas z.string(). Usar z.enum transforma o record num mapa de configuração com conjunto fechado de chaves:

record-chaves.ts
// configuração por ambiente — apenas as três chaves são válidas
const ConfigPorAmbiente = z.record(
  z.enum(['development', 'production', 'test']),
  z.object({
    db_url: z.url(),
    port:   z.number().int().positive(),
  })
);
type ConfigPorAmbiente = z.infer<typeof ConfigPorAmbiente>;
// Record<'development' | 'production' | 'test', { db_url: string; port: number }>

ConfigPorAmbiente.parse({
  development: { db_url: 'postgresql://localhost/dev', port: 5432 },
  production:  { db_url: 'postgresql://prod.host/app',  port: 5432 },
  test:        { db_url: 'postgresql://localhost/test', port: 5433 },
});  // OK

ConfigPorAmbiente.parse({
  staging: { db_url: '...', port: 5432 },
});  // ZodError — 'staging' não está no enum
Boa prática
Quando as chaves são conhecidas em design, prefira z.object — cada campo tem seu próprio schema e o tipo inferido é mais preciso. Use z.record quando as chaves são dinâmicas (slugs de produto, nomes de usuário, chaves de tradução) ou quando o conjunto de chaves é grande demais para declarar campo a campo.

# z.map

z.map(keySchema, valueSchema) valida instâncias nativas de Map<K, V>. Objetos plain falham — o schema verifica o tipo da coleção, não apenas a estrutura:

map.ts
// Map<number, string> — id do produto para nome
const NomesPorId = z.map(
  z.number().int().positive(),
  z.string().min(1)
);
type NomesPorId = z.infer<typeof NomesPorId>;
// Map<number, string>

const mapa = new Map([
  [1, 'Cadeira Ergonômica'],
  [2, 'Mesa de Escritório'],
]);
NomesPorId.parse(mapa);              // OK
NomesPorId.parse({ 1: 'Cadeira' }); // ZodError — objeto plain não é Map
Observação
z.map é raro em fronteiras HTTP — JSON não tem representação nativa de Map. O uso típico é em lógica interna da aplicação, validando Maps construídos em memória. Se o dado vem de HTTP e precisa virar um Map, valide com z.record e converta depois: new Map(Object.entries(record)).

# z.set

z.set(schema) valida instâncias nativas de Set<T>. Como Set elimina duplicatas por definição, o schema valida apenas os tipos dos elementos. Métodos de restrição de tamanho são análogos aos de z.array:

set.ts
// conjunto de IDs de categorias — sem duplicatas
const IdsUnicos = z.set(z.number().int().positive());
type IdsUnicos = z.infer<typeof IdsUnicos>;
// Set<number>

IdsUnicos.parse(new Set([1, 2, 3]));        // OK
IdsUnicos.parse(new Set([1, 2, 2, 3]));     // OK — Set já deduplicou
IdsUnicos.parse([1, 2, 3]);               // ZodError — array não é Set

// validações de tamanho (espelho de z.array)
z.set(z.string()).nonempty();            // ao menos 1 elemento
z.set(z.string()).min(2).max(10);        // entre 2 e 10 elementos
z.set(z.string()).size(5);              // exatamente 5 elementos

usos-praticos.ts

Refinamentos e transforms

Os capítulos anteriores cobriram a forma estática dos schemas — quais tipos cada campo aceita. Este capítulo cobre o que vem depois: validações de regra de negócio que dependem do valor (não só do tipo) e transformações que alteram o output. .refine e .superRefine permitem expressar predicados customizados; .transform permite reescrever o valor após a validação; .pipe permite encadear schemas em sequência. O conjunto forma um pipeline cujas etapas rodam em ordem fixa — entender essa ordem é o que separa schemas que funcionam de schemas que falham por motivos estranhos.

# O pipeline de validação

Um schema Zod é uma sequência de etapas executadas em ordem. Para um input qualquer, o pipeline é:

pipeline.ts
// um schema Zod processa o input nesta ordem:
//   1. parse base       — verifica o tipo (é string? number? array?)
//   2. checks built-in  — .min, .max, .email, .regex, .int, etc.
//   3. refinamentos     — .refine, .superRefine
//   4. transforms       — .transform
// se qualquer etapa falhar, o pipeline para — etapas posteriores não rodam

const Senha = z
  .string()                                              // 1. é string?
  .min(8)                                                // 2. tamanho >= 8?
  .refine(s => /[A-Z]/.test(s), 'precisa maiúscula') // 3. tem maiúscula?
  .transform(s => s.trim());                          // 4. remove espaços

// 'abc'      → falha em .min(8); .refine e .transform não rodam
// 'abcdefgh' → passa .min(8); falha em .refine; .transform não roda
// 'Abcdefgh' → passa todas; transform retorna 'Abcdefgh'

Essa ordem fixa tem três consequências práticas. Refinamentos só recebem valores que já passaram nos checks anteriores — você nunca precisa checar tipo dentro de um .refine. Transforms só rodam se tudo antes passou — o output transformado é garantidamente válido. E o output do parser é o resultado após os transforms — se você precisa do valor original, capture antes de aplicar .transform.

# .refine: validação customizada

.refine(predicado, mensagem) aplica um predicado boolean ao valor já parseado. Se retorna false, um ZodIssue de código custom é adicionado. A mensagem pode ser uma string ou um objeto com message e path — o path define onde, na estrutura do output, o erro foi originado:

refine.ts
// forma simples — string como mensagem
const Senha = z.string().min(8).refine(
  s => /[A-Z]/.test(s) && /[0-9]/.test(s),
  'Senha precisa de letra maiúscula e número'
);

Senha.parse('abcdefgh');   // ZodError — falta maiúscula
Senha.parse('Abcdef12');   // 'Abcdef12'

// forma com objeto — controla mensagem E path do erro
const Cep = z.string().refine(
  s => /^\d{8}$/.test(s.replace(/-/, '')),
  { message: 'CEP inválido — 8 dígitos' }
);

// refinamento entre campos — predicado recebe o objeto inteiro
const SignUp = z.object({
  senha:       z.string().min(8),
  confirmacao: z.string().min(8),
}).refine(
  d => d.senha === d.confirmacao,
  { message: 'Senhas não conferem', path: ['confirmacao'] }
);

SignUp.parse({ senha: 'abcdefgh', confirmacao: 'diferente' });
// ZodError em path ['confirmacao'] — o erro aparece "no campo certo"
Boa prática
Sempre passe path em refinamentos cross-field. Sem ele, o erro aparece na raiz do objeto, e o cliente (formulário, UI, API consumer) não sabe em qual campo marcar a falha. Com path: ['confirmacao'], bibliotecas de formulário como React Hook Form (Cap 20) destacam o campo correto automaticamente.

Refinamentos podem ser encadeados. Cada .refine que falha vira um issue independente — todos os issues são retornados juntos, não apenas o primeiro:

refine-encadeado.ts
const CriarPedido = z.object({
  itens:    z.array(z.unknown()).min(1),
  cupom:    z.string().optional(),
  desconto: z.number().min(0).max(100).optional(),
})
.refine(d => !d.desconto || d.cupom, {
  message: 'Desconto requer cupom',
  path: ['cupom'],
})
.refine(d => d.itens.length <= 50, {
  message: 'Máximo 50 itens por pedido',
  path: ['itens'],
});

// um único parse pode retornar múltiplos issues — um por refine que falhou

# .superRefine: múltiplos issues e controle fino

.refine é binário — passa ou falha, com uma única mensagem. .superRefine recebe um callback (valor, ctx) => void onde ctx.addIssue permite adicionar quantos issues quiser, cada um com seu próprio código, mensagem e path. É a ferramenta certa quando uma única validação produz múltiplos erros distintos ou quando o tipo de erro depende do valor:

super-refine.ts
const SignUp = z.object({
  email:       z.string(),
  senha:       z.string(),
  confirmacao: z.string(),
}).superRefine((val, ctx) => {
  if (!val.email.includes('@')) {
    ctx.addIssue({
      code:    'custom',
      message: 'Email inválido',
      path:    ['email'],
    });
  }
  if (val.senha.length < 8) {
    ctx.addIssue({
      code:    'too_small',
      minimum: 8,
      type:    'string',
      inclusive: true,
      message: 'Senha precisa ao menos 8 caracteres',
      path:    ['senha'],
    });
  }
  if (val.senha !== val.confirmacao) {
    ctx.addIssue({
      code:    'custom',
      message: 'Senhas não conferem',
      path:    ['confirmacao'],
    });
  }
});

// um único safeParse devolve até TRÊS issues, um por addIssue acionado
const res = SignUp.safeParse({ email: 'a', senha: 'b', confirmacao: 'c' });
// res.error.issues.length === 3 — todos reportados juntos
Zod 4
Zod 4 introduziu .check() como API alternativa para validações com múltiplos issues — semanticamente próxima a .superRefine mas com ergonomia ligeiramente diferente. .superRefine continua suportada e é a forma mais documentada. Para código novo, ambas funcionam; siga a convenção do projeto.

O código do issue (code) determina como ele é classificado. 'custom' é o caminho geral para regras de negócio. Códigos como 'too_small', 'too_big', 'invalid_type' existem em Zod e podem ser usados em addIssue para alinhar erros customizados ao formato dos erros nativos — útil quando a UI já interpreta o discriminador code (Cap 13).

# .transform: alterar o output

.transform(fn) reescreve o valor após a validação. O input do schema continua sendo o que z.string() ou qualquer outro tipo declara; o output passa a ser o que fn retorna. Como o Cap 4 mostrou, isso faz z.input e z.output divergirem:

transform.ts
// transform que preserva o tipo — só normaliza o valor
const EmailNormalizado = z.email().transform(s => s.trim().toLowerCase());
EmailNormalizado.parse('  Ana@Example.COM  ');  // 'ana@example.com'

// transform que muda o tipo
const ListaCsv = z.string().transform(s => s.split(','));
type ListaCsv = z.infer<typeof ListaCsv>;
// type ListaCsv = string[]  (output após transform)

// transform com possível falha — use ctx + z.NEVER para abortar
const NumeroDeString = z.string().transform((s, ctx) => {
  const n = parseInt(s, 10);
  if (isNaN(n)) {
    ctx.addIssue({ code: 'custom', message: 'não é um número válido' });
    return z.NEVER; // sentinela: aborta a transformação
  }
  return n;
});

NumeroDeString.parse('42');    // 42
NumeroDeString.parse('abc');   // ZodError — 'não é um número válido'
Armadilha
Dentro de um .transform que pode falhar, return z.NEVER é obrigatório após chamar ctx.addIssue. Sem ele, a função continua executando e retorna um valor que não bate com o tipo declarado — Zod aceita o issue mas o output fica inconsistente. z.NEVER é o tipo sentinela que comunica "abortei, ignore o retorno".

# .pipe: composição sequencial

A.pipe(B) roda A, pega o output, e passa como input para B. É a forma natural de "transformar e depois validar" — algo que .refine sozinho não faz (refine não muda o tipo) e .transform sozinho também não (transform aceita qualquer retorno, sem revalidar):

pipe.ts
// padrão "transforma → valida": string → number → number positivo
const PositivoDeString = z
  .string()
  .transform(s => parseInt(s, 10))   // agora é number (mesmo se NaN)
  .pipe(z.number().int().positive());  // valida o number resultante

PositivoDeString.parse('42');    // 42
PositivoDeString.parse('-1');    // ZodError em z.number().positive()
PositivoDeString.parse('abc');   // parseInt('abc') = NaN → falha em .int()

// CSV de query string → array de números validados
const CsvIds = z
  .string()
  .transform(s => s.split(','))
  .pipe(z.array(z.coerce.number().int().positive()).min(1));

CsvIds.parse('1,2,3');     // [1, 2, 3]
CsvIds.parse('1,abc,3');   // ZodError em [1] — 'abc' não coage para int
CsvIds.parse('');          // transform → [''] → coerce falha

Sem .pipe, o output de .transform entra no tipo final sem revalidação. Com .pipe, o output de .transform vira o input de outro schema completo — incluindo seus próprios refinements e transforms. É a forma idiomática de aplicar regras de negócio a um valor já normalizado.

# Caso real: pedido com regras de negócio

O exemplo a seguir combina tudo. Um schema de criação de pedido valida os campos estaticamente com Zod, e usa .superRefine para expressar três regras de negócio que dependem da relação entre campos:

criar-pedido.ts
const CriarPedido = z.object({
  user_id: z.number().int().positive(),
  itens:   z.array(z.object({
    product_id: z.number().int().positive(),
    quantidade: z.number().int().positive(),
    preco_unit: z.number().positive(),
  })).min(1).max(50),
  cupom:    z.string().optional(),
  desconto: z.number().min(0).max(100).optional(),
  metodo:   z.enum(['cartao', 'pix', 'boleto']),
}).superRefine((val, ctx) => {
  // regra 1: desconto exige cupom
  if (val.desconto && !val.cupom) {
    ctx.addIssue({
      code: 'custom',
      message: 'Desconto requer cupom de validação',
      path: ['cupom'],
    });
  }

  // regra 2: boleto não aceita desconto acima de 5%
  if (val.metodo === 'boleto' && val.desconto && val.desconto > 5) {
    ctx.addIssue({
      code: 'custom',
      message: 'Boleto aceita desconto máximo de 5%',
      path: ['desconto'],
    });
  }

  // regra 3: PIX exige valor total mínimo de R$10
  const total = val.itens.reduce(
    (acc, i) => acc + i.preco_unit * i.quantidade,
    0
  );
  if (val.metodo === 'pix' && total < 10) {
    ctx.addIssue({
      code: 'custom',
      message: 'PIX exige valor mínimo de R$10',
      path: ['itens'],
    });
  }
});

const pedido = CriarPedido.parse(await req.json());
// se passar, todas as regras de negócio foram satisfeitas
Performance & custo
Refinamentos rodam apenas se o parse estrutural passou — não há custo em campos rejeitados antes. Mas refinamentos cross-field em objetos grandes podem ler todos os campos uma vez por refine encadeado. Em hot paths (rotas chamadas milhares de vezes por segundo), prefira .superRefine a múltiplos .refine — uma única função roda o predicado para todas as regras em uma passada sobre o objeto.

Strings: validações

Zod 4 promoveu as validações de formato de string de métodos encadeados (z.string().email()) para schemas top-level (z.email()). A mudança não é só sintática: cada format top-level é um schema independente com suas próprias opções — mensagem de erro, padrão regex, restrições adicionais. Este capítulo cobre o catálogo completo de formats, os schemas z.iso.* para datas e horas expressas como strings, z.regex para padrões customizados, e os métodos de normalização que transformam o valor enquanto validam.

# Formatos top-level

Em Zod 4, cada formato de string tem seu próprio schema de nível raiz. O tipo inferido é sempre string — a semântica do formato é expressa no schema, não no tipo TypeScript:

formatos.ts
import * as z from 'zod';

z.email();      // email válido — ex: 'ana@example.com'
z.url();        // URL com protocolo — ex: 'https://example.com'
z.uuid();       // UUID v4  — ex: '123e4567-e89b-12d3-a456-426614174000'
z.ipv4();       // IP v4    — ex: '192.168.1.1'
z.ipv6();       // IP v6    — ex: '::1' ou '2001:db8::1'
z.base64();     // Base64 padrão
z.base64url(); // Base64url — seguro em URLs
z.jwt();        // JWT — verifica estrutura, NÃO a assinatura
z.emoji();      // string composta apenas de emojis

// todos inferem type: string
// branded types (Cap 4) podem adicionar semântica nominal se necessário
Zod 4
Em Zod 3, os formatos eram métodos de z.string(): z.string().email(), z.string().uuid() etc. Em Zod 4 eles são schemas autônomos. A forma antiga ainda funciona para compatibilidade mas está deprecated. Migração: substitua z.string().email() por z.email(). Para branded types, o encadeamento continua funcional: z.email().brand<'Email'>().

# Uso nos schemas do e-commerce

Os formats entram diretamente nos schemas de entidade. Notar que z.url() exige protocolo — uma string como 'example.com' sem https:// falha:

ecommerce-strings.ts
// tabela users — email + avatar opcional
const UsuarioPublico = z.object({

  email:      z.email(),
  avatar_url: z.url().optional(),

// z.url exige protocolo
z.url().parse('example.com');           // ZodError — sem protocolo
z.url().parse('https://example.com');  // OK

const WebhookPayload = z.object({

// validação de assinatura fica em middleware de auth (Cap 13 de Vol XIII)

# z.iso.* — data e hora como string

O namespace z.iso agrupa schemas para strings no formato ISO 8601. Diferente de z.date() que exige um objeto Date, esses schemas trabalham com strings — que é o formato natural em HTTP, JSON e banco de dados:

iso.ts
// z.iso.datetime — data + hora completa
z.iso.datetime();
// '2025-01-15T10:30:00Z'          OK (UTC)
// '2025-01-15T10:30:00.000Z'      OK (com milissegundos)
// '2025-01-15T10:30:00+03:00'     OK (com offset)

// z.iso.date — apenas data
z.iso.date();
// '2025-01-15'   OK
// '2025-1-5'     ZodError — precisa zero-padded

// z.iso.time — apenas hora
z.iso.time();
// '10:30:00'     OK
// '10:30'        ZodError — segundos obrigatórios

// z.iso.duration — duração ISO 8601
z.iso.duration();
// 'P1Y2M3D'      OK (1 ano, 2 meses, 3 dias)
// 'PT4H30M'      OK (4 horas, 30 minutos)

// opções de z.iso.datetime
z.iso.datetime({ offset: true  });   // exige timezone offset (+03:00)
z.iso.datetime({ local:  true  });   // aceita sem Z e sem offset
z.iso.datetime({ precision: 3 });    // exige milissegundos (.sss)

// campo criado_em da tabela orders do Vol XI
const CamposAuditoria = z.object({
  criado_em:     z.iso.datetime(),
  atualizado_em: z.iso.datetime().optional(),
  data_entrega:  z.iso.date().optional(),
});
Observação
z.iso.datetime() retorna e infere string. Para obter um objeto Date, encadeie com .transform(s => new Date(s)) ou use z.coerce.date() (Cap 15). A abordagem string é preferível em schemas de API onde a data é transmitida e armazenada como string — a conversão para Date deve acontecer no ponto de uso.

# z.regex — padrão customizado

z.string().regex(pattern, message) valida a string contra uma expressão regular. É o escape hatch para qualquer formato que não tem schema top-level dedicado — CEPs, telefones, slugs, códigos internos:

regex.ts
// CEP brasileiro — 8 dígitos, hífen opcional
const Cep = z.string().regex(/^\d{5}-?\d{3}$/, 'CEP inválido');
Cep.parse('01310-100');    // OK
Cep.parse('01310100');     // OK — hífen opcional no padrão
Cep.parse('abc');         // ZodError — 'CEP inválido'

// slug para URL de produto — letras minúsculas, números, hífens
const Slug = z.string()
  .min(1)
  .max(80)
  .regex(/^[a-z0-9]+(?:-[a-z0-9]+)*$/, 'Slug inválido');

Slug.parse('cadeira-ergonomica-2025');  // OK
Slug.parse('Cadeira Ergonômica');      // ZodError — maiúscula e espaço

// z.email com regex customizado — ajusta estriteza do padrão
z.email({ pattern: /^[^@\s]+@[^@\s]+\.[^@\s]+$/ });  // menos estrito

# Opções e mensagens customizadas

Todos os format schemas top-level aceitam um objeto de opções como primeiro argumento. Isso centraliza a customização — sem necessidade de .refine apenas para mudar a mensagem:

opcoes.ts
// mensagem customizada
z.email({ message: 'Informe um email válido' });
z.url(  { message: 'URL deve incluir https://' });
z.uuid( { message: 'ID de produto inválido'  });

  .min(1,   'Nome obrigatório')
  .max(200, 'Nome muito longo (máx. 200 caracteres)');

// combinar format com refine para regras adicionais
const UrlSegura = z
  .url({ message: 'URL inválida' })
  .refine(s => s.startsWith('https://'), 'Apenas HTTPS')
  .refine(s => !s.includes('localhost'), 'URLs localhost não permitidas em produção');

# Métodos de normalização

.trim(), .toLowerCase() e .toUpperCase() não apenas validam — transformam o valor. O output do schema é a string modificada, o que os torna transforms implícitos. Como result, z.input e z.output são tecnicamente iguais em tipo (string) mas o valor muda:

normalizacao.ts
// email normalizado — trim + lowercase antes de salvar no banco
const Email = z.email().trim().toLowerCase();
Email.parse('  Ana@Example.COM  ');  // 'ana@example.com'

// nome do produto — trim, comprimento após trim
const NomeProduto = z.string().trim().min(1).max(200);
NomeProduto.parse('  ');   // ZodError — após trim, string vazia falha em .min(1)
NomeProduto.parse(' Mesa '); // 'Mesa' — trim aplicado, valor normalizado

// código de produto — uppercase para padronizar
const Sku = z.string()
  .trim()
  .toUpperCase()
  .regex(/^[A-Z0-9-]{3,20}$/, 'SKU inválido');
Sku.parse(' cad-001 ');  // 'CAD-001' — normalizado
Armadilha
.trim() e .toLowerCase() modificam o valor antes de todos os checks subsequentes. Isso significa que z.string().trim().min(1) rejeita uma string de espaços (' ' vira '' após trim, que falha no min(1)) — comportamento desejado na maioria dos casos, mas que pode surpreender quando a lógica espera o valor original para depuração.

# z.number: catálogo de restrições

Todos os métodos de restrição de z.number são encadeáveis. O tipo inferido é sempre number — as restrições vivem no schema, não no tipo TypeScript:

number-metodos.ts
import * as z from 'zod';

z.number().int();                     // apenas inteiros — rejeita 1.5
z.number().positive();                // > 0
z.number().nonnegative();             // >= 0
z.number().negative();                // < 0
z.number().nonpositive();             // <= 0

# NaN, Infinity e safe integers

z.number() aceita NaN e Infinity por padrão porque typeof NaN === 'number' em JavaScript — o schema verifica o tipo JS, não a validade matemática. O comportamento surpreende na primeira vez:

casos-especiais.ts
// comportamento padrão — três valores problemáticos passam
z.number().parse(NaN);        // OK — use .finite() para rejeitar
z.number().parse(Infinity);   // OK — use .finite() para rejeitar
z.number().parse(-Infinity);  // OK — use .finite() para rejeitar

// soluções por caso
z.number().finite();         // rejeita NaN e Infinity
z.number().int();            // rejeita NaN (Number.isInteger(NaN) === false)
z.number().min(0).max(100); // rejeita Infinity implicitamente

// .safe() — garante precisão de representação em float64
// equivale a .min(Number.MIN_SAFE_INTEGER).max(Number.MAX_SAFE_INTEGER)
// 2^53 - 1 = 9_007_199_254_740_991
z.number().int().safe();

// IDs do PostgreSQL — limites por tipo de coluna
const IdInt4  = z.number().int().min(1).max(2_147_483_647); // integer
const IdInt8  = z.number().int().positive().safe();            // bigint (dentro do safe range)
Armadilha
Em colunas numéricas vindas de JSON, NaN e Infinity raramente chegam — JSON.stringify(NaN) produz "null". O risco real é em cálculos internos: divisão por zero, parseInt de string não numérica, operações com undefined. Nesses casos, o NaN pode aparecer no objeto antes do parse. Use .finite() em campos numéricos que passam por cálculos.

# z.bigint

z.bigint() valida o tipo primitivo bigint do JavaScript. As mesmas restrições de z.number estão disponíveis, com a diferença que os argumentos de .min(), .max() e .multipleOf() devem ser literais bigint (sufixo n). O uso principal é em IDs de alta cardinalidade e cálculos monetários de alta precisão:

bigint.ts
// ID estilo snowflake — 64 bits, não cabe em number seguro
const IdSnowflake = z.bigint().positive();
IdSnowflake.parse(1234567890123456789n);           // OK
IdSnowflake.parse(BigInt('1234567890123456789')); // OK

// restrições (argumentos devem ser bigint literal com 'n')
z.bigint().min(0n).max(1_000_000n);
z.bigint().multipleOf(100n);  // múltiplos de 100

// em HTTP, bigint chega como string — não existe representação JSON nativa
// z.coerce.bigint() converte (Cap 15)
const BigintDeString = z.string().transform(s => BigInt(s));
// input: string → output: bigint

# z.date: datas como objetos

z.date() aceita exclusivamente objetos Date JavaScript válidos — não strings ISO, não timestamps numéricos. Os métodos .min() e .max() recebem instâncias de Date como limite:

date.ts
// z.date rejeita strings — mesmo que pareçam datas
z.date().parse(new Date('2025-01-15'));  // OK — objeto Date
z.date().parse('2025-01-15');            // ZodError — string, use z.coerce.date()
z.date().parse(new Date('invalido'));    // ZodError — Invalid Date

// .min e .max com objetos Date
const DataFutura = z.date().min(new Date(), 'Deve ser futura');
const DataPassada = z.date().max(new Date(), 'Deve ser passada');

// data de nascimento — usuário com ao menos 18 anos
const hoje   = new Date();
const limite = new Date(
  hoje.getFullYear() - 18,
  hoje.getMonth(),
  hoje.getDate()
);
const DataNascimento = z.date().max(limite, 'Mínimo 18 anos');

// range para reservas — hoje até 365 dias à frente
const anoMs = 365 * 24 * 60 * 60 * 1000;
const DataReserva = z.date()
  .min(new Date(), 'Não pode ser no passado')
  .max(new Date(Date.now() + anoMs), 'Máximo 1 ano à frente');

# z.date vs z.iso.*

A escolha entre z.date() e z.iso.datetime() depende de onde a data vive. Em HTTP, datas chegam como strings — z.iso.* é o validador natural. Em lógica interna e DB queries, trabalhar com objetos Date é mais ergonômico. O padrão recomendado é validar na fronteira como string ISO e converter para Date no ponto de uso:

date-vs-iso.ts
// z.iso.datetime — para fronteiras HTTP (string → validada → string)
const CriarEvento = z.object({
  nome:      z.string().min(1),
  inicio:    z.iso.datetime(),   // valida o formato ISO 8601
  fim:       z.iso.datetime(),
});
const evento = CriarEvento.parse(await req.json());
// evento.inicio: string — o tipo é string, não Date

// z.date — para lógica interna onde Date é necessário
const inicio = new Date(evento.inicio);  // converte no ponto de uso
const fim    = new Date(evento.fim);

// .refine cross-field após converter para Date
const CriarEventoV2 = CriarEvento.refine(
  d => new Date(d.inicio) < new Date(d.fim),
  { message: 'Início deve ser antes do fim', path: ['fim'] }
);

// transform para converter ISO string para Date no schema
const DataDeISO = z.iso.datetime().transform(s => new Date(s));
// input: string ISO → output: Date
Boa prática
Use z.iso.datetime() nos schemas de entrada de rotas HTTP — valida o formato sem forçar conversão. Converta para Date com new Date(s) na camada de serviço onde a data é usada. Isso separa a responsabilidade de validação da de representação, e mantém os schemas de rota simples e serializáveis.

Capítulo 13

Erros: ZodError, issues, format e maps

Erros não são exceções acidentais — são a outra metade do contrato do schema. Para cada input que falha, Zod produz um ZodError com estrutura previsível: um array de ZodIssue, cada um com código discriminador, caminho no objeto, mensagem e dados específicos do tipo de falha. Este capítulo cobre a estrutura do erro, a escolha entre .parse (exceção) e .safeParse (Result discriminado), as APIs .format() e .flatten() para converter issues em formatos diferentes, a customização de mensagens por schema e via error maps, a internacionalização do Zod 4, e o padrão idiomático de tratamento de erros em rotas HTTP.

# .parse vs .safeParse

Os dois métodos validam de forma idêntica. A diferença é o canal de saída: .parse lança um ZodError em caso de falha, .safeParse devolve um discriminated union { success: true; data } | { success: false; error }. A escolha depende do estilo de código — em handlers HTTP, .safeParse evita try/catch; em pipelines internos onde falhas são raras, .parse deixa o caminho feliz mais legível:

parse-vs-safe.ts
import * as z from 'zod';

const Usuario = z.object({
  email: z.email(),
  nome:  z.string().min(1),
});

// .parse — lança ZodError em caso de falha
try {
  const u = Usuario.parse({ email: 'invalid', nome: '' });
  // u: { email: string; nome: string }
} catch (err) {
  if (err instanceof z.ZodError) {
    console.error(err.issues);
  }
}

// .safeParse — Result discriminado, nunca lança
const res = Usuario.safeParse({ email: 'invalid', nome: '' });
if (res.success) {
  // res.data: { email: string; nome: string }
  return res.data;
} else {
  // res.error: ZodError
  return responder400(res.error);
}

// versões assíncronas (Cap 17) — para schemas com .refine async
await Usuario.parseAsync(...);
await Usuario.safeParseAsync(...);
Boa prática
Em handlers HTTP, prefira .safeParse — o discriminated union casa naturalmente com a estrutura success branch / error branch de uma resposta. Em código interno onde inputs vêm do próprio sistema (config carregada uma vez, transformações de DTO), prefira .parse — uma exceção não tratada serve como contrato de "isso nunca deveria falhar".

# ZodError e o array de issues

Cada falha de validação vira um ZodIssue dentro do array error.issues. Um único parse pode produzir múltiplos issues — todos os erros de campos do objeto, todos os refines que falharam, todos os elementos inválidos de um array. A estrutura de cada issue é estável e discriminada por code:

issues-estrutura.ts
const res = Usuario.safeParse({ email: 42, nome: '' });

if (!res.success) {
  res.error.issues;
  // [
  //   {
  //     code:     'invalid_type',
  //     expected: 'string',
  //     received: 'number',
  //     path:     ['email'],
  //     message:  'Expected string, received number',
  //   },
  //   {
  //     code:      'too_small',
  //     minimum:   1,
  //     type:      'string',
  //     inclusive: true,
  //     path:      ['nome'],
  //     message:   'String must contain at least 1 character(s)',
  //   },
  // ]

  // caminhar pelos issues e formatar como string
  for (const issue of res.error.issues) {
    console.error(`[${issue.path.join('.')}] ${issue.message}`);
  }
  // [email] Expected string, received number
  // [nome]  String must contain at least 1 character(s)
}
Zod 4
Em Zod 3, error.errors e error.issues eram ambos aceitos. Em Zod 4, error.issues é a forma canônica. error.errors ainda funciona mas está deprecated. Toda análise nova deve usar .issues.

# ZodIssueCode: discriminar e tratar

O campo code de cada issue identifica o tipo da falha. Os códigos são strings literais — você pode usar switch sobre eles para tratar cada categoria com lógica específica e tirar proveito do narrowing TypeScript para acessar campos específicos do código:

issue-codes.ts
// principais ZodIssueCode
//   'invalid_type'        — tipo errado (string esperada, number recebido)
//   'invalid_literal'     — z.literal() não bate
//   'invalid_enum_value'  — valor fora do enum
//   'invalid_union'       — nenhum branch de z.union passou
//   'invalid_string'      — formato falhou (email, url, uuid, regex)
//   'too_small'           — .min() falhou (string, array, number, date)
//   'too_big'             — .max() falhou
//   'not_multiple_of'     — .multipleOf() falhou
//   'not_finite'          — .finite() falhou (NaN ou Infinity)
//   'unrecognized_keys'   — .strict() recebeu chaves extras
//   'custom'              — .refine() ou .superRefine()

// switch com narrowing: cada case expõe campos específicos do código
for (const issue of res.error.issues) {
  switch (issue.code) {
    case 'invalid_type':
      // issue.expected, issue.received disponíveis aqui
      console.log(`Tipo errado: esperado ${issue.expected}, recebido ${issue.received}`);
      break;
    case 'too_small':
      // issue.minimum, issue.type, issue.inclusive disponíveis
      console.log(`Muito pequeno: mínimo ${issue.minimum}`);
      break;
    case 'invalid_string':
      // issue.validation disponível: 'email', 'url', 'regex', etc
      console.log(`Formato inválido: ${issue.validation}`);
      break;
    case 'custom':
      // só a mensagem do .refine ou ctx.addIssue
      console.log(issue.message);
      break;
    default:
      console.log(issue.message);
  }
}

# .format() — árvore aninhada

Para objetos com estrutura profunda, iterar manualmente pelo array de issues e remontar a hierarquia é repetitivo. .format() faz esse trabalho — devolve uma estrutura aninhada que espelha o objeto validado, com a propriedade _errors contendo as mensagens em cada nível:

format.ts
const SignUp = z.object({
  email:    z.email(),
  endereco: z.object({
    rua:    z.string().min(1),
    numero: z.number().int().positive(),
  }),
});

const res = SignUp.safeParse({
  email: 'invalid',
  endereco: { rua: '', numero: -1 },
});

if (!res.success) {
  const tree = res.error.format();
  // {
  //   _errors: [],
  //   email:    { _errors: ['Invalid email'] },
  //   endereco: {
  //     _errors: [],
  //     rua:    { _errors: ['String must contain at least 1 character(s)'] },
  //     numero: { _errors: ['Number must be greater than 0'] },
  //   },
  // }

  // acesso direto via optional chaining
  tree.email?._errors;             // ['Invalid email']
  tree.endereco?.rua?._errors;     // ['String must contain ...']
  tree.endereco?.numero?._errors;  // ['Number must be ...']
}

# .flatten() — formato plano para formulários

.flatten() produz uma estrutura plana com dois campos: formErrors (erros no nível raiz do objeto, tipicamente vindos de .refine no objeto inteiro) e fieldErrors (mapa nome do campo → array de mensagens). É o formato natural para bibliotecas de formulário e UIs simples:

flatten.ts
const SignUpForm = z.object({
  email:       z.email('Email inválido'),
  senha:       z.string().min(8, 'Mínimo 8 caracteres'),
  confirmacao: z.string(),
}).refine(d => d.senha === d.confirmacao, {
  message: 'Senhas não conferem',
  path: ['confirmacao'],
});

const res = SignUpForm.safeParse({
  email: 'inv', senha: 'curta', confirmacao: 'diferente',
});

if (!res.success) {
  const flat = res.error.flatten();
  // {
  //   formErrors: [],  ← erros no objeto raiz (refine sem path)
  //   fieldErrors: {
  //     email:       ['Email inválido'],
  //     senha:       ['Mínimo 8 caracteres'],
  //     confirmacao: ['Senhas não conferem'],
  //   },
  // }

  flat.fieldErrors.email;  // ['Email inválido']
}
Armadilha
.flatten() é shallow — funciona apenas para objetos de um único nível. Para estruturas aninhadas (endereco.rua), os erros do nível interno são perdidos em fieldErrors. Use .format() para hierarquias profundas, ou itere sobre .issues diretamente e remonte conforme a necessidade da UI.

# Mensagens customizadas

Mensagens podem ser definidas em três níveis: como segundo argumento de cada check, como propriedade message de um objeto de opções, e como mensagem global do schema base via opções:

mensagens.ts
// 1. string como segundo argumento — atalho mais comum
z.string().min(1, 'Nome obrigatório');
z.number().positive('Deve ser positivo');
z.email('Email inválido');

// 2. objeto com message — quando precisa de mais opções juntas
z.string().max(200, { message: 'Máximo 200 caracteres' });

// 3. mensagem no schema base (Zod 4 unifica required/invalid_type)
z.string({ error: 'Esperava texto' });
z.number({ error: 'Esperava número' });

// 4. função para mensagem dinâmica
z.number({
  error: (iss) => iss.code === 'invalid_type'
    ? `Esperava número, recebi ${iss.received}`
    : undefined,
});
Zod 4
Em Zod 3, eram duas opções separadas — required_error (campo ausente) e invalid_type_error (tipo errado). Em Zod 4, ambas se unificaram em error, que aceita string estática ou função que recebe o issue e retorna a mensagem. Migrar é direto: { required_error: 'X' } e { invalid_type_error: 'X' } viram { error: 'X' }.

# Error maps e internacionalização

Quando o mesmo mapeamento de mensagens precisa ser aplicado em vários schemas, mensagens inline ficam repetitivas. Um error map é uma função que recebe o issue e devolve a mensagem — pode ser aplicada por schema, por chamada de parse ou globalmente. Zod 4 também publica pacotes de locale prontos:

error-maps.ts
// error map em PT-BR — função que mapeia issue → { message }
const ptBrErrorMap = (iss: z.$ZodRawIssue) => {
  switch (iss.code) {
    case 'invalid_type':
      return { message: `Esperava ${iss.expected}, recebi ${iss.received}` };
    case 'too_small':
      return { message: `Mínimo: ${iss.minimum}` };
    case 'too_big':
      return { message: `Máximo: ${iss.maximum}` };
    case 'invalid_string':
      if (iss.validation === 'email') return { message: 'Email inválido' };
      return { message: `Formato inválido` };
    default:
      return { message: 'Valor inválido' };
  }
};

// aplicar globalmente — afeta todos os schemas a partir daqui
z.config({ customError: ptBrErrorMap });

// aplicar apenas em um schema
const Email = z.email({ error: ptBrErrorMap });

// aplicar apenas em um parse específico
Usuario.safeParse(input, { error: ptBrErrorMap });

// Zod 4 inclui locales prontos via subpath 'zod/locales'

# Caso real: rota HTTP com tratamento estruturado

O padrão idiomático em uma rota HTTP combina .safeParse para evitar try/catch, mensagens customizadas inline para erros específicos do domínio, e .flatten() para devolver erros num formato consumível pelo frontend:

rota-criar-usuario.ts
import { Hono } from 'hono';
import * as z from 'zod';
import { ptBR } from 'zod/locales';

z.config(ptBR());  // erros padrão em PT-BR

const CriarUsuario = z.object({
  email: z.email('Email com formato inválido'),
  nome:  z.string().min(1, 'Nome obrigatório').max(200),
  senha: z.string().min(8, 'Senha precisa ao menos 8 caracteres'),
});

const app = new Hono();

app.post('/users', async (c) => {
  const json = await c.req.json();
  const res = CriarUsuario.safeParse(json);

  if (!res.success) {
    // resposta estruturada — frontend mapeia campos para inputs
    return c.json({
      erro:    'validacao',
      campos:  res.error.flatten().fieldErrors,
      globais: res.error.flatten().formErrors,
    }, 400);
  }

  // res.data: CriarUsuario — tipo seguro daqui em diante
  const usuario = await criarUsuarioNoBanco(res.data);
  return c.json(usuario, 201);
});
Performance & custo
A criação de ZodError e o cálculo das mensagens só acontece quando há falha — o caminho feliz não paga pelo formato dos erros. .format() e .flatten() rodam em O(N) sobre o array de issues, mas N tende a ser pequeno na prática (poucos campos errados por requisição). Para o hot path (rotas chamadas milhares de vezes/segundo) com taxa de erro baixa, o custo é desprezível. Em endpoints com alta taxa de erro (importação em lote, validação de CSV), considere coletar issues em estruturas próprias antes de formatar para resposta.

Capítulo 14

Opcionais, defaults e catch

Nem todo campo de um schema precisa de um valor obrigatório e não-nulo. Zod oferece seis modificadores que expressam os diferentes graus de ausência: .optional() aceita undefined, .nullable() aceita null, .nullish() aceita os dois. Quando o campo pode estar ausente mas o output deve ser preenchido, .default() fornece o valor de substituição. Quando qualquer falha deve ter um fallback, .catch() cobre além do undefined. .readonly() completa o grupo marcando o output como imutável no TypeScript. A distinção entre eles determina os tipos de entrada e saída do schema — especialmente o que z.input e z.output produzem.

# .optional, .nullable, .nullish

Os três modificadores de ausência controlam qual combinação de undefined e null o schema aceita. Cada um infere um tipo diferente:

ausencia.ts
import * as z from 'zod';

// .optional() — aceita undefined, campo pode estar ausente
const Opcl = z.string().optional();
// type: string | undefined
Opcl.parse('Ana');      // 'Ana'
Opcl.parse(undefined); // undefined
Opcl.parse(null);      // ZodError — null não é undefined

// .nullable() — aceita null, campo deve estar presente
const Nullbl = z.string().nullable();
// type: string | null
Nullbl.parse('Ana');      // 'Ana'
Nullbl.parse(null);       // null
Nullbl.parse(undefined);  // ZodError — undefined não é string | null

// .nullish() — aceita null E undefined (atalho para .nullable().optional())
const Nullsh = z.string().nullish();
// type: string | null | undefined
Nullsh.parse('Ana');      // 'Ana'
Nullsh.parse(null);       // null
Nullsh.parse(undefined);  // undefined

// campo parent_id da tabela categories (Vol XI) — id ou null
const Categoria = z.object({
  id:        z.number().int().positive(),
  nome:      z.string().min(1),
  parent_id: z.number().int().positive().nullable(), // null = raiz
});
Observação
Em banco de dados, colunas que aceitam NULL mapeiam para .nullable() no schema Zod — o campo existe no registro mas seu valor é nulo. Campos opcionais em requisições HTTP (que o cliente pode omitir) mapeiam para .optional(). Se o campo pode ser omitido E ser nulo, use .nullish() — comum em campos de update (PATCH) onde ausente significa "não alterar" e null significa "apagar o valor".

# .default: valor padrão quando ausente

.default(valor) substitui undefined pelo valor fornecido antes da validação do schema interno. O input passa a ser opcional, mas o output nunca é undefined — essa divergência é exatamente o que z.input vs z.output captura:

default.ts
const Ativo = z.boolean().default(true);

Ativo.parse(false);     // false
Ativo.parse(undefined); // true  (default aplicado)
Ativo.parse(null);      // ZodError — null não aciona o default

// .default com função — novo valor a cada parse (evita mutação compartilhada)
const CriadoEm = z.string().default(() => new Date().toISOString());

// campos da tabela products com defaults (Vol XI)
const CriarProduto = z.object({
  nome:     z.string().min(1),
  preco:    z.number().positive(),
  ativo:    z.boolean().default(true),
  estoque:  z.number().int().nonnegative().default(0),
  metadata: z.record(z.string(), z.unknown()).default({}),
});

CriarProduto.parse({ nome: 'Mesa', preco: 350 });
// { nome: 'Mesa', preco: 350, ativo: true, estoque: 0, metadata: {} }

# A distinção input/output com .default

O campo com .default() pode estar ausente no input, mas nunca no output. O tipo muda conforme a perspectiva:

input-output-default.ts
const Schema = z.object({
  id:    z.number().int().positive(),
  ativo: z.boolean().default(true),
});

type Input  = z.input<typeof Schema>;
// { id: number; ativo?: boolean | undefined }  ← ativo opcional no input

type Output = z.infer<typeof Schema>;
// { id: number; ativo: boolean }              ← ativo obrigatório no output

Schema.parse({ id: 1 });
// { id: 1, ativo: true }  — default preenchido

Schema.parse({ id: 1, ativo: false });
// { id: 1, ativo: false }  — valor explícito respeitado
Boa prática
Use z.input<typeof Schema> para tipar o parâmetro de uma função que recebe dados antes do parse, e z.infer<typeof Schema> (= z.output) para o que entra no banco ou é devolvido pela rota. Essa distinção evita erros onde o chamador passa um objeto com campos ausentes esperando que o Zod preencha os defaults, mas o TypeScript reclama de campos obrigatórios.

# .catch: fallback para qualquer falha

.catch(valor) difere de .default() em escopo: enquanto .default() age apenas quando o input é undefined, .catch() age quando qualquer validação falha — tipo errado, tamanho fora do intervalo, regex não bateu. O valor de fallback é retornado silenciosamente:

catch.ts
const Pagina = z.number().int().positive().catch(1);

Pagina.parse(5);           // 5  — OK, nenhum fallback
Pagina.parse(undefined);   // 1  — undefined não é number
Pagina.parse('abc');       // 1  — string não é number
Pagina.parse(-1);           // 1  — positive() falhou
Pagina.parse(null);         // 1  — null não é number

// padrão idiomático: parâmetros de query string imprevisíveis
// o cliente pode enviar valores inválidos — o fallback garante o comportamento
const QueryProdutos = z.object({
  pagina:   z.coerce.number().int().positive().catch(1),
  limite:   z.coerce.number().int().min(1).max(100).catch(20),
  ordenar:  z.enum(['nome', 'preco', 'criado_em']).catch('criado_em'),
});
Armadilha
.catch() silencia erros — qualquer input inválido passa sem aviso. Em schemas de input de usuário ou de corpo de requisição, isso pode mascarar bugs. Reserve .catch() para parâmetros onde um fallback sensato é preferível ao erro (query strings de paginação, preferências de UI, filtros opcionais) e nunca use em campos críticos como IDs, emails ou valores monetários.

# .readonly

.readonly() não afeta a validação em runtime — o valor é aceito como sempre. O efeito é só de tipo: arrays e objetos no output ficam marcados com o modificador readonly do TypeScript, impedindo mutação em tempo de compilação:

readonly.ts
// array readonly — push/pop/splice bloqueados em compilação
const Permissoes = z.array(z.string()).readonly();
type Permissoes = z.infer<typeof Permissoes>;
// type: readonly string[]

const perms = Permissoes.parse(['read', 'write']);
// perms.push('delete');  // ERRO de compilação — array é readonly

// objeto readonly — propriedades não podem ser reatribuídas
const Config = z.object({
  host: z.string(),
  port: z.number().int(),
}).readonly();
type Config = z.infer<typeof Config>;
// type: Readonly<{ host: string; port: number }>

const cfg = Config.parse({ host: 'localhost', port: 3000 });
// cfg.port = 8080;  // ERRO de compilação

# Composição nos schemas do e-commerce

Um schema de produto real usa os modificadores em combinação — campos obrigatórios, nullable de banco, opcionais de API, defaults de negócio:

produto-completo.ts
const Produto = z.object({
  // obrigatórios — sem modificador de ausência
  id:    z.number().int().positive(),
  nome:  z.string().min(1),
  preco: z.number().positive().finite(),

  // .default — obrigatório no output, opcional no input
  ativo:   z.boolean().default(true),
  estoque: z.number().int().nonnegative().default(0),

  // .nullable — NULL do banco (coluna nullable)
  categoria_id:  z.number().int().positive().nullable(),

  // .optional — campo pode estar ausente na requisição
  descricao:     z.string().max(2000).optional(),

  // .nullish — ausente (não enviado) OU null (apagar o valor) em PATCH
  desconto:      z.number().min(0).max(100).nullish(),
});

// schema de update — todos campos (exceto id) podem estar ausentes
const AtualizarProduto = Produto.omit({ id: true }).partial();
type AtualizarProduto = z.infer<typeof AtualizarProduto>;

Coerção e codecs

Fronteiras como query strings, process.env e form data entregam tudo como string — mesmo campos que o código trata como número, booleano ou data. z.coerce é o namespace que aplica o construtor JavaScript correspondente antes de validar, convertendo o tipo automaticamente. Para casos onde a conversão precisa ser bidirecional — encode para serializar, decode para deserializar — Zod 4 introduziu z.codec, que formaliza o par encode/decode num único artefato em vez de dois schemas com transforms separados.

# z.coerce — coerção automática

Cada schema do namespace z.coerce envolve o schema base em uma etapa de conversão que roda antes da validação. Não é magia: é literalmente o construtor JavaScript aplicado ao input antes do parse:

coerce-overview.ts
import * as z from 'zod';

// cada coerce.X equivale ao construtor correspondente + validação
z.coerce.string();   // String(input)    → valida como string
z.coerce.number();   // Number(input)    → valida como number
z.coerce.boolean();  // Boolean(input)   → valida como boolean
z.coerce.date();     // new Date(input)  → valida como Date
z.coerce.bigint();   // BigInt(input)    → valida como bigint

// caso principal: query string onde tudo chega como string
const QuerySchema = z.object({
  pagina:   z.coerce.number().int().positive().default(1),
  limite:   z.coerce.number().int().min(1).max(100).default(20),
  ativo:    z.coerce.boolean().optional(),
});

QuerySchema.parse({ pagina: '3', limite: '50' });
// { pagina: 3, limite: 50, ativo: undefined }  — strings convertidas para number

# z.coerce.number — e a armadilha do NaN

Number(input) retorna NaN para strings não numéricas — e z.coerce.number() passa esse NaN adiante para o schema base. Como z.number() aceita NaN por padrão (Cap 3), uma string inválida passa silenciosamente como NaN a menos que .finite() seja encadeado:

coerce-number.ts
// coerções esperadas
z.coerce.number().parse('42');     // 42
z.coerce.number().parse('3.14');   // 3.14
z.coerce.number().parse(true);     // 1  (Number(true) === 1)
z.coerce.number().parse(false);    // 0
z.coerce.number().parse('');       // 0  (Number('') === 0)

// ARMADILHA: string inválida → NaN → z.number() aceita por padrão
z.coerce.number().parse('abc');    // NaN — sem erro!

// solução: .finite() após coerce rejeita NaN e Infinity
z.coerce.number().finite().parse('abc');   // ZodError
z.coerce.number().finite().parse('42');    // 42

// paginação com fallback seguro
const Paginacao = z.object({
  pagina:     z.coerce.number().int().positive().catch(1),
  por_pagina: z.coerce.number().int().min(1).max(100).catch(20),
});
Armadilha
Sempre encadeie .finite() ou .int() após z.coerce.number() quando strings inválidas devem rejeitar. Sem ele, 'abc' passa como NaN e o dado vai para o banco ou para a lógica de negócio silenciosamente corrompido. Para query strings onde inválido deve cair no default, combine com .catch(n) após o .finite().

# z.coerce.boolean — a armadilha da string

Boolean(input) segue a semântica de truthy/falsy do JavaScript — qualquer string não-vazia é true, incluindo "false" e "0". Para checkboxes HTML e parâmetros que enviam literalmente a string "true" ou "false", o mapeamento explícito é mais seguro:

coerce-boolean.ts
// comportamentos esperados
z.coerce.boolean().parse(true);    // true
z.coerce.boolean().parse(false);   // false
z.coerce.boolean().parse(1);       // true
z.coerce.boolean().parse(0);       // false
z.coerce.boolean().parse('');      // false  (string vazia)

// SURPRESA: strings não-vazias são sempre true
z.coerce.boolean().parse('false'); // true  ← armadilha!
z.coerce.boolean().parse('0');     // true  ← armadilha!
z.coerce.boolean().parse('no');    // true  ← armadilha!

// alternativa segura para query string de boolean
const BoolParam = z.enum(['true', 'false', '1', '0'])
  .transform(s => s === 'true' || s === '1')
  .optional();

// alternativa segura para checkbox HTML (envia 'on' quando marcado, ausente quando não)
const Checkbox = z.string().optional().transform(s => s === 'on');

# z.coerce.date e z.coerce.bigint

z.coerce.date() resolve o caso mais comum de conversão temporal: strings ISO chegando de HTTP que precisam virar objetos Date para lógica interna. new Date('data-invalida') produz Invalid Date — e z.coerce.date() rejeita esses:

coerce-date-bigint.ts
// z.coerce.date — new Date(input) antes de validar
z.coerce.date().parse('2025-01-15');             // Date object
z.coerce.date().parse('2025-01-15T10:30:00Z');     // Date object
z.coerce.date().parse(1705276800000);             // Date do timestamp Unix
z.coerce.date().parse(new Date());               // passthrough — já é Date
z.coerce.date().parse('invalido');               // ZodError — Invalid Date

// com restrições
const DataFutura = z.coerce.date().min(new Date(), 'Deve ser futura');

// z.coerce.bigint — BigInt(input)
z.coerce.bigint().parse('9007199254740992');   // BigInt de string
z.coerce.bigint().parse(42);                  // BigInt(42)
// BigInt('abc') lança RangeError — z.coerce.bigint() converte para ZodError

// variáveis de ambiente: DATABASE_URL, PORT, NODE_ENV
const Env = z.object({
  DATABASE_URL: z.url(),
  PORT:         z.coerce.number().int().positive().default(3000),
  NODE_ENV:     z.enum(['development', 'production', 'test']),
}).parse(process.env);

# z.codec — encoder/decoder bidirecional

Transformações com .transform().pipe() são unidirecionais: parse converte de um formato para outro, mas não há como serializar de volta automaticamente. z.codec (novo em Zod 4) formaliza o par decode/encode num único objeto — para cada tipo de dado que atravessa uma fronteira de serialização, o codec define as duas direções:

codec.ts
import * as z from 'zod';

// sem codec: duas transformações separadas, sem ligação formal entre si
const decodeDate = z.string().transform(s => new Date(s));
const encodeDate = z.date().transform(d => d.toISOString());

// com z.codec: decode e encode como par formal
const DateCodec = z.codec({
  decode: z.string().transform(s => new Date(s)),  // string → Date
  encode: z.date().transform(d => d.toISOString()), // Date → string ISO
});

DateCodec.decode.parse('2025-01-15T00:00:00Z');   // Date object
DateCodec.encode.parse(new Date('2025-01-15'));     // '2025-01-15T00:00:00.000Z'

// codec de JSON: qualquer valor ↔ string JSON
const JsonCodec = z.codec({
  decode: z.string().transform(s => JSON.parse(s)),
  encode: z.unknown().transform(v => JSON.stringify(v)),
});
Zod 4
z.codec é nova API do Zod 4, voltada para bibliotecas e camadas de persistência que precisam serializar e deserializar o mesmo tipo de forma consistente. O caso de uso principal são ORMs customizados, adaptadores de cache e contratos de API onde o mesmo schema define tanto como um valor é recebido quanto como é enviado de volta. A API pode ter evoluído na versão atual — confira zod.dev para a forma canônica.

Capítulo 16

Schemas recursivos

Algumas estruturas de dados se referenciam: uma categoria que tem subcategorias, um comentário que tem respostas, um sistema de arquivos com pastas e arquivos aninhados. O schema precisa expressar essa referência circular — e tanto Zod quanto TypeScript têm restrições que tornam isso não-trivial. O TypeScript exige que o tipo já esteja declarado para ser referenciado; o Zod exige o mesmo para o schema. A solução combina três técnicas: z.lazy() para adiar a avaliação do schema, declaração explícita do tipo TS antes do schema (o type hole), e a anotação z.ZodType<T> que conecta os dois lados. Este capítulo cobre a árvore de categorias do Vol XI como caso canônico, a recursão mútua entre dois schemas, e a proteção contra ciclos infinitos.

# O problema da auto-referência

Tentar declarar um schema que se referencia diretamente falha porque o identificador ainda não existe durante a expressão de definição. A mesma restrição vale para o tipo TypeScript em alguns casos:

o-problema.ts
import * as z from 'zod';

// NÃO FUNCIONA — Comentario não existe ainda dentro da própria expressão
const Comentario = z.object({
  id:        z.number().int(),
  texto:     z.string(),
  respostas: z.array(Comentario), // ReferenceError: Comentario não definido
});

// O TypeScript permite tipos recursivos via interface ou type direto:
interface Comentario {
  id:        number;
  texto:     string;
  respostas: Comentario[];  // OK — tipo se autorreferencia
}

// Mas o SCHEMA precisa do valor (não só do tipo) em runtime — daí z.lazy()

# z.lazy + ZodType: o padrão completo

A solução tem três passos. Primeiro, declare o tipo TypeScript usando interface ou type — TS aceita tipos auto-referenciados naturalmente. Segundo, declare o schema com a anotação : z.ZodType<T> — isso informa ao compilador que esse identificador é um schema do tipo declarado, mesmo que ele ainda esteja sendo construído. Terceiro, envolva a referência recursiva em z.lazy(() => ...) — o callback adia a avaliação para o momento do parse, quando o identificador já existe:

lazy-pattern.ts
// 1. tipo TypeScript primeiro
type Comentario = {
  id:        number;
  texto:     string;
  respostas: Comentario[];
};

// 2. schema anotado com z.ZodType<T>, 3. lazy quebra a referência circular
const Comentario: z.ZodType<Comentario> = z.object({
  id:        z.number().int().positive(),
  texto:     z.string().min(1),
  respostas: z.lazy(() => z.array(Comentario)),
});

// agora pode ser usado normalmente
const c = Comentario.parse({
  id: 1,
  texto: 'discussão raiz',
  respostas: [
    { id: 2, texto: 'concordo', respostas: [] },
    { id: 3, texto: 'discordo', respostas: [
      { id: 4, texto: 'por quê?', respostas: [] },
    ] },
  ],
});
Observação
z.ZodType<T> é o tipo genérico raiz de todos os schemas Zod. Anotar a constante com ele desativa parte da inferência automática — o tipo passa a ser o que você declarou em T, não o que o Zod inferiria. Isso é necessário porque a inferência depende do schema estar completamente avaliado, e o ciclo recursivo torna isso impossível. O custo: você precisa manter o type TS e o schema sincronizados manualmente.

# Árvore de categorias: o caso canônico

A tabela categories do Vol XI tem uma coluna parent_id que aponta para a própria tabela — relacionamento self-FK. A representação plana (linhas com FK) é o que vive no banco; a representação em árvore (filhos aninhados) é o que normalmente sai pela API. Para essa segunda forma, um schema recursivo expressa exatamente a estrutura:

categoria-arvore.ts
// tipo recursivo da árvore — parent_id mantido para preservar a FK original
type CategoriaArvore = {
  id:        number;
  nome:      string;
  parent_id: number | null;
  filhos:    CategoriaArvore[];
};

const CategoriaArvore: z.ZodType<CategoriaArvore> = z.object({
  id:        z.number().int().positive(),
  nome:      z.string().min(1),
  parent_id: z.number().int().positive().nullable(),
  filhos:    z.lazy(() => z.array(CategoriaArvore)),
});

// árvore resultante de uma query recursiva (WITH RECURSIVE no Postgres, Vol X)
const arvore = CategoriaArvore.parse({
  id: 1,
  nome: 'Móveis',
  parent_id: null,
  filhos: [
    {
      id: 2,
      nome: 'Cadeiras',
      parent_id: 1,
      filhos: [
        { id: 5, nome: 'Ergonômicas', parent_id: 2, filhos: [] },
        { id: 6, nome: 'Gamer',       parent_id: 2, filhos: [] },
      ],
    },
    { id: 3, nome: 'Mesas',  parent_id: 1, filhos: [] },
  ],
});

Branded types do Cap 4 compõem naturalmente com schemas recursivos. Em vez de id: number e parent_id: number | null intercambiáveis, marcar o ID com .brand garante que parent_id não pode ser confundido com um ID de outra tabela em compilação:

categoria-branded.ts
// brand torna o ID nominalmente distinto de outros ids numéricos
const CategoriaId = z.number().int().positive().brand<'CategoriaId'>();
type CategoriaId = z.infer<typeof CategoriaId>;
// type CategoriaId = number & z.BRAND<'CategoriaId'>

type Categoria = {
  id:        CategoriaId;
  nome:      string;
  parent_id: CategoriaId | null;
  filhos:    Categoria[];
};

const Categoria: z.ZodType<Categoria> = z.object({
  id:        CategoriaId,
  nome:      z.string().min(1),
  parent_id: CategoriaId.nullable(),
  filhos:    z.lazy(() => z.array(Categoria)),
});

# Recursão mútua

Quando dois schemas se referenciam mutuamente (pasta contém arquivos e outras pastas; sistema de arquivos é o exemplo clássico), o padrão é o mesmo, aplicado em ambos os lados. Cada schema declara sua referência ao outro via z.lazy, e os dois tipos TS são declarados antes:

recursao-mutua.ts
// dois tipos que se referem mutuamente
type Pasta = {
  tipo:   'pasta';
  nome:   string;
  filhos: (Pasta | Arquivo)[];
};
type Arquivo = {
  tipo:    'arquivo';
  nome:    string;
  tamanho: number;
};

// modelar como discriminated union (Cap 7) — o discriminador é 'tipo'
type No = Pasta | Arquivo;

const No: z.ZodType<No> = z.discriminatedUnion('tipo', [
  z.object({
    tipo:   z.literal('pasta'),
    nome:   z.string(),
    filhos: z.lazy(() => z.array(No)),  // referência recursiva via union
  }),
  z.object({
    tipo:    z.literal('arquivo'),
    nome:    z.string(),
    tamanho: z.number().int().nonnegative(),
  }),
]);

const raiz = No.parse({
  tipo: 'pasta', nome: 'projeto',
  filhos: [
    { tipo: 'arquivo', nome: 'README.md', tamanho: 1024 },
    { tipo: 'pasta', nome: 'src', filhos: [
      { tipo: 'arquivo', nome: 'index.ts', tamanho: 2048 },
    ] },
  ],
});
Boa prática
Para recursão mútua, prefira discriminated union com um schema único em vez de dois schemas separados que se referenciam. Reduz boilerplate, dá narrowing automático no consumidor (Cap 7) e elimina a possibilidade de inconsistência entre os dois lados. O exemplo acima usa um único No com discriminador tipo, em vez de Pasta e Arquivo independentes referenciando uns aos outros.

# Ciclos infinitos e detecção

z.lazy não detecta ciclos automaticamente — se a estrutura validada contém referências circulares (um objeto que aparece dentro de si mesmo), o parser recurse infinitamente até estourar o stack. Em fronteiras HTTP isso raramente acontece porque JSON não suporta ciclos, mas em validação de objetos construídos em memória é um risco real:

ciclos.ts
// criando um ciclo manualmente
const ciclico: any = { id: 1, nome: 'raiz', filhos: [] };
ciclico.filhos.push(ciclico);  // referência circular: filho aponta para o pai

CategoriaArvore.parse(ciclico);
// stack overflow — Zod recurse até esgotar a pilha de chamadas

// proteção: refine que rastreia IDs visitados durante o parse
const CategoriaSemCiclo: z.ZodType<CategoriaArvore> = z.object({
  id:        z.number().int().positive(),
  nome:      z.string().min(1),
  parent_id: z.number().int().positive().nullable(),
  filhos:    z.lazy(() => z.array(CategoriaSemCiclo)),
}).refine(
  (raiz) => {
    const vistos = new Set<number>();
    function visitar(no: CategoriaArvore): boolean {
      if (vistos.has(no.id)) return false;
      vistos.add(no.id);
      return no.filhos.every(visitar);
    }
    return visitar(raiz);
  },
  { message: 'Estrutura contém ciclo' }
);
Performance & custo
Schemas recursivos têm custo linear no tamanho total da estrutura — cada nó é parseado uma vez. Para árvores muito profundas (centenas de níveis), o limite prático é o stack size do runtime, não o Zod. z.lazy em si tem overhead mínimo: o callback é uma função-fábrica memoizada. O caso onde a recursão fica cara é quando combinada com .refine que percorre a árvore toda novamente — como o exemplo de detecção de ciclos acima. Em validação de payloads de webhook ou snapshots, esse custo extra é aceitável; em hot paths, considere validar a estrutura sem o refine e fazer a checagem de ciclos só quando suspeita.

Validação assíncrona

Algumas validações não podem ser respondidas só com o input do schema — é preciso consultar o banco, chamar uma API externa, ler do sistema de arquivos. Para esses casos, .refine e .transform aceitam funções async; em troca, o parse inteiro passa a exigir parseAsync ou safeParseAsync. Este capítulo cobre a API assíncrona, o padrão de validação cruzada que consulta o banco (email único, produto existe, estoque disponível), e como evitar serialização desnecessária de queries com Promise.all.

# parseAsync e safeParseAsync

Schemas que não usam refinements ou transforms assíncronos continuam síncronos — .parse() e .safeParse() retornam imediatamente. No momento em que qualquer refinement ou transform na cadeia é async, todo o parse vira assíncrono. Chamar a versão síncrona em um schema async lança um erro de runtime:

parse-async.ts
import * as z from 'zod';

// schema sem async — parse síncrono é o normal
const Schema = z.object({ id: z.number() });
const u = Schema.parse({ id: 1 });   // retorno direto

// adicionar .refine async muda o jogo — toda a cadeia vira async
const SchemaAsync = z.object({
  email: z.email(),
}).refine(
  async (d) => await emailDisponivel(d.email),
  'Email já cadastrado'
);

// .parse() em schema async lança em runtime
SchemaAsync.parse({ email: 'a@b.com' });
// Error: Async refinement encountered during synchronous parse

// versões corretas: parseAsync / safeParseAsync
const ok  = await SchemaAsync.parseAsync({ email: 'a@b.com' });
const res = await SchemaAsync.safeParseAsync({ email: 'a@b.com' });

  // res.data: { email: string }
} else {
  // res.error: ZodError (mesmo formato do parse síncrono)

Armadilha
A propagação do async é viral: um único .refine assíncrono no fundo da árvore de schemas obriga todos os .parse a cima a virarem .parseAsync. Em codebases grandes, isso pode forçar refatoração de handlers que assumiam parse síncrono. Quando possível, prefira validar coisas assíncronas fora do schema (no service layer, após o parse síncrono garantir a estrutura) — só use refine async quando a regra realmente faz parte da validação do dado.

# .refine async: validação que consulta o banco

O caso mais comum de validação assíncrona é checar unicidade — email não cadastrado, slug não em uso, código não duplicado. A função recebe o valor já parseado e devolve uma Promise<boolean>:

refine-async.ts
import { db } from './db';
import { users, products } from './schema';
import { eq } from 'drizzle-orm';

// schema com refine async — email não pode existir
const CriarUsuario = z.object({
  email: z.email(),
  nome:  z.string().min(1),
}).refine(
  async (d) => {
    const existente = await db
      .select().from(users)
      .where(eq(users.email, d.email))
      .limit(1);
    return existente.length === 0;
  },
  { message: 'Email já cadastrado', path: ['email'] }
);

// uso em rota Hono
app.post('/users', async (c) => {
  const body = await c.req.json();
  const res  = await CriarUsuario.safeParseAsync(body);

  if (!res.success) {
    return c.json({ erros: res.error.flatten() }, 400);
  }

  // res.data — email garantidamente único + formato válido
  return c.json(await criar(res.data), 201);
});

# .transform async: enriquecer dados

.transform aceita função async com a mesma API de transform com falha (Cap 10): a função recebe (valor, ctx), pode chamar ctx.addIssue e retornar z.NEVER para abortar. Útil quando o input contém um identificador que precisa ser resolvido contra o banco antes de prosseguir:

transform-async.ts
// recebe product_id no input, hidrata com o produto completo no output
const ItemHidratado = z.object({
  product_id: z.number().int().positive(),
  quantidade: z.number().int().positive(),
}).transform(async (item, ctx) => {
  const produto = await db
    .select().from(products)
    .where(eq(products.id, item.product_id))
    .limit(1);

  if (produto.length === 0) {
    ctx.addIssue({
      code:    'custom',
      message: 'Produto não encontrado',
      path:    ['product_id'],
    });
    return z.NEVER;
  }

  return {
    ...item,
    produto:  produto[0],
    subtotal: produto[0].preco * item.quantidade,
  };
});

const item = await ItemHidratado.parseAsync({ product_id: 1, quantidade: 3 });
// item: { product_id, quantidade, produto: {...}, subtotal: number }

# Validação cruzada com superRefine async

Quando múltiplas regras dependentes do banco precisam ser reportadas juntas, .superRefine assíncrono é a ferramenta — todas as queries acontecem em sequência ou em paralelo, e cada falha vira um issue independente no array final:

super-refine-async.ts
const CriarPedido = z.object({
  user_id: z.number().int().positive(),
  itens:   z.array(z.object({
    product_id: z.number().int().positive(),
    quantidade: z.number().int().positive(),
  })).min(1),
}).superRefine(async (val, ctx) => {
  // regra 1: user existe
  const [user] = await db
    .select().from(users)
    .where(eq(users.id, val.user_id))
    .limit(1);

  if (!user) {
    ctx.addIssue({
      code: 'custom', message: 'Usuário inexistente', path: ['user_id'],
    });
  }

  // regra 2: cada item tem produto válido E estoque suficiente
  for (const [idx, item] of val.itens.entries()) {
    const [p] = await db
      .select().from(products)
      .where(eq(products.id, item.product_id))
      .limit(1);

    if (!p) {
      ctx.addIssue({
        code: 'custom',
        message: 'Produto inexistente',
        path: ['itens', idx, 'product_id'],
      });
    } else if (p.estoque < item.quantidade) {
      ctx.addIssue({
        code: 'custom',
        message: `Estoque insuficiente (disponível: ${p.estoque})`,
        path: ['itens', idx, 'quantidade'],
      });
    }
  }
});

# Performance: serialização e paralelismo

O exemplo anterior tem um problema escondido: as queries de produto rodam em série dentro do for. Para um pedido com 10 itens, isso significa 10 round-trips ao banco em sequência — latência alta sem necessidade. Quando as consultas são independentes, paralelize com Promise.all:

paralelismo.ts
// MAU: queries serializadas — latência total = soma de cada uma
for (const [idx, item] of val.itens.entries()) {
  const [p] = await db.select().from(products)
    .where(eq(products.id, item.product_id)).limit(1);
  // ... processa p
}

// BOM: queries em paralelo — latência total = a mais lenta
const resultados = await Promise.all(
  val.itens.map((item) =>
    db.select().from(products)
      .where(eq(products.id, item.product_id)).limit(1)
  )
);
resultados.forEach(([p], idx) => {
  if (!p) {
    ctx.addIssue({
      code: 'custom', message: 'Produto inexistente',
      path: ['itens', idx, 'product_id'],
    });
  }
});

// MELHOR ainda: uma única query com IN — 1 round-trip total
const ids = val.itens.map((i) => i.product_id);
const produtos = await db.select().from(products)
  .where(inArray(products.id, ids));
const mapa = new Map(produtos.map((p) => [p.id, p]));
Performance & custo
Refinamentos async pagam o custo de I/O completo a cada parse — em endpoints de alta frequência, isso pode dominar a latência total. Três otimizações em ordem crescente de impacto: (1) Promise.all para queries independentes — paraleliza sem mudar a lógica. (2) Uma única query com IN ou batch — reduz N round-trips a 1. (3) Considere se a validação async deveria estar no schema mesmo — checagens de "produto existe" muitas vezes são melhor feitas no service layer ou via foreign key do banco, deixando o schema apenas para validação estrutural.

Capítulo 18

drizzle-zod: uma fonte da verdade

O Capítulo 22 do Volume XI terminou apontando para este — com o exemplo de createInsertSchema que une o tipo do banco ao schema de validação em runtime. Sem essa ponte, a definição da tabela existe duas vezes: uma em pgTable (Drizzle), outra em z.object (Zod). Quando uma coluna é adicionada ou modificada, manter os dois lados em sincronia é trabalho manual e propenso a erro silencioso. drizzle-zod resolve isso gerando schemas Zod automaticamente a partir das definições Drizzle. Este capítulo cobre os três geradores (createSelectSchema, createInsertSchema, createUpdateSchema), o sistema de refinements por coluna para regras que o Drizzle não expressa, e o padrão CRUD completo que usa uma única fonte da verdade.

# O problema da duplicação

Sem drizzle-zod, a forma da tabela é declarada duas vezes — uma vez no schema Drizzle, outra no schema Zod. A duplicação introduz uma classe de bug particular: quando uma coluna é adicionada, modificada ou removida no Drizzle, o schema Zod fica desatualizado silenciosamente — o código continua compilando, o parse continua passando, mas o tipo de banco e o tipo de fronteira deixam de bater:

duplicacao.ts
// 1. tabela Drizzle (fonte da verdade no banco — Vol XI)
import { pgTable, serial, varchar, integer, boolean } from 'drizzle-orm/pg-core';

export const products = pgTable('products', {
  id:           serial('id').primaryKey(),
  nome:         varchar('nome', { length: 200 }).notNull(),
  preco:        integer('preco').notNull(),
  categoria_id: integer('categoria_id'),
  ativo:        boolean('ativo').default(true).notNull(),
});

// 2. schema Zod (escrito manualmente, repetindo a estrutura acima)
const Produto = z.object({
  id:           z.number().int().positive(),
  nome:         z.string().min(1).max(200),
  preco:        z.number().int(),
  categoria_id: z.number().int().nullable(),
  ativo:        z.boolean(),
});

// problema: adicionar coluna 'descricao' em products → esquecer de adicionar em Produto
// → o Zod aceita objetos sem descricao, o Drizzle exige (se notNull) — bug em runtime

# createSelectSchema

createSelectSchema(table) gera o schema Zod que descreve uma linha retornada por SELECT — todas as colunas presentes, cada uma com seu tipo derivado da declaração Drizzle. Colunas nullable viram .nullable(), colunas com tipos específicos (varchar, integer, timestamp) mapeiam para os primitivos Zod correspondentes:

select-schema.ts
import { createSelectSchema } from 'drizzle-zod';
import { products } from './schema';

export const ProdutoSelect = createSelectSchema(products);
export type ProdutoSelect = z.infer<typeof ProdutoSelect>;
// type ProdutoSelect = {
//   id:           number;
//   nome:         string;
//   preco:        number;
//   categoria_id: number | null;  ← coluna nullable do Drizzle
//   ativo:        boolean;
// }

// uso: validar a saída de uma query antes de retornar pela API
const produtos = await db.select().from(products);
const validos  = produtos.map((p) => ProdutoSelect.parse(p));
Boa prática
Em endpoints REST, use createSelectSchema para validar respostas antes de serializar para JSON. Isso garante que mudanças no schema do banco não vazem campos inesperados para clientes (uma nova coluna sensível adicionada em produção, por exemplo). O custo é pequeno; a garantia é robusta.

# createInsertSchema

createInsertSchema(table) produz o schema para o que entra num INSERT. A diferença em relação a createSelectSchema é tornar opcionais as colunas que o banco preenche automaticamente: serial primários, colunas com .default(), timestamps automáticos. O schema reflete exatamente o que o cliente precisa enviar:

insert-schema.ts
import { createInsertSchema } from 'drizzle-zod';

export const CriarProduto = createInsertSchema(products);
type CriarProduto = z.infer<typeof CriarProduto>;
// {
//   id?:           number;          ← serial, opcional
//   nome:          string;          ← notNull, obrigatório
//   preco:         number;          ← notNull, obrigatório
//   categoria_id?: number | null;   ← nullable, opcional
//   ativo?:        boolean;         ← .default(true), opcional
// }

// rota POST /products
app.post('/products', async (c) => {
  const body = await c.req.json();
  const res  = CriarProduto.safeParse(body);

  if (!res.success) {
    return c.json({ erros: res.error.flatten() }, 400);
  }

  // res.data tem o tipo certo para passar diretamente para db.insert().values()
  const [produto] = await db.insert(products).values(res.data).returning();
  return c.json(produto, 201);
});

# createUpdateSchema

createUpdateSchema(table) torna todos os campos opcionais — adequado para PATCH onde o cliente envia apenas o que mudou. Conceitualmente equivale a createInsertSchema(table).partial(), mas é mais direto e expressa a intenção:

update-schema.ts
import { createUpdateSchema } from 'drizzle-zod';

export const AtualizarProduto = createUpdateSchema(products);
type AtualizarProduto = z.infer<typeof AtualizarProduto>;
// todos os campos opcionais — equivale a .partial() sobre o insert

// rota PATCH /products/:id
app.patch('/products/:id', async (c) => {
  const id   = Number(c.req.param('id'));
  const body = await c.req.json();
  // id vem da URL, não do body — remover do schema de update
  const res  = AtualizarProduto.omit({ id: true }).safeParse(body);

  if (!res.success) {
    return c.json({ erros: res.error.flatten() }, 400);
  }

  const [produto] = await db
    .update(products).set(res.data).where(eq(products.id, id)).returning();
  return c.json(produto);
});

# Refinements por coluna

O schema gerado captura a estrutura, mas nem todas as regras de validação vivem no esquema do banco. email é uma coluna varchar — Drizzle não sabe que tem que ser email válido. preco é integer notNull — mas a regra "deve ser positivo" pode estar como check constraint no banco e não chega ao schema gerado. O segundo argumento dos geradores recebe um objeto de refinements por coluna:

refinements.ts
import { createInsertSchema } from 'drizzle-zod';
import { users, products } from './schema';

// refine de usuário — schema completo por coluna OU função que adapta o padrão
export const CriarUsuario = createInsertSchema(users, {
  // forma 1: schema completo SUBSTITUI o padrão
  email: z.email(),

  // forma 2: função recebe o schema base, devolve schema modificado
  nome: (s) => s.min(1).max(200).trim(),

  // forma 3: combinar várias regras
  senha: (s) => s.min(8).regex(/[A-Z]/).regex(/[0-9]/),
});

// refine de produto — preco positivo é regra de negócio, não vem do Drizzle
export const CriarProduto = createInsertSchema(products, {
  nome:  (s) => s.min(1).max(200).trim(),
  preco: (s) => s.int().positive(),
});

// colunas não listadas mantêm o schema padrão derivado do Drizzle
Zod 4
A forma de função (s) => s.min(...) é a recomendada em drizzle-zod com Zod 4 — preserva o tipo derivado pelo Drizzle e adiciona refinamentos sobre ele. A forma de schema completo (email: z.email()) substitui completamente, perdendo características derivadas. createUpdateSchema também aceita o objeto de refinamentos com a mesma sintaxe.

# Composição com .pick, .omit, .extend

Os schemas gerados são z.object normais — todos os métodos de composição do Capítulo 5 funcionam neles. Isso permite derivar variantes específicas (resumo público, formulário interno, payload de cache) a partir do mesmo schema base:

composicao.ts
const ProdutoSelect = createSelectSchema(products);

// resumo público — só campos visíveis ao cliente
export const ProdutoPublico = ProdutoSelect.pick({
  id:    true,
  nome:  true,
  preco: true,

// sem campos sensíveis — omitir o que não deve sair
export const ProdutoSemMeta = ProdutoSelect.omit({ metadata: true });

// estender com campos calculados — útil em respostas enriquecidas
export const ProdutoComEstoque = ProdutoSelect.extend({
  em_estoque:    z.boolean(),
  ultima_compra: z.iso.datetime().nullable(),
});

// combinar com schemas vindos de outras tabelas — Vol XI Cap 11 (joins)
const UserSelect = createSelectSchema(users);
export const PedidoComUser = z.object({
  pedido: createSelectSchema(orders),
  user:   UserSelect.pick({ id: true, nome: true, email: true }),

# Limitações: o que drizzle-zod NÃO faz

drizzle-zod deriva a estrutura, não regras de negócio nem invariantes de runtime. Quatro coisas continuam sendo responsabilidade explícita do desenvolvedor:

limitacoes.ts
// 1. UNIQUE constraint — Drizzle marca como unique, Zod não checa unicidade
// solução: .refine async (Cap 17)
const CriarUsuario = createInsertSchema(users, {
  email: z.email(),
}).refine(
  async (d) => await emailDisponivel(d.email),
  'Email já cadastrado'
);

// 2. CHECK constraint — drizzle-zod ignora; declare explicitamente
// banco: CHECK (preco > 0); schema: refine ou .positive() no refinement
// 3. FOREIGN KEY existência — drizzle-zod só tipa como number
// se quiser validar que o ID existe, use refine async

// 4. Computed columns / generated columns — não aparecem por padrão no schema gerado
// (depende da versão; verifique a documentação)

// 5. .strict() — schemas gerados são .strip() por padrão (campos extras removidos)
const EstritoUsuario = createInsertSchema(users).strict();
// agora chaves extras lançam erro em vez de serem descartadas
Performance & custo
A geração via createInsertSchema roda uma vez na importação do módulo — sem custo em runtime de parse. O schema resultante tem o mesmo custo de parse que um z.object declarado à mão; a diferença é só na fonte. Para apps com dezenas de tabelas, isso evita centenas de linhas de declaração Zod e elimina a chance de drift entre a tabela e o schema de fronteira.

Validação em Hono

O Volume IX cobriu Hono como framework de roteamento — rápido, tipado, com middleware encadeável. A integração com Zod fecha o arco: @hono/zod-validator fornece zValidator, um middleware que valida a entrada de uma rota antes de chamar o handler, e expõe o valor tipado via c.req.valid(). Isso elimina o safeParse manual em cada handler. O capítulo cobre os seis alvos de validação (json, query, param, form, header, cookie), o tratamento de erros customizado, a composição de múltiplos validators por rota, e o cliente RPC tipado gerado por hc.

# zValidator — o middleware

zValidator(alvo, schema) retorna um middleware Hono que, ao executar, chama schema.safeParse no valor do alvo indicado. Se falhar, retorna 400 com o erro Zod serializado. Se passar, o valor validado e tipado fica disponível no handler via c.req.valid(alvo):

zvalidator-basico.ts
import { Hono } from 'hono';
import { zValidator } from '@hono/zod-validator';
import * as z from 'zod';

const CriarProduto = z.object({
  nome:  z.string().min(1),
  preco: z.number().positive(),
  ativo: z.boolean().default(true),
});

const app = new Hono();

app.post(
  '/products',
  zValidator('json', CriarProduto),   // middleware de validação
  async (c) => {
    const body = c.req.valid('json');   // tipo: CriarProduto (não any)
    // body.nome: string, body.preco: number, body.ativo: boolean
    const [produto] = await db
      .insert(products).values(body).returning();
    return c.json(produto, 201);
  }
);
Observação
Sem zValidator, o await c.req.json() retorna unknown (ou any em versões mais antigas), e seria necessário um safeParse manual em cada handler. Com zValidator, o middleware garante que o handler só executa com input válido — o handler fica limpo e o tipo de c.req.valid('json') é inferido diretamente do schema.

# json, query e param

Cada parte da requisição tem seu alvo. query valida os parâmetros da query string (todos chegam como string — z.coerce converte). param valida segmentos da URL, igualmente como strings:

const QueryProdutos = z.object({
  pagina:     z.coerce.number().int().positive().default(1),
  por_pagina: z.coerce.number().int().min(1).max(100).default(20),

const ParamId = z.object({
  id: z.coerce.number().int().positive(),
});

app.get(
  '/products',
  zValidator('query', QueryProdutos),
  async (c) => {
    const { pagina, por_pagina, ordenar } = c.req.valid('query');
    // todos: number | string corretos após coerção
    return c.json(await buscarProdutos({ pagina, por_pagina, ordenar }));
  }
);

app.get(
  '/products/:id',
  zValidator('param', ParamId),

# Tratamento de erros customizado

Por padrão, quando a validação falha, zValidator retorna 400 com a estrutura de erros do Zod serializada. Para formatar a resposta de erro de acordo com o padrão da API, passe um callback como terceiro argumento:

erro-customizado.ts
// callback recebe (result, context) — se não retornar nada, o handler continua
app.post(
  '/products',
  zValidator('json', CriarProduto, (result, c) => {
    if (!result.success) {
      return c.json({
        erro:    'validacao',
        campos:  result.error.flatten().fieldErrors,
        globais: result.error.flatten().formErrors,
      }, 400);
    }
  }),
  async (c) => {
    const body = c.req.valid('json');
    return c.json(await criar(body), 201);
  }
);

// fatorar o handler de erro para reutilizar em todas as rotas
const handleValidationError = (result: any, c: any) => {
  if (!result.success) {
    return c.json({
      erro:   'validacao',
      campos: result.error.flatten().fieldErrors,
    }, 400);
  }
};

# Múltiplos validators em uma rota

Uma rota pode encadear zValidator para diferentes alvos — por exemplo, validar tanto o param :id quanto o body de um PUT. Cada c.req.valid(alvo) retorna o tipo correto do schema correspondente:

multiplos-validators.ts
const AtualizarProduto = z.object({
  nome:  z.string().min(1).optional(),
  preco: z.number().positive().optional(),
  ativo: z.boolean().optional(),
});

app.patch(
  '/products/:id',
  zValidator('param', ParamId),         // valida :id
  zValidator('json', AtualizarProduto),   // valida body
  async (c) => {
    const { id }   = c.req.valid('param');   // number
    const body      = c.req.valid('json');    // AtualizarProduto
    const [produto] = await db
      .update(products)
      .set(body)
      .where(eq(products.id, id))
      .returning();
    return c.json(produto);
  }

# RPC: hc — cliente tipado

Forms e React Hook Form

@hookform/resolvers/zod conecta um schema Zod a um formulário React Hook Form. # zodResolver — conectar schema ao hook

zodResolver(schema) retorna um objeto de configuração que React Hook Form usa para validar ao submeter (e, com mode: 'onChange', em tempo real). O tipo do formulário é inferido do schema via z.infer — campos do hook ficam tipados automaticamente:

zod-resolver.ts
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import * as z from 'zod';

const CriarProdutoSchema = z.object({
  nome:  z.string().min(1, 'Nome obrigatório').max(200),
  preco: z.coerce.number().positive('Deve ser positivo'),
  ativo: z.boolean().default(true),
});
type CriarProduto = z.infer<typeof CriarProdutoSchema>;

function FormProduto() {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<CriarProduto>({
    resolver: zodResolver(CriarProdutoSchema),
    defaultValues: { ativo: true },

    // data: CriarProduto — tipado e validado antes de chegar aqui

# Server Actions: validação no servidor

No App Router do Next.js, Server Actions recebem FormData — não um objeto JSON. A validação é feita com Object.fromEntries e safeParse direto, sem zodResolver (que é um conceito client-only). O schema do cliente e do servidor pode ser o mesmo:

server-action.ts
'use server';

import * as z from 'zod';
import { db } from './db';
import { products } from './schema';

// o mesmo schema reutilizado no client (zodResolver) e no server (safeParse)
export const CriarProdutoSchema = z.object({
  nome:  z.string().min(1, 'Nome obrigatório'),
  preco: z.coerce.number().positive('Deve ser positivo'),
  ativo: z.coerce.boolean().default(true),
});

export async function criarProduto(formData: FormData) {
  // FormData → plain object → safeParse
  const raw = Object.fromEntries(formData.entries());
  const res = CriarProdutoSchema.safeParse(raw);

  if (!res.success) {
    return { erros: res.error.flatten().fieldErrors };
  }

  const [produto] = await db
    .insert(products).values(res.data).returning();
  return { sucesso: true, produto };
}

# Padrão completo: cliente + servidor

O padrão recomendado no App Router combina zodResolver no cliente para UX imediata (erros sem round-trip) e safeParse no servidor como segunda defesa (não confiar no cliente). Erros do servidor são propagados de volta ao formulário via form.setError:

cliente-servidor.ts
'use client';

import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { criarProduto, CriarProdutoSchema } from './actions';
import * as z from 'zod';

type Form = z.infer<typeof CriarProdutoSchema>;

function FormProduto() {
  const form = useForm<Form>({
    resolver: zodResolver(CriarProdutoSchema),
  });

  const onSubmit = form.handleSubmit(async (data: Form) => {
    // 1. validação client-side pelo zodResolver já passou
    const fd = new FormData();
    Object.entries(data).forEach(([k, v]) => fd.append(k, String(v)));

    // 2. Server Action — segunda camada de validação
    const resultado = await criarProduto(fd);

    if (resultado.erros) {
      // propagar erros do servidor para os campos do formulário
      Object.entries(resultado.erros).forEach(([campo, msgs]) => {
        form.setError(campo as keyof Form, {
          type: 'server',
          message: msgs?.[0],
        });
      });
    }
  });

  return { onSubmit, form };
}
Boa prática
Exporte o schema do mesmo arquivo da Server Action (export const CriarProdutoSchema = ...) e importe no componente cliente. O schema é TypeScript puro — tree-shaking remove o que não for usado, sem impacto no bundle do servidor. Isso garante que cliente e servidor usam exatamente o mesmo schema, eliminando divergências silenciosas.

Variáveis de ambiente

O Cap 2 desta série prometeu resolver o process.env.DATABASE_URL! herdado do Volume XI. process.env é tipado como Record<string, string | undefined> — tudo é string, tudo pode ser undefined, e o TypeScript não sabe quais chaves existem. Zod transforma isso numa configuração completamente tipada que falha em tempo de inicialização se algo estiver faltando ou com o formato errado, bem antes de aceitar qualquer conexão. Este capítulo cobre o padrão básico de módulo de configuração, os schemas úteis para tipos comuns de variáveis de ambiente, e a integração com t3-env para projetos Next.js que precisam separar variáveis de servidor das expostas ao cliente.

# O problema: process.env sem tipo

Sem Zod, variáveis de ambiente entram no código via non-null assertion ou conversão manual — nenhuma das duas opcções falha cedo nem documenta as expectativas:

antes-do-zod.ts
// three padrões problemáticos — todos comuns, todos frágeis
const dbUrl  = process.env.DATABASE_URL!;          // asserting não-undefined
const port   = parseInt(process.env.PORT || '3000'); // conversion manual
const debug  = process.env.DEBUG === 'true';         // boolean manual

// riscos em runtime:
// — DATABASE_URL ausente: dbUrl = undefined, erro ao conectar no banco
// — PORT = 'abc': parseInt('abc') = NaN, servidor falha ao fazer listen
// — typo em chave: process.env.DATABSE_URL = undefined (silencioso)
// — todos falham tarde, longe do ponto de inicialização

# Schema de ambiente: falha na inicialização

Com Zod, o schema é parseado uma vez quando o módulo de configuração é importado. Se qualquer variável estiver ausente ou malformada, ZodError lança antes de qualquer código de negócio executar — a startup falha com uma mensagem clara sobre qual variável causou o problema:

env.ts
import * as z from 'zod';

const EnvSchema = z.object({
  // banco — obrigatório, formato URL
  DATABASE_URL: z.url(),

  // servidor — coerce string para number, default 3000
  PORT:         z.coerce.number().int().positive().default(3000),
  HOST:         z.string().default('0.0.0.0'),
  NODE_ENV:     z.enum(['development', 'production', 'test']),

  // autenticação — comprimento mínimo como restrição de segurança
  JWT_SECRET:   z.string().min(32, 'JWT_SECRET precisa ao menos 32 caracteres'),

  // opcional
  SENTRY_DSN:   z.url().optional(),
});

// parse executado no import — antes de qualquer rota ser registrada
export const env = EnvSchema.parse(process.env);
export type Env = z.infer<typeof EnvSchema>;

// após o import, env.DATABASE_URL: string (não string | undefined)
// env.PORT: number  (não string)
// env.SENTRY_DSN: string | undefined  (opcional explícito)
Boa prática
Coloque o parse em um módulo dedicado — src/config/env.ts ou src/env.ts — e importe sempre esse módulo em vez de process.env diretamente. Toda parte do código que precisa de configuração fica com tipos corretos sem nenhum cast. O env.PORT é number, não string; o env.JWT_SECRET é string, não string | undefined.

# Padrões úteis para variáveis comuns

Alguns padrões aparecem com frequência em schemas de ambiente — boolean de string, arrays separados por vírgula, números inteiros, enums de ambientes:

# Módulo env com fail-fast e mensagem clara

Substituir .parse() por uma função que captura o ZodError e imprime as variáveis ausentes antes de encerrar o processo melhora muito a experiência de depuração — especialmente em deploys onde o log de startup é a única fonte de diagnóstico:

env-modulo.ts
import * as z from 'zod';

const EnvSchema = z.object({
  DATABASE_URL: z.url(),
  PORT:         z.coerce.number().int().positive().default(3000),
  NODE_ENV:     z.enum(['development', 'production', 'test']),
  JWT_SECRET:   z.string().min(32),
}).strict(); // .strict() rejeita variáveis extras (evita typos na chave)

function validarEnv() {
  const res = EnvSchema.safeParse(process.env);
  if (!res.success) {
    const erros = res.error.issues
      .map((i) => `  ${i.path.join('.')}: ${i.message}`)
      .join('\n');
    console.error('Variáveis de ambiente inválidas:\n' + erros);
    process.exit(1);
  }
  return res.data;
}

export const env = validarEnv();
export type Env = z.infer<typeof EnvSchema>;
Armadilha
Usar .strict() no schema de ambiente garante que variáveis com nome incorreto (ex.: DATABSE_URL) são reportadas como chave não reconhecida em vez de silenciosamente ignoradas. O trade-off: qualquer variável de sistema (HOME, PATH, SHELL) presente em process.env causará erro. Prefira .strict() quando o schema só lista as variáveis que o código usa; omita quando o ambiente pode ter variáveis extras legítimas (AWS Lambda, Docker, CI).

# parse, safeParse e o padrão assert

As três formas de validar têm casos de uso distintos. .parse() é assert-style: lança em falha, falha alta no stack — ideal para inicialização onde dado inválido significa parar o processo. .safeParse() devolve discriminated union — ideal para handlers HTTP onde falha é parte do fluxo normal. O "padrão assert" é uma convenção (não uma API separada): usar .parse em pontos onde a falha é exceção arquitetural, capturando o erro só no top-level handler do processo:

parse-modes.ts
import * as z from 'zod';

// 1. parse() — assert-style: lança em falha
// para inicialização: env, config, schemas carregados de disco
export const env = EnvSchema.parse(process.env);
// se algo está errado, ZodError lança AQUI — o processo nem inicia

// 2. safeParse() — Result discriminado, nunca lança
// para handlers onde falha é caminho normal
app.post('/users', async (c) => {
  const res = Schema.safeParse(await c.req.json());
  if (!res.success) return c.json(res.error.flatten(), 400);
  return c.json(await criar(res.data), 201);
});

// 3. "padrão assert" — parse onde falha = bug, não input ruim
function processarPedido(pedido: Pedido) {
  // pedido já passou pelo schema na fronteira HTTP
  // reparsear aqui seria desperdício — confie no tipo TypeScript
  // se quiser uma rede de segurança em pontos críticos, use .parse:
  const validado = PedidoCritico.parse(pedido); // assert defensivo
}

# Custo de runtime

Em benchmarks típicos do Zod 4 (até 14× mais rápido que Zod 3), um .parse de objeto plano com 5–10 campos primitivos custa entre 1 e 3 microssegundos. Estruturas aninhadas, refinamentos e discriminated unions adicionam overhead proporcional à complexidade. Para colocar em contexto: um endpoint HTTP típico passa centenas de microssegundos no banco e dezenas de milissegundos em latência de rede — o custo de parse fica abaixo do ruído. Em hot paths não-I/O (jogos, streaming, processamento de eventos a 10k+/s), o cálculo é diferente:

benchmark.ts

const Schema = z.object({
  id:    z.number(),
  nome:  z.string(),
  preco: z.number().positive(),
  ativo: z.boolean(),
});

const sample = { id: 1, nome: 'X', preco: 10, ativo: true };

for (let i = 0; i < 100_000; i++) {
  Schema.parse(sample);
}
const ms = (performance.now() - inicio) / 100_000;
console.log(`${ms.toFixed(4)} ms por parse`);
// em Node 22, Zod 4.4.3, hardware moderno: ~0.001-0.005 ms (1-5 μs)

// custo dominante em parses individuais é a CRIAÇÃO de objetos de resultado
// se 1% do parse falha, o ZodError adiciona overhead proporcional ao número de issues
Performance & custo
Antes de otimizar, meça. Em 95% dos casos de aplicação web, o tempo de parse desaparece dentro do tempo de banco e rede. Apenas em pipelines que processam milhões de mensagens por segundo (filas Kafka, ingestão de telemetria, parsing de logs em massa) a otimização do schema vira prioridade. Nesses casos, a estratégia geralmente é menos sobre tunar Zod e mais sobre reduzir o que precisa ser validado — parse só o que será consumido, mantenha o resto como z.unknown().

# Cache de schemas, não de resultados

Schemas Zod são objetos imutáveis. Criá-los tem custo (alocação, encadeamento de métodos); usá-los tem custo independente. A regra é simples: schemas vivem no escopo do módulo (criados uma vez no carregamento), parses vivem nos handlers (executados a cada chamada). Resultados de parse nunca devem ser cacheados — input diferente exige parse diferente:

cache-pattern.ts
// CORRETO: schema no módulo, parse no handler
const CriarProduto = z.object({ /* ... */ });

app.post('/products', async (c) => {
  const res = CriarProduto.safeParse(await c.req.json());
  // ...
});

// ANTI-PADRÃO: schema dentro do handler — recriado a cada requisição
app.post('/products', async (c) => {
  const Schema = z.object({ /* ... */ }); // alocação por chamada!
  // ...
});

// SCHEMAS DERIVADOS: use .pick/.omit/.extend sobre o base cacheado
const ProdutoBase    = createSelectSchema(products);
const ProdutoPublico = ProdutoBase.pick({ id: true, nome: true });
const ProdutoSemMeta = ProdutoBase.omit({ metadata: true });
// todos criados no carregamento, todos reutilizados em todas as requisições

# Lazy parsing: deixar campos opacos

Nem todo campo precisa ser validado estruturalmente. Payloads grandes (webhooks com 50+ campos, JSONB de terceiros, snapshots) podem ter trechos que a aplicação nem lê. Declarar esses trechos como z.unknown() reduz drasticamente o custo e a manutenção, sem perder type-safety nos campos que importam:

// padrão: validar a estrutura externa, deixar payload interno opaco
const WebhookGenerico = z.object({
  id:        z.string(),
  type:      z.string(),
  timestamp: z.iso.datetime(),
  data:      z.unknown(),  // não validamos a forma agora
});

// quando precisar usar 'data', valide o subtipo específico
const InvoiceData = z.object({
  invoice_id:  z.string().startsWith('in_'),
  amount_paid: z.number().int(),
});

function processarPago(evento: z.infer<typeof WebhookGenerico>) {
  if (evento.type !== 'invoice.paid') return;
  const data = InvoiceData.parse(evento.data);
  // só validou o subtipo de 'data' quando o handler PRECISA dele
  // outros handlers de outros 'type' nunca pagam esse custo
}

// VS schema "exato" — valida tudo, mesmo o que não é usado
const WebhookExato = z.discriminatedUnion('type', [/* 30 variantes */]);

# Quando NÃO usar Zod

Zod resolve o problema da fronteira — tudo que entra ou sai da aplicação. Para tudo o mais, o sistema de tipos TypeScript já é suficiente. Reparsear dados que já vieram tipados, ou duplicar regras que o banco já garante, é trabalho extra sem benefício:

quando-nao-usar.ts
// 1. DADOS INTERNOS JÁ TIPADOS — não há fronteira a cruzar
function calcularTotal(itens: OrderItem[]): number {
  // itens já é OrderItem[] — vindo do schema parseado na rota
  // NÃO: itens.map(i => OrderItem.parse(i)) — desperdício de runtime
  return itens.reduce((acc, i) => acc + i.preco_unit * i.quantidade, 0);
}

// 2. REGRAS QUE O BANCO JÁ GARANTE
// products.preco tem CHECK (preco > 0) no Postgres
// FK products.categoria_id → categories.id
// — duplicar essas regras em Zod NÃO previne nada

Boa prática
A pergunta diagnóstica é: "de onde esse dado vem?". Se vem de fora do build TypeScript atual (rede, disco, fila, banco escrito por outra versão), valide. Se vem de outra função do mesmo módulo, do mesmo runtime, do mesmo build — confie no tipo. Validação onde o tipo já garante é como verificar duas vezes se a porta está trancada antes de sair: faz sentido em raras situações de paranoia justificada, raramente como hábito.
