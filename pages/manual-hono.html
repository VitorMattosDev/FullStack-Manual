Introdução

Hono é um framework web minúsculo, ultra-rápido e multi-runtime: a mesma codebase TypeScript roda em Node, Bun, Deno, Cloudflare Workers, Vercel Edge, AWS Lambda e Fastly. Antes de escrever a primeira rota, vale entender por que Hono existe, qual problema resolve, e em que ele se distingue de Express ou Fastify. Este capítulo é o modelo mental — os próximos 21 são as APIs.

# O problema que Hono resolve

Por quase uma década, "framework web em JavaScript" significou Express. Express foi escrito para Node em 2010, num mundo onde existia um runtime servidor (Node, com a API de http embutida). Em 2025/2026 a paisagem é radicalmente diferente:

  • Cloudflare Workers, Vercel Edge, Fastly e Netlify rodam JavaScript em V8 isolates no edge — sem node:fs, sem node:net, sem o ciclo de vida de processo do Node.
  • Deno e Bun nasceram falando Web APIs (Fetch, Request, Response, Streams) como cidadãos de primeira classe.
  • O Node, a partir da v18, embarcou fetch global; na v22 LTS suporta Request/Response nativos via undici.

Express e Fastify ainda dependem de (req, res) com a API node:http: dois objetos próprios de Node, com semânticas (streams, headers case-insensitive, encerramento via res.end()) que só existem ali. Para rodar em Cloudflare Workers, você precisaria de um shim caro ou de reescrever a aplicação.

Hono fez a aposta oposta: tratar Request/Response da spec Web como contrato universal. Um handler Hono recebe um contexto que encapsula uma Request padrão e retorna (direta ou indiretamente) uma Response padrão. Cada runtime suportado já fala essa língua — o que muda é apenas o adapter que liga a aplicação ao loop de eventos local.

A regra de ouro do Hono

Se você sabe como funcionam Request e Response do navegador, você já sabe 80% do Hono. O servidor virou um service worker com roteador na frente.

# A aposta edge-first

"Edge-first" não é marketing — é uma restrição de engenharia que molda o framework inteiro. Workers V8 isolates impõem limites severos:

  • Bundle size: Cloudflare Workers tem teto de 1 MB no plano free, 10 MB no paid. Express + middlewares facilmente passa de 5 MB. Hono core: ~14 KB minificado.
  • Cold start: V8 isolates inicializam em microssegundos, mas só se o código for pequeno e tree-shakable. Hono é construído como módulos ESM com zero dependências de runtime.
  • CPU budget: Workers free dão ~10 ms de CPU por request. Cada middleware caro custa caro. Hono otimiza o roteador para ser O(1) amortizado.
  • Sem APIs Node: process.env, fs, crypto Node, http, net — nada disso existe. Hono nunca importa nada de node:* no core.

O efeito colateral é elegante: o framework que cabe em 14 KB também funciona muito bem em Node tradicional. A direção da otimização é unilateral — vai do mais restrito (edge) ao mais permissivo (Node) sem perder nada no caminho.

Por que isso importa para você

Mesmo que seu deploy alvo seja Node + Docker, escolher Hono te dá portabilidade gratuita: amanhã você pode mover endpoints frios para Workers (custo zero quando ociosos), manter os quentes em Node, e compartilhar 100% do código e dos tipos.

# Hello world: a essência em 6 linhas

Antes de qualquer comparação, veja o que se assina ao adotar Hono. A função fetch exportada é literalmente o que cada runtime espera receber — é a interface universal.

src/index.ts
import { Hono } from "hono"

const app = new Hono()

app.get("/", (c) => c.text("Olá, Hono"))

export default app // = { fetch: (req: Request) => Promise<Response> }

O app exportado é um objeto com método fetch. Cloudflare Workers procura export default { fetch }. Deno Deploy, Bun, Vercel Edge — todos consomem a mesma interface. Para Node, o adapter @hono/node-server faz a ponte entre http.IncomingMessage e Request:

src/node.ts
import { serve } from "@hono/node-server"
import app from "./index"

serve({ fetch: app.fetch, port: 3000 })

# Hono vs Express vs Fastify

Os três frameworks resolvem o mesmo problema superficial — rotear HTTP e responder. As diferenças aparecem quando você olha o modelo:

Modelo de handler

Express usa (req, res, next): você muta res e chama next() ou encerra com res.send(). Não há retorno — o fim da response é detectado por efeito colateral. Isso torna middleware difícil de tipar e fácil de "esquecer" de encerrar.

Fastify usa async (req, reply) => payload: o valor de retorno vira o body. Boa ergonomia, mas req/reply são objetos próprios do Fastify, com semânticas Node-específicas.

Hono usa async (c) => Response: um único objeto de contexto, e o retorno é uma Response Web padrão (criada por helpers como c.json()). O middleware é um wrapper em volta do handler — modelo onion, como Koa.

comparação
// Express
app.get("/u/:id", (req, res) => {
  res.json({ id: req.params.id })  // efeito colateral
})

// Fastify
fastify.get("/u/:id", async (req) => {
  return { id: req.params.id }     // retorno serializado
})

// Hono
app.get("/u/:id", (c) => {
  return c.json({ id: c.req.param("id") })  // Response padrão
})

Tipagem

Express foi escrito antes do TypeScript. A tipagem em @types/express é retrofit — params são any por padrão, middlewares aumentam Request via declaration merging global (frágil). Fastify oferece tipagem opt-in via generics nas rotas. Hono infere os tipos a partir das rotas: path params, body validado com Zod, variáveis adicionadas por middleware — tudo flui pelo sistema de tipos sem você escrever interfaces.

Performance

Em benchmarks de roteamento puro (request → match → response), Hono está consistentemente entre os mais rápidos do ecossistema JavaScript. O RegExpRouter compila todas as rotas numa única regex e faz match em O(1) — Fastify usa find-my-way (radix tree, também rápido) e Express usa lista linear de regex. Não confunda micro-benchmark com gargalo real: na vida real o roteador raramente é o limite. O que muda é o perfil — Hono e Fastify têm overhead constante baixíssimo, Express acumula custo proporcional ao número de rotas e middlewares.

# Posicionamento no ecossistema

Hono não compete com tudo. Onde ele encaixa bem — e onde não:

Onde Hono brilha

  • APIs HTTP / JSON em qualquer escala: do endpoint único em Worker até monolito Node de centenas de rotas.
  • BFF (Backend-for-Frontend) de SPAs e apps mobile, com RPC tipado via hc() dispensando geração de cliente externo.
  • Edge functions para autenticação, rewrites, A/B testing, geolocation, rate limiting próximo ao usuário.
  • Webhooks e integrações: o overhead mínimo combina com cargas pontuais e imprevisíveis (cobrança por execução, não por uptime).
  • APIs full-stack com JSX no servidor: substituto direto e mais leve para Express + EJS/Handlebars, sem build step para o servidor.

Onde provavelmente não é o ajuste

  • SSR de SPAs complexas com hidratação: Next.js, Remix ou Astro resolvem isso melhor (Hono pode ser o BFF delas).
  • WebSockets de longa duração em escala: edge runtimes têm limites; Node + Hono funciona, mas para milhares de conexões persistentes considere soluções dedicadas (uWS direto, Erlang/Elixir, Go).
  • Aplicações que dependem fortemente de bibliotecas Node-only (Puppeteer, drivers nativos antigos): você pode usar Hono, mas perde o argumento da portabilidade.
Hono é um framework, não uma stack

Diferente de Next.js ou NestJS, Hono não opina sobre ORM, validação, autenticação, deploy ou estrutura de pastas. Ele entrega roteamento + middleware + tipagem e te deixa montar o resto. Os próximos volumes desta coleção (Drizzle, Zod, Autenticação) fecham essa lacuna por composição.

# Anatomia de uma aplicação Hono típica

Para fechar o modelo mental, eis o esqueleto de uma API real — você vai reconhecer cada peça nos próximos capítulos:

src/app.ts
import { Hono } from "hono"
import { logger } from "hono/logger"
import { cors } from "hono/cors"
import { HTTPException } from "hono/http-exception"
import { zValidator } from "@hono/zod-validator"
import { z } from "zod"

const app = new Hono()

// 1. Middlewares globais — executam em toda requisição
app.use(logger())
app.use("/api/*", cors())

// 2. Schema de validação — reutilizado pelo cliente RPC
const createUser = z.object({
  name: z.string().min(2),
  email: z.string().email(),
})

// 3. Rotas — handler retorna Response
app.post(
  "/api/users",
  zValidator("json", createUser),
  async (c) => {
    const body = c.req.valid("json") // já tipado e validado
    return c.json({ created: body }, 201)
  }
)

// 4. Tratamento centralizado de erros
app.onError((err, c) => {
  if (err instanceof HTTPException) return err.getResponse()
  return c.json({ error: "internal" }, 500)
})

export default app

São quatro camadas claras: middlewares (cross-cutting), schemas (contrato de dados), handlers (lógica por rota), e error boundary (uniformidade de falhas). Cada uma delas tem seu próprio capítulo neste volume.

# tsconfig.json recomendado

Hono usa TypeScript 5.x e infere tipos de rotas via generics avançados. O tsconfig.json mínimo para ter a melhor experiência:

tsconfig.json
{
  "compilerOptions": {
    "target":      "ES2022",
    "module":      "NodeNext",  // ou "ESNext" para Bun/Deno/Workers
    "moduleResolution": "NodeNext",
    "lib":         ["ES2022", "DOM"],  // DOM para tipos Web (Request, Response, etc.)
    "strict":      true,
    "noUncheckedIndexedAccess": true,
    "outDir":      "dist",
    "rootDir":     "src",
    "skipLibCheck": true
  },
  "include": ["src"]
}

Ponto importante: a lib "DOM" é necessária mesmo em código servidor — ela contém as definições de Request, Response, Headers, ReadableStream e FormData que Hono usa como contratos. Para Cloudflare Workers, substitua "DOM" por "@cloudflare/workers-types" no campo "types" para evitar conflitos entre a API DOM e a API Workers.

Capítulo 03

Roteamento

Um framework HTTP é, antes de tudo, um roteador: dado um (método, path), qual handler chamar? A resposta parece trivial em projetos pequenos, mas vira problema sério em escala — centenas de rotas, parâmetros opcionais, padrões com sobreposição, exigência de baixa latência por request. Hono trata roteamento como um dos seus diferenciais técnicos: oferece três algoritmos diferentes e um quarto, o SmartRouter, que escolhe entre eles automaticamente. Este capítulo é sobre o que está debaixo do app.get().

# O que um roteador faz

Em essência, um roteador é uma função:

conceito
match(method: string, path: string) => { handler, params } | null

Mas a complexidade aparece quando você tem rotas como estas no mesmo app:

  • GET /users — listagem
  • GET /users/:id — um usuário
  • GET /users/:id/posts — posts do usuário
  • GET /users/me — perfil próprio (precede /users/:id!)
  • GET /static/* — wildcard para arquivos
  • GET /api/v:version{[0-9]+}/data — regex constraint

Cada decisão tem custo. Um roteador linear (lista de regex) responde em O(n × custo_regex). Um trie (árvore de prefixos) responde em O(comprimento_do_path), independente do número de rotas. Uma regex compilada única (todas as rotas combinadas) responde em O(1) amortizado, mas paga caro no setup. Não existe escolha universal — existe trade-off entre velocidade de roteamento, velocidade de cold start e flexibilidade de padrões.

A virada de Hono

Outros frameworks fixam uma estratégia. Express é linear, Fastify é trie via find-my-way, Koa não tem roteador nativo. Hono permite que você troque o algoritmo de roteamento sem reescrever uma linha do app — basta passar { router: ... } ao construtor.

# Sintaxe básica e métodos HTTP

Métodos HTTP têm helpers dedicados. Cada um aceita (path, ...middleware, handler) e adiciona a rota à tabela interna do roteador escolhido.

src/routes.ts
import { Hono } from "hono"

const app = new Hono()

app.get("/users",    (c) => c.json([]))
app.post("/users",   (c) => c.json({}, 201))
app.put("/users/:id",    (c) => c.json({}))
app.patch("/users/:id",  (c) => c.json({}))
app.delete("/users/:id", (c) => c.body(null, 204))

// Casar todos os métodos HTTP
app.all("/health", (c) => c.text("OK"))

// Métodos arbitrários (ex.: PROPFIND, MKCOL para WebDAV)
app.on("PROPFIND", "/dav/*", (c) => c.text(""))

// Vários métodos para o mesmo path
app.on(["PUT", "DELETE"], "/docs/:id", (c) => c.json({}))

app.on(method, path, handler) é o método de baixo nível — todos os helpers (.get, .post, etc.) chamam on internamente. Use-o para métodos HTTP customizados ou para registrar várias verbos de uma vez.

# Path parameters

A sintaxe :nome captura um segmento do path. O valor é acessível via c.req.param("nome"), totalmente tipado pelo TypeScript a partir da string do path.

params básicos
app.get("/users/:id", (c) => {
  const id = c.req.param("id")   // string (inferido)
  return c.json({ id })
})

app.get("/posts/:slug/comments/:cid", (c) => {
  const { slug, cid } = c.req.param()  // objeto com ambos
  return c.json({ slug, cid })
})
Params são sempre string

Mesmo que o conteúdo pareça numérico, params chegam como string. Se você precisa de number, converta explicitamente (Number(id)) ou — melhor ainda — valide com Zod (Capítulo 9), que faz a coerção e a validação juntas.

Optional parameters

Adicione ? ao final do nome para tornar o segmento opcional:

optional params
app.get("/api/animals/:type?", (c) => {
  const type = c.req.param("type")  // string | undefined
  return c.json({ type: type ?? "todos" })
})

// Casa: /api/animals  e  /api/animals/cats

Regex constraints

Restrinja o formato aceito com {regex} entre chaves após o nome do param. Útil para forçar IDs numéricos, slugs, versões — sem precisar validar manualmente.

regex constraints
// Só casa se :id for puramente numérico
app.get("/users/:id{[0-9]+}", (c) => {
  const id = Number(c.req.param("id"))  // pode converter sem medo
  return c.json({ id })
})

// Slug: letras, números e hífen
app.get("/posts/:slug{[a-z0-9-]+}", (c) => {
  return c.json({ slug: c.req.param("slug") })
})

// Versão semver simples
app.get("/api/v:version{[0-9]+}/data", (c) => {
  return c.json({ v: c.req.param("version") })
})

// Captura tudo após /files/ (inclusive barras)
app.get("/files/:path{.+\\.png}", (c) => {
  return c.json({ file: c.req.param("path") })
})

O regex é interno ao segmento, sem âncoras ^ ou $ — o Hono insere o que for necessário. Se a regex contém /, o param pode atravessar segmentos (como :path{.+\.png} no exemplo acima).

Wildcards

O * casa qualquer sequência de caracteres restante, atravessando barras. É a forma idiomática de criar catch-alls e namespaces.

wildcards
// Casa qualquer path dentro de /static/
app.get("/static/*", (c) => {
  return c.text(c.req.path)
})

// Casa qualquer rota não atendida (catch-all)
app.get("*", (c) => c.text("fallback", 404))

// Wildcard nomeado é apenas regex que captura tudo:
app.get("/proxy/:rest{.+}", (c) => {
  return c.json({ rest: c.req.param("rest") })
})

# Ordem de matching e ambiguidade

Quando uma URL casa com mais de uma rota, qual ganha? Hono usa ordem de registro — a primeira rota registrada que casa, ganha. Isso é diferente de Express (mesmo comportamento) e de Fastify (que escolhe a mais específica via radix tree).

a ordem importa
// CORRETO — rota específica antes da genérica
app.get("/users/me",   (c) => c.json({ self: true }))
app.get("/users/:id", (c) => c.json({ id: c.req.param("id") }))

// ERRADO — /users/me cairia em :id="me"
app.get("/users/:id", (c) => c.json({ id: c.req.param("id") }))
app.get("/users/me",   (c) => c.json({ self: true }))
Pegadinha clássica

Registre rotas estáticas antes de rotas com params, e rotas com regex constraints antes de wildcards. É a regra de ouro para evitar handlers "fantasmas" que nunca executam. Se uma rota nunca dispara em testes, quase sempre é ordem.

# Agrupando rotas com sub-routers

Apps reais não cabem num único arquivo. O padrão idiomático em Hono é criar sub-apps e montá-los na raiz com app.route(). Cada sub-app é uma instância Hono completa — com middlewares, validação e tipos próprios.

src/routes/users.ts
import { Hono } from "hono"

const users = new Hono()

users.get("/",         (c) => c.json([]))
users.get("/:id",      (c) => c.json({ id: c.req.param("id") }))
users.post("/",        (c) => c.json({}, 201))

export default users
src/index.ts
import { Hono } from "hono"
import users from "./routes/users"
import posts from "./routes/posts"

const app = new Hono()

app.route("/users", users)   // monta sub-app em /users
app.route("/posts", posts)

export default app

O caminho do sub-app é prefixado ao path da rota: users.get("/:id") montado em "/users" vira GET /users/:id. Sub-apps podem ser aninhados:

aninhamento
const api = new Hono()
api.route("/users", users)
api.route("/posts", posts)

const app = new Hono()
app.route("/api/v1", api)

// Resultado: GET /api/v1/users/:id, GET /api/v1/posts, etc.
Hono 4.x · route() preserva tipos

Em Hono 3, app.route() perdia parcialmente o tipo das rotas para o RPC (Capítulo 13). Em Hono 4, a inferência de tipos atravessa montagens — você pode estruturar o app em dezenas de arquivos sem perder o type-safety end-to-end do cliente hc().

app.basePath()

Alternativa a route() quando o sub-app é interno e você só quer prefixar tudo:

basePath
const api = new Hono().basePath("/api/v1")

api.get("/users", ...) // → GET /api/v1/users
api.get("/posts", ...) // → GET /api/v1/posts

Use route() quando o sub-app vive em arquivo próprio (modularidade); use basePath() quando você só quer um prefixo no app principal.

# Method chaining

Todos os métodos de rota retornam this — você pode encadear handlers. Esse padrão é especialmente importante para o RPC (Cap. 13), porque preserva os tipos de cada rota numa cadeia única que o cliente consegue ler.

chaining
const app = new Hono()
  .get("/users",     (c) => c.json([]))
  .post("/users",    (c) => c.json({}, 201))
  .get("/users/:id", (c) => c.json({ id: c.req.param("id") }))

export type AppType = typeof app   // usado pelo cliente RPC
export default app

# Os três routers internos

Hono 4 vem com três implementações de roteador. Você escolhe (ou deixa o SmartRouter escolher) ao construir a instância:

trocando o router
import { Hono }            from "hono"
import { TrieRouter }      from "hono/router/trie-router"
import { RegExpRouter }    from "hono/router/reg-exp-router"
import { PatternRouter }   from "hono/router/pattern-router"
import { SmartRouter }     from "hono/router/smart-router"

const app = new Hono({ router: new RegExpRouter() })

RegExpRouter — o padrão rápido

É o router default em Hono 4. Estratégia: combinar todas as rotas numa única regex compilada. O matching vira uma execução de regex em O(1) amortizado, independente do número de rotas.

Trade-offs:

  • Match: extremamente rápido — uma única operação regex.exec()
  • Setup: caro — a regex é construída na primeira request; em apps com muitas rotas o cold start sobe
  • Limitação: não suporta certos padrões ambíguos. Se você combinar rotas que geram regex conflitante (ex.: /:a/:b e /:a/x em alguns casos), o RegExpRouter lança erro no setup — e o SmartRouter cai pro TrieRouter

TrieRouter — o fallback flexível

Implementa uma árvore de prefixos (trie) onde cada nó representa um segmento do path. O matching percorre a árvore segmento a segmento.

  • Match: O(comprimento_do_path) — rápido, mas proporcional ao número de segmentos
  • Setup: barato — construir a trie é linear no número de rotas
  • Sem limitações de padrão — aceita tudo que o RegExpRouter aceita e mais alguns casos

PatternRouter — o minúsculo

Usa a Web API URLPattern nativa. É o menor em bytes (~3 KB) — útil quando bundle size é o limite absoluto, como em edge runtimes com cap apertado.

  • Match: O(n) — testa cada padrão em sequência
  • Setup: zero — usa API embutida do runtime
  • Bundle: o menor; ideal para Workers free tier com muitas dependências
  • Disponibilidade: requer URLPattern no runtime (todos os modernos têm, mas Node antigo pode precisar de polyfill)

SmartRouter — escolha automática

É o router default de fato em Hono 4. Recebe uma lista de routers candidatos e, na primeira request, tenta construir cada um até achar o primeiro que aceita todas as rotas registradas. Resultado: você ganha o RegExpRouter quando possível, com fallback automático ao TrieRouter quando não.

SmartRouter manual
import { Hono }         from "hono"
import { SmartRouter }  from "hono/router/smart-router"
import { RegExpRouter } from "hono/router/reg-exp-router"
import { TrieRouter }   from "hono/router/trie-router"

const app = new Hono({
  router: new SmartRouter({
    routers: [new RegExpRouter(), new TrieRouter()],
  }),
})

Esse já é o setup default — você raramente precisa configurar manualmente. Mas saber que ele existe ajuda a entender mensagens de log do tipo "SmartRouter fallback to TrieRouter": significa que alguma combinação de rotas é ambígua o suficiente pro RegExpRouter rejeitar.

Quando trocar o router manualmente

Três cenários reais: (1) cold start crítico em Workers free tier com muitas rotas — use TrieRouter direto, evita o custo da compilação regex; (2) bundle no limite — PatternRouter economiza ~10 KB; (3) app com poucas rotas (<30) e match na hot path — RegExpRouter direto, evita o overhead do SmartRouter na primeira request.

Capítulo 04

O contexto (c)

Todo handler Hono recebe um único argumento: c, o objeto de contexto. Ele substitui o par (req, res) de Express e o (req, reply) do Fastify por uma única superfície onde request, response, variáveis tipadas, bindings de runtime e controles de execução convivem. Entender o contexto é entender Hono — quase todo capítulo seguinte é uma exploração de alguma propriedade dele.

# Por que um único objeto

Em frameworks Node clássicos, request e response são objetos diferentes — porque assim eles são na API de node:http: IncomingMessage (stream legível) e ServerResponse (stream escrevível). Faz sentido lá embaixo. Mas no modelo Web Fetch (Request → Response), a resposta é um valor de retorno, não um stream que você manipula. Ter dois objetos vira artefato histórico.

Hono une os dois — e mais coisas — em c por três razões:

  • Modelo de retorno explícito: o handler retorna uma Response via c.json(), c.text(), etc. Não há "esquecer de chamar res.end()".
  • Storage tipado de meio-de-execução: middlewares precisam passar dados para handlers (usuário autenticado, request ID, conexão de DB). c.set()/c.get() faz isso com tipos inferidos, sem precisar mutar globais.
  • Acesso uniforme a recursos de runtime: c.env abstrai bindings de Workers, variáveis Node e args de Lambda numa única superfície. Trocar de runtime não muda o handler.

O contexto agrupa propriedades por responsabilidade. Veja o mapa antes de mergulhar:

# c.res — a Response em construção

Embora a forma idiomática seja retornar uma Response, o Hono mantém uma Response "em construção" acessível via c.res. Você raramente precisa dela diretamente — a exceção é em middlewares após o handler (modelo onion, Cap. 7), onde você pode inspecionar ou substituir a resposta já criada.

modificando c.res num middleware
app.use(async (c, next) => {
  await next()
  // Após next(), c.res existe — adicione um header pós-handler
  c.res.headers.set("X-Response-Time", "12ms")
})
c.res é mutável — c.json/text/html não

O retorno de c.json() é uma Response nova, imutável quanto a headers depois de construída. Se você precisa modificar a resposta após ela ser criada, use c.res.headers.set() ou substitua a resposta inteira via c.res = new Response(...).

# c.set / c.get / c.var — storage tipado

O caso clássico: um middleware de autenticação valida o token e quer disponibilizar o usuário para os handlers. Em Express isso vira req.user (mutação não-tipada). Em Hono, c.set("user", user) + c.get("user") — com tipos checados em tempo de compilação.

storage entre middleware e handler
import { Hono } from "hono"

type User = { id: string; name: string }

// Declare o shape de Variables ao instanciar
const app = new Hono<{
  Variables: { user: User; requestId: string }
}>()

// Middleware seta valores tipados
app.use(async (c, next) => {
  c.set("requestId", crypto.randomUUID())
  c.set("user", { id: "u_1", name: "Ana" })  // tipado!
  await next()
})

// Handler lê com tipos preservados
app.get("/me", (c) => {
  const user      = c.get("user")        // User
  const requestId = c.get("requestId")   // string
  return c.json({ user: user, id: requestId })
})

O dot-access c.var.user é um alias equivalente a c.get("user"). Mais ergonômico em handlers, especialmente com auto-complete:

c.var (alternativa idiomática)
app.get("/me", (c) => {
  return c.json({
    user: c.var.user,        // equivale a c.get("user")
    id:   c.var.requestId,
  })
})
c.set é escopado à request

Cada request cria um c novo. Valores setados num request não vazam para outros — não há estado global compartilhado. Isso é fundamental em edge runtimes, onde um isolate atende muitos requests em paralelo no mesmo processo.

Sem declarar Variables: o tipo é any

Se você não declarar Variables no generic, c.get retorna any e você perde o type-check. Em apps reais, sempre declare:

tipagem opcional, mas recomendada
// Sem tipos — c.get("user") é any
const app1 = new Hono()

// Com tipos — c.get só aceita chaves declaradas, e retorna o tipo certo
const app2 = new Hono<{ Variables: { user: User } }>()
app2.use((c) => { c.get("xxx") })  // ❌ erro de compilação

# c.executionCtx — tarefas pós-resposta

Em runtimes que entendem o conceito de "trabalho em background após a resposta" (Cloudflare Workers, Vercel Edge), Hono expõe esse controle via c.executionCtx. Tem dois usos principais:

waitUntil — fire-and-forget seguro

Permite agendar uma Promise que continua executando depois da response ser enviada ao cliente. O runtime mantém o isolate vivo até a promise resolver. Útil para: logging assíncrono, cache warming, métricas, webhooks downstream.

waitUntil
app.post("/order", async (c) => {
  const order = await c.req.json()
  await saveOrder(order)

  // Resposta retorna imediatamente; o log roda em background
  c.executionCtx.waitUntil(
    fetch("https://analytics.example.com/event", {
      method: "POST",
      body: JSON.stringify({ type: "order_created", order: order }),
    })
  )

  return c.json({ ok: true }, 201)
})
Hono 4.x · waitUntil portátil

Em Hono 4, c.executionCtx é exposto com o mesmo formato em Workers, Vercel Edge e (parcialmente) em Bun. Em Node tradicional, waitUntil existe mas é um no-op que apenas aguarda a promise antes de encerrar o processo — comportamento sensato para evitar quebras de portabilidade.

passThroughOnException

Específico a Workers. Se chamado, faz o request "passar" para o origin original caso o handler lance uma exceção não tratada — em vez de devolver erro 500. Útil em workers que agem como proxy/CDN.

passThroughOnException (Workers)
app.use(async (c, next) => {
  c.executionCtx.passThroughOnException()
  await next()
})

Você já viu pedaços. Aqui está o padrão completo, que aparece em todo app Hono real:

o generic completo
type AppEnv = {

    DB:      D1Database

Define uma vez no arquivo de tipos, importe em todos os sub-apps. Isso garante que c.env, c.var e c.get sempre tenham o mesmo shape — você não pode acidentalmente registrar um sub-app com Variables conflitantes.

Por que separar Bindings de Variables

Bindings são valores que vêm de fora — injetados pelo runtime por request, imutáveis pelo handler. Variables são valores que o app cria e passa entre middlewares e handlers, mutáveis durante o ciclo do request. Manter os dois separados clareia a intenção e torna os tipos navegáveis.

# Lifecycle do c

Cada request gera um c novo. A ordem de eventos é:

  1. Runtime recebe uma Request e invoca app.fetch(req, env, executionCtx)
  2. Hono cria um novo Context populando c.req, c.env, c.executionCtx
  3. Middlewares e handler executam, lendo/gravando c.var e construindo c.res
  4. O handler retorna uma Response (ou c.res é finalizado)
  5. Hono devolve a Response ao runtime
  6. c sai de escopo e é descartado pelo GC

Não há reuso de contexto entre requests — mesmo em isolates V8 com alto fan-out, cada request ganha o seu. Variáveis declaradas no nível do módulo (fora do handler) persistem, mas são compartilhadas entre todos os requests do mesmo isolate e devem ser tratadas como caches/singletons cuidadosamente.

app.get("/posts/:postId/comments/:cid", (c) => {
  const postId = c.req.param("postId")  // string
  const all    = c.req.param()           // { postId: string, cid: string }
  return c.json(all)
})

# Query string

query() retorna um único valor; queries() retorna array (para parâmetros repetidos como ?tag=js&tag=ts):

query strings
app.get("/search", (c) => {
  const q      = c.req.query("q")       // string | undefined
  const page   = c.req.query("page")    // string | undefined
  const tags   = c.req.queries("tag")   // string[]  (?tag=js&tag=ts)
  const allQs  = c.req.query()          // Record<string, string>
  return c.json({ q, page, tags })
})
Query params são sempre string

Assim como path params, valores de query chegam como string | undefined. Use Number(page) para converter — ou melhor, valide com @hono/zod-validator (Capítulo 9), que faz coerção e validação em um passo.

# Headers

header() é case-insensitive e retorna string | undefined. Sem argumento, retorna todos os headers como objeto:

headers
app.post("/upload", async (c) => {
  const auth        = c.req.header("authorization")   // string | undefined
  const contentType = c.req.header("content-type")    // case-insensitive
  const allHeaders  = c.req.header()                  // Record<string, string>

  if (!auth?.startsWith("Bearer ")) {
    return c.json({ error: "não autorizado" }, 401)
  }
  return c.json({ ok: true })
})

# Body — JSON e texto

Os métodos de body são async — consomem o stream da request e retornam uma Promise. Um body só pode ser lido uma vez; se precisar reler, guarde o resultado numa variável.

json e texto
app.post("/echo", async (c) => {
  const body = await c.req.json()   // qualquer — type: unknown
  return c.json(body)
})

app.post("/text", async (c) => {
  const text = await c.req.text()   // string
  return c.text(text.toUpperCase())
})

app.post("/binary", async (c) => {
  const buf  = await c.req.arrayBuffer()  // ArrayBuffer
  const blob = await c.req.blob()         // Blob
  return c.json({ bytes: buf.byteLength })
})
req.json() não valida

await c.req.json() retorna unknown — faz o parse do JSON mas não garante o shape dos dados. Use junto com Zod ou @hono/zod-validator para garantir o tipo antes de usar o body no handler. Capítulo 9 mostra o padrão completo.

# Body — form e multipart

app.post("/multi", async (c) => {

# c.req.valid() — dados validados

Quando você usa um middleware de validação (@hono/zod-validator, Capítulo 9), os dados validados e tipados são armazenados internamente no contexto e acessados via c.req.valid(). A string passada indica a fonte:

c.req.valid — acesso pós-validação
import { zValidator } from "@hono/zod-validator"
import { z } from "zod"

const schema = z.object({ name: z.string(), age: z.number() })

app.post(
  "/users",
  zValidator("json", schema),
  (c) => {
    // c.req.valid("json") retorna { name: string; age: number } — garantido!
    const { name, age } = c.req.valid("json")
    return c.json({ created: { name, age } }, 201)
  }
)

// Fontes disponíveis: "json" | "form" | "query" | "param" | "header" | "cookie"

O grande benefício: o TypeScript sabe o tipo exato do body sem nenhuma asserção manual. O middleware de validação e o handler formam um contrato estático — se o schema mudar, o compilador aponta onde o tipo quebrou.

Prefira c.req.valid() a c.req.json()

Em rotas com validação, use sempre c.req.valid("json") em vez de await c.req.json(). Além do tipo garantido, evita consumir o body duas vezes (o validator já o leu — chamar .json() de novo resulta em body vazio).

# Acesso à Request crua

c.req.raw expõe a Request padrão subjacente. Use quando Hono não oferece helper para o que você precisa — leitura de stream manual, uso de APIs específicas do runtime, ou interop com libs que esperam um Request nativo:

c.req.raw — acesso direto
app.post("/stream", async (c) => {
  const raw = c.req.raw

  // Leitura manual do body como stream
  const reader = raw.body?.getReader()
  if (!reader) return c.text("sem body", 400)

  let total = 0
  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    total += value.byteLength
  }

  return c.json({ bytes: total })
})

// Passar Request para uma lib externa (ex.: Stripe webhook)
app.post("/webhook", async (c) => {
  const sig   = c.req.header("stripe-signature") ?? ""
  const event = await stripe.webhooks.constructEventAsync(
    await c.req.text(),   // body como string
    sig,
    c.env.STRIPE_SECRET
  )
  return c.json({ received: true })
})

Capítulo 06

Response patterns

Enquanto o Capítulo 5 cobriu a leitura do request, este capítulo cobre o outro lado: construir e retornar respostas. Hono oferece helpers tipados para os casos mais comuns — JSON, texto, HTML, binário — e mecanismos para customizar status codes, headers, cookies, redirects e respostas de streaming. A regra central é sempre a mesma: o handler retorna uma Response.

# c.json — resposta mais comum

Serializa qualquer valor como JSON, define Content-Type: application/json e permite status e headers extras nos argumentos seguintes:

c.json
// Assinatura: c.json(data, status?, headers?)

app.get("/users", (c) => c.json([]))                   // 200
app.post("/users", (c) => c.json({}, 201))             // 201 Created
app.get("/err",   (c) => c.json({ error: "não achei" }, 404))

// Com headers extras no terceiro argumento
app.get("/cached", (c) =>
  c.json({ data: "ok" }, 200, {
    "Cache-Control": "public, max-age=60",
    "X-Source": "cache",
  })
)

// Tipagem do corpo inferida automaticamente
const users: User[] = await db.query()
return c.json(users)   // Response tipada como User[]

# c.text e c.html

Para respostas em texto puro ou HTML. c.html() aceita tanto string quanto JSX (coberto no Capítulo 12):

c.text e c.html

// Aceita JSX (requer tsconfig "jsx": "react-jsx" e hono/jsx)

)

# Status codes e headers — modificadores

Além de passar status e headers inline, você pode defini-los separadamente com c.status() e c.header() antes de retornar a resposta. Útil em middlewares que não conhecem o status final:

c.status e c.header
app.post("/items", async (c) => {
  const item = await createItem(await c.req.json())

  c.status(201)
  c.header("Location", `/items/${item.id}`)
  c.header("X-Request-Id", c.get("requestId"))  // de middleware

  return c.json(item)  // usa o status já setado
})

// header() com append — não sobrescreve, concatena (ex.: Set-Cookie múltiplo)
c.header("Set-Cookie", "a=1")
c.header("Set-Cookie", "b=2", { append: true })  // dois cookies
Inline vs modificadores — qual usar?

Prefira a forma inline c.json(data, 201, headers) quando o status é conhecido na hora do retorno — mais explícito e fácil de rastrear. Use c.status() e c.header() em middleware genérico que não sabe qual helper o handler vai usar.

# c.redirect — redirecionamentos

# Streaming — introdução

Hono oferece helpers de streaming em hono/streaming. A versão completa está no Capítulo 15; aqui está o padrão básico para respostas que crescem progressivamente — útil para logs, AI token-by-token, CSV grande:

stream básico
import { stream, streamText, streamSSE } from "hono/streaming"

// Escrita sequencial via helper stream()
app.get("/progress", (c) =>
  stream(c, async (s) => {
    for (let i = 0; i < 5; i++) {
      await s.write(`linha ${i}\n`)
      await s.sleep(100)  // ms
    }
  })
)

// Server-Sent Events — evento com nome e data
app.get("/events", (c) =>
  streamSSE(c, async (sse) => {
    for (let i = 0; i < 3; i++) {
      await sse.writeSSE({ data: `msg ${i}`, event: "update" })
      await sse.sleep(500)
    }
  })
)
Streaming em edge runtimes

Em Workers e Vercel Edge, o streaming funciona via ReadableStream nativo — sem buffer intermediário. Em Node com @hono/node-server, o adapter faz a ponte entre o stream padrão e a API de Node. A API stream() do Hono é a mesma nos dois casos — sem mudança no seu código.

# Padrões de resposta de erro

O padrão mais consistente para erros é um shape JSON uniforme, com o tratamento centralizado em app.onError (Capítulo 11). Nos handlers, use HTTPException ou retorne diretamente:

padrões de erro
import { HTTPException } from "hono/http-exception"

app.get("/secret", (c) => {
  const token = c.req.header("authorization")

  // Opção 1: retornar direto (simples)
  if (!token) return c.json({ error: "não autorizado" }, 401)

  // Opção 2: HTTPException — sobe pro onError centralizado
  if (!isValid(token)) throw new HTTPException(403, {
    message: "token inválido"
  })

  return c.json({ secret: "42" })
})
Consistência sobre conveniência

Escolha um padrão de resposta de erro e use em todo o app. Times que misturam c.json(…, 404) diretamente em cada handler com HTTPException acabam com formatos de erro inconsistentes. O Capítulo 11 mostra como centralizar tudo em app.onError.

Capítulo 07

Middleware

Middleware é como o Hono compõe comportamento. Logging, autenticação, CORS, cache, compressão, rate limiting — todos esses são cross-cutting concerns, código que precisa rodar em torno de muitas rotas sem se misturar à lógica de cada uma. Hono herda o modelo onion de Koa: middlewares são camadas concêntricas em torno do handler, com execução antes e depois. Entender essa estrutura é entender como composer aplicações inteiras a partir de funções pequenas.

# O modelo onion

Em Express, middlewares formam uma fila linear: cada um decide se passa ao próximo via next(). Quando o último responde, acabou. Não há "execução depois". Para fazer logging do tempo total, você precisa de ginástica: salvar Date.now() no req, registrar listener no res.on("finish").

Em Hono (e Koa), middlewares são funções recursivas. next() não é "passa adiante e acabou" — é "executa o restante da cadeia e me devolve o controle". O código antes do await next() roda antes; o código depois, depois. Visualmente:

modelo onion (visualização)
                    ┌─────────── A: antes ──────────┐
                    │   ┌─────── B: antes ───────┐   │
                    │   │   ┌─── C: antes ──┐    │   │
  request  ───────► │   │   │    handler    │    │   │ ───────► response
                    │   │   └─── C: depois ─┘    │   │
                    │   └─────── B: depois ──────┘   │
                    └─────────── A: depois ──────────┘

Cada middleware envolve os de dentro. O timing do logger do exemplo abaixo cai naturalmente do modelo: você marca o tempo antes, chama next() que executa tudo até o handler e volta, e mede o delta depois. Sem listener, sem mutação compartilhada.

logger de tempo: antes e depois num só lugar
app.use(async (c, next) => {
  const start = Date.now()      // antes
  await next()                       // executa o resto da cadeia
  const ms = Date.now() - start   // depois
  c.res.headers.set("X-Response-Time", `${ms}ms`)
})
A regra única do middleware

Tudo antes de await next() roda na descida. Tudo depois roda na subida. Se você não chamar next(), a cadeia encerra ali — útil para early return (auth falhou, 401 imediato). Se chamar duas vezes, exceção.

# Anatomia de um middleware

A assinatura é simples: uma função async que recebe (c, next) e retorna void | Response | Promise<void | Response>. Hono exporta o tipo MiddlewareHandler:

assinatura tipada
import type { MiddlewareHandler } from "hono"

const timing: MiddlewareHandler = async (c, next) => {
  const t0 = performance.now()
  await next()
  const dur = performance.now() - t0
  c.res.headers.set("Server-Timing", `total;dur=${dur}`)
}

app.use(timing)

Três coisas que um middleware pode fazer, sozinhas ou combinadas:

  1. Modificar o request antes do handler (setar c.var, adicionar headers, validar).
  2. Encerrar a cadeia sem chamar next() — retorna uma Response ou usa um helper como c.json().
  3. Modificar a response depois do await next() — adicionar headers, transformar o body, logar tempo.

# Escopos: global, por path, por rota, por grupo

O mesmo método app.use() faz tudo, mudando apenas o que você passa antes do middleware:

escopos de middleware
// 1. Global — todas as rotas
app.use(logger())

// 2. Por padrão de path — só rotas que casam
app.use("/api/*", cors())
app.use("/admin/*", requireAdmin)

// 3. Por rota — passados como argumentos ao helper HTTP
app.get("/profile", requireAuth, (c) => c.json(c.var.user))
app.post("/posts", requireAuth, checkQuota, (c) => c.json({}, 201))

// 4. Por grupo — sub-app com seus próprios middlewares
const admin = new Hono()
admin.use(requireAdmin)          // aplica a todas as rotas do sub-app
admin.get("/users", ...)
admin.delete("/users/:id", ...)

app.route("/admin", admin)         // monta em /admin/*

Os padrões de path em app.use() seguem a mesma sintaxe do roteador (Cap 3): /api/* casa qualquer subpath, /users/:id casa o template exato. Use * liberalmente — middlewares são baratos no Hono.

# Ordem de execução

Middlewares executam na ordem em que foram registrados. Em apps com várias camadas, é fácil errar a ordem e gerar bugs sutis. A ordem canônica para uma API típica é:

ordem canônica
app.use(requestId())        // 1. ID único primeiro — todos os logs dependem dele
app.use(logger())           // 2. Logger — registra início/fim com o ID
app.use(cors())             // 3. CORS — antes de tudo que pode falhar com 401/403
app.use(secureHeaders())    // 4. Security headers — antes da response final
app.use(bodyLimit(...))      // 5. Body limit — antes de tentar ler o body
app.use("/api/*", auth())   // 6. Auth — só depois de CORS responder OPTIONS
app.use("/api/*", rateLimit()) // 7. Rate limit — depois de auth para ter o user

// Rotas — middlewares acima já rodaram
app.get("/api/users", ...)
CORS antes de auth, sempre

Browsers enviam um preflight OPTIONS antes de requests CORS — esse preflight não traz Authorization. Se você puser auth antes do CORS, todo preflight retorna 401 e o browser bloqueia o request real. CORS deve responder o preflight sem passar por auth.

# Early return — não chamando next()

O middleware controla se a cadeia continua. Quando você decide encerrar (auth falhou, rate limit excedido, body inválido), não chame next() e retorne diretamente uma resposta:

early return
const requireAuth: MiddlewareHandler = async (c, next) => {
  const token = c.req.header("authorization")
  if (!token) {
    return c.json({ error: "não autorizado" }, 401)
    // ↑ não chama next() — handler nunca executa
  }
  const user = await verify(token)
  c.set("user", user)
  await next()
}

Quando o middleware retorna sem chamar next(), todos os middlewares que estavam na descida param ali — mas os que já tinham passado pelo await next() continuam na subida normalmente. Isso permite que o logger global ainda registre o tempo do 401.

# Modificando request vs response

O posicionamento em relação ao await next() determina o que você consegue mutar:

Antes de next() — modificar request, setar c.var

middleware "descendo"
const attachUser: MiddlewareHandler = async (c, next) => {
  const user = await loadUser(c.req.header("x-user-id"))
  c.set("user", user)        // disponível em c.var.user no handler
  await next()
}

Depois de next() — modificar response, logar

middleware "subindo"
const addPoweredBy: MiddlewareHandler = async (c, next) => {
  await next()
  c.res.headers.set("X-Powered-By", "Hono")
}

// Substituir a response inteira pós-handler
const enforceJson: MiddlewareHandler = async (c, next) => {
  await next()
  if (c.res.headers.get("content-type")?.includes("text/html")) {
    c.res = c.json({ error: "apenas JSON" }, 406)
  }
}
c.res vs retornar Response

Em código antes de next(), retorne uma Response ou use c.json()/c.text() diretamente — você está construindo a resposta. Depois de next(), a resposta já existe em c.res; modifique seus headers via c.res.headers.set() ou substitua o objeto inteiro via c.res = ....

# Padrão before/after num único middleware

Métricas, tracing distribuído, contexto de banco — coisas que precisam abrir e fechar — encaixam naturalmente:

transação por request
const withTransaction: MiddlewareHandler<{ Variables: { tx: Tx } }> =
  async (c, next) => {
    const tx = await db.beginTransaction()
    c.set("tx", tx)
    try {
      await next()
      if (c.res.status >= 400) await tx.rollback()
      else                       await tx.commit()
    } catch (err) {
      await tx.rollback()
      throw err     // propaga para app.onError (Cap 11)
    }
  }

# Tratamento de erros

Exceções lançadas em qualquer middleware propagam pela cadeia normalmente — middlewares acima (na subida) ainda executam seus blocos finally, e o erro acaba em app.onError (Capítulo 11). Você raramente precisa de try/catch em handlers; centralize o tratamento.

erros propagam pela cadeia
app.use(async (c, next) => {
  try {
    await next()
  } finally {
    console.log("sempre roda — sucesso ou erro")
  }
})

app.get("/oops", () => {
  throw new Error("falhou")  // pega no app.onError
})

app.onError((err, c) => {
  return c.json({ error: err.message }, 500)
})

# Factory pattern — middlewares parametrizados

Middlewares prontos do Hono (cors(), logger(), bearerAuth({...})) seguem o padrão de factory: uma função que recebe configuração e retorna o middleware. Escreva os seus assim para deixar o uso ergonômico:

factory tipado
import type { MiddlewareHandler } from "hono"

type RateLimitOpts = { max: number; windowMs: number }

export const rateLimit = (opts: RateLimitOpts): MiddlewareHandler => {
  const counts = new Map<string, { n: number; reset: number }>()

  return async (c, next) => {
    const key = c.req.header("x-forwarded-for") ?? "anon"
    const now = Date.now()
    const slot = counts.get(key) ?? { n: 0, reset: now + opts.windowMs }

    if (now > slot.reset) { slot.n = 0; slot.reset = now + opts.windowMs }
    slot.n++
    counts.set(key, slot)

    if (slot.n > opts.max) {
      return c.json({ error: "rate limit" }, 429)
    }
    await next()
  }
}

// Uso ergonômico
app.use(rateLimit({ max: 100, windowMs: 60_000 }))
Hono 4.x · createMiddleware

Hono 4 expõe createMiddleware em hono/factory, uma forma tipada de construir factories que contribuem com Variables ao app. Usado dentro do middleware, c.set("user", ...) adiciona user ao tipo de c.var nas rotas que usam o middleware — sem precisar declarar Variables manualmente no new Hono<...>.

createMiddleware com Variables contribuídas
import { createMiddleware } from "hono/factory"

type User = { id: string; role: "admin" | "user" }

export const authMw = createMiddleware<{
  Variables: { user: User }
}>(async (c, next) => {
  const user = await verifyToken(c.req.header("authorization"))
  c.set("user", user)
  await next()
})

// Em qualquer rota: c.var.user está tipado como User automaticamente
app.get("/me", authMw, (c) => c.json(c.var.user))

# Compondo middlewares: ordem importa

Quando você compõe middlewares numa rota (app.get(path, mw1, mw2, mw3, handler)), eles formam um mini-onion em torno do handler, na ordem listada. Isso é exatamente equivalente a:

composição inline equivale a aninhamento
// Forma compacta
app.get("/x", mw1, mw2, mw3, handler)

// Equivalente conceitual:
// mw1 envolve (mw2 envolve (mw3 envolve handler))

// Ordem de execução:
// mw1 antes → mw2 antes → mw3 antes → handler → mw3 depois → mw2 depois → mw1 depois

Mantenha mentalmente esse onion ao decidir a ordem. Auth antes de validação de body (rejeita rápido sem custo de parsing). Cache antes de rate limit (não conta hits cacheados). Compress depois de tudo (compressão acontece na subida).

# Anti-padrões a evitar

  • Chamar next() duas vezes — lança Error: next() called more than once. Acontece geralmente em early returns mal escritos: if (cond) c.json(...) seguido de await next() incondicional. Use return.
  • Esquecer await antes de next() — sem await, o middleware retorna antes da cadeia terminar; código pós-next roda no momento errado e mutações em c.res não fazem efeito. Sempre await next().
  • Estado global em factories — o rate limiter do exemplo usa Map em escopo de factory. Funciona em Node single-process; em Workers (vários isolates) cada um tem seu Map. Use KV ou Durable Objects para estado real distribuído.
  • Middlewares pesados na descida sem necessidade — carregar dados que nem todo handler usa é desperdício. Carregue dentro do handler ou em middlewares por rota.

Middleware nativos

Hono vem com uma biblioteca de middlewares prontos para os casos de uso mais frequentes. # cors

Configura os headers CORS para permitir requests entre origens. Responde automaticamente a preflights (OPTIONS).

cors
import { cors } from "hono/cors"

// Permissivo (dev): aceita qualquer origem
app.use(cors())

// Produção: lista de origens e métodos explícitos
app.use("/api/*", cors({
  origin:      ["https://meuapp.com", "https://staging.meuapp.com"],
  allowMethods: ["GET", "POST", "PUT", "DELETE", "PATCH"],
  allowHeaders: ["Content-Type", "Authorization"],
  credentials:  true,   // permite cookies cross-origin
  maxAge:       86400, // cache do preflight por 24h
}))

// Origin dinâmico via função
app.use(cors({
  origin: (origin) => {
    if (origin.endsWith(".meuapp.com")) return origin
    return "https://meuapp.com"
  },
}))

# csrf

Proteção contra CSRF verificando o header Origin nos requests de mutação (POST, PUT, DELETE, PATCH). Simples e sem token — adequado para APIs que já usam CORS restrito.

csrf
import { csrf } from "hono/csrf"

app.use(csrf())  // bloqueia origins não listadas

// Whitelist explícita de origins permitidas
app.use(csrf({ origin: "https://meuapp.com" }))

// Múltiplas origens ou função
app.use(csrf({
  origin: (origin, c) => origin.endsWith(".meuapp.com"),
}))
csrf vs cors — não são a mesma coisa

cors diz ao browser quais origens podem acessar a API. csrf verifica se a origin do request é uma que você conhece. Use os dois juntos em apps que renderizam formulários HTML: CORS para requests de APIs externas, CSRF para proteger mutações vindas de formulários.

# logger

Loga método, path, status e tempo de cada request no console. Pronto para uso em desenvolvimento; em produção, substitua por um logger estruturado.

logger
import { logger } from "hono/logger"

app.use(logger())
// → GET /users 200 4ms
// → POST /login 401 2ms

// Logger customizado (por exemplo, estruturado para JSON)
app.use(logger((str, ...rest) => {
  console.log(JSON.stringify({ msg: str, ts: new Date().toISOString() }))
}))

# secureHeaders

Adiciona um conjunto conservador de headers de segurança HTTP em todas as respostas. Equivalente ao pacote helmet do Express.

secureHeaders
import { secureHeaders } from "hono/secure-headers"

// Padrão — aplica todos os headers recomendados
app.use(secureHeaders())

// Customizar CSP e outros individualmente
app.use(secureHeaders({
  contentSecurityPolicy: {
    defaultSrc:  ["'self'"],
    scriptSrc:   ["'self'", "'unsafe-inline'"],
    connectSrc:  ["'self'", "https://api.meuapp.com"],
  },
  xFrameOptions:      "DENY",          // bloqueia iframes
  referrerPolicy:     "no-referrer",
  permissionsPolicy:  { camera: [] },   // bloqueia câmera
}))
Headers aplicados por padrão

secureHeaders() sem opções aplica: X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, Strict-Transport-Security, X-XSS-Protection: 0, Referrer-Policy: no-referrer, Cross-Origin-Embedder-Policy, Cross-Origin-Opener-Policy, e Cross-Origin-Resource-Policy. Para remover um específico, passe false na opção correspondente.

# basicAuth

Implementa HTTP Basic Authentication. Adequado para proteger rotas internas (admin, healthcheck, Swagger) sem infraestrutura de token.

basicAuth

# bearerAuth

Valida o header Authorization: Bearer <token>. Simples de configurar com token fixo; aceita validação custom para tokens JWT ou API keys dinâmicas.

bearerAuth
import { bearerAuth } from "hono/bearer-auth"

// Token fixo — bom para API keys de serviço a serviço
app.use("/api/*", bearerAuth({ token: "meu-token-secreto" }))

// Múltiplos tokens válidos
app.use(bearerAuth({ token: ["token-a", "token-b"] }))

// Validação async — para JWT ou DB lookup
app.use(bearerAuth({
  verifyToken: async (token, c) => {
    const payload = await verifyJwt(token, c.env.JWT_SECRET)
    if (!payload) return false
    c.set("user", payload)
    return true
  },
}))

# requestId

Gera um ID único por request e o disponibiliza via c.get("requestId") e via header X-Request-Id na resposta. Essencial para rastreamento de logs distribuídos.

requestId

app.use(requestId())

app.get("/users", (c) => {

app.use(requestId({

# timing

Implementa o header Server-Timing (spec W3C). Permite medir e expor o tempo de partes específicas do request — visível nas DevTools do browser.

timing
import { timing, startTime, endTime } from "hono/timing"

app.use(timing())   // habilita coleta

app.get("/report", async (c) => {

  endTime(c, "db")

# bodyLimit

Rejeita requests cujo body ultrapassa o limite configurado, com 413 Content Too Large. Sempre registre antes de tentar ler o body.

bodyLimit
import { bodyLimit } from "hono/body-limit"

// Limite global de 1 MB
app.use(bodyLimit({ maxSize: 1 * 1024 * 1024 }))

// Limite maior só para upload de arquivos
app.post("/upload", bodyLimit({ maxSize: 10 * 1024 * 1024 }), async (c) => {
  const body = await c.req.parseBody()
  return c.json({ ok: true })
})

// Resposta customizada em caso de body muito grande
app.use(bodyLimit({
  maxSize:  512 * 1024,
  onError:  (c) => c.json({ error: "body muito grande" }, 413),
}))

# compress

Comprime a response com gzip ou deflate de acordo com o header Accept-Encoding do cliente. Aplique depois dos middlewares de conteúdo para comprimí-los juntos.

compress
import { compress } from "hono/compress"

app.use(compress())  // gzip por padrão se suportado

// Forçar deflate (raro)
app.use(compress({ encoding: "deflate" }))
compress em edge runtimes

Em Cloudflare Workers e Vercel Edge, a compressão é feita automaticamente pela CDN — adicionar compress() é redundante e adiciona CPU budget desnecessário. Use-o apenas em deploys Node (Docker, VPS) onde você é responsável pela compressão.

# etag

Gera e valida ETag para respostas, permitindo cache condicional com 304 Not Modified. Reduz tráfego em recursos que mudam com baixa frequência.

etag
import { etag } from "hono/etag"

app.use(etag())  // ETag fraco: W/"..."

// ETag forte (byte-a-byte idêntico)
app.use(etag({ weak: false }))

// Uso: client envia If-None-Match, servidor responde 304 se não mudou
// GET /api/config → 200 com ETag: W/"a1b2c3"
// GET /api/config [If-None-Match: W/"a1b2c3"] → 304 (sem body)

# cache

Integra com a Cache API nativa do runtime (disponível em Cloudflare Workers e alguns ambientes de edge). Armazena e serve respostas diretamente do cache, sem chegar ao handler.

cache (Workers / edge)
import { cache } from "hono/cache"

// Cache por 1 hora para GETs de /api/config
app.get("/api/config",
  cache({
    cacheName:    "config-cache",
    cacheControl: "max-age=3600, stale-while-revalidate=60",
  }),
  (c) => c.json({ feature: true })
)

// Cache key customizada (ex.: por user-agent)
app.get("/api/data",
  cache({
    cacheName:   "api-cache",
    cacheControl: "max-age=60",
    keyGenerator: (c) =>
      new URL(c.req.url).toString() + (c.req.header("accept-language") ?? ""),
  }),
  (c) => c.json({})
)
Hono 4.x · cache API

O middleware cache usa a Cache API do runtime (mesmo spec do browser). Em Cloudflare Workers, isso é a cache do CDN — respostas servidas direto da edge sem custo de CPU. Em Node, não há Cache API nativa; o middleware não faz nada sem polyfill. Para cache em Node, use Redis ou memória com uma solução customizada.

Capítulo 09

Validação com Zod

Dados do mundo externo — body, query string, path params, headers, cookies — chegam sempre como strings não confiáveis. @hono/zod-validator integra Zod diretamente no pipeline de middleware do Hono: valida, coerce e tipifica os dados de entrada antes de o handler executar, e disponibiliza o resultado via c.req.valid() com tipo completamente inferido. Se a validação falhar, a cadeia encerra ali com uma resposta de erro formatada — sem código defensivo no handler.

# Instalação

terminal
npm install zod @hono/zod-validator

# Uso básico — validando o body JSON

O pattern central é zValidator(fonte, schema) inserido como middleware antes do handler:

validação de body
import { zValidator } from "@hono/zod-validator"
import { z } from "zod"

const createUserSchema = z.object({
  name:  z.string().min(2).max(100),
  email: z.string().email(),
  age:   z.number().int().min(18).optional(),
})

app.post(
  "/users",
  zValidator("json", createUserSchema),
  (c) => {
    // tipo inferido: { name: string; email: string; age?: number }
    const { name, email, age } = c.req.valid("json")
    return c.json({ created: { name, email, age } }, 201)
  }
)

Se o body não cumprir o schema, zValidator interrompe a cadeia e retorna 400 Bad Request com os erros do Zod — o handler nunca executa. Se cumprir, c.req.valid("json") retorna o valor já parseado e tipado.

c.req.valid() nunca é undefined no handler

Quando o handler executa, a validação já passou. O TypeScript sabe disso — c.req.valid("json") retorna o tipo exato do schema, sem | undefined. Não é necessário checar ou assertar. Se você chegou ao handler, os dados são válidos.

# Fontes de validação

O primeiro argumento de zValidator indica de onde os dados vêm. As seis fontes disponíveis:

query — query string

validando query string
const paginationSchema = z.object({
  page:  z.string().regex(/^\d+$/).transform(Number).default("1"),
  limit: z.string().regex(/^\d+$/).transform(Number).default("20"),
  q:     z.string().optional(),
})

app.get("/users", zValidator("query", paginationSchema), (c) => {
  const { page, limit, q } = c.req.valid("query")
  // page e limit são number (transformados pelo Zod)
  return c.json({ page, limit, q })
})
Query params chegam como string — use .transform()

Query strings são sempre string. Para ter number tipado no handler, use .transform(Number) no schema. O Zod transforma e o TypeScript infere number automaticamente. Sem transform, page seria string mesmo que você queira um número.

param — path parameters

validando path params
const idSchema = z.object({
  id: z.string().uuid()  // garante UUID válido
})

app.get("/users/:id", zValidator("param", idSchema), async (c) => {
  const { id } = c.req.valid("param")  // id: string (UUID garantido)
  const user = await db.findById(id)
  if (!user) return c.notFound()
  return c.json(user)
})

header — headers HTTP

validando headers
const apiKeySchema = z.object({
  "x-api-key": z.string().min(32),
})

app.use("/api/*", zValidator("header", apiKeySchema))

cookie — cookies da requisição

validando cookies
const sessionSchema = z.object({
  sessionId: z.string().min(1),
})

app.get("/dashboard", zValidator("cookie", sessionSchema), (c) => {
  const { sessionId } = c.req.valid("cookie")
  return c.json({ sessionId })
})

form — form-data e url-encoded

validando formulário
const loginSchema = z.object({
  email:    z.string().email(),
  password: z.string().min(8),
})

app.post("/login", zValidator("form", loginSchema), async (c) => {
  const { email, password } = c.req.valid("form")
  return c.json({ ok: true })

# Múltiplas fontes na mesma rota

Encadeie vários zValidator para validar mais de uma fonte. Cada um acessa sua própria chave em c.req.valid():

múltiplas fontes
app.put(
  "/posts/:id",
  zValidator("param", z.object({ id: z.string().uuid() })),
  zValidator("query", z.object({ draft: z.enum(["true", "false"]).optional() })),
  zValidator("json",  z.object({ title: z.string(), body: z.string() })),
  async (c) => {
    const { id }     = c.req.valid("param")
    const { draft }  = c.req.valid("query")
    const { title, body } = c.req.valid("json")

  }

# Hook customizado — onError e validação parcial

Por padrão, falha na validação retorna 400 com os erros do Zod como JSON. O terceiro argumento do zValidator é um hook chamado com o resultado da validação — você pode customizar completamente o comportamento:

hook de validação
app.post(
  "/users",
  zValidator("json", createUserSchema, (result, c) => {
    if (!result.success) {
      // Formatar erros ao gosto da API
      const errors = result.error.issues.map((i) => ({
        field:   i.path.join("."),
        message: i.message,
        code:    i.code,
      }))
      return c.json({ error: "dados inválidos", errors }, 422)
    }
    // Se não retornar nada, o Hono continua para o próximo middleware
  }),
  (c) => {
    const data = c.req.valid("json")
    return c.json({ created: data }, 201)
  }
)
422 vs 400 para erros de validação

O status 400 Bad Request (padrão do zValidator) é tecnicamente correto, mas 422 Unprocessable Entity é semanticamente mais preciso para falhas de validação de dados: a sintaxe HTTP estava certa, mas o conteúdo não passou na validação de negócio. O hook permite escolher o status que faz sentido para a sua API.

# Validação assíncrona com refine

Para validações que precisam consultar o banco (unicidade de e-mail, existência de recurso), use z.refine() ou z.superRefine(). Como o Zod roda parseAsync internamente, zValidator suporta isso nativamente:

const uniqueEmailSchema = z.object({
  email: z.string().email(),

  async (data) => {
    const existing = await db.findByEmail(data.email)
    return !existing
  },
  { message: "e-mail já cadastrado", path: ["email"] }
)

app.post("/users", zValidator("json", uniqueEmailSchema), async (c) => {
  const { email } = c.req.valid("json")
  return c.json({ email }, 201)
})
refine com DB em validação — cuidado

Consultas de unicidade em refine rodam em toda chamada, incluindo caminhos de erro anteriores. Prefira validar unicidade dentro do handler, após checar o resto do schema, para ter melhor controle de performance e de mensagens de erro — especialmente em rotas de alta frequência.

# Validador customizado

Quando as bibliotecas acima não servem (biblioteca interna, validação proprietária, ou só curiosidade), você pode criar um adapter diretamente via validator de hono/validator. A API é baixo nível: você recebe o valor bruto, valida como quiser, e retorna o valor ou uma Response de erro:

validador customizado com validator()
import { validator } from "hono/validator"

app.post(
  "/users",
  validator("json", (value, c) => {
    // value é o body JSON parseado (unknown)
    if (typeof value !== "object" || !value) {
      return c.json({ error: "body inválido" }, 400)
    }
    const v = value as { name?: unknown; email?: unknown }
    if (typeof v.name !== "string" || v.name.length < 2) {
      return c.json({ error: "name inválido" }, 422)
    }
    // Retornar o valor é registrá-lo em c.req.valid("json")
    return { name: v.name, email: v.email as string }
  }),
  (c) => {
    const data = c.req.valid("json")
    return c.json({ created: data }, 201)
  }
)

Criando um adapter reutilizável para qualquer biblioteca

Para empacotar uma biblioteca nova como adapter oficial, siga o padrão dos adapters existentes — uma função que recebe fonte e schema e retorna um MiddlewareHandler:

src/validators/myValidator.ts
import { validator } from "hono/validator"
import type { ValidationTargets } from "hono"

// Tipo genérico de "schema" de qualquer biblioteca
type MySchema<T> = {
  parse(input: unknown): T    // lança em caso de erro
}

export function myValidator<T>(
  target: keyof ValidationTargets,
  schema: MySchema<T>
) {
  return validator(target, (value, c) => {
    try {
      return schema.parse(value) as T
    } catch (err) {
      return c.json({
        error: "validação falhou",
        detail: err instanceof Error ? err.message : String(err),
      }, 400)
    }
  })
}

Capítulo 11

Tratamento de erros

Toda API real falha — entrada inválida, banco fora, terceiro lento, bug no código. A diferença entre uma API profissional e uma amadora não é evitar falhas, é como elas são comunicadas: shape consistente de resposta, status code semanticamente correto, sem vazar stack trace, com identificador rastreável. Hono oferece três primitivos para isso — HTTPException, app.onError e app.notFound — e o modelo onion já visto no Capítulo 7 faz o restante.

# A virada do tratamento centralizado

Em Express, é comum ver código assim em cada handler:

antipadrão — tratamento espalhado
app.post("/users", async (req, res) => {
  try {
    const user = await createUser(req.body)
    res.status(201).json(user)
  } catch (err) {
    if (err.code === "DUPLICATE") return res.status(409).json({...})
    if (err.code === "INVALID")   return res.status(422).json({...})
    res.status(500).json({ error: "internal" })
  }
})

Multiplique isso por 50 endpoints e três programadores e o resultado é previsível: dezenas de variações de "shape de erro", status codes inconsistentes, logging esparso. Em Hono, a abordagem é inversa: handlers lançam, middleware central traduz.

o mesmo, com tratamento centralizado
// O handler só lança — sem try/catch
app.post("/users", async (c) => {
  const user = await createUser(await c.req.json())
  return c.json(user, 201)
})

// Tradução de erros em um único lugar
app.onError((err, c) => {
  if (err instanceof DuplicateError) return c.json({ error: "duplicado" }, 409)
  if (err instanceof HTTPException)   return err.getResponse()
  console.error(err)
  return c.json({ error: "internal" }, 500)
})
Regra de ouro: o handler não trata, ele lança

Tudo que não é caso de sucesso deve sair do handler como throw. O app.onError é onde a tradução acontece. Quanto mais código de tratamento de erro nos handlers, mais inconsistência você acumula com o tempo.

# HTTPException — o erro estruturado do Hono

HTTPException é uma classe que carrega: status code, mensagem, e opcionalmente uma Response customizada. Quando lançada em qualquer middleware ou handler, é capturada pelo Hono e convertida em resposta HTTP — sem passar pelo app.onError a menos que você queira.

HTTPException — uso básico
import { HTTPException } from "hono/http-exception"

app.get("/users/:id", async (c) => {
  const user = await db.findUser(c.req.param("id"))
  if (!user) throw new HTTPException(404, { message: "usuário não encontrado" })
  return c.json(user)
})

// 401 com header WWW-Authenticate
throw new HTTPException(401, {
  message: "token expirado",
  res: new Response(JSON.stringify({ error: "token expirado" }), {
    status: 401,
    headers: {
      "Content-Type":     "application/json",
      "WWW-Authenticate":  'Bearer error="invalid_token"',
    },
  }),
})

// Causa interna (não vai pro cliente) — útil para log
throw new HTTPException(500, {
  message: "falha ao processar pedido",
  cause:   originalDbError,  // fica acessível em err.cause no onError
})

Quando você passa res customizado, Hono devolve essa Response exata — você tem controle total. Quando passa apenas message, Hono constrói a Response automaticamente com o status e a mensagem como body texto.

# app.onError — o tradutor global

app.onError recebe a função que processa qualquer erro não tratado durante o ciclo de request — incluindo HTTPException, exceções de validação, e qualquer Error não capturado. É chamado exatamente uma vez por request com falha.

app.onError — assinatura completa
app.onError((err, c) => {
  // err: Error  (incluindo HTTPException e subclasses)
  // c:   Context — para construir a Response

  if (err instanceof HTTPException) {
    // getResponse() devolve a Response que o HTTPException construiu
    return err.getResponse()
  }

  // Erros inesperados — log e mensagem genérica
  console.error("unhandled:", err)
  return c.json({ error: "internal" }, 500)
})

Detalhe importante: se você não chamar err.getResponse() em HTTPException, Hono ainda vai serializá-la com o status e a mensagem padrão — mas você perde a Response customizada do res opcional. Sempre delegue ao getResponse() quando o erro for um HTTPException.

Padrão completo: switch por tipo

onError com discriminação por tipo
import { HTTPException } from "hono/http-exception"
import { ZodError }       from "zod"

app.onError((err, c) => {
  const requestId = c.get("requestId") ?? "unknown"

  // 1. HTTPException (incluindo subclasses NotFoundError etc.)
  if (err instanceof HTTPException) {
    return err.getResponse()
  }

  // 2. Erros de validação Zod escapados
  if (err instanceof ZodError) {
    return c.json({
      error:  "validação falhou",
      issues: err.issues,
      requestId,
    }, 422)
  }

  // 3. Falhas de banco
  if (err instanceof DatabaseError) {
    logger.error({ err, requestId }, "db failure")
    return c.json({ error: "serviço indisponível", requestId }, 503)
  }

  // 4. Tudo o mais — fallback
  logger.error({ err, requestId }, "unhandled")
  return c.json({ error: "internal", requestId }, 500)
})
Shape de erro padrão

Defina um shape de resposta de erro para toda a API — e respeite-o em onError. Um shape comum: { error: string, code?: string, requestId?: string, issues?: any[] }. Clientes (incluindo o cliente RPC tipado do Hono) sabem o que esperar; documentação OpenAPI fica trivial.

# app.notFound — 404 customizado

Para requests que não casaram com nenhuma rota, Hono devolve 404 Not Found com body de texto. Para customizar, registre um handler global de 404:

app.notFound
app.notFound((c) => {
  return c.json({
    error: "recurso não encontrado",
    path:  c.req.path,
  }, 404)
})

// Em handlers, c.notFound() delega para este handler global
app.get("/users/:id", async (c) => {
  const user = await db.findUser(c.req.param("id"))
  if (!user) return c.notFound()  // usa o app.notFound acima
  return c.json(user)
})
notFound vs throw 404

c.notFound() e throw new HTTPException(404) têm semânticas ligeiramente diferentes: c.notFound() chama o handler de app.notFound (formatação centralizada para "recurso não existe"); HTTPException(404) passa pelo app.onError com a mensagem customizada do throw. Use c.notFound() para "rota não bate" e HTTPException para "recurso específico não existe com este ID".

# Propagação de erros pela cadeia onion

O modelo onion (Capítulo 7) é central no tratamento de erros. Quando algo lança no handler ou em qualquer middleware, o erro sobe pela cadeia: cada middleware que estava aguardando await next() recebe a oportunidade de capturar (via try/catch), modificar ou propagar adiante. Se ninguém capturar, o app.onError recebe.

propagação na cadeia
// Middleware externo: captura para garantir cleanup
app.use(async (c, next) => {
  const tx = await db.beginTransaction()
  c.set("tx", tx)
  try {
    await next()
    await tx.commit()
  } catch (err) {
    await tx.rollback()
    throw err      // propaga para app.onError tratar a resposta
  }
})

// Middleware mais interno: adiciona request-id ao erro antes de subir
app.use(async (c, next) => {
  try {
    await next()
  } catch (err) {
    if (err instanceof Error) {
      (err as any).requestId = c.get("requestId")
    }
    throw err
  }
})

// Handler: lança sem se preocupar com cleanup ou ID
app.post("/order", async (c) => {
  await processOrder(c.var.tx)  // se falhar, transação faz rollback automático
  return c.json({ ok: true })
})

Note que try/catch em middleware é diferente de resolver o erro — você ainda precisa throw de novo para o app.onError receber. Capturar sem propagar significa "este erro é meu, não conta como falha" — só faça isso quando for de fato isso o que você quer.

# O que NÃO é capturado

O app.onError captura erros lançados dentro do ciclo de request. Há três casos onde ele não vê o problema:

  • Promises não-aguardadas — somePromise.then(...) ou void asyncFn() dentro do handler. Use c.executionCtx.waitUntil() ou await; senão o erro vira unhandled rejection.
  • Erros em setTimeout/setInterval — handlers desses callbacks vivem fora do ciclo do request. Capture localmente.
  • Erros síncronos em event handlers de streams — para streams retornados via c.body()/streamSSE(), qualquer throw dentro da função de stream após o início precisa ser tratado dentro da própria função.

# Logging seguro — não vazar para o cliente

Stack traces, mensagens de banco e detalhes internos não devem chegar ao cliente — vão para o log. A separação é:

log interno vs resposta externa
app.onError((err, c) => {
  const requestId = c.get("requestId") ?? crypto.randomUUID()

  // 1. Log completo (interno) — toda a riqueza
  logger.error({
    requestId,
    method:  c.req.method,
    path:    c.req.path,
    err: {
      name:    err.name,
      message: err.message,
      stack:   err.stack,
      cause:   (err as any).cause,
    },
  }, "request failed")

  // 2. Resposta externa — mínimo necessário + requestId para correlacionar
  if (err instanceof HTTPException) return err.getResponse()
  return c.json({ error: "internal", requestId }, 500)
})

O cliente recebe { "error": "internal", "requestId": "abc-123" }. Quando alguém reportar o problema, você usa o requestId para encontrar o log completo. Sem expor stack, sem leak.

Nunca exponha err.message diretamente em 5xx

Mensagens de erro do banco frequentemente incluem informações sensíveis (nomes de colunas, valores rejeitados, queries fragmentadas). Em erros 4xx esperados (validação, autorização) usar a mensagem é seguro. Em 5xx genéricos, devolva sempre uma mensagem fixa e logue a real.

# Erros assíncronos esquecidos

Um caso comum que escapa do onError: chamadas assíncronas que você dispara sem await. Em Workers, sem o waitUntil, a Promise é abandonada quando o isolate sai do request:

o problema
app.post("/event", async (c) => {
  // ❌ Fogo e esquece — se logEvent lançar, ninguém captura
  logEvent(await c.req.json())

  return c.json({ ok: true })
})

// ✅ Correto — waitUntil pega o erro e o runtime registra
app.post("/event", async (c) => {
  const body = await c.req.json()
  c.executionCtx.waitUntil(logEvent(body).catch(logger.error))
  return c.json({ ok: true })
})

  return c.json({ error: "internal" }, 500)
})

JSX e renderização

Hono tem suporte nativo a JSX no servidor — sem build step separado, sem React, sem hydration obrigatória. Você escreve componentes TypeScript que renderizam HTML diretamente na resposta. Capítulo 13

RPC type-safe

A maioria dos projetos full-stack tem uma fronteira entre servidor e cliente onde os tipos desaparecem: você define POST /users no servidor, e no cliente escreve fetch("/users", { body: JSON.stringify({...}) }) sem nenhuma garantia de que o shape bate. Hono resolve isso com hc() — um cliente HTTP gerado a partir dos tipos das suas rotas. Sem geração de código, sem OpenAPI manual, sem tRPC: os tipos fluem do servidor para o cliente via TypeScript puro.

# O problema que o RPC resolve

Considere a fronteira clássica:

sem RPC — fronteira sem tipos
// Servidor define:
app.post("/users", zValidator("json", createUserSchema), (c) => {
  return c.json({ id: "u_1", name: "Ana" })
})

// Cliente chama: string arbitrária, body any, resposta any
const res = await fetch("/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Ana", emal: "ana@b.com" })  // typo: emal
})
const data = await res.json()  // tipo: any

Três problemas em evidência: (1) o typo emal passa em tempo de compilação; (2) a string "/users" não tem relação com a rota do servidor; (3) res.json() retorna any. Refatorar a rota não quebra o cliente. Com RPC, os três problemas desaparecem.

# Exportando o AppType

O mecanismo central é exportar o tipo da instância do app (não o app em si). O tipo carrega o shape de todas as rotas: método, path, validators, e tipo de retorno.

src/index.ts (servidor)
import { Hono } from "hono"
import { zValidator } from "@hono/zod-validator"
import { z } from "zod"

const app = new Hono()
  .get("/users", (c) => {
    return c.json([{ id: "u_1", name: "Ana" }])
  })
  .post("/users",
    zValidator("json", z.object({ name: z.string(), email: z.string().email() })),
    (c) => {
      const body = c.req.valid("json")
      return c.json({ id: "u_new", ...body }, 201)
    }
  )

// Exportar o tipo — não o valor runtime
export type AppType = typeof app
export default app
Method chaining é obrigatório para RPC

Para o TypeScript inferir os tipos de todas as rotas no AppType, elas precisam estar encadeadas num único valor. Se você registrar rotas via app.get(...); app.post(...) (imperativos separados), o tipo de typeof app só carrega a última chamada. Use new Hono().get(...).post(...) ou monte sub-apps via app.route() (que também preserva tipos em Hono 4).

# hc() — o cliente tipado

hc() recebe a URL base e o AppType como generic. Retorna um objeto proxy cujas chaves espelham as rotas — com tipo completo em cada nível:

src/client.ts (cliente)
import { hc } from "hono/client"
import type { AppType } from "../server/index"  // só o tipo, zero runtime

const client = hc<AppType>("http://localhost:3000")

// GET /users — retorno tipado como { id: string; name: string }[]
const listRes = await client.users.$get()
const users   = await listRes.json()   // tipo: { id: string; name: string }[]

// POST /users — body checado em compilação
const createRes = await client.users.$post({
  json: { name: "Ana", email: "ana@b.com" },  // tipo exato do schema Zod
  // json: { name: "Ana", emal: "..." }  ← erro de compilação!
})
const novo = await createRes.json()  // { id: string; name: string; email: string }

O prefixo $ converte o método HTTP em nome de método do cliente: $get, $post, $put, $patch, $delete. O argumento é um objeto com as fontes de dados tipadas — json, query, param, form, header, cookie.

# Tratamento de resposta com status

O cliente RPC preserva o status code na Response — você pode fazer early return por status sem perder o tipo:

  const err = await res.json()  // tipo de erro se o status for erro
  console.error(err)
  return
}

const data = await res.json()    // { id: string; name: string; email: string }

// Shorthand para uso em React Query / SWR
async function fetchUsers() {
  const res = await client.users.$get()
  if (!res.ok) throw new Error(await res.text())
  return res.json()  // tipado
}

# Limitações e edge cases

  • Retorno do handler deve ser c.json() para o tipo ser inferido. Se você retornar new Response() diretamente, o tipo de .json() no cliente será unknown.
  • Validators obrigatórios para tipagem de body: sem zValidator (ou equivalente), o campo json do cliente aceita qualquer coisa. Validators são o contrato.
  • Middleware que muda o body não é refletido: se um middleware altera a resposta, o tipo do cliente ainda vê o que o handler declarou. O tipo é estático.
  • Rotas com app.on(["GET","POST"], ...): geram ambos $get e $post no cliente corretamente.
  • Headers e cookies no cliente RPC: tipados quando há zValidator("header") / zValidator("cookie") na rota. Sem validator, aceitam qualquer objeto.
hc() não é um fetch polyfill

hc() usa o fetch global do ambiente. Em Node antes da v18 sem polyfill, ele não funciona. Em ambientes com fetch nativo (browsers modernos, Bun, Deno, Node 18+), funciona sem configuração. Para testes em Node 16, injete um polyfill como undici antes de chamar hc().

Capítulo 14

WebSockets

Hono oferece uma API unificada de WebSocket via upgradeWebSocket — a mesma interface funciona em Cloudflare Workers, Deno, Bun e (com o adapter @hono/node-ws) em Node.js. Você define handlers de eventos (onOpen, onMessage, onClose, onError) e o Hono cuida do upgrade HTTP→WS por runtime. Este capítulo cobre o setup em cada runtime, padrões de broadcast e autenticação no handshake.

# API universal — upgradeWebSocket

O ponto de entrada é sempre o mesmo: upgradeWebSocket retorna um middleware que intercepta o request HTTP, faz o upgrade e entrega o objeto ws (WebSocket server-side) nos callbacks.

estrutura básica
import { upgradeWebSocket } from "hono/websocket"  // Deno, Bun, Workers
// import { upgradeWebSocket } from "@hono/node-ws"    // Node.js

app.get(
  "/ws",
  upgradeWebSocket((c) => ({
    onOpen(evt, ws) {
      console.log("conexão aberta")
      ws.send("bem-vindo!")
    },
    onMessage(evt, ws) {
      const msg = typeof evt.data === "string"
        ? evt.data
        : new TextDecoder().decode(evt.data as ArrayBuffer)
      console.log("recebido:", msg)
      ws.send(`eco: ${msg}`)
    },
    onClose(evt, ws) {
      console.log("conexão fechada, código:", evt.code)
    },
    onError(evt, ws) {
      console.error("ws error", evt)
    },
  }))
)

O factory recebe c — o contexto da requisição de upgrade — o que permite ler query params, headers e variáveis de middleware antes de estabelecer a conexão. O retorno é o objeto de handlers do WebSocket.

# Node.js com @hono/node-ws

Em Node, o adapter @hono/node-ws faz a ponte entre o WebSocket nativo do Node e a API do Hono. A diferença está no setup do servidor — o handler é idêntico.

})))

// 3. Iniciar o servidor e injetar o suporte a WS

injectWebSocket(server)  // vincula o servidor HTTP ao handler WS

console.log("Servidor WS em ws://localhost:3000/ws")
Por que injectWebSocket?

O Node não faz upgrade de WebSocket automaticamente — é necessário escutar o evento "upgrade" no servidor HTTP. injectWebSocket faz exatamente isso: adiciona o listener ao server retornado por serve(). Sem ele, o cliente recebe 426 Upgrade Required e a conexão não sobe.

# Autenticação no handshake

O WebSocket não envia headers customizados no upgrade (limitação do browser). O padrão é autenticar via query param ou cookie — ambos acessíveis no c que chega ao factory:

auth via query token
app.get(
  "/ws",
  async (c, next) => {
    // Middleware de auth antes do upgrade
    const token = c.req.query("token")
    if (!token) return c.json({ error: "token obrigatório" }, 401)
    const user = await verifyToken(token)
    if (!user) return c.json({ error: "inválido" }, 403)
    c.set("user", user)
    await next()
  },
  upgradeWebSocket((c) => {
    const user = c.var.user  // disponível via c.var
    return {
      onOpen(_, ws) {
        ws.send(`olá, ${user.name}!`)
      },
      onMessage(evt, ws) {
        ws.send(evt.data)
      },
    }
  })
)
Auth por cookie — alternativa mais segura

Browsers enviam cookies automaticamente no handshake WebSocket quando a URL é do mesmo domínio. Use getCookie(c, "session") no middleware de auth antes do upgradeWebSocket. Isso evita expor o token na URL (que aparece em logs de servidor).

# Broadcast — enviando para múltiplas conexões

O Hono não tem broker de WebSocket embutido — você gerencia conexões numa estrutura de dados. O padrão mais simples é um Set de clientes no módulo:

broadcast com Set
import type { WSContext } from "hono/websocket"

// Estado compartilhado entre handlers (atenção: por isolate em Workers)
const clients = new Set<WSContext>()

app.get("/ws", upgradeWebSocket((c) => ({
  onOpen(_, ws) {
    clients.add(ws)
    broadcast(`usuário entrou (total: ${clients.size})`)
  },
  onMessage(evt, ws) {
    // Retransmite para todos exceto o remetente
    const msg = evt.data as string
    for (const client of clients) {
      if (client !== ws && client.readyState === WebSocket.OPEN) {
        client.send(msg)
      }
    }
  },
  onClose(_, ws) {
    clients.delete(ws)
    broadcast(`usuário saiu (total: ${clients.size})`)
  },
})))

function broadcast(msg: string) {
  for (const ws of clients) {
    if (ws.readyState === WebSocket.OPEN) ws.send(msg)
  }
}

# Salas (rooms)

Para separar clientes em grupos (canais, salas de chat), use um Map de salas:

rooms com Map
import type { WSContext } from "hono/websocket"

const rooms = new Map<string, Set<WSContext>>()

app.get("/ws/:room", upgradeWebSocket((c) => {
  const roomId = c.req.param("room")

  return {
    onOpen(_, ws) {
      if (!rooms.has(roomId)) rooms.set(roomId, new Set())
      rooms.get(roomId)!.add(ws)
    },
    onMessage(evt, ws) {
      for (const client of rooms.get(roomId) ?? []) {
        if (client.readyState === WebSocket.OPEN) client.send(evt.data)
      }
    },
    onClose(_, ws) {
      const room = rooms.get(roomId)
      room?.delete(ws)
      if (room?.size === 0) rooms.delete(roomId)
    },
  }
}))

# streamSSE() — Server-Sent Events

SSE é o protocolo ideal para notificações push unidirecionais do servidor para o cliente. O browser reconecta automaticamente; cada evento tem data, event (opcional), id (opcional) e retry (opcional).

streamSSE básico
import { streamSSE } from "hono/streaming"

app.get("/events", (c) =>
  streamSSE(c, async (sse) => {
    let id = 0
    while (true) {
      await sse.writeSSE({
        data:  JSON.stringify({ ts: Date.now(), msg: "ping" }),
        event: "heartbeat",
        id:    String(++id),
      })
      await sse.sleep(5000)

      // Encerrar quando o cliente desconectar
      if (sse.aborted) break
    }
  })
)
consumindo SSE no browser

})

SSE vs WebSocket — quando escolher

SSE é unidirecional (servidor → cliente), mais simples, reconecta automaticamente, funciona sobre HTTP/1.1 e HTTP/2, e é suportado por todo proxy HTTP. WebSocket é bidirecional e tem menor latência, mas requer infraestrutura de upgrade. Use SSE para notificações, feeds e streaming de AI; use WebSocket para chat, jogos e colaboração em tempo real.

# Backpressure em edge runtimes

Backpressure e CPU budget

Em Cloudflare Workers, o CPU budget (~10 ms free / 30 ms paid por request) continua consumindo durante o streaming — mesmo que o cliente leia devagar. Se você usa await s.sleep() ou await em geral, o Workers "hiberna" nesse período e não consome CPU, o que permite streams longos. Evite loops tight (sem await) — consomem budget rapidamente. No Deno e Bun, não há limite de CPU, mas o backpressure é tratado pelo runtime nativo via ReadableStreamDefaultController.desiredSize.

Cookies, JWT e auth

Autenticação é o sistema que prova "quem é o usuário"; autorização decide "o que ele pode fazer". Hono fornece primitivos para os dois: cookies (com helpers de assinatura HMAC), JWT (com suporte a HS256, RS256 e mais), e os middlewares basicAuth/bearerAuth já vistos. Este capítulo monta o quadro completo — modelo mental de quando usar cada um, como combinar cookies e tokens em produção, e os padrões consagrados de refresh, logout e revogação.

# Sessão vs JWT — o trade-off central

Duas filosofias coexistem no mundo da auth web:

  • Sessão (stateful): o servidor guarda dados do usuário (em Redis, banco, memória) e devolve ao cliente um identificador opaco (cookie de session ID). Cada request o servidor consulta o store para ressuscitar a sessão. Revogar é trivial — basta apagar a entrada no store.
  • JWT (stateless): o servidor não guarda nada. Devolve um token assinado que carrega os dados do usuário. Cada request o servidor verifica a assinatura — sem I/O. Revogar é o ponto fraco: se o token vazou, ele vale até expirar.

A escolha não é dogmática:

Use sessão quando...Use JWT quando...
Revogação imediata é crítica (banking, dados sensíveis)Performance e escala horizontal são prioridade
Você tem um banco/Redis confiável próximoO serviço é stateless e pode rodar no edge
App web monolítico com mesmo domínioAPI consumida por múltiplos clientes (web, mobile, CLI)
Permissões mudam dinamicamente em runtimePermissões são estáveis dentro do TTL do token
A escolha pragmática: híbrido

Apps reais frequentemente combinam: refresh token longo (gerenciado como sessão, em DB ou Redis) emite access tokens JWT de curta duração. O JWT carrega permissões para chamadas rápidas; o refresh permite revogação. Você ganha o melhor dos dois — esse é o padrão coberto adiante neste capítulo.

# Signed cookies — proteção contra adulteração

Um cookie comum pode ser editado pelo cliente — basta inspecionar e mudar o valor no DevTools. Signed cookies anexam um HMAC do conteúdo: se o cliente editar, a verificação falha. Não criptografia: o conteúdo continua legível, mas não é mais modificável sem detecção.

# JWT — estrutura e claims

Um JWT é uma string de três partes separadas por ponto: header.payload.signature, cada uma em base64url. Quando decodificado:

anatomia de um JWT
// Header — algoritmo de assinatura
{ "alg": "HS256", "typ": "JWT" }

// Payload — claims (declarações sobre o usuário)
{
  "sub":   "u_123",             // subject (ID do usuário)
  "name":  "Ana",
  "role":  "admin",
  "iat":   1701000000,          // issued at (timestamp)
  "exp":   1701003600,          // expires at (timestamp)
  "iss":   "meuapp.com"          // issuer (opcional)
}

// Signature — HMAC(header + "." + payload, secret) ou RSA assinatura

Claims começando com 3 letras (sub, iat, exp, iss, aud, jti, nbf) são registrados (RFC 7519). Os outros são livres — você define para o seu domínio (role, org_id, etc.).

# hono/jwt — sign e verify

criando e verificando JWT
import { sign, verify, decode } from "hono/jwt"

const SECRET = "sua-chave-aleatória-de-256-bits"  // usar env var em produção

// Assinar — async, retorna o token como string
const token = await sign(
  {
    sub:  "u_123",
    name: "Ana",
    role: "admin",
    exp:  Math.floor(Date.now() / 1000) + 60 * 60,  // 1h
  },
  SECRET,
  "HS256"  // algoritmo (default HS256 se omitido)
)

// Verificar — lança se assinatura inválida ou expirado
try {
  const payload = await verify(token, SECRET, "HS256")
  console.log(payload.sub, payload.role)
} catch (err) {
  // JwtTokenExpired, JwtTokenInvalid, JwtTokenSignatureMismatched...
  console.error("token inválido:", err)
}

// Decode sem verificar — útil para debug, NUNCA para auth
const { header, payload } = decode(token)
decode() não autentica

decode apenas faz base64-decode das partes — não verifica a assinatura. Nunca confie em dados de decode para autorização. Sempre use verify em qualquer fluxo de auth real.

# O padrão completo: access + refresh tokens

Em produção, a solução robusta combina dois tokens com tempos de vida muito diferentes:

  • Access token — JWT curto (15 min a 1 h), enviado em toda request, verificado sem I/O.
  • Refresh token — opaco e longo (7 dias a meses), guardado em DB ou Redis, usado apenas para emitir novos access tokens. Pode ser revogado.
fluxo access + refresh
import { sign, verify } from "hono/jwt"
import { setCookie, getCookie, deleteCookie } from "hono/cookie"

const ACCESS_TTL  = 15 * 60          // 15 min
const REFRESH_TTL = 7 * 24 * 60 * 60 // 7 dias

async function issueAccessToken(user: User, secret: string) {
  return sign({
    sub:  user.id,
    role: user.role,
    exp:  Math.floor(Date.now() / 1000) + ACCESS_TTL,
  }, secret)
}

// 1. Login: emite ambos
app.post("/login", async (c) => {
  const user = await authenticate(await c.req.json())
  if (!user) return c.json({ error: "inválido" }, 401)

  const accessToken  = await issueAccessToken(user, c.env.JWT_SECRET)
  const refreshToken = crypto.randomUUID()  // opaco — guardado em DB

  await c.env.DB.storeRefreshToken(refreshToken, user.id, REFRESH_TTL)

  setCookie(c, "access_token", accessToken,
    { httpOnly: true, secure: true, sameSite: "Lax", maxAge: ACCESS_TTL, path: "/" })
  setCookie(c, "refresh_token", refreshToken,
    { httpOnly: true, secure: true, sameSite: "Lax", maxAge: REFRESH_TTL, path: "/auth" })

  return c.json({ ok: true })
})

// 2. Refresh: troca o refresh_token por um access_token novo
app.post("/auth/refresh", async (c) => {
  const rt = getCookie(c, "refresh_token")
  const userId = rt ? await c.env.DB.lookupRefreshToken(rt) : null
  if (!userId) return c.json({ error: "expirado" }, 401)

  const user = await c.env.DB.getUser(userId)
  const newAccess = await issueAccessToken(user, c.env.JWT_SECRET)
  setCookie(c, "access_token", newAccess,
    { httpOnly: true, secure: true, sameSite: "Lax", maxAge: ACCESS_TTL, path: "/" })
  return c.json({ ok: true })
})

// 3. Logout: invalida refresh no DB e limpa cookies
app.post("/logout", async (c) => {
  const rt = getCookie(c, "refresh_token")
  if (rt) await c.env.DB.deleteRefreshToken(rt)
  deleteCookie(c, "access_token",  { path: "/" })
  deleteCookie(c, "refresh_token", { path: "/auth" })
  return c.json({ ok: true })
})

Note três decisões importantes: o refresh tem path: "/auth" (não vai em todo request), o access tem TTL curto (limita janela de exploração se vazar), e o logout revoga o refresh no DB (a única forma de "matar" a sessão antes do TTL).

# Autorização baseada em role/permission

Com o payload do JWT em c.var.jwtPayload, autorização é só um middleware:

import { HTTPException } from "hono/http-exception"

function requireRole(role: string): MiddlewareHandler {
  return async (c, next) => {
    const payload = c.get("jwtPayload")
    if (payload?.role !== role) {
      throw new HTTPException(403, { message: "sem permissão" })
    }
    await next()
  }
}

# Pegadinhas comuns

  • Secret no código — JWT_SECRET deve vir de env vars/secrets do runtime, nunca commitado. Em Workers: secret binding. Em Node: process.env.
  • Token grande no cookie — JWT cresce com cada claim. Headers de cookie têm limite (~4 KB total). Mantenha payload mínimo — apenas sub e o que muda raramente.
  • Confiar em claims sem ressuscitar — para dados críticos (saldo, plano de assinatura), busque do DB usando sub. JWT é só identidade, não estado do usuário.
  • Não validar exp — verify do hono/jwt já valida; mas se você usar decode para outra coisa, lembre que decode ignora exp.
  • Logout no JWT puro — se você não tem refresh + DB, a única forma de "deslogar" é o cliente apagar o token. Em casos críticos (banking), use uma denylist de tokens revogados (Redis) consultada no middleware.
Hono 4.x · jwt edge runtimes

O hono/jwt usa a Web Crypto API — não depende de bibliotecas Node-only. Funciona idêntico em Workers, Vercel Edge, Bun, Deno e Node 18+. HS256 é o mais rápido (verifica em ~50 μs); RS256 e PS256 também são suportados sem polyfill.

Capítulo 19

Adapters de runtime

Hono tem uma promessa central: "escreva uma vez, rode em qualquer runtime que entenda fetch". A promessa é real, mas não absoluta. Cada adapter introduz convenções, limitações e oportunidades próprias — Workers tem bindings e CPU budget, Node tem process.env e filesystem, Lambda tem cold start e eventos. Este capítulo é o mapa dessas diferenças: o que muda entre adapters, o que se preserva, e como estruturar o código para que portar de um para outro seja questão de minutos, não dias.

# O modelo central — app.fetch

Todo adapter, no fundo, faz a mesma coisa: converter o evento de request do runtime para um Request padrão e invocar app.fetch(req, env, executionCtx). O retorno — uma Response — é então traduzido de volta para o formato esperado pelo runtime.

o contrato universal
// app.fetch tem essa assinatura em todos os adapters
type AppFetch = (
  request:       Request,
  env?:          unknown,           // bindings/vars do runtime
  executionCtx?: ExecutionContext   // waitUntil, passThroughOnException
) => Promise<Response>

// O adapter é a ponte runtime ↔ app.fetch

O que muda entre adapters é o entorno: como você sobe o servidor, de onde vêm as variáveis de ambiente, quais APIs estão disponíveis, quanto tempo de CPU você pode usar. O handler nunca muda.

# Node.js — @hono/node-server

O runtime mais familiar e o mais permissivo. Tudo do Node está disponível: fs, http, net, process, worker_threads, bibliotecas nativas com bindings C++.

setup Node
import { serve } from "@hono/node-server"
import { serveStatic } from "@hono/node-server/serve-static"
import app from "./app"

// Servir arquivos estáticos do disco
app.use("/static/*", serveStatic({ root: "./public" }))

const server = serve({
  fetch:     app.fetch,
  port:      3000,
  hostname:  "0.0.0.0",         // importante em Docker
}, (info) => {
  console.log(`servidor: http://localhost:${info.port}`)
})

// Graceful shutdown
process.on("SIGTERM", () => server.close())

Características relevantes

  • Sem limite de CPU por request — perfeito para uploads pesados, geração de PDF, batch jobs.
  • c.env vazio por padrão: use process.env diretamente, ou injete num middleware (Cap 4).
  • Single-process por padrão: estado em memória persiste entre requests, o que é tanto vantagem (cache simples) quanto risco (memory leaks).
  • Filesystem disponível: fs/promises, leitura de templates, escrita de logs locais — tudo funciona.

# Cloudflare Workers

O runtime mais restritivo e mais barato. V8 isolates iniciam em microssegundos, mas você opera num "Node-shaped vacío": fetch existe, fs não. Bindings são o mecanismo central de acesso a recursos.

setup Workers
import { Hono } from "hono"

type Bindings = {
  DB:        D1Database
  CACHE:     KVNamespace
  ASSETS:    R2Bucket
  QUEUE:     Queue
  JWT_SECRET: string
}

const app = new Hono<{ Bindings: Bindings }>()

app.get("/cached/:key", async (c) => {
  const key    = c.req.param("key")
  const cached = await c.env.CACHE.get(key)
  if (cached) return c.text(cached)

  const row = await c.env.DB.prepare("SELECT data FROM t WHERE key=?").bind(key).first()
  if (!row) return c.notFound()

  // waitUntil — escreve cache sem atrasar resposta
  c.executionCtx.waitUntil(c.env.CACHE.put(key, row.data as string, { expirationTtl: 3600 }))
  return c.text(row.data as string)
})

export default app  // Workers procura o objeto com { fetch }

# Vercel Edge Functions

Vercel Edge usa o mesmo runtime V8 isolate da Cloudflare (em essência). O adapter exporta um config que sinaliza ao Vercel para usar o runtime edge:

# Gotchas comuns ao portar

1. process.env vs c.env

Em Node, process.env.JWT_SECRET é o padrão. Em Workers, isso é undefined — secrets vêm de c.env.JWT_SECRET. Para código portável, sempre prefira c.env com um middleware de bootstrap que popula a partir de process.env quando estiver em Node:

portabilidade de env
app.use(async (c, next) => {
  if (typeof process !== "undefined" && process.env) {
    // Em Node — copia tudo do process.env para c.env
    c.env = { ...process.env, ...c.env } as any
  }
  await next()
})

// Handlers usam c.env uniformemente em qualquer runtime

2. Módulos Node-only escondidos em deps

Algumas bibliotecas (Drizzle Postgres, drivers SQL antigos, libs com binding C++) parecem funcionar em qualquer lugar mas internamente importam node:fs, node:net, etc. O wrangler build avisa; o bundle Vercel Edge falha em produção. Use o flag nodejs_compat em Workers ou substitua pela versão "edge" da lib quando existir.

3. Filesystem em Lambda

Lambda tem acesso a /tmp (512 MB padrão, 10 GB configurável), efêmero e compartilhado por invocações na mesma instância. Útil para cache temporário, perigoso se você assumir isolamento.

4. Estado em memória entre requests

cuidado com estado global
// ❌ Parece OK em Node, BUG em Workers (vários isolates)
const cache = new Map<string, unknown>()

app.get("/data/:key", (c) => {
  const key = c.req.param("key")
  if (cache.has(key)) return c.json(cache.get(key))
  // ...
})

// ✅ Para Workers: use KV. Para Node: documente claramente.

5. Bundling

Workers, Vercel Edge e Fastly exigem um bundle único. Wrangler usa esbuild internamente; Vercel detecta automaticamente; Fastly tem seu CLI. Node e Bun rodam TypeScript direto (com tsx/tsc/bun). Isso afeta como você estrutura imports: caminhos relativos funcionam em todos, mas dependências de arquivos fora do bundle quebram nos edge runtimes.

# Estratégia de código portável

Para um app real que precisa rodar em mais de um runtime:

  • Mantenha o app Hono num módulo separado. src/app.ts exporta o app; cada entry-point (src/node.ts, src/workers.ts, src/lambda.ts) faz só o setup do runtime.
  • Acesse env via c.env, nunca process.env no app. Use um middleware de bootstrap para popular se necessário.
  • Para recursos como DB, abstraia atrás de uma interface. c.var.db pode ser um cliente Drizzle ligado a Postgres em Node, ou a D1 em Workers — o handler não muda.
  • Teste no bundle, não no dev. wrangler dev usa miniflare (simulação fiel); vercel dev simula o edge; teste antes de deployar.
  • Reserve um benchmark de cold start para detectar regressões. Workers a 5 ms vs 50 ms é uma diferença visível.
Por que isso vale a pena

O esforço de manter código portável é pequeno comparado ao benefício: você pode mover um endpoint pesado de Workers para Lambda quando a complexidade crescer, ou levar um endpoint frio de Node para Workers para economizar. Sem mudança de framework, sem reescrita. É a diferença entre lock-in arquitetural e flexibilidade real.

Capítulo 20

Performance

Hono é rápido por design — mas "rápido" não é uma propriedade do framework isolado, é o resultado de decisões que você toma sobre router, middleware, bundle e arquitetura. Este capítulo é o mapa dessas decisões: onde o tempo realmente vai num request, como medir antes de adivinhar, e os trade-offs específicos do edge que costumam ser invisíveis em benchmarks Node tradicionais.

# Onde o tempo realmente vai

Um request HTTP típico atravessa quatro fases. Saber onde cada uma cabe na sua latência ajuda a focar otimização onde importa:

anatomia da latência
┌──────────────────────────────────────────────────────────┐
│  1. Network              │ 5–200 ms │ depende de geografia │
│  2. Cold start           │ 0–2 s    │ só em runtimes edge  │
│  3. Roteamento (Hono)    │ 0.001 ms │ negligível           │
│  4. Middleware + handler │ 1–500 ms │ ONDE A AÇÃO ESTÁ     │
└──────────────────────────────────────────────────────────┘

O que isso significa: a escolha de router quase nunca é o gargalo. Você ganha muito mais tirando uma chamada de banco do hot path do que trocando RegExpRouter por TrieRouter. Mas em casos extremos — Workers free tier com milhares de rotas, cold start crítico, ou benchmark sintético — as decisões abaixo importam.

Regra zero da otimização

Meça antes de mudar. Bench micro de roteador conta uma história; Server-Timing no production conta outra. timing() middleware (Cap 8) + startTime/endTime mostram exatamente onde os milissegundos vão — substitua adivinhação por dados antes de mexer em arquitetura.

# Escolha de router — o trade-off de cold start

Hono 4 oferece três routers e um SmartRouter que escolhe entre eles. Recapitulação rápida (detalhes no Cap 3):

RouterCusto de matchCusto de setupBundleSuporte a padrões
RegExpRouterO(1) — uma regex compiladaAlto — compila no primeiro request~7 KBMaioria; falha em alguns ambíguos
TrieRouterO(segmentos)Baixo — linear no número de rotas~5 KBUniversal

  • Muitas rotas e cold start importa — TrieRouter direto. Compilar uma regex gigante na primeira request adiciona dezenas de ms de cold start.
  • Bundle no limite — PatternRouter economiza ~7 KB. Em Workers free tier com cap de 1 MB e dependências pesadas, isso pode ser a diferença entre deployar e não deployar.
  • Hot path crítica com poucas rotas — RegExpRouter direto. Você assume o custo de cold start uma vez para ganhar performance em cada request seguinte.

# O custo do middleware

Cada middleware adiciona uma camada à cebola — overhead de função, alocação de promise, possíveis allocations. Em isolation o custo é desprezível; somado em hot path com 8–12 middlewares, vira ms reais.

medindo custo de middleware
import { timing, startTime, endTime } from "hono/timing"

app.use(timing())

app.use(async (c, next) => {
  startTime(c, "auth")
  await checkAuth(c)
  endTime(c, "auth")
  await next()
})

app.get("/data", async (c) => {
  startTime(c, "db")
  const data = await db.query("...")
  endTime(c, "db")
  return c.json(data)
})
// → Server-Timing: auth;dur=2.1, db;dur=43.7

Padrões para reduzir custo de middleware:

  • Middleware por path em vez de global: app.use("/api/*", auth) em vez de app.use(auth) evita rodar auth em rotas estáticas.
  • Early return: middleware que precisa decidir cedo (rate limit excedido, IP banido) deve fazê-lo antes de await next() — economiza o trabalho da cadeia inteira.
  • Caches no escopo de módulo: parsing de tokens, compilação de regex, conexões de DB — tudo isso pode ficar fora do middleware, reutilizado entre requests.
  • Lazy initialization: dependências pesadas (PDF generator, ML model) carregadas só no handler que as usa, não no nível do módulo.

# CPU budget — o relógio invisível em edge

Em Workers, cada request tem orçamento de CPU. Não é tempo total — é só o tempo computando. Awaits em I/O não consomem CPU; o isolate "hiberna" durante a espera.

o que consome vs o que não consome
// ❌ Consome CPU continuamente — loop tight, sem await
for (let i = 0; i < 1_000_000; i++) {
  total += heavyCompute(i)
}

// ✅ I/O não conta — o isolate hiberna durante o await
const data = await fetch("https://api.upstream.com")  // 200 ms de I/O
const row  = await c.env.DB.first("...")            // 50 ms de I/O
// Total real: 250 ms — CPU usado: ~2 ms (parse + handler)

Os limites práticos em Workers:

  • Free: 10 ms de CPU por request — suficiente para handlers que delegam tudo a I/O.
  • Paid: 30 s de CPU por request — folgado para quase tudo.
  • Wall clock: independente do CPU, há limites de duração total (geralmente 30 s).

Operações CPU-intensivas que vão estourar 10 ms em Workers free: criptografia pesada (RSA com chaves grandes), parsing de XML/JSON enorme (>5 MB), compressão de imagem, regex catastróficos. Para essas, use paid plan, Lambda, ou Node.

# Caching strategies

Cache é a otimização com melhor retorno — uma resposta cacheada custa zero em CPU, banco e largura de banda upstream. Hono tem três camadas naturais:

1. Cache de runtime (Workers Cache API)

Workers Cache API via middleware
import { cache } from "hono/cache"

app.get("/api/popular",
  cache({
    cacheName:    "popular",
    cacheControl: "max-age=60, stale-while-revalidate=120",
  }),
  async (c) => c.json(await expensiveQuery())
)
// Após primeiro request, próximos vêm do cache da CDN — zero CPU

2. KV / D1 / Redis — cache compartilhado

cache em KV
app.get("/api/users/:id", async (c) => {
  const id  = c.req.param("id")
  const key = `user:${id}`

  const cached = await c.env.CACHE.get(key, "json")
  if (cached) return c.json(cached)

  const user = await db.findUser(id)

  // Escreve em background — não atrasa resposta
  c.executionCtx.waitUntil(
    c.env.CACHE.put(key, JSON.stringify(user), { expirationTtl: 300 })
  )
  return c.json(user)
})

3. In-memory (escopo do isolate/processo)

memoização in-process
// ⚠️  Em Workers: cada isolate tem sua cópia. Útil para hot-cache curto.
// Em Node: cache real entre requests.
const cache = new Map<string, { value: unknown; exp: number }>()

function memoize<T>(key: string, ttlMs: number, fn: () => Promise<T>): Promise<T> {
  const hit = cache.get(key)
  if (hit && hit.exp > Date.now()) return Promise.resolve(hit.value as T)
  return fn().then((value) => {
    cache.set(key, { value, exp: Date.now() + ttlMs })
    return value
  })
}

A leitura: se o handler faz I/O substancial, o framework é irrelevante para performance. Hono e Fastify só se destacam de Express em microbenchmarks ou em apps com altíssima taxa de requests pequenos (>50k RPS por processo).

Onde Hono ganha de fato

Não é em RPS de microbenchmark — é em portabilidade (mesmo código em 8 runtimes), cold start em edge (Workers ~5 ms vs Express via @vendia/serverless-express ~500 ms), e bundle size (core de 14 KB vs Express ~250 KB com middlewares típicos). Isso traduz em economia real de custo em workloads serverless/edge.

# Anti-padrões de performance

  • Logger pesado em produção: serializar objetos grandes em todo request é caro. Use logger condicional por sample (1% de requests) ou logger nativo do runtime (Cloudflare logs, CloudWatch).
  • Reler o body múltiplas vezes: c.req.json() consome o stream. Chamar de novo retorna body vazio. Cacheie o resultado.
  • Validar com Zod o que já está em cache: se a resposta vem do cache, ela já é válida. Aplique validação só no caminho de criação.
  • Round-trips desnecessários ao banco: SELECTs em loop dentro do handler. Use queries com IN ou JOIN, ou prepare statements.
  • Imports síncronos pesados: import "moment-timezone" no top-level adiciona MB ao bundle. Use Intl.DateTimeFormat nativo ou imports dinâmicos.
  • JSON.parse de respostas que vão direto pro cliente: const data = JSON.parse(json); return c.json(data) faz parse + stringify desnecessários. Use c.body(json, 200, { "Content-Type": "application/json" }).

# Checklist de profiling em produção

  1. Habilite timing() em todas as rotas críticas — Server-Timing aparece nas DevTools.
  2. Mensure cold start separadamente: o p99 do primeiro request é diferente do p99 do request quente.
  3. Identifique os top 10 endpoints por latência × frequência: otimize um endpoint chamado 1M vezes/dia antes de um chamado 10 vezes.
  4. Profile o handler, não o framework: 80% do tempo está em I/O e código de negócio, não em Hono.
  5. Compare RegExpRouter vs TrieRouter no seu app real: a diferença é menor do que benchmarks sugerem.
  6. Audite o bundle: wrangler deploy --dry-run --outdir=dist ou similar para outros runtimes; investigue toda dep com mais de 100 KB.

# O princípio organizador

A pergunta central de arquitetura não é "como dividir em pastas" — é "o que precisa mudar junto deve ficar junto, o que muda por razões diferentes deve ficar separado". Em uma API Hono, há três tipos de código que mudam por razões distintas:

  • Transporte HTTP (rotas, validação, status codes) — muda quando o contrato da API muda.
  • Lógica de negócio (services) — muda quando as regras do domínio mudam.
  • Acesso a dados (repositories) — muda quando a fonte de dados muda.

Misturar os três num único handler funciona em protótipos e quebra em escala: uma mudança de banco vira uma mudança em 40 handlers; um teste de regra de negócio exige subir um servidor HTTP. A separação não é dogma — é o que torna cada mudança local.

# A camada de rotas — fina e declarativa

Handlers devem ser finos: validar entrada, chamar um service, formatar a resposta. Zero regra de negócio, zero SQL. Se um handler tem mais de ~15 linhas, provavelmente está fazendo trabalho de service.

src/routes/users.ts
import { Hono } from "hono"
import { zValidator } from "@hono/zod-validator"
import { createUserSchema } from "../schemas/user.schema"
import * as userService from "../services/user.service"

const users = new Hono()
  .get("/", async (c) => {
    const list = await userService.listUsers()
    return c.json(list)
  })
  .get("/:id", async (c) => {
    const user = await userService.getUser(c.req.param("id"))
    if (!user) return c.notFound()
    return c.json(user)
  })
  .post("/", zValidator("json", createUserSchema), async (c) => {
    const created = await userService.createUser(c.req.valid("json"))
    return c.json(created, 201)
  })

export default users

# A camada de service — onde mora o domínio

Services são funções sem nenhuma dependência de Hono. Recebem dados, aplicam regras, retornam dados ou lançam erros de domínio. Isso os torna testáveis sem HTTP e reutilizáveis fora de rotas (cron jobs, CLI, filas).

src/services/user.service.ts
import * as userRepo from "../repositories/user.repo"
import { ConflictError } from "../lib/errors"
import type { CreateUserInput } from "../schemas/user.schema"

export async function createUser(input: CreateUserInput) {
  // Regra de negócio: e-mail único
  const existing = await userRepo.findByEmail(input.email)
  if (existing) throw new ConflictError("e-mail já cadastrado")

  // Domínio: hash de senha, normalização, etc.
  const user = await userRepo.insert({
    ...input,
    email: input.email.toLowerCase().trim(),
  })
  return user
}

export async function getUser(id: string) {
  return userRepo.findById(id)
}

export async function listUsers() {
  return userRepo.findAll()
}
O teste de fogo da separação

Se você consegue escrever um teste de createUser sem importar Hono, sem instanciar um app e sem fazer app.request() — a separação está certa. Services testáveis isoladamente são o sinal mais confiável de uma arquitetura saudável. Se o teste de negócio precisa de HTTP, a lógica vazou para o handler.

# Erros de domínio padronizados

Defina uma hierarquia de erros que o app.onError traduz de forma consistente (Capítulo 11). Services lançam erros de domínio; a camada HTTP nunca decide status code ad hoc:

import { HTTPException } from "hono/http-exception"

export class NotFoundError extends HTTPException {
  constructor(resource: string) {
    super(404, { message: `${resource} não encontrado` })
  }
}
export class ConflictError extends HTTPException {
  constructor(msg: string) { super(409, { message: msg }) }
}
export class ForbiddenError extends HTTPException {
  constructor(msg: string) { super(403, { message: msg }) }
}
src/middleware/error.ts
import { HTTPException } from "hono/http-exception"
import type { ErrorHandler } from "hono"

export const errorHandler: ErrorHandler = (err, c) => {
  const requestId = c.get("requestId") ?? "unknown"

  if (err instanceof HTTPException) {
    return err.getResponse()
  }

  console.error({ requestId, err })
  return c.json({ error: "internal", requestId }, 500)
}

# Checklist de code review

Antes de aprovar um PR numa API Hono, verifique:

Estrutura e separação

  • Handlers têm menos de ~15 linhas e não contêm SQL nem regra de negócio?
  • Lógica de domínio está em services, testável sem HTTP?
  • Schemas Zod são compartilhados (não duplicados entre validação e tipos)?
  • Rotas usam method chaining ou route() (para preservar tipos RPC)?

Validação e erros

  • Todo input externo (body, query, param) passa por um validator?
  • Handlers lançam erros de domínio em vez de montar respostas de erro ad hoc?
  • Existe um app.onError e ele não vaza stack trace em 5xx?
  • Status codes são semanticamente corretos (404 vs 422 vs 409)?

Segurança

  • Secrets vêm de env/bindings, nunca hardcoded nem versionados?
  • CORS está configurado antes de auth (preflight não bloqueado)?
  • secureHeaders() está aplicado?
  • Cookies de auth têm httpOnly, secure, sameSite?
  • bodyLimit protege rotas que leem body?

Performance e portabilidade

  • Sem estado mutável global que assuma single-process (quebra em isolates)?
  • I/O fire-and-forget usa c.executionCtx.waitUntil()?
  • Env é acessado via c.env (portável) e não process.env direto no app?
  • Sem dependências Node-only se o alvo inclui edge runtimes?

Testes

  • Rotas críticas têm teste via app.request() (sucesso, validação, auth)?
  • Services têm teste unitário sem HTTP?
  • Casos de erro (401, 403, 404, 422) são testados, não só o caminho feliz?

  • Avançado — JSX no servidor, RPC type-safe sem geração de código, WebSockets, streaming/SSE, e o sistema completo de autenticação.
  • Qualidade — testes sem servidor e documentação OpenAPI automática.
  • Produção — adapters de runtime, performance honesta, deploy em todos os destinos, e a arquitetura deste capítulo.

O fio condutor de tudo: Hono trata Request → Response da spec Web como contrato universal. Cada recurso — do roteador ao RPC — é construído sobre essa fundação, o que explica tanto a portabilidade quanto a previsibilidade do framework.
