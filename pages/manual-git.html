Capítulo 1

O modelo de dados do Git

Os treze volumes anteriores produziram código — tipos, componentes, rotas, schemas, autenticação. O Volume XIII fechou a Onda 3 com um backend inteiro: Hono servindo, Drizzle mapeando, Postgres guardando, autenticação protegendo. Todo esse código precisa de uma história — quem mudou o quê, quando, e como reverter quando algo quebra. O Git é a ferramenta que registra essa história, e a maior parte da confusão em torno dele vem de aprendê-lo pelos comandos antes de entender o que esses comandos manipulam. Este capítulo inverte a ordem: antes de qualquer commit ou branch, desmonta o modelo de dados que o Git é por baixo — um pequeno banco de dados de objetos imutáveis endereçados por hash, sobre o qual todo comando é apenas uma operação. Entender esses objetos é o que transforma o Git de uma sequência de feitiços decorados num sistema previsível.

# Git é um banco de dados de conteúdo

A intuição errada mais comum é pensar no Git como algo que guarda diferenças entre versões de arquivos — uma pilha de patches. Não é. No fundo, o Git é um armazém de chave-valor endereçado por conteúdo: você entrega um conteúdo, ele devolve uma chave (um hash SHA), e com essa chave você recupera exatamente aquele conteúdo de volta. A chave é derivada do próprio conteúdo, então conteúdos idênticos produzem a mesma chave, e qualquer alteração — um byte — produz uma chave completamente diferente.

Tudo o que o Git faz se constrói sobre essa ideia. Um repositório é, essencialmente, esse armazém (a pasta .git/objects) mais alguns ponteiros. Os comandos do dia a dia — add, commit, branch, merge — são formas convenientes de criar objetos nesse armazém e mover ponteiros entre eles. Quando o modelo de objetos fica claro, os comandos param de ser mágicos.

terminal
# Inicia um repositório: cria a pasta .git com o armazém de objetos
git init meu-projeto
cd meu-projeto

# O coração do Git vive em .git/ — objetos, refs e configuração
ls -F .git/
# HEAD  config  description  hooks/  info/  objects/  refs/

# Os três objetos: blob, tree, commit

O armazém guarda essencialmente três tipos de objeto, e a relação entre eles é toda a estrutura do Git. O blob guarda o conteúdo de um arquivo — só os bytes, sem nome, sem caminho. A tree guarda uma listagem de diretório: nomes de arquivos e subpastas, cada um apontando para o blob ou a tree correspondente. O commit aponta para uma tree (o estado completo do projeto naquele instante) e adiciona metadados: autor, data, mensagem, e o(s) commit(s) anterior(es).

A analogia direta é com um sistema de arquivos. O blob é o conteúdo de um arquivo; a tree é uma pasta; o commit é uma fotografia datada e assinada da pasta-raiz inteira. A diferença é que, no Git, esses objetos são imutáveis e endereçados pelo hash do seu conteúdo — o que dá ao sistema propriedades que um sistema de arquivos comum não tem.

terminal
# Guarda um conteúdo no armazém e recebe a chave (hash) de volta
echo 'console.log("oi")' | git hash-object -w --stdin
# 8c1420 ... (o SHA-1 do blob, 40 caracteres hex)

# Recupera o conteúdo pela chave — content-addressable na prática
git cat-file -p 8c1420
# console.log("oi")

# O tipo do objeto também se consulta pela chave
git cat-file -t 8c1420
# blob

# O SHA: identidade derivada do conteúdo

Cada objeto é identificado por um hash do seu próprio conteúdo — historicamente SHA-1 (40 caracteres hexadecimais), com o Git em migração para SHA-256. Esse endereçamento por conteúdo tem consequências profundas. Primeiro, a integridade é automática: se um byte de um objeto corromper, seu hash deixa de bater, e o Git detecta na hora. Segundo, a deduplicação é gratuita: dois arquivos idênticos em pastas diferentes são o mesmo blob, guardado uma vez. Terceiro, e mais importante para entender branches e merges: a identidade de um commit depende de tudo que veio antes dele.

Como o commit inclui no seu conteúdo o hash da tree e o hash do commit pai, o hash do commit é uma função de todo o seu histórico. Mudar qualquer coisa no passado — uma mensagem, um arquivo, a ordem — muda o hash daquele commit e, em cascata, o de todos os commits seguintes. Essa é a razão técnica pela qual "reescrever a história" no Git não edita commits: cria commits novos, com hashes novos. Voltaremos a isso no rebase (Cap 8); por ora, basta fixar que o hash é uma impressão digital de toda a linhagem.

Snapshot, não diff
Cada commit referencia uma tree que descreve o estado completo do projeto naquele momento — não as mudanças desde o commit anterior. O Git calcula diffs sob demanda, comparando duas trees quando você pede um git diff, mas não é assim que ele armazena. Pensar em snapshots (e não em patches acumulados) é o que torna branches baratos e merges compreensíveis: trocar de branch é apenas apontar para outra tree completa.

# Por dentro de uma tree e de um commit

Vale abrir os objetos com as próprias mãos uma vez — depois disso o modelo nunca mais parece abstrato. Uma tree é uma lista de entradas, cada uma com modo (permissões), tipo, hash e nome. Um commit é um cabeçalho de texto simples apontando para uma tree e para o pai.

terminal
# Conteúdo de uma tree: nome -> hash do blob/tree, com modo e tipo
git cat-file -p HEAD^{tree}
# 100644 blob 8c1420...    index.ts
# 100644 blob a93f01...    package.json
# 040000 tree f20ab8...    src

# Conteúdo de um commit: aponta para a tree e para o pai
git cat-file -p HEAD
# tree   f7c3e0...                 <- snapshot completo do projeto
# parent 4a2b9d...                 <- commit anterior (ausente no 1o commit)
# author Vitor <vitor@exemplo.com> 1730000000 -0300
# committer Vitor <vitor@exemplo.com> 1730000000 -0300
#
# feat: primeira versão da API

É só isso. Um commit é um pedaço de texto que aponta para uma tree e para um pai, com alguns metadados — e cujo hash identifica o conjunto inteiro. Os "grafos de commits" que ferramentas visuais desenham nada mais são do que esses ponteiros parent ligando um commit ao anterior. Um histórico linear é uma corrente de commits, cada um apontando para o seu antecessor; um merge é simplesmente um commit com dois pais.

# Refs: branches e tags são ponteiros

Se commits são imutáveis e identificados por hashes ilegíveis, como o Git sabe onde está o "topo" do trabalho? Por meio de referências (refs): nomes legíveis que apontam para um hash de commit. Um branch é exatamente isso — um arquivo cujo conteúdo é um hash de commit. Criar um branch não copia nada; escreve um ponteiro. Avançar um branch (fazer um commit) é regravar esse ponteiro para o novo commit. É por isso que branches no Git são instantâneos e baratíssimos: são literalmente um arquivo de 41 bytes.

terminal
# Um branch é um arquivo em refs/heads/ contendo um hash de commit
cat .git/refs/heads/main
# 4a2b9d3f7c1e0a... (o commit para onde 'main' aponta, e nada mais)

# HEAD aponta para o branch atual (indireção de um nível)
cat .git/HEAD
# ref: refs/heads/main

# Visão do grafo: cada commit aponta para o pai; refs apontam para commits
git log --oneline --graph --all
# * 4a2b9d3 (HEAD -> main) feat: primeira versão da API
# * 1f0c8e2 chore: estrutura inicial do projeto

Essa separação entre objetos (imutáveis, endereçados por conteúdo) e refs (mutáveis, nomes legíveis que apontam para objetos) é a dobradiça do Git inteiro. Os objetos formam a história permanente; as refs são marcadores móveis sobre essa história. HEAD é uma ref especial que indica onde você está agora — normalmente apontando para um branch, que por sua vez aponta para um commit. Os Capítulos 5 e 6 exploram branches e HEAD em profundidade; aqui o ponto é que nada disso é mágico — são ponteiros sobre o armazém de objetos.

Não pense em arquivos sendo editados no lugar
O instinto de "o Git guarda meus arquivos e as mudanças neles" leva a erros conceituais que se pagam caro no merge e no rebase. Nada no histórico do Git é editado depois de criado: cada estado é um snapshot novo e imutável, e cada operação que "muda o passado" na verdade cria objetos novos e move refs. Internalizar isso agora evita o pânico de "perdi meu trabalho" mais tarde — quase nada se perde de fato, porque os objetos antigos continuam no armazém até serem coletados (e o reflog, Cap 14, sabe onde estavam).

# Onde tudo isso vive: a pasta .git

Todo o banco de dados do Git para um projeto cabe numa única pasta na raiz: .git/. Apagá-la remove a história e devolve uma pasta comum de arquivos; copiá-la copia o repositório inteiro. Conhecer seu esqueleto desmistifica o resto do volume.

terminal
.git/
├── objects/      # o armazém: blobs, trees, commits (endereçados por hash)
├── refs/         # ponteiros: heads/ (branches), tags/, remotes/
├── HEAD          # onde você está agora (geralmente ref: refs/heads/...)
├── index         # a staging area — o próximo commit em preparação (Cap 4)
├── config        # configuração local do repositório
└── logs/         # o reflog: histórico de movimentos das refs (Cap 14)
Explore com cat-file e ls-tree
Sempre que um comando do Git parecer obscuro, abra os objetos que ele tocou. git cat-file -p <hash> imprime qualquer objeto; git cat-file -t <hash> diz o tipo; git ls-tree HEAD lista a tree do commit atual; git rev-parse HEAD resolve uma ref para o hash. Esses comandos "de baixo nível" (plumbing) são a melhor ferramenta de aprendizado do Git — eles revelam que os comandos do dia a dia só criam objetos e movem refs.

Capítulo 2

Repositório, working tree e staging

O Capítulo 1 mostrou que o Git é um armazém de objetos imutáveis dentro de .git/. Mas você não edita objetos diretamente — edita arquivos numa pasta comum, e em algum momento esses arquivos viram blobs, trees e commits. Entre o arquivo que você salva no editor e o commit gravado na história existem três áreas distintas, e quase toda confusão sobre add e commit nasce de não enxergá-las separadamente. Este capítulo isola cada uma — a working tree onde você trabalha, o index (staging area) onde você monta o próximo commit, e o repositório onde a história mora — e segue o ciclo de vida de um arquivo entre elas. Quando as três áreas ficam nítidas, git status deixa de ser um oráculo e vira um mapa.

# As três áreas

Trabalhar com Git é mover conteúdo entre três lugares. A working tree (árvore de trabalho) é a pasta do projeto como o sistema operacional a vê: os arquivos reais que seu editor abre e salva. O index, também chamado de staging area, é uma área intermediária onde você monta o próximo commit — uma espécie de rascunho do que será fotografado. O repositório é o .git/ do Capítulo 1: o armazém permanente de commits.

O fluxo padrão atravessa as três em ordem. Você edita um arquivo (working tree), seleciona o que entra no próximo snapshot com git add (index), e grava o snapshot com git commit (repositório). O index é o que confunde quem vem de ferramentas mais simples — por que um passo intermediário? Porque ele permite escolher precisamente o que entra em cada commit, em vez de fotografar tudo que mudou de uma vez. Essa precisão é o que torna possível um histórico limpo, com commits coesos.

O index é uma tree em preparação
Conectando ao Cap 1: o index nada mais é do que uma tree em construção, guardada em .git/index. Quando você faz git add, o Git cria o blob do conteúdo e registra-o no index. Quando você faz git commit, ele congela o index numa tree, embrulha num objeto commit e move a ref do branch. "Staging" não é uma metáfora vaga — é literalmente montar a próxima tree, entrada por entrada.

# git status: o mapa das três áreas

O git status é a bússola do dia a dia, e ele descreve exatamente as diferenças entre as três áreas. "Changes to be committed" são diferenças entre o index e o último commit — o que já está preparado. "Changes not staged for commit" são diferenças entre a working tree e o index — o que você mudou mas ainda não preparou. "Untracked files" são arquivos que existem na working tree mas o Git nunca viu.

terminal
git status
# Changes to be committed:        <- index vs último commit (já preparado)
#   modified:   src/api.ts
#
# Changes not staged for commit:  <- working tree vs index (mudou, falta add)
#   modified:   src/db.ts
#
# Untracked files:                <- existe no disco, o Git nunca viu
#   .env.local

# Versão compacta: duas colunas (index, working tree) por arquivo
git status --short
# M  src/api.ts     <- M na 1a coluna = staged
#  M src/db.ts      <- M na 2a coluna = modificado, não staged
# ?? .env.local     <- untracked

# O ciclo de vida de um arquivo

Do ponto de vista do Git, um arquivo está em um de dois estados macro: untracked (o Git não o rastreia) ou tracked (rastreado). Um arquivo tracked, por sua vez, pode estar unmodified (igual ao último commit), modified (mudou na working tree) ou staged (a mudança está no index). O git add faz duas coisas conforme o caso: promove um untracked a tracked+staged, ou move uma modificação da working tree para o index.

terminal
# Novo arquivo: nasce untracked
echo 'export const PI = 3.14' > math.ts

# add: registra no index (untracked -> staged)
git add math.ts

# Edita de novo DEPOIS do add: a nova mudança fica só na working tree
echo 'export const E = 2.71' >> math.ts

# status mostra o arquivo nas DUAS colunas: parte staged, parte não
git status --short
# MM math.ts   <- a 1a linha (PI) está staged; a 2a (E) não

Esse exemplo expõe o ponto mais escorregadio do index: o git add fotografa o arquivo no instante do add. Editar depois não atualiza o que foi preparado — a edição posterior vive na working tree até um novo add. Por isso "MM": a versão no index difere tanto do commit anterior quanto da working tree. Não é bug; é o index funcionando como rascunho explícito.

git add . não é sempre o que você quer
O reflexo de git add . (preparar tudo) ou git add -A arrasta arquivos que não deveriam entrar — um .env com segredos, artefatos de build, arquivos temporários. Isso conecta diretamente à autenticação do Vol XIII: um .env com JWT_SECRET commitado vaza o segredo para sempre na história (mesmo que removido depois — Cap 14). Prefira preparar arquivos explicitamente, use .gitignore (Cap 17) para o que nunca deve ser rastreado, e confira sempre com git status antes de commitar.

# git add: seletivo e por partes

A vantagem do index é a seletividade. Você pode preparar arquivos individuais, e até partes de um arquivo, montando commits coesos mesmo quando suas mudanças locais misturam assuntos diferentes. O modo interativo por blocos (-p, de patch) é a ferramenta para isso: o Git apresenta cada trecho de mudança e pergunta se ele entra no commit.

terminal
# Preparar arquivos específicos, não tudo de uma vez
git add src/api.ts src/db.ts

# Preparar só PARTES de um arquivo, bloco a bloco (y/n por trecho)
git add -p src/api.ts
# Stage this hunk [y,n,q,a,d,s,e,?]?  <- y entra, n pula, s divide o bloco

# Conferir o que está preparado (diff entre index e último commit)
git diff --staged

# Desfazer: tirar do stage e descartar

Mover conteúdo para o index não é definitivo. O Git moderno separa dois verbos para desfazer, e a distinção importa porque eles atuam em áreas diferentes. git restore --staged tira um arquivo do index sem tocar na working tree (a edição continua lá, só deixa de estar preparada). git restore (sem --staged) descarta a edição na working tree, devolvendo o arquivo ao estado do index — operação destrutiva, pois a mudança não commitada se perde.

terminal
# Tirar do index, preservando a edição na working tree (reversível)
git restore --staged src/api.ts

# Descartar a edição na working tree (DESTRUTIVO: a mudança some)
git restore src/db.ts

# Versões antigas (ainda comuns) faziam o mesmo com checkout/reset:
# git reset HEAD <arquivo>   = git restore --staged <arquivo>
# git checkout -- <arquivo>  = git restore <arquivo>
restore e switch vs o velho checkout
O git checkout fazia coisas demais — trocava de branch e restaurava arquivos, com semântica ambígua. O Git moderno divide essas funções em verbos claros: git switch para mudar de branch (Cap 5) e git restore para mexer em arquivos. Use os novos por clareza, mas conheça o checkout — ele é onipresente em tutoriais e scripts antigos, e o Cap 15 detalha as três funções sobrepostas que ele acumulava.

Capítulo 3

Commits e o grafo de objetos

O Capítulo 1 apresentou o commit como um objeto que aponta para uma tree e para um pai; o Capítulo 2 mostrou como o index prepara a tree que o commit congela. Falta juntar as peças e ver o que emerge quando commits encadeiam: um grafo acíclico dirigido — a estrutura que organiza toda a história e que sustenta branches, merges e rebase. Este capítulo trata o commit como unidade de trabalho: o que é um bom commit, como a mensagem comunica intenção, e — sobretudo — como os ponteiros parent formam o grafo que você navega o resto do volume. Entender o grafo não é trivia acadêmica: é o que faz HEAD~3, main..feature e "o ancestral comum de dois branches" pararem de ser jargão e virarem geografia legível.

# O commit como unidade atômica

Um commit registra um estado completo do projeto num instante, com a intenção por trás dele. A palavra-chave é atômico: um bom commit captura uma mudança coesa e completa — uma correção, uma feature pequena, um refactor — e não uma mistura de assuntos não relacionados. Essa disciplina não é estética; é o que torna a história utilizável. Um commit atômico pode ser revertido sozinho (Cap 9), inspecionado isoladamente, ou identificado por um bisect (Cap 21) como o introdutor de um bug. Um commit que mistura cinco assuntos não pode ser desfeito sem desfazer os outros quatro.

terminal
# Grava o index atual como um novo commit na história
git commit -m 'feat: valida o corpo do login com Zod'

# Atalho: prepara todos os arquivos JÁ rastreados e commita (não pega untracked)
git commit -am 'fix: corrige expiração da sessão'

# Sem -m: abre o editor para uma mensagem com título + corpo
git commit

# A mensagem comunica intenção

O diff mostra o que mudou; a mensagem explica por quê. Daqui a seis meses, o "porquê" é a única coisa que o código não consegue recuperar sozinho. A convenção amplamente adotada é uma linha de resumo curta (≤ 50 caracteres) no imperativo, opcionalmente seguida de uma linha em branco e um corpo explicando contexto e motivação. O padrão Conventional Commits formaliza o resumo com um prefixo de tipo, o que permite gerar changelogs e versionar automaticamente.

mensagem de commit
# Resumo: tipo(escopo): descrição imperativa, curta
feat(auth): adiciona refresh token com rotação

# Corpo (após linha em branco): o PORQUÊ, não o quê
O access token de 15 min exigia novo login frequente. A rotação de
refresh tokens mantém a sessão viva sem reduzir a segurança, pois
cada uso invalida o token anterior (detecção de replay).

# Rodapé: referências, breaking changes
Refs: #142
Conventional Commits, em uma linha
O prefixo segue tipo(escopo): descrição. Tipos comuns: feat (nova funcionalidade), fix (correção), refactor, docs, test, chore (manutenção). Um ! antes dos dois-pontos ou um rodapé BREAKING CHANGE: sinaliza incompatibilidade. Ferramentas leem essa convenção para bump de versão semântica e changelog automático — mas o ganho principal é humano: a história fica escaneável.

# O grafo acíclico dirigido

Cada commit aponta para o seu pai. Encadeie isso e surge um grafo: dirigido (as setas vão do commit para o ancestral, nunca o contrário) e acíclico (não há ciclos — você nunca é seu próprio ancestral). Um histórico linear é o caso mais simples desse grafo: uma corrente. Mas o grafo admite ramificações — dois commits com o mesmo pai (um branch divergiu) — e junções — um commit com dois pais (um merge uniu dois caminhos, Cap 7).

grafo de commits
# Histórico linear: cada commit aponta para o anterior (setas = parent)
A <- B <- C <- D   (main)

# Branch diverge em B: dois caminhos partem do mesmo pai
A <- B <- C <- D        (main)
       \
        E <- F          (feature)

# Merge: um commit (M) com DOIS pais junta os caminhos
A <- B <- C <- D <- M    (main)
       \         /
        E <----- F

Esse desenho é o Git inteiro em uma figura. Branches são apenas nomes apontando para commits específicos do grafo (Cap 5); o "estado" do projeto em qualquer ponto é a tree daquele commit. Operações que parecem complicadas — rebase, cherry-pick, merge — são todas manipulações desse grafo: copiar commits para outro ponto, criar junções, mover ponteiros. Visualizar o grafo antes de rodar o comando é o hábito que mais previne erros.

# Navegando o grafo: ~ e ^

Para falar sobre commits sem decorar hashes, o Git oferece uma sintaxe de navegação relativa a partir de qualquer ref. O ~ (til) anda para trás na linha de ancestrais: HEAD~1 é o pai, HEAD~3 é o bisavô. O ^ (circunflexo) seleciona qual pai quando há mais de um (relevante só em commits de merge): M^1 é o primeiro pai, M^2 o segundo.

terminal
git show HEAD          # o commit atual
git show HEAD~1        # o pai (um passo atrás na linha principal)
git show HEAD~3        # três commits atrás

# Em um commit de merge M (dois pais):
git show M^1           # primeiro pai (o branch onde o merge foi feito)
git show M^2           # segundo pai (o branch que foi incorporado)

# Resolver qualquer expressão para o hash completo
git rev-parse HEAD~2

# Ranges: o que está entre dois pontos

A sintaxe de range expressa "os commits alcançáveis a partir de X mas não de Y" — a base para comparar branches, revisar o que um PR adiciona, ou listar o que falta integrar. git log Y..X mostra os commits em X que não estão em Y. Essa é a pergunta que você faz o tempo todo: "o que feature tem que main ainda não tem?".

terminal
# Commits em 'feature' que ainda não estão em 'main' (o que o PR adiciona)
git log main..feature --oneline

# O inverso: o que 'main' tem que 'feature' não tem (está atrasada?)
git log feature..main --oneline

# Diferença simétrica: commits exclusivos de cada lado
git log main...feature --oneline --left-right
git log é uma ferramenta de navegação, não só de leitura
Vale investir em alguns formatos: --oneline condensa cada commit a uma linha; --graph desenha o grafo com as ramificações; --all inclui todos os branches; --stat mostra arquivos alterados. A combinação git log --oneline --graph --all é o mapa visual da história inteira. Para investigar um arquivo: git log -p -- caminho/arquivo.ts mostra cada mudança que ele sofreu, com diff.

# Corrigir o último commit

Um commit ainda não compartilhado pode ser ajustado. O --amend substitui o último commit por um novo — útil para corrigir a mensagem ou incluir um arquivo esquecido. É importante entender, à luz do Cap 1, que --amend não edita o commit: cria um commit novo (com hash novo) e move a ref para ele, descartando o anterior. Por isso a regra que atravessa todo o volume: só altere commits que ainda não saíram da sua máquina.

terminal
# Esqueceu um arquivo? Prepare e amende o último commit
git add src/esquecido.ts
git commit --amend --no-edit   # mantém a mensagem, troca a tree

# Só corrigir a mensagem do último commit
git commit --amend -m 'feat: mensagem corrigida'
--amend reescreve história
Como --amend cria um commit novo e abandona o antigo, usá-lo em um commit já enviado a um remoto (Cap 11) diverge a sua história da dos colegas — e o próximo push falha ou exige force. Regra de ouro do volume: nunca reescreva história pública. Amende, rebaseie e resete à vontade enquanto o trabalho é só seu; uma vez compartilhado, prefira commits novos (como revert, Cap 9).

Capítulo 4

O índice (staging area)

O Capítulo 2 apresentou o index como uma das três áreas e mostrou o fluxo add → commit. Mas o index é uma estrutura de dados concreta — um arquivo binário em .git/index — e entendê-lo de verdade desfaz uma classe inteira de confusões: por que add "congela" o arquivo, o que o Git faz para saber rapidíssimo quais arquivos mudaram, e o que significam aquelas mensagens de "stage 1, 2, 3" durante um conflito. Este capítulo abre o index: a tree em construção que liga a working tree ao repositório, o cache de metadados que torna o git status instantâneo mesmo em projetos gigantes, e os comandos de baixo nível que o manipulam diretamente. É o capítulo que transforma o staging de "um passo que o Git me obriga a fazer" em "a ferramenta que me dá controle preciso sobre cada commit".

# O que o index realmente guarda

O index é uma lista ordenada de entradas, uma por arquivo rastreado. Cada entrada amarra três coisas: o caminho do arquivo, o hash do blob com o conteúdo já registrado no armazém de objetos (Cap 1), e os metadados do arquivo (modo/permissões e dados de stat do sistema de arquivos — tamanho, data de modificação). Não é uma cópia dos arquivos: é uma tabela de ponteiros para blobs, mais informação de cache. Quando você faz git commit, o Git converte essa lista numa tree e a sela num commit.

terminal
# Lista as entradas do index com o hash do blob e o modo de cada uma
git ls-files --stage
# 100644 8c1420e... 0    src/api.ts
# 100644 a93f01b... 0    package.json
# 100755 f3c0d12... 0    scripts/build.sh   <- 755 = executável
#       ^modo   ^hash do blob  ^stage  ^caminho

Repare na coluna do meio: cada arquivo no index aponta para um blob que já existe no armazém. É por isso que o git add "congela" o conteúdo (Cap 2) — no instante do add, o Git cria o blob e grava seu hash na entrada do index. Editar o arquivo depois muda a working tree, mas a entrada do index continua apontando para o blob antigo, até um novo add. O "0" na coluna de stage é o estado normal; veremos os outros valores no fim do capítulo.

# Por que o index existe: precisão e velocidade

O index resolve dois problemas de uma vez. O primeiro é a precisão já vista: ele permite montar um commit com exatamente o que você quer, arquivo a arquivo ou trecho a trecho (Cap 2). O segundo, menos óbvio, é a velocidade. Os metadados de stat guardados em cada entrada funcionam como cache: para saber se um arquivo mudou, o Git compara o stat atual do disco com o guardado no index. Se data e tamanho batem, o arquivo não mudou — sem precisar ler e re-hashear o conteúdo. É esse cache que faz git status responder em milissegundos mesmo num repositório com dezenas de milhares de arquivos.

O index é uma tree achatada
Uma tree (Cap 1) é hierárquica: a tree-raiz aponta para subtrees, que apontam para blobs. O index é a mesma informação achatada numa lista de caminhos completos (src/api.ts, não "api.ts dentro da subtree src"). No commit, o Git reconstrói a hierarquia a partir dessa lista achatada, criando as trees intermediárias. Por isso o staging é literalmente "preparar a próxima tree": cada add insere ou atualiza uma linha na lista que virará o commit.

# Comparando as três áreas com diff

Como o index é uma área distinta, há dois diffs possíveis, e confundi-los é fonte de erro. git diff (sem argumentos) compara a working tree com o index — "o que mudei mas ainda não preparei". git diff --staged compara o index com o último commit — "o que vai entrar no próximo commit". Saber qual diff você está olhando é a diferença entre revisar o que falta preparar e revisar o que já está pronto para commitar.

terminal
# working tree vs index: mudanças ainda NÃO preparadas
git diff

# index vs último commit: o que ESTÁ preparado (revisão pré-commit)
git diff --staged

# working tree vs último commit: todas as mudanças, staged ou não
git diff HEAD
Reviste sempre o --staged antes de commitar
O hábito que mais previne commits ruins é rodar git diff --staged imediatamente antes de git commit. Ele mostra exatamente o snapshot que será gravado — nem mais (mudanças que ainda estão só na working tree não aparecem), nem menos. É o último ponto de checagem antes de algo entrar permanentemente na história, e onde você pega um console.log esquecido, um segredo coando, ou um arquivo que não devia estar ali.

# Manipulando o index diretamente

O add e o restore --staged (Cap 2) são as portas de entrada do dia a dia, mas há comandos de baixo nível que operam direto no index — úteis para entender o que acontece por baixo e para casos especiais. git reset (sem flags destrutivas) move entradas do index de volta ao estado de um commit, sem tocar na working tree. É a operação inversa do add em massa.

terminal
# Esvazia o index de volta ao último commit (working tree intacta).
# Tudo volta a "not staged" — útil para remontar o commit do zero.
git reset

# Tira um arquivo específico do index (= git restore --staged)
git reset src/api.ts

# Remove do index E do controle de versão, mas mantém no disco
# (clássico para parar de rastrear um arquivo que virou .gitignore)
git rm --cached .env

O git rm --cached merece destaque: ele remove o arquivo do index (deixa de ser rastreado) sem apagá-lo do disco. É a forma correta de "parar de versionar" um arquivo que nunca deveria ter entrado — um .env, um log, um build. Combinado com uma entrada no .gitignore (Cap 17), faz o Git esquecer o arquivo daqui para a frente. (Ele continua na história passada — removê-lo de lá é assunto do Cap 14.)

# O index durante um conflito: os três stages

Aquela coluna "0" do ls-files --stage tem um propósito que só aparece em merges (Cap 12). Quando um merge conflita num arquivo, o Git não consegue decidir qual versão vai para o index — então guarda as três ao mesmo tempo, em slots numerados. Stage 1 é a versão do ancestral comum (a base). Stage 2 é a sua versão (a do branch atual). Stage 3 é a versão que chega (a do branch sendo incorporado). O arquivo fica "não resolvido" no index até você escolher e fazer add, o que colapsa os três stages de volta a um único stage 0.

terminal
# Durante um conflito, o index guarda as TRÊS versões do arquivo
git ls-files --stage
# 100644 aaa... 1    src/api.ts   <- base (ancestral comum)
# 100644 bbb... 2    src/api.ts   <- nossa versão (HEAD)
# 100644 ccc... 3    src/api.ts   <- versão que chega (branch incorporado)

# Resolver = editar o arquivo e fazer add: colapsa para stage 0
git add src/api.ts
git ls-files --stage -- src/api.ts
# 100644 ddd... 0    src/api.ts   <- resolvido, um único stage
"add para resolver conflito" não é mágica — é colapsar stages
A instrução "edite o arquivo e dê git add para marcar o conflito como resolvido" (Cap 12) costuma soar arbitrária. Agora ela faz sentido mecânico: o add pega o conteúdo que você editou na working tree, cria um blob, e substitui os três stages conflitantes por uma única entrada stage 0. O Git considera o conflito resolvido porque o arquivo voltou a ter exatamente uma versão no index. Se você der add sem resolver de verdade (deixando os marcadores <<<<<<< no arquivo), o Git aceita assim mesmo — ele só checa que há um stage 0, não que o conteúdo faz sentido.

Capítulo 5

Branches e referências

O Capítulo 1 deixou uma ideia plantada: um branch é apenas um arquivo de 41 bytes contendo um hash de commit. Este capítulo cobra essa promessa e mostra todas as consequências dela. Quase todo o medo que cerca branches no Git — "vou perder trabalho", "trocar de branch é arriscado", "criar branch é pesado" — vem de imaginá-los como cópias de pastas, como em ferramentas mais antigas. Não são. Um branch é um ponteiro móvel sobre o grafo de commits (Cap 3), e entender isso torna criar, trocar e descartar branches operações triviais e instantâneas. Vamos ver como criar e mover entre branches com os verbos modernos, o que acontece com cada commit que você faz, e por que branches são a unidade natural de trabalho paralelo — a base de todo fluxo de colaboração dos Capítulos 18 e 19.

# Um branch é um ponteiro para um commit

Repetindo o Capítulo 1 com todas as letras: um branch não contém arquivos, não contém commits, não é uma cópia de nada. É um nome legível armazenado em .git/refs/heads/ cujo conteúdo é o hash de um commit — o commit mais recente daquele branch (a "ponta", ou tip). Como cada commit aponta para o seu pai (Cap 3), conhecer a ponta basta para reconstruir todo o histórico do branch seguindo a corrente de parent para trás. O branch é só a etiqueta na ponta dessa corrente.

terminal
# Criar um branch é escrever um ponteiro — instantâneo, nada é copiado
git branch feature-login

# O arquivo do branch contém apenas o hash do commit-ponta
cat .git/refs/heads/feature-login
# 4a2b9d3f7c1e0a... (o mesmo commit onde você estava ao criar)

# Listar branches; o asterisco marca o branch atual
git branch
# * main
#   feature-login
Por que branches são baratos
Em sistemas de versão antigos (SVN, CVS), criar um branch copiava a árvore de arquivos inteira — caro em disco e tempo, raro na prática. No Git, criar um branch escreve 41 bytes. Essa diferença de custo muda a cultura: branches deixam de ser eventos cerimoniais e viram descartáveis. Você cria um branch para experimentar uma ideia de cinco minutos, e o apaga se não der certo. Essa leveza é o que torna possível o fluxo "um branch por feature, um branch por correção" dos Caps 18-19.

# Trocar de branch: git switch

Mudar de branch faz duas coisas: aponta o HEAD (Cap 6) para o outro branch e atualiza a working tree para refletir a tree do commit-ponta daquele branch. O Git moderno usa git switch para isso — um verbo dedicado, mais claro que o antigo git checkout sobrecarregado (Cap 2). Criar e já trocar para um branch novo é o caso mais comum, e tem um atalho.

terminal
# Trocar para um branch existente
git switch feature-login

# Criar E trocar de uma vez (o -c = create), o fluxo do dia a dia
git switch -c feature-checkout

# Voltar ao branch anterior (como 'cd -' no shell)
git switch -

# Equivalentes antigos, ainda muito vistos:
# git checkout feature-login       = git switch feature-login
# git checkout -b feature-checkout  = git switch -c feature-checkout

# O que acontece ao commitar num branch

Aqui está o mecanismo que faz tudo se encaixar. Quando você faz um commit, o Git cria o objeto commit (apontando para o pai, que é a ponta atual) e então move o ponteiro do branch atual para o novo commit. O HEAD, que aponta para o branch, segue junto. Nenhum outro branch se mexe. É por isso que trabalhar num branch não afeta os outros: cada commit só avança o ponteiro do branch onde você está.

grafo de commits
# Antes: ambos os branches apontam para C
A <- B <- C   (main, feature-login <- HEAD)

# Você está em feature-login e faz um commit D.
# Só feature-login avança; main fica parado em C.
A <- B <- C        (main)
           \
            D       (feature-login <- HEAD)

# Mais um commit E: o branch continua avançando sozinho
A <- B <- C        (main)
           \
            D <- E  (feature-login <- HEAD)

Esse desenho é o coração do trabalho paralelo. Dois colaboradores em dois branches partem do mesmo commit e cada um avança o seu ponteiro independentemente. A história diverge — formam-se dois caminhos no grafo. Reconciliar esses caminhos é o trabalho de merge (Cap 7) e rebase (Cap 8); por ora, o ponto é que a divergência é normal, esperada, e barata, porque cada branch é só um ponteiro andando.

# Fast-forward: quando o branch só desliza

Há um caso especial que vale antecipar porque ilumina o modelo. Se main aponta para C e feature está em E (descendente de C, sem que main tenha avançado), então integrar feature em main não exige criar nada: basta deslizar o ponteiro de main de C para E. Isso se chama fast-forward — não há trabalho de mesclagem, só o movimento de um ponteiro ao longo de uma linha que já existe. É o merge mais simples possível, e acontece o tempo todo.

terminal
# main em C, feature em E (descendente direto). Integrar = fast-forward:
git switch main
git merge feature
# Updating C..E
# Fast-forward    <- nenhum commit de merge criado; main só deslizou para E

# Antes:  A <- B <- C (main)  ... C <- D <- E (feature)
# Depois: A <- B <- C <- D <- E (main, feature)  <- ambos na ponta

# Renomear e apagar branches

Como branches são só ponteiros, manipulá-los é leve e seguro. Apagar um branch remove a etiqueta, não os commits — eles continuam no armazém de objetos, alcançáveis por outros branches ou pelo reflog (Cap 14). O Git protege você de apagar trabalho ainda não integrado: -d recusa apagar um branch cujos commits não estão em nenhum outro lugar, enquanto -D força.

terminal
# Renomear o branch atual
git branch -m nome-novo

# Apagar um branch já integrado (seguro: -d recusa se houver trabalho perdido)
git branch -d feature-login

# Forçar a remoção mesmo com commits não integrados (cuidado)
git branch -D experimento-abandonado
-D não apaga commits na hora, mas perde o acesso a eles
Apagar um branch com -D remove o único ponteiro nomeado para aquela linha de commits. Os objetos não somem imediatamente — ficam "órfãos" no armazém e são recuperáveis pelo reflog (Cap 14) por algumas semanas, até a coleta de lixo (git gc) removê-los de vez. Então -D não é catastrófico se você perceber rápido, mas é o tipo de operação que o -d seguro existe para evitar. Use -d por padrão; reserve -D para quando tem certeza de que o trabalho é descartável.
Convenções de nome de branch
Nomes de branch comunicam intenção. Convenções difundidas usam prefixos: feature/login-social, fix/sessao-expirada, chore/atualiza-deps. A barra não cria hierarquia real (o branch ainda é um arquivo), mas muitas ferramentas agrupam visualmente por ela. O branch padrão é main (o antigo master caiu em desuso); configure-o globalmente com git config --global init.defaultBranch main para que todo git init já nasça assim.

Capítulo 6

HEAD e detached HEAD

Os capítulos anteriores mencionaram o HEAD de passagem — "o branch atual", "onde você está". Chegou a hora de tratá-lo como o que é: a referência mais importante do Git no dia a dia, e a fonte de um dos avisos mais assustadores e mais incompreendidos da ferramenta — "you are in detached HEAD state". A maioria dos desenvolvedores encontra essa mensagem por acidente, entra em pânico e sai dela torcendo para não ter quebrado nada. Este capítulo desarma esse medo explicando exatamente o que o HEAD é, o que significa ele estar "destacado", por que esse estado existe (ele é útil, não um bug), e como entrar e sair dele com intenção. Entender o HEAD é o que conecta os ponteiros do Capítulo 5 com as operações de navegação na história que vêm a seguir.

# HEAD: o ponteiro para onde você está

O HEAD responde a uma pergunta: "qual commit a working tree reflete agora, e onde o próximo commit vai se ligar?". Normalmente, o HEAD não aponta direto para um commit — aponta para um branch, que por sua vez aponta para um commit. Essa indireção de um nível é o que faz seus commits avançarem o branch (Cap 5): você commita, o HEAD diz "estou em main", e o Git move main para o commit novo.

terminal
# O caso normal: HEAD aponta para um branch (indireção simbólica)
cat .git/HEAD
# ref: refs/heads/main   <- HEAD -> main -> commit

# Resolver onde o HEAD aponta, no fim da cadeia
git rev-parse HEAD
# 4a2b9d3... (o commit atual)

# Qual branch o HEAD segue agora
git symbolic-ref HEAD
# refs/heads/main
Dois níveis de indireção
A cadeia normal é HEAD → branch → commit → tree → .... O HEAD aponta para um branch (por nome); o branch aponta para um commit (por hash); o commit aponta para a tree e o pai (Cap 1). Quando você troca de branch (git switch), só o primeiro elo muda — o HEAD passa a apontar para outro branch. Quando você commita, só o segundo elo muda — o branch avança. Essa separação limpa é o que torna o modelo previsível.

# O que é "detached HEAD"

Há um segundo modo. Em vez de apontar para um branch, o HEAD pode apontar direto para um commit, sem branch no meio. Isso é o detached HEAD — "cabeça destacada". O nome é literal: o HEAD foi destacado do branch e fixado num commit específico. A working tree mostra aquele commit normalmente, você pode olhar arquivos, rodar a aplicação, até commitar — mas não há branch acompanhando.

terminal
# Ir direto a um commit antigo destaca o HEAD
git switch --detach HEAD~3
# (ou, comum em tutoriais: git checkout 4a2b9d3)

# Agora HEAD contém um HASH, não 'ref: refs/heads/...'
cat .git/HEAD
# 1f0c8e2a... (aponta direto para o commit, sem branch)

git status
# HEAD detached at 1f0c8e2

# Por que esse estado existe

O detached HEAD não é um erro — é um recurso. Ele permite "visitar" qualquer ponto da história sem mover nenhum branch. Você quer ver como a aplicação se comportava três versões atrás? Destaque o HEAD ali, rode os testes, inspecione. Quer testar um commit específico durante um bisect (Cap 21)? O Git destaca o HEAD automaticamente em cada candidato. É a forma do Git dizer "você está olhando o passado, em modo somente-visita — nada de permanente está acontecendo".

O cuidado vem de uma consequência do Capítulo 5: commits só são preservados de forma estável se um branch aponta para eles. Em detached HEAD, se você fizer commits e depois trocar de branch, o HEAD larga aqueles commits — e sem um branch apontando para eles, viram órfãos, candidatos à coleta de lixo. Não é que o Git os apague na hora (o reflog ainda os conhece, Cap 14), mas você perde a etiqueta que os tornava fáceis de achar.

Commits em detached HEAD podem ficar órfãos
Este é o perigo real do detached HEAD — e o motivo do aviso. Se você commitar enquanto destacado e depois fizer git switch main, esses commits deixam de ter qualquer ref apontando para eles. O Git avisa na saída: "Warning: you are leaving N commits behind". A solução é simples e o próprio Git a sugere: crie um branch antes de sair — git switch -c salva-meu-trabalho —, ancorando os commits a um ponteiro nomeado. Feito isso, eles estão tão seguros quanto qualquer outro trabalho.

# Saindo do detached HEAD

Sair é trivial quando você sabe o que quer. Se estava só olhando e não fez nada que importe, basta voltar a um branch. Se fez commits que quer manter, crie um branch a partir do HEAD atual antes de voltar — isso transforma a linha de commits órfãos numa linha de commits nomeada, indistinguível de qualquer branch normal.

terminal
# Caso 1: só estava visitando, nada a salvar — volte a um branch
git switch main

# Caso 2: fez commits em detached HEAD e quer mantê-los
# Crie um branch AQUI, ancorando os commits, e só então saia
git switch -c minha-experiencia
# Agora os commits pertencem a 'minha-experiencia' — seguros

# HEAD na navegação relativa

O HEAD é o ponto de partida da sintaxe de navegação do Capítulo 3. HEAD~1 é o pai do commit atual, HEAD~3 o tataravô, e assim por diante — sempre relativos a onde você está agora. Isso aparece em quase todo comando: resetar, comparar, inspecionar. Como o HEAD se move junto com você, essas expressões são sempre interpretadas a partir da sua posição corrente no grafo.

terminal
# Diferença entre o commit atual e o anterior
git diff HEAD~1 HEAD

# Ver o commit de três posições atrás
git show HEAD~3

# O @ é um apelido de HEAD (digita-se mais rápido)
git show @~2   # = HEAD~2
HEAD@{...}: a posição no tempo, não no grafo
Há uma segunda sintaxe que confunde por parecer com a primeira: HEAD@{2} (com chaves) não é o segundo ancestral — é onde o HEAD esteve duas movimentações atrás, segundo o reflog (Cap 14). HEAD~2 anda no grafo de commits; HEAD@{2} anda no histórico de movimentos do seu HEAD. O primeiro é geografia (ancestralidade); o segundo é cronologia (o que você fez). Confundi-los leva a resultados surpreendentes — guarde a distinção: til/circunflexo = grafo; arroba-chaves = tempo.

Capítulo 7

Merge unindo histórias

Branches divergem — é para isso que servem (Cap 5). Em algum momento, o trabalho paralelo precisa se reunir, e o merge é a operação que reconcilia dois caminhos do grafo num só. É também o ponto onde o modelo de dados do Git paga todos os dividendos: porque commits são snapshots imutáveis e o grafo registra a ancestralidade, o Git consegue descobrir sozinho como combinar duas linhas de trabalho na maioria dos casos. Este capítulo desmonta o merge em suas duas formas — o fast-forward, que só desliza um ponteiro, e o three-way merge, que cria um commit com dois pais — e explica como o Git encontra o ancestral comum que torna a fusão possível. Entender o que o merge faz por baixo é o que prepara o terreno para o contraste com o rebase (Cap 8) e para a resolução de conflitos (Cap 12).

# Duas formas de merge

O git merge tem dois comportamentos radicalmente diferentes, e saber qual vai acontecer evita surpresas. Se o branch de destino não avançou desde que o branch de origem partiu dele, o merge é um fast-forward: não há divergência real para resolver, então o Git apenas desliza o ponteiro do destino para frente (já visto no Cap 5). Se ambos os branches avançaram — divergiram de verdade —, o Git faz um three-way merge: cria um commit novo, especial, que tem dois pais e une as duas histórias.

grafo de commits
# FAST-FORWARD: main não andou desde que feature partiu
# Antes:
A <- B <- C          (main)
           \
            D <- E   (feature)
# merge: main desliza para E. Nenhum commit novo.
A <- B <- C <- D <- E   (main, feature)

# THREE-WAY: ambos andaram (divergência real)
# Antes:
A <- B <- C <- F      (main)
           \
            D <- E    (feature)
# merge: cria M com DOIS pais (F e E), unindo os caminhos
A <- B <- C <- F <- M   (main)
           \      /
            D <- E

# O ancestral comum: a base do three-way

O "three-way" tem três participantes, e identificá-los explica o algoritmo inteiro. Para mesclar feature em main, o Git acha o ancestral comum dos dois — o commit onde eles divergiram (o C do diagrama acima), chamado de merge base. Então compara três versões de cada arquivo: a da base (C), a do seu lado (main, em F) e a do outro lado (feature, em E). Para cada arquivo, decide o que fazer comparando os dois lados com a base — não os dois lados entre si.

Essa é a sacada do three-way. Se um arquivo mudou só de um lado em relação à base, o Git pega esse lado — a mudança é inequívoca. Se mudou dos dois lados mas em trechos diferentes, o Git combina as duas mudanças automaticamente. Só quando os dois lados mudaram a mesma região de formas diferentes é que o Git não consegue decidir e declara um conflito (Cap 12). A base é o que permite distinguir "uma mudança nova" de "uma mudança conflitante": sem ela, o Git só veria dois arquivos diferentes, sem saber quem mexeu no quê.

terminal
# Descobrir o ancestral comum (merge base) entre dois branches
git merge-base main feature
# C3a1f0... (o commit onde os dois divergiram)

# Ver o que cada lado adicionou desde a base (Cap 3, ranges)
git log --oneline main...feature --left-right
Por que se chama "three-way"
Um merge ingênuo (two-way) compararia só os dois arquivos finais e, ao vê-los diferentes, não saberia qual vale — todo arquivo modificado viraria conflito. O three-way adiciona a terceira referência, a base comum, e isso muda tudo: comparando cada lado com a base, o Git distingue "este lado mudou, o outro não" (aplica a mudança) de "os dois mudaram o mesmo ponto" (conflito). A base transforma um problema indecidível num problema quase sempre resolúvel automaticamente.

# Fazendo um merge

O fluxo é sempre o mesmo: vá para o branch que vai receber o trabalho e mande mesclar o outro nele. Mesclar feature em main significa estar em main e rodar git merge feature — a direção importa, pois é o branch atual que ganha o commit de merge e avança.

terminal
# Receber 'feature' em 'main': primeiro vá para main
git switch main
git merge feature

# Se for three-way, o Git abre o editor para a mensagem do commit de merge.
# Saída típica de um merge bem-sucedido:
# Merge made by the 'ort' strategy.
#  src/api.ts | 12 ++++++++++++
#  1 file changed, 12 insertions(+)

# Controlando o tipo de merge

Às vezes você quer forçar um comportamento. O --no-ff obriga a criar um commit de merge mesmo quando um fast-forward seria possível — útil para preservar no histórico o fato de que aquele grupo de commits veio de um branch de feature (muitos fluxos de PR fazem isso). O inverso, --ff-only, recusa o merge se ele não puder ser um fast-forward — uma rede de segurança para garantir histórico linear.

terminal
# Sempre criar commit de merge (preserva a "bolha" do feature no histórico)
git merge --no-ff feature

# Só aceitar se for fast-forward (garante história linear; falha se divergiu)
git merge --ff-only feature

# Mesclar sem commitar, para inspecionar o resultado antes de selar
git merge --no-commit --no-ff feature
--no-ff e a legibilidade do histórico
Um fast-forward integra os commits da feature na linha principal sem deixar marca de que formavam uma unidade. O --no-ff cria um commit de merge que agrupa visualmente aquela feature — no git log --graph, ela aparece como uma "bolha" que partiu e voltou. Equipes que valorizam ler a história em termos de features integradas (não de commits individuais) costumam padronizar --no-ff nos merges de PR. É uma escolha de legibilidade, não de correção — ambos produzem o mesmo código final.

# Abortando e desfazendo

Um merge three-way que encontra conflitos deixa o repositório num estado intermediário, esperando você resolver (Cap 12). Se você decidir que não quer seguir, --abort desfaz tudo e devolve o branch ao estado anterior ao merge. E se um merge já foi concluído mas você quer desfazê-lo, o caminho depende de ele ter sido publicado ou não — tema que conecta ao Cap 9 (revert) e à regra de ouro de não reescrever história pública.

terminal
# Conflito no meio do merge e você desistiu: volta tudo ao estado anterior
git merge --abort

# Merge já feito e ainda NÃO publicado: resetar para antes dele (Cap 15)
git reset --hard HEAD~1

# Merge já PUBLICADO: reverter com um commit novo (não reescreve história)
git revert -m 1 <hash-do-merge>   # Cap 9
Reverter um merge é mais sutil do que parece
Um commit de merge tem dois pais, então git revert precisa saber qual linha "desfazer" — daí o -m 1 (manter o primeiro pai, a linha principal). Mas reverter um merge tem uma pegadinha: o Git passa a considerar aquele branch como "já mesclado e desfeito", e mesclá-lo de novo mais tarde não traz os commits de volta automaticamente. Se você reverteu um merge e depois quer reintegrar o branch, precisará reverter o revert. Por isso, sempre que possível, prefira desfazer merges não publicados com reset (Cap 15), e reserve revert para o que já é público.

Capítulo 8

Rebase reescrevendo a base

O merge (Cap 7) une dois caminhos preservando ambos: a divergência fica registrada para sempre no grafo, com um commit de duas cabeças. O rebase resolve o mesmo problema — integrar trabalho que divergiu — por uma estratégia oposta: em vez de unir os caminhos, ele reescreve um deles para que pareça ter sido feito a partir do outro desde o início. O resultado é uma história linear, sem bifurcações. Esse contraste — preservar versus reescrever — é uma das decisões mais consequentes do uso diário do Git, e a fonte da regra mais importante do volume: nunca reescreva história que já é pública. Este capítulo mostra o que o rebase faz commit a commit, por que ele produz uma história mais limpa, o rebase interativo para arrumar commits antes de compartilhar, e exatamente quando ele é perigoso.

# Rebase: replay de commits sobre uma nova base

Lembre do Capítulo 1: o hash de um commit depende do seu pai. Mudar o pai de um commit é, portanto, criar um commit novo com o mesmo conteúdo mas hash diferente. É exatamente isso que o rebase faz, em série. Rebasear feature sobre main significa: pegar cada commit exclusivo de feature, e reaplicá-lo, um por um, a partir da ponta atual de main. Cada commit reaplicado é um commit novo (pai diferente, hash novo); os originais são abandonados.

grafo de commits
# Antes: feature partiu de C; main avançou para F
A <- B <- C <- F        (main)
           \
            D <- E      (feature)

# git rebase main (estando em feature):
# D e E são RE-CRIADOS sobre F, como D' e E' (commits novos)
A <- B <- C <- F <- D' <- E'   (feature)
                              (main ainda em F)

# Resultado: história LINEAR. Os D/E originais viram órfãos (Cap 14).

Compare com o merge do Capítulo 7. O merge teria criado um commit M com dois pais, deixando D e E onde estavam e registrando a bifurcação. O rebase, em vez disso, finge que D e E sempre foram feitos depois de F — produz D' e E' numa linha reta. O código final pode ser idêntico ao do merge, mas a forma da história é completamente diferente: uma reta contra uma bifurcação reconciliada.

A linha (D', E') de "linha" — commits novos, não os mesmos
É crucial internalizar que D' não é D "movido". D foi abandonado; D' é um commit inteiramente novo, com o mesmo diff e a mesma mensagem, mas pai diferente e, portanto, hash diferente. Tudo no Git que dependia do hash de D — outro branch apontando para ele, uma referência num PR, o commit que alguém já baixou — agora aponta para um commit que "sumiu" da linha principal. Essa é a raiz de todos os perigos do rebase, e o motivo da regra de ouro.

# Por que rebasear: história legível

O argumento a favor do rebase é a legibilidade. Um histórico cheio de merges de branches curtos vira um emaranhado de bifurcações no git log --graph — difícil de ler, difícil de seguir a evolução real do projeto. Rebasear seu branch de feature sobre a main atualizada antes de integrá-lo produz uma linha reta: primeiro todo o trabalho anterior da main, depois seus commits, em sequência limpa. O fluxo típico é "rebasear para atualizar, depois integrar".

terminal
# Sua feature ficou para trás; main avançou. Atualize por rebase:
git switch feature
git rebase main
# Seus commits são reaplicados sobre a ponta atual de main

# Agora a integração em main é um fast-forward limpo (Cap 5/7)
git switch main
git merge --ff-only feature
A regra de ouro: nunca rebaseie história pública
Como o rebase substitui commits por versões novas, rebasear commits que outras pessoas já baixaram cria caos: a história delas ainda tem os commits originais, a sua tem os reescritos, e o Git não consegue reconciliar as duas sem duplicar tudo. Só rebaseie commits que ainda são exclusivamente seus — trabalho local, não publicado, ou um branch de feature que só você usa. Uma vez que commits foram para um branch compartilhado (a main, um branch que alguém revisou), eles são públicos: a partir daí, integre com merge, não com rebase. Essa única regra evita 90% dos desastres com rebase.

# Conflitos durante o rebase

Como o rebase reaplica commits um a um, um conflito (Cap 12) pode surgir em cada commit reaplicado — diferente do merge, onde o conflito acontece uma vez só. O fluxo é resolver o conflito daquele commit, marcar como resolvido com add, e mandar o rebase continuar para o próximo. A qualquer momento você pode abortar e voltar ao estado anterior.

terminal
# Rebase parou num conflito. Resolva o arquivo, prepare-o, e continue:
git add src/api.ts
git rebase --continue

# Pular o commit atual (se ele virou redundante)
git rebase --skip

# Desistir e voltar tudo ao estado anterior ao rebase
git rebase --abort

# Rebase interativo: arrumando a casa

O recurso mais valioso do rebase no dia a dia não é mudar a base, mas reorganizar os próprios commits antes de compartilhá-los. O rebase -i (interativo) abre um editor com a lista de commits e deixa você reordená-los, fundi-los (squash), reescrever mensagens (reword), dividir ou apagar. É como você transforma um histórico bagunçado de "wip", "wip 2", "conserta typo" numa sequência limpa de commits atômicos (Cap 3) antes de abrir um PR.

terminal
# Reorganizar os últimos 4 commits interativamente
git rebase -i HEAD~4

# O editor abre com a lista (ordem cronológica, mais antigo no topo):
# pick a1b2c3 feat: estrutura do endpoint de login
# squash d4e5f6 wip                  <- funde no commit acima
# squash 7a8b9c conserta typo        <- funde também
# reword 0d1e2f feat: validacao       <- só edita a mensagem
# Comandos: pick, reword, edit, squash, fixup, drop, e reordenar linhas
squash vs fixup, e o autosquash
squash funde o commit no anterior e abre o editor para combinar as mensagens; fixup funde mas descarta a mensagem do commit fundido — perfeito para aqueles commits "conserta o anterior". Há um fluxo automatizado: ao fazer um ajuste, commite com git commit --fixup <hash>, e depois rode git rebase -i --autosquash — o Git já posiciona os fixups no lugar certo. É a forma mais limpa de manter commits atômicos sem trabalho manual de reordenação.

# Merge ou rebase: a decisão

Não há resposta universal — há uma escolha de filosofia sobre o que a história deve registrar. Quem prefere merge valoriza a fidelidade: a história mostra exatamente o que aconteceu, inclusive a divergência e o momento da integração, e nunca reescreve nada. Quem prefere rebase valoriza a legibilidade: a história é uma narrativa linear e curada, mais fácil de ler depois. Muitas equipes combinam os dois — rebase para limpar e atualizar branches locais antes de integrar, merge (com --no-ff) para registrar a integração da feature na linha principal. O que não muda é a regra de ouro: rebase só no que é privado.

Capítulo 9

Cherry-pick e revert

Merge e rebase movem conjuntos de commits entre branches. Mas às vezes você quer operar sobre um commit específico: levar só aquela correção para outro branch, ou desfazer só aquela mudança que quebrou produção. Cherry-pick e revert são as ferramentas cirúrgicas para isso, e ambas se entendem melhor à luz de uma ideia do Capítulo 8: um commit pode ser tratado como um conjunto de mudanças (um diff em relação ao seu pai) que pode ser reaplicado — ou aplicado ao contrário — em qualquer ponto da história. O cherry-pick reaplica o diff de um commit em outro lugar; o revert aplica o diff invertido para anular uma mudança. Este capítulo mostra os dois, e por que o revert é a forma correta de desfazer algo que já é público — fechando o arco da regra de ouro dos capítulos anteriores.

# O commit como um diff aplicável

Até aqui tratamos o commit como um snapshot (Cap 1). Para cherry-pick e revert, é mais útil a outra visão: cada commit também é uma mudança — a diferença entre a sua tree e a do seu pai. O Git calcula esse diff sob demanda, e pode reaplicá-lo a partir de qualquer commit-base. É essa dualidade (snapshot armazenado, diff calculável) que permite "pegar a mudança deste commit e aplicá-la noutro lugar" sem mover o commit original.

# Cherry-pick: levar um commit para outro branch

O cherry-pick pega o diff de um ou mais commits e os reaplica no branch atual, criando commits novos. O caso clássico: uma correção urgente foi feita num branch de desenvolvimento, mas precisa ir agora para o branch de produção, sem arrastar junto todo o resto do desenvolvimento. Você vai para produção e "colhe" só aquele commit.

terminal
# A correção está em 'develop' (commit abc1234), precisa ir para produção
git switch producao
git cherry-pick abc1234
# Cria um commit NOVO em 'producao' com o mesmo diff (hash diferente)

# Colher um intervalo de commits (exclusivo..inclusivo)
git cherry-pick abc1234..def5678

# Colher sem commitar, para ajustar antes de selar
git cherry-pick -n abc1234
Cherry-pick cria um commit novo, não copia o original
Como no rebase (Cap 8), o commit colhido é um commit novo: mesmo diff, mesma mensagem, mas pai diferente e hash diferente. Isso tem uma consequência prática: se mais tarde você mesclar os dois branches, o Git pode ver "a mesma mudança" chegando por dois caminhos (o original e o colhido) e, na maioria dos casos, lida bem com isso — mas pode gerar conflito se as mudanças ao redor divergiram. Cherry-pick é ideal para casos pontuais (um hotfix urgente); não é substituto para merge/rebase como forma regular de integrar branches.

# Revert: desfazer aplicando o inverso

O revert faz o oposto do cherry-pick: pega o diff de um commit e aplica-o invertido, criando um commit novo que anula exatamente aquela mudança. O ponto central — e o que o distingue do reset (Cap 15) — é que o revert não apaga nada da história. Ele adiciona um commit que diz "desfaz o que aquele commit fez". A mudança original continua visível na história; por cima dela, há o registro explícito de que foi revertida.

terminal
# O commit bad9999 quebrou produção. Reverter cria um commit que o anula:
git revert bad9999
# Abre o editor com uma mensagem padrão: "Revert: ..."

# A história fica assim (nada removido; um commit a mais por cima):
# ... <- bad9999 (a mudança ruim) <- R (desfaz bad9999)

# Reverter sem commitar na hora (para agrupar vários reverts)
git revert -n bad9999

# Revert é o "desfazer" do que é público

Aqui o arco dos capítulos anteriores se fecha. A regra de ouro diz: não reescreva história pública (Caps 3, 8). Mas e quando algo que já é público precisa ser desfeito? A resposta é o revert. Como ele desfaz adicionando um commit novo — sem alterar os commits existentes —, ele respeita a regra: a história de todos continua válida, e o "desfazer" é apenas mais um passo à frente que todos recebem normalmente no próximo pull (Cap 11). Onde o reset reescreveria (apropriado só para o que é privado), o revert avança (apropriado para o que é compartilhado).

reset apaga, revert anula — escolha pela visibilidade
A decisão entre reset (Cap 15) e revert tem uma regra simples baseada em uma pergunta: o commit já saiu da minha máquina? Se não (trabalho local, não publicado), reset é limpo — apaga o commit como se nunca tivesse existido. Se sim (já está num branch que outros têm), revert é o único caminho seguro — anula o efeito sem mexer no que os outros já baixaram. Aplicar reset em algo público recria o caos do rebase público; aplicar revert em algo privado funciona, mas deixa um commit de "desfazer" desnecessário num histórico que você poderia simplesmente ter limpado.

# Conflitos em cherry-pick e revert

Ambas as operações reaplicam um diff, e um diff pode não encaixar limpo no contexto de destino — gerando conflito (Cap 12), exatamente como no merge e no rebase. O fluxo de resolução é o mesmo, com verbos próprios de cada comando para continuar ou abortar.

terminal
# Cherry-pick conflitou: resolva o arquivo, prepare-o, e continue
git add src/api.ts
git cherry-pick --continue
git cherry-pick --abort   # ou desistir

# Revert conflitou: mesmo padrão
git revert --continue
git revert --abort
Revert de um commit de merge precisa de -m
Como visto no Cap 7, um commit de merge tem dois pais, e o Git não sabe qual lado você quer "desfazer". É preciso indicar a linha principal com -m 1 (manter o primeiro pai). E lembre da pegadinha: reverter um merge não "desmescla" o branch para sempre — o Git passa a considerá-lo já integrado, e reintegrá-lo depois exigirá reverter o próprio revert. Reverter merges é legítimo, mas planeje a reintegração com cuidado, ou prefira desfazer merges não publicados com reset (Cap 15).

Capítulo 10

Remotos e tracking branches

Os nove capítulos anteriores trataram o Git como um sistema local: objetos, branches e operações dentro de um único .git/. Mas a razão de o Git existir é a colaboração — vários desenvolvedores, em várias máquinas, trabalhando no mesmo projeto. Um remoto é a ponte entre repositórios: outra cópia do projeto, normalmente num servidor (GitHub, GitLab), com a qual a sua cópia troca commits. O ponto que mais confunde aqui é que o Git é distribuído: não existe um "servidor central" privilegiado no sentido técnico — cada clone é um repositório completo, com toda a história. O que chamamos de "o servidor" é só um remoto que a equipe combinou de tratar como ponto de encontro. Este capítulo explica o que é um remoto, como os remote-tracking branches espelham o estado do servidor localmente, e por que essa separação entre "meu branch" e "o que eu vi do branch dele" é a chave para entender fetch, pull e push (Cap 11).

# Git é distribuído: cada clone é completo

Diferente de sistemas centralizados antigos, onde o servidor guardava a história e os clientes tinham só uma cópia de trabalho, no Git cada clone contém o repositório inteiro — todos os commits, todos os branches, toda a história, no .git/ local. Você pode commitar, criar branches, ver o log e mesclar sem nenhuma conexão de rede. A rede só entra quando você quer sincronizar com outra cópia. Essa é a natureza distribuída: o "servidor" não tem nada que o seu clone não tenha; ele é apenas o remoto que todos elegeram como ponto comum.

terminal
# Clonar = copiar o repositório inteiro + configurar um remoto chamado 'origin'
git clone https://github.com/usuario/projeto.git

# Listar os remotos configurados (clone cria 'origin' automaticamente)
git remote -v
# origin  https://github.com/usuario/projeto.git (fetch)
# origin  https://github.com/usuario/projeto.git (push)
"origin" é só um nome, não algo especial
origin é o nome padrão que o git clone dá ao remoto de onde você clonou — pura convenção, não uma palavra mágica. Você pode renomeá-lo, ter vários remotos (um origin para o seu fork, um upstream para o repositório original — fluxo comum em open source), ou nenhum (um repositório puramente local). Um remoto é apenas um apelido para uma URL de outro repositório, guardado em .git/config.

# Remote-tracking branches: o espelho do servidor

Aqui está o conceito central do capítulo, e o mais subestimado. Quando você se comunica com um remoto, o Git mantém localmente um conjunto especial de referências que espelham o estado dos branches daquele remoto: os remote-tracking branches, com nomes como origin/main. Eles não são branches seus — você não commita neles. São fotografias: "da última vez que falei com o origin, o branch main dele estava neste commit". Ficam em .git/refs/remotes/, separados dos seus branches em refs/heads/.

terminal
# Seus branches locais
cat .git/refs/heads/main
# 4a2b9d3... (onde VOCÊ está)

# O espelho do main do servidor (atualizado só quando você sincroniza)
cat .git/refs/remotes/origin/main
# 1f0c8e2... (onde o main do servidor estava na última vez que você viu)

# Listar todos os branches, locais e remote-tracking
git branch -a
# * main
#   remotes/origin/main
#   remotes/origin/feature-x

Essa separação é o que torna o modelo distribuído compreensível. main é o seu branch — onde você trabalha. origin/main é o seu conhecimento do branch do servidor — uma cópia local que só se atualiza quando você explicitamente busca novidades (Cap 11). Entre uma sincronização e outra, os dois podem divergir: você avança o seu main com commits locais, e enquanto isso o main do servidor avança com commits de colegas — mas o seu origin/main permanece congelado na última foto, até você buscar de novo.

origin/main está sempre "atrasado" — por design
O erro conceitual mais comum é achar que origin/main reflete o estado atual do servidor em tempo real. Não reflete: é a última foto que você baixou. Se um colega fez push há cinco minutos e você não buscou desde então, o seu origin/main não sabe disso. Por isso o git fetch (Cap 11) existe — é o ato de atualizar essas fotos. Compreender que origin/main é um cache local, não uma janela ao vivo, explica por que às vezes o Git diz que seu branch está "atualizado" e o push falha mesmo assim: você está comparando com uma foto velha.

# Tracking: ligando um branch local ao remoto

Um branch local pode estar associado a um remote-tracking branch — uma relação chamada de upstream ou tracking. Quando main rastreia origin/main, o Git sabe, sem você dizer, de onde puxar e para onde empurrar, e ainda informa quão à frente ou atrás você está. O git clone configura isso automaticamente para o branch principal; ao criar um branch novo que vai para o servidor, você estabelece o tracking no primeiro push.

terminal
# Ver a relação de tracking e o status à frente/atrás
git status -sb
# ## main...origin/main [ahead 2, behind 1]
#    ^seu   ^upstream   ^2 commits seus não enviados, 1 do servidor não baixado

# Estabelecer tracking ao enviar um branch novo pela primeira vez
git push -u origin feature-login
# -u (--set-upstream) liga feature-login -> origin/feature-login

# Ver o upstream de cada branch local
git branch -vv

O [ahead 2, behind 1] do git status é a informação mais útil que o tracking fornece, e só faz sentido com tudo deste capítulo no lugar: o Git compara o seu main com a foto origin/main e conta os commits exclusivos de cada lado (os ranges do Cap 3). "Ahead 2" são dois commits seus que o servidor — na última foto — não tinha. "Behind 1" é um commit que a foto tem e o seu branch não. Resolver essa divergência é exatamente o trabalho de pull e push do próximo capítulo.

# Gerenciando remotos

Remotos são entradas de configuração simples, fáceis de adicionar, renomear e remover. Os casos comuns: adicionar um upstream ao trabalhar com um fork, trocar a URL ao migrar de HTTPS para SSH, ou limpar referências de branches que já foram apagados no servidor.

terminal
# Adicionar um segundo remoto (fluxo de fork: origin = seu, upstream = original)
git remote add upstream https://github.com/original/projeto.git

# Trocar a URL de um remoto (ex.: HTTPS -> SSH)
git remote set-url origin git@github.com:usuario/projeto.git

# Limpar remote-tracking branches que não existem mais no servidor
git remote prune origin
# (ou git fetch --prune para buscar e limpar de uma vez)
HTTPS ou SSH?
A URL do remoto define o protocolo de autenticação. HTTPS (https://...) usa usuário/token e funciona em qualquer rede, inclusive atrás de proxies corporativos restritivos — daí ser o padrão recomendado por muitas plataformas. SSH (git@host:...) usa um par de chaves configurado uma vez, dispensando digitar credenciais a cada push. Em ambos, nunca se autentica com senha de conta direto — HTTPS usa personal access tokens, conectando à disciplina de segredos do Vol XIII (Cap 22): o token é um segredo, tratado como tal, fora do código.

Capítulo 11

Fetch, pull e push

O Capítulo 10 montou o cenário: o seu branch local, a foto origin/main que espelha o servidor, e a divergência que surge entre eles. Este capítulo é sobre os três verbos que movem commits através dessa ponte — e sobre por que separá-los importa. fetch baixa novidades sem tocar no seu trabalho; pull baixa e integra de uma vez; push envia os seus commits. A maioria dos desenvolvedores usa pull no automático e ocasionalmente se vê num emaranhado de merges acidentais ou num push rejeitado que não entende. A cura é enxergar o que cada comando faz em termos das fotos e ponteiros do Capítulo 10: fetch atualiza a foto, pull = fetch + integração, push atualiza o servidor. Com esse modelo, sincronizar deixa de ser um ritual e vira uma operação previsível.

# Fetch: atualizar a foto, sem mexer no seu trabalho

O git fetch faz uma coisa só, e é a mais segura de todas: baixa os commits novos do remoto e atualiza os remote-tracking branches (as fotos origin/* do Cap 10). Ele não toca nos seus branches locais nem na sua working tree. Depois de um fetch, origin/main reflete o estado atual do servidor, mas o seu main continua exatamente onde estava. Você ganhou informação — "o servidor avançou para cá" — sem que nada do seu trabalho mudasse.

terminal
# Baixar novidades e atualizar as fotos origin/* (seguro, não integra nada)
git fetch origin

# Agora você pode inspecionar o que chegou ANTES de integrar:
git log --oneline main..origin/main   # o que o servidor tem e eu não
git diff main origin/main               # as diferenças, em detalhe

# Buscar e limpar branches que não existem mais no servidor
git fetch --prune
fetch primeiro, decidir depois
O hábito que mais reduz surpresas é separar "ver o que mudou" de "integrar". Um git fetch seguido de git log main..origin/main mostra exatamente o que chegou, sem comprometer você a nada. Só então você decide como integrar — merge ou rebase (Caps 7-8). O git pull junta esses dois passos, o que é conveniente mas esconde a decisão de integração; quando o pull surpreende, é quase sempre porque a parte de integração fez algo que você não escolheu conscientemente.

# Pull: fetch + integração

O git pull é literalmente dois comandos num: um fetch seguido de uma integração do remote-tracking branch no seu branch local. A pergunta crucial é qual integração — merge ou rebase? — porque isso determina a forma da sua história (todo o Cap 8). Por padrão o pull faz merge, o que, quando há divergência, cria um commit de merge. Configurado para rebase, ele reaplica os seus commits locais sobre o que veio do servidor, mantendo a linha reta.

terminal
# pull = fetch + merge (padrão): cria commit de merge se houver divergência
git pull origin main

# pull com rebase: reaplica seus commits locais sobre origin/main (linha reta)
git pull --rebase origin main

# Definir o padrão de uma vez (recomendado para histórico limpo):
git config --global pull.rebase true
# E recusar pulls ambíguos quando não há fast-forward:
git config --global pull.ff only
O "merge commit acidental" do pull padrão
Cenário clássico: você fez um commit local, um colega fez push de outro commit, e você dá git pull. Como ambos divergiram de origin/main, o pull padrão (merge) cria um commit de merge — muitas vezes indesejado, poluindo a história com "Merge branch 'main' of origin..." para uma divergência trivial de um commit. Configurar pull.rebase true resolve: em vez do merge, seus commits são reaplicados sobre os do colega, sem commit de merge. A ressalva da regra de ouro (Cap 8) ainda vale — mas aqui ela está sendo aplicada aos seus commits locais ainda não publicados, então é seguro.

# Push: enviar os seus commits

O git push é o inverso do fetch: envia os seus commits locais para o remoto e avança o branch do servidor. Ele só funciona limpo num caso — quando o seu push é um fast-forward do branch remoto, ou seja, quando você tem todos os commits que o servidor tem mais alguns a frente. Se o servidor avançou desde a sua última sincronização (você está "behind"), o Git rejeita o push para não sobrescrever o trabalho que chegou: você precisa primeiro integrar (pull) e só então enviar.

terminal
# Enviar commits do branch atual para o seu upstream
git push

# Primeiro push de um branch novo: cria no servidor e estabelece tracking
git push -u origin feature-login

# Push rejeitado? O servidor avançou. Integre primeiro, depois reenvie:
# ! [rejected] main -> main (fetch first)
git pull --rebase
git push

# Force push: o necessário e o perigoso

Há um caso em que o push rejeitado é legítimo e você precisa sobrescrever: depois de rebasear um branch de feature seu (Cap 8), os commits foram reescritos, então o seu branch local "diverge" da versão antiga no servidor. Forçar o push é necessário aqui — mas o --force cru é perigoso, pois sobrescreve cegamente, podendo apagar commits que um colega tenha enviado nesse meio-tempo. A versão segura é --force-with-lease: ela só força se o servidor ainda estiver onde você espera, recusando se alguém empurrou algo que você não viu.

terminal
# Você rebaseou SEU branch de feature; precisa reenviar a versão reescrita.
# NUNCA use --force cru: pode apagar trabalho que chegou sem você ver.
#   git push --force            <- perigoso

# Versão segura: só força se o servidor estiver onde você acha que está
git push --force-with-lease origin feature-login
# Se um colega empurrou nesse meio-tempo, o push é RECUSADO (você confere antes)
Force push só em branches que são seus
Force push reescreve o branch no servidor — é a versão remota da regra de ouro (Cap 8). Em um branch de feature pessoal (que só você usa, típico antes de um PR), é uma operação rotineira e segura com --force-with-lease. Em um branch compartilhado como main, é quase sempre um desastre: você reescreve a história que toda a equipe tem, e cada colega terá conflitos terríveis no próximo pull. A regra prática: force push nunca em main ou em branches que outros usam; com lease nos seus branches de feature; cru, praticamente nunca.

# O ciclo completo de sincronização

Juntando tudo, o ciclo diário de colaboração tem uma forma estável. Você começa o dia atualizando, trabalha localmente fazendo commits, atualiza de novo antes de integrar (resolvendo divergências por rebase), e envia. Cada passo agora tem um significado mecânico claro em termos de fotos e ponteiros.

terminal
# 1. Atualizar a foto do servidor
git fetch origin

# 2. Trabalhar: commits locais (avançam só o seu branch)
git add . && git commit -m 'feat: ...'

# 3. Integrar novidades do servidor por rebase (mantém linear)
git pull --rebase

# 4. Enviar (agora é fast-forward, aceito limpo)
git push

Capítulo 12

Resolução de conflitos

Conflitos assustam porque chegam no meio de outra operação — um merge, um rebase, um cherry-pick — e param tudo com mensagens que parecem dizer que algo quebrou. Nada quebrou. Um conflito é o Git sendo honesto: ele chegou num ponto onde dois lados mudaram a mesma região de um arquivo de formas incompatíveis, e — como vimos no three-way merge (Cap 7) — ele não tem base para decidir qual vale. Em vez de adivinhar e arriscar destruir trabalho, ele para e pede a você, a única pessoa que conhece a intenção, para decidir. Este capítulo desmistifica o processo: o que os marcadores de conflito significam, como o index guarda as três versões durante a disputa (Cap 4), o fluxo de resolução, e os hábitos que tornam conflitos raros e rápidos. Conflitos são parte normal de colaborar; a competência está em resolvê-los com calma, não em evitá-los a todo custo.

# Por que conflitos acontecem

O Git resolve automaticamente quase tudo (Cap 7): se um lado mudou um arquivo e o outro não, ele aplica a mudança; se os dois mudaram regiões diferentes do mesmo arquivo, ele combina as duas. O conflito surge no caso restante e específico: os dois lados mudaram a mesma região de formas diferentes. Aí não há combinação possível sem perder a intenção de um deles, e o Git se recusa a escolher por você. Note o que isso implica — conflitos são proporcionais à sobreposição do trabalho, não ao seu volume. Dois branches enormes que mexem em arquivos distintos mesclam sem um arranhão; duas linhas que tocam a mesma função conflitam.

Conflito não é erro — é uma pergunta
A mensagem "CONFLICT (content): Merge conflict in src/api.ts" não relata uma falha; relata uma decisão pendente. O Git fez tudo que podia automaticamente e isolou os pontos exatos onde precisa de você. A operação (merge, rebase, etc.) fica pausada num estado intermediário, esperando. Você não está num beco sem saída: pode resolver, ou pode abortar (--abort) e voltar ao estado anterior como se nada tivesse começado. Encarar o conflito como "o Git me perguntando algo" em vez de "o Git quebrou" muda toda a relação com a operação.

# Lendo os marcadores de conflito

Quando há conflito, o Git edita o arquivo afetado inserindo marcadores que delimitam as versões em disputa. Entender essa anatomia é o essencial do capítulo. O bloco superior, entre <<<<<<< e =======, é a sua versão (a do branch atual, HEAD). O bloco inferior, entre ======= e >>>>>>>, é a versão que chega (a do branch sendo incorporado).

src/api.ts (com conflito)
export const TIMEOUT = 5000

<<<<<<< HEAD                    // início da SUA versão (branch atual)
export const RETRIES = 3
=======                          // divisor entre as duas versões
export const RETRIES = 5
>>>>>>> feature-retry            // fim da versão QUE CHEGA (branch incorporado)

export const BASE_URL = '/api'

Resolver o conflito é editar esse trecho para o que você quer que fique — e remover os três marcadores. Você pode ficar com a sua versão, com a que chega, com uma combinação das duas, ou com algo inteiramente novo. O Git não impõe nenhuma dessas; ele só marcou a região e devolveu a decisão. O conteúdo fora dos marcadores (as linhas TIMEOUT e BASE_URL acima) foi mesclado automaticamente e não está em disputa — só o miolo entre os marcadores precisa da sua mão.

Esquecer um marcador é um bug silencioso
O erro mais comum ao resolver à mão é deixar um marcador para trás — um ======= ou um >>>>>>> esquecido. Como o Git só verifica que o conflito foi marcado como resolvido (um stage 0 no index, Cap 4), ele aceita o arquivo com marcadores dentro, e eles viram código inválido que quebra o build ou, pior, passa despercebido. Antes de commitar uma resolução, faça uma busca por <<<<<<< no projeto inteiro. Um hook de pre-commit (Cap 20) que recusa marcadores de conflito é a defesa automática contra isso.

# O fluxo de resolução

O processo tem sempre a mesma forma, qualquer que seja a operação que gerou o conflito. Primeiro, ver quais arquivos conflitaram. Depois, editar cada um, resolvendo os marcadores. Em seguida, marcar como resolvido com git add — que, como vimos no Capítulo 4, colapsa os três stages num só. Por fim, concluir a operação que estava pausada.

terminal
# 1. Ver os arquivos em conflito
git status
# Unmerged paths:
#   both modified:   src/api.ts

# 2. Editar cada arquivo, resolvendo os marcadores (no editor)

# 3. Marcar como resolvido (colapsa os 3 stages para stage 0)
git add src/api.ts

# 4. Concluir a operação pausada (o verbo depende dela)
git commit                # se era um merge (usa a mensagem padrão)
# git rebase --continue       se era um rebase (Cap 8)
# git cherry-pick --continue  se era um cherry-pick (Cap 9)

# Ferramentas que facilitam a leitura

Editar marcadores na mão funciona, mas o Git oferece atalhos para casos comuns e visões melhores. Quando você sabe que quer um lado inteiro, --ours e --theirs resolvem sem edição manual. E o formato diff3 melhora a leitura ao mostrar também a base comum (Cap 7) entre os dois lados, revelando o que cada um mudou em relação ao ponto de partida — muitas vezes a informação que torna óbvia a resolução.

terminal
# Ficar com um lado inteiro do arquivo, sem editar marcadores:
git checkout --ours src/config.ts     # a minha versão (HEAD)
git checkout --theirs src/config.ts   # a versão que chega
git add src/config.ts

# Ativar o formato diff3, que mostra a BASE comum entre os marcadores:
git config --global merge.conflictStyle zdiff3
# Agora o conflito mostra 3 seções: HEAD, base original, e o que chega

# Abrir uma ferramenta visual de merge configurada
git mergetool
"ours" e "theirs" invertem no rebase
Cuidado com uma sutileza que pega muita gente: no merge, --ours é o seu branch e --theirs é o que chega — intuitivo. No rebase, os papéis invertem, porque o rebase reaplica os seus commits sobre o outro branch: do ponto de vista interno, "ours" passa a ser o branch base (sobre o qual você rebaseia) e "theirs" os seus próprios commits sendo reaplicados. Quando estiver resolvendo conflitos num rebase e --ours/--theirs parecerem trocados, é porque estão — confie no conteúdo que você lê nos marcadores, não no rótulo.

# Tornando conflitos raros e baratos

Conflitos não se eliminam, mas se minimizam com hábitos. Integrar com frequência — rebasear ou mesclar a main no seu branch todo dia — mantém a divergência pequena, então cada conflito é minúsculo. Branches curtos conflitam menos que branches que vivem semanas acumulando divergência. Commits atômicos (Cap 3) tornam a resolução mais clara, porque cada conflito tem um propósito legível. E quando um conflito for grande e confuso demais, lembre que --abort sempre devolve o estado anterior — recuar, entender melhor e tentar de novo é legítimo.

terminal
# Abortar e voltar ao estado anterior — sempre disponível, sem prejuízo
git merge --abort
# git rebase --abort   /   git cherry-pick --abort

# Hábito que reduz conflitos: integrar a main no seu branch com frequência
git switch feature
git fetch origin
git rebase origin/main   # divergência pequena = conflitos pequenos

Capítulo 13

Stash guardando o trabalho em curso

Você está no meio de uma mudança, nada pronto para commitar, e surge uma urgência: um bug em produção que precisa de correção agora, num outro branch. Trocar de branch carregaria suas mudanças não commitadas junto — ou o Git recusaria a troca para não atropelá-las. O stash resolve esse impasse: guarda temporariamente o trabalho em curso num canto, limpa a working tree, e devolve tudo quando você voltar. É a gaveta do Git — um lugar para pôr o que está pela metade sem precisar fazer um commit incompleto. Este capítulo mostra como o stash funciona (spoiler: são commits disfarçados), como guardar e recuperar, a pilha de stashes, e os casos onde ele brilha — e o aviso de que uma gaveta cheia de coisas esquecidas é uma forma silenciosa de perder trabalho.

# O problema que o stash resolve

O Git protege trabalho não commitado: se você tentar trocar de branch com mudanças locais que colidiriam com o branch de destino, ele recusa, para não sobrescrever o que você fez. Mas nem sempre você quer commitar — o trabalho está incompleto, não merece entrar na história ainda. O stash dá a terceira via: nem carregar as mudanças, nem commitá-las, mas reservá-las. Ele tira as mudanças da working tree e do index, guarda-as à parte, e deixa a working tree limpa, como no último commit — livre para trocar de branch.

terminal
# Trabalho pela metade, e surge uma urgência em outro branch.
# Guardar tudo e limpar a working tree:
git stash
# Saved working directory and index state WIP on feature: 4a2b9d3 ...

# Agora a working tree está limpa — livre para trocar de branch
git switch producao
# ... corrige o bug urgente, commita, volta ...
git switch feature

# Recuperar o trabalho guardado de volta na working tree
git stash pop
Stashes são commits disfarçados
Fiel ao modelo do Capítulo 1, o stash não é um mecanismo paralelo: cada stash é guardado como commits comuns no armazém de objetos — tipicamente um commit para o estado da working tree e outro para o index, presos a uma ref especial (refs/stash) em vez de a um branch. Por isso o stash preserva fielmente tudo (inclusive o que estava staged separadamente) e por isso ele aparece no reflog (Cap 14). Saber que é "só commits numa ref escondida" desmistifica o comando e explica por que stashes perdidos podem ser recuperados.

# pop, apply e a diferença

Há dois verbos para recuperar um stash, e a diferença importa. git stash pop aplica o stash e o remove da pilha — o fluxo normal, "tirei da gaveta, usei, gaveta vazia". git stash apply aplica mas mantém o stash guardado — útil quando você quer aplicar a mesma mudança guardada em mais de um branch, ou ter uma rede de segurança caso a aplicação dê conflito.

terminal
# Aplicar e remover da pilha (o caso comum)
git stash pop

# Aplicar mas MANTER guardado (para reaplicar noutro branch, p.ex.)
git stash apply

# Listar a pilha de stashes (sim, podem ser vários)
git stash list
# stash@{0}: WIP on feature: 4a2b9d3 ajusta validacao
# stash@{1}: WIP on main: 1f0c8e2 experimento de layout
pop com conflito não esvazia a gaveta
Uma pegadinha: se o git stash pop gera conflito ao reaplicar (porque o branch mudou desde que você guardou), o Git aplica o que consegue, marca o conflito — mas não remove o stash da pilha, justamente para você não perdê-lo se a resolução der errado. Muita gente resolve o conflito e segue achando que a gaveta esvaziou, deixando o stash acumulado lá. Depois de resolver um pop conflituoso, confira com git stash list e remova manualmente com git stash drop se já estiver tudo certo.

# Stash seletivo e com untracked

Por padrão o stash guarda mudanças em arquivos rastreados (tracked), mas deixa de fora arquivos novos (untracked) e ignorados. Frequentemente você quer incluir os untracked — um arquivo novo que faz parte do trabalho em curso. Há flags para isso, além de poder nomear o stash para lembrar do que era.

terminal
# Incluir arquivos novos (untracked) no stash
git stash -u

# Dar um nome ao stash, para reconhecê-lo na lista depois
git stash push -m 'metade do refactor do login'

# Guardar apenas arquivos específicos
git stash push -m 'só o css' -- src/styles.css

# Ver o conteúdo de um stash antes de aplicar
git stash show -p stash@{0}

# Limpando a gaveta

A pilha de stashes precisa de manutenção. Stashes individuais se removem com drop; a pilha inteira, com clear. E um stash pode virar um branch próprio com branch — útil quando o trabalho guardado cresceu e merece seguir como uma linha de desenvolvimento de verdade.

terminal
# Remover um stash específico
git stash drop stash@{1}

# Esvaziar a pilha inteira (irreversível pela interface normal)
git stash clear

# Promover um stash a branch (parte do commit onde foi criado)
git stash branch feature-retomada stash@{0}
O stash é gaveta, não armário
O stash brilha para o que é genuinamente temporário — minutos ou horas, uma interrupção rápida. Ele é péssimo como armazenamento de longo prazo: stashes não têm nome descritivo por padrão, não aparecem em git log, não são compartilhados num push, e somem da memória depressa. Trabalho que vai esperar dias merece um branch (um git switch -c wip-algo e um commit), não um stash. A regra: se você não vai recuperar até o fim do dia, faça um commit num branch em vez de empilhar na gaveta — commits têm nome, história e sobrevivem; stashes esquecidos são trabalho perdido à espera de acontecer.

Capítulo 14

Reflog e recuperação

Vários capítulos anteriores fizeram a mesma promessa em voz baixa: "não se preocupe, o reflog sabe onde estava". Commits órfãos após um detached HEAD (Cap 6), commits abandonados por um rebase (Cap 8), um branch apagado com -D (Cap 5), um reset --hard precipitado (Cap 15) — em todos esses casos, o trabalho parece ter sumido, e quase sempre não sumiu. O reflog é a rede de segurança que torna o Git muito mais perdoável do que sua reputação sugere. Ele registra cada movimento das suas referências, permitindo voltar a estados que nenhum branch aponta mais. Este capítulo explica o que o reflog grava, como usá-lo para recuperar o "irrecuperável", e por que entender essa rede transforma a relação com operações arriscadas — você opera com mais coragem quando sabe que há um caminho de volta.

# O que o reflog registra

Toda vez que uma referência se move — o HEAD muda de commit, um branch avança, você troca de branch, reseta, rebaseia — o Git anota esse movimento num log local: o reflog (reference log). Cada entrada guarda o commit para onde a ref apontava antes e depois, com data e a operação que causou a mudança. É um diário cronológico dos seus passos, mantido em .git/logs/. Crucialmente, ele é local e privado — não viaja num push, não é compartilhado, é só o registro da sua própria atividade naquele clone.

terminal
# O histórico de movimentos do HEAD (mais recente no topo)
git reflog
# 4a2b9d3 HEAD@{0}: commit: feat: novo endpoint
# 1f0c8e2 HEAD@{1}: rebase finished: returning to refs/heads/feature
# 8c14207 HEAD@{2}: reset: moving to HEAD~3
# d4e5f6a HEAD@{3}: checkout: moving from main to feature
#    ^commit   ^posição   ^operação que causou o movimento

# O reflog de um branch específico
git reflog show feature
HEAD@{n}: navegação no tempo, não no grafo
Aqui se fecha a distinção antecipada no Capítulo 6. HEAD~2 anda dois passos no grafo de commits (dois ancestrais). HEAD@{2} anda duas posições no reflog — onde o HEAD esteve duas movimentações atrás, cronologicamente. Se você fez reset, rebase e checkout, HEAD@{3} aponta para onde estava antes dessas três ações, independentemente de relação de ancestralidade. Til/circunflexo = geografia da história; arroba-chaves = cronologia dos seus atos. O reflog é o que dá sentido à segunda sintaxe.

# Recuperando commits "perdidos"

Aqui está o superpoder. Quando uma operação deixa commits sem nenhum branch apontando para eles — órfãos —, eles continuam no armazém de objetos (Cap 1), só sem etiqueta que os torne fáceis de achar. O reflog é essa etiqueta. Ele lista os commits onde o HEAD esteve, inclusive os que nenhum branch alcança mais, e a partir do hash você recria um branch ali, ressuscitando o trabalho.

terminal
# Cenário: um reset --hard apagou commits que você afinal queria.
# 1. Achar no reflog o estado anterior ao reset:
git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~3   <- depois do reset
# 9f8e7d6 HEAD@{1}: commit: trabalho que sumiu <- o que você quer de volta

# 2. Recriar um branch no commit perdido — trabalho recuperado
git branch recuperado 9f8e7d6
# (ou: git reset --hard HEAD@{1} para voltar o branch atual àquele ponto)

# Desfazendo um rebase ruim

Um dos usos mais valiosos do reflog é reverter um rebase (Cap 8) que deu errado. Como o rebase abandona os commits originais e cria novos, "desfazê-lo" significa fazer o branch voltar a apontar para o commit-ponta de antes do rebase — que o reflog guardou. É a rede que torna o rebase, apesar de reescrever história, uma operação da qual se pode recuar.

terminal
# Rebase interativo bagunçou o branch. O reflog marca o "antes":
git reflog
# ... HEAD@{0}: rebase (finish): returning to refs/heads/feature
# ... HEAD@{5}: rebase (start): checkout main
# ... HEAD@{6}: commit: estado bom ANTES do rebase   <- o alvo

# Voltar o branch ao estado pré-rebase, descartando o rebase inteiro
git reset --hard HEAD@{6}
O reflog torna operações arriscadas reversíveis
A maior lição do reflog é psicológica. reset --hard, rebase, branch -D — operações que parecem aterrorizantes porque "destroem" trabalho — são, na prática, reversíveis enquanto o reflog lembra delas. Isso não é desculpa para imprudência, mas permite operar com confiança: você pode experimentar um rebase complicado sabendo que git reset --hard HEAD@{1} o desfaz. Antes de qualquer operação grande e arriscada, vale lembrar que o reflog está lá — ele é o "Ctrl+Z" do Git, com muitos níveis de desfazer.

# Os limites: garbage collection

A rede não é eterna, e entender por quê evita falsa segurança. Commits órfãos e entradas de reflog têm prazo de validade: por padrão, o Git mantém entradas de reflog por 90 dias (e 30 dias para commits inalcançáveis), após o que o git gc (garbage collection) pode removê-los de vez do armazém de objetos. Enquanto o reflog os referencia, eles estão protegidos da coleta; uma vez expirados, somem para sempre. Na prática, isso significa que recuperação via reflog funciona para "ops, acabei de fazer besteira", não para "aquele commit de três meses atrás".

terminal
# Listar objetos órfãos (dangling) que a coleta removeria
git fsck --unreachable

# A coleta de lixo é automática, mas pode ser disparada à mão.
# CUIDADO: prune agressivo remove órfãos imediatamente, sem rede.
git gc --prune=now   # raramente necessário; remove a chance de recuperação
O reflog é local — não substitui um remoto
Duas limitações importam. Primeira: o reflog é por clone. Ele registra a sua atividade naquele repositório local; se você apagar o .git/ ou o disco morrer, o reflog morre junto. Ele protege contra erros de comando, não contra perda da máquina. Segunda: ele não é compartilhado — não há reflog "do servidor" para recuperar o que outra pessoa perdeu. A defesa real contra perda catastrófica é ter o trabalho num remoto (Caps 10-11): faça push com frequência. O reflog te salva de um reset --hard; o remoto te salva de um HD queimado.

Capítulo 15

Reset, restore e checkout

Três comandos aparecem espalhados por todo este volume — reset, restore, checkout — e juntos formam o ponto mais confuso do Git para quem aprende. A confusão tem uma causa histórica clara: o git checkout original acumulou funções demais (trocar de branch, restaurar arquivos, destacar o HEAD), e o git reset faz coisas diferentes conforme a flag, mexendo em áreas diferentes (Cap 2). O Git moderno criou switch e restore para desmembrar o checkout sobrecarregado, mas o reset permanece, poderoso e perigoso. Este capítulo organiza os três de uma vez, à luz das três áreas (Cap 2) e do reflog (Cap 14): qual comando mexe em qual área, o que cada modo do reset faz, e quando cada um é seguro ou destrutivo. É o capítulo que transforma "tenho medo de usar reset" em "sei exatamente o que cada reset vai fazer".

# Três áreas, três alvos

A chave para organizar tudo é lembrar das três áreas do Capítulo 2 — working tree, index, repositório (HEAD/branch) — e perguntar, para cada comando, qual delas ele altera. reset mexe principalmente no branch/HEAD e no index. restore mexe na working tree e no index (arquivos). switch (Cap 5) mexe em qual branch o HEAD aponta. O checkout antigo fazia o trabalho do switch e do restore ao mesmo tempo — daí a ambiguidade que motivou a separação.

O mapa mental
switch (Cap 5) → move o HEAD para outro branch. restore → restaura conteúdo de arquivos (na working tree e/ou index), sem mexer em branches. reset → move o branch atual para outro commit, e opcionalmente arrasta index e working tree junto. O checkout faz papéis de switch e restore conforme os argumentos — funciona, mas é por isso que tutoriais antigos confundem. Use os verbos novos para clareza; reconheça o checkout porque ele é onipresente.

# restore: consertar arquivos

O restore opera sobre o conteúdo de arquivos, e tem dois alvos controlados por flags. Sem flag, ele restaura a working tree a partir do index — descartando edições não preparadas (destrutivo, já visto no Cap 2). Com --staged, ele restaura o index a partir do HEAD — tirando arquivos do stage sem perder a edição. Com ambos, restaura as duas áreas. É a ferramenta cirúrgica para mexer em arquivos sem tocar na história.

terminal
# Descartar edição não preparada (working tree volta ao index) — DESTRUTIVO
git restore src/api.ts

# Tirar do stage, preservando a edição (index volta ao HEAD) — reversível
git restore --staged src/api.ts

# Restaurar um arquivo a partir de um commit específico (não do HEAD)
git restore --source=HEAD~3 src/api.ts
# (substitui o antigo: git checkout HEAD~3 -- src/api.ts)

# reset: mover o branch, com três intensidades

O reset move o ponteiro do branch atual para outro commit. A pergunta é o que fazer com o index e a working tree ao mover — e aí entram os três modos, em intensidade crescente. --soft: move só o branch; index e working tree intactos (as mudanças dos commits "desfeitos" ficam preparadas). --mixed (padrão): move o branch e reseta o index; working tree intacta (as mudanças viram "não preparadas"). --hard: move o branch, reseta o index e a working tree — descartando tudo (destrutivo).

terminal
# --soft: desfaz o commit, mas mantém tudo PREPARADO (index e working tree)
# Uso clássico: refazer o último commit (recommitar diferente)
git reset --soft HEAD~1

# --mixed (padrão): desfaz o commit E tira do stage; edições ficam na working tree
git reset HEAD~1

# --hard: desfaz o commit e DESCARTA todas as mudanças (working tree limpa)
git reset --hard HEAD~1   # recuperável só pelo reflog (Cap 14)
o que cada reset toca
# Em intensidade crescente — cada modo arrasta mais áreas junto:
#                  branch/HEAD   index    working tree
# --soft              move        -            -          (mudanças ficam staged)
# --mixed (padrão)    move       reset        -          (mudanças não-staged)
# --hard              move       reset      reset        (mudanças DESCARTADAS)
--hard é o único que destrói trabalho não commitado
Entre todos os comandos deste capítulo, reset --hard é o de maior poder destrutivo: ele descarta mudanças não commitadas na working tree, que não estão no reflog (o reflog rastreia commits e refs, não edições soltas). Commits desfeitos pelo --hard são recuperáveis via reflog (Cap 14); edições não commitadas que ele apagar, não. Antes de um reset --hard, certifique-se de que não há trabalho não commitado que importe — ou guarde-o antes com git stash (Cap 13). É a operação onde o "tenho certeza?" do Git mais se justifica.

# Os usos canônicos do reset

Cada modo tem um caso de uso natural. O --soft HEAD~1 é a forma elegante de "refazer o último commit": desfaz o commit mas mantém tudo preparado, pronto para você recommitar com outra mensagem ou outro agrupamento. O --mixed serve para "desfazer o commit e o stage, mas continuar editando". O --hard é para "joguei fora, quero voltar limpo a este ponto". E todos respeitam a regra de ouro: só em commits não publicados.

terminal
# "Combinar os últimos 3 commits em um": soft reset + recommit
git reset --soft HEAD~3
git commit -m 'feat: tudo num commit limpo'
# (os 3 commits viram 1; alternativa não-interativa ao rebase -i)

# "Descartar tudo o que fiz desde o último push": hard reset ao upstream
git reset --hard origin/main   # joga fora commits locais não enviados
reset move o branch; em público, isso é o caos do Cap 8/11
Como o reset reescreve para onde o branch aponta, aplicá-lo a commits já publicados é a mesma classe de problema do rebase público (Cap 8) e do force push (Cap 11): a sua história diverge da dos colegas, e reenviar exige force, que sobrescreve o trabalho deles. reset é uma ferramenta de história local. Para desfazer algo público, o caminho é revert (Cap 9), que adiciona um commit em vez de mover o ponteiro. A pergunta de sempre: já saiu da minha máquina? Se sim, revert; se não, reset à vontade.

Capítulo 16

Tags e versionamento

Branches são ponteiros que se movem — toda vez que você commita, o branch avança (Cap 5). Mas às vezes você quer o oposto: marcar um ponto específico da história e fixá-lo para sempre, um marco que nunca se move. "Esta é a versão 1.0.0." "Este é o commit que foi para produção na sexta." Tags são essas marcas permanentes. Este capítulo mostra os dois tipos de tag — a leve, que é só um apelido para um commit, e a anotada, que é um objeto completo com autor, data e mensagem —, como elas se conectam ao versionamento semântico (o mesmo SemVer que o Vol XII e os releases de bibliotecas usam), e por que tags são a espinha dorsal de releases e deploys. É um capítulo curto e prático, mas central: tags são como a história ganha pontos de referência estáveis no meio de um grafo em constante movimento.

# Tag: um ponteiro que não se move

Uma tag é uma referência nomeada para um commit — como um branch, mas com uma diferença essencial: ela não acompanha novos commits. Um branch aponta para a ponta e avança quando você commita; uma tag aponta para um commit específico e fica lá, congelada, para sempre. É a ferramenta certa para marcar algo que tem identidade permanente: uma versão lançada, um marco. Enquanto branches respondem "onde está o trabalho agora?", tags respondem "onde estava a versão X?".

terminal
# Marcar o commit atual como a versão 1.0.0
git tag v1.0.0

# Marcar um commit específico do passado (não o atual)
git tag v0.9.0 9f8e7d6

# Listar tags (e filtrar por padrão)
git tag
git tag -l 'v1.*'

# Leve vs anotada

Há dois tipos de tag, e a diferença é a mesma do blob para o commit (Cap 1): uma é só um ponteiro, a outra é um objeto com metadados. A tag leve (lightweight) é apenas um nome apontando para um commit — nada mais, como um post-it. A tag anotada (annotated) é um objeto completo no armazém: guarda quem criou, quando, uma mensagem, e pode ser assinada com GPG. Para releases, use sempre a anotada — ela registra quem lançou quando e por quê, informação que a leve descarta.

terminal
# Tag leve: só um apelido para o commit (sem metadados)
git tag v1.0.0-rc1

# Tag anotada (-a): objeto completo com autor, data e mensagem
git tag -a v1.0.0 -m 'Release 1.0.0: autenticação completa'

# Inspecionar uma tag anotada (mostra metadados + o commit apontado)
git show v1.0.0
# tag v1.0.0
# Tagger: Vitor <vitor@exemplo.com>  Date: ...
# Release 1.0.0: autenticação completa
Para releases, sempre anotada
A regra prática é simples: tags leves para marcações temporárias e privadas ("estado bom antes do experimento"); tags anotadas para qualquer release público. A anotada é um objeto de primeira classe — datada, atribuída, opcionalmente assinada — que documenta o lançamento. Plataformas como o GitHub tratam tags anotadas como releases formais, e ferramentas de CI/CD (Cap 20 do Vol XV — Docker) frequentemente disparam builds e deploys ao detectar uma tag v*. Uma tag leve num release perde toda essa informação e integração.

# Versionamento semântico (SemVer)

A convenção dominante para nomear versões é o SemVer: MAJOR.MINOR.PATCH, o mesmo esquema que você viu nas versões de bibliotecas ao longo da coleção (jose@6.2.3, better-auth@1.6.14). Cada número comunica a natureza da mudança. MAJOR sobe quando há quebra de compatibilidade — código que dependia da versão anterior pode parar de funcionar. MINOR sobe quando se adiciona funcionalidade de forma retrocompatível. PATCH sobe para correções retrocompatíveis. Tags Git e SemVer se casam: cada tag vX.Y.Z marca o commit exato daquela versão.

versionamento semântico
# vMAJOR.MINOR.PATCH — cada número comunica o tipo de mudança
v1.4.2
#  │ │ │
#  │ │ └─ PATCH: correção retrocompatível (bug fix)
#  │ └─── MINOR: nova funcionalidade retrocompatível
#  └───── MAJOR: mudança incompatível (breaking change)

# Pré-lançamentos e build metadata:
v2.0.0-rc1        # release candidate (antes do 2.0.0 final)
v2.0.0-beta.3     # beta

A conexão com os Conventional Commits (Cap 3) fecha o ciclo: fix: sugere um bump de PATCH, feat: de MINOR, e um BREAKING CHANGE: de MAJOR. Ferramentas de release automatizado leem os commits desde a última tag, calculam o próximo número SemVer e criam a tag — transformando a disciplina de mensagens (Cap 3) em versionamento automático. Mensagens estruturadas e tags SemVer são duas pontas do mesmo sistema.

# Enviando tags ao remoto

Aqui mora uma pegadinha que pega quase todo mundo: tags não vão junto no git push normal. O push envia commits de branches, mas ignora tags por padrão — você precisa enviá-las explicitamente. Criar uma tag localmente e esquecer de enviá-la é a razão nº 1 de "criei o release mas ele não aparece no GitHub".

terminal
# Enviar UMA tag específica ao remoto
git push origin v1.0.0

# Enviar todas as tags de uma vez
git push --tags

# Apagar uma tag: localmente, e depois no remoto (são passos separados)
git tag -d v1.0.0
git push origin --delete v1.0.0
Não mova uma tag já publicada
Tags são marcas permanentes — e o mundo confia nessa permanência. Se você publicou v1.0.0 apontando para um commit, e depois "move" a tag para outro commit (recriando-a com -f e force push), quebra todos que já baixaram aquela versão: para eles, v1.0.0 agora significa código diferente. Gerenciadores de pacotes e deploys partem do princípio de que uma versão lançada é imutável. Se uma release saiu com defeito, a prática correta é lançar uma nova versão (v1.0.1) com a correção, nunca remarcar a antiga. É a mesma lógica da regra de ouro (Cap 8) aplicada a versões: o que é público não se reescreve.

Capítulo 17

.gitignore e atributos

Nem tudo numa pasta de projeto pertence à história. Dependências instaladas (node_modules), artefatos de build (dist), arquivos de ambiente com segredos (.env), logs, caches do editor — versionar isso polui o repositório, infla os clones e, no caso dos segredos, é uma falha de segurança direta (Vol XIII). O .gitignore é como você diz ao Git o que deliberadamente não rastrear. Este capítulo cobre a sintaxe dos padrões, a hierarquia de arquivos de ignore, a pegadinha clássica de tentar ignorar algo que já está rastreado, e — mais brevemente — o .gitattributes, o primo menos conhecido que controla finais de linha e tratamento de arquivos. É o capítulo que mantém o repositório enxuto e contém uma das conexões de segurança mais importantes do volume: o .env que nunca deve entrar.

# O que ignorar, e por quê

A regra geral: versione o que é fonte e ignore o que é derivado ou local. Código-fonte, configuração compartilhada, documentação — entram na história. Já o que pode ser regenerado a partir da fonte (artefatos de build, dependências instaladas), o que é específico da sua máquina (configs de editor, caches), e o que é secreto ou local (variáveis de ambiente) — fica de fora. Versionar dependências infla o repositório com milhares de arquivos que o npm install recria; versionar segredos os expõe permanentemente na história.

.gitignore
# Dependências (regeneráveis com npm install)
node_modules/

# Artefatos de build (regeneráveis a partir da fonte)
dist/
build/
*.tsbuildinfo

# Segredos e ambiente — NUNCA versionar (Vol XIII, Cap 22)
.env
.env.local
.env.*.local

# Local / editor / SO
.vscode/
.idea/
.DS_Store
*.log
O .env é a conexão de segurança crítica
Todo o Vol XIII gira em torno de segredos — JWT_SECRET, GOOGLE_CLIENT_SECRET, connection strings. Esses valores vivem em .env, e o .env tem que estar no .gitignore desde o primeiro commit. Um segredo commitado vaza permanentemente: mesmo que você o remova num commit seguinte, ele continua na história, recuperável por qualquer um com acesso ao repositório (e indexado para sempre se o repo for público). A prática correta é versionar um .env.example com as chaves mas sem os valores, e manter o .env real ignorado. Se um segredo já vazou, não basta removê-lo — é preciso rotacioná-lo (trocá-lo) e limpar a história, assunto do fim deste capítulo.

# Sintaxe dos padrões

Os padrões do .gitignore seguem regras de glob com algumas convenções próprias. Uma barra no fim (dir/) casa só diretórios. Uma barra no início (/arquivo) ancora o padrão na raiz do repositório. O asterisco (*) casa qualquer coisa exceto barra; o duplo (**) atravessa diretórios. E o ponto de exclamação (!) nega um padrão — reincluindo algo que uma regra anterior excluiu, o que permite exceções precisas.

.gitignore (padrões)
# Diretório (a barra final casa só pastas, não arquivos)
logs/

# Ancorado na raiz (só /config.json da raiz, não src/config.json)
/config.json

# Extensão em qualquer lugar
*.log

# Atravessar diretórios com **
**/temp/

# Negação: ignora tudo em build/, MENOS o .gitkeep
build/*
!build/.gitkeep

# A pegadinha: ignorar não desrastreia

O erro mais comum com .gitignore: adicionar um arquivo às regras e descobrir que o Git continua rastreando-o. A razão é simples e remete ao Capítulo 4 — o .gitignore só afeta arquivos untracked. Se um arquivo já está no index (já foi commitado antes), o Git continua a rastreá-lo independentemente do .gitignore; ignorar só impede que arquivos novos sejam adicionados. Para parar de rastrear algo que já entrou, é preciso removê-lo do index explicitamente, mantendo-o no disco.

terminal
# Adicionou .env ao .gitignore mas ele continua sendo rastreado?
# É porque já estava no index. Remova-o de lá (mantendo no disco, Cap 4):
git rm --cached .env
git commit -m 'chore: para de rastrear .env'

# Para uma pasta inteira já rastreada:
git rm -r --cached node_modules/

# Conferir se um arquivo está sendo ignorado e por qual regra
git check-ignore -v .env
# .gitignore:5:.env    .env

# Hierarquia e ignore global

O Git lê regras de ignore de vários lugares, em camadas. Um .gitignore pode existir em qualquer pasta e vale para aquela subárvore — o da raiz cobre o projeto, mas subpastas podem ter os seus. Além disso, há um ignore global, na sua máquina, para o que é pessoal e vale em todos os repositórios (configs do seu editor, arquivos do seu SO) — assim você não polui o .gitignore compartilhado do projeto com preferências individuais.

terminal
# Ignore global: para o que é SEU, não do projeto (editor, SO)
git config --global core.excludesfile ~/.gitignore_global

# Nesse arquivo global vão coisas pessoais como:
# .DS_Store        (macOS)
# Thumbs.db        (Windows)
# .idea/           (seu editor, se a equipe não padroniza)

# .gitattributes: finais de linha e mais

O primo menos conhecido do .gitignore é o .gitattributes, que define como o Git trata certos arquivos (em vez de se os rastreia). O uso mais importante — especialmente relevante por você estar no Windows — é normalizar finais de linha. Windows usa CRLF, Unix usa LF, e essa diferença pode fazer o Git ver "todo arquivo modificado" quando colaboradores usam sistemas diferentes. O .gitattributes com text=auto normaliza isso no repositório, eliminando a guerra de finais de linha.

.gitattributes
# Normaliza finais de linha: LF no repositório, nativo na working tree
* text=auto

# Força LF em scripts shell (quebram com CRLF), mesmo no Windows
*.sh text eol=lf

# Marca arquivos binários: o Git não tenta fazer diff/merge de linha
*.png binary
*.pdf binary
No Windows: core.autocrlf e .gitattributes
Em máquinas Windows, a configuração git config --global core.autocrlf true converte LF→CRLF ao baixar e CRLF→LF ao commitar, mantendo o repositório consistente. Mas a configuração é por máquina; o .gitattributes com * text=auto é superior porque vive no repositório — todos os colaboradores herdam a mesma regra, independentemente das configurações locais de cada um. Para projetos com colaboradores em sistemas mistos, comitar um .gitattributes é a forma robusta de acabar com os diffs fantasma de finais de linha.

Capítulo 18

Workflows de branching

Os capítulos anteriores deram as peças: branches, merge, rebase, remotos, tags. Mas peças não fazem uma equipe funcionar — é preciso um acordo sobre como usá-las. Um workflow de branching é exatamente isso: uma convenção combinada sobre quais branches existem, o que cada um significa, e como o trabalho flui de uma ideia até a produção. Não há workflow "certo" universal; há escolhas adequadas a contextos diferentes. Uma equipe que faz deploy dez vezes por dia precisa de algo diferente de uma que lança versões trimestrais. Este capítulo apresenta os dois grandes modelos — o trunk-based, simples e contínuo, e o Git Flow, estruturado e versionado — com o feature branch workflow no meio como o denominador comum. O objetivo não é prescrever um, mas dar critério para escolher e entender o que cada um otimiza.

# Por que workflows existem

Sem uma convenção, um repositório compartilhado vira caos: ninguém sabe se a main está sempre estável, onde uma feature em andamento vive, ou como uma correção urgente chega à produção sem arrastar trabalho pela metade. Um workflow responde a essas perguntas antes que elas surjam. Ele define contratos: "a main sempre reflete produção", "todo trabalho novo nasce num branch a partir da main", "nada entra na main sem revisão". Esses contratos transformam o grafo de commits — que tecnicamente admite qualquer topologia — numa estrutura previsível que a equipe consegue raciocinar em conjunto.

O denominador comum: feature branches
Quase todo workflow moderno compartilha uma base: o trabalho novo não acontece direto na main, mas num branch dedicado (uma feature branch) criado a partir dela. Você ramifica, trabalha isolado, e integra de volta quando pronto — via merge ou rebase (Caps 7-8), normalmente através de um pull request (Cap 19). Isso mantém a main sempre num estado conhecido e dá a cada trabalho um espaço próprio. Os workflows divergem no que acontece além dessa base: quantos branches de longa vida existem e como as releases são geridas.

# Feature branch workflow

O modelo mais simples que ainda escala: existe a main (sempre estável), e cada trabalho ganha um branch curto a partir dela. Quando o trabalho fica pronto e revisado, volta para a main. Não há outros branches de longa duração. É a base sobre a qual os outros modelos adicionam estrutura.

terminal
# 1. Partir da main atualizada
git switch main
git pull --rebase

# 2. Criar a feature branch (nome descritivo, Cap 5)
git switch -c feature/login-social

# 3. Trabalhar: commits atômicos (Cap 3), push para colaborar/backup
git push -u origin feature/login-social

# 4. Integrar via Pull Request (Cap 19); depois apagar o branch
git switch main && git pull
git branch -d feature/login-social

# Trunk-based development

O trunk-based leva a simplicidade ao limite e otimiza para velocidade de integração. Há um único branch de longa vida — o "tronco" (main) — e os branches de feature são extremamente curtos: horas, não dias. A ideia central é que todos integram na main com altíssima frequência, mantendo a divergência mínima e os conflitos triviais (Cap 12). É o modelo por trás da entrega contínua (CI/CD), onde cada merge na main pode disparar um deploy.

O preço dessa frequência é que a main precisa estar sempre deployável, mesmo com features incompletas integradas. A técnica que viabiliza isso são as feature flags: código novo é integrado mas fica desligado por uma chave, ativada só quando pronto. Assim, integrar não significa lançar — você integra cedo e com frequência (evitando divergência), mas controla o lançamento separadamente. Trunk-based troca a segurança de branches longos pela disciplina de integração contínua e flags.

Trunk-based combina com deploy contínuo
O trunk-based brilha em equipes com forte automação: testes automatizados robustos (que pegam regressões a cada merge), CI/CD que valida e implanta sozinho, e cultura de integrar várias vezes ao dia. Sem essa infraestrutura, integrar constantemente na main é arriscado. Com ela, é o modelo mais eficiente — minimiza o "merge hell" de branches que viveram semanas e maximiza a velocidade de feedback. É o workflow dominante em times de produto modernos que fazem deploy contínuo.

# Git Flow

No extremo oposto da simplicidade está o Git Flow, que otimiza para releases versionados e estruturados. Ele define múltiplos branches de longa vida com papéis fixos: main guarda só releases lançados (cada commit é uma versão em produção); develop é a linha de integração do trabalho em andamento; branches feature/* nascem de develop e voltam para lá; branches release/* preparam um lançamento; e hotfix/* corrigem produção urgentemente, partindo da main.

Git Flow — estrutura de branches
main      # só releases lançados; cada commit é uma versão (tag vX.Y.Z)
  └─ hotfix/*   # correção urgente de produção (parte de main, volta p/ main+develop)
develop   # linha de integração contínua do trabalho
  ├─ feature/*  # funcionalidades (partem de develop, voltam p/ develop)
  └─ release/*  # estabilização de um lançamento (develop -> main, vira tag)

# Fluxo: feature -> develop -> release -> main (tag) ; hotfix -> main + develop

Git Flow oferece estrutura e rastreabilidade fortes — sabe-se exatamente onde cada tipo de trabalho vive e como uma versão foi montada. O custo é a complexidade: muitos branches de longa vida, mais merges, mais cerimônia. Ele faz sentido para software com releases versionados explícitos — bibliotecas, aplicações desktop, produtos com múltiplas versões em suporte simultâneo. Para uma aplicação web com deploy contínuo, costuma ser excesso de estrutura: o trunk-based entrega o mesmo com muito menos atrito.

Não confunda estrutura com qualidade
Um erro comum é assumir que mais branches e mais cerimônia significam um processo "mais sério" ou mais seguro. Não significam. Git Flow numa equipe que faz deploy contínuo adiciona fricção sem benefício — branches develop e release que só atrasam a integração que o trunk-based faria direto. Por outro lado, trunk-based sem testes automatizados e CI é uma receita para quebrar a main. O workflow deve servir ao ritmo de entrega e à infraestrutura da equipe, não a uma noção abstrata de rigor. Escolha pelo contexto: cadência de release, tamanho do time, maturidade da automação.

# Escolhendo um workflow

A decisão se reduz a poucas perguntas sobre o contexto. Com que frequência você lança? Deploy contínuo (várias vezes ao dia) pede trunk-based; releases periódicos versionados pedem Git Flow. Qual a maturidade da automação? CI/CD forte habilita trunk-based; sem ela, branches mais longos dão margem de segurança. Quantas versões você mantém? Uma só (uma web app sempre na última) → simples; várias em suporte → estrutura. A maioria das equipes de produto web modernas converge para algo entre o feature branch workflow e o trunk-based, com PRs e CI — e reserva Git Flow para quando o versionamento explícito realmente importa.

Capítulo 19

Pull requests e code review

O Capítulo 18 estabeleceu que o trabalho nasce em branches e volta para a linha principal. O pull request (PR) — ou merge request, no GitLab — é o mecanismo que governa esse retorno. Ele não é um recurso do Git em si, mas das plataformas construídas sobre ele (GitHub, GitLab, Bitbucket): uma proposta formal de integrar um branch noutro, embrulhada num espaço de discussão, revisão e verificação automática. O PR é onde a colaboração técnica acontece de verdade — onde código é lido por outros olhos antes de entrar, onde testes automáticos rodam, onde decisões ficam documentadas. Este capítulo explica a anatomia de um PR, o que torna uma revisão útil, como o PR se conecta à autorização e à segurança dos volumes anteriores, e os hábitos que transformam revisão de código de gargalo burocrático em rede de qualidade.

# O que é um pull request

Tecnicamente, um PR é um pedido: "por favor, integrem os commits do meu branch feature/x no branch main". Mas o valor está no que a plataforma constrói em torno desse pedido. O PR mostra o diff completo (o que muda), permite comentários linha a linha, roda verificações automáticas (testes, lint, build), exige aprovações, e só então libera o merge. É um portão de qualidade entre "o código existe num branch" e "o código está na linha principal" — e um registro permanente de por que aquela mudança entrou.

terminal
# Fluxo até o PR: branch, commits, push
git switch -c feature/rate-limit
# ... commits atômicos (Cap 3) ...
git push -u origin feature/rate-limit

# Abrir o PR pela CLI do GitHub (gh), sem sair do terminal
gh pr create --base main --title 'feat: rate limiting no login' \
  --body 'Adiciona janela deslizante por IP e conta (Vol XIII, Cap 19).'

# Acompanhar e revisar PRs pela linha de comando
gh pr list
gh pr checkout 142   # baixar o branch de um PR para testar local

# A anatomia de um bom PR

A qualidade de um PR começa antes da revisão — no quão revisável ele é. Um PR pequeno e focado recebe revisão atenta; um PR de 2.000 linhas recebe um "aprovado" superficial porque ninguém consegue revisar 2.000 linhas com cuidado. Um PR deve fazer uma coisa, ter uma descrição que explique o porquê (o que o diff não conta), e idealmente uma sequência de commits atômicos (Cap 3) que conte a história da mudança passo a passo.

PRs pequenos são revisados de verdade
Existe uma relação inversa cruel entre o tamanho de um PR e a qualidade da revisão que ele recebe. Estudos e experiência convergem: acima de algumas centenas de linhas, a capacidade de encontrar problemas despenca — o revisor satura e passa a aprovar no automático. A solução é dividir o trabalho em PRs pequenos e sequenciais, cada um completo e revisável em minutos. Isso exige planejar a mudança em incrementos (uma habilidade), mas o retorno é revisão real em vez de carimbo. Um PR que você consegue revisar em 10 minutos pega bugs; um que leva 2 horas, não.

# O que uma boa revisão procura

Revisar código não é caçar erros de estilo — disso cuidam as ferramentas automáticas (linters, formatters). A revisão humana se concentra no que máquinas não veem: a lógica está correta? A abordagem é adequada, ou há uma forma mais simples? Há casos de borda não tratados? A mudança introduz problemas de segurança ou performance? E, crucialmente para os volumes desta coleção: a autorização foi verificada no servidor (Vol XIII, Caps 16-18)? Um segredo coou para o código (Vol XIII, Cap 22)? A revisão é onde o conhecimento dos volumes anteriores vira uma checagem prática.

checklist de revisão
# O que a revisão HUMANA procura (o que linters não pegam):

# Correção:   a lógica faz o que a descrição diz? casos de borda?
# Design:     há uma abordagem mais simples? acopla demais?

#             segredo no código (Vol XIII, 22)? SQL/XSS?

# CI: a revisão automática

Antes mesmo de um humano olhar, um PR moderno passa por verificações automáticas — a integração contínua (CI). A cada push no branch do PR, a plataforma roda um pipeline: instala dependências, roda os testes, checa lint e tipos, faz o build, e às vezes uma varredura de segurança. O PR só fica elegível para merge se tudo passar. Isso libera a revisão humana para o que importa (lógica, design) em vez de gastar atenção com "será que compila?" — a máquina já garantiu o básico.

.github/workflows/ci.yml (esqueleto)
# A cada PR, o GitHub Actions roda este pipeline antes do merge
name: CI
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci          # instala dependências
      - run: npm run lint     # estilo e regras
      - run: npm run typecheck
      - run: npm test         # testes automatizados
      # PR só fica "mergeable" se todos os passos passarem

# Estratégias de merge do PR

Ao aprovar um PR, a plataforma oferece três formas de integrá-lo, e cada uma molda a história de um jeito (ecoando os Caps 7-8). Merge commit cria um commit de merge preservando todos os commits do branch (o --no-ff do Cap 7). Squash and merge funde todos os commits do PR num único commit na main — limpa o ruído de "wip" e "conserta typo", deixando um commit por feature. Rebase and merge reaplica os commits do PR linearmente, sem commit de merge.

Squash é o padrão pragmático para muitas equipes
O squash and merge virou o padrão de muitos times de produto por um motivo: ele desacopla a higiene do branch de feature da higiene da main. Você pode commitar livremente no seu branch (commits bagunçados de "wip", úteis durante o trabalho), e na hora do merge tudo vira um único commit limpo e atômico na main, com a mensagem do PR. A main fica com uma história legível de "uma feature = um commit", e o histórico detalhado do desenvolvimento, que raramente importa depois, é descartado. A alternativa — exigir commits atômicos perfeitos no branch — é mais trabalhosa e o rebase -i (Cap 8) seria a ferramenta, mas o squash entrega o resultado limpo sem essa cerimônia.

# Branch protection: forçando o portão

As plataformas permitem tornar o PR obrigatório via regras de proteção de branch. Você pode exigir que a main só receba mudanças por PR (nunca push direto), que o CI passe, que haja N aprovações, que a discussão esteja resolvida. Isso transforma a convenção do workflow (Cap 18) num contrato aplicado — ninguém, nem por engano, empurra direto para a main. É a materialização técnica do "nada entra sem revisão", e conecta à autorização do Vol XIII: quem pode aprovar e fazer merge é uma decisão de permissão.

Revisão é proteção, não obstrução
É fácil a revisão degenerar em duas patologias opostas. De um lado, o carimbo automático — aprovar sem ler, anulando todo o benefício. De outro, o gargalo — revisões que demoram dias, bloqueando o time e incentivando PRs gigantes para "compensar" o atrito. O equilíbrio vem de PRs pequenos (revisáveis rápido), revisão como prioridade (não algo deixado para o fim do dia), e foco no que importa (lógica e segurança, deixando estilo para a automação). Uma cultura de revisão saudável acelera o time ao pegar problemas cedo — quando custam minutos — em vez de em produção, onde custam incidentes.

Capítulo 20

Hooks automatizando o Git

Vários capítulos terminaram com a mesma ideia: "um hook poderia automatizar isso". Recusar um commit com marcadores de conflito (Cap 12), barrar um segredo antes que vaze (Cap 17), garantir que os testes passem antes de um push. Hooks são scripts que o Git executa automaticamente em momentos específicos do seu ciclo — antes de um commit, depois de um merge, antes de um push. Eles transformam convenções que dependem de disciplina humana em garantias aplicadas pela máquina. Este capítulo mostra os hooks mais úteis, como eles funcionam (são apenas scripts executáveis numa pasta), a diferença crucial entre hooks locais e o que pode ser compartilhado com a equipe, e as ferramentas modernas que tornam hooks versionáveis. É o capítulo que fecha o ciclo de automação que o volume vinha prometendo.

# O que são hooks

Um hook é simplesmente um script executável que o Git roda automaticamente quando um evento acontece. Eles vivem em .git/hooks/, e o nome do arquivo determina quando o Git o chama: um arquivo chamado pre-commit roda antes de cada commit ser criado; pre-push, antes de cada push; commit-msg, para validar a mensagem. O Git não se importa com a linguagem — pode ser shell, Node, Python — desde que o arquivo seja executável. Se um hook de "pre" termina com erro (código de saída diferente de zero), o Git aborta a operação. É essa capacidade de barrar que torna hooks uma rede de proteção, não só um automatizador.

terminal
# O Git já cria exemplos (desativados, com sufixo .sample)
ls .git/hooks/
# pre-commit.sample  pre-push.sample  commit-msg.sample  ...

# Ativar um hook = criar o arquivo SEM .sample e torná-lo executável
# (no Windows com Git Bash, scripts shell funcionam normalmente)
chmod +x .git/hooks/pre-commit

# pre-commit: o portão mais útil

O pre-commit roda antes de o commit ser criado, e é o hook mais valioso do dia a dia. Ele é o lugar para checagens rápidas que pegam problemas antes de entrarem na história: rodar o linter, formatar o código, e — fechando o Capítulo 12 — recusar qualquer arquivo que contenha marcadores de conflito esquecidos. Se qualquer checagem falhar, o commit é abortado e você corrige antes de seguir.

.git/hooks/pre-commit
#!/bin/sh
# Aborta o commit se houver marcadores de conflito (Cap 12)
if git diff --cached --check | grep -q 'conflict marker'; then
  echo 'Erro: marcadores de conflito no commit. Resolva antes.'
  exit 1
fi

# Roda o linter só nos arquivos preparados; aborta se falhar
npm run lint || { echo 'Lint falhou.'; exit 1; }

exit 0   # tudo certo: o commit prossegue
Hooks rápidos no commit, lentos no push
A regra de ouro de performance dos hooks: o pre-commit deve ser rápido (segundos), porque roda a cada commit e você commita o tempo todo — um hook lento aqui sabota o fluxo e leva as pessoas a pular hooks com --no-verify. Checagens demoradas (a suíte de testes completa, o build) vão no pre-push, que roda com menos frequência. Reserve o pre-commit para o que é instantâneo: lint dos arquivos staged, formatação, detecção de segredos e marcadores de conflito. A divisão certa mantém os hooks como aliados em vez de obstáculos.

# commit-msg e pre-push

Outros dois hooks completam o kit essencial. O commit-msg recebe a mensagem do commit e pode validá-la — por exemplo, exigir o formato Conventional Commits (Cap 3) ou um número de issue. O pre-push roda antes de enviar ao remoto, o lugar certo para checagens mais pesadas que você não quer rodar a cada commit, mas quer garantir antes que o código saia da sua máquina.

.git/hooks/pre-push
#!/bin/sh
# Garante que a suíte de testes passa antes de enviar (checagem pesada)
echo 'Rodando testes antes do push...'
npm test || {
  echo 'Testes falharam — push abortado.'
  exit 1
}
Hooks locais não são compartilhados — e podem ser pulados
Duas limitações fundamentais dos hooks em .git/hooks/. Primeira: eles não são versionados. A pasta .git/ não vai num clone ou push (Cap 1), então um hook que você criou existe só na sua máquina — um colega que clona o repositório não o tem. Segunda: qualquer um pode burlá-los com git commit --no-verify. Por isso hooks locais são uma conveniência pessoal, não uma garantia de equipe. As garantias reais que não podem ser puladas vivem no servidor: o CI do PR (Cap 19) e as regras de proteção de branch. Hooks ajudam o indivíduo a errar menos; o CI impede que o erro entre na main.

# Hooks versionados: Husky e companhia

A limitação "hooks não são compartilhados" tem uma solução madura no ecossistema. Ferramentas como Husky (no mundo Node) versionam a configuração de hooks dentro do projeto: os hooks ficam num diretório rastreado (não no .git/), e a ferramenta os instala automaticamente quando alguém roda npm install. Assim, toda a equipe herda os mesmos hooks, comitados junto com o código. Combinado com lint-staged (que roda checagens só nos arquivos preparados, mantendo o pre-commit rápido), é o padrão moderno de hooks de equipe.

terminal
# Husky aponta o Git para hooks versionados no projeto (não em .git/)
npx husky init

# Configura core.hooksPath para a pasta versionada .husky/
git config core.hooksPath
# .husky/_

# Um pre-commit típico com lint-staged (só arquivos preparados = rápido)
# .husky/pre-commit:  npx lint-staged
core.hooksPath: o mecanismo por baixo
A mágica de Husky e similares é uma configuração simples: core.hooksPath diz ao Git para procurar hooks numa pasta diferente de .git/hooks/. Apontando-a para um diretório versionado (como .husky/), os hooks passam a viajar com o repositório. Não há nada de proprietário — você pode configurar core.hooksPath à mão e versionar seus próprios scripts. As ferramentas só automatizam a instalação e adicionam conveniências. Entender que é só uma config aponta o Git para outra pasta desmistifica o que essas ferramentas fazem.

Capítulo 21

Bisect e arqueologia da história

A história do Git não serve só para registrar o passado — serve para investigá-lo. Quando um bug aparece e ninguém sabe quando foi introduzido, ou quando você precisa entender por que uma linha de código existe, o grafo de commits vira um banco de dados forense. Este capítulo reúne as ferramentas de arqueologia do Git: o bisect, que encontra o commit exato que introduziu um bug por busca binária — transformando "em algum lugar dos últimos 500 commits" em uma dúzia de testes; o blame, que atribui cada linha de um arquivo ao commit que a escreveu; e o log investigativo, que rastreia a evolução de um trecho específico. São ferramentas que pagam dividendos enormes nos momentos de crise — quando algo quebrou e a pergunta é "quando, e por quê?". Dominar a investigação da história é o que distingue usar o Git de realmente alavancá-lo.

# git bisect: busca binária por um bug

O cenário: algo funcionava numa versão antiga e está quebrado agora, mas você não sabe qual dos centenas de commits no meio causou a regressão. Testar um por um seria inviável. O git bisect aplica busca binária ao grafo: você marca um commit antigo conhecido como "bom" e o atual como "ruim", e o Git te leva ao commit do meio. Você testa, diz se é bom ou ruim, e ele descarta metade dos candidatos. Em log₂(n) passos — cerca de 10 testes para 1000 commits — ele isola o commit exato que introduziu o problema.

terminal
# Iniciar a busca
git bisect start

# Marcar o estado atual como ruim e um commit/tag antigo como bom
git bisect bad                 # HEAD está quebrado
git bisect good v1.0.0          # essa versão funcionava

# O Git faz checkout do commit do meio (detached HEAD, Cap 6).
# Você testa e classifica; ele descarta metade a cada resposta:
git bisect good   # este commit está ok -> o bug está depois
git bisect bad    # este já tem o bug -> está aqui ou antes

# Após ~log2(n) passos, o Git aponta o culpado:
# abc1234 is the first bad commit

# Encerrar e voltar ao branch original
git bisect reset
Por que a busca binária funciona aqui
O bisect depende de uma propriedade da história: a partir do commit que introduziu o bug, todos os commits seguintes têm o bug, e todos os anteriores não. Isso forma uma fronteira única — bom, bom, bom, RUIM, ruim, ruim — e a busca binária acha fronteiras em tempo logarítmico. É o mesmo princípio de procurar uma palavra num dicionário: você não folheia página por página, abre no meio e elimina metade. Para 1000 commits, são ~10 testes em vez de 1000. Quanto maior a história, mais absurda fica a vantagem.

# Bisect automatizado

Se você consegue escrever um script ou comando que decide automaticamente se um commit é bom ou ruim (um teste que retorna sucesso ou falha), o bisect roda sozinho. Você fornece o comando, e o Git testa cada commit candidato, classifica pelo código de saída, e te entrega o culpado sem nenhuma interação — encontra a regressão enquanto você toma um café.

terminal
# bisect run: o Git testa cada commit com o comando dado.
# Saída 0 = good, saída 1-127 (exceto 125) = bad, 125 = pular (untestável)
git bisect start HEAD v1.0.0
git bisect run npm test

# O Git percorre os commits sozinho e anuncia o primeiro ruim.

# git blame: quem escreveu esta linha

O blame responde a uma pergunta diferente: para cada linha de um arquivo, qual commit a introduziu (ou alterou pela última vez), quem foi o autor e quando. O nome soa acusatório, mas o uso real raramente é apontar culpa — é contexto. Diante de uma linha estranha, o blame leva ao commit que a criou, e a mensagem desse commit (Cap 3) costuma explicar por que ela existe. É a ponte entre "este código é esquisito" e "ah, foi feito assim por causa daquele requisito".

terminal
# Atribuir cada linha ao commit que a introduziu
git blame src/auth.ts
# abc1234 (Vitor 2026-03-10) export function validateToken() {
# def5678 (Maria 2026-04-02)   const claims = jwtVerify(...)
#  ^commit  ^autor   ^data        ^a linha

# Focar num intervalo de linhas (ex.: linhas 40 a 60)
git blame -L 40,60 src/auth.ts

# Do commit culpado, ver a mudança inteira que deu contexto à linha
git show def5678
Do blame ao contexto, não à culpa
A sequência investigativa mais útil: git blame num trecho confuso revela o commit; git show <commit> mostra a mudança completa e a mensagem; a mensagem (se bem escrita, Cap 3) explica a intenção. É por isso que commits atômicos com boas mensagens são um investimento que se paga meses depois — o blame de hoje só é útil porque alguém escreveu uma mensagem clara ontem. Quando o blame leva a um commit "wip" sem explicação, sente-se na prática o custo de uma história mal cuidada. A arqueologia do Git é tão boa quanto a disciplina de quem escreveu a história.

# Log investigativo: rastreando mudanças

O git log (Cap 3) tem modos de investigação que vão além de listar commits. O -p mostra o diff de cada commit. O -S (pickaxe) busca commits que adicionaram ou removeram uma string específica — perfeito para "quando esta função foi introduzida?" ou "quem removeu esta verificação?". E o -L rastreia a evolução de um intervalo de linhas ao longo de toda a história, mostrando cada mudança que aquele trecho sofreu.

terminal
# Histórico de mudanças de UM arquivo, com o diff de cada commit
git log -p -- src/auth.ts

# Pickaxe: commits que adicionaram/removeram a string 'JWT_SECRET'
# (excelente para rastrear quando algo entrou ou sumiu)
git log -S 'JWT_SECRET' --oneline

# Evolução de um intervalo de linhas ao longo de toda a história
git log -L 40,60:src/auth.ts

# Buscar nas MENSAGENS de commit (não no conteúdo)
git log --grep='rate limit' --oneline
Pickaxe para auditar segredos vazados
O git log -S tem um uso de segurança direto, conectando ao Vol XIII e ao Cap 17: rastrear se um segredo entrou na história. git log -S 'sk_live_' --all encontra qualquer commit que adicionou uma string parecida com uma chave de API, em qualquer branch. Se a busca encontrar algo, o segredo está comprometido — removê-lo do commit atual não basta, pois ele vive no histórico. A resposta é dupla: rotacionar o segredo (invalidá-lo no provedor) e, se necessário, reescrever a história para expungi-lo (com git filter-repo ou similar) — mas a rotação é o que de fato protege, já que cópias do repositório antigo podem existir. Prevenir com .gitignore (Cap 17) é infinitamente mais barato que remediar.

# O princípio que organiza tudo

Se houver uma única ideia para levar deste volume, é a do Capítulo 1: o Git é um banco de dados de objetos imutáveis (blobs, trees, commits) endereçados por hash, com referências móveis (branches, tags, HEAD) apontando para eles. Toda operação, por mais intimidante que pareça, é alguma combinação de "criar objetos" e "mover refs". Merge cria um commit de dois pais; rebase cria commits novos e move um branch; reset move um branch; cherry-pick copia um diff num commit novo. Quando um comando confunde, a pergunta que desfaz a confusão é sempre a mesma: que objetos isso cria, e que refs isso move?

A pergunta que resolve quase tudo
Diante de qualquer situação no Git — um estado estranho, um comando que você não tem certeza do efeito, um erro assustador — volte ao modelo: desenhe o grafo de commits, identifique onde as refs apontam, e pergunte o que o comando fará com esses dois. O git log --oneline --graph --all (Cap 3) e o git reflog (Cap 14) são suas duas lentes: o primeiro mostra a geografia atual, o segundo o histórico dos seus movimentos. Com essas duas visões e o modelo de objetos+refs na cabeça, nenhum estado do Git é misterioso — só ainda não examinado.

# Commits: atômicos e bem descritos

A qualidade da história nasce na qualidade dos commits, e duas regras do Capítulo 3 sustentam tudo o mais. Atomicidade: cada commit faz uma coisa coesa e completa — revertível, inspecionável e identificável sozinho. Mensagens que explicam o porquê: o diff mostra o que mudou; só a mensagem preserva a intenção, a única informação que o código não recupera. Esses dois hábitos são o que tornam todas as ferramentas dos capítulos posteriores — bisect, blame, revert, cherry-pick — realmente úteis. Uma história de commits atômicos e bem descritos é um ativo que se valoriza; uma de "wip" e "conserta" é dívida que se cobra nos momentos de crise.

# A regra de ouro, em definitivo

Nenhuma regra atravessou tantos capítulos quanto esta: não reescreva história pública. Ela apareceu no amend (Cap 3), no rebase (Cap 8), no force push (Cap 11), no reset (Cap 15), no mover tags (Cap 16). É a mesma regra em todas as roupagens, e se resume a uma pergunta: este commit já saiu da minha máquina para um lugar compartilhado? Se não, reescreva à vontade — rebaseie, amende, resete, esprema. Se sim, ele pertence aos outros também; para desfazer, avance com um commit novo (revert, Cap 9), não reescreva o passado. Quem internaliza essa única distinção evita a esmagadora maioria dos desastres de colaboração.

Privado vs público: a fronteira que define o que é seguro
Antes de publicar, o seu trabalho é um rascunho — limpe-o sem cerimônia: rebase -i para esmagar commits bagunçados, amend para corrigir, reset para reorganizar. Depois de publicar (push para um branch compartilhado, abertura de um PR que outros revisaram), o trabalho é um fato compartilhado — qualquer reescrita quebra a história alheia. A transição de "privado" para "público" é o momento em que a régua muda. Cultive commits limpos antes de cruzar essa linha; depois dela, só avance. É a diferença entre editar um documento e republicar uma edição que outros já citaram.

# Hábitos de colaboração

Os capítulos de equipe (18-20) convergem em hábitos simples que reduzem atrito. Branches curtos: integre cedo e com frequência, mantendo a divergência — e portanto os conflitos (Cap 12) — pequena. Sincronize antes de integrar: um fetch e um rebase sobre a main atualizada antes de abrir um PR evitam surpresas. PRs pequenos: revisáveis de verdade, ao contrário dos gigantes que recebem carimbo. Push frequente: o remoto é o seu backup real (Cap 14) — trabalho que só existe na sua máquina é trabalho em risco.

o ciclo diário, consolidado
# Começar do estado atualizado
git switch main && git pull --rebase

# Branch curto e focado para o trabalho
git switch -c fix/sessao-expirada

# Commits atômicos; push cedo (backup + colaboração)
git commit -m 'fix: renova sessão deslizante corretamente'
git push -u origin fix/sessao-expirada

# Sincronizar com a main antes de integrar; abrir PR pequeno
git fetch && git rebase origin/main
gh pr create

# Configuração inicial recomendada

Vale fechar com a configuração que torna o Git mais previsível e seguro desde o início — especialmente no Windows, onde finais de linha (Cap 17) merecem atenção. Esses ajustes, feitos uma vez globalmente, aplicam as boas práticas do volume por padrão em todos os seus repositórios.

terminal
# Identidade (vai em cada commit)
git config --global user.name 'Seu Nome'
git config --global user.email 'voce@exemplo.com'

# Branch padrão main (não master) — Cap 5
git config --global init.defaultBranch main

# Pull com rebase: história linear, sem merges acidentais — Cap 11
git config --global pull.rebase true

# Conflitos com a base comum visível — Cap 12
git config --global merge.conflictStyle zdiff3

# Windows: finais de linha consistentes — Cap 17
git config --global core.autocrlf true

# Fechando a Onda 4 e o caminho adiante

Este volume abriu a Onda 4 — Ferramentas do ofício — colocando sob versionamento todo o código construído nas ondas anteriores: os tipos, as interfaces, o backend, a autenticação. O Git deu a esse código uma história navegável, uma forma de colaborar sem colisões, e uma rede de segurança contra os próprios erros. Mas versionar o código resolve metade do problema de "funciona na minha máquina": a outra metade é o ambiente em que ele roda.

É exatamente onde entra o Volume XV — Docker. Se o Git empacota o código no tempo — cada versão recuperável, cada mudança rastreável —, o Docker o empacota no espaço: um recorte reproduzível do sistema operacional, com todas as dependências, que sobe idêntico no laptop, no CI e em produção. Os dois se complementam de forma direta: o Git versiona o Dockerfile e o docker-compose.yml; o CI (Cap 19) constrói a imagem a cada commit; uma tag v1.0.0 (Cap 16) vira uma imagem versionada pronta para deploy. Do versionamento do código à conteinerização do ambiente, a Onda 4 segue montando as ferramentas que transformam código que funciona em software que se entrega com confiança.
