Regex

O Volume XVI tocou em regex de passagem — o grep, o sed e o awk já a usavam para descrever padrões de texto. Este volume, o último da coleção, a trata por inteiro. Expressões regulares são uma linguagem minúscula e densa para descrever padrões em texto: o que validar, o que buscar, o que substituir. Elas estão em toda parte — na validação do Zod (Vol XII), na busca de código, no processamento de logs, no shell (Vol XVI) —, e a mesma sintaxe, com pequenas variações de sabor, atravessa quase todas as linguagens. Este volume constrói a regex do átomo ao padrão complexo: caracteres e classes, quantificadores e âncoras, grupos e lookaround, e — crucialmente — os perigos de performance (o catastrophic backtracking e o ReDoS) que tornam uma regex inocente um vetor de ataque. Dominar regex é ganhar uma ferramenta universal de manipulação de texto.

Capítulo 1

O que é uma expressão regular

O Volume XVI tocou em regex de passagem — o grep filtrava por padrão, o sed substituía, o awk combinava. Por trás dos três estava a mesma linguagem, e agora a tratamos por inteiro. Uma expressão regular é uma linguagem minúscula e densa para descrever padrões em texto: em vez de procurar uma string exata, você descreve a forma do que procura — "três dígitos seguidos de um hífen", "uma palavra que termina em .com", "qualquer coisa entre aspas". Essa capacidade de descrever padrões, não apenas literais, é o que torna regex onipresente — na validação (o Zod do Vol XII), na busca de código, no processamento de logs, no shell. Este capítulo estabelece o modelo mental antes de qualquer metacaractere: o que uma regex é, como o motor de correspondência (matching) a aplica ao texto, e a distinção fundamental entre caracteres que significam a si mesmos e caracteres que significam um padrão.

# Uma linguagem para descrever padrões

A diferença essencial entre buscar uma string e buscar com regex: a string descreve exatamente o que procurar, a regex descreve uma classe de coisas. Procurar a string "gato" encontra só "gato". Uma regex pode descrever "gato ou gatos", "qualquer palavra de quatro letras", "uma data no formato dd/mm/aaaa". Você não enumera as possibilidades — descreve a regra que todas seguem. Essa é a mudança de pensamento que a regex exige e a fonte do seu poder: pensar em termos de padrões, de estruturas que o texto pode ter, em vez de valores específicos.

regex
# Buscar a string "erro" encontra exatamente isso:
erro

# Uma regex descreve um PADRÃO — uma classe de correspondências.
# Ex.: um padrão para "três dígitos" (sintaxe dos próximos capítulos):
[0-9]{3}
# combina "123", "007", "999"... qualquer sequência de 3 dígitos

# O motor de correspondência

Quando você aplica uma regex a um texto, um motor de correspondência (regex engine) faz o trabalho: ele percorre o texto tentando encaixar o padrão. Para cada posição, pergunta "o padrão combina a partir daqui?", e avança. O resultado pode ser um simples sim/não (o texto contém o padrão?), a primeira correspondência encontrada, ou todas elas. Entender que há um motor percorrendo o texto, posição por posição, é a base para entender depois o comportamento mais sutil — a ganância (Cap 11), o backtracking (Cap 18) e os problemas de performance que dele decorrem.

Match, search, replace: o que você pede ao motor
O motor de regex responde a perguntas diferentes conforme o que você pede. Testar: "o texto contém o padrão?" (sim/não). Buscar: "onde está a primeira/próxima correspondência?". Encontrar todas: "liste todas as correspondências". Substituir: "troque cada correspondência por outra coisa" (Cap 16). Capturar: "extraia partes da correspondência" (Cap 6). A regex em si — o padrão — é a mesma; o que muda é a operação que você manda o motor executar com ela. Por isso a mesma expressão serve para validar (testar), buscar num editor, e transformar texto: o padrão descreve o "o quê", e a operação decide o "fazer o quê com isso".

# Literais vs metacaracteres

A distinção que organiza toda a sintaxe da regex: alguns caracteres significam a si mesmos (literais), outros têm significado especial (metacaracteres). A letra a numa regex combina a letra "a" — é literal. Mas o . não combina um ponto literal; ele é um metacaractere que significa "qualquer caractere". O * não combina um asterisco; significa "repita o anterior". Aprender regex é, em grande parte, aprender o que cada metacaractere faz — e como escapar um metacaractere quando você quer o caractere literal.

regex
# Literais: cada caractere combina a si mesmo
gato          # combina exatamente "gato"

# Metacaracteres: têm significado especial
g.to          # . = qualquer caractere -> "gato", "gxto", "g7to"...

# Escapar com \ para usar um metacaractere LITERALMENTE
3\.14         # \. = um ponto literal -> combina "3.14" (não "3x14")
Os metacaracteres que você precisará escapar
Um conjunto de caracteres tem significado especial em regex e precisa ser escapado com \ quando você quer o caractere literal: . ^ $ * + ? ( ) [ ] { } | \. O exemplo mais comum é o ponto: para combinar um ponto literal (num número decimal, num domínio, numa extensão de arquivo), use \. — escrever só . combinaria qualquer caractere, aceitando "3x14" onde você queria só "3.14". Esquecer de escapar é uma fonte clássica de regex que "combina demais", aceitando entradas que deveriam ser rejeitadas. Os próximos capítulos apresentam cada metacaractere; por ora, fixe a ideia: se um caractere especial deve ser tratado literalmente, escape-o.

# Onde regex aparece

A regex não é uma curiosidade isolada — ela atravessa toda a programação, com a mesma sintaxe básica e pequenas variações de "sabor" (Cap 17). Você a encontra na validação (o z.string().regex() do Zod, Vol XII), na busca (o "find" com regex de qualquer editor, o grep do Vol XVI), na substituição (o sed, o "replace" do editor), no roteamento (padrões de URL em frameworks web), no parsing de logs e dados. Aprender regex uma vez rende em todos esses contextos, porque o núcleo da linguagem é o mesmo em JavaScript, Python, no shell e em quase toda ferramenta que processa texto.

regex em vários contextos
# JavaScript (o sabor de referência deste volume, Cap 13):
//   /[0-9]{3}/.test("abc123")  -> true

# Shell, com grep (Vol XVI, Cap 11):
#   grep -E "[0-9]{3}" arquivo.txt

# Validação com Zod (Vol XII, Cap 15 deste volume):
//   z.string().regex(/^[A-Z]{2}[0-9]{4}$/)

# A MESMA linguagem de padrões, em todos eles.
Poderosa, mas não para tudo
A regex é uma ferramenta afiada, e como toda ferramenta afiada, tem o seu domínio. Ela brilha em padrões regulares — estruturas locais e repetitivas no texto: formatos, validações simples, buscas, extrações. Mas há tarefas para as quais ela é a ferramenta errada, e insistir nela gera código ilegível e frágil. Validar e-mail por regex (Cap 15), fazer parsing de HTML ou JSON, lidar com estruturas aninhadas — nesses casos, parsers dedicados são superiores. Um princípio que o volume vai reforçar: regex resolve elegantemente uma classe específica de problemas, e reconhecer quando você saiu dessa classe — quando a regex está virando um monstro de cinquenta caracteres ilegível — é tão importante quanto saber escrevê-la. Comece aprendendo o poder; o Cap 22 fecha com os limites.

Capítulo 2

Literais e metacaracteres

O Capítulo 1 introduziu a distinção mais importante da regex: caracteres literais (que combinam a si mesmos) e metacaracteres (que têm significado especial). Este capítulo detalha essa fronteira — o catálogo dos metacaracteres fundamentais, o que cada um faz, e a mecânica do escape que permite alternar entre os dois mundos. É um capítulo de vocabulário básico, mas central: sem entender quais caracteres são especiais e como neutralizá-los, toda regex vira tentativa e erro. O ponto de maior atenção é o ponto (.), o metacaractere mais usado e mais mal-entendido, e o escape — a operação que você fará constantemente para tratar metacaracteres como literais. Dominar isto é a base sobre a qual classes, quantificadores e âncoras (próximos capítulos) se constroem.

# O ponto: qualquer caractere

O metacaractere mais usado é o ponto (.): ele combina qualquer caractere único (com uma exceção — a quebra de linha, por padrão). Onde uma letra literal combina só aquela letra, o ponto é um curinga que aceita qualquer coisa naquela posição. É poderoso e perigoso: poderoso porque expressa "algo aqui, não importa o quê"; perigoso porque combina demais quando você queria algo específico, aceitando entradas inválidas.

regex
# . combina qualquer caractere único
c.sa          # combina "casa", "cosa", "c3sa", "c sa"...

# Três pontos = exatamente três caracteres quaisquer
...           # combina "abc", "123", "x y"... (qualquer 3 caracteres)

# Por padrão, o ponto NÃO combina quebra de linha (\n)
# (a flag "dotall" muda isso, Cap 12)
O ponto combina demais — use-o com consciência
O . é tentador por ser fácil, mas seu excesso de permissividade é uma fonte comum de bugs de validação. Uma regex como 3.14 (sem escapar o ponto) aceita "3.14", mas também "3x14", "3 14", "3@14" — qualquer caractere entre o 3 e o 14. Se você queria validar um número decimal, isso é um furo: entradas inválidas passam. Duas disciplinas: (1) quando quer um ponto literal (decimal, domínio, extensão), escape-o — 3\.14; (2) quando quer "algo aqui", prefira ser específico — uma classe de caracteres (Cap 3) como [0-9] diz "um dígito" em vez do permissivo "qualquer coisa". O ponto tem seu lugar, mas a regra é: seja tão específico quanto o problema permite, e reserve o . para quando "qualquer caractere" é genuinamente o que você quer.

# O catálogo dos metacaracteres

Há um conjunto definido de caracteres com significado especial em regex. Vale conhecê-los desde já, mesmo que cada um seja detalhado adiante, para reconhecer quando um caractere é especial. Os principais: . (qualquer caractere), * + ? (quantificadores, Cap 4), ^ $ (âncoras, Cap 5), [ ] (classes, Cap 3), ( ) (grupos, Cap 6), { } (quantificadores precisos), | (alternância, Cap 7), e \ (escape). Cada um transforma o significado da regex; conhecer a lista é saber quais caracteres exigem cuidado.

os metacaracteres
# Os caracteres com significado especial em regex:
.    # qualquer caractere
* + ?  # quantificadores (Cap 4)
^ $    # âncoras: início / fim (Cap 5)
[ ]    # classe de caracteres (Cap 3)
( )    # grupo (Cap 6)
{ }    # quantificador preciso {n,m} (Cap 4)
|      # alternância: ou (Cap 7)
\      # escape

# O escape: de especial para literal

O \ (barra invertida) é o interruptor entre os dois mundos. Antes de um metacaractere, ele o torna literal: \. combina um ponto de verdade, \* um asterisco, \( um parêntese. E, num truque que confunde no início, antes de certas letras comuns, ele cria sequências especiais — \d não combina a letra "d", combina um dígito (Cap 3). Então a barra faz duas coisas opostas conforme o que vem depois: neutraliza metacaracteres, e ativa sequências especiais a partir de letras.

regex
# \ antes de metacaractere -> literal
\.            # um ponto literal
\*            # um asterisco literal
\(            # um parêntese literal
\\            # uma barra invertida literal (escape da própria barra)

# \ antes de certas letras -> sequência especial (Cap 3)
\d            # um dígito (não a letra "d")
\w            # um caractere de palavra
\s            # um espaço em branco
Escapar o que não é especial é inofensivo (quase sempre)
Uma dúvida comum: e se eu escapar um caractere que não é metacaractere, como \a ou \g? Na maioria dos sabores, escapar um caractere comum que não tem sequência especial definida simplesmente resulta no próprio caractere literal — \g combina "g". É inofensivo, embora desnecessário. O cuidado é com as letras que têm significado especial quando escapadas (\d, \w, \s, \b, \n...): aí o \ ativa a sequência, não produz a letra. Na dúvida sobre se um caractere precisa de escape, escapar metacaracteres conhecidos é sempre seguro; escapar letras aleatórias é melhor evitar, porque você pode ativar uma sequência especial sem querer. A regra prática: escape deliberadamente os metacaracteres que quer tornar literais, e conheça as sequências \letra que usa.

# Sequências de escape comuns

Além de dígitos e palavras (Cap 3), a barra invertida cria sequências para caracteres que não se digitam diretamente: a quebra de linha (\n), a tabulação (\t), o retorno de carro (\r). Essas aparecem ao processar texto multilinha, dados tabulados, ou ao lidar com finais de linha (o CRLF do Windows, Vol XIV, Cap 17). São as mesmas sequências de escape de strings em muitas linguagens (toda a coleção).

regex
\n            # quebra de linha (newline)
\t            # tabulação (tab)
\r            # retorno de carro (carriage return)

# Ex.: combinar um campo seguido de tab e outro campo
#   \w+\t\w+   -> "nome[tab]valor"

# Combinando literais e o ponto

Com literais, o ponto e o escape, você já consegue padrões úteis — misturando partes fixas (literais) com partes variáveis (o ponto ou sequências). O segredo de uma boa regex começa aqui: usar literais para as partes que você conhece exatamente, e metacaracteres só onde há variação real. Quanto mais literal e específica a regex, menos ela combina por engano.

regex
# Misturar literais (fixos) com o ponto (variável):
arquivo.txt   # CUIDADO: o . combina qualquer caractere
              # combina "arquivo.txt" mas TAMBÉM "arquivoXtxt"

arquivo\.txt  # com \. -> só "arquivo.txt" (ponto literal)

# Literal + sequência especial: um código tipo "AB-12"
#   [A-Z][A-Z]-\d\d   (classes do Cap 3 + literal hífen)

Capítulo 3

Classes de caracteres

O ponto (Cap 2) combina qualquer caractere — mas raramente você quer qualquer coisa. Quer um dígito, ou uma letra, ou uma vogal, ou qualquer caractere exceto certos. As classes de caracteres dão essa precisão: elas definem um conjunto de caracteres aceitos numa posição. Em vez do permissivo ., você diz exatamente "um destes". Este capítulo cobre as classes entre colchetes ([...]), os intervalos ([a-z]), a negação ([^...]), e as classes pré-definidas (\d, \w, \s) que abreviam as mais comuns. São a ferramenta que transforma regex de "combina qualquer coisa" em "combina exatamente o tipo de caractere que eu quero" — a base de toda validação precisa, e o antídoto contra o excesso de permissividade do ponto.

# Colchetes: um conjunto de caracteres

Uma classe de caracteres é escrita entre colchetes [...], e combina um caractere que seja qualquer um dos listados dentro. [aeiou] combina uma vogal; [abc] combina a, b ou c. Note a diferença para uma sequência: [abc] combina um caractere que seja a, b ou c, não a string "abc". A classe é sobre escolha numa posição — "qual destes caracteres está aqui?".

regex
# [...] combina UM caractere de um conjunto
[aeiou]       # uma vogal: "a", "e", "i", "o" ou "u"
gr[ae]y       # "gray" ou "grey" (a ou e na posição)

# Dentro dos colchetes, a maioria dos metacaracteres perde o poder:
[.+*]         # um ponto, mais OU asterisco LITERAIS (sem escape)

# Intervalos: a-z, 0-9

Listar cada caractere seria tedioso, então as classes aceitam intervalos com hífen: [a-z] é toda letra minúscula, [A-Z] toda maiúscula, [0-9] todo dígito. Você combina intervalos e caracteres avulsos na mesma classe: [a-zA-Z0-9] é "qualquer letra ou dígito", [a-z_] é "minúscula ou underscore". Os intervalos tornam classes compactas e legíveis.

regex
# Intervalos com hífen
[a-z]         # uma letra minúscula
[A-Z]         # uma letra maiúscula
[0-9]         # um dígito

# Combinar intervalos e caracteres avulsos
[a-zA-Z]      # qualquer letra (maiúscula ou minúscula)
[a-zA-Z0-9_]  # letra, dígito ou underscore (caractere "de palavra")
[a-f0-9]      # um dígito hexadecimal
Dentro de [ ], os metacaracteres se acalmam
Uma propriedade conveniente das classes: dentro dos colchetes, a maioria dos metacaracteres perde o significado especial e vira literal. Um ponto dentro de [.] é só um ponto, sem precisar de escape; [+*?] combina esses três símbolos literalmente. Isso simplifica muito — você não precisa escapar tudo dentro de uma classe. Há poucas exceções que continuam especiais dentro dos colchetes e merecem atenção: o ^ (no início, significa negação — próxima seção), o - (entre caracteres, forma intervalo — para um hífen literal, coloque-o no início ou fim, como [-a-z]), o ] (que fecha a classe — escape-o se quiser literal), e a \ (escape). Fora dessas, dentro de uma classe os caracteres são literais — uma das poucas simplificações que a regex oferece.

# Negação: [^...]

Um ^ logo após o colchete de abertura inverte a classe: [^...] combina qualquer caractere que não esteja listado. [^0-9] é "qualquer caractere que não seja dígito"; [^aeiou] é "qualquer não-vogal". A negação é poderosa para "tudo exceto" — combinar até encontrar um delimitador, aceitar qualquer coisa menos certos caracteres proibidos. Cuidado para não confundir esse ^ (dentro da classe, negação) com o ^ de âncora de início (fora da classe, Cap 5) — mesmo símbolo, contextos diferentes.

regex
# [^...] : qualquer caractere que NÃO está no conjunto
[^0-9]        # qualquer caractere que NÃO é dígito
[^aeiou]      # qualquer não-vogal

# Útil para "tudo até um delimitador":
[^,]          # qualquer caractere exceto vírgula
"[^"]*"       # conteúdo entre aspas (qualquer coisa menos aspas)

# Classes pré-definidas: \d \w \s

Algumas classes são tão comuns que ganharam atalhos com barra invertida (Cap 2). \d equivale a [0-9] (um dígito); \w equivale a [a-zA-Z0-9_] (caractere "de palavra" — letra, dígito ou underscore); \s combina espaço em branco (espaço, tab, quebra de linha). Suas versões maiúsculas são as negações: \D é "não-dígito", \W "não-palavra", \S "não-espaço". Essas abreviações tornam regex comuns muito mais legíveis.

regex
# Atalhos (minúsculas) e suas negações (maiúsculas):
\d   # dígito       = [0-9]          \D = não-dígito
\w   # de palavra   = [a-zA-Z0-9_]   \W = não-palavra
\s   # espaço       = [ \t\n\r...]   \S = não-espaço

# Comparação: estas duas são equivalentes
[0-9][0-9][0-9]    # três dígitos (verboso)
\d\d\d            # três dígitos (conciso)

# Montando padrões com classes

Com classes, você descreve formatos com precisão. Um código de produto "AB-1234"? [A-Z][A-Z]-\d\d\d\d. Um identificador de variável (letra ou underscore, depois letras/dígitos/underscores)? Começa a tomar forma. As classes são os "tijolos" que definem que tipo de caractere vai em cada posição; os quantificadores (Cap 4) cuidarão de quantos. Juntos, expressam quase qualquer formato.

regex
# Código "AB-1234": duas maiúsculas, hífen, quatro dígitos
[A-Z][A-Z]-\d\d\d\d

# Um caractere hexadecimal de cor: # seguido de 6 hex
#[a-fA-F0-9][a-fA-F0-9][a-fA-F0-9]...   # (Cap 4 abrevia isto)

# Início de identificador: letra ou underscore
[a-zA-Z_]
Prefira classes específicas ao ponto genérico
A lição que une os Caps 2 e 3: sempre que puder, use uma classe específica em vez do ponto permissivo. Validar um código de país com .. (dois caracteres quaisquer) aceita "1@", " ", "x!"; com [A-Z][A-Z] aceita só duas letras maiúsculas — exatamente o pretendido. Cada vez que você troca um . por uma classe que descreve o que realmente é válido naquela posição, sua regex fica mais correta, rejeitando o que deveria rejeitar. Esse é o princípio de uma boa regex de validação: seja o mais específico que o formato permite. O ponto tem seu lugar (quando "qualquer caractere" é genuíno), mas a classe é a ferramenta de precisão, e a precisão é o que separa uma validação que protege de uma que deixa lixo passar.

Capítulo 4

Quantificadores quantas vezes

As classes (Cap 3) dizem que tipo de caractere vai numa posição; os quantificadores dizem quantas vezes ele se repete. Juntos, eles expressam a maioria dos padrões reais — "um ou mais dígitos", "exatamente quatro letras", "zero ou mais espaços". Sem quantificadores, você teria que repetir manualmente cada elemento (\d\d\d\d para quatro dígitos); com eles, \d{4} diz o mesmo, e \d+ diz "um ou mais" sem saber quantos de antemão. Este capítulo cobre os quantificadores — *, +, ? e o preciso {n,m} —, o que cada um significa, e a armadilha de combiná-los com o ponto. São o elemento que dá à regex sua expressividade sobre repetição, e a porta de entrada para um tema delicado que volta no Cap 11 (ganância) e no Cap 18 (performance).

# Os três básicos: * + ?

Três quantificadores cobrem os casos mais comuns. O * significa "zero ou mais" do elemento anterior — ele pode aparecer nenhuma, uma, ou muitas vezes. O + significa "um ou mais" — pelo menos uma vez. O ? significa "zero ou um" — opcional, aparece ou não. Cada um se aplica ao elemento imediatamente anterior (um caractere, uma classe, um grupo do Cap 6).

regex
# * : zero ou mais (o anterior pode nem aparecer)
a*            # "", "a", "aa", "aaa"... (até nada combina)
\d*           # zero ou mais dígitos

# + : um ou mais (pelo menos uma vez)
\d+           # "1", "42", "1000"... (mas NÃO string vazia)

# ? : zero ou um (opcional)
colou?r       # "color" ou "colour" (o u é opcional)
-?\d+         # um número com sinal de menos opcional
* aceita "nada" — uma fonte de surpresa
A diferença entre * e + parece pequena mas importa muito. O * (zero ou mais) combina até a ausência do elemento — \d* dá match numa string sem nenhum dígito, porque "zero dígitos" satisfaz "zero ou mais". Isso surpreende em validações: uma regex \d* para "um número" aceita string vazia ou texto sem números, porque o "zero" é válido. Quando você quer exigir pelo menos um, use +. A regra: * quando o elemento é genuinamente opcional e pode não existir; + quando precisa de ao menos uma ocorrência. Confundir os dois produz regex que combinam mais do que deveriam — um * onde deveria ser + é um furo comum de validação, aceitando o vazio onde algo era obrigatório.

# Quantificadores precisos: {n,m}

Para controle exato sobre a quantidade, há a forma com chaves. {n} significa "exatamente n vezes"; {n,} significa "n ou mais"; {n,m} significa "entre n e m vezes". Essa é a ferramenta para formatos com tamanho definido — um CEP de 8 dígitos, uma senha de 8 a 20 caracteres, um código de exatamente 4 letras. Onde * e + são vagos sobre a quantidade, {n,m} é preciso.

regex
# {n} : exatamente n vezes
\d{4}         # exatamente 4 dígitos (um ano, um PIN)
[A-Z]{2}      # exatamente 2 maiúsculas (código de país)

# {n,} : n ou mais
\d{3,}        # 3 ou mais dígitos

# {n,m} : entre n e m (faixa)
.{8,20}       # entre 8 e 20 caracteres (senha)
\d{2,4}       # de 2 a 4 dígitos

# Equivalências: ? = {0,1}   * = {0,}   + = {1,}

# Quantificando classes e grupos

Os quantificadores se aplicam ao elemento anterior — e esse elemento pode ser uma classe inteira (Cap 3) ou um grupo (Cap 6), não só um caractere. [a-z]+ é "uma ou mais minúsculas"; (\d{3}){2} é "três dígitos, repetidos duas vezes". É essa combinação — classes definindo o tipo, quantificadores definindo a quantidade, aplicados a unidades maiores — que dá à regex o poder de descrever formatos complexos de forma compacta.

regex
# Quantificar uma classe: o quantificador vale para toda a classe
[a-z]+        # uma ou mais letras minúsculas
[0-9]{1,3}    # de 1 a 3 dígitos (um octeto de IP, quase)

# Cor hexadecimal compacta (compare com o Cap 3, sem quantificador)
#[a-fA-F0-9]{6}    # # seguido de exatamente 6 hex

# Quantificar um grupo (Cap 6): repetir uma sequência inteira
(ab)+         # "ab", "abab", "ababab"...
.* e .+ : poderosos e perigosos
A combinação do ponto (qualquer caractere, Cap 2) com um quantificador — .* ("qualquer coisa, zero ou mais vezes") e .+ ("qualquer coisa, uma ou mais") — é a mais usada e a mais traiçoeira da regex. Ela combina praticamente tudo, o que a torna tentadora para "qualquer coisa aqui", mas perigosa por três razões. Validação: .* aceita qualquer entrada, anulando a validação. Ganância: ela combina o máximo possível, frequentemente mais do que você queria (Cap 11). Performance: combinada com outras partes, pode causar backtracking catastrófico e até virar um vetor de ataque (Caps 18-19). Use .* e .+ com consciência: quase sempre uma classe específica ([^"]* para "até a próxima aspa", \d+ para "dígitos") é mais correta e segura. Quando vir .* numa regex, pergunte se ela não está combinando demais.

Capítulo 5

Âncoras e limites

Os capítulos anteriores construíram padrões que combinam onde quer que apareçam no texto. Mas frequentemente a posição importa: você quer que o padrão case o texto inteiro (validação), ou só no início de uma linha, ou numa fronteira de palavra. As âncoras resolvem isso — elas não combinam caracteres, combinam posições. ^ ancora no início, $ no fim, \b numa fronteira de palavra. Este capítulo cobre essas âncoras e por que elas são essenciais para validação: a diferença entre "o texto contém este padrão" e "o texto é exatamente este padrão" depende inteiramente de ancorar com ^ e $. É um dos pontos onde o descuido custa mais caro — uma validação sem âncoras é uma validação furada, que aceita lixo ao redor do que deveria ser o valor inteiro.

# Âncoras combinam posições, não caracteres

A ideia que distingue âncoras de tudo o que veio antes: elas têm largura zero. Uma classe ou um literal consomem um caractere do texto; uma âncora não consome nada — ela apenas verifica que está numa certa posição. ^ não combina o primeiro caractere; combina a posição antes dele. Por isso âncoras se chamam "assertions" (afirmações): elas afirmam algo sobre a posição atual sem avançar no texto. Esse conceito de "largura zero" volta com força no lookaround (Cap 10).

regex
# ^ : posição de INÍCIO (do texto, ou da linha com flag multiline)
^abc          # "abc" só se estiver no início

# $ : posição de FIM
xyz$          # "xyz" só se estiver no fim

# Âncoras não consomem caractere — afirmam uma posição
#   ^ combina a posição ANTES do primeiro caractere
#   $ combina a posição DEPOIS do último

# ^ e $ : a chave da validação

Aqui está a seção mais importante do capítulo. Sem âncoras, uma regex combina se o padrão aparece em algum lugar do texto. Para validar — garantir que o texto inteiro é o padrão, sem nada a mais — você ancora com ^ no início e $ no fim. ^\d{4}$ exige que o texto seja exatamente quatro dígitos, nada antes, nada depois. Sem as âncoras, \d{4} combinaria "abc1234xyz", porque há quatro dígitos em algum ponto. A diferença é entre "contém" e "é".

exemplo.js
// SEM âncoras: combina se o padrão aparece EM ALGUM LUGAR
/\d{4}/.test("abc1234xyz")      // true (há 4 dígitos no meio!)

// COM âncoras: o texto INTEIRO precisa ser o padrão
/^\d{4}$/.test("abc1234xyz")    // false (tem lixo ao redor)
/^\d{4}$/.test("2026")           // true (exatamente 4 dígitos)

// Validação sempre ancora início E fim:
/^[A-Z]{2}\d{4}$/.test("AB1234")  // true
Validação sem ^ e $ é validação furada
Este é talvez o erro de segurança mais comum com regex, e conecta ao Vol XIII. Uma validação sem âncoras verifica se o input contém algo válido, não se é válido — e isso deixa passar entradas perigosas. Uma regex /[a-z]+/ para validar um nome de usuário aceita "admin'; DROP TABLE--", porque há letras minúsculas em algum lugar dela. Com âncoras, /^[a-z]+$/ exige que o input inteiro seja só minúsculas, rejeitando o ataque. A regra é absoluta: toda regex de validação deve ancorar com ^ no início e $ no fim, garantindo que o valor completo — não um pedaço dele — satisfaz o padrão. Esquecer as âncoras transforma uma validação aparentemente correta numa peneira. Quando o Zod (Vol XII) usa z.string().regex(), a mesma regra vale: ancore o padrão.

# \b : fronteira de palavra

A âncora \b combina uma fronteira de palavra — a transição entre um caractere "de palavra" (\w: letra, dígito, underscore) e um que não é (espaço, pontuação, início/fim do texto). Ela permite combinar uma palavra inteira, não como parte de outra. \bgato\b combina "gato" em "o gato dorme" mas não em "gatorade" — porque em "gatorade" não há fronteira após "gato". É a ferramenta para busca de palavras exatas.

regex
# \b : fronteira entre caractere de palavra e não-palavra
\bgato\b      # "gato" como palavra inteira
#   combina:    "o gato dorme"   (gato cercado por espaços)
#   NÃO combina: "gatorade"      (não há fronteira após gato)

# Útil para buscar/substituir palavras exatas:
\bfor\b       # a palavra "for", não "before" nem "format"

# \B é o oposto: NÃO-fronteira (dentro de uma palavra)

# Início e fim de linha vs de texto

Há uma sutileza com ^ e $ que depende de uma flag (Cap 12). Por padrão, em muitos sabores, ^ e $ combinam o início e o fim do texto inteiro. Com a flag multiline ativada, eles passam a combinar o início e o fim de cada linha dentro de um texto multilinha. Essa diferença importa ao processar arquivos ou textos com várias linhas — você escolhe se as âncoras se referem ao documento todo ou a cada linha.

exemplo.js
const texto = "linha1\nlinha2\nlinha3"

// Sem multiline: ^ e $ = início/fim do TEXTO inteiro
/^linha\d$/.test(texto)        // false (o texto todo não é "linhaN")

// Com a flag m (multiline): ^ e $ = início/fim de cada LINHA
texto.match(/^linha\d$/gm)       // ["linha1","linha2","linha3"]
// agora cada linha é testada individualmente

Capítulo 6

Grupos e captura

Os parênteses (...) são um dos elementos mais versáteis da regex, com dois papéis que vale separar desde já. O primeiro é agrupar: tratar uma sequência como uma unidade, para aplicar um quantificador a ela toda (Cap 4) ou delimitar uma alternância (Cap 7). O segundo é capturar: marcar uma parte da correspondência para extraí-la depois — pegar o ano de uma data, o domínio de um e-mail, o valor entre aspas. Essa segunda função transforma a regex de uma ferramenta de "combina ou não" numa de extração de dados: você não só verifica que o texto tem um formato, você arranca as partes que interessam. Este capítulo cobre os grupos de captura, como acessar o que foi capturado, e a base para a substituição (Cap 16) e as backreferences (Cap 8).

# Agrupar: tratar como unidade

O uso mais básico dos parênteses é agrupar uma sequência para que um quantificador (Cap 4) se aplique a ela inteira, não só ao último caractere. Sem grupo, ab+ significa "a, seguido de um ou mais b". Com grupo, (ab)+ significa "um ou mais 'ab'". Os parênteses delimitam a unidade sobre a qual o quantificador atua — essencial para repetir sequências, não apenas caracteres isolados.

regex
# Sem grupo: o + aplica só ao b
ab+           # "ab", "abb", "abbb"... (a, depois um ou mais b)

# Com grupo: o + aplica à sequência inteira "ab"
(ab)+         # "ab", "abab", "ababab"...

# Repetir um grupo de dígitos (ex.: blocos)
(\d{3}){2}    # dois blocos de 3 dígitos: "123456"

# Capturar: extrair partes

Aqui está o salto. Quando você envolve parte de uma regex em parênteses, além de agrupar, você captura o que aquela parte combinou — o motor guarda esse trecho num "grupo de captura" numerado, da esquerda para a direita (grupo 1, grupo 2...). Depois da correspondência, você acessa esses grupos para extrair os dados. Isso transforma "esta string é uma data?" em "extraia o dia, o mês e o ano desta data" — a regex vira uma ferramenta de parsing.

exemplo.js
// Cada (...) cria um grupo de captura, numerado da esquerda p/ direita
const data = "09/06/2026"
const m = data.match(/(\d{2})\/(\d{2})\/(\d{4})/)

// m[0] = a correspondência inteira; m[1], m[2]... os grupos
m[0]    // "09/06/2026"  (tudo)
m[1]    // "09"  (grupo 1 = dia)
m[2]    // "06"  (grupo 2 = mês)
m[3]    // "2026" (grupo 3 = ano)
O grupo 0 é a correspondência inteira
Uma convenção universal: o "grupo 0" não é um grupo que você criou, é a correspondência completa — tudo que a regex casou, parênteses ou não. Os grupos que você definiu com parênteses começam no 1, numerados pela posição do parêntese de abertura, da esquerda para a direita. Isso importa quando há grupos aninhados: em ((\d)(\d)), o grupo 1 é o par externo, o grupo 2 o primeiro dígito, o grupo 3 o segundo — a ordem segue os parênteses de abertura. Saber numerar os grupos corretamente é essencial para extrair a parte certa, e a numeração por posição de abertura (não de fechamento) é a regra a fixar. Quando a numeração fica confusa, os grupos nomeados (Cap 9) resolvem dando rótulos em vez de números.

# Extraindo dados estruturados

A captura é o que torna a regex uma ferramenta de extração prática. Um log com formato conhecido, uma URL, um par chave-valor — você descreve o formato com a regex, marca as partes de interesse com parênteses, e extrai. É parsing leve: para dados com estrutura regular e previsível, a regex com grupos é rápida e direta, evitando escrever um parser à mão.

exemplo.js
// Extrair partes de uma linha de log: "[ERROR] 14:30 - falhou"
const linha = "[ERROR] 14:30 - falhou"
const m = linha.match(/\[(\w+)\] (\d{2}:\d{2}) - (.+)/)

m[1]    // "ERROR"  (nível)
m[2]    // "14:30"  (hora)
m[3]    // "falhou" (mensagem)

// Extrair todos os pares de uma vez com a flag g (Cap 13):
// [...texto.matchAll(/(\w+)=(\w+)/g)]  -> pares chave=valor

# Grupos e quantificadores: uma sutileza

Há uma pegadinha ao combinar captura com repetição. Quando um grupo é quantificado — (\d{2})+ —, o grupo de captura guarda apenas a última repetição, não todas. Se você quer capturar várias ocorrências, a captura num grupo repetido não basta; é preciso outra abordagem (iterar com a flag global, Cap 13, ou estruturar a regex diferente). É uma fonte comum de confusão: "por que meu grupo só pegou a última parte?".

exemplo.js
// Grupo quantificado captura só a ÚLTIMA repetição:
"123456".match(/(\d{2})+/)
// m[1] = "56"  (só o último par, não "12","34","56"!)

// Para todas as ocorrências, use matchAll com a flag g (Cap 13):
[..."123456".matchAll(/(\d{2})/g)].map(m => m[1])
// ["12", "34", "56"]  (cada par capturado)
Capture só o que vai usar
Como os parênteses fazem duas coisas (agrupar e capturar), é fácil acabar com grupos de captura que você só queria para agrupamento — poluindo a numeração e o resultado com trechos que não interessam. Quando você usa parênteses apenas para agrupar (aplicar um quantificador, delimitar uma alternância) e não precisa extrair aquele trecho, prefira um grupo não-capturante (?:...) (Cap 9) — ele agrupa sem criar um grupo de captura, mantendo a numeração limpa e o motor um pouco mais eficiente. A disciplina: capture deliberadamente as partes que vai extrair, e use grupos não-capturantes para o agrupamento puro. Isso mantém m[1], m[2] apontando para o que você realmente quer, em vez de você ter que contar parênteses para descobrir qual grupo é qual.

Capítulo 7

Alternância este ou aquele

As classes de caracteres (Cap 3) expressam "um destes caracteres", mas e quando você quer "uma destas palavras" ou "um destes padrões"? A alternância, o operador | (barra vertical), resolve isso: ela combina um padrão ou outro. gato|cachorro combina "gato" ou "cachorro"; sim|não|talvez combina qualquer uma das três. É o "ou" lógico da regex, e parece simples — até você esbarrar na questão do escopo: até onde vai cada alternativa? Esse é o ponto central do capítulo, e onde os parênteses (Cap 6) se tornam essenciais. Entender que a alternância tem a menor precedência de todos os operadores, e como delimitá-la com grupos, é o que separa uma alternância que funciona de uma que combina coisas inesperadas.

# O | : este padrão ou aquele

O | separa alternativas: o motor tenta combinar a primeira; se falhar, tenta a próxima. Diferente da classe [...] (que escolhe entre caracteres), a alternância escolhe entre padrões inteiros — podem ser palavras, sequências, ou expressões complexas. É a ferramenta para "qualquer uma destas opções", onde as opções são maiores que um único caractere.

regex
# | combina um padrão OU outro
gato|cachorro     # "gato" ou "cachorro"
sim|não|talvez    # qualquer uma das três palavras

# Diferença para a classe: [...] escolhe CARACTERES, | escolhe PADRÕES
[gc]              # o caractere g OU c
gato|carro        # a palavra "gato" OU "carro"

# Alternativas podem ser padrões complexos
\d{4}|\d{2}       # quatro dígitos OU dois dígitos

# O problema do escopo

Aqui está a armadilha central. O | tem a menor precedência de todos os operadores da regex — ele divide a expressão nos maiores pedaços possíveis. Isso significa que ^gato|cachorro$ não significa "gato ou cachorro, ancorados"; significa "^gato" OU "cachorro$" — duas alternativas que incluem as âncoras de forma assimétrica. A alternância se estende da esquerda do | até a borda da expressão (ou de um grupo), não só à palavra adjacente. Não reconhecer isso produz regex que combinam algo bem diferente do pretendido.

regex
# ARMADILHA: o | tem a menor precedência, divide TUDO
^gato|cachorro$
#   NÃO é: (gato ou cachorro) ancorados
#   É:     "^gato"  OU  "cachorro$"
#   ou seja: começa com "gato"  OU  termina com "cachorro"

# Provavelmente o pretendido era:
^(gato|cachorro)$
#   o texto INTEIRO é "gato" ou "cachorro"
Delimite a alternância com parênteses
A regra que evita a armadilha: quando a alternância é parte de um padrão maior, quase sempre ela precisa ir entre parênteses para delimitar o escopo (Cap 6). Sem o grupo, o | se estende até as bordas da expressão, capturando muito mais do que você queria — incluindo âncoras, prefixos e sufixos no lado errado. Com (gato|cachorro), as alternativas ficam contidas, e o resto do padrão (âncoras, quantificadores) se aplica ao grupo como um todo. A heurística: sempre que escrever um | que não ocupa a expressão inteira sozinho, pergunte "até onde cada alternativa vai?" e envolva-as num grupo para ter certeza. Lembre que o parêntese aqui pode ser não-capturante (?:gato|cachorro) (Cap 9) se você só quer agrupar, não extrair — delimitando o escopo sem criar um grupo de captura desnecessário.

# Alternância em parte de um padrão

O uso mais comum e útil da alternância é como parte de um padrão maior — uma escolha numa posição específica, cercada por elementos fixos. "Um arquivo .jpg, .png ou .gif"? A extensão é uma alternância dentro do padrão de nome. Os parênteses isolam exatamente onde a escolha acontece, e o resto do padrão (literais, quantificadores, âncoras) opera ao redor.

regex
# Extensão de imagem: alternância dentro de um padrão maior
\w+\.(jpg|png|gif)     # nome + ponto + uma das extensões

# Protocolo de URL
(https?|ftp)://        # http, https ou ftp, seguido de ://
#   (https? = http com s opcional, Cap 4)

# Saudação flexível, ancorada
^(oi|olá|e aí)$        # o texto é exatamente uma dessas

# Ordem das alternativas importa

Um detalhe de comportamento: o motor tenta as alternativas da esquerda para a direita e fica com a primeira que combina, mesmo que uma alternativa posterior combinasse mais. Isso importa quando as alternativas se sobrepõem — se uma é prefixo da outra. (jan|janeiro) aplicada a "janeiro" combina apenas "jan", porque "jan" é tentada primeiro e já satisfaz. Para combinar o mais longo, coloque as alternativas mais longas (ou mais específicas) primeiro: (janeiro|jan).

regex
# O motor pega a PRIMEIRA alternativa que combina (esquerda p/ direita)
(jan|janeiro)     # em "janeiro", combina só "jan" (tentada primeiro)

# Coloque a mais longa/específica primeiro:
(janeiro|jan)     # em "janeiro", combina "janeiro" (correto)

# Regra: alternativas mais específicas/longas antes das genéricas/curtas

Capítulo 8

Backreferences combinando o que foi capturado

Os grupos de captura (Cap 6) guardam o que combinaram para você extrair depois. Mas há um uso mais sutil e poderoso: referenciar, dentro da própria regex, o texto que um grupo capturou — exigindo que ele se repita. Isso é uma backreference: \1 dentro da regex significa "o mesmo texto que o grupo 1 capturou". Com ela, a regex ganha uma capacidade que parece quase impossível para um padrão estático: detectar repetições, palavras duplicadas, tags que abrem e fecham com o mesmo nome, aspas que combinam. Este capítulo cobre as backreferences e o que elas tornam possível — e também o que elas não tornam possível, marcando a fronteira onde a regex deixa de ser a ferramenta certa (um tema que o Cap 22 retoma).

# \1 : repita o que o grupo capturou

Uma backreference é um \ seguido do número de um grupo: \1 refere-se ao grupo 1, \2 ao grupo 2. Mas o ponto crucial é o que ela combina: não o padrão do grupo, e sim o texto exato que aquele grupo capturou naquela correspondência. Se o grupo 1 capturou "abc", então \1 combina literalmente "abc" — não "qualquer coisa que o padrão do grupo 1 aceitaria". É essa exigência de igualdade de texto que dá às backreferences seu poder único.

regex
# \1 = o TEXTO que o grupo 1 capturou (não o padrão dele)
(\w+) \1          # uma palavra, espaço, e a MESMA palavra de novo
#   combina:    "olá olá"     (palavra repetida)
#   NÃO combina: "olá tchau"   (palavras diferentes)

# O grupo captura "olá"; \1 exige "olá" de novo, não outra palavra

# Detectando duplicatas

O caso de uso clássico das backreferences é encontrar repetições — algo que padrões sem estado não conseguem. Palavras duplicadas num texto ("o o gato"), caracteres repetidos, valores idênticos lado a lado. Sem backreference, você teria que enumerar cada palavra possível; com ela, (\w+)\s+\1 diz "qualquer palavra seguida dela mesma", capturando a duplicata seja qual for.

exemplo.js
// Encontrar palavras duplicadas consecutivas (erro de digitação)
const texto = "o o gato dorme no no sofá"
texto.match(/\b(\w+)\s+\1\b/g)
// ["o o", "no no"]  (as repetições detectadas)

// Caractere triplicado:
/(.)\1\1/.test("aaa")     // true (um char, seguido dele 2x)

# Combinando delimitadores que casam

Outro uso elegante: garantir que um delimitador de abertura combine com o de fechamento. Aspas que precisam ser do mesmo tipo (simples ou duplas), uma tag HTML que abre e fecha com o mesmo nome. A backreference exige que o fechamento seja idêntico à captura da abertura — algo impossível de expressar sem ela, já que o padrão precisa "lembrar" o que casou antes.

regex
# Aspas que combinam: a de fechar deve ser igual à de abrir
(['"]).*?\1       # 'texto' ou "texto", mas não 'texto"
#   (['"]) captura a aspa; \1 exige a MESMA no fim

# Tag HTML simples com nome casado (mas veja o aviso abaixo!)
<(\w+)>.*?</\1>     # <p>...</p> — abertura e fechamento iguais
Backreferences impressionam, mas não tornam regex onipotente
O exemplo de tag HTML acima funciona para casos simples, mas é uma armadilha perigosa em geral, e ilustra um limite fundamental. Backreferences permitem casar uma repetição de algo capturado, mas a regex não consegue lidar com aninhamento arbitrário — tags dentro de tags dentro de tags, parênteses balanceados em qualquer profundidade. Isso não é uma limitação de esforço; é uma limitação teórica: regex (no sentido clássico) descreve "linguagens regulares", e estruturas aninhadas como HTML e JSON são "livres de contexto", uma classe mais poderosa que regex não alcança. Por isso a famosa advertência: não use regex para fazer parsing de HTML — use um parser de verdade. Backreferences expandem o que regex faz, mas não mudam a classe de problemas que ela resolve. O Cap 22 fecha com essa fronteira: regex para padrões locais e repetições simples; parsers para estruturas aninhadas.

# Backreferences na substituição

As backreferences também aparecem na substituição (Cap 16), com uma sintaxe ligeiramente diferente — geralmente $1 em vez de \1, dependendo do contexto. Ali, elas referenciam os grupos capturados para reusá-los no texto de substituição: reordenar uma data, envolver um valor em aspas, reformatar. É a ponte entre capturar (Cap 6) e transformar (Cap 16), antecipada aqui.

exemplo.js
// Na substituição, $1, $2... referenciam os grupos (Cap 16)
// Reformatar data: "09/06/2026" -> "2026-06-09"
"09/06/2026".replace(
  /(\d{2})\/(\d{2})\/(\d{4})/,
  "$3-$2-$1"          // ano-mês-dia (grupos reordenados)
)
// "2026-06-09"

// Dentro da regex: \1 ; na substituição: $1 (sintaxes distintas)

Capítulo 9

Grupos não-capturantes e nomeados

O Capítulo 6 mostrou que os parênteses fazem duas coisas — agrupar e capturar — e antecipou um problema: às vezes você quer só agrupar, e a captura indesejada polui a numeração. Este capítulo resolve isso com duas variações dos parênteses. O grupo não-capturante (?:...) agrupa sem capturar, mantendo a numeração limpa. O grupo nomeado dá um nome a uma captura em vez de um número, tornando a extração legível e robusta a mudanças. Juntos, eles transformam regex de média complexidade de um amontoado de m[1], m[2] difíceis de manter num código onde cada parte capturada tem um rótulo significativo. É um capítulo sobre legibilidade e manutenção da regex — o que, como o Cap 20 reforça, é tão importante quanto fazê-la funcionar.

# Grupos não-capturantes: (?:...)

O grupo não-capturante (?:...) agrupa um padrão — para aplicar um quantificador ou delimitar uma alternância — sem criar um grupo de captura numerado. O ?: logo após o parêntese de abertura é o que o marca como "só agrupamento". O resultado: você ganha o agrupamento sem poluir a numeração dos grupos de captura nem desperdiçar memória guardando trechos que não vai extrair.

regex
# (?:...) agrupa SEM capturar
(?:https?|ftp)://(\w+)
#   (?:https?|ftp) -> agrupa a alternância, NÃO captura
#   (\w+)          -> ESTE captura, e é o grupo 1

# Compare a numeração:
(https?)://(\w+)     # grupo 1 = protocolo, grupo 2 = domínio
(?:https?)://(\w+)   # protocolo não capturado; grupo 1 = domínio
Use (?:...) para agrupamento puro
A regra prática que une os Caps 6 e 9: se você usa parênteses apenas para agrupar — aplicar um quantificador a uma sequência ((?:ab)+), delimitar uma alternância dentro de um padrão maior ((?:gato|cachorro), Cap 7) — e não vai extrair aquele trecho, use o grupo não-capturante (?:...). Dois benefícios: a numeração dos grupos de captura reais fica limpa e previsível (você não precisa contar parênteses para descobrir que o dado que quer é o grupo 3 e não o 1), e o motor não desperdiça trabalho guardando capturas que ninguém usa. Em regex com muitos grupos, essa disciplina é a diferença entre um código onde m[2] aponta confiavelmente para o que você espera e um onde cada mudança no padrão renumera tudo. Capture o que vai usar; agrupe o resto com (?:...).

# Grupos nomeados: capturas com rótulo

Acessar capturas por número (m[1], m[2]) funciona, mas é frágil e ilegível: o número não diz o que aquele grupo é, e adicionar um grupo no meio renumera todos os seguintes, quebrando o código que os acessava. Os grupos nomeados resolvem isso dando um nome à captura. A sintaxe (no sabor JavaScript) é (?<nome>...) — o nome entre < e > logo após o ?. Depois, você acessa por nome em vez de número.

exemplo.js
// Grupo nomeado: (?<nome>padrão)  — note o nome entre < e >
const data = "09/06/2026"
const m = data.match(
  /(?<dia>\d{2})\/(?<mes>\d{2})\/(?<ano>\d{4})/
)

// Acesso por NOME via .groups (legível e robusto)
m.groups.dia     // "09"
m.groups.mes     // "06"
m.groups.ano     // "2026"
// compare com m[1], m[2], m[3] — qual é mais claro?

# Por que nomear: legibilidade e robustez

Os grupos nomeados trazem dois ganhos concretos. Legibilidade: m.groups.ano diz o que é; m[3] exige contar parênteses para entender. Quem lê a regex e o código que a usa entende a intenção. Robustez: se você adicionar um grupo no meio da regex, os números de todos os seguintes mudam — e o código que usava m[3] agora pega o dado errado, silenciosamente. Com nomes, m.groups.ano continua apontando para o ano, não importa quantos grupos surjam antes. É a mesma vantagem de nomear variáveis em vez de usar posições mágicas (toda a coleção).

Nomeie grupos em qualquer regex que outra pessoa vai ler
A heurística: para uma regex descartável de uma linha, números bastam. Para qualquer regex que vive no código, que extrai múltiplas partes, ou que outra pessoa (incluindo seu eu futuro) vai manter, nomeie os grupos. O custo é mínimo — alguns caracteres a mais no padrão — e o benefício é grande: o código que consome a regex fica autoexplicativo (m.groups.email em vez de m[2]), e a regex resiste a edições sem quebrar silenciosamente os acessos. É a aplicação à regex do mesmo princípio que vale para código em geral: nomes significativos derrotam posições mágicas. Uma regex com grupos nomeados se documenta sozinha — você lê o padrão e os nomes já dizem o que cada parte representa, transformando uma string críptica em algo legível.

# Backreferences e substituição com nomes

Os nomes também funcionam onde os números funcionavam. Uma backreference nomeada (Cap 8) usa \k<nome> para exigir a repetição de um grupo nomeado. E na substituição (Cap 16), $<nome> referencia o grupo nomeado no texto de saída. A mesma legibilidade se estende a esses contextos — em vez de \1 e $1, você usa o nome.

exemplo.js
// Backreference nomeada: \k<nome> (em vez de \1)
/(?<palavra>\w+) \k<palavra>/    // palavra repetida (Cap 8)

// Substituição com nomes: $<nome> (em vez de $1) — Cap 16
"09/06/2026".replace(
  /(?<dia>\d{2})\/(?<mes>\d{2})\/(?<ano>\d{4})/,
  "$<ano>-$<mes>-$<dia>"     // "2026-06-09" (legível!)
)

Capítulo 10

Lookahead e lookbehind

As âncoras (Cap 5) introduziram uma ideia poderosa: afirmações de largura zero, que verificam uma posição sem consumir caracteres. O lookaround generaliza isso ao extremo — ele permite afirmar que um padrão inteiro está (ou não está) presente antes ou depois da posição atual, sem incluí-lo na correspondência. "Combine um número, mas só se for seguido de %", "combine uma palavra, mas só se não for precedida de @". Essas condições contextuais, antes impossíveis, ficam ao alcance. O lookaround é a parte mais avançada da regex de uso comum, e a que mais confunde — em parte por sua sintaxe densa, em parte pelo conceito de "olhar sem consumir". Este capítulo desmonta os quatro tipos (lookahead/lookbehind, positivo/negativo), com cuidado especial na sintaxe do lookbehind, cujo (?<= é um ponto quente de confusão.

# Olhar sem consumir

O conceito central, herdado das âncoras: o lookaround tem largura zero. Ele verifica se um padrão está presente numa direção, mas não o inclui na correspondência nem move a posição do motor. \d+(?=%) combina os dígitos que vêm antes de um % — mas o % em si não faz parte do resultado; ele é apenas uma condição que precisa ser satisfeita. Essa separação entre "o que combina" e "as condições ao redor" é o que torna o lookaround único: você expressa contexto sem capturá-lo.

exemplo.js
// \d+(?=%) : dígitos SEGUIDOS de %, mas o % NÃO entra no match
"desconto de 50% hoje".match(/\d+(?=%)/)
// ["50"]  — só "50", o % ficou de fora (largura zero)

// Sem lookahead, o % entraria no resultado:
"desconto de 50% hoje".match(/\d+%/)
// ["50%"]  — agora o % faz parte da correspondência

# Lookahead: (?=...) e (?!...)

O lookahead olha para frente — verifica o que vem depois da posição atual. O positivo (?=...) afirma "seguido por este padrão"; o negativo (?!...) afirma "NÃO seguido por este padrão". Combine-os com o que vem antes para expressar condições: "um número seguido de %", "uma palavra não seguida de dois pontos". O lookahead é o mais usado dos quatro, em parte porque tem suporte universal entre os sabores.

regex
# Lookahead POSITIVO (?=...): seguido por
\d+(?=px)         # dígitos seguidos de "px" (sem incluir px)
#   em "16px" -> combina "16"

# Lookahead NEGATIVO (?!...): NÃO seguido por
\d+(?!px)         # dígitos NÃO seguidos de "px"
foo(?!bar)        # "foo" que não vem antes de "bar"

# Lookbehind: (?<=...) e (?<!...)

O lookbehind olha para trás — verifica o que vem antes da posição atual. A sintaxe inclui um < que a distingue do lookahead: o positivo (?<=...) afirma "precedido por"; o negativo (?<!...) afirma "NÃO precedido por". O exemplo clássico é extrair um valor após um símbolo sem incluir o símbolo: o preço depois de R$, o nome após @. O < na sintaxe é o que indica "para trás" — pense nele como uma seta apontando para a esquerda.

exemplo.js
// Lookbehind POSITIVO (?<=...): precedido por
"custa R$50 hoje".match(/(?<=R\$)\d+/)
// ["50"]  — dígitos precedidos de "R$", sem incluir o R$

// Lookbehind NEGATIVO (?<!...): NÃO precedido por
"preço 50 e R$80".match(/(?<!R\$)\b\d+/g)
// dígitos NÃO precedidos de R$ (pega o "50" solto)

// A sintaxe: o < indica "para trás" (seta à esquerda)
Lookbehind tem suporte e restrições variáveis por sabor
Diferente do lookahead (universal), o lookbehind tem história mais acidentada entre os sabores (Cap 17). No JavaScript, ele só foi padronizado em 2018 — código que precisa rodar em ambientes muito antigos pode não tê-lo. Alguns sabores exigem que o padrão dentro do lookbehind tenha tamanho fixo (sem quantificadores variáveis como + ou *), embora o JavaScript moderno permita tamanho variável. E motores diferentes têm comportamentos sutis. A consequência prática: lookbehind é poderoso, mas verifique o suporte no seu ambiente-alvo antes de depender dele, especialmente em código que roda em navegadores diversos ou em sabores não-JavaScript. Quando o lookbehind não está disponível ou complica, frequentemente um grupo de captura comum (Cap 6) resolve o mesmo problema de forma mais portátil — capture o que vem antes num grupo e ignore-o, em vez de usar lookbehind para excluí-lo.

# Lookahead para validação composta

Um uso elegante do lookahead: validar múltiplas condições sobre a mesma string. Uma senha que precisa ter ao menos uma maiúscula, um dígito e um símbolo — cada exigência é um lookahead no início, todos verificados a partir da posição inicial sem consumir nada, e então o padrão real combina o comprimento. É a forma idiomática de expressar "tudo isto deve ser verdade" numa única regex.

exemplo.js
// Senha: ≥8 chars, com maiúscula, minúscula e dígito.
// Cada (?=...) verifica uma condição sem consumir; tudo a partir do ^
const senha = /^(?=.*[A-Z])(?=.*[a-z])(?=.*\d).{8,}$/
senha.test("Abc12345")    // true
senha.test("abc12345")    // false (sem maiúscula)
//   (?=.*[A-Z]) -> "em algum lugar há uma maiúscula"
//   (?=.*\d)    -> "em algum lugar há um dígito"
//   .{8,}       -> e tem pelo menos 8 caracteres

Capítulo 11

Ganância vs preguiça

Os quantificadores (Cap 4) têm um comportamento que o capítulo anterior não revelou inteiramente, e que é responsável por uma das surpresas mais frequentes da regex: por padrão, eles são gananciosos (greedy) — combinam o máximo possível. Um .* não combina "o mínimo até encontrar o que vem depois"; ele combina tudo que puder e só recua se for forçado. Isso explica por que uma regex que parecia certa captura muito mais do que você queria. A solução é tornar o quantificador preguiçoso (lazy) com um ?, fazendo-o combinar o mínimo. Este capítulo desmonta a diferença entre ganância e preguiça, mostra o exemplo clássico onde isso morde (extrair conteúdo entre delimitadores), e prepara o terreno para entender o backtracking (Cap 18) — porque a ganância e o recuo que ela provoca são a raiz dos problemas de performance.

# Quantificadores são gananciosos por padrão

Por padrão, *, +, ? e {n,m} são gananciosos: eles consomem o máximo de texto que conseguem, e só devolvem (fazem backtrack) se o resto do padrão não conseguir combinar. .* aplicado a um texto agarra tudo até o fim, e então recua caractere por caractere até o restante da regex encaixar. Esse "pegar tudo e recuar" é o comportamento padrão, e a causa de capturas inesperadamente grandes.

exemplo.js
// .* é GANANCIOSO: pega o máximo possível
const html = "<b>negrito</b> e <b>mais</b>"
html.match(/<b>.*<\/b>/)
// ["<b>negrito</b> e <b>mais</b>"]
// O .* agarrou TUDO até o ÚLTIMO </b>, não o primeiro!
"Pegar tudo, depois recuar": como a ganância funciona
Vale entender o mecanismo, porque ele explica tanto a surpresa quanto a performance (Cap 18). Quando o motor encontra .*, ele primeiro consome todo o texto restante — o máximo possível. Depois, tenta combinar o que vem depois do .* na regex (no exemplo, </b>). Como o .* já comeu tudo, não sobrou nada para o </b> combinar, então o motor recua (backtrack): devolve um caractere de cada vez, testando a cada passo se o </b> agora encaixa. Ele para no último ponto onde encaixa — daí pegar até o último </b>, não o primeiro. Esse ciclo de "consumir o máximo, depois recuar até funcionar" é a ganância, e o número de recuos que ela pode gerar é exatamente o que torna certas regex catastroficamente lentas (Caps 18-19).

# Preguiça: o ? que minimiza

A solução para a ganância indesejada é tornar o quantificador preguiçoso (lazy, ou "não-guloso"), adicionando um ? logo depois dele: *?, +?, {n,m}?. Um quantificador preguiçoso combina o mínimo possível — ele consome só o necessário para o resto do padrão encaixar, parando na primeira oportunidade em vez da última. .*? entre delimitadores pega o menor trecho, resolvendo o problema do exemplo anterior.

exemplo.js
// .*? é PREGUIÇOSO: pega o mínimo possível
const html = "<b>negrito</b> e <b>mais</b>"
html.match(/<b>.*?<\/b>/)
// ["<b>negrito</b>"]  — para no PRIMEIRO </b> (correto!)

// O ? após o quantificador o torna preguiçoso:
//   *  -> *?     (zero ou mais, preguiçoso)
//   +  -> +?     (um ou mais, preguiçoso)
//   {2,5} -> {2,5}?

# O exemplo que todo mundo encontra

O caso clássico onde ganância vs preguiça importa: extrair conteúdo entre delimitadores quando há vários no texto. Tags HTML, valores entre aspas, blocos entre marcadores. A versão gananciosa pega do primeiro delimitador de abertura ao último de fechamento, englobando tudo no meio; a preguiçosa pega cada par individualmente. Reconhecer esse padrão — "estou extraindo entre delimitadores repetidos" — é o sinal para usar a versão preguiçosa.

exemplo.js
const texto = 'a="1" b="2" c="3"'

// Ganancioso: pega da primeira à última aspa (errado)
texto.match(/"(.*)"/)[1]      // '1" b="2" c="3'  (tudo no meio!)

// Preguiçoso: cada valor individual (certo)
[...texto.matchAll(/"(.*?)"/g)].map(m => m[1])
// ["1", "2", "3"]  (cada par de aspas)

// Alternativa muitas vezes melhor: classe negada (sem backtracking)
[...texto.matchAll(/"([^"]*)"/g)].map(m => m[1])
// ["1", "2", "3"]  — [^"]* = "até a próxima aspa", direto
Classe negada costuma ser melhor que .*?
Há uma alternativa à preguiça que muitas vezes é superior: a classe negada (Cap 3). Para "conteúdo entre aspas", tanto ".*?" (preguiçoso) quanto "[^"]*" (qualquer coisa menos aspa) funcionam — mas o segundo é frequentemente mais rápido e mais claro. A razão liga ao Cap 18: .*? ainda envolve backtracking (o motor testa parar a cada caractere), enquanto [^"]* avança direto até a aspa sem recuar, porque a classe exclui o delimitador por construção. Como princípio: quando você quer "tudo até o caractere X", prefira a classe negada [^X]* à versão preguiçosa .*?X — ela expressa a intenção mais diretamente ("nada de X até o X") e evita o backtracking que o ponto-estrela gera. A preguiça é a ferramenta certa quando o delimitador é mais complexo que um único caractere; para delimitadores simples, a classe negada é mais eficiente e legível.

Capítulo 12

Flags e modificadores

Uma mesma regex pode se comportar de formas diferentes conforme as flags (modificadores) ativadas. Elas ajustam regras globais do motor: diferenciar ou não maiúsculas, fazer o . incluir quebras de linha, mudar o que ^ e $ significam (Cap 5), processar todas as ocorrências em vez da primeira. As flags já apareceram de passagem nos capítulos anteriores — a g nos exemplos de matchAll, a m nas âncoras —; este capítulo as reúne e explica cada uma. São poucas, mas mudam profundamente o resultado, e escolher as flags certas é parte essencial de escrever a regex correta. Confundir o efeito de uma flag (ou esquecer uma necessária) é uma fonte comum de regex que "quase funciona". Este é um capítulo de referência prática que fecha os fundamentos antes da parte aplicada.

# Onde as flags ficam

A localização das flags depende do sabor (Cap 17). No JavaScript, a regex literal as coloca após a barra de fechamento: /padrão/flags. Várias flags se combinam concatenando suas letras: /padrão/gi ativa a g e a i. Em outras formas e linguagens, há sintaxes diferentes (um argumento separado, modificadores inline), mas o conjunto de flags e seus efeitos são amplamente compartilhados.

exemplo.js
// No JS: as flags vêm após a barra final
/padrão/g          // flag g (global)
/padrão/gi         // g e i combinadas

// Forma com o construtor RegExp (flags como 2º argumento):
new RegExp("padrão", "gi")

// Modificador inline (alguns sabores): (?i) no início do padrão

# g (global): todas as ocorrências

A flag g (global) muda o motor de "encontre a primeira correspondência" para "encontre todas". Sem ela, métodos como match e replace param na primeira ocorrência; com ela, processam todas. É a flag que você ativa para contar ocorrências, substituir todas as instâncias, ou iterar sobre cada correspondência (matchAll). A maioria dos casos de "substituir tudo" e "encontrar todos" depende dela.

exemplo.js
// SEM g: só a primeira ocorrência
"a-b-c".replace(/-/, "_")       // "a_b-c" (só o 1º)

// COM g: todas as ocorrências
"a-b-c".replace(/-/g, "_")      // "a_b_c" (todos)

// matchAll exige g para iterar sobre todas (Cap 13)
[..."1 2 3".matchAll(/\d/g)]      // todas as correspondências

# i (insensível a maiúsculas)

A flag i (case-insensitive) faz a regex ignorar a diferença entre maiúsculas e minúsculas. Com ela, /gato/i combina "gato", "Gato", "GATO". É extremamente comum em buscas e validações onde o caso não importa — nomes, comandos, palavras-chave. Sem ela, você teria que escrever classes como [gG][aA][tT][oO], verboso e ilegível; a flag i resolve numa letra.

exemplo.js
// Sem i: sensível ao caso
/gato/.test("GATO")        // false

// Com i: ignora maiúsculas/minúsculas
/gato/i.test("GATO")       // true
/gato/i.test("Gato")       // true

// Equivale a, mas muito mais legível que:
//   [gG][aA][tT][oO]

# m (multiline) e s (dotall)

Duas flags mudam como o motor lida com texto multilinha, e é fácil confundi-las. A m (multiline) muda as âncoras: com ela, ^ e $ combinam o início e fim de cada linha, não do texto inteiro (Cap 5). A s (dotall, ou "single line") muda o ponto: com ela, o . passa a combinar também a quebra de linha, que por padrão ele ignora (Cap 2). Nomes parecidos, efeitos diferentes: m mexe nas âncoras, s mexe no ponto.

exemplo.js
const texto = "linha1\nlinha2"

// m (multiline): ^ e $ valem por LINHA (Cap 5)
texto.match(/^linha\d$/gm)     // ["linha1", "linha2"]

// s (dotall): o . passa a incluir \n também
/linha1.linha2/s.test(texto)  // true (o . casou o \n)
/linha1.linha2/.test(texto)   // false (sem s, . não casa \n)

// MEMORIZE: m -> âncoras (^ $);  s -> o ponto (.)
A flag g e o estado: a pegadinha do lastIndex
A flag g tem um comportamento traiçoeiro em JavaScript quando você reutiliza o mesmo objeto regex em chamadas sucessivas de test() ou exec(). Uma regex com g mantém estado interno (a propriedade lastIndex): cada chamada continua de onde a anterior parou, em vez de recomeçar. O resultado é o bug clássico em que regex.test(x) retorna true numa chamada e false na seguinte com a mesma entrada, porque o lastIndex avançou. A defesa: não reutilize uma regex global com test()/exec() em loop esperando que recomece; use match/matchAll (Cap 13) para iteração, ou crie a regex de novo a cada uso, ou resete lastIndex = 0. É uma das pegadinhas mais confusas do JavaScript, e ela existe só com a flag g — uma razão a mais para entender o que cada flag ativa.

Capítulo 13

Regex em JavaScript

Os doze capítulos anteriores trataram da linguagem da regex — os padrões em si. Este e os próximos a colocam para trabalhar em contextos reais, começando pelo JavaScript, o sabor de referência deste volume e a linguagem do stack da coleção (Vols I-II). JavaScript tem regex de primeira classe — uma sintaxe literal nativa e um conjunto de métodos para testar, buscar, extrair e substituir. Conhecer qual método usar para quê é tão importante quanto conhecer os padrões: usar test quando você quer um booleano, match ou matchAll para extrair, replace para transformar. Este capítulo é o guia prático desses métodos, das duas formas de criar uma regex, e das pegadinhas específicas do JavaScript — fechando a ponte entre a teoria dos padrões e o código que os usa.

# Duas formas de criar uma regex

JavaScript oferece duas sintaxes para criar uma regex. A literal, entre barras — /padrão/flags —, é compilada uma vez quando o código é lido, mais rápida e legível, ideal para padrões fixos. O construtor new RegExp("padrão", "flags") recebe strings, e é necessário quando o padrão é dinâmico — montado a partir de variáveis em runtime. A escolha: literal para padrões conhecidos em código, construtor quando o padrão depende de dados.

exemplo.js
// Literal: padrão fixo, compilado uma vez (preferível)
const re = /^\d{4}$/

// Construtor: para padrões DINÂMICOS (montados em runtime)
const palavra = "gato"
const re2 = new RegExp(`\\b${palavra}\\b`, "gi")
// CUIDADO: na string, \ vira \\ (dupla barra) — ver aviso
No construtor, escape as barras invertidas
Uma pegadinha do new RegExp: o padrão é uma string, e na string a barra invertida \ já é um caractere de escape. Então o que na regex literal é \d vira, na string do construtor, \\d — você precisa de duas barras para que a string produza uma barra que a regex enxergue. Esquecer isso é um erro comum: new RegExp("\d") não combina dígitos (o \d da string vira só d), enquanto new RegExp("\\d") funciona. Por isso a regex literal é preferível quando possível — sem barras duplicadas, mais legível, e o editor entende que é uma regex. Reserve o construtor para quando o padrão é genuinamente dinâmico, e aí lembre da regra das barras duplas. E um cuidado de segurança: se o padrão vem de input do usuário, você corre risco de ReDoS (Cap 19) — nunca construa regex a partir de dados não confiáveis sem cuidado.

# test: a pergunta sim/não

Quando você só quer saber se o texto combina — validação, verificação de formato —, o método test retorna um booleano. É o método mais simples e o certo para validação: regex.test(texto) dá true ou false. Combinado com âncoras (Cap 5), é a base de toda validação de formato em JavaScript.

exemplo.js
// test() -> booleano: o texto combina?
const cep = /^\d{5}-?\d{3}$/
cep.test("12345-678")     // true
cep.test("abc")           // false

// Uso típico em validação:
if (!cep.test(entrada)) {
  throw new Error("CEP inválido")
}

# match e matchAll: extrair

Para extrair correspondências e grupos (Cap 6), há match e matchAll. Sem a flag g, str.match(re) retorna a primeira correspondência com seus grupos. Com a flag g, match retorna só o array das correspondências completas (sem grupos) — e para iterar sobre todas com os grupos, usa-se matchAll, que devolve um iterador. A regra prática: match sem g para uma correspondência detalhada, matchAll com g para todas com detalhes.

exemplo.js
// match SEM g: a 1ª correspondência + seus grupos
"09/06/2026".match(/(\d{2})\/(\d{2})/)
// ["09/06", "09", "06", ...]  (match + grupos)

// match COM g: só os textos completos (sem grupos)
"a1 b2 c3".match(/\w\d/g)      // ["a1", "b2", "c3"]

// matchAll: TODAS as correspondências COM grupos (precisa de g)
for (const m of "a1 b2".matchAll(/(\w)(\d)/g)) {
  console.log(m[1], m[2])    // "a" "1", depois "b" "2"
}

# replace e replaceAll: transformar

Para transformar texto, replace substitui correspondências por outra coisa — e o texto de substituição pode referenciar grupos capturados ($1, $<nome>, Caps 8-9). Sem a flag g, substitui a primeira; com g (ou usando replaceAll), substitui todas. E o substituto pode ser uma função, que recebe a correspondência e os grupos e retorna o texto de troca — útil para transformações que dependem do conteúdo. O Cap 16 aprofunda a substituição.

exemplo.js
// replace com grupos: reformatar (Cap 16)
"09/06/2026".replace(/(\d{2})\/(\d{2})\/(\d{4})/, "$3-$2-$1")
// "2026-06-09"

// replaceAll (ou replace com g): todas as ocorrências
"a-b-c".replaceAll("-", "_")        // "a_b_c"

// Substituto como FUNÇÃO: transforma cada correspondência
"abc".replace(/[a-z]/g, (c) => c.toUpperCase())
// "ABC"
O método certo para a pergunta certa
A escolha do método decorre do que você quer fazer, e usar o errado complica o código. Quer um sim/não (validar, verificar)? → test(). Quer extrair uma parte ou os grupos de uma correspondência? → match() sem g. Quer extrair de todas as correspondências com seus grupos? → matchAll() com g. Quer transformar o texto? → replace() ou replaceAll(). Há um anti-padrão comum: usar match só para saber se algo combina (checando se o retorno é não-nulo) — test é mais claro e eficiente para isso. E matchAll exige a flag g, ou lança erro. Mapear a intenção ao método correto torna o código de regex em JavaScript direto e legível, em vez de uma coleção de truques. Memorize o quarteto: test (booleano), match (uma), matchAll (todas), replace (transforma).

Capítulo 14

Regex no shell

O Volume XVI mostrou grep, sed e awk processando texto; agora fechamos o círculo explicando a regex que os move. No shell, regex aparece em toda parte, mas com uma complicação que confunde: há dois dialetos — a regex "básica" (BRE) e a "estendida" (ERE) — e as ferramentas diferem em qual usam por padrão. Caracteres que são metacaracteres num dialeto precisam de escape no outro, o que faz a "mesma" regex parecer diferente entre grep e grep -E. Este capítulo desmonta essa confusão, mostra como usar regex efetivamente nas três ferramentas clássicas, e conecta os padrões dos capítulos anteriores ao seu uso no terminal — onde a regex deixa de ser teoria e vira a ferramenta diária de buscar em código, filtrar logs e transformar texto em lote.

# BRE vs ERE: os dois dialetos

A fonte de confusão da regex no shell: existem duas variantes POSIX. Na BRE (Basic Regular Expression), metacaracteres como +, ?, {}, () e | são tratados literalmente a menos que escapados com \. Na ERE (Extended Regular Expression), eles são metacaracteres diretamente, como na regex que você aprendeu. O grep usa BRE por padrão; grep -E (ou egrep) usa ERE. Por isso a mesma intenção se escreve diferente: na BRE \(grupo\), na ERE (grupo).

terminal
# BRE (grep padrão): +, ?, {}, (), | precisam de \ para serem especiais
grep "colou\?r" arquivo      # ? especial só com \  (BRE)
grep "\(ab\)\+" arquivo      # grupo e + escapados (BRE)

# ERE (grep -E): metacaracteres diretos, como a regex "normal"
grep -E "colou?r" arquivo    # ? especial direto (ERE)
grep -E "(ab)+" arquivo      # grupo e + diretos (ERE)
Prefira grep -E: o dialeto que você já conhece
A recomendação prática que simplifica a vida: use grep -E (ERE) quase sempre. A ERE corresponde à regex que você aprendeu nos capítulos anteriores — +, ?, (, ), | funcionam diretamente, sem o escape extra da BRE. A BRE existe por razões históricas e ainda é o padrão do grep e do sed por compatibilidade, mas seus escapes (\+, \(, \|) são uma fonte constante de erro e ilegibilidade. Adotar grep -E como hábito (e sed -E para o sed) faz a regex no shell se comportar como a do JavaScript e de quase todo lugar, eliminando a necessidade de lembrar quais caracteres precisam de barra em qual ferramenta. Quando vir uma regex de shell cheia de \( e \{, é BRE; reescrevê-la em ERE com -E a torna legível.

# grep: buscar com regex

O grep (Vol XVI, Cap 11) é a ferramenta de busca por excelência, e suas opções essenciais para regex valem revisar. -E ativa a ERE; -i ignora o caso (a flag i do Cap 12); -o mostra só a parte que combinou (não a linha inteira), útil para extrair; -P (onde disponível) ativa a regex estilo Perl (PCRE), com recursos avançados como lookaround (Cap 10) que a ERE não tem.

terminal
# Buscar linhas que combinam (ERE + ignorar caso)
grep -Ei "erro|falha" app.log

# -o : mostrar só a parte que combinou (extrair)
grep -Eo "[0-9]{3}-[0-9]{4}" contatos.txt

# -P : PCRE (Perl), com lookaround e mais (onde disponível)
grep -Po "(?<=R\\$)[0-9]+" precos.txt   # valor após R$ (lookbehind)

# sed: substituir com regex

O sed (Vol XVI, Cap 12) usa regex no seu comando de substituição s/padrão/troca/. As backreferences na substituição (Cap 8) usam \1, \2 (não $1 como no JavaScript). E, como o grep, o sed usa BRE por padrão — sed -E ativa a ERE, recomendada pela mesma razão. É a ferramenta para transformações de texto em lote no shell, do reformatar ao limpar.

terminal
# Substituir com regex (use -E para ERE)
sed -E "s/[0-9]+/N/g" arquivo     # todo número vira "N"

# Backreferences na substituição: \1, \2 (não $1)
echo "09/06/2026" | sed -E "s|([0-9]{2})/([0-9]{2})/([0-9]{4})|\3-\2-\1|"
# 2026-06-09  (grupos reordenados; | como separador p/ evitar / na data)

# awk: regex em colunas

O awk (Vol XVI, Cap 12) integra regex ao seu processamento por colunas. Você pode filtrar linhas por um padrão (/regex/ { ação }), testar se um campo combina, e usar regex como separador de campos. Combina o poder dos padrões com o pensamento em colunas, sendo a escolha quando a tarefa envolve dados tabulares e correspondência de padrões.

terminal
# Filtrar linhas por regex e processar colunas
awk "/ERROR/ { print \$4 }" app.log   # campo 4 das linhas com ERROR

# Testar se um campo combina com um padrão (~)
awk "\$1 ~ /^[0-9]+\$/ { print }" dados   # linhas cujo campo 1 é numérico

# Regex como separador de campos (-F aceita regex)
awk -F"[,;]" "{ print \$2 }" dados      # separa por vírgula OU ponto-e-vírgula
Aspas e escape: a regex enfrenta o shell primeiro
Uma complicação extra da regex no shell, conectando ao Vol XVI (Caps 9, 14): a regex passa primeiro pelo shell, que tem suas próprias regras de expansão e caracteres especiais, antes de chegar à ferramenta. Caracteres como $, \, * e aspas significam coisas para o shell e para a regex — e os dois podem brigar. A defesa: envolva os padrões de regex em aspas simples ('...'), que impedem o shell de interpretar o conteúdo (Vol XVI, Cap 14), deixando a regex chegar intacta à ferramenta. Use aspas duplas só quando precisa que o shell expanda uma variável dentro do padrão — e aí cuidado redobrado com o escape. A regra geral: regex de shell vai entre aspas simples, salvo quando você precisa de interpolação. Ignorar isso leva a erros bizarros onde o shell come parte do padrão antes de o grep vê-lo.

Capítulo 15

Validação com regex

A validação é o uso mais comum de regex — e o mais cheio de armadilhas. Garantir que um input tem o formato certo (um CEP, um código, um telefone) é onde a regex brilha, mas também onde excessos de confiança geram código que valida mal ou rejeita entradas legítimas. Este capítulo reúne os princípios de uma boa validação por regex — as âncoras obrigatórias (Cap 5), a especificidade (Cap 3), a conexão com o Zod (Vol XII) — e enfrenta de frente o exemplo mais instrutivo de todos: validar e-mail, o caso onde "use uma regex" é quase sempre a resposta errada. É um capítulo tanto sobre como validar com regex quanto sobre quando não, porque saber a fronteira é parte de usar a ferramenta com competência. A regra que atravessa tudo: valide o formato, não a semântica; e conheça os limites do que um padrão pode garantir.

# Os princípios de uma boa validação

Três regras, todas vistas antes, formam a base de uma validação correta. Ancore com ^ e $ (Cap 5): sem isso, você verifica se o input contém algo válido, não se é válido — um furo grave. Seja específico (Cap 3): use classes que descrevem exatamente o que é aceito, não o permissivo . que aceita lixo. Valide o formato, não a semântica: regex verifica estrutura ("quatro dígitos"), não significado ("um ano válido") — para regras semânticas, código comum é melhor. Essas três disciplinas pegam a maioria dos erros de validação.

exemplo.js
// CEP brasileiro: 5 dígitos, hífen opcional, 3 dígitos — ANCORADO
const cep = /^\d{5}-?\d{3}$/
cep.test("12345-678")    // true
cep.test("x12345-678x")  // false (âncoras barram o lixo ao redor)

// Placa Mercosul: 3 letras, 1 dígito, 1 letra, 2 dígitos
const placa = /^[A-Z]{3}\d[A-Z]\d{2}$/
placa.test("ABC1D23")     // true
Validação sem âncoras é o erro nº 1 (de novo)
Vale repetir o alerta do Cap 5 porque é o erro mais frequente e mais perigoso. Uma regex de validação sem ^ e $ verifica "contém", não "é" — e isso deixa passar entradas maliciosas com o formato válido escondido no meio de lixo. Conecta diretamente ao Vol XIII: input não validado é a porta de entrada de ataques. Uma validação /\d{4}/ para um PIN aceita "meu pin é 1234, hackeie-me"; com âncoras, /^\d{4}$/ exige que o input inteiro sejam quatro dígitos. Toda regex de validação ancora início e fim. Se você revisar uma única coisa numa regex de validação, que seja a presença das âncoras — a ausência delas transforma a validação numa ilusão de segurança.

# Regex e Zod: validação tipada

No stack da coleção, a regex de validação raramente fica solta — ela vive dentro do Zod (Vol XII), que a integra à validação tipada da fronteira de dados. z.string().regex(/.../) aplica o padrão como parte de um schema, combinando a precisão da regex com as mensagens de erro, a inferência de tipos e a composição do Zod. É a forma idiomática de usar regex para validação numa aplicação TypeScript: o regex descreve o formato, o Zod cuida do resto.

schema.ts
import { z } from "zod"

// Regex dentro do Zod: formato + validação tipada (Vol XII)
const schema = z.object({
  cep: z.string().regex(/^\d{5}-?\d{3}$/, "CEP inválido"),
  placa: z.string().regex(/^[A-Z]{3}\d[A-Z]\d{2}$/),
})
// a regex valida o formato; o Zod dá tipo, erro e composição
// nota: o Zod já tem z.email(), z.url() etc. — prefira-os (ver abaixo)

# O caso do e-mail: quando NÃO usar regex

O exemplo mais instrutivo de validação é o e-mail, justamente porque a regex é a ferramenta errada para ele — e entender o porquê ensina os limites da regex em geral. A especificação real de e-mail (RFC 5322) é absurdamente complexa; uma regex que a implemente fielmente tem milhares de caracteres e é ilegível e propensa a erros. Regex simples de e-mail ou rejeitam endereços válidos (e-mails com +, subdomínios, caracteres incomuns mas legais) ou aceitam inválidos. E mesmo a regex perfeita não diz se o e-mail existe — só a verificação real (enviar um e-mail de confirmação, o Vol XIII) prova isso.

exemplo.js
// ❌ Regex "de e-mail" comum: rejeita endereços VÁLIDOS
//   /^\w+@\w+\.\w+$/  -> rejeita "ana+tag@sub.exemplo.com" (válido!)

// ✅ Use um validador dedicado — o Zod tem um (Vol XII):
z.email()           // validação de e-mail mantida e testada

// ✅ E a ÚNICA prova real de que o e-mail existe é a confirmação:
//   enviar um magic link / código (Vol XIII, Cap 15)
// Regex valida FORMATO; confirmação valida EXISTÊNCIA.
A lição do e-mail: valide formato, confirme existência
O e-mail ensina uma distinção que vale para muita validação: regex valida formato (a estrutura sintática), nunca existência ou semântica (se o valor é real, válido no mundo). Uma regex pode confirmar que "31/02/2026" tem o formato de data, mas não que 31 de fevereiro existe — isso é regra semântica, para código. Pode confirmar que um e-mail parece um e-mail, mas não que ele recebe mensagens — só o envio de uma confirmação prova (Vol XIII, Cap 15). A regra geral: use regex para uma checagem de formato razoável e permissiva (rejeitar lixo óbvio), e deixe a validação séria para validadores dedicados (o z.email(), parsers de data) e para a confirmação real onde a existência importa. Tentar fazer regex resolver semântica produz monstros ilegíveis que ainda assim falham. Conhecer essa fronteira é usar a regex com sabedoria.

Capítulo 16

Substituição e captura

A regex não só encontra padrões — ela os transforma. A substituição é onde a captura (Cap 6) e as backreferences (Cap 8) pagam todos os dividendos: você combina um padrão, captura suas partes, e as reorganiza num novo formato. Reformatar datas, mascarar dados sensíveis, converter delimitadores, limpar texto — tudo isso é substituição com regex. Este capítulo reúne as técnicas: o texto de substituição com referências aos grupos ($1, $<nome>), a substituição por função que permite lógica arbitrária, e os casos práticos onde substituir com regex resolve em uma linha o que exigiria laços manuais. É o capítulo que completa o ciclo da regex — de encontrar (testar, buscar) a extrair (capturar) a transformar (substituir) —, mostrando a regex como uma ferramenta de manipulação de texto, não só de busca.

# Referências aos grupos no substituto

O texto de substituição pode referenciar o que a regex capturou, usando $1, $2 para os grupos numerados (Cap 6) e $<nome> para os nomeados (Cap 9). O $& refere-se à correspondência inteira. Isso permite reorganizar o que foi combinado: você captura as partes na ordem em que aparecem e as recoloca em outra ordem ou formato no substituto. A reformatação de data — de dd/mm/aaaa para aaaa-mm-dd — é o exemplo canônico.

exemplo.js
// $1, $2... referenciam os grupos no texto de substituição
"09/06/2026".replace(/(\d{2})\/(\d{2})\/(\d{4})/, "$3-$2-$1")
// "2026-06-09"  (grupos reordenados)

// $<nome> para grupos nomeados (Cap 9) — mais legível
"09/06/2026".replace(
  /(?<d>\d{2})\/(?<m>\d{2})\/(?<a>\d{4})/,
  "$<a>-$<m>-$<d>"
)

// $& = a correspondência inteira
"erro 42".replace(/\d+/, "[$&]")   // "erro [42]"

# Substituição por função

Quando a transformação precisa de lógica — não só rearranjar, mas calcular, condicionar, ou transformar cada correspondência de forma diferente —, o substituto pode ser uma função. Ela recebe a correspondência e os grupos como argumentos e retorna o texto de troca. Isso abre a porta para transformações arbitrárias: converter unidades, aplicar cálculos, formatar conforme o conteúdo. É o que torna a substituição com regex tão poderosa quanto um laço de transformação, mas em uma expressão.

exemplo.js
// O substituto como função: lógica por correspondência
// Dobrar todos os números de um texto:
"tenho 3 gatos e 2 cães".replace(/\d+/g, (m) => Number(m) * 2)
// "tenho 6 gatos e 4 cães"

// A função recebe (match, grupo1, grupo2, ...):
"09/06".replace(/(\d{2})\/(\d{2})/, (m, dia, mes) => {
  return `dia ${dia} do mês ${mes}`
})
// "dia 09 do mês 06"

# Casos práticos de substituição

A substituição com regex resolve elegantemente tarefas comuns de manipulação de texto. Mascarar dados sensíveis (esconder dígitos de um cartão, conectando à segurança do Vol XIII). Normalizar formatos (espaços múltiplos em um, separadores inconsistentes). Limpar texto (remover caracteres indesejados, tags). Cada um seria um laço manual; com regex, é uma substituição.

exemplo.js
// Mascarar: manter os 4 últimos dígitos de um cartão (Vol XIII)
"1234567812345678".replace(/\d(?=\d{4})/g, "*")
// "************5678"  (cada dígito seguido de ≥4 dígitos vira *)

// Normalizar espaços múltiplos em um só
"texto   com    espaços".replace(/\s+/g, " ")
// "texto com espaços"

// Remover tudo que não é dígito (extrair só números)
"(11) 98765-4321".replace(/\D/g, "")
// "11987654321"
Substituição é extração + transformação numa só passada
A substituição com regex é frequentemente a forma mais concisa e eficiente de uma transformação de texto, porque combina três operações numa só passada: encontrar o padrão, capturar suas partes, e reescrever. O que em código imperativo seria "percorra o texto, identifique cada ocorrência, extraia os pedaços, monte a saída" vira uma chamada a replace. A substituição por função leva isso ao limite, permitindo qualquer lógica por correspondência. Mas vale o mesmo cuidado dos outros capítulos: para transformações muito complexas, ou que envolvem estrutura aninhada (Cap 8), a substituição com regex pode virar ilegível, e um parser ou processamento explícito é melhor. A heurística: substituição com regex brilha em transformações locais e regulares — reformatar, mascarar, limpar, normalizar; quando a lógica fica intrincada demais para caber confortavelmente numa função de substituição, é sinal de cruzar para código comum.

# No shell: a mesma ideia, outra sintaxe

A substituição com regex não é exclusiva do JavaScript — ela é a essência do sed (Caps 12, 14) e aparece em editores, IDEs e quase toda ferramenta de texto. A diferença está na sintaxe das referências (\1 no sed, $1 no JS) e dos delimitadores, mas o conceito é idêntico: padrão, captura, reescrita. Aprender a substituição em um contexto transfere para todos — a mesma reformatação de data se faz no JavaScript, no sed, no "find and replace" do editor.

Capítulo 17

Sabores PCRE, POSIX, JS

"A mesma regex" nem sempre se comporta igual em lugares diferentes — e quem não sabe disso perde horas com uma expressão que funciona no editor mas falha no código, ou no JavaScript mas não no grep. A razão é que regex não é um padrão único: é uma família de sabores (flavors), implementações com sintaxes e recursos que divergem em detalhes. O Cap 14 já mostrou um exemplo (BRE vs ERE no shell). Este capítulo mapeia os principais sabores — POSIX, PCRE, e o do JavaScript —, o que cada um suporta e onde divergem, para que você saiba qual regex escrever em qual contexto, e como portar entre eles. Não é um catálogo exaustivo (seria infindável), mas o mapa das diferenças que mais mordem, fechando a parte prática antes dos capítulos de produção sobre performance e segurança.

# Por que existem sabores

A regex nasceu na teoria dos autômatos e se espalhou por ferramentas e linguagens ao longo de décadas, cada uma implementando-a com pequenas variações e extensões. Não houve um "padrão único" desde o início — houve o POSIX (formalizando as variantes BRE e ERE), depois o Perl, que adicionou tantos recursos que virou referência própria (PCRE), e cada linguagem moderna seguiu uma dessas tradições com seus ajustes. O resultado é uma família aparentada mas não idêntica: o núcleo (literais, classes, quantificadores, âncoras, grupos) é praticamente universal, mas os recursos avançados e detalhes de sintaxe divergem.

O núcleo é universal; as bordas divergem
A boa notícia que relativiza a confusão: tudo o que você aprendeu nos Caps 1-8 — caracteres literais, o ponto, classes [...] e \d\w\s, quantificadores * + ? {n,m}, âncoras ^ $ \b, grupos (...), alternância |, backreferences — é praticamente idêntico em todos os sabores. É o núcleo comum, e ele cobre a vasta maioria do uso real. As divergências ficam nas bordas: lookbehind (Cap 10), grupos nomeados (sintaxe varia), classes Unicode, modificadores inline, alguns atalhos. Então não se assuste: a regex que você sabe transfere quase inteira entre JavaScript, Python, grep -E e a maioria dos lugares. Os sabores importam quando você usa um recurso avançado ou porta uma regex entre contextos muito diferentes — aí vale conferir.

# POSIX: BRE e ERE

O padrão POSIX define duas variantes, vistas no Cap 14: BRE (básica) e ERE (estendida), que diferem em quais metacaracteres exigem escape. É o sabor do mundo Unix tradicional — grep, sed, awk. Suas limitações são notáveis para quem vem de sabores modernos: o POSIX clássico não tem \d (usa [[:digit:]]), nem lookaround, nem grupos nomeados. As "classes POSIX" como [[:alpha:]] e [[:digit:]] são sua forma de expressar conjuntos comuns.

# PCRE: o sabor rico

O PCRE (Perl Compatible Regular Expressions) é o sabor mais rico e influente — originado do Perl, adotado por muitas linguagens e ferramentas (PHP, o grep -P, muitas outras). Ele tem praticamente tudo: lookaround completo, grupos nomeados, backreferences, modificadores inline, recursão, e mais. Quando um tutorial mostra um recurso avançado, frequentemente é PCRE. Sua riqueza é poder e também peso — alguns recursos do PCRE não existem em sabores mais enxutos, então depender deles reduz a portabilidade.

# O sabor do JavaScript

O JavaScript (o sabor de referência deste volume) é moderno e capaz, próximo do PCRE em muitos aspectos, mas com particularidades. Ele tem lookahead desde sempre e lookbehind desde 2018 (Cap 10), grupos nomeados com a sintaxe (?<nome>...) (Cap 9), e as flags do Cap 12. Mas difere em detalhes: a sintaxe de algumas construções, o tratamento de Unicode (que melhora muito com a flag u), e a ausência de alguns recursos do PCRE (como recursão). Para o stack da coleção, é o sabor que importa.

Conheça o sabor do seu alvo, e teste lá
A lição prática para não perder tempo com diferenças de sabor: saiba onde sua regex vai rodar e teste-a nesse contexto. Uma regex que você validou no console do navegador (sabor JavaScript) pode não funcionar igual no grep (POSIX) ou no seu validador de backend em outra linguagem. Antes de depender de um recurso avançado — lookbehind, grupos nomeados, classes Unicode —, confirme que o sabor do destino o suporta. Ferramentas como o regex101.com (Cap 21) permitem escolher o sabor e testar exatamente nele, evitando a surpresa de "funcionava no meu teste". E uma estratégia de portabilidade: quando a regex precisa rodar em múltiplos sabores, fique no núcleo comum (Caps 1-8) e evite os recursos de borda — uma regex que usa só literais, classes, quantificadores, âncoras e grupos funciona em praticamente todo lugar. Os recursos avançados são poderosos, mas cada um que você usa amarra a regex a um conjunto menor de sabores.

Capítulo 18

Performance e backtracking

Uma regex pode estar correta e ainda assim ser desastrosa — combinar o que deveria, mas levar segundos, minutos, ou efetivamente para sempre em certas entradas. A causa tem nome: catastrophic backtracking, uma explosão do número de tentativas que o motor faz antes de desistir. O Cap 11 mostrou o backtracking como mecanismo da ganância; aqui vemos como ele pode sair de controle, transformando uma regex inocente numa bomba de performance. Este capítulo explica como o motor de regex funciona por baixo (o backtracking), os padrões que disparam a explosão exponencial, e como reescrevê-los para evitá-la. É conhecimento essencial não só por performance, mas por segurança: o catastrophic backtracking é a base do ataque ReDoS (Cap 19), onde uma entrada maliciosa derruba um servidor. Entender o motor é o que permite escrever regex que são rápidas e seguras.

# Como o motor faz backtracking

A maioria dos motores de regex (incluindo o do JavaScript) é do tipo backtracking: ao encontrar várias possibilidades, ele tenta uma, e se ela leva a um beco sem saída, volta (backtracks) e tenta outra. Com quantificadores gananciosos (Cap 11), há muitas possibilidades — cada * pode consumir diferentes quantidades de texto, e o motor explora essas opções. Na maioria dos casos, isso é rápido. O problema surge quando as possibilidades se multiplicam umas com as outras, gerando um número astronômico de combinações a testar.

Backtracking: tentar, falhar, voltar, tentar de novo
O modelo mental: imagine o motor num labirinto de escolhas. Cada quantificador é uma bifurcação — "consumo mais um caractere ou paro aqui?". O motor escolhe um caminho (ganancioso: consome o máximo), avança, e se chega a um beco sem saída (o resto do padrão não combina), ele volta à última bifurcação e tenta o outro caminho. Para padrões simples, há poucas bifurcações e o labirinto se resolve rápido. Mas quando quantificadores se aninham ou se sobrepõem de certas formas, o número de caminhos a explorar cresce exponencialmente com o tamanho da entrada — e o motor pode precisar testar bilhões de combinações antes de concluir que não há match. É aí que uma regex de aparência inocente trava por completo: não é um bug do motor, é a estrutura da regex gerando um labirinto de tamanho explosivo.

# Os padrões que explodem

O catastrophic backtracking tem assinaturas reconhecíveis. A mais clássica é um quantificador aninhado sobre algo ambíguo — (a+)+, (a*)*, (.*)* — onde o motor tem incontáveis formas de dividir o texto entre os dois níveis de repetição. Outra é a alternância com sobreposição dentro de um quantificado — (a|a)*, (\d+|\w+)*. Quando uma entrada que quase combina (mas falha no fim) atinge esses padrões, o motor explora todas as divisões possíveis antes de desistir, e o tempo explode.

exemplo.js
// ☠️ Padrão clássico de catastrophic backtracking:
const perigosa = /^(a+)+$/

perigosa.test("aaaaaaaaaaaaaaaaaaaa!")
// A entrada termina com "!" (não combina o $), forçando o motor
// a tentar TODAS as formas de dividir os "a" entre os dois +.
// Com 20 "a", são ~1 milhão de tentativas; com 30, ~1 bilhão.
// O tempo cresce EXPONENCIALMENTE com o nº de "a".

// Outras assinaturas de risco:
//   (a*)*    (.*)+    (\d+|\w+)*    (.*,)*

# Por que a entrada "quase válida" é a pior

Uma sutileza importante: o catastrophic backtracking se manifesta na sua pior forma quando a entrada quase combina mas falha no final. Se a entrada combina logo, o motor para cedo. Se falha logo, ele desiste cedo. Mas quando a entrada satisfaz quase tudo e só falha no último caractere (o ! no exemplo), o motor é forçado a esgotar todas as combinações antes de concluir o fracasso — explorando o labirinto inteiro. É por isso que o problema é tão traiçoeiro: a regex funciona perfeitamente nos testes (entradas válidas, que combinam rápido) e só explode com uma entrada específica que quase passa.

# Como evitar: reescrever os padrões

A defesa é estrutural: evitar os padrões que geram ambiguidade. Não aninhe quantificadores sobre o mesmo tipo de caractere — (a+)+ deve ser só a+. Use classes negadas em vez de .* ambíguo (Cap 11) — [^"]* em vez de .*?, eliminando o backtracking. Seja específico — quanto menos ambiguidade sobre como o texto se divide, menos caminhos o motor explora. A regra geral: se dois quantificadores podem combinar o mesmo texto de formas diferentes, há risco.

exemplo.js
// ☠️ Perigoso: quantificador aninhado e ambíguo
/^(a+)+$/

// ✅ Seguro: o mesmo significado, sem aninhamento
/^a+$/

// ☠️ Perigoso: .* ambíguo entre delimitadores repetidos
/^(.*),(.*)$/

// ✅ Seguro: classe negada elimina a ambiguidade (Cap 11)
/^([^,]*),([^,]*)$/
// [^,]* avança direto até a vírgula, sem caminhos alternativos
Motores sem backtracking existem (e não têm o problema)
Vale saber que o catastrophic backtracking é uma característica de certos motores — os baseados em backtracking, como os do JavaScript, Python, Java, PCRE. Existe outra família de motores, baseados em autômatos finitos (a teoria original da regex), que garantem tempo linear — eles nunca explodem, não importa a entrada. O grep tradicional e a engine RE2 (usada pelo Go e disponível como biblioteca) são desse tipo. O custo é que esses motores não suportam alguns recursos (backreferences, lookaround), justamente os que exigem backtracking. A consequência prática: para sistemas onde a regex processa input não confiável e a segurança importa (Cap 19), usar um motor sem backtracking (como RE2) elimina o risco de ReDoS por construção. No sabor padrão do seu ambiente, porém, a defesa é escrever regex sem os padrões ambíguos — e, idealmente, validar suas regex com uma ferramenta de análise (Cap 21) que detecta o risco antes de produção.

Capítulo 19

ReDoS regex como ataque

O catastrophic backtracking (Cap 18) é um problema de performance — mas quando a regex processa input que vem de fora, de usuários ou atacantes, ele vira uma vulnerabilidade de segurança com nome próprio: ReDoS (Regular Expression Denial of Service). Um atacante que conhece uma regex vulnerável no seu sistema pode enviar uma entrada cuidadosamente construída que faz o motor travar por segundos ou minutos — consumindo CPU, bloqueando o processo, e, num servidor de thread única como o Node (Vol VIII), derrubando a aplicação inteira com uma única requisição. Este capítulo conecta o backtracking do capítulo anterior à segurança do Vol XIII: como uma regex inocente vira vetor de ataque, como identificar regex vulneráveis no seu código, e como se defender. É o capítulo onde a regex encontra a segurança, e onde o "input não confiável é hostil" do Vol XIII se aplica a um lugar que poucos suspeitam — a expressão regular.

# De backtracking a negação de serviço

A ponte entre o Cap 18 e este: o catastrophic backtracking consome CPU proporcionalmente ao número de tentativas, que explode exponencialmente. Se a regex vulnerável processa input do usuário — um campo de formulário, um parâmetro de URL, um header HTTP —, um atacante pode fornecer a entrada "quase válida" que dispara a explosão. O resultado é um ataque de negação de serviço: o servidor gasta todo o seu tempo de CPU num único match, ficando incapaz de atender outras requisições. Uma string de algumas dezenas de caracteres pode travar o processo por minutos.

exemplo.js
// Uma regex vulnerável processando input do usuário:
function validarTag(input) {
  // regex com backtracking catastrófico (Cap 18)
  return /^(\w+\s?)*$/.test(input)
}

// Uso normal: rápido
validarTag("tag valida")        // instantâneo

// Ataque: uma entrada "quase válida" que falha no fim
validarTag("aaaaaaaaaaaaaaaaaaaaaaaa!")
// trava por segundos/minutos — UMA requisição derruba o servidor
// (Node é single-threaded: o event loop fica bloqueado, Vol VIII)
No Node, uma regex travada bloqueia tudo
O ReDoS é especialmente devastador no Node.js (Vol VIII) por causa do seu modelo de thread única. Enquanto uma regex está em catastrophic backtracking, ela ocupa a única thread que processa todas as requisições — o event loop fica bloqueado, e o servidor inteiro congela, incapaz de responder a qualquer outro usuário. Não é só a requisição maliciosa que sofre: todas as requisições ficam paradas até a regex terminar (se terminar). Isso transforma uma vulnerabilidade de uma única requisição numa queda total do serviço. É o pior cenário de negação de serviço: barato para o atacante (uma string curta, uma requisição), catastrófico para a vítima (servidor inteiro fora do ar). Por isso o ReDoS é levado a sério — ele aparece regularmente em CVEs de bibliotecas populares, onde uma regex de validação aparentemente inofensiva era explorável.

# Onde o ReDoS se esconde

O ReDoS é traiçoeiro porque se esconde em lugares comuns e de aparência benigna. Validações de formato (o tipo de regex que você escreve o tempo todo), parsing de input, bibliotecas de terceiros (você herda as vulnerabilidades das regex delas). Os pontos de risco compartilham uma característica: uma regex com potencial de backtracking (Cap 18) aplicada a dados que o atacante controla. Qualquer regex que toca input externo — direto ou através de uma biblioteca — é um candidato a auditar.

# Defesas

Há várias camadas de defesa, e a melhor combina-as (defesa em profundidade, Vol XIII, Cap 21). Escreva regex seguras: evite os padrões ambíguos do Cap 18 — essa é a defesa de raiz. Limite o tamanho do input: validar o comprimento antes da regex impede que entradas enormes alimentem a explosão. Use um motor sem backtracking (RE2, Cap 18) para regex sobre input não confiável — elimina o risco por construção. Analise suas regex com ferramentas que detectam vulnerabilidade. E prefira validadores dedicados (o z.email() do Cap 15) a regex próprias para formatos complexos.

// Defesa 1: limitar o tamanho ANTES da regex (barato e eficaz)
if (input.length > 100) return false   // corta a explosão na raiz

// Defesa 3: motor linear (RE2) para input não confiável (Cap 18)
// Defesa 4: analisar a regex com ferramentas (Cap 21)
ReDoS é o "input hostil" do Vol XIII aplicado à regex
O ReDoS é, no fundo, mais uma manifestação do princípio central de segurança do Vol XIII (Cap 21): todo input não confiável é hostil até prova em contrário. Assim como um campo de texto pode carregar SQL injection ou XSS, ele pode carregar uma entrada de ReDoS — e a defesa segue a mesma filosofia: validar (limitar tamanho), não confiar (assumir que o input quer te derrubar), e usar ferramentas robustas (validadores dedicados, motores seguros) em vez de soluções caseiras frágeis. O que torna o ReDoS insidioso é que ele se esconde numa ferramenta que parece puramente técnica e inofensiva — uma expressão regular de validação. Mas se essa regex toca input do atacante e tem backtracking, é uma porta. Internalizar que a regex faz parte da superfície de ataque — que validar input com uma regex mal construída pode ser pior que não validar — é a lição de segurança deste volume, e o ponto onde regex e o Vol XIII se encontram.

Capítulo 20

Legibilidade e manutenção

Regex tem fama de ilegível, e a fama é merecida quando ela é escrita sem cuidado: uma string de cinquenta caracteres densos que ninguém — nem quem escreveu, meses depois — consegue decifrar. Mas essa ilegibilidade não é inevitável; é uma escolha. Há técnicas que tornam uma regex compreensível e manutenível, e usá-las é parte de escrever regex profissional, não só funcional. Este capítulo reúne essas técnicas: o modo "verbose" que permite comentar e espaçar a regex, a decomposição em partes nomeadas, os grupos nomeados (Cap 9) como documentação, e — a decisão mais madura — saber quando não usar regex. É um capítulo sobre tratar a regex como código de verdade, sujeito aos mesmos cuidados de clareza que o resto da coleção exige. Uma regex que funciona mas ninguém entende é dívida técnica; uma que comunica sua intenção é um ativo.

# O problema da regex ilegível

Uma regex complexa escrita como uma única string densa é hostil à manutenção: não há onde explicar a intenção, as partes se misturam, e modificá-la com segurança exige decifrar tudo. O custo aparece depois — quando um bug surge, ou um requisito muda, e a regex precisa ser entendida. Como qualquer código críptico (toda a coleção), ela vira um ponto de medo no código, que ninguém quer tocar. A boa notícia: regex longas quase sempre podem ser tornadas legíveis, e o esforço se paga na primeira vez que alguém precisa entendê-las.

exemplo.js
// ❌ Densa e ilegível: o que isto valida?
const re = /^(?:(?:\+|00)?(\d{1,3}))?[\s.-]?\(?(\d{2,3})\)?[\s.-]?(\d{4,5})[\s.-]?(\d{4})$/

// É um telefone, mas decifrar cada parte exige esforço.
// As próximas seções mostram como tornar isto legível.

# Modo verbose: comentar e espaçar

Muitos sabores (incluindo o JavaScript com a flag x em alguns ambientes, e nativamente em Python, PCRE) oferecem um modo verbose (ou "extended"): nele, espaços em branco na regex são ignorados, e você pode adicionar comentários. Isso transforma a regex de uma linha densa numa estrutura espaçada e anotada, onde cada parte fica numa linha com uma explicação. É a forma mais direta de tornar uma regex complexa legível — quebrar e comentar, como faria com qualquer código.

exemplo.py
# Modo verbose (Python re.VERBOSE; PCRE com flag x):
# espaços são ignorados e # inicia comentário
padrao = r"""
    ^
    [A-Z]{3}      # três letras maiúsculas (prefixo)
    -             # hífen literal
    \d{4}         # quatro dígitos (número)
    $
"""
# A mesma regex, agora autoexplicativa linha a linha.
No JavaScript, decomponha em variáveis
O JavaScript não tem (até recentemente, de forma padronizada) um modo verbose tão acessível, mas há uma técnica igualmente eficaz: construir a regex a partir de partes nomeadas. Você define cada componente como uma variável ou string com nome significativo, com um comentário, e os compõe na regex final — frequentemente com new RegExp (Cap 13) ou template strings. Cada parte ganha um nome que documenta sua intenção (const ano = "\\d{4}"), e a regex montada lê-se como a soma de partes compreensíveis em vez de um bloco denso. É o mesmo princípio de decompor uma função grande em funções menores nomeadas: a clareza vem de dar nomes às partes e montá-las explicitamente. O custo é um pouco mais de código; o benefício é que cada componente é entendível isoladamente e a composição mostra a estrutura.

# Decompor em partes nomeadas

A técnica de decomposição, aplicada: em vez de uma regex monolítica, defina cada parte com um nome e componha. No JavaScript, isso usa o construtor RegExp (Cap 13) ou strings que se juntam. Cada peça vira compreensível por si, e a montagem final revela a estrutura. É especialmente valioso quando partes se repetem ou quando a regex é longa.

exemplo.js
// Decompor a regex de telefone em partes nomeadas e legíveis:
const ddd    = "\\(?(\\d{2})\\)?"       // DDD, parênteses opcionais
const sep    = "[\\s.-]?"             // separador opcional
const numero = "(\\d{4,5})" + sep + "(\\d{4})"  // número

const telefone = new RegExp(`^${ddd}${sep}${numero}$`)
// Cada parte é compreensível; a montagem mostra a estrutura.

# Grupos nomeados como documentação

Os grupos nomeados (Cap 9) são, além de uma conveniência de acesso, uma forma de documentação embutida. Uma regex com (?<ano>\d{4}) diz, no próprio padrão, que aquela parte é o ano — quem lê a regex entende a intenção sem comentário externo. Combinados com a decomposição, eles tornam a regex e o código que a consome legíveis: o padrão se documenta, e o acesso (m.groups.ano) é claro. Usá-los em qualquer regex que extrai múltiplas partes é uma das melhores práticas de legibilidade.

A decisão mais madura: não usar regex
A técnica de legibilidade mais valiosa é, às vezes, abandonar a regex. Quando um padrão fica tão complexo que nem comentários e decomposição o tornam claro — ou quando você está combatendo os limites da regex (estruturas aninhadas, Cap 8; semântica, Cap 15) —, o problema não é como escrever a regex, é que regex é a ferramenta errada. Um parser dedicado, uma biblioteca especializada, ou código de processamento explícito serão mais legíveis, mais corretos e mais seguros (sem risco de ReDoS, Cap 19). O sinal: se você precisa de uma regex de cinquenta caracteres com comentários extensos para validar algo, pergunte se um validador dedicado (o z.email() do Cap 15) ou algumas linhas de código não fariam melhor. A maturidade com regex não é escrever as mais impressionantes — é saber quando uma regex simples basta, quando uma complexa precisa de cuidado de legibilidade, e quando nenhuma regex é a resposta certa. O Cap 22 fecha o volume com essa sabedoria.

Ferramentas e depuração

Escrever regex na cabeça e torcer para funcionar é a receita da frustração — e desnecessário, porque há ferramentas excelentes que tornam o processo visual, interativo e seguro. Um bom depurador de regex mostra exatamente o que cada parte do padrão faz, destaca as correspondências numa amostra de texto, explica o padrão em linguagem natural, e até alerta sobre problemas de performance (Cap 18). Este capítulo apresenta o ecossistema de ferramentas que transforma regex de adivinhação em engenharia: os testadores online, a análise de vulnerabilidade, e o fluxo de trabalho de construir uma regex incrementalmente e testá-la contra casos reais. É um capítulo prático e curto, mas que muda a relação com a regex — de "espero que funcione" para "vejo que funciona", testando contra exemplos válidos e inválidos antes de confiar a expressão ao código de produção.

# Testadores visuais: regex101 e similares

A ferramenta mais valiosa é um testador visual de regex — sites como o regex101.com são o padrão. Você cola o padrão, cola um texto de amostra, e vê em tempo real o que combina (destacado), o que cada grupo capturou, e — crucialmente — uma explicação de cada parte do padrão em linguagem natural. Você escolhe o sabor (Cap 17) para testar exatamente no contexto-alvo. É um ambiente de experimentação onde você constrói a regex vendo o efeito de cada mudança, em vez de adivinhar.

o que um testador visual oferece

A explicação em linguagem natural é a melhor professora
O recurso mais subestimado dos bons testadores é a explicação do padrão. Cole uma regex que você não entende — uma que herdou no código, ou um exemplo de um tutorial — e a ferramenta a traduz em linguagem natural, parte por parte: "início da string, depois três dígitos, depois um hífen literal...". Isso é tanto uma ferramenta de aprendizado quanto de depuração: você entende regex alheias decifrando-as ali, e confirma que a sua faz o que pretende. Quando uma regex não combina o que você espera, a explicação revela o porquê — frequentemente um metacaractere que você esqueceu de escapar, ou um quantificador ganancioso pegando demais (Cap 11). Pegar o hábito de colar regex no testador para lê-las, não só testá-las, acelera enormemente o aprendizado e a depuração. É como ter um intérprete que traduz a linguagem densa da regex para algo que você lê de imediato.

# O fluxo de construção incremental

A regex, como os pipelines do shell (Vol XVI, Cap 10), se constrói melhor incrementalmente. Comece com a parte mais simples, teste-a contra a amostra, adicione o próximo elemento, teste de novo. Em vez de escrever a regex inteira e debugar o conjunto, você valida cada acréscimo. Esse método torna padrões complexos tratáveis: cada passo é uma adição pequena e verificável, e quando algo quebra, você sabe exatamente o que mudou.

construção incremental
# Construir um padrão de data passo a passo, testando cada etapa:
\d{2}                  # 1. o dia — confere?
\d{2}/\d{2}            # 2. + mês (esqueça o escape do / por ora)
\d{2}/\d{2}/\d{4}      # 3. + ano
^\d{2}/\d{2}/\d{4}$    # 4. ancorar para validação (Cap 5)
# Cada etapa testada na amostra antes da próxima.

# Testar contra casos válidos E inválidos

Uma regex de validação só está pronta quando você a testou contra ambos: entradas que devem combinar (para garantir que não rejeita o válido) e entradas que não devem (para garantir que não aceita o inválido). É o mesmo princípio de testes (toda a coleção): casos positivos e negativos. Uma regex testada só com entradas válidas pode estar aceitando lixo silenciosamente — o teste com casos inválidos é o que pega o excesso de permissividade (a falta de âncoras do Cap 5, o ponto solto do Cap 2).

exemplo.js
// Teste a regex contra os DOIS conjuntos:
const cep = /^\d{5}-?\d{3}$/

// Devem PASSAR (válidos):
["12345-678", "12345678"].every(s => cep.test(s))   // true

// Devem FALHAR (inválidos) — tão importante quanto:
["1234-678", "abcde-fgh", "x12345-678"].some(s => cep.test(s))
// false (nenhum inválido passa — a regex rejeita corretamente)

# Análise de segurança e performance

Conectando aos Caps 18-19: algumas ferramentas analisam a regex em busca de vulnerabilidade a ReDoS, detectando os padrões de backtracking catastrófico antes que cheguem à produção. Linters de código (como plugins do ESLint para regex) e analisadores dedicados sinalizam regex perigosas. Para regex que processam input não confiável, passar por essa análise é parte da diligência de segurança — o equivalente do shellcheck (Vol XVI, Cap 21) ou do scan de CVEs (Vol XV, Cap 17) para o mundo da regex.

Integre a verificação ao fluxo, como nos outros volumes
A lição que ecoa toda a coleção: a verificação automática deve fazer parte do fluxo, não ser um passo manual esquecível. Assim como o TypeScript checa tipos, o ESLint checa código, o shellcheck (Vol XVI) checa scripts e o scan de CVEs (Vol XV) checa imagens, há linters que checam regex — detectando vulnerabilidade a ReDoS e padrões problemáticos. Integrá-los ao CI (Vol XIV, Cap 19) ou a um hook de pre-commit (Vol XIV, Cap 20) faz a verificação acontecer automaticamente, pegando regex perigosas antes que entrem em produção. E o testador visual, embora manual, deve ser um reflexo: antes de colar uma regex no código, teste-a contra casos válidos e inválidos, confira a explicação, veja o aviso de performance. Esse hábito — não confiar numa regex que você não viu funcionar — é o que separa regex de produção confiável de uma bomba esperando a entrada certa. A regex é código; mereça-a o mesmo rigor de verificação que o resto.

# O princípio que organiza a regex

Se cada volume teve seu princípio organizador — "objetos imutáveis" no Git, "imagem imutável" no Docker, "expandir antes de executar" no shell —, a regex tem o seu: ela descreve padrões regulares, e brilha quando o problema é regular. Padrões locais, repetitivos, com estrutura previsível — formatos, validações, buscas, extrações, substituições — são o seu domínio, e ali ela é insuperável em concisão. O contraponto é igualmente importante: estruturas aninhadas (HTML, JSON, código) e semântica (existência, validade no mundo) estão fora do seu alcance, não por falta de esforço, mas por natureza. Toda boa decisão sobre regex deriva de reconhecer de que lado dessa fronteira o seu problema está.

A pergunta que resolve quase tudo
Diante de uma tarefa, antes de escrever a regex, pergunte: este é um padrão regular? Se o que você quer é reconhecer um formato local e repetitivo — "três dígitos, hífen, quatro dígitos", "qualquer coisa entre aspas", "a palavra X seguida de Y" —, a regex é a ferramenta certa, e os Caps 1-12 dão a sintaxe. Se você está tentando processar estrutura aninhada de profundidade arbitrária, ou validar significado em vez de forma, a regex é a ferramenta errada (Caps 8, 15), e um parser ou código comum servirá melhor. E quando usar regex, a segunda pergunta: ela toca input não confiável? Se sim, a segurança (ReDoS, Cap 19) e a robustez entram em cena. Essas duas perguntas — "é regular?" e "o input é confiável?" — guiam quase toda decisão sobre regex.

# A disciplina que atravessa o volume

Alguns hábitos apareceram repetidamente porque são os que mais importam. Ancore para validar — ^ e $ em toda validação (Caps 5, 15): a ausência é o erro nº 1, transformando validação em ilusão. Seja específico — classes precisas em vez do . permissivo (Caps 2, 3): a precisão rejeita o que deve rejeitar. Cuide da segurança — evite backtracking catastrófico, limite o tamanho do input (Caps 18-19): a regex é superfície de ataque. Trate como código — torne-a legível, teste-a, conheça seus limites (Caps 20-21): regex é código, não um feitiço.

os hábitos essenciais
// 1. Validação SEMPRE ancora (Caps 5, 15)
/^\d{4}$/          // não /\d{4}/

// 2. Específico, não permissivo (Caps 2, 3)
/[A-Z]{2}/         // não /../

// 3. Sem backtracking catastrófico sobre input hostil (Caps 18-19)
/^[^,]+,[^,]+$/    // não /^(.+)+,(.+)$/

// 4. Legível e testada (Caps 20-21)
//    grupos nomeados, decomposição, casos válidos E inválidos

# Saber quando não usar regex

A competência mais madura com regex, repetida ao longo do volume porque é a mais valiosa, é saber não usá-la. Não faça parsing de HTML, XML ou JSON com regex — use um parser (Cap 8). Não valide e-mail com regex própria — use um validador dedicado (Cap 15). Não force semântica em padrões — deixe para o código. Não escreva uma regex de cinquenta caracteres ilegível quando algumas linhas seriam mais claras (Cap 20). A regex é uma ferramenta afiada para uma classe específica de problemas; reconhecer quando você saiu dessa classe é o que separa o uso experiente do uso ingênuo. O poder está em saber onde ela brilha — e onde recuar.
