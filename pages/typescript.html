Capítulo 01

Introdução ao TypeScript

TypeScript é um superconjunto tipado de JavaScript, desenvolvido pela Microsoft. Tudo o que é JavaScript válido é também TypeScript válido — a linguagem adiciona, sobre isso, um sistema de tipos estático opcional que é apagado na compilação, resultando em JavaScript puro que roda em qualquer lugar.

# Por que usar TypeScript?

JavaScript é uma linguagem dinâmica: o mesmo identificador pode conter um número agora e uma função mais tarde. Isso é flexível, mas custa caro em bugs silenciosos e refatorações arriscadas. TypeScript trabalha em tempo de desenvolvimento para:

  • Detectar erros antes do código rodar, não durante uma chamada em produção.
  • Oferecer autocomplete e navegação confiáveis no editor.
  • Documentar contratos entre funções, módulos e equipes.
  • Facilitar refatorações em bases de código grandes.
exemplo.ts
// JavaScript aceita silenciosamente:
function somar(a, b) { return a + b; }
somar("5", 10); // "510" em runtime, sem aviso.

// TypeScript bloqueia o erro antes da execução:
function somarTS(a: number, b: number): number {
  return a + b;
}
somarTS("5", 10); // ❌ Erro: 'string' não é atribuível a 'number'.

# Instalação e setup

TypeScript é distribuído como um pacote npm. A instalação global é útil para experimentos, mas em projetos reais prefira adicionar como dependência de desenvolvimento.

terminal
# Instalação global (opcional)
npm install -g typescript

# Em um projeto novo:
npm init -y
npm install --save-dev typescript @types/node

# Gerar o arquivo de configuração:
npx tsc --init

# Compilar um arquivo:
npx tsc arquivo.ts

# Compilar todo o projeto em modo watch:
npx tsc --watch

Para executar arquivos .ts diretamente, sem gerar .js, existem runners como tsx, ts-node ou o próprio Bun e Deno, que entendem TypeScript nativamente.

terminal
npm install --save-dev tsx
npx tsx arquivo.ts     # Executa direto, sem passo de build

# Ou com Bun (suporte nativo, muito rápido):
bun run arquivo.ts

# Seu primeiro programa

Crie um arquivo ola.ts e experimente a experiência de tipos desde a primeira linha:

ola.ts
interface Pessoa {
  nome: string;
  idade: number;
}

function saudar(p: Pessoa): string {
  return `Olá, ${p.nome}! Você tem ${p.idade} anos.`;
}

const maria: Pessoa = { nome: "Maria", idade: 28 };
console.log(saudar(maria));
Observação
O compilador (tsc) gera JavaScript a partir de TypeScript — ele não verifica tipos em tempo de execução. Toda a tipagem acontece no editor e na hora do build.

# O arquivo tsconfig.json

O tsconfig.json é o coração de um projeto TypeScript. Ele diz ao compilador quais arquivos incluir, qual versão do JavaScript gerar, e quão rigoroso ele deve ser. Um tsconfig moderno e sensato tem mais ou menos esta cara:

tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",               // versão do JS gerado
    "module": "NodeNext",             // sistema de módulos
    "moduleResolution": "NodeNext",
    "lib": ["ES2022", "DOM"],         // APIs disponíveis
    "outDir": "./dist",               // pasta de saída
    "rootDir": "./src",               // pasta de entrada

    "strict": true,                   // ativa todas checagens rigorosas
    "noImplicitAny": true,            // proíbe 'any' implícito
    "strictNullChecks": true,         // null/undefined são explícitos
    "noUncheckedIndexedAccess": true, // arr[i] pode ser undefined
    "exactOptionalPropertyTypes": true,

    "esModuleInterop": true,          // compatibilidade CommonJS/ESM
    "forceConsistentCasingInFileNames": true,
    "skipLibCheck": true,
    "resolveJsonModule": true,
    "declaration": true,              // gera .d.ts junto com .js
    "sourceMap": true                 // facilita debug
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
Dica
Sempre comece com "strict": true. Lutar contra ele depois é muito mais doloroso do que escrever código correto desde o início.
Capítulo 02

Strict mode e configuração

O Capítulo 1 instalou o TypeScript e tocou no tsconfig.json. Mas há uma decisão de configuração que importa mais que todas as outras juntas, e que separa um TypeScript que de fato protege de um que só decora o código: o strict mode. Sem ele, o compilador deixa passar a maior parte dos erros que justificam usar TypeScript — variáveis possivelmente null, parâmetros com any implícito, atribuições inseguras. Este capítulo trata o tsconfig.json a sério: o que o strict realmente ativa, as flags que mais importam, como o compilador resolve módulos, e por que começar todo projeto com a configuração mais rígida possível é o caminho para colher o valor real da linguagem.

# A flag que define tudo: strict

O "strict": true no tsconfig.json não é uma opção entre muitas — é a opção. Ela é um atalho que liga um conjunto de verificações rigorosas de uma vez, e cada uma fecha uma classe de bug que, desligada, o TypeScript ignora silenciosamente. Sem strict, o compilador aceita código que parece tipado mas não é checado de verdade, dando uma falsa sensação de segurança. Com ele, o TypeScript cumpre a promessa: pegar erros antes da execução.

tsconfig.json
{
  "compilerOptions": {
    "strict": true,            // liga TODAS as checagens rígidas de uma vez
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler"
  }
}

// "strict": true é equivalente a ligar individualmente:
//   strictNullChecks, noImplicitAny, strictFunctionTypes,
//   strictBindCallApply, strictPropertyInitialization,
//   noImplicitThis, useUnknownInCatchVariables, alwaysStrict

# strictNullChecks: o bilhão de dólares

A checagem mais importante que o strict ativa é strictNullChecks. Sem ela, null e undefined são atribuíveis a qualquer tipo — um string pode secretamente ser null, e o compilador não avisa. Com ela, null e undefined são tipos próprios, e você é obrigado a lidar com a possibilidade de um valor estar ausente antes de usá-lo. É a checagem que elimina o erro mais comum da programação — o acesso a algo que não existe.

strict-null.ts
function primeiraLetra(texto: string): string {
  return texto[0].toUpperCase()
}

// SEM strictNullChecks: compila, mas quebra em runtime se vier null
// COM strictNullChecks: o tipo abaixo exige tratamento explícito
function buscar(id: number): string | undefined {
  return id === 1 ? "Ana" : undefined
}

const nome = buscar(2)
nome.toUpperCase()      // ❌ Erro: 'nome' é possivelmente 'undefined'

if (nome !== undefined) {
  nome.toUpperCase()    // ✅ ok — o narrowing (Cap 5) provou que existe
}
Sem strictNullChecks, o TypeScript mente
A "invenção do bilhão de dólares" — o null reference — é o erro que mais custou à indústria. Sem strictNullChecks, o TypeScript reproduz exatamente esse problema: um valor tipado como string pode ser null em runtime, e o compilador garante que está tudo bem quando não está. É a configuração que, sozinha, justifica migrar para TypeScript — e desligá-la (ou não ligar o strict) joga fora a maior parte do valor da linguagem. Todo projeto novo deve nascer com strict: true; projetos legados devem migrar gradualmente para ele.

# noImplicitAny: sem buracos silenciosos

Outra checagem central do strict é noImplicitAny. Quando o TypeScript não consegue inferir o tipo de algo (um parâmetro de função sem anotação, por exemplo), ele tem duas opções: assumir any em silêncio (desligando a checagem para aquele valor) ou apontar um erro exigindo que você o tipe. O noImplicitAny escolhe a segunda. Sem ele, parâmetros não anotados viram any e propagam a ausência de checagem pelo código; com ele, você é forçado a ser explícito onde a inferência não alcança.

implicit-any.ts
// SEM noImplicitAny: 'item' vira 'any' silenciosamente
function processar(item) {        // ❌ com a flag: erro, 'item' tem any implícito
  return item.qualquerCoisa()     // any desliga toda a checagem aqui
}

// COM noImplicitAny: você anota e o compilador checa
function processarTS(item: { nome: string }) {
  return item.nome.toUpperCase()  // ✅ checado de verdade
}

# Flags além do strict

O strict é a base, mas há flags adicionais que valem ligar em projetos sérios. Elas pegam casos que o strict não cobre — índices de array possivelmente indefinidos, variáveis não usadas, retornos faltando. Cada uma fecha mais uma fresta. As mais valiosas estão abaixo.

tsconfig.json
{
  "compilerOptions": {
    "strict": true,

    // arr[i] passa a ser 'T | undefined' — força checar o índice
    "noUncheckedIndexedAccess": true,

    // erro em variáveis e parâmetros declarados mas não usados
    "noUnusedLocals": true,
    "noUnusedParameters": true,

    // erro se um caminho da função não retorna valor
    "noImplicitReturns": true,

    // exige 'override' ao sobrescrever métodos (Cap 6)
    "noImplicitOverride": true
  }
}
noUncheckedIndexedAccess: a flag esquecida que mais protege
Curiosamente, uma das checagens mais úteis não está incluída no strict: noUncheckedIndexedAccess. Por padrão, o TypeScript assume que array[i] sempre existe e tem o tipo dos elementos — mas isso é mentira, pois i pode estar fora dos limites, e obj[chave] pode não existir. Com a flag, todo acesso por índice retorna T | undefined, forçando você a checar antes de usar — fechando uma classe inteira de erros de "undefined is not a function". É uma das primeiras flags a ligar depois do strict, e a que mais surpreende quem não a conhece.

# Como o compilador acha os módulos

Uma fonte comum de confusão é a resolução de módulos — como o TypeScript transforma um import "./algo" num arquivo real. As opções module e moduleResolution controlam isso, e a escolha certa depende do ambiente. Para projetos modernos com bundlers (Vite, esbuild) ou runtimes modernos, "moduleResolution": "Bundler" é a escolha atual; para Node puro, "NodeNext". Acertar isso evita os erros enigmáticos de "cannot find module" que não têm a ver com o código, e sim com a configuração.

tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",            // qual versão de JS gerar
    "module": "ESNext",            // sintaxe de módulo na saída
    "moduleResolution": "Bundler", // como resolver imports (projetos modernos)
    "esModuleInterop": true,       // interop suave entre ESM e CommonJS (Vol VIII)
    "skipLibCheck": true,          // não rechecar os .d.ts das dependências (mais rápido)
    "verbatimModuleSyntax": true   // import type explícito (Cap sobre módulos)
  }
}
// Para Node puro (sem bundler): use "moduleResolution": "NodeNext"
Comece rígido, relaxe só com motivo
A estratégia certa para a configuração é o oposto da intuição: comece com o máximo de rigor (strict mais as flags extras) e só desligue uma checagem se houver um motivo concreto e documentado. É muito mais fácil afrouxar uma regra pontualmente do que apertar depois — um projeto que cresceu sem strictNullChecks acumula milhares de erros ao tentar ligá-la. Os presets da comunidade (como os @tsconfig/strictest) embalam essas escolhas rígidas e são um bom ponto de partida. Rigor de configuração é dívida que você não paga depois.

Capítulo 03

Os tipos básicos

TypeScript herda de JavaScript todos os tipos primitivos e adiciona alguns próprios, nascidos da necessidade de descrever situações que o JavaScript não trata. Este capítulo é o vocabulário fundamental da linguagem.

# Primitivos: string, number, boolean

Os três tipos primitivos principais são praticamente os mesmos de JavaScript, agora com rótulos explícitos.

primitivos.ts
let nome: string = "Ana";
let idade: number = 30;
let ativo: boolean = true;

// Template literals funcionam normalmente:
let apresentacao: string = `${nome} tem ${idade} anos`;

// number cobre inteiros, decimais, hex, binário, octal:
let hex: number = 0xff;
let bin: number = 0b1010;
let dec: number = 3.14;

// Além destes, TypeScript também tem:
let grande: bigint = 9007199254740991n;
let id: symbol = Symbol("id");

# Arrays e Tuplas

Arrays têm duas notações equivalentes. A tupla (tuple) é uma invenção do TypeScript: um array de tamanho e tipos fixos por posição.

arrays-tuplas.ts
// Duas formas de declarar arrays:
let numeros: number[] = [1, 2, 3];
let nomes: Array<string> = ["Ana", "Bruno"];

// Array com tipos variados (union):
let mistos: (string | number)[] = ["a", 1, "b", 2];

// TUPLA — ordem e tipo fixos:
let coord: [number, number] = [10, 20];
let registro: [string, number, boolean] = ["item", 10, true];

// Tupla com elementos opcionais (?):
let ponto: [number, number, number?] = [1, 2];

// Tupla com rest (...) — útil para padrões variádicos:
let eventos: [string, ...number[]] = ["click", 10, 20, 30];

// Tupla readonly — imutável:
let rgb: readonly [number, number, number] = [255, 0, 0];
// rgb[0] = 100; // ❌ Erro

# Objetos

Objetos são descritos pelo formato dos seus campos. O TypeScript chama isso de tipagem estrutural: o que importa é o formato, não o nome.

objetos.ts
// Tipo inline em um parâmetro:
function imprimirPonto(p: { x: number; y: number }): void {
  console.log(`(${p.x}, ${p.y})`);
}

// Propriedades opcionais usam '?':
function criarUsuario(info: { nome: string; email?: string }) {
  console.log(info.nome);
  if (info.email) console.log(info.email);
}

// Objeto com campos readonly:
let config: { readonly versao: string; porta: number } = {
  versao: "1.0",
  porta: 8080,
};
// config.versao = "2.0"; // ❌ readonly

# any, unknown, never, void

Estes são os quatro tipos "especiais" de TypeScript. Entender a diferença entre eles é um dos pontos de virada no aprendizado da linguagem.

TipoSignificadoQuando usar
any"Não checar nada"Fuga de emergência. Evite sempre que possível.
unknown"Algo, mas não sei o quê"Valores externos (JSON, API) que você vai validar.
never"Nunca acontece"Funções que lançam erro ou fazem loop infinito.
void"Sem valor de retorno útil"Funções que não retornam nada significativo.
especiais.ts
// ANY — desliga o type checker. Cuidado!
let qualquerCoisa: any = 4;
qualquerCoisa = "texto";
qualquerCoisa.foo.bar; // passa, mas quebra em runtime.

// UNKNOWN — obriga você a verificar antes de usar:
let valor: unknown = JSON.parse('{"x": 1}');
// valor.x; // ❌ Erro: valor é unknown
if (typeof valor === "object" && valor !== null && "x" in valor) {
  console.log(valor.x); // ✅ ok aqui dentro
}

// NEVER — um valor que nunca existe:
function erroFatal(msg: string): never {
  throw new Error(msg);
}
function loopInfinito(): never {
  while (true) {}
}

// VOID — função sem retorno significativo:
function log(msg: string): void {
  console.log(msg);
  // não precisa de 'return'
}
Atenção
Usar any é como remover a tipagem. Se a intenção é "valor desconhecido que vou validar", use unknown. Se a intenção é "qualquer tipo genérico", use generics. any quase sempre é um cheiro de código.

# null e undefined

Com strictNullChecks ativo (o padrão em projetos modernos), null e undefined são tipos distintos e precisam ser tratados explicitamente.

null-undefined.ts
let a: string = null;       // ❌ em strict mode
let b: string | null = null; // ✅

function buscarUsuario(id: number): string | undefined {
  if (id < 0) return undefined;
  return "Ana";
}

const nome = buscarUsuario(1);
// nome.toUpperCase(); // ❌ possivelmente undefined

// Encadeamento opcional (?.) — retorna undefined se null/undefined:
console.log(nome?.toUpperCase());

// Coalescência nula (??) — só usa o fallback em null/undefined:
const tamanho = nome?.length ?? 0;

// Non-null assertion (!) — você jura que não é null:
const nomeCerto = buscarUsuario(1)!;
console.log(nomeCerto.toUpperCase()); // use com cuidado!

# Inferência de tipos

TypeScript é inteligente. Na maior parte do tempo, você não precisa escrever tipos — ele descobre sozinho a partir do valor. O segredo do código TypeScript limpo é escrever tipos só onde acrescentam informação.

inferencia.ts
let total = 10;           // inferido como number
let nome = "Ana";         // inferido como string
let ativos = [1, 2, 3];   // inferido como number[]

// Em const, o tipo é ainda mais estreito (literal):
const cor = "vermelho";   // tipo: "vermelho" (não string)

// Em funções, o retorno é inferido a partir do corpo:
function dobrar(n: number) {
  return n * 2; // TS sabe que retorna number
}

// Em objetos literais o TS também infere:
const pessoa = { nome: "Ana", idade: 30 };
// tipo: { nome: string; idade: number }

# Type assertions: as e satisfies

Às vezes você sabe mais que o compilador. as diz "confie em mim", enquanto satisfies (TypeScript 4.9+) é uma checagem sem mudar o tipo inferido. São ferramentas diferentes para problemas diferentes.

assertions.ts
// AS — afirma um tipo ao compilador:
const elemento = document.getElementById("app") as HTMLInputElement;
elemento.value = "oi"; // acessa propriedade de input

// Dupla asserção (use em último caso):
const x = "123" as unknown as number;

// SATISFIES — valida sem apagar o tipo inferido:
type Cor = "red" | "green" | "blue";

const paleta = {
  primaria: "red",
  secundaria: "blue",
} satisfies Record<string, Cor>;

// paleta.primaria ainda é "red" literal, não 'Cor'.
// E o TS validou que os valores são Cor válidas.

// Compare com 'as', que perderia a inferência:
const paleta2 = {
  primaria: "red",
  secundaria: "blue",
} as Record<string, Cor>;
// aqui paleta2.primaria é Cor, não "red".
Use satisfies
Sempre que você quiser validar que um objeto tem certo formato, mas sem perder a precisão dos tipos literais que o TypeScript infere, prefira satisfies em vez de as.

# Literal types

Você pode usar valores literais como tipos. Isso é a base dos discriminated unions e de muitos padrões avançados.

literal.ts
// Literal types em união formam um "enum leve":
type Alinhamento = "left" | "center" | "right";

function alinhar(texto: string, como: Alinhamento) { /* ... */ }
alinhar("oi", "center"); // ✅
alinhar("oi", "centro"); // ❌ Erro: "centro" não existe

// Também funciona com números e booleanos:
type Dado = 1 | 2 | 3 | 4 | 5 | 6;
type Bit = 0 | 1;

// 'as const' congela literais em um objeto:
const config = {
  modo: "dark",
  versao: 1,
} as const;
// config.modo é "dark", não string
// config agora é readonly

# Enums

Enums são conjuntos nomeados de constantes. TypeScript oferece numeric enums, string enums e const enums. A comunidade moderna tem preferido unions de literais, mas enums ainda aparecem muito em código legado e em APIs de bibliotecas.

enums.ts
// Enum numérico (valores começam em 0 por padrão):
enum Direcao {
  Norte,       // 0
  Leste,       // 1
  Sul,         // 2
  Oeste,       // 3
}

// Você pode customizar:
enum Status {
  Ativo = 1,
  Inativo = 2,
  Banido = 99,
}

// String enum (mais seguro — sem mágica numérica):
enum Cor {
  Vermelho = "RED",
  Verde = "GREEN",
  Azul = "BLUE",
}

// const enum — apagado no build, vira valor literal:
const enum Tamanho { Pequeno = "S", Medio = "M", Grande = "G" }
const t = Tamanho.Medio; // vira "M" no JS final

// Alternativa moderna recomendada — union type:
type StatusModerno = "ativo" | "inativo" | "banido";
Prefira unions
Em código novo, unions de literais ("a" | "b") costumam ser mais previsíveis, mais fáceis de usar com JSON e não deixam artefatos no bundle final. Reserve enum para quando for realmente necessário ou para compatibilidade.
Capítulo 04

Funções tipadas

Funções são cidadãs de primeira classe em JavaScript. Em TypeScript, isso significa que elas têm tipos ricos: parâmetros tipados, retornos tipados, parâmetros opcionais, sobrecargas e até a assinatura do this.

# Assinatura básica

funcoes.ts
// Declaração de função com tipos:
function somar(a: number, b: number): number {
  return a + b;
}

// Arrow function:
const multiplicar = (a: number, b: number): number => a * b;

// Função como valor tipado:
const dividir: (a: number, b: number) => number = (a, b) => a / b;

// Usando um type alias para a assinatura:
type Operacao = (a: number, b: number) => number;
const subtrair: Operacao = (a, b) => a - b;

// Void em retornos — não precisa de return:
function logar(msg: string): void {
  console.log(msg);
}

# Parâmetros opcionais, padrão e rest

params.ts
// Opcional — '?' após o nome:
function saudar(nome: string, titulo?: string): string {
  return titulo ? `${titulo} ${nome}` : nome;
}
saudar("Ana");            // ✅
saudar("Ana", "Dra.");    // ✅

// Padrão — atribui um valor se nada for passado:
function criarConfig(host: string, porta: number = 8080) {
  return `${host}:${porta}`;
}

// Rest — coleta argumentos em um array:
function somarTudo(...numeros: number[]): number {
  return numeros.reduce((acc, n) => acc + n, 0);
}
somarTudo(1, 2, 3, 4);

// Destructuring tipado:
function perfil({ nome, idade }: { nome: string; idade: number }) {
  return `${nome} (${idade})`;
}

# Function overloads

Sobrecarga permite descrever múltiplas formas de chamar a mesma função. Você escreve várias assinaturas seguidas da implementação, que precisa cobrir todos os casos.

// Implementação (não visível externamente):
function pesquisar(query: number | string | boolean): string | number | string[] {
  if (typeof query === "number") return "usuario-" + query;
  if (typeof query === "string") return query.length;
  return [];
}

# Narrowing e Type Guards

O TypeScript observa o fluxo do seu código e, a cada verificação, estreita (narrow) o tipo automaticamente. Conhecer as formas de guard é essencial.

narrowing.ts
// 1) typeof — para primitivos:
function imprimir(v: string | number) {
  if (typeof v === "string") {
    console.log(v.toUpperCase()); // v é string aqui
  } else {
    console.log(v.toFixed(2));    // v é number aqui
  }
}

// 2) instanceof — para classes:
function lidar(e: Error | string) {
  if (e instanceof Error) {
    console.log(e.stack);
  } else {
    console.log(e);
  }
}

// 3) in — testa a presença de propriedade:
type Carro = { rodas: number };
type Barco = { remos: number };

function mover(v: Carro | Barco) {
  if ("rodas" in v) {
    console.log(v.rodas);  // v é Carro
  } else {
    console.log(v.remos);  // v é Barco
  }
}

// 4) Comparação com literal:
function estado(s: "loading" | "ok" | "erro") {
  if (s === "loading") { /* s é "loading" */ }
}

// 5) Truthiness narrowing:
function tamanho(x: string | null) {
  if (x) {
    return x.length; // x é string aqui
  }
  return 0;
}

// 6) User-defined type guard (predicate):
function ehString(v: unknown): v is string {
  return typeof v === "string";
}

function usar(v: unknown) {
  if (ehString(v)) {
    console.log(v.trim()); // v é string
  }
}

// 7) Assertion function:
function garantirString(v: unknown): asserts v is string {
  if (typeof v !== "string") throw new Error("não é string");
}

function process(v: unknown) {
  garantirString(v);
  console.log(v.toUpperCase()); // v é string após a asserção
}

# Discriminated Unions

O padrão mais poderoso do sistema de tipos TypeScript. Cada variante da união carrega uma propriedade literal única (a "tag"), e o compilador usa essa tag para distinguir os casos.

discriminated.ts
type Requisicao =
  | { status: "loading" }
  | { status: "ok"; dados: string[] }
  | { status: "erro"; mensagem: string };

function renderizar(req: Requisicao) {
  switch (req.status) {
    case "loading":
      return "Carregando...";
    case "ok":
      return `${req.dados.length} itens`; // dados existe aqui
    case "erro":
      return `Falha: ${req.mensagem}`;   // mensagem existe aqui
  }
}

// Exaustividade com 'never' — garante que todos os casos foram tratados:
function renderizarCompleto(req: Requisicao): string {
  switch (req.status) {
    case "loading": return "...";
    case "ok":      return "ok";
    case "erro":    return "erro";
    default:
      const _exhaustive: never = req; // erro se faltar caso
      return _exhaustive;
  }
}
O padrão da discriminated union
Sempre que você tiver "um valor que pode ter formatos diferentes", pense em discriminated union com uma tag literal. É a forma idiomática de representar estados, resultados de API e eventos em TypeScript.
Capítulo 07

Narrowing avançado

O capítulo de Unions introduziu o narrowing — como o TypeScript estreita um tipo amplo (string | number) para um específico conforme você o testa. Aquilo cobriu o básico: typeof, instanceof, checagem de igualdade. Mas o narrowing tem ferramentas mais poderosas que permitem ensinar ao compilador coisas que ele não inferiria sozinho — funções que afirmam um tipo, predicados customizados que descrevem checagens complexas, e a checagem de exaustividade que garante que você tratou todos os casos. Este capítulo aprofunda o narrowing, e é onde o TypeScript deixa de ser um verificador passivo para virar uma ferramenta que você programa para entender a lógica do seu domínio. Dominar isto é a diferença entre lutar contra o compilador e fazê-lo trabalhar a seu favor.

# Type predicates: ensinando o narrowing

Às vezes a checagem que distingue um tipo de outro é complexa demais para o compilador inferir — está dentro de uma função. Um type predicate resolve isso: uma função cujo tipo de retorno é parametro is Tipo, que diz ao compilador "se esta função retornar true, então o argumento é deste tipo". Você encapsula a lógica de checagem numa função, e o TypeScript passa a confiar nela para estreitar o tipo onde ela for usada.

predicates.ts
type Gato = { tipo: "gato"; miar: () => void }
type Cao = { tipo: "cao"; latir: () => void }
type Animal = Gato | Cao

// Type predicate: o retorno "animal is Gato" ensina o narrowing
function ehGato(animal: Animal): animal is Gato {
  return animal.tipo === "gato"
}

function interagir(animal: Animal) {
  if (ehGato(animal)) {
    animal.miar()    // ✅ aqui o tipo é Gato (o predicate provou)
  } else {
    animal.latir()   // ✅ aqui é Cao (por eliminação)
  }
}
O compilador confia no predicate — então acerte a lógica
O type predicate é uma promessa que você faz ao compilador, e ele a aceita sem verificar. Se a sua função ehGato retornar true para algo que não é um Gato, o TypeScript vai tratar aquele valor como Gato mesmo assim — e o erro só aparece em runtime, justamente o que o TypeScript deveria prevenir. Por isso a lógica dentro de um predicate precisa estar correta de verdade: você está desligando a checagem do compilador e assumindo a responsabilidade. Use predicates para encapsular checagens genuínas (verificar uma propriedade discriminante, validar a forma de um objeto), não para mentir sobre tipos. É poder com responsabilidade.

# Assertion functions: asserts

Um parente do type predicate é a assertion function — uma função que, em vez de retornar um booleano, lança um erro se a condição não for satisfeita. Seu tipo de retorno usa a palavra asserts: asserts x is Tipo. Depois de chamar a função, o compilador sabe que, se a execução continuou, o valor é daquele tipo (porque, caso contrário, a função teria lançado). É o padrão por trás de funções como assert e de validações que abortam em caso de dados inválidos — conectando à validação do Zod (Vol XII).

asserts.ts
// "asserts valor is string" — se a função retornar (não lançar),
// o compilador passa a tratar 'valor' como string dali em diante.
function assertString(valor: unknown): asserts valor is string {
  if (typeof valor !== "string") {
    throw new Error("esperava uma string")
  }
}

function usar(entrada: unknown) {
  assertString(entrada)
  // a partir daqui, 'entrada' é string (senão teria lançado)
  return entrada.toUpperCase()   // ✅ sem erro
}

// Variante só de condição: "asserts condicao" (sem 'is')
function assert(condicao: unknown, msg: string): asserts condicao {
  if (!condicao) throw new Error(msg)
}

# Exaustividade com never

Uma das técnicas mais valiosas do TypeScript: garantir, em tempo de compilação, que você tratou todos os casos de uma union. Quando você estreita uma union até o fim, o tipo restante é never (o tipo vazio, que não tem valores). Atribuir o valor a uma variável never num ramo default faz o compilador falhar se algum caso ficou sem tratamento — porque aí o tipo não seria never. É uma rede de segurança: adicionar um novo membro à union quebra a compilação em todo lugar que precisa tratá-lo.

exhaustive.ts
type Forma =
  | { tipo: "circulo"; raio: number }
  | { tipo: "quadrado"; lado: number }

function area(f: Forma): number {
  switch (f.tipo) {
    case "circulo":  return Math.PI * f.raio ** 2
    case "quadrado": return f.lado ** 2
    default:
      // Se todos os casos foram tratados, 'f' aqui é 'never'.
      const _exaustivo: never = f
      return _exaustivo
  }
}

// Se você adicionar { tipo: "triangulo"; ... } à union e esquecer
// o case, o 'const _exaustivo: never = f' QUEBRA a compilação. ✅
O checador de exaustividade é o melhor amigo das unions
A checagem de exaustividade com never transforma uma union (Cap 5) num contrato que o compilador faz cumprir. Sem ela, adicionar um novo membro a uma union (um novo tipo de evento, um novo estado, um novo papel de usuário) compila sem reclamar, e os pontos que precisavam tratar o caso novo ficam silenciosamente incompletos — um bug esperando para acontecer em runtime. Com o ramo never, cada lugar que faz switch sobre a union quebra a compilação ao surgir um caso não tratado, apontando exatamente onde adicionar o tratamento. É a aplicação prática que torna as discriminated unions (Cap 5) tão poderosas, e um padrão que você usará constantemente em estados, eventos e máquinas de estado.

# in, typeof e o fluxo de controle

Além dos predicates e asserts, o TypeScript estreita tipos automaticamente a partir de operadores comuns, e vale conhecer o repertório completo. O operador in checa a presença de uma propriedade, estreitando para o membro da union que a tem. O typeof distingue tipos primitivos. E a análise de fluxo de controle do compilador acompanha as checagens ao longo do código — um return ou throw dentro de um if estreita o tipo no restante da função.

// Análise de fluxo: o early return estreita o resto da função
function comprimento(x: string | null): number {
  if (x === null) return 0        // descarta o null
  return x.length                  // ✅ aqui x é string

Generics

Generics são a ferramenta para escrever código que funciona com múltiplos tipos mantendo total segurança. Em vez de abrir mão da tipagem com any, você parametriza a função, classe ou tipo — o TypeScript preenche o parâmetro conforme o uso.

# Generics em funções

generics.ts
// Sem generics — perde informação:
function primeiroRuim(arr: any[]): any {
  return arr[0];
}
const x = primeiroRuim([1, 2, 3]); // x é any :(

// Com generics — preserva o tipo:
function primeiro<T>(arr: T[]): T | undefined {
  return arr[0];
}

const a = primeiro([1, 2, 3]);      // number | undefined
const b = primeiro(["x", "y"]);     // string | undefined
const c = primeiro<boolean>([true]);// especificando manualmente

// Múltiplos parâmetros de tipo:
function par<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}

const p = par("idade", 30); // [string, number]

# Constraints — restringindo T com extends

Às vezes você precisa que o tipo tenha certas capacidades. extends em um generic significa "T precisa ser compatível com X".

// T precisa ter length:
function maisLongo<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

// T restrito a chaves de um objeto:
function pegar<T, K extends keyof T>(obj: T, chave: K): T[K] {
  return obj[chave];
}

Generics avançados

O capítulo de Generics ensinou o essencial: parametrizar tipos para escrever código reutilizável e seguro, restringir parâmetros com extends, dar defaults. Mas os generics têm uma camada mais profunda, onde mora boa parte do poder real do TypeScript: como o compilador infere os parâmetros de tipo a partir dos argumentos, como restringir um parâmetro com base em outro (usando keyof), e os padrões que tornam funções genéricas verdadeiramente type-safe. # Inferência de parâmetros de tipo

O recurso que torna generics agradáveis de usar: você raramente precisa anotar os parâmetros de tipo explicitamente, porque o compilador os infere a partir dos argumentos passados. Quando você chama uma função genérica, o TypeScript olha os valores reais e deduz o tipo. Isso é o que faz identidade("oi") funcionar sem escrever identidade<string>("oi") — o compilador vê a string e preenche o T sozinho. Entender quando a inferência funciona (e quando precisa de ajuda) é central para escrever APIs genéricas ergonômicas.

inferencia.ts
function primeiro<T>(arr: T[]): T | undefined {
  return arr[0]
}

// O compilador INFERE T a partir do argumento — sem anotar:
const n = primeiro([1, 2, 3])        // T = number, n: number | undefined
const s = primeiro(["a", "b"])       // T = string, s: string | undefined

// A inferência segue os valores: aqui T captura a forma do objeto
function envolver<T>(valor: T): { valor: T } {
  return { valor }
}
const r = envolver({ id: 1, nome: "Ana" })
// r: { valor: { id: number; nome: string } } — tudo inferido

# Restringindo um tipo com base em outro

O padrão genérico mais poderoso na prática: usar keyof para amarrar um parâmetro de tipo a outro. Uma função que pega uma propriedade de um objeto não deve aceitar qualquer string como chave — só as chaves que aquele objeto realmente tem. Combinando dois parâmetros de tipo com K extends keyof T, você expressa exatamente isso: "K é uma das chaves de T". O resultado é um acesso a propriedade totalmente type-safe, onde o retorno tem o tipo correto e chaves inexistentes são erro de compilação.

keyof-generic.ts
// K é restrito às chaves de T; o retorno é o tipo daquela propriedade
function pegar<T, K extends keyof T>(obj: T, chave: K): T[K] {
  return obj[chave]
}

const usuario = { id: 1, nome: "Ana", ativo: true }

const nome = pegar(usuario, "nome")    // nome: string  (tipo correto!)
const id = pegar(usuario, "id")        // id: number
pegar(usuario, "idade")                // ❌ Erro: "idade" não é chave de usuario

// T[K] é um "indexed access type": o tipo da propriedade K em T.
Este é o padrão que torna bibliotecas type-safe
A combinação <T, K extends keyof T> com retorno T[K] não é um exercício acadêmico — é o coração de como bibliotecas como o Drizzle (Vol XI) e o Zod (Vol XII) entregam segurança de tipos. Quando você acessa uma coluna de uma tabela tipada, ou uma propriedade de um schema, e o editor sabe exatamente o tipo de retorno e recusa chaves inexistentes, é este padrão operando por baixo. Ele captura a relação "a chave pertence a este objeto e o retorno é o tipo daquela chave" — uma relação que só os generics conseguem expressar. Reconhecer este padrão te permite tanto entender como essas bibliotecas funcionam quanto escrever as suas próprias APIs genéricas seguras.

# Defaults e constraints combinados

Constraints (extends) e defaults trabalham juntos para criar APIs genéricas flexíveis mas seguras. A constraint limita o que o parâmetro pode ser; o default define o que ele é quando não especificado. Combinados, permitem um parâmetro de tipo que tem um valor sensato por padrão mas pode ser sobrescrito dentro de um limite. É comum em tipos de configuração e factories — o usuário não precisa especificar o tipo no caso comum, mas pode no caso específico.

defaults-constraints.ts
// T restrito a objetos, com default de objeto vazio
interface Resposta<T extends object = {}> {
  ok: boolean
  dados: T
}

const vazia: Resposta = { ok: true, dados: {} }            // T = {} (default)
const cheia: Resposta<{ id: number }> = {                   // T explícito
  ok: true,
  dados: { id: 1 },
}

// Constraint sem default: T DEVE ser fornecido e DEVE ser objeto
function fundir<T extends object>(base: T, extra: Partial<T>): T {
  return { ...base, ...extra }
}

# Controlando a inferência com NoInfer

Às vezes a inferência atrapalha: o compilador deduz um parâmetro de tipo de um argumento que você gostaria que ele ignorasse, levando a um tipo amplo demais. O utilitário NoInfer<T> (adicionado ao TypeScript recentemente) diz ao compilador "não use este argumento para inferir o tipo" — fazendo a inferência vir só dos outros argumentos. É um recurso de borda, mas resolve casos reais onde a inferência produz um tipo indesejado, especialmente em funções com um argumento que define o tipo e outro que deveria apenas se conformar a ele.

noinfer.ts
// Sem NoInfer: o 'padrao' poderia ampliar T para incluir seu próprio tipo
function criarEstado<T>(opcoes: T[], padrao: NoInfer<T>): T {
  return padrao
}

// T é inferido SÓ de 'opcoes'; 'padrao' precisa se conformar a ele
criarEstado(["a", "b", "c"], "a")     // ✅ T = "a" | "b" | "c"
criarEstado(["a", "b", "c"], "x")     // ❌ Erro: "x" não está nas opções
Generics são sobre relações, não só reutilização
A virada conceitual deste capítulo: generics não servem só para "escrever código que funciona com vários tipos". O poder real está em capturar relações entre tipos — "a chave pertence a este objeto", "o retorno tem o tipo daquela propriedade", "o default se conforma às opções". Cada constraint e cada parâmetro de tipo expressa uma regra que o compilador faz cumprir. Quando você escreve <T, K extends keyof T>: T[K], não está só generalizando — está descrevendo uma lei sobre como os tipos se relacionam, e o TypeScript a impõe em todo uso. Essa é a mentalidade que separa quem usa generics para evitar repetição de quem os usa para construir APIs onde tipos errados são impossíveis de escrever. Os capítulos de infer e utility types levam essa ideia ainda mais longe.

Tipos avançados

A partir daqui, o sistema de tipos deixa de ser "mais um anotador" e começa a ser quase uma linguagem de programação própria. Esta é a parte que torna possível bibliotecas como Zod, tRPC e Prisma produzirem tipagens tão precisas.

# O operador keyof

keyof T produz uma união com as chaves de um tipo.

keyof.ts
interface Pessoa {
  nome: string;
  idade: number;
  email: string;
}

type ChavesDePessoa = keyof Pessoa;
// "nome" | "idade" | "email"

function lerCampo<T, K extends keyof T>(obj: T, chave: K): T[K] {
  return obj[chave];
}

const p: Pessoa = { nome: "Ana", idade: 30, email: "a@x.com" };
const nome = lerCampo(p, "nome");  // string
const idade = lerCampo(p, "idade"); // number

# O operador typeof (em contexto de tipo)

Dentro do contexto de tipos, typeof extrai o tipo de uma variável ou valor existente.

typeof.ts
const config = {
  host: "localhost",
  porta: 8080,
  debug: true,
};

type Config = typeof config;
// { host: string; porta: number; debug: boolean }

const ROTAS = {
  HOME: "/",

# Conditional Types

Tipos condicionais seguem a mesma ideia do operador ternário do JavaScript, mas no nível de tipos. A forma é T extends U ? X : Y: "se T é compatível com U, então X, senão Y".

conditional.ts
type EhString<T> = T extends string ? "sim" : "nao";

type A = EhString<"ola">;    // "sim"
type B = EhString<42>;       // "nao"

// Distribui automaticamente em unions:
type Envelope<T> = T extends unknown ? { valor: T } : never;

type E = Envelope<string | number>;
// { valor: string } | { valor: number }

// Útil para "filtrar" unions:
type ApenasStrings<T> = T extends string ? T : never;
type Filtrado = ApenasStrings<"a" | 1 | "b" | 2>;
// "a" | "b"

# A palavra-chave infer

infer aparece apenas dentro de conditional types e diz "crie uma variável de tipo com o que estiver nesta posição". É a ferramenta mais poderosa para extrair partes de um tipo.

infer.ts
// Extrair o tipo de retorno de uma função:
type MeuReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

function usuario() { return { nome: "Ana", idade: 30 }; }
type U = MeuReturnType<typeof usuario>;
// { nome: string; idade: number }

// Extrair o tipo dos parâmetros:
type MeuParameters<T> = T extends (...args: infer P) => any ? P : never;

type P = MeuParameters<(a: string, b: number) => void>;
// [string, number]

// Extrair o elemento de um array:
type Elemento<T> = T extends (infer E)[] ? E : never;

type X = Elemento<number[]>;     // number
type Y = Elemento<string[][]>;   // string[]

// Extrair o valor resolvido de uma Promise:
type Desenrolar<T> = T extends Promise<infer V> ? V : T;

type D = Desenrolar<Promise<string>>; // string

# Mapped Types

Mapped types geram novos tipos iterando sobre as chaves de um tipo existente. Essa é a engrenagem por trás de quase todos os utility types.

mapped.ts
// Torna todas as propriedades opcionais:
type MeuPartial<T> = {
  [K in keyof T]?: T[K];
};

// Torna todas readonly:
type MeuReadonly<T> = {
  readonly [K in keyof T]: T[K];
};

// Inverte — remove readonly e opcional:
type Mutavel<T> = {
  -readonly [K in keyof T]-?: T[K];
};

// Renomear chaves com 'as':
type ComPrefixo<T, P extends string> = {
  [K in keyof T as `${P}${Capitalize<string & K>}`]: T[K];
};

type Eventos = { click: MouseEvent; hover: MouseEvent };
type Handlers = ComPrefixo<Eventos, "on">;
// { onClick: MouseEvent; onHover: MouseEvent }

// Filtrar propriedades com 'as ... never':
type SomenteStrings<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K];
};

type Pessoa = { nome: string; idade: number; email: string };
type SoStrings = SomenteStrings<Pessoa>;
// { nome: string; email: string }

type Json =

  | boolean

  | Json[]

type ConfigCongelada = DeepReadonly<Config>;

Capítulo 12

O operador infer

O capítulo de Tipos Avançados apresentou os conditional types — tipos que escolhem entre dois resultados conforme uma condição. O infer é o que os torna verdadeiramente poderosos: ele permite extrair um tipo de dentro de outro durante uma checagem condicional. Onde os conditional types decidem, o infer captura. Quer o tipo de retorno de uma função? O tipo dos elementos de um array? O tipo resolvido de uma Promise? Tudo isso é extração com infer. É o operador por trás de muitos dos utility types nativos (ReturnType, Awaited, Parameters), e o que permite escrever os seus próprios. Este capítulo desmonta o infer — um operador que parece mágico no início e se torna uma ferramenta precisa de manipulação de tipos quando o modelo fica claro.

# Capturando um tipo durante a condição

O infer só aparece dentro de um conditional type, no lado da condição (depois do extends). Ele declara uma "variável de tipo" que o compilador preenche com o que encaixar naquela posição. A leitura é: "se T tem a forma X com algo na posição P, capture esse algo como U e use-o no resultado". É pattern matching para tipos — você descreve uma forma com um buraco, e o infer preenche o buraco com o que estava lá.

infer-basico.ts
// "Se T for um array de algum tipo U, capture U; senão, never"
type ElementoDe<T> = T extends (infer U)[] ? U : never

type A = ElementoDe<number[]>        // number
type B = ElementoDe<string[]>        // string
type C = ElementoDe<boolean>         // never (não é array)

// O 'infer U' captura o tipo dos elementos durante a checagem.
// É pattern matching: a forma "(infer U)[]" tem um buraco, U o preenche.

# Extraindo de funções: retorno e parâmetros

O uso mais comum do infer é extrair partes de tipos de função. O tipo de retorno de uma função, ou os tipos dos seus parâmetros, podem ser capturados descrevendo a forma da função com um infer na posição desejada. É exatamente assim que os utility types ReturnType e Parameters (do catálogo, capítulo de Utility Types) são implementados — e entender a implementação desmistifica o que parecia mágica.

infer-funcoes.ts
// Extrair o tipo de RETORNO de uma função (assim ReturnType é feito)
type RetornoDe<T> = T extends (...args: any[]) => infer R ? R : never

function criarUsuario() {
  return { id: 1, nome: "Ana" }
}
type Usuario = RetornoDe<typeof criarUsuario>   // { id: number; nome: string }

// Extrair os tipos dos PARÂMETROS (assim Parameters é feito)
type ParamsDe<T> = T extends (...args: infer P) => any ? P : never

function salvar(id: number, nome: string) {}
type Args = ParamsDe<typeof salvar>             // [number, string]
infer revela como os utility types nativos funcionam
Muitos dos utility types que você usa prontos são, por dentro, conditional types com infer. ReturnType<T> é "extraia o tipo após o =>". Parameters<T> é "extraia a tupla antes do =>". Awaited<T> é "se for uma Promise, extraia o tipo resolvido". Saber que eles são infer por baixo tem dois benefícios: desmistifica a "mágica" desses utilitários, e te dá o poder de escrever os seus próprios quando o nativo não existe para o seu caso. O infer é a peça que faltava entre "consumir utility types" e "criar utility types" — o capítulo de construir utilities (adiante) leva isso adiante.

# Extraindo de Promises e estruturas

O infer extrai de qualquer forma de tipo, não só funções e arrays. Um caso muito útil é "desembrulhar" uma Promise — capturar o tipo que ela resolve, o que o utility Awaited faz (importante no código assíncrono, Vol VIII e capítulo de tipos assíncronos). Você também pode extrair de tuplas, objetos, e tipos aninhados, combinando infer com recursão para casos mais complexos.

infer-promise.ts
// Desembrulhar uma Promise (assim Awaited é feito, simplificado)
type Resolvido<T> = T extends Promise<infer U> ? U : T

type R1 = Resolvido<Promise<string>>    // string
type R2 = Resolvido<number>              // number (não é Promise)

// Extrair o primeiro elemento de uma tupla
type Primeiro<T> = T extends [infer P, ...any[]] ? P : never
type P = Primeiro<[boolean, number, string]>   // boolean

// Combinar com recursão: desembrulhar Promises aninhadas
type ResolvidoFundo<T> = T extends Promise<infer U> ? ResolvidoFundo<U> : T
type R3 = ResolvidoFundo<Promise<Promise<number>>>   // number
infer é pattern matching para tipos
O modelo mental que torna o infer intuitivo: pense nele como pattern matching, o mesmo conceito que linguagens funcionais usam para desestruturar valores — só que aqui sobre tipos. Você escreve uma "forma" com um espaço a preencher ((infer U)[], Promise<infer U>, (...args: any) => infer R), e o infer captura o que estava naquele espaço. Uma vez que você enxerga assim — "descrevo a estrutura, marco onde quero capturar, o compilador preenche" —, o infer deixa de ser críptico e vira uma ferramenta precisa. É um recurso de borda (você não o usa todo dia), mas quando precisa extrair um tipo de dentro de outro, é insubstituível, e entender a sua mecânica é o que separa quem só consome tipos avançados de quem os escreve.

TypeScript vem com uma biblioteca embutida de utility types — transformadores de tipo úteis para o dia-a-dia. Todos são implementados usando os recursos do capítulo anterior (keyof, conditional types, mapped types e infer). Conhecê-los é economia de tempo pura.

utility-objeto.ts
interface Usuario {
  id: number;
  nome: string;
  email: string;
  senha: string;
}

type UsuarioParcial = Partial<Usuario>;
// { id?: number; nome?: string; email?: string; senha?: string }

// Required<T> — todos os campos obrigatórios (remove ?):

type UsuarioImutavel = Readonly<Usuario>;

// Pick<T, K> — só as chaves escolhidas:
type UsuarioPublico = Pick<Usuario, "id" | "nome" | "email">;

// Omit<T, K> — tudo menos as chaves informadas:
type UsuarioSemSenha = Omit<Usuario, "senha">;

// Record<K, T> — objeto com chaves K e valores T:
type Permissoes = Record<"ler" | "escrever" | "admin", boolean>;
// { ler: boolean; escrever: boolean; admin: boolean }

const p: Permissoes = { ler: true, escrever: false, admin: false };

Construindo Utility Types

O capítulo anterior catalogou os utility types nativos — Partial, Pick, Omit, Record e companhia — como ferramentas prontas. Mas eles não são mágica embutida no compilador: são tipos comuns, escritos em TypeScript, que você poderia ter escrito. Reimplementá-los do zero é o melhor exercício de type-level programming que existe, porque combina tudo dos capítulos avançados — mapped types, conditional types, keyof, infer — em construções pequenas e compreensíveis. Este capítulo reconstrói os utility types mais importantes passo a passo. O objetivo não é decorar as implementações, mas entender o mecanismo: depois deste capítulo, você não só usa os utilitários nativos com clareza, mas escreve os seus próprios quando o nativo não cobre o seu caso.

# Partial e Required: mexendo na opcionalidade

O Partial<T> torna todas as propriedades opcionais; o Required<T> faz o oposto. Ambos são mapped types — eles iteram sobre as chaves de T e reconstroem o tipo aplicando um modificador. O ? adiciona opcionalidade; o -? a remove. Ver a implementação revela que "tornar opcional" é só um modificador num mapped type.

partial-required.ts
// Partial: itera as chaves de T e marca cada uma como opcional (?)
type MeuPartial<T> = {
  [K in keyof T]?: T[K]
}

// Required: o -? REMOVE a opcionalidade de cada chave
type MeuRequired<T> = {
  [K in keyof T]-?: T[K]
}

interface Config { host: string; porta?: number }

type ConfigParcial = MeuPartial<Config>    // { host?: string; porta?: number }
type ConfigCheia = MeuRequired<Config>     // { host: string; porta: number }

# Readonly e Mutable

O mesmo padrão de mapped type com modificador serve para readonly. O Readonly<T> adiciona readonly a cada propriedade; o modificador -readonly o remove (um "Mutable" que o TypeScript não fornece nativamente, mas você escreve em uma linha). É a prova de que os modificadores ? e readonly são manipuláveis em mapped types, com + para adicionar e - para remover.

readonly-mutable.ts
// Readonly: adiciona readonly a cada propriedade
type MeuReadonly<T> = {
  readonly [K in keyof T]: T[K]
}

// Mutable: -readonly REMOVE o readonly (não existe nativo!)
type Mutable<T> = {
  -readonly [K in keyof T]: T[K]
}

type Congelado = MeuReadonly<{ x: number }>   // { readonly x: number }
type Destravado = Mutable<Congelado>           // { x: number }

# Pick e Omit: selecionando chaves

O Pick<T, K> seleciona um subconjunto de propriedades; o Omit<T, K> remove um subconjunto. O Pick usa um mapped type que itera só sobre as chaves K (restritas a keyof T, o padrão do capítulo de generics avançados). O Omit é construído com Exclude para tirar as chaves indesejadas de keyof T, e então faz Pick do resto — mostrando como os utilitários se compõem uns sobre os outros.

pick-omit.ts
// Pick: itera só as chaves K (que devem ser chaves de T)
type MeuPick<T, K extends keyof T> = {
  [P in K]: T[P]
}

// Omit: pega todas as chaves de T MENOS as de K, e faz Pick do resto
type MeuOmit<T, K extends keyof T> = MeuPick<T, Exclude<keyof T, K>>

interface Usuario { id: number; nome: string; senha: string }

type PublicoA = MeuPick<Usuario, "id" | "nome">   // { id, nome }
type PublicoB = MeuOmit<Usuario, "senha">         // { id, nome } (sem senha)
Utilitários se compõem uns sobre os outros
Repare como Omit é construído a partir de Pick e Exclude. Essa composição é a essência do type-level programming: você não escreve cada utilitário do zero a cada vez — combina peças pequenas e bem definidas em construções maiores, exatamente como compõe funções no código comum (toda a coleção). Exclude remove de uma union; Pick seleciona chaves; Omit = Pick do que Exclude deixou. Cada utility type é uma pequena função sobre tipos, e elas se encaixam. Entender essa composicionalidade é o que permite, diante de uma necessidade nova de transformação de tipos, montá-la a partir das peças que você já conhece em vez de ficar travado.

# Record e utilitários condicionais

O Record<K, V> constrói um tipo de objeto com chaves K e valores V — um mapped type sobre uma union de chaves. E os utilitários "condicionais" como Exclude, Extract e NonNullable usam conditional types distribuídos sobre unions. Ver o Exclude implementado mostra um comportamento importante: conditional types se distribuem automaticamente sobre cada membro de uma union, processando-os um a um.

record-conditional.ts
// Record: objeto com chaves K e valores V
type MeuRecord<K extends string | number | symbol, V> = {
  [P in K]: V
}
type Notas = MeuRecord<"mat" | "port", number>   // { mat: number; port: number }

// Exclude: distribui sobre a union, removendo o que combina com U
type MeuExclude<T, U> = T extends U ? never : T
type Sem = MeuExclude<"a" | "b" | "c", "b">       // "a" | "c"

// NonNullable: remove null e undefined
type MeuNonNullable<T> = T extends null | undefined ? never : T
type Limpo = MeuNonNullable<string | null>        // string
Escrever utility types ensina a pensar em tipos
Reimplementar os utility types não é só curiosidade — é o exercício que consolida todo o conhecimento de tipos avançados num modelo operacional. Mapped types (iterar chaves), modificadores (?, readonly, -), keyof (as chaves), indexed access (T[K]), conditional types (decidir), distribuição sobre unions, infer (extrair) — cada utility type combina alguns desses, e construí-los faz você praticar a combinação. Depois deste capítulo, você lê uma assinatura de tipo complexa de uma biblioteca e a decompõe mentalmente, e diante de uma transformação de tipo que o TypeScript não oferece pronta, você a escreve. É a passagem de consumidor a autor de tipos — a fronteira do domínio real da linguagem.

Capítulo 15

Branded types e nominal typing

O sistema de tipos do TypeScript é estrutural: dois tipos são compatíveis se têm a mesma forma, independentemente de como se chamam. Isso é flexível e prático na maioria das vezes — mas cria um problema sutil. Um UserId e um ProductId, ambos sendo string por baixo, são intercambiáveis para o compilador, mesmo que misturá-los seja um bug grave. Os branded types (ou nominal typing) resolvem isso: eles "marcam" um tipo de forma que o torna incompatível com outros da mesma estrutura, fazendo o compilador distinguir um ID de usuário de um ID de produto, um e-mail validado de uma string qualquer. Este capítulo — cujo padrão aparece nos seus próprios volumes de Drizzle, Zod e Autenticação (Vols XI–XIII) — mostra como simular tipagem nominal numa linguagem estrutural, e quando isso vale a complexidade extra.

# Estrutural vs nominal: o problema

Em tipagem estrutural (a do TypeScript), o que importa é a forma. Se dois tipos têm os mesmos membros, são compatíveis — o nome é irrelevante. Em tipagem nominal (a de linguagens como Java), o nome importa: dois tipos com a mesma forma mas nomes diferentes são incompatíveis. O TypeScript é estrutural, o que significa que type UserId = string e type ProductId = string são, para o compilador, exatamente a mesma coisa — string. Passar um onde se espera o outro compila sem reclamar, e o bug escapa.

problema.ts
// Aliases simples NÃO criam distinção — são só string por baixo
type UserId = string
type ProductId = string

function buscarUsuario(id: UserId) { /* ... */ }

const produtoId: ProductId = "prod_123"
buscarUsuario(produtoId)   // ❌ deveria ser erro... mas COMPILA!
// Para o compilador, UserId e ProductId são ambos 'string'.
// O bug de passar o ID errado escapa silenciosamente.

# A técnica: marcar o tipo

O truque dos branded types é adicionar uma propriedade "fantasma" ao tipo — uma marca que existe só no nível de tipos, nunca em runtime — que o torna estruturalmente distinto. Como UserId passa a ter uma marca diferente de ProductId, suas formas deixam de ser idênticas, e o compilador os trata como incompatíveis. A marca usa uma técnica de intersection (Cap 5) com um símbolo único, e o valor em runtime continua sendo apenas uma string — o branding é puramente uma ficção de tipos.

branding.ts
// Um helper genérico de branding: marca T com um rótulo B
type Brand<T, B> = T & { readonly __brand: B }

// Agora os IDs são estruturalmente DISTINTOS
type UserId = Brand<string, "UserId">
type ProductId = Brand<string, "ProductId">

function buscarUsuario(id: UserId) { /* ... */ }

const pid = "prod_123" as ProductId
buscarUsuario(pid)        // ✅ AGORA é erro: ProductId não é UserId

// A marca __brand não existe em runtime — pid ainda é só "prod_123".
// É uma ficção de tipos que o compilador faz cumprir.
A marca existe só no compilador, nunca em runtime
O ponto que confunde no início: a propriedade __brand nunca existe de fato no valor. Você nunca cria { __brand: "UserId" } — o valor continua sendo uma string pura. A marca é uma anotação de tipo que existe apenas durante a checagem, e desaparece completamente no JavaScript gerado (toda a tipagem some na compilação). É por isso que branded types têm custo zero em runtime: não há objeto a mais, não há verificação a mais, nenhum overhead. O branding é puramente uma forma de dar ao compilador estrutural a capacidade de distinguir tipos que, sem a marca, ele consideraria iguais. É um truque elegante: usar o próprio sistema estrutural (intersection com uma forma única) para simular nominalidade.

# Branding como prova de validação

O uso mais valioso dos branded types vai além de distinguir IDs: eles representam provas de que um valor passou por uma validação. Um Email branded não é qualquer string — é uma string que comprovadamente passou pela validação de e-mail. Como a marca só pode ser aplicada pela função de validação (que é a única que faz o as), o tipo Email garante, em tempo de compilação, que aquele valor foi validado. Isso conecta diretamente ao Zod (Vol XII) e à autenticação (Vol XIII): tipos que carregam a garantia de que cruzaram a fronteira de validação.

prova-validacao.ts
type Email = Brand<string, "Email">

// A ÚNICA forma de obter um Email é passar pela validação.
// O branding vira uma "prova" de que o valor foi validado.
function validarEmail(entrada: string): Email | null {
  return entrada.includes("@") ? (entrada as Email) : null
}

function enviar(para: Email) { /* confia que 'para' é válido */ }

const cru = "ana@exemplo.com"
enviar(cru)                    // ❌ erro: string não é Email (não validado)

const email = validarEmail(cru)
if (email) enviar(email)       // ✅ ok: passou pela validação
Use branding com moderação, onde a confusão é cara
Branded types adicionam complexidade — os as necessários, o helper de Brand, a fricção de criar valores marcados. Por isso não se deve "brandar tudo": a maioria dos tipos vive bem com a tipagem estrutural padrão, que é prática justamente por ser flexível. Reserve o branding para onde a confusão entre tipos de mesma forma é genuinamente perigosa: IDs de entidades diferentes que nunca devem ser trocados, valores que precisam carregar uma garantia de validação (e-mails, valores sanitizados, dinheiro em centavos vs reais), unidades que não se misturam. Nesses casos, o custo se paga ao tornar uma classe inteira de bugs impossível de compilar. É a aplicação ao TypeScript do princípio que atravessa a coleção: torne os estados inválidos irrepresentáveis — e o branding é a ferramenta quando a estrutura sozinha não basta.

Decorators são funções que modificam classes, métodos, propriedades, acessores e parâmetros em tempo de declaração. TypeScript 5.0 adotou a sintaxe padrão do ECMAScript (Stage 3) — mais simples e alinhada com o futuro do JavaScript.

}

function medirTempo(
  metodoOriginal: any,

Tipos assíncronos

Promises e async/await são JavaScript puro, mas TypeScript traz tipagem rica para eles. Saber ler e escrever assinaturas assíncronas é requisito para qualquer código de backend ou de chamadas HTTP.

async.ts
// Funções async sempre retornam Promise<T>:
async function buscarUsuario(id: number): Promise<Usuario> {
  const res = await fetch(`/api/users/${id}`);
  const json = await res.json();
  return json as Usuario;
}

interface Usuario { id: number; nome: string; }

// Promise.all é tipado por tupla:
async function carregar(): Promise<[Usuario, Post[]]> {
  const [u, p] = await Promise.all([
    buscarUsuario(1),
    buscarPosts(),
  ]);
  return [u, p];
}

async function buscarPosts(): Promise<Post[]> { return []; }
interface Post { id: number; titulo: string; }

// Awaited<T> — extrai o tipo resolvido:
type DadosUsuario = Awaited<ReturnType<typeof buscarUsuario>>;
// Usuario

// Result pattern — alternativa a try/catch:
type Resultado<T, E = Error> =
  | { ok: true; valor: T }
  | { ok: false; erro: E };

async function pegarUsuarioSeguro(id: number): Promise<Resultado<Usuario>> {
  try {
    const u = await buscarUsuario(id);
    return { ok: true, valor: u };
  } catch (e) {
    return { ok: false, erro: e as Error };
  }
}

Padrões de tipagem do mundo real

Os capítulos anteriores construíram o vocabulário do sistema de tipos, peça por peça. Este capítulo monta esse vocabulário em padrões — formas recorrentes de usar tipos para resolver problemas reais de aplicação. Modelar estados que não podem ser inválidos, representar operações que podem falhar sem exceções, tipar configurações e eventos com precisão. Estes não são recursos novos da linguagem; são aplicações dos recursos que você já conhece, na forma como aparecem no código de produção da coleção inteira. O princípio que une todos eles é o mais importante do TypeScript prático: tornar os estados inválidos irrepresentáveis — desenhar os tipos de modo que o código errado simplesmente não compile, em vez de confiar que o programador lembrará de cada regra.

# Tornar estados inválidos irrepresentáveis

O padrão mais valioso, e o que dá sentido a todos os outros. Em vez de um tipo que permite combinações inválidas (e confiar em checagens de runtime para evitá-las), você modela o tipo de forma que as combinações inválidas não existam. O exemplo clássico é um estado de carregamento: um objeto com flags carregando, dados e erro permite o estado impossível "carregando e com erro ao mesmo tempo". Uma discriminated union (Cap 5) elimina isso — cada estado é um membro distinto, e os impossíveis nem têm como ser escritos.

estados.ts
// ❌ Permite estados impossíveis (carregando E com erro E com dados?)
interface EstadoRuim<T> {
  carregando: boolean
  dados: T | null
  erro: string | null
}

// ✅ Discriminated union: só os estados VÁLIDOS existem
type Estado<T> =
  | { status: "carregando" }
  | { status: "sucesso"; dados: T }
  | { status: "erro"; mensagem: string }

function render(estado: Estado<string>) {
  switch (estado.status) {
    case "carregando": return "..."
    case "sucesso":    return estado.dados      // só existe aqui
    case "erro":       return estado.mensagem   // só existe aqui
  }
}
O princípio que organiza o TypeScript prático
"Make illegal states unrepresentable" é a ideia que transforma o TypeScript de um verificador de tipos num desenhador de domínios. Em vez de escrever um tipo permissivo e cercá-lo de validações e comentários sobre o que é válido, você molda o tipo para que o inválido seja impossível de expressar — e então o compilador faz a regra cumprir gratuitamente, em todo lugar, para sempre. Um estado que não pode ser "carregando e erro" não precisa de teste para isso. Um Email branded (capítulo anterior) que só a validação produz não precisa de checagem de "será que validei?". Cada vez que você consegue codificar uma regra de negócio na forma do tipo, ela deixa de ser uma disciplina que se pode esquecer e vira uma garantia que o compilador impõe. Esse é o retorno máximo do investimento em tipos, e o fio que conecta discriminated unions, branded types e os padrões deste capítulo.

# Result: erros sem exceções

Um padrão difundido para operações que podem falhar: em vez de lançar exceções (que o sistema de tipos não rastreia — uma função pode lançar sem que sua assinatura avise), retornar um Result — uma discriminated union que representa explicitamente sucesso ou falha. O chamador é obrigado pelo compilador a tratar ambos os casos antes de acessar o valor, porque o dado só existe no ramo de sucesso. É a tipagem de erros tornada visível e inescapável, popular em linguagens como Rust e cada vez mais em TypeScript.

result.ts
type Result<T, E = Error> =
  | { ok: true; valor: T }
  | { ok: false; erro: E }

function dividir(a: number, b: number): Result<number, string> {
  if (b === 0) return { ok: false, erro: "divisão por zero" }
  return { ok: true, valor: a / b }
}

const r = dividir(10, 0)
// r.valor          ❌ erro: 'valor' não existe quando ok é false
if (r.ok) {
  console.log(r.valor)     // ✅ só aqui o valor existe
} else {
  console.error(r.erro)    // ✅ e aqui, o erro
}

# Tipando configuração e dados externos

Dois padrões para os limites da aplicação. Para configuração, o satisfies (do capítulo de assertions) valida a forma sem alargar o tipo, mantendo a inferência precisa de cada valor. Para dados externos (JSON, respostas de API), o tipo correto de entrada é unknown — não any —, forçando você a validar antes de usar, exatamente como o Zod (Vol XII) faz. Esses padrões marcam a fronteira entre o mundo tipado interno e o mundo não confiável externo.

// CONFIG: satisfies valida a forma SEM perder os tipos literais precisos

  ambiente: "producao",

// config.ambiente continua sendo "producao" (literal), não string genérica

// DADOS EXTERNOS: a entrada é unknown, não any — força validar
function processarResposta(json: unknown) {
  // não dá para usar json direto — precisa validar/estreitar (Cap 5, Zod)
  if (typeof json === "object" && json !== null && "id" in json) {
    // agora o narrowing permite acessar com segurança
  }
}

# Tipando eventos e callbacks

Um padrão comum em UIs e sistemas orientados a eventos: um mapa de eventos onde cada nome de evento tem um tipo de payload específico, e o tipo garante que o handler de cada evento receba o payload correto. Usando um Record de eventos e keyof (capítulo de generics avançados), você cria uma API de eventos totalmente type-safe, onde emitir um evento com o payload errado ou registrar um handler com a assinatura errada é erro de compilação.

eventos.ts
// Mapa: cada evento -> o tipo do seu payload
interface Eventos {
  login: { userId: number }
  logout: { motivo: string }
  erro: { codigo: number; mensagem: string }
}

// 'on' usa keyof para amarrar o nome ao payload correto
function on<K extends keyof Eventos>(
  evento: K,
  handler: (payload: Eventos[K]) => void
) { /* ... */ }

on("login", (p) => p.userId)        // ✅ p é { userId: number }
on("erro", (p) => p.mensagem)       // ✅ p é { codigo, mensagem }
on("login", (p) => p.motivo)        // ❌ 'motivo' não existe em login

# Tipagem estrutural: forma, não nome

A decisão de design mais fundamental do TypeScript, já tocada nos branded types: a compatibilidade é estrutural. Um valor é atribuível a um tipo se tem pelo menos a forma que o tipo exige — os membros certos com os tipos certos —, independentemente de qual classe ou interface o declarou. Isso explica muito: por que um objeto literal pode satisfazer uma interface sem "implementá-la" explicitamente, por que tipos com a mesma forma são intercambiáveis, e por que o branding (capítulo anterior) é necessário para distingui-los. Pensar "forma, não nome" desfaz muitas surpresas.

structural.ts
interface Ponto { x: number; y: number }

// Nenhuma menção a 'Ponto', mas a FORMA bate — é compatível
const p = { x: 1, y: 2, z: 3 }
function plotar(ponto: Ponto) { /* ... */ }
plotar(p)        // ✅ p tem x e y (z a mais não importa)

// Duas formas idênticas são intercambiáveis, nomes à parte
interface Coord { x: number; y: number }
const c: Coord = p
const q: Ponto = c    // ✅ Coord e Ponto têm a mesma forma

# Lendo erros de tipo

Mensagens de erro do TypeScript têm fama de assustadoras — longas, aninhadas, cheias de tipos. Mas elas seguem uma estrutura legível quando você sabe lê-las: o compilador relata o erro de fora para dentro, e a causa raiz geralmente está no final da mensagem, na linha mais indentada. A técnica é começar pela última linha (o conflito específico) e subir para entender o contexto. Erros sobre objetos grandes mostram só a propriedade que diverge. Aprender a ler o erro — em vez de fechá-lo no susto — resolve a maioria dos problemas sem busca externa.

erro.ts
interface Usuario { nome: string; idade: number }
const u: Usuario = { nome: "Ana", idade: "30" }

// O erro lê-se de FORA para DENTRO; a causa está no fim:
//
//   Type '{ nome: string; idade: string }' is not assignable
//   to type 'Usuario'.
//     Types of property 'idade' are incompatible.   <- contexto
//       Type 'string' is not assignable to 'number'. <- A CAUSA (fim)
//
// Comece pela última linha: idade deveria ser number, veio string.
Leia o erro de baixo para cima
A heurística que desarma os erros mais assustadores do TypeScript: leia-os de baixo para cima. A primeira linha de um erro costuma ser o conflito de alto nível ("este tipo grande não é atribuível àquele tipo grande"), que parece esmagador. Mas o compilador então detalha, descendo cada nível de aninhamento até a incompatibilidade específica — e essa causa raiz, na linha final e mais indentada, é quase sempre simples e acionável ("string não é number"). Em vez de tentar processar o tipo inteiro de uma vez, pule para o fim, entenda o conflito pontual, e suba o necessário para localizá-lo no seu código. Com prática, erros que pareciam exigir um especialista viram diagnósticos de dez segundos. O TypeScript não está sendo hostil — está te mostrando exatamente onde a forma esperada e a fornecida divergem.

# Inspecionar e depurar tipos

Quando um tipo complexo (um conditional, um mapped, um resultado de infer) produz algo inesperado, há ferramentas para inspecioná-lo. Passar o mouse sobre um valor no editor mostra seu tipo inferido. Um truque útil é atribuir o tipo a um alias e inspecioná-lo, ou usar um utilitário que "expande" tipos para ver a forma final em vez do alias. E o // @ts-expect-error documenta e verifica que uma linha deve causar erro — útil em testes de tipo e para marcar incompatibilidades conhecidas.

inspecionar.ts
// Inspecionar um tipo: atribua a um alias e passe o mouse no editor
type Resultado = ReturnType<typeof minhaFuncao>
//   hover em 'Resultado' mostra a forma final

// Forçar a expansão de um tipo para ver a forma (truque comum)
type Expandir<T> = { [K in keyof T]: T[K] } & {}

// @ts-expect-error: afirma que a PRÓXIMA linha DEVE dar erro.
// Se ela NÃO der erro, o próprio @ts-expect-error vira um erro.
// @ts-expect-error
const x: number = "texto"   // esperado falhar; documenta a intenção

# Os tipos somem em runtime

O fato estrutural mais importante de todos, e fonte de muita confusão: os tipos não existem em runtime. O TypeScript compila para JavaScript apagando toda a informação de tipos — interfaces, anotações, generics, tudo desaparece. O JavaScript gerado não sabe nada sobre os seus tipos. Isso tem consequências práticas profundas: você não pode checar um tipo em runtime (if (x instanceof MinhaInterface) não existe), não pode validar dados externos só com tipos (precisa de validação real, como o Zod do Vol XII), e o branding (capítulo anterior) tem custo zero justamente porque some.

runtime.ts
interface Usuario { nome: string }

// ❌ NÃO funciona: interfaces não existem em runtime
// if (dado instanceof Usuario) { }   // erro: Usuario não é um valor

// O JavaScript gerado deste arquivo NÃO tem nada sobre Usuario.
// Toda a tipagem foi apagada na compilação.

// Para checar a forma em RUNTIME, você precisa de código real
// (ou de uma biblioteca de validação como o Zod — Vol XII):
function ehUsuario(d: unknown): d is Usuario {
  return typeof d === "object" && d !== null && "nome" in d
}
Tipos são para o compilador; validação é para o runtime
A lição que fecha o volume e conecta toda a coleção: tipos e validação são coisas diferentes que resolvem problemas diferentes. Os tipos do TypeScript protegem você durante o desenvolvimento — pegam erros no editor, no build, antes de rodar — e então desaparecem. Eles não fazem nada em runtime, e não podem proteger contra dados que chegam de fora (uma resposta de API, um formulário, um JSON) em runtime. Para isso existe a validação (Zod, Vol XII), que roda de verdade e verifica os dados quando eles cruzam a fronteira. Confundir os dois é um erro clássico: tipar uma resposta de API como Usuario não garante que ela seja um usuário — só diz ao compilador para confiar que é. A garantia real vem de validar em runtime e derivar o tipo dessa validação. Tipos para o que você escreve; validação para o que você recebe. Entender essa divisão é entender o lugar do TypeScript no stack.

Boas práticas

Você aprendeu a mecânica da linguagem. Esta última parte reúne regras não-oficiais que a comunidade TypeScript costuma seguir — o tipo de coisa que faz um código "cheirar" certo.

# Ative o modo strict

Todas as flags strict* ativadas por padrão. Em tsconfig.json, "strict": true é o primeiro passo de um projeto saudável. Também considere:

  • noUncheckedIndexedAccess — acesso a arr[i] devolve T | undefined. Quase sempre o correto.
  • exactOptionalPropertyTypes — diferencia "propriedade ausente" de "propriedade com valor undefined".
  • noImplicitOverride — força override explícito em subclasses.

# Prefira tipos a any

Quando for tentador usar any, pare e pense: seria unknown? Um generic? Uma union? O any só deve aparecer em interop raro com código legado.

# Deixe o TypeScript inferir

Anotações em todo lugar não deixam o código mais seguro — apenas mais ruidoso. Escreva tipos em:

  • Assinaturas públicas (parâmetros e retorno de funções exportadas).
  • APIs de módulos e classes.
  • Casos onde a inferência fica ampla demais (ex.: array vazio).

E confie na inferência em variáveis locais, callbacks inline e destructuring.

# Modelos com discriminated unions

Cada vez que você tem um objeto que "pode ser de três tipos" ou um estado com "várias fases", o padrão correto é quase sempre uma discriminated union. Evite optional chaining intrincado em estruturas que deveriam ser unions.

# Valide entradas externas

TypeScript protege você dentro do seu código. Tudo que vem de fora (JSON de APIs, localStorage, process.env, formulários) deve ser validado em runtime. Use bibliotecas como Zod, Valibot ou ArkType, que fornecem validação e tipos no mesmo gesto.

com-zod.ts
import { z } from "zod";

const UsuarioSchema = z.object({
  id: z.number(),
  nome: z.string(),
  email: z.string().email(),
});

type Usuario = z.infer<typeof UsuarioSchema>;
// { id: number; nome: string; email: string }

async function carregar(): Promise<Usuario> {
  const res = await fetch("/api/me");
  const json = await res.json();
  return UsuarioSchema.parse(json); // valida + tipa em runtime
}

# Nomenclatura

  • PascalCase para tipos, interfaces, classes e enums: Usuario, StatusHttp.
  • camelCase para variáveis, funções e propriedades: buscarUsuario.
  • CONSTANT_CASE para constantes de nível de módulo: MAX_RETRIES.
  • Evite prefixos tipo IUsuario — é cultura do C#, não casa com TypeScript.
  • Prefira nomes concretos a "genéricos demais". T em generics é tradicional, mas TItem, TKey comunicam mais.

# Organize o tsconfig do projeto

Em monorepos, use project references (references no tsconfig) para builds incrementais mais rápidos. Prefira um tsconfig.base.json que é estendido por cada pacote, em vez de duplicar configuração.

  • ESLint com @typescript-eslint para regras de estilo e boas práticas.
  • Prettier para formatação automática.
  • tsx ou Bun para rodar .ts direto em desenvolvimento.
  • vitest ou Jest + ts-jest para testes.
  • zod, valibot para validação em runtime.
