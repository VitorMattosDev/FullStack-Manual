Capítulo 1

Drizzle como camada fina sobre SQL

Drizzle ORM é uma biblioteca TypeScript que faz duas coisas: descreve o schema relacional como código e expõe um query builder que se lê como SQL idiomático. Não há DSL externa, não há cliente gerado, não há query engine compilado — apenas TypeScript puro, ~7 KB minificado, com zero dependências. Este capítulo estabelece o modelo mental que orienta todos os outros: schema é código, queries são SQL, e o tipo certo aparece sem que ninguém precise pedir.

# O que Drizzle resolve

ORMs clássicos venderam a promessa de "abstrair o banco". Na prática, isso significou três coisas: uma DSL paralela para descrever o schema (arquivos .prisma, decorators TypeORM), um cliente gerado que precisa ser recompilado a cada mudança, e queries cuja tradução para SQL é uma caixa-preta. Em desenvolvimento, isso parece prático. Em produção, vira fonte recorrente de surpresas: N+1 silencioso, joins inferidos errados, prepared statements ignorados, planos de execução que não se parecem com o que a query expressa.

Drizzle inverte a equação. O schema vive em arquivos .ts normais, sem geração. As queries se parecem com SQL — porque são SQL, traduzidas mecanicamente para a string que vai ao banco. Quando você escreve db.select().from(users).leftJoin(orders, ...), o que sai é exatamente um SELECT ... FROM users LEFT JOIN orders ON .... A previsibilidade é o produto.

Nota
"ORM" é um nome que Drizzle aceita por força do hábito. O time descreve o projeto como "headless TypeScript ORM with a head": o núcleo é um query builder e um schema toolkit; o "head" opcional é a camada de relational queries que torna leituras com joins navegáveis. Os dois convivem no mesmo db e este manual cobre os dois.

# Schema é código TypeScript

O CREATE TABLE que aparece no Volume X tem tradução direta para Drizzle. Em vez de DSL nova, você usa funções que retornam descritores de coluna, agrupadas em um objeto que descreve a tabela. O tipo de cada linha — para leitura e para escrita — é inferido a partir dessa descrição. Sem etapa de build, sem watcher, sem comando generate entre o schema e a query.

schema/users.ts
import { pgTable, serial, varchar, timestamp } from 'drizzle-orm/pg-core';

export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  email: varchar('email', { length: 255 }).notNull().unique(),
  nome: varchar('nome', { length: 120 }).notNull(),
  criadoEm: timestamp('criado_em').defaultNow().notNull(),
});

// Os tipos são derivados do próprio descritor — nada é gerado em disco.
export type User    = typeof users.$inferSelect;
export type NewUser = typeof users.$inferInsert;

O par $inferSelect / $inferInsert é a peça que substitui o cliente gerado de outros ORMs. O primeiro é o shape de uma linha lida do banco — todos os campos presentes, com seus tipos exatos. O segundo é o shape aceitável em um INSERT: id é opcional (serial gera automaticamente), criadoEm é opcional (tem default), email e nome são obrigatórios. Essa distinção, que em Prisma exige tipos separados como User e Prisma.UserCreateInput, em Drizzle cai direto do schema.

# Os dois lados do db

Drizzle expõe duas APIs sobre a mesma conexão. O query builder é a tradução literal do SQL: db.select(...).from(...).where(...).leftJoin(...). Ele é o que se usa quando a query é explicitamente relacional, quando se precisa de controle fino sobre o SQL gerado, ou quando o resultado deve ser uma forma achatada de várias tabelas. As relational queries — db.query.users.findMany({ with: { orders: true } }) — são a camada declarativa por cima: você descreve o que quer ler, navegando relações, e Drizzle decide entre joins e subqueries para entregar uma árvore tipada.

query/dois-estilos.ts
import { eq } from 'drizzle-orm';
import { db } from './db';
import { users, orders } from './schema';

// Estilo 1 — query builder: SELECT literal, resultado achatado.
const linhas = await db
  .select({ nome: users.nome, total: orders.total })
  .from(users)
  .leftJoin(orders, eq(orders.userId, users.id))
  .where(eq(users.id, 42));
// linhas: { nome: string; total: string | null }[]

// Estilo 2 — relational query: árvore aninhada, tipada por relação.
const u = await db.query.users.findFirst({
  where: eq(users.id, 42),
  with: { orders: true },
});
// u: { id, email, nome, criadoEm, orders: Order[] } | undefined

A escolha entre os dois não é dogmática: leituras com agregação, filtros pesados, ou que produzem uma linha por par usuário × pedido ficam no builder; leituras que querem um usuário com seus pedidos aninhados ficam no db.query. O Capítulo 16 trata disso com critérios para decidir caso a caso.

# Drizzle, Prisma e TypeORM

As três ferramentas competem pelo mesmo espaço, mas com pressupostos arquiteturais incompatíveis. Prisma trata o schema como uma DSL própria (schema.prisma) e gera um cliente tipado a cada mudança; o runtime depende de um query engine binário em Rust (cerca de 40 MB) que interpreta requisições do cliente JS e produz o SQL final. TypeORM herda o modelo do Hibernate: classes anotadas com decorators, metadata coletada em tempo de execução, e dois paradigmas concorrentes — active record e data mapper — convivendo no mesmo projeto. Drizzle não tem DSL externa, não tem cliente gerado e não tem binário: o schema é TS, os tipos são inferidos, o SQL é construído por funções e enviado direto pelo driver da sua escolha (pg, postgres, @neondatabase/serverless, entre outros).

Quando Drizzle ganha — e quando não
Drizzle é a escolha óbvia em edge runtimes (Cloudflare Workers, Vercel Edge), funções serverless sensíveis a cold start, projetos que precisam de SQL controlado para EXPLAIN e tuning, equipes que já dominam SQL e não querem aprender DSL nova. Prisma continua à frente em ergonomia para times que preferem abstração total e aceitam o custo de bundle. TypeORM segue presente em bases legadas com forte cultura de decorators e migração custosa.

# Type-safety de ponta a ponta

O argumento central de Drizzle é que o tipo da query nunca diverge do schema, porque ele é o schema. Não há "regenerar o client" depois de adicionar uma coluna; basta editar o arquivo. O exemplo abaixo encadeia schema, query e resultado, mostrando a inferência em cada etapa:

query/type-flow.ts
// 1. SELECT inferido a partir do schema — sem anotação manual.
const lista = await db.select().from(users);
//    ^? { id: number; email: string; nome: string; criadoEm: Date }[]

// 2. Projeção parcial reduz o tipo correspondentemente.
const emails = await db.select({ email: users.email }).from(users);
//    ^? { email: string }[]

// 3. INSERT — o TS exige email e nome; id e criadoEm são opcionais.
const [novo] = await db
  .insert(users)
  .values({ email: 'ana@ex.com', nome: 'Ana' })
  .returning();
// novo: { id: number; email: string; nome: string; criadoEm: Date }

Renomear nome para nomeCompleto no schema quebra, no compilador, todas as queries que referenciam users.nome — sem etapa intermediária entre o erro e a visibilidade. Esse é o sentido prático de "end-to-end": a fonte da verdade tem um caminho único e direto até cada ponto de uso.

Capítulo 2

Setup e instalação

Drizzle se instala em três partes: o runtime que você importa no código da aplicação, o driver do banco de dados de sua escolha, e o kit CLI que gera migrations e sobe o Studio. Este capítulo configura o projeto do zero — pacotes, variáveis de ambiente, o arquivo drizzle.config.ts e a instância db que os capítulos seguintes vão usar.

# Os três pacotes

drizzle-orm é o runtime: query builder, schema toolkit, relational queries. drizzle-kit é o CLI de desenvolvimento: gera arquivos de migration a partir do schema, aplica migrations, abre o Studio. drizzle-kit nunca vai para produção — é sempre devDependency. O terceiro pacote é o driver do banco: Drizzle não vem com driver embutido, o que permite usar o cliente mais adequado ao ambiente (Node.js tradicional, Neon serverless, Supabase, etc.). O Capítulo 3 detalha cada driver; aqui usamos postgres (postgres.js) como padrão para Node.js 22 LTS.

terminal
# Dependências de produção
npm install drizzle-orm postgres

# Dependência de desenvolvimento
npm install --save-dev drizzle-kit

# TypeScript e utilitários de execução
npm install --save-dev typescript tsx @types/node
Nota
drizzle-kit vai em devDependencies. Em produção, a aplicação só precisa de drizzle-orm e do driver. Nenhum passo de build envolve o kit — ele só é chamado durante o desenvolvimento e em pipelines de CI para aplicar migrations antes do deploy.

Atenção
O operador ! de non-null assertion (process.env.DATABASE_URL!) silencia o TypeScript mas não valida em runtime — se a variável estiver ausente, o erro chega como mensagem confusa, longe do ponto de leitura. Em produção, valide explicitamente antes de criar o cliente:

# drizzle.config.ts

O drizzle.config.ts é lido exclusivamente pelo kit — não pelo runtime da aplicação. Ele informa onde estão o schema e as migrations, qual dialeto de banco usar, e como se conectar para o push e o Studio.

drizzle.config.ts
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  schema:   './src/db/schema/index.ts',
  out:      './drizzle',
  dialect:  'postgresql',
  dbCredentials: {
    url: process.env.DATABASE_URL!,
  },
});

Os campos mínimos obrigatórios são schema, out e dialect. O campo dbCredentials.url é necessário apenas para os comandos que abrem conexão real: push, pull, studio e migrate. O comando generate lê apenas o schema local e não precisa de banco acessível.

Dica
Ambientes diferentes podem ter arquivos de configuração separados: drizzle.config.staging.ts, drizzle.config.prod.ts. Passe o arquivo desejado com drizzle-kit migrate --config drizzle.config.prod.ts. Útil para separar credenciais e pastas de saída sem lógica condicional no arquivo principal.

# A instância db

A instância db é o objeto central do Drizzle: recebe o cliente do driver e, opcionalmente, o schema. Passar o schema é obrigatório para usar as relational queries (db.query.*) — sem ele, apenas o query builder está disponível. A instância é criada uma vez e exportada como singleton.

src/db/index.ts
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';
import * as schema from './schema';

if (!process.env.DATABASE_URL) {
  throw new Error('DATABASE_URL não definida');
}

const client = postgres(process.env.DATABASE_URL);

export const db = drizzle(client, { schema });
// db.query.users, db.query.orders etc. disponíveis
// porque o schema foi passado na construção.
Performance
O cliente postgres mantém um pool de conexões por padrão (10 conexões). Em ambientes serverless, onde cada função tem seu próprio processo, esse pool não é compartilhado entre invocações — cada execução abre seu próprio conjunto de conexões ao banco. A solução é um pooler externo como PgBouncer ou o pooler gerenciado de Neon/Supabase, com o driver configurado para max: 1 em funções de vida curta. O Capítulo 3 detalha cada cenário.

Capítulo 3

Drivers e conexão

Drizzle não vem com driver embutido — você escolhe o cliente de banco mais adequado ao seu ambiente e passa para a função drizzle(). Essa separação mantém o bundle enxuto e permite trocar de driver sem reescrever queries. Este capítulo cobre os drivers mais usados com PostgreSQL: postgres.js, node-postgres, Neon serverless e Supabase, com atenção às diferenças de pooling e suporte a transações.

# Por que o driver é separado

Cada ambiente tem necessidades diferentes: um servidor Node.js de longa duração se beneficia de um pool de conexões TCP persistentes; uma função Cloudflare Worker não pode abrir conexões TCP e precisa de HTTP ou WebSocket; um script de seed quer uma única conexão simples. Em vez de empacotar todos esses casos, Drizzle expõe um adaptador por driver — o import path muda (drizzle-orm/postgres-js, drizzle-orm/node-postgres, etc.), mas a API do db que você usa no código da aplicação é idêntica.

Nota
O import path do adaptador (drizzle-orm/postgres-js, drizzle-orm/neon-http etc.) determina qual wrapper interno o Drizzle usa para traduzir queries ao protocolo do driver. Fora isso, db.select(), db.insert() e db.query.* funcionam da mesma forma independentemente do driver escolhido.

# postgres.js — padrão para Node.js

O postgres (postgres.js) é o driver recomendado para aplicações Node.js tradicionais. Ele mantém um pool de conexões nativo, tem suporte completo a prepared statements e lida bem com tipos PostgreSQL customizados. É o driver usado nos exemplos deste manual.

src/db/index.ts
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';
import * as schema from './schema';

const client = postgres(process.env.DATABASE_URL!, {
  max: 10,           // conexões máximas no pool
  idle_timeout: 20,  // fecha conexões ociosas após 20 s
  connect_timeout: 10,
});

export const db = drizzle(client, { schema });

# node-postgres (pg)

O pg é o driver histórico do ecossistema Node.js/PostgreSQL e ainda a escolha dominante em bases de código legadas. O Drizzle aceita tanto Client (uma conexão) quanto Pool (múltiplas). Para aplicações reais, sempre use Pool.

src/db/index.ts
import { drizzle } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';
import * as schema from './schema';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL!,
  max: 10,
});

export const db = drizzle(pool, { schema });

# Neon serverless

Neon oferece dois modos de conexão. O modo HTTP envia cada query como uma requisição HTTP — sem TCP, compatível com qualquer edge runtime, mas sem suporte a transações interativas. O modo WebSocket abre uma conexão persistente e suporta transações completas, sendo necessário quando db.transaction() está em uso.

src/db/neon-http.ts — sem transações, ideal para edge
import { drizzle } from 'drizzle-orm/neon-http';
import { neon } from '@neondatabase/serverless';
import * as schema from './schema';

const sql = neon(process.env.DATABASE_URL!);
export const db = drizzle(sql, { schema });
src/db/neon-ws.ts — com transações, Node.js e edge com ws
import { drizzle } from 'drizzle-orm/neon-serverless';
import { Pool, neonConfig } from '@neondatabase/serverless';
import ws from 'ws';
import * as schema from './schema';

// Necessário em Node.js — edge runtimes já têm WebSocket nativo.
neonConfig.webSocketConstructor = ws;

const pool = new Pool({ connectionString: process.env.DATABASE_URL! });
export const db = drizzle(pool, { schema });
Atenção
O driver Neon HTTP (neon-http) não suporta db.transaction() — cada query é uma requisição HTTP independente e não há como agrupar em uma sessão. Se o código usa transações, troque para neon-serverless com WebSocket. A mesma restrição vale para qualquer driver HTTP-only.

# Supabase

Supabase usa PostgreSQL internamente e aceita qualquer driver padrão. A atenção fica no modo de conexão: a string de Session mode (porta 5432) mantém prepared statements e funciona com postgres.js sem modificações; a string de Transaction mode (porta 6543) passa pelo PgBouncer, que não suporta prepared statements — nesse caso é obrigatório passar prepare: false.

src/db/index.ts — Supabase Transaction mode (porta 6543)
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';
import * as schema from './schema';

const client = postgres(process.env.DATABASE_URL!, {
  prepare: false, // obrigatório no Transaction mode — PgBouncer não aceita prepared statements
});

export const db = drizzle(client, { schema });

# Pooling e ambientes serverless

O modelo de pool do banco de dados muda radicalmente entre ambientes de longa duração e funções serverless. Em um servidor Node.js convencional, um pool de 10 conexões é criado uma vez e reutilizado por todas as requisições do processo. Em uma função serverless, cada instância tem seu próprio processo — se cada uma abrir 10 conexões, 100 instâncias simultâneas abrem 1.000 conexões, esgotando rapidamente os limites do PostgreSQL.

src/db/index.ts — configuração para funções serverless
const client = postgres(process.env.DATABASE_URL!, {
  max: 1,             // uma conexão por função — pooler externo cuida do resto
  idle_timeout: 20,
  max_lifetime: 60 * 30, // recicla conexões a cada 30 min
});
Performance
Em produção serverless, use um pooler externo entre a aplicação e o PostgreSQL: PgBouncer (auto-hospedado), ou os poolers gerenciados de Neon e Supabase. O pooler mantém um conjunto fixo de conexões reais ao banco e multiplexa centenas de conexões de curta duração das funções. Com isso, o driver da função pode usar max: 1 com segurança.

Capítulo 4

Drizzle Kit — CLI de migrations

Drizzle Kit é o CLI de desenvolvimento que fecha o ciclo schema → banco. Ele lê o schema TypeScript, compara com o estado anterior, e gera os arquivos SQL que descrevem a diferença. Esses arquivos viajam no repositório e são aplicados por um comando separado — em qualquer ambiente, com rastreamento completo. Este capítulo cobre os cinco comandos do kit e como encaixá-los no fluxo de trabalho por ambiente.

# O que o kit faz — e o que não faz

O kit opera exclusivamente em tempo de desenvolvimento e CI: nunca é importado pelo código da aplicação em runtime. Ele não executa queries de negócio, não faz ORM, não toca nas tabelas além de criar e alterar estrutura. Seu único produto são arquivos .sql versionados e o estado de snapshot que permite calcular diffs futuros.

Nota
O kit mantém uma tabela de controle no banco (__drizzle_migrations por padrão) para registrar quais migrations já foram aplicadas — o mesmo padrão de ferramentas como Flyway e Liquibase. Cada migration tem um hash; o kit não reaplicará um arquivo já registrado.

# generate — criando arquivos de migration

O comando generate lê o schema TypeScript local, compara com o snapshot anterior em drizzle/meta/, e escreve um novo arquivo .sql com as instruções DDL necessárias. Ele não conecta ao banco — opera apenas em arquivos locais.

terminal

npx drizzle-kit generate

# Nomear a migration para facilitar o histórico:
npx drizzle-kit generate --name add_categoria_id

O resultado é uma pasta drizzle/ com arquivos numerados sequencialmente e snapshots em meta/:

# migrate — aplicando migrations

O comando migrate lê os arquivos .sql em drizzle/ e aplica os ainda não registrados na tabela de controle. É o comando usado em produção e em pipelines de CI — previsível, auditável, reversível via controle de versão.

terminal
# Aplica migrations pendentes ao banco apontado em DATABASE_URL.
npx drizzle-kit migrate

# Com arquivo de config específico (staging, produção):
npx drizzle-kit migrate --config drizzle.config.prod.ts

Em vez de chamar o kit diretamente em produção, muitos projetos preferem um script TypeScript que usa a função migrate() do runtime — isso evita instalar drizzle-kit no ambiente de produção:

import postgres from 'postgres';

Dica

# push — sync direto em desenvolvimento

O comando push leva o schema TypeScript direto ao banco, sem gerar arquivos de migration. É a ferramenta de iteração rápida em desenvolvimento local: adicionar uma coluna, testar, ajustar — sem acumular arquivos SQL de rascunho.

terminal
# Sincroniza o schema TypeScript com o banco diretamente.
npx drizzle-kit push
Atenção
push não gera histórico de migrations e pode executar operações destrutivas (renomear coluna vira DROP + ADD, por exemplo). Nunca use em staging ou produção — dados podem ser perdidos sem possibilidade de rollback rastreável. O fluxo correto para esses ambientes é sempre generate + commit + migrate.

# pull — engenharia reversa

O comando pull conecta a um banco existente, lê seu schema DDL, e gera os arquivos TypeScript correspondentes em drizzle/schema.ts. É o ponto de entrada para projetos que já têm um banco e querem adotar Drizzle sem reescrever o schema do zero.

Capítulo 5

Tabelas e colunas

Em Drizzle, o schema relacional é declarado em TypeScript puro usando pgTable e funções de coluna. Não há DSL externa, não há decorators, não há arquivo .prisma — o mesmo arquivo que o compilador lê é o que o kit usa para gerar migrations. Este capítulo percorre a API de declaração de tabelas, os tipos de coluna disponíveis para PostgreSQL, o mapeamento entre nomes TypeScript e nomes no banco, e as generated columns.

# pgTable — a unidade básica

pgTable recebe o nome da tabela no banco e um objeto de definição de colunas. Cada propriedade do objeto é uma coluna; o nome da propriedade é o identificador TypeScript (camelCase), e o primeiro argumento da função de coluna é o nome real no banco (snake_case).

schema/users.ts
import { pgTable, serial, varchar, timestamp } from 'drizzle-orm/pg-core';

export const users = pgTable('users', {
  // propriedade TS  nome no banco   tipo e modificadores
  id:        serial('id').primaryKey(),
  email:     varchar('email', { length: 255 }).notNull().unique(),
  nome:      varchar('nome',  { length: 120 }).notNull(),
  criadoEm: timestamp('criado_em').defaultNow().notNull(),
});

export type User    = typeof users.$inferSelect;
export type NewUser = typeof users.$inferInsert;

O mapeamento é explícito: você controla o nome no banco. Isso elimina surpresas quando o kit gera migrations — o nome que aparece no .sql é exatamente o que você declarou como primeiro argumento.

Dica
Exporte sempre os tipos $inferSelect e $inferInsert junto com a tabela. Eles substituem qualquer tipagem manual e se atualizam automaticamente quando o schema muda — sem regeneração de código.

# Nomes TypeScript vs nomes no banco

A convenção em TypeScript é camelCase; a convenção em PostgreSQL é snake_case. Drizzle trata os dois de forma independente: o nome da propriedade é o identificador usado nas queries TypeScript, e o string passado para a função de coluna é o nome real da coluna no banco.

mapeamento de nomes
// No TypeScript: users.criadoEm  (camelCase — o que você escreve nas queries)
// No banco:      criado_em       (snake_case — o que aparece no SQL gerado)

const recentes = await db
  .select()
  .from(users)
  .orderBy(users.criadoEm); // gera: ORDER BY "criado_em"

# Generated columns

Colunas geradas são calculadas pelo banco automaticamente a partir de outras colunas — nunca são gravadas diretamente pelo aplicativo. Em Drizzle, são declaradas com .generatedAlwaysAs() passando uma expressão SQL. O caso mais comum no schema de e-commerce é o campo de busca full-text:

schema/products.ts — com campo de busca gerado
import { pgTable, serial, varchar, tsvector } from 'drizzle-orm/pg-core';
import { sql } from 'drizzle-orm';

export const products = pgTable('products', {
  id:    serial('id').primaryKey(),
  nome:  varchar('nome', { length: 255 }).notNull(),

  // Calculada pelo PostgreSQL — nunca inserida ou atualizada pelo app.
  busca: tsvector('busca')
    .generatedAlwaysAs(
      sql`to_tsvector('portuguese', nome)`
    ),
});
Nota
O campo busca aparece no tipo $inferSelect como string mas está ausente do $inferInsert — o TypeScript impede que você tente gravá-lo acidentalmente. O índice GIN sobre esse campo é declarado no Capítulo 8.

Capítulo 6

Constraints e defaults

Constraints são as regras de integridade que o banco aplica em todas as operações — independente de qual aplicação escreve. Drizzle declara essas regras no mesmo arquivo TypeScript do schema, gerando o DDL correto nas migrations. Este capítulo cobre notNull, default, unique, check, chaves estrangeiras com references() e chaves primárias compostas.

# notNull, default e $onUpdateFn

Os modificadores encadeiam diretamente na função de coluna. .notNull() gera NOT NULL no DDL. .default(valor) gera DEFAULT valor. .defaultNow() é um atalho para DEFAULT now(). O helper .$onUpdateFn() é exclusivo do Drizzle — ele não gera SQL no banco, mas injeta o valor automaticamente em todo UPDATE feito pela instância db.

schema/products.ts — defaults e notNull
import { pgTable, serial, varchar, boolean, integer, timestamp, numeric } from 'drizzle-orm/pg-core';

export const products = pgTable('products', {
  id:           serial('id').primaryKey(),
  nome:         varchar('nome', { length: 255 }).notNull(),
  preco:        numeric('preco', { precision: 10, scale: 2 }).notNull(),
  ativo:        boolean('ativo').notNull().default(true),
  estoque:      integer('estoque').notNull().default(0),
  criadoEm:    timestamp('criado_em').notNull().defaultNow(),

  // Não gera SQL no banco — o Drizzle injeta o valor em cada UPDATE.
  atualizadoEm: timestamp('atualizado_em').notNull().$onUpdateFn(() => new Date()),
});
Nota
.$onUpdateFn() só funciona para updates feitos via db.update() — não dispara em SQL executado diretamente no banco ou por outras aplicações. Para um updated_at garantido independentemente do caminho de escrita, use um trigger PostgreSQL ou uma generated column com now().

# unique — coluna e tabela

Um .unique() encadeado na coluna cria um índice único simples. Para constraints únicas compostas — que envolvem mais de uma coluna — o lugar correto é o terceiro argumento de pgTable, que recebe uma função retornando um array de constraints de tabela.

schema/users.ts — unique simples e composto
import { pgTable, serial, varchar, unique } from 'drizzle-orm/pg-core';

export const users = pgTable('users', {
  id:    serial('id').primaryKey(),
  email: varchar('email', { length: 255 }).notNull().unique(), // único simples
  cpf:   varchar('cpf',   { length: 14  }).notNull(),
  nome:  varchar('nome',  { length: 120 }).notNull(),
}, (table) => [
  // Unique nomeado sobre múltiplas colunas
  unique('users_email_cpf_uq').on(table.email, table.cpf),
]);
Dica
Nomeie as constraints explicitamente — unique('users_email_cpf_uq') em vez de deixar o PostgreSQL gerar o nome. Nomes previsíveis facilitam identificar a constraint em erros de runtime (duplicate key value violates unique constraint "users_email_cpf_uq") e evitam surpresas em migrations quando a constraint precisa ser alterada.

# check — constraint de verificação

Constraints CHECK são validadas pelo banco em todo INSERT e UPDATE, independente do caminho de escrita. Em Drizzle, são declaradas com a função check() no terceiro argumento de pgTable, passando o nome da constraint e uma expressão SQL.

schema/products.ts — check constraints
import { pgTable, serial, numeric, integer, check } from 'drizzle-orm/pg-core';
import { sql } from 'drizzle-orm';

export const products = pgTable('products', {
  id:      serial('id').primaryKey(),
  preco:   numeric('preco',   { precision: 10, scale: 2 }).notNull(),
  estoque: integer('estoque').notNull().default(0),
}, (table) => [
  check('preco_positivo',      sql`${table.preco}   > 0`),
  check('estoque_nao_negativo', sql`${table.estoque} >= 0`),
]);

# Chaves estrangeiras com references()

A forma mais comum de FK é encadear .references() diretamente na coluna. O argumento é uma função que retorna a coluna referenciada — a função é necessária para quebrar referências circulares entre módulos que ainda não foram totalmente carregados.

schema/orders.ts — FK com references()
import { pgTable, serial, integer, varchar, timestamp } from 'drizzle-orm/pg-core';
import { users } from './users';

export const orders = pgTable('orders', {
  id:        serial('id').primaryKey(),
  userId:    integer('user_id')
               .notNull()
               .references(() => users.id, { onDelete: 'cascade' }),
  status:    varchar('status', { length: 50 }).notNull().default('pendente'),
  criadoEm: timestamp('criado_em').defaultNow().notNull(),
});

# onDelete e onUpdate

As ações referenciais controlam o que acontece com as linhas dependentes quando o registro pai é deletado ou atualizado. Drizzle aceita as mesmas ações do PostgreSQL como strings no segundo argumento de references():

schema/products.ts — ações referenciais
categoriaId: integer('categoria_id')
  .references(() => categories.id, {
    onDelete: 'set null',  // produto permanece, categoriaId vira null
    onUpdate: 'cascade',   // se o id da categoria mudar, atualiza aqui
  }),
Atenção
onDelete: 'cascade' deleta silenciosamente todos os registros filhos quando o pai é removido. Em tabelas de negócio como orders, prefira 'restrict' (impede a deleção do pai) ou soft delete no nível da aplicação. Reserve cascade para dados auxiliares sem valor próprio — logs de sessão, tokens temporários, registros de auditoria.

# primaryKey composta

Tabelas que não têm uma coluna de ID natural — como order_items, cuja identidade é a combinação de pedido e produto — usam chave primária composta. Em Drizzle, isso vai no terceiro argumento de pgTable com a função primaryKey:

schema/orders.ts — order_items com PK composta
import { pgTable, integer, numeric, primaryKey } from 'drizzle-orm/pg-core';
import { orders } from './orders';
import { products } from './products';

export const orderItems = pgTable('order_items', {
  orderId:    integer('order_id')
                .notNull()
                .references(() => orders.id,    { onDelete: 'cascade' }),
  productId:  integer('product_id')
                .notNull()
                .references(() => products.id,  { onDelete: 'restrict' }),
  quantidade: integer('quantidade').notNull(),
  precoUnit:  numeric('preco_unit', { precision: 10, scale: 2 }).notNull(),
}, (table) => [
  primaryKey({ columns: [table.orderId, table.productId] }),
]);

export type OrderItem    = typeof orderItems.$inferSelect;
export type NewOrderItem = typeof orderItems.$inferInsert;
Performance

Em cargas altas de inserção em lote, esse overhead pode ser significativo. Capítulo 7

Relações — navegação tipada

Em Drizzle, "relação" é um conceito de duas camadas que convém distinguir desde o primeiro contato. A integridade referencial — o que o banco impõe — vem das chaves estrangeiras declaradas com references() no Capítulo 6. A camada de navegação — o que o TypeScript entende para permitir db.query.users.findMany({ with: { orders: true } }) — é declarada com a função relations(). As duas são independentes; este capítulo cobre a segunda, sem perder de vista como ela se apoia (ou não) na primeira.

# references() e relations() — duas camadas distintas

A confusão mais comum em Drizzle é assumir que references() e relations() são duas formas de dizer a mesma coisa. Não são. references() gera FOREIGN KEY no DDL — vai para a migration, é executado no banco, garante integridade em qualquer caminho de escrita. relations() não gera nada no banco: é puramente um mapa TypeScript que o relational query builder usa para resolver with, agrupar resultados em árvore e inferir tipos.

É perfeitamente possível ter um sem o outro. Um schema sem relations() mas com references() funciona normalmente — o query builder com joins explícitos resolve tudo, apenas as relational queries (db.query.*) ficam indisponíveis. Um schema com relations() mas sem references() também funciona — as queries relacionais usam os campos declarados em fields e references para fazer o join, e o banco simplesmente não impõe integridade. Em projetos reais, sempre declare as duas: FKs no Capítulo 6 para o banco, relations() aqui para a aplicação.

As duas camadas, lado a lado
references() — vai para o DDL → executado no banco → impõe integridade em todo INSERT/UPDATE/DELETE.
relations() — fica em TypeScript → consumido por db.query → permite with, tipos aninhados, navegação.

# one e many — os dois lados de uma relação

A função relations recebe a tabela e uma função que retorna o mapa de relações. Essa função destrutura { one, many } — os dois únicos tipos de relação que existem. one declara o lado "muitos→um" (a coluna FK fica nesta tabela e aponta para uma única linha da outra). many declara o lado "um→muitos" (esta tabela é referenciada por várias linhas da outra). Toda relação 1:N gera os dois: um one no lado filho e um many no lado pai.

# 1:N — categorias e produtos

Uma categoria tem muitos produtos; cada produto pertence a uma categoria. A FK está em products.categoria_id apontando para categories.id — esse é o lado one. O lado many só precisa do nome da tabela do outro lado:

schema/categories.ts
import { pgTable, serial, varchar, integer } from 'drizzle-orm/pg-core';
import { relations } from 'drizzle-orm';
import { products } from './products';

export const categories = pgTable('categories', {
  id:   serial('id').primaryKey(),
  nome: varchar('nome', { length: 100 }).notNull(),
});

export const categoriesRelations = relations(categories, ({ many }) => ({
  products: many(products), // uma categoria, muitos produtos
}));
schema/products.ts
import { pgTable, serial, varchar, integer } from 'drizzle-orm/pg-core';
import { relations } from 'drizzle-orm';
import { categories } from './categories';

export const products = pgTable('products', {
  id:          serial('id').primaryKey(),
  nome:        varchar('nome', { length: 255 }).notNull(),
  categoriaId: integer('categoria_id').references(() => categories.id),
});

export const productsRelations = relations(products, ({ one }) => ({
  categoria: one(categories, {
    fields:     [products.categoriaId], // coluna desta tabela
    references: [categories.id],      // coluna apontada na outra
  }),
}));

O lado many tem apenas o nome da tabela porque a informação de chave estrangeira já está no lado one — Drizzle usa essa única declaração de fields/references para resolver os dois sentidos da navegação. Depois disso, ambos os lados funcionam em db.query:

uso das relações
// Do lado da categoria: pegar todos os produtos
const cat = await db.query.categories.findFirst({
  where: eq(categories.id, 1),
  with: { products: true },
});
// cat: { id, nome, products: Product[] } | undefined

// Do lado do produto: pegar a categoria
const prod = await db.query.products.findFirst({
  where: eq(products.id, 42),
  with: { categoria: true },
});
// prod: { id, nome, categoriaId, categoria: Category | null } | undefined

# 1:1 — usuários e perfis

Uma relação 1:1 é, mecanicamente, um caso especial de 1:N — uma FK em um lado, garantida como única (pela própria PK ou por unique). Em Drizzle, isso significa one dos dois lados. O lado que tem a FK declara fields/references; o lado oposto declara apenas a tabela:

schema/user-profiles.ts
export const userProfiles = pgTable('user_profiles', {
  userId:    integer('user_id')
                .primaryKey()
                .references(() => users.id, { onDelete: 'cascade' }),
  bio:       text('bio'),
  avatarUrl: varchar('avatar_url', { length: 500 }),
});

export const userProfilesRelations = relations(userProfiles, ({ one }) => ({
  user: one(users, {
    fields:     [userProfiles.userId],
    references: [users.id],
  }),
}));

// No arquivo de users:
export const usersRelations = relations(users, ({ one }) => ({
  profile: one(userProfiles), // lado sem FK — apenas referencia a tabela
}));

# N:N — produtos e pedidos via order_items

Não existe relação many-to-many "direta" no modelo relacional — toda N:N é, na prática, duas relações 1:N que se encontram em uma tabela de junção. No schema de e-commerce, a junção entre orders e products é a própria order_items — que tem campos próprios (quantidade, precoUnit) e merece existir como entidade. Drizzle reflete essa realidade: você declara as três tabelas e três blocos de relations(), sem nenhuma macro mágica para "many-to-many".

schema/orders.ts — todas as relações da junção
export const ordersRelations = relations(orders, ({ one, many }) => ({
  user:  one(users, { fields: [orders.userId], references: [users.id] }),
  items: many(orderItems),
}));

export const orderItemsRelations = relations(orderItems, ({ one }) => ({
  order:   one(orders,   { fields: [orderItems.orderId],   references: [orders.id]   }),
  product: one(products, { fields: [orderItems.productId], references: [products.id] }),
}));

export const productsRelations = relations(products, ({ one, many }) => ({
  categoria:  one(categories, {
    fields: [products.categoriaId], references: [categories.id],
  }),
  orderItems: many(orderItems),
}));

Com essas declarações, a travessia natural de N:N — buscar um usuário com seus pedidos e os produtos de cada pedido — é uma única query relacional:

travessia N:N
const u = await db.query.users.findFirst({
  where: eq(users.id, 1),
  with: {
    orders: {
      with: {
        items: {
          with: { product: true },
        },
      },
    },
  },
});
// u.orders[0].items[0].product.nome — tipo navegável até a folha

# Self-reference — categorias com parent

Uma tabela que referencia a si mesma — categorias com subcategorias, comentários com respostas, funcionários com gestor — apresenta um problema novo: o mesmo par de tabelas (no caso, categories com categories) aparece nos dois lados da relação. Drizzle precisa de um nome de relação para diferenciar quem é o "pai" e quem é o "filho":

schema/categories.ts — self-reference
export const categories = pgTable('categories', {
  id:       serial('id').primaryKey(),
  nome:     varchar('nome', { length: 100 }).notNull(),
  parentId: integer('parent_id').references((): AnyPgColumn => categories.id),
});

export const categoriesRelations = relations(categories, ({ one, many }) => ({
  parent:   one(categories, {
    fields:       [categories.parentId],
    references:   [categories.id],
    relationName: 'category_tree',
  }),
  children: many(categories, {
    relationName: 'category_tree', // mesmo nome para ligar os dois lados
  }),
}));
Atenção
No .references() de uma self-reference, o TypeScript pode falhar em inferir o tipo da coluna que ainda não terminou de ser declarada. A solução padrão é anotar o tipo de retorno da função como AnyPgColumn (importado de drizzle-orm/pg-core) — isso quebra o ciclo de inferência sem perder type-safety nas queries.

# Múltiplas relações entre as mesmas tabelas

Quando duas tabelas se relacionam por mais de uma chave estrangeira — um pedido que tem tanto userId (cliente) quanto atendenteId (vendedor), ambos apontando para users — o relationName é obrigatório também, para que Drizzle saiba qual FK corresponde a qual lado:

schema/orders.ts — duas FKs para a mesma tabela
export const ordersRelations = relations(orders, ({ one }) => ({
  cliente:   one(users, {
    fields:       [orders.userId],
    references:   [users.id],
    relationName: 'order_cliente',
  }),
  atendente: one(users, {
    fields:       [orders.atendenteId],
    references:   [users.id],
    relationName: 'order_atendente',
  }),
}));

export const usersRelations = relations(users, ({ many }) => ({
  pedidos:      many(orders, { relationName: 'order_cliente'   }),
  atendimentos: many(orders, { relationName: 'order_atendente' }),
}));
Dica
Use relationName sempre que houver ambiguidade — ou seja, sempre que o par de tabelas envolvidas se repete na mesma direção. Sem isso, Drizzle não consegue resolver qual many corresponde a qual one e o erro aparece em tempo de compilação como um tipo opaco no resultado das relational queries.

# Como o Drizzle resolve relational queries

Quando você escreve db.query.users.findMany({ with: { orders: true } }), Drizzle não gera um LEFT JOIN tradicional — gera uma subquery lateral que retorna os pedidos agregados como um array JSON dentro de cada linha de usuário. A motivação é evitar a "explosão cartesiana": se um usuário tem 50 pedidos e cada pedido tem 10 itens, um JOIN retorna 500 linhas; a subquery aninhada retorna 1 linha por usuário com a árvore completa em JSON.

Performance
A estratégia de subqueries lateralizadas paga um preço fixo de serialização JSON no banco, mas evita a multiplicação de linhas no fio. Para a maioria dos casos de leitura aninhada, é a escolha mais eficiente. O query builder com leftJoin explícito continua sendo a opção certa quando você quer agregações horizontais ou precisa de controle fino sobre o plano de execução — o tema do Capítulo 15.

Capítulo 8

Índices no schema

Em Drizzle, índices são declarados no terceiro argumento de pgTable — o mesmo lugar onde vivem constraints de tabela. O kit traduz cada declaração em CREATE INDEX nas migrations. Este capítulo cobre index simples e composto, uniqueIndex, índices em expressões, índices parciais com where, e os índices GIN necessários para busca full-text e queries em JSONB.

# Índices no terceiro argumento

A função passada como terceiro argumento de pgTable recebe a tabela como parâmetro e retorna um array — esse array mistura constraints (do Capítulo 6) e índices, sem distinção de ordem. As funções index e uniqueIndex vêm de drizzle-orm/pg-core, e o método .on() recebe as colunas a indexar.

schema/products.ts — índices simples e composto
import { pgTable, serial, varchar, integer, boolean, index } from 'drizzle-orm/pg-core';

export const products = pgTable('products', {
  id:          serial('id').primaryKey(),
  nome:        varchar('nome', { length: 255 }).notNull(),
  categoriaId: integer('categoria_id'),
  ativo:       boolean('ativo').notNull().default(true),
}, (table) => [
  index('products_nome_idx').on(table.nome),
  index('products_categoria_idx').on(table.categoriaId),

  // Índice composto — ordem das colunas importa para o plano de execução
  index('products_categoria_ativo_idx').on(table.categoriaId, table.ativo),
]);
Ordem em índices compostos
PostgreSQL usa um índice composto da esquerda para a direita. Um índice em (categoria_id, ativo) acelera queries filtrando por categoria_id sozinho ou por ambos, mas não acelera queries filtrando apenas por ativo. Coloque sempre a coluna mais seletiva (com mais valores distintos) primeiro.

# uniqueIndex vs unique

uniqueIndex e .unique() entregam a mesma garantia de unicidade, mas têm intenções ligeiramente diferentes. .unique() é uma constraint — aparece em mensagens de erro como "violação de constraint". uniqueIndex é um índice — pode receber expressões, condições parciais e configurações específicas de índice. Para casos simples de unicidade em uma coluna, prefira .unique(); para qualquer cenário que combine unicidade com expressão ou filtro, use uniqueIndex.

schema/users.ts — unicidade case-insensitive
import { pgTable, serial, varchar, uniqueIndex } from 'drizzle-orm/pg-core';
import { sql } from 'drizzle-orm';

export const users = pgTable('users', {
  id:    serial('id').primaryKey(),
  email: varchar('email', { length: 255 }).notNull(),
}, (table) => [
  // Unicidade ignorando case — 'Ana@ex.com' e 'ana@ex.com' contam como duplicatas
  uniqueIndex('users_email_lower_uq')
    .on(sql`lower(${table.email})`),
]);

# Índices em expressões

Quando uma query filtra por uma transformação da coluna — LOWER(email), DATE(criado_em), (metadata->>'cor') — o índice normal sobre a coluna bruta não ajuda. PostgreSQL só usa o índice se a expressão da query bate exatamente com a expressão do índice. Em Drizzle, expressões vão em template sql passado ao .on():

schema/products.ts — índices em expressões
}, (table) => [
  // Para queries com WHERE lower(nome) LIKE 'caf%'
  index('products_nome_lower_idx').on(sql`lower(${table.nome})`),

  // Para queries em campo JSONB — extrai 'cor' antes de indexar
  index('products_cor_idx').on(sql`(${table.metadata} ->> 'cor')`),
]);

# Índices parciais com where

Um índice parcial indexa apenas as linhas que satisfazem um predicado. É a ferramenta certa quando a maioria das queries filtra um subconjunto previsível — pedidos pendentes, produtos ativos, sessões não expiradas. O índice fica menor, mais rápido de manter, e o plano de execução evita varreduras sobre dados que nunca seriam consultados.

schema/orders.ts — índice parcial
}, (table) => [
  // Indexa apenas pedidos pendentes — fila de processamento típica
  index('orders_pendentes_idx')
    .on(table.criadoEm)
    .where(sql`${table.status} = 'pendente'`),
]);
Dica
Para que PostgreSQL use o índice parcial, a query precisa conter um predicado implicado pelo WHERE do índice. WHERE status = 'pendente' AND criado_em > ... usa o índice; WHERE criado_em > ... (sem o filtro de status) não usa. Rode EXPLAIN ANALYZE para confirmar — o Capítulo 22 mostra como executar isso direto pelo Drizzle.

# GIN para JSONB e busca full-text

Índices B-tree (o padrão) não funcionam para operações em JSONB nem para o operador @@ de busca textual em tsvector. Para esses casos, PostgreSQL oferece o tipo GIN (Generalized Inverted Index), que indexa cada elemento interno do valor — todas as chaves de um objeto JSONB, todos os lexemas de um tsvector. Em Drizzle, escolhe-se o tipo de índice com .using('gin', ...):

schema/products.ts — índices GIN
import { pgTable, serial, varchar, jsonb, tsvector, index } from 'drizzle-orm/pg-core';
import { sql } from 'drizzle-orm';

export const products = pgTable('products', {
  id:       serial('id').primaryKey(),
  nome:     varchar('nome', { length: 255 }).notNull(),
  metadata: jsonb('metadata'),
  busca:    tsvector('busca').generatedAlwaysAs(
    sql`to_tsvector('portuguese', nome)`
  ),
}, (table) => [
  // GIN para queries do tipo WHERE metadata @> '{"cor": "azul"}'
  index('products_metadata_gin').using('gin', table.metadata),

  // GIN para busca full-text com to_tsquery
  index('products_busca_gin').using('gin', table.busca),
]);

Com esses índices, as queries de busca passam a usar o GIN automaticamente — o operador @@ com to_tsquery consulta o índice de busca; o operador @> (contém) e ? (chave existe) consultam o índice de metadata.

# Como nomear índices

A convenção que este manual usa segue um padrão estável: <tabela>_<coluna_ou_propósito>_<tipo>. products_nome_idx, users_email_lower_uq, products_busca_gin. Nomes previsíveis ajudam em três cenários: leitura do plano de execução (EXPLAIN menciona o índice usado), depuração de migrations (o diff é compreensível), e operações ad-hoc (DROP INDEX sem ambiguidade).

Custo de manutenção
Cada índice acelera leituras na coluna indexada mas torna INSERT, UPDATE e DELETE mais lentos — toda escrita atualiza todos os índices afetados. Em tabelas com cargas altas de escrita, mantenha apenas índices que respaldam queries reais e medidas. EXPLAIN ANALYZE mostra quais índices estão sendo efetivamente usados; índices nunca usados são puro custo. Para identificar índices ociosos em produção, consulte pg_stat_user_indexes.

Enums e tipos customizados

Drizzle oferece três caminhos para ir além dos tipos de coluna nativos: pgEnum cria um tipo enumerado real no PostgreSQL, com verificação de valor garantida pelo banco; customType encapsula qualquer tipo do banco com conversores TypeScript; e o modificador .$type() sobrescreve o tipo inferido de uma coluna existente — útil para tipar JSONB e arrays sem criar um tipo novo no banco. Este capítulo cobre os três, usando o schema de e-commerce como terreno.

# pgEnum — enums nativos do PostgreSQL

pgEnum cria um tipo ENUM no banco — não é só uma validação TypeScript, mas um objeto de banco de dados com um nome e um conjunto fixo de valores aceitos. Qualquer tentativa de inserir um valor fora do conjunto falha no banco, independente do caminho de escrita.

schema/orders.ts — enum de status
import { pgEnum, pgTable, serial, integer, timestamp } from 'drizzle-orm/pg-core';

// Declarado fora do pgTable — é um tipo de banco independente.
export const statusPedidoEnum = pgEnum('status_pedido', [
  'pendente',
  'pago',
  'enviado',
  'entregue',
  'cancelado',
]);

export const orders = pgTable('orders', {
  id:        serial('id').primaryKey(),
  userId:    integer('user_id').notNull(),
  status:    statusPedidoEnum('status').notNull().default('pendente'),
  criadoEm: timestamp('criado_em').defaultNow().notNull(),
});
Nota
pgEnum gera dois comandos na migration: CREATE TYPE status_pedido AS ENUM (...) e depois o CREATE TABLE que o usa. O enum é um objeto de banco com nome — ele pode ser referenciado por múltiplas tabelas e aparece em \dT no psql. Exporte sempre o enum junto com as tabelas que o usam para que o Drizzle Kit consiga rastrear o tipo nas migrations.

# O tipo TypeScript inferido de um enum

O tipo inferido do campo status em $inferSelect é a union literal de todos os valores declarados no enum — sem necessidade de redeclarar manualmente. Para reutilizar esse tipo em outros lugares da aplicação, extraia-o diretamente do enum:

tipos inferidos do enum
// Tipo derivado do enum — atualiza automaticamente quando o enum muda.
export type StatusPedido = typeof statusPedidoEnum.enumValues[number];
// 'pendente' | 'pago' | 'enviado' | 'entregue' | 'cancelado'

// O TypeScript valida o valor na query — valores inválidos são erro de compilação.
const enviados = await db
  .select()
  .from(orders)
  .where(eq(orders.status, 'enviado'));
// eq(orders.status, 'invalido') → erro de compilação TS
Atenção
Adicionar um valor a um enum em produção é seguro (ALTER TYPE ... ADD VALUE). Remover ou renomear um valor existente não é — PostgreSQL não permite DROP VALUE em enums. Para enums que mudam frequentemente, prefira varchar com check constraint, ou migre para uma tabela de lookup. Enums são ideais para conjuntos estáveis com semântica de negócio clara.

# customType — tipos totalmente customizados

customType encapsula qualquer tipo PostgreSQL — nativo ou de extensão — com conversores explícitos entre o valor que o driver retorna (driverData) e o tipo que o TypeScript expõe (data). É o mecanismo correto para tipos que o banco retorna como string mas a aplicação quer consumir como outro tipo.

schema/types.ts — tipo monetário customizado
import { customType } from 'drizzle-orm/pg-core';

// O driver retorna NUMERIC como string. Convertemos para number automaticamente.
export const money = customType<{ data: number; driverData: string }>({
  dataType() {
    return 'numeric(12, 2)';
  },
  fromDriver(val) {
    return parseFloat(val);
  },
  toDriver(val) {
    return val.toFixed(2);
  },
});
schema/products.ts — usando o tipo money
import { money } from './types';

export const products = pgTable('products', {
  id:    serial('id').primaryKey(),
  nome:  varchar('nome', { length: 255 }).notNull(),
  preco: money('preco').notNull(),
  // $inferSelect: { preco: number } — não string, apesar do NUMERIC no banco
});

# JSONB tipado com $type()

O modificador .$type() não cria nenhum tipo novo no banco — ele apenas substitui o tipo TypeScript inferido para a coluna. É puramente uma anotação em tempo de compilação: a coluna continua sendo jsonb no PostgreSQL, mas o TypeScript passa a saber o shape esperado. A abordagem certa é declarar o tipo separadamente e aplicá-lo no schema:

schema/products.ts — JSONB tipado
import { pgTable, serial, varchar, jsonb } from 'drizzle-orm/pg-core';

// Shape esperado do campo metadata — declare como type, não como class.
type Metadata = {
  cor?:     string;
  tamanho?: string;
  tags?:    string[];
  peso?:    number;
};

export const products = pgTable('products', {
  id:       serial('id').primaryKey(),
  nome:     varchar('nome', { length: 255 }).notNull(),
  metadata: jsonb('metadata').$type<Metadata>(),
  // $inferSelect: { metadata: Metadata | null }
});
Dica
.$type() é TypeScript puro — não valida em runtime. Se um valor inválido entrar no banco por outro caminho (SQL direto, outra aplicação), o Drizzle vai retornar o dado sem erro. Para validação de runtime, aplique um schema Zod sobre o resultado — o Volume XII cobre exatamente essa integração.

# Arrays de colunas

PostgreSQL suporta arrays nativos de qualquer tipo escalar. Em Drizzle, basta encadear .array() na coluna — o tipo inferido no TypeScript passa a ser um array do tipo correspondente:

schema/products.ts — arrays nativos
export const products = pgTable('products', {
  id:        serial('id').primaryKey(),
  nome:      varchar('nome', { length: 255 }).notNull(),
  tags:      text('tags').array(),
  // $inferSelect: { tags: string[] | null }

  tamanhos:  varchar('tamanhos', { length: 10 }).array().notNull().default([]),
  // $inferSelect: { tamanhos: string[] }
});
Arrays vs JSONB
Arrays nativos do PostgreSQL são ideais para listas de valores escalares do mesmo tipo — IDs, tags, strings. Para estruturas heterogêneas ou aninhadas, prefira JSONB. Arrays permitem indexação com GIN e operadores como @> (contém) e && (intersecta); JSONB é mais flexível mas tem overhead de serialização maior.

SELECT e projeção

O query builder de Drizzle modela o SELECT como uma cadeia de métodos que espelha a ordem lógica do SQL: select → from → where → orderBy → limit. Cada método retorna um objeto que ancora o próximo — e o tipo do resultado é inferido a partir da projeção declarada, não de uma anotação manual. Este capítulo percorre todas as formas de SELECT: projeção total e parcial, expressões e alias, distinct, ordenação, paginação e construção dinâmica de queries com $dynamic.

# db.select() — projeção total

Sem argumentos, db.select() seleciona todas as colunas da tabela passada em .from(). O tipo de retorno é inferido do schema — nenhuma anotação necessária.

query/select-basico.ts
import { db } from './db';
import { users } from './schema';

const lista = await db.select().from(users);
// lista: { id: number; email: string; nome: string; criadoEm: Date }[]

// Equivalente SQL: SELECT id, email, nome, criado_em FROM users
Performance
Evite SELECT * em tabelas com colunas pesadas — campos jsonb, text grandes ou bytea. Mesmo sem o curinga, db.select() sem argumentos seleciona todas as colunas do schema. Em queries de lista ou listagem paginada, prefira projeção parcial para reduzir os dados transferidos pelo wire.

# Projeção parcial

Passando um objeto para db.select(), você declara exatamente quais colunas quer. O tipo de retorno é reduzido ao shape declarado — colunas não listadas não existem no resultado em TypeScript.

query/projecao-parcial.ts
// Apenas os campos necessários — o tipo reflete a seleção.
const nomes = await db
  .select({ nome: users.nome, email: users.email })
  .from(users);
// nomes: { nome: string; email: string }[]

// Projeção de múltiplas tabelas (sem JOIN — apenas estrutura):
const resumo = await db
  .select({
    produtoNome: products.nome,
    preco:       products.preco,
    ativo:       products.ativo,
  })
  .from(products);
// resumo: { produtoNome: string; preco: string; ativo: boolean }[]

# Expressões e alias

O objeto de projeção aceita qualquer expressão SQL — não apenas referências a colunas. Use o template sql para funções de agregação, casts, expressões matemáticas e qualquer construção que o banco suporte. O método .as() dá um alias à expressão; o parâmetro de tipo do sql informa ao TypeScript o tipo do valor retornado.

query/expressoes.ts
import { sql } from 'drizzle-orm';

const resultado = await db
  .select({
    nome:      users.nome,
    email:     users.email,

    // Expressão com alias — sql<T> informa o tipo ao TypeScript.
    dominioEmail: sql<string>`split_part(${users.email}, '@', 2)`
                    .as('dominio_email'),
  })
  .from(users);
// resultado: { nome: string; email: string; dominioEmail: string }[]
Nota
O parâmetro de tipo em sql<T> é uma asserção — o TypeScript confia que o banco retornará aquele tipo, sem verificação em runtime. Se a expressão puder retornar null (função aplicada a coluna nullable, por exemplo), declare sql<string | null> para refletir a realidade.

# selectDistinct

db.selectDistinct() é o equivalente de SELECT DISTINCT. A API é idêntica ao select() — aceita projeção parcial, encadeia os mesmos métodos:

query/distinct.ts
// Categorias distintas que têm pelo menos um produto.
const comProdutos = await db
  .selectDistinct({ categoriaId: products.categoriaId })
  .from(products)
  .where(isNotNull(products.categoriaId));
// comProdutos: { categoriaId: number | null }[]

# orderBy, limit e offset

.orderBy() aceita colunas e expressões SQL, com asc() e desc() para direção. Múltiplos critérios de ordenação são passados como argumentos em sequência. .limit() e .offset() constroem paginação:

query/ordenacao-paginacao.ts
import { desc, asc } from 'drizzle-orm';

const pagina = 2;
const porPagina = 20;

const pedidos = await db
  .select()
  .from(orders)
  .orderBy(desc(orders.criadoEm), asc(orders.id)) // mais recente primeiro
  .limit(porPagina)
  .offset((pagina - 1) * porPagina);

// SQL: SELECT ... FROM orders ORDER BY criado_em DESC, id ASC LIMIT 20 OFFSET 20
Atenção — paginação com OFFSET
Paginação com OFFSET degrada linearmente: para a página 500 com 20 itens por página, PostgreSQL lê e descarta 9.980 linhas antes de retornar as 20 desejadas. Para conjuntos grandes, prefira paginação baseada em cursor — filtrando pela última chave vista (WHERE id > ultimo_id). O Capítulo 11 mostra como compor esse padrão com os operadores do Drizzle.

# $dynamic — construção dinâmica de queries

O método .$dynamic() converte a query em modo de construção incremental, permitindo encadear cláusulas condicionalmente em código TypeScript. Sem ele, adicionar um .where() condicional exigiria duplicar a query inteira.

query/busca-dinamica.ts
import { and, eq, gte, lte } from 'drizzle-orm';

async function buscarProdutos(opts: {
  categoriaId?: number;
  precoMin?:    number;
  precoMax?:    number;
  apenasAtivos?: boolean;
  limite?:      number;
}) {
  let query = db
    .select({ id: products.id, nome: products.nome, preco: products.preco })
    .from(products)
    .$dynamic();

  const filtros = [];
  if (opts.categoriaId !== undefined)
    filtros.push(eq(products.categoriaId, opts.categoriaId));
  if (opts.precoMin !== undefined)
    filtros.push(gte(products.preco, String(opts.precoMin)));
  if (opts.precoMax !== undefined)
    filtros.push(lte(products.preco, String(opts.precoMax)));
  if (opts.apenasAtivos)
    filtros.push(eq(products.ativo, true));

  if (filtros.length) query = query.where(and(...filtros));
  if (opts.limite)    query = query.limit(opts.limite);

  return query;
}

const resultado = await buscarProdutos({
  categoriaId: 3, apenasAtivos: true, limite: 10,
});
Dica
A técnica acima de acumular filtros em um array e combinar com and(...filtros) é o padrão idiomático para filtros opcionais múltiplos — evita o aninhamento de and(and(...)) e deixa explícito que os filtros são todos aditivos. Para filtros alternativos (OR), o mesmo padrão funciona substituindo and por or.

WHERE e operadores

Drizzle representa condições SQL como funções TypeScript — não como strings interpoladas. Isso traz duas vantagens diretas: o compilador valida o tipo de cada operando, e nenhum valor é interpolado diretamente no SQL (proteção automática contra injeção). Este capítulo cobre todos os operadores disponíveis — de comparações simples a existência, arrays e paginação baseada em cursor.

# Operadores de comparação

Os seis operadores fundamentais aceitam uma coluna e um valor do tipo compatível. O TypeScript recusa valores do tipo errado em tempo de compilação.

query/comparacao.ts
import { eq, ne, gt, lt, gte, lte } from 'drizzle-orm';

// eq  → WHERE id = 1
const u = await db.select().from(users).where(eq(users.id, 1));

// ne  → WHERE status != 'cancelado'
const abertos = await db.select().from(orders).where(ne(orders.status, 'cancelado'));

// gt  → WHERE preco > '100'
const caros = await db.select().from(products).where(gt(products.preco, '100'));

// gte → WHERE quantidade >= 1
const emEstoque = await db.select().from(products).where(gte(products.estoque, 1));

// lt  → WHERE estoque < 5  (alerta de reposição)
const baixo = await db.select().from(products).where(lt(products.estoque, 5));

// lte → WHERE preco <= '50'
const baratos = await db.select().from(products).where(lte(products.preco, '50'));
Nota — numeric como string
Colunas numeric/decimal têm tipo TypeScript string por padrão (o driver retorna o valor como string para evitar perda de precisão de ponto flutuante). Por isso gt(products.preco, '100') recebe string — o banco interpreta corretamente como número na comparação SQL. Para trabalhar com number, use customType (Capítulo 9).

# like e ilike

like gera LIKE (case-sensitive). ilike gera ILIKE, extensão do PostgreSQL que ignora maiúsculas/minúsculas — e é o operador correto para buscas de texto que não dependem de índice GIN:

query/texto.ts
import { like, ilike, notIlike } from 'drizzle-orm';

// Prefixo — usa índice B-tree em lower(nome) se declarado (Cap 8)
const cafes = await db.select().from(products)
  .where(ilike(products.nome, 'caf%'));

// Busca em qualquer posição — requer varredura ou índice GIN
const termoBusca = 'orgânico';
const resultado = await db.select().from(products)
  .where(ilike(products.nome, `%${termoBusca}%`));

# and, or, not — combinando condições

Condições compostas se constroem com and(), or() e not(). Todos aceitam número variável de argumentos; undefined é ignorado — o que elimina a necessidade de lógica condicional para filtros opcionais:

query/condicoes-compostas.ts
import { and, or, not, eq, gte, lte } from 'drizzle-orm';

// AND: produtos ativos com preço entre 50 e 200
const filtrado = await db.select().from(products)
  .where(and(
    eq(products.ativo, true),
    gte(products.preco, '50'),
    lte(products.preco, '200'),
  ));

// OR: pedidos pendentes ou pagos
const pendentesOuPagos = await db.select().from(orders)
  .where(or(
    eq(orders.status, 'pendente'),
    eq(orders.status, 'pago'),
  ));

// undefined é ignorado — filtro opcional sem condicional:
const categoriaFiltro = undefined; // poderia vir de query param
const listagem = await db.select().from(products)
  .where(and(
    eq(products.ativo, true),
    categoriaFiltro !== undefined
      ? eq(products.categoriaId, categoriaFiltro)
      : undefined,   // ignorado pelo and()
  ));

# inArray e notInArray

inArray gera IN (...) — aceita um array de valores ou uma subquery. notInArray gera NOT IN (...):

query/in-array.ts
import { inArray, notInArray } from 'drizzle-orm';

// Array de valores literais
const ids = [1, 2, 3, 5, 8];
const selecionados = await db.select().from(products)
  .where(inArray(products.id, ids));

// Subquery — IN (SELECT id FROM users WHERE ...)
const idsUsuariosVip = db
  .select({ id: users.id })
  .from(users)
  .where(eq(users.vip, true));

const pedidosVip = await db.select().from(orders)
  .where(inArray(orders.userId, idsUsuariosVip));
Atenção
inArray(col, []) — array vazio — gera SQL inválido no PostgreSQL (IN () não é permitido). Antes de passar um array dinâmico para inArray, verifique se está vazio: se estiver, pule a query inteira ou use uma condição que retorne zero linhas (sql\`false\`). O mesmo vale para notInArray.

# isNull e isNotNull

Para comparar com NULL, use sempre isNull() e isNotNull() — nunca eq(col, null). Em SQL, col = NULL é sempre falso; apenas IS NULL funciona corretamente.

query/null.ts
import { isNull, isNotNull } from 'drizzle-orm';

// Produtos sem categoria atribuída
const semCategoria = await db.select().from(products)
  .where(isNull(products.categoriaId));

// Produtos com categoria atribuída
const comCategoria = await db.select().from(products)
  .where(isNotNull(products.categoriaId));

# between

between(col, min, max) gera BETWEEN min AND max — inclusivo nos dois extremos. Funciona com números, strings e datas:

query/between.ts
import { between } from 'drizzle-orm';

// Produtos com preço entre 50 e 200
const faixaMed = await db.select().from(products)
  .where(between(products.preco, '50', '200'));

// Pedidos criados num intervalo de datas
const emJaneiro = await db.select().from(orders)
  .where(between(
    orders.criadoEm,
    new Date('2024-01-01'),
    new Date('2024-01-31T23:59:59'),
  ));

# exists

exists(subquery) gera EXISTS (...) — retorna linhas da tabela principal para as quais a subquery retorna pelo menos uma linha. Em geral mais eficiente que IN com subqueries grandes, pois para na primeira linha encontrada:

query/exists.ts
import { exists } from 'drizzle-orm';

// Usuários que fizeram pelo menos um pedido
const comPedidos = await db.select().from(users)
  .where(
    exists(
      db.select({ _: orders.id })
        .from(orders)
        .where(eq(orders.userId, users.id))
    )
  );

# Paginação baseada em cursor

A alternativa ao OFFSET (Cap 10) é paginar pelo valor da última chave vista. O banco não descarta linhas — vai direto ao ponto de corte com o índice. O padrão usa lt ou gt dependendo da direção da ordenação:

query/cursor-pagination.ts
import { and, eq, lt, desc } from 'drizzle-orm';

// Primeira página — sem cursor
const pag1 = await db.select().from(orders)
  .where(eq(orders.userId, 42))
  .orderBy(desc(orders.id))
  .limit(20);

// Próxima página — cursor = último id retornado
const cursor = pag1.at(-1)?.id;

const pag2 = cursor
  ? await db.select().from(orders)
      .where(and(
        eq(orders.userId, 42),
        lt(orders.id, cursor), // WHERE id < cursor
      ))
      .orderBy(desc(orders.id))
      .limit(20)
  : [];
Dica
Paginação baseada em cursor exige que a coluna de cursor tenha um índice — de preferência a chave primária ou outro campo com unique. Com o índice, a performance é constante independente da página. A desvantagem é que não permite "saltar" para uma página arbitrária — só avançar ou recuar sequencialmente. Para UIs com paginação numerada, avalie cursor com cache da posição das páginas já visitadas.

Capítulo 12

INSERT e returning

O db.insert() do Drizzle segue o mesmo padrão de cadeia dos outros comandos: a tabela vai em insert(), os valores em .values(), e o restante é opcional. O tipo aceito por .values() é o $inferInsert da tabela — campos com default ou sem notNull são automaticamente opcionais. Este capítulo cobre insert simples, lote, retorno de colunas e os dois padrões de conflito: ignorar e atualizar (upsert).

# Insert básico

O argumento de .values() é tipado pelo $inferInsert da tabela — o TypeScript exige os campos obrigatórios e torna opcionais os que têm default ou são nullable. Sem .returning(), o comando não retorna nada.

query/insert-basico.ts
import { db } from './db';
import { users } from './schema';
import type { NewUser } from './schema/users';

// O tipo NewUser é typeof users.$inferInsert
const novoUser: NewUser = {
  email: 'joao@ex.com',
  nome:  'João Silva',
  // id e criadoEm omitidos — têm default no banco
};

await db.insert(users).values(novoUser);

# .returning() — obter o registro criado

.returning() instrui o PostgreSQL a retornar as colunas do registro inserido. Sem argumentos, retorna todas as colunas — com o tipo completo de $inferSelect. Com um objeto de projeção, retorna apenas o especificado:

query/insert-returning.ts
// Retorno completo — desestrutura o primeiro elemento do array
const [criado] = await db
  .insert(users)
  .values({ email: 'ana@ex.com', nome: 'Ana' })
  .returning();
// criado: { id: number; email: string; nome: string; criadoEm: Date }

// Projeção parcial — retorna apenas o id gerado
const [{ id }] = await db
  .insert(orders)
  .values({ userId: 1, status: 'pendente' })
  .returning({ id: orders.id });
// id: number
Nota
.returning() é uma extensão do PostgreSQL — não existe em MySQL ou SQLite padrão. Em Drizzle com dialeto postgresql, é sempre seguro usar. Se o insert não inserir nenhuma linha (por exemplo, em combinação com onConflictDoNothing), o array retornado estará vazio — desestruture com cuidado ou verifique o comprimento antes.

# Inserção em lote

.values() aceita um array de objetos — isso gera um único INSERT INTO ... VALUES (...), (...), (...). É ordens de magnitude mais eficiente do que um loop de inserts individuais para volumes grandes:

query/insert-lote.ts
const novosUsers: NewUser[] = [
  { email: 'alice@ex.com', nome: 'Alice' },
  { email: 'bob@ex.com',   nome: 'Bob'   },
  { email: 'carol@ex.com', nome: 'Carol' },
];

const criados = await db
  .insert(users)
  .values(novosUsers)
  .returning({ id: users.id, email: users.email });
// criados: { id: number; email: string }[] — um elemento por linha inserida
Performance
Para inserções de centenas ou milhares de linhas, considere dividir em lotes de 500 a 1.000 registros por INSERT. Lotes muito grandes aumentam o tempo de lock na tabela e o volume de memória consumido pelo parser. Um loop com db.insert().values(chunk) por chunk é o padrão adequado para imports de dados em produção.

# onConflictDoNothing

Quando há risco de violar uma constraint única e o comportamento desejado é simplesmente ignorar a linha duplicada, .onConflictDoNothing() adiciona ON CONFLICT DO NOTHING. Sem argumento target, se aplica a qualquer conflito de constraint; com target, restringe o tratamento à coluna ou constraint especificada:

query/conflict-nothing.ts
// Ignora qualquer conflito de constraint na tabela
await db
  .insert(users)
  .values({ email: 'existente@ex.com', nome: 'Alguém' })
  .onConflictDoNothing();

// Restringe ao conflito no campo email
await db
  .insert(users)
  .values({ email: 'existente@ex.com', nome: 'Alguém' })
  .onConflictDoNothing({ target: users.email });
Atenção
onConflictDoNothing() sem target silencia conflitos em qualquer constraint da tabela — inclusive constraints que indicam erros genuínos de lógica, como FK inválida ou check violado. Em tabelas com várias constraints, prefira sempre especificar target para que apenas o conflito esperado seja ignorado.

# onConflictDoUpdate — upsert

O padrão upsert — inserir ou atualizar se já existir — usa .onConflictDoUpdate(). O campo set define o que atualizar em caso de conflito. O valor especial EXCLUDED referencia os valores que foram tentados no insert (os "rejeitados" pelo conflito):

query/upsert.ts
import { sql } from 'drizzle-orm';

// Upsert de produto — atualiza nome e preço se o id já existir
const [produto] = await db
  .insert(products)
  .values({
    id:    42,
    nome:  'Café Especial',
    preco: '29.90',
    ativo: true,
  })
  .onConflictDoUpdate({
    target: products.id,
    set: {
      nome:        sql`EXCLUDED.nome`,
      preco:       sql`EXCLUDED.preco`,
      atualizadoEm: new Date(),
    },
  })
  .returning();

O argumento opcional setWhere adiciona uma condição ao update — útil para upserts condicionais onde a atualização só deve ocorrer se o novo valor satisfaz algum critério:

query/upsert-condicional.ts
import { sql, lt } from 'drizzle-orm';

// Atualiza o preço apenas se o novo valor for menor que o atual
await db
  .insert(products)
  .values({ id: 42, nome: 'Café', preco: '25.00', ativo: true })
  .onConflictDoUpdate({
    target:   products.id,
    set:      { preco: sql`EXCLUDED.preco` },
    setWhere: lt(products.preco, sql`EXCLUDED.preco`),
    // Atualiza somente se preco atual < novo preco (EXCLUDED)
  });
Construindo set dinamicamente
Para upserts onde o set deve espelhar todos os campos do insert (exceto a chave), importe getTableColumns de drizzle-orm e exclua as colunas que não devem ser sobrescritas:
const cols = getTableColumns(products);
const { id, criadoEm, ...updateCols } = cols;
Então use set: updateCols para construir o payload dinamicamente, sem listar campo a campo.

UPDATE — atualizações tipadas

O db.update() segue o mesmo modelo encadeado dos outros comandos: tabela em update(), campos em .set(), condição em .where(). O objeto passado para .set() é verificado pelo TypeScript — apenas colunas existentes são aceitas, com os tipos corretos. Este capítulo cobre update simples, expressões SQL em set, updates em lote via CASE, soft delete e a proteção necessária contra updates sem WHERE.

# Update básico

A estrutura mínima é update → set → where. Sem .returning(), o comando executa silenciosamente — nenhum dado é retornado pelo Drizzle.

query/update-basico.ts
import { eq } from 'drizzle-orm';

// Atualiza o nome de um usuário específico
await db
  .update(users)
  .set({ nome: 'João Atualizado' })
  .where(eq(users.id, 1));

// Múltiplos campos na mesma operação
await db
  .update(orders)
  .set({
    status:      'pago',
    atualizadoEm: new Date(),
  })
  .where(eq(orders.id, 100));
$onUpdateFn e o update
Se a tabela declara uma coluna com .$onUpdateFn(() => new Date()) (Capítulo 6), o Drizzle injeta automaticamente esse valor em todo db.update() — você não precisa incluir atualizadoEm: new Date() manualmente no set. O campo é adicionado à query pelo runtime antes de enviar ao driver.

# .returning()

.returning() funciona exatamente como no insert — retorna um array com as linhas afetadas. Se o WHERE não encontrar nenhuma linha, o array estará vazio:

query/update-returning.ts
// Retorno completo após update
const [atualizado] = await db
  .update(users)
  .set({ nome: 'Ana Silva' })
  .where(eq(users.id, 2))
  .returning();
// atualizado: { id, email, nome, criadoEm } | undefined (pode ser vazio)

// Projeção parcial — retorna só o status atualizado
const confirmados = await db
  .update(orders)
  .set({ status: 'enviado' })
  .where(eq(orders.status, 'pago'))
  .returning({ id: orders.id, status: orders.status });
// confirmados: { id: number; status: string }[]

# Expressões SQL em set()

O .set() aceita expressões sql além de valores literais. Isso permite operações atômicas — incrementos, concatenações, cálculos — sem precisar ler o valor atual primeiro e arriscar race conditions:

query/update-expressoes.ts
import { sql, eq } from 'drizzle-orm';

// Incremento atômico de estoque — seguro para concorrência
await db
  .update(products)
  .set({ estoque: sql`${products.estoque} + 10` })
  .where(eq(products.id, 42));

// Decremento com proteção de mínimo zero
await db
  .update(products)
  .set({ estoque: sql`GREATEST(${products.estoque} - 1, 0)` })
  .where(eq(products.id, 42));

// Concatenação de texto
await db
  .update(products)
  .set({ nome: sql`${products.nome} || ' (Edição Limitada)'` })
  .where(eq(products.categoriaId, 3));

# Update em lote com CASE

Para atualizar múltiplas linhas com valores diferentes em uma única query, o padrão SQL é o CASE ... WHEN ... THEN ... END. Combinado com inArray no WHERE, é a alternativa eficiente a um loop de updates individuais:

query/update-lote.ts
import { sql, inArray } from 'drizzle-orm';

// Atualiza preços de vários produtos em um único round-trip
await db
  .update(products)
  .set({
    preco: sql`CASE
      WHEN id = 1 THEN '29.90'
      WHEN id = 2 THEN '49.90'
      WHEN id = 3 THEN '19.90'
      ELSE ${products.preco}
    END`,
  })
  .where(inArray(products.id, [1, 2, 3]));
Performance
Para atualizar N linhas com valores distintos, o padrão CASE custa um único round-trip ao banco. Um loop de db.update().where(eq(id, x)) por linha custa N round-trips — inaceitável para N grande. Para dezenas de linhas, use o CASE; para centenas ou milhares, considere INSERT INTO ... ON CONFLICT DO UPDATE (Capítulo 12) ou um UPDATE FROM (VALUES ...) via sql raw (Capítulo 21).

# Soft delete

O padrão soft delete marca registros como removidos em vez de apagá-los. A coluna deletadoEm — timestamp nullable — serve como flag: null significa ativo, qualquer data significa removido. Todas as queries precisam filtrar por isNull(deletadoEm):

schema/users.ts + query/soft-delete.ts
// Schema — adicionar coluna nullable sem default
export const users = pgTable('users', {
  // ... outras colunas
  deletadoEm: timestamp('deletado_em'), // null = ativo
});

// Soft delete — marca sem apagar
await db
  .update(users)
  .set({ deletadoEm: new Date() })
  .where(eq(users.id, 42));

// Query padrão — exclui deletados
const ativos = await db
  .select()
  .from(users)
  .where(isNull(users.deletadoEm));

// Restaurar
await db
  .update(users)
  .set({ deletadoEm: null })
  .where(eq(users.id, 42));
Dica
Para garantir que isNull(deletadoEm) apareça em toda query da tabela, encapsule o db em uma função ou helper que adicione o filtro automaticamente — ou use uma view PostgreSQL que filtre os deletados. Esquecer o filtro em uma query é o principal custo operacional do soft delete.

# Proteção contra UPDATE sem WHERE

Drizzle não impede db.update(t).set({...}) sem .where() — isso gera um UPDATE que afeta todas as linhas da tabela. Não há guarda automático. O controle deve vir da revisão de código e de testes:

query/update-sem-where.ts
// PERIGOSO — atualiza TODOS os registros da tabela
await db.update(products).set({ ativo: false });

// Padrão seguro: exigir where via wrapper
async function updateComWhere(
  tabela: typeof products,
  dados: Partial<NewProduct>,
  where: SQL,
) {
  return db.update(tabela).set(dados).where(where).returning();
}
// Chamar sem where resulta em erro de tipagem
Atenção
Em ambientes de produção, considere usar o campo rowCount do resultado para detectar atualizações inesperadamente grandes — se um update que deveria afetar uma linha retornar rowCount > 1, algo está errado. Isso exige acessar o resultado raw do driver, não a API padrão do Drizzle, mas é uma camada de defesa valiosa em código crítico.

DELETE — remoção controlada

O db.delete() é o comando mais simples em estrutura, mas o mais consequente em erro. Drizzle não impõe nenhuma barreira contra delete sem WHERE, não oferece transação automática, e não desfaz cascatas de FK já executadas. Este capítulo cobre o delete básico, returning, deleção por subquery, proteção contra delete global e a relação com cascatas de chaves estrangeiras declaradas no Capítulo 6.

# Delete básico

A estrutura mínima é delete → where. Sem .returning(), a execução é silenciosa — nenhum dado é retornado.

query/delete-basico.ts
import { eq, and, lt } from 'drizzle-orm';

// Deleta um usuário pelo id
await db.delete(users).where(eq(users.id, 42));

// Deleta pedidos cancelados anteriores a uma data
await db
  .delete(orders)
  .where(and(
    eq(orders.status, 'cancelado'),
    lt(orders.criadoEm, new Date('2023-01-01')),
  ));

# .returning()

Como no insert e no update, .returning() instrui o PostgreSQL a retornar as linhas removidas. Útil para confirmar o que foi apagado, emitir eventos de domínio ou registrar em log de auditoria:

query/delete-returning.ts
// Retorno completo da linha removida
const [removido] = await db
  .delete(users)
  .where(eq(users.id, 42))
  .returning();
// removido: { id, email, nome, criadoEm } | undefined

// Projeção parcial — retorna só os ids removidos para log
const removidos = await db
  .delete(orderItems)
  .where(eq(orderItems.orderId, 100))
  .returning({ orderId: orderItems.orderId, productId: orderItems.productId });
// removidos: { orderId: number; productId: number }[]

# DELETE com subquery

Para deletar linhas com base em dados de outra tabela, use inArray com uma subquery — o equivalente de um DELETE ... WHERE id IN (SELECT ...):

query/delete-subquery.ts
import { inArray, isNotNull } from 'drizzle-orm';

// Deleta todos os pedidos de usuários marcados como deletados
await db
  .delete(orders)
  .where(
    inArray(
      orders.userId,
      db.select({ id: users.id })
        .from(users)
        .where(isNotNull(users.deletadoEm)),
    )
  );

// Limpa itens de pedidos que não existem mais
await db
  .delete(orderItems)
  .where(
    inArray(
      orderItems.orderId,
      db.select({ id: orders.id })
        .from(orders)
        .where(eq(orders.status, 'cancelado')),
    )
  );

# Cascata de chaves estrangeiras

Quando uma FK é declarada com onDelete: 'cascade' (Capítulo 6), deletar a linha pai apaga automaticamente todas as linhas filhas no banco — sem que o Drizzle ou a aplicação precisem orquestrar. Esse comportamento é executado dentro da mesma transação implícita do DELETE:

cascade em ação
// orders.userId tem onDelete: 'cascade' para users
// orderItems.orderId tem onDelete: 'cascade' para orders

// Deletar o user remove orders e orderItems automaticamente
await db.delete(users).where(eq(users.id, 42));
// PostgreSQL: DELETE users → cascade orders → cascade order_items
Cascata e returning()
.returning() no delete principal retorna apenas as linhas diretamente deletadas — não as linhas removidas por cascata nas tabelas filhas. Se precisar dos ids dos filhos removidos, delete de baixo para cima manualmente (primeiro orderItems, depois orders, depois users) dentro de uma transação (Capítulo 19), usando .returning() em cada etapa.

# Hard delete vs soft delete

A decisão entre remover fisicamente uma linha (hard delete) e marcá-la como removida (soft delete, visto no Capítulo 13) depende de requisitos de negócio. Hard delete libera espaço, mantém o banco limpo e não exige filtros em todas as queries. Soft delete preserva histórico, permite restauração e facilita auditoria — mas aumenta a complexidade de cada query que precisa ignorar os registros removidos.

Quando usar cada um
Hard delete: dados sem valor histórico após a remoção — sessões expiradas, tokens, logs de debug, itens de carrinho abandonado.
Soft delete: entidades de negócio com histórico relevante — usuários, pedidos, produtos. Prefira hard delete por padrão e adote soft delete apenas onde há requisito explícito de auditoria ou restauração.

Capítulo 15

JOINs — combinando tabelas

O query builder de Drizzle expõe os quatro JOINs do SQL — innerJoin, leftJoin, rightJoin, fullJoin — encadeados após o from(). A peculiaridade que merece atenção desde o primeiro contato é a forma do resultado: quando o select() não declara projeção, Drizzle retorna um array de objetos com uma chave por tabela envolvida — não um objeto achatado. Esse é o ponto onde quem vem de Prisma ou TypeORM precisa recalibrar o modelo mental. Este capítulo cobre os quatro JOINs, a estrutura do resultado, projeção parcial, self-join com alias, e o padrão de agrupamento manual em árvore.

# A estrutura do resultado: chave por tabela

Sem projeção parcial, db.select().from(A).innerJoin(B, ...) retorna { A: TipoA; B: TipoB }[] — um objeto por linha do produto cartesiano, com uma chave nomeada para cada tabela. É a tradução literal do que SQL realmente faz: o JOIN combina linhas, e a linha resultante carrega todas as colunas das duas tabelas. Drizzle apenas mantém essa separação visível em vez de fundir tudo em um objeto plano com nomes colidentes.

query/join-resultado.ts
import { eq } from 'drizzle-orm';

const linhas = await db
  .select()
  .from(users)
  .innerJoin(orders, eq(orders.userId, users.id));

// linhas: Array<{
//   users:  { id: number; email: string; nome: string; criadoEm: Date };
//   orders: { id: number; userId: number; status: string; criadoEm: Date };
// }>

// Acesso por tabela — sem ambiguidade de nome
linhas.forEach((linha) => {
  console.log(linha.users.nome, linha.orders.status);
});
Por que chave por tabela
Em um JOIN entre users e orders, ambos têm id e criadoEm — colunas com o mesmo nome em tabelas diferentes. Achatar tudo em um objeto plano forçaria invenção de aliases (users_id, orders_id) ou perda de dados (a última coluna sobrescreve a primeira). Drizzle escolhe não improvisar: o resultado preserva a estrutura do SQL, e o programador decide se quer projetar para uma forma achatada ou navegar pela aninhada.

# innerJoin — interseção

innerJoin retorna apenas as linhas em que a condição se aplica — equivalente a INNER JOIN ... ON. Linhas sem correspondência no outro lado são descartadas dos dois lados:

query/inner-join.ts
// Usuários que têm ao menos um pedido — sem usuários sem pedidos
const ativos = await db
  .select({
    nomeUser:   users.nome,
    pedidoId:   orders.id,
    status:     orders.status,
  })
  .from(users)
  .innerJoin(orders, eq(orders.userId, users.id));

// ativos: { nomeUser: string; pedidoId: number; status: string }[]
// nenhum campo é nullable — innerJoin garante presença em ambos os lados

# leftJoin — preservando a esquerda

leftJoin retorna todas as linhas da tabela em from(), com null nas colunas da tabela à direita quando não há correspondência. O tipo TypeScript do lado direito passa a ser ... | null:

query/left-join.ts
// Todos os produtos, com sua categoria quando existir
const catalogo = await db
  .select({
    produto:         products.nome,
    categoria:       categories.nome,
    categoriaId:     categories.id,
  })
  .from(products)
  .leftJoin(categories, eq(categories.id, products.categoriaId));

// catalogo: {
//   produto: string;
//   categoria: string | null;     ← null para produtos sem categoria
//   categoriaId: number | null;
// }[]

# rightJoin e fullJoin

rightJoin é o espelho de leftJoin: preserva a tabela à direita. fullJoin preserva ambos os lados — uma linha por correspondência, mais linhas para os "órfãos" de cada lado, com null nas colunas ausentes. Em prática, rightJoin é raro (basta inverter o from) e fullJoin aparece em relatórios de reconciliação:

query/full-join.ts
// Reconciliação: todas as categorias e todos os produtos,
// mostrando órfãos dos dois lados
const reconciliacao = await db
  .select({
    categoriaNome: categories.nome,
    produtoNome:   products.nome,
  })
  .from(categories)
  .fullJoin(products, eq(products.categoriaId, categories.id));

// Ambos os campos são string | null:
//  - categoriaNome=null → produto sem categoria
//  - produtoNome=null   → categoria sem produtos
//  - ambos preenchidos  → match normal

# Múltiplos JOINs em cadeia

JOINs se encadeiam diretamente. A ordem importa: cada innerJoin ou leftJoin referencia a "tabela acumulada" anterior. Para a travessia clássica do schema de e-commerce — pedido → cliente, itens, produtos — a cadeia natural é:

query/multi-join.ts
// Detalhe completo de pedidos: cliente, itens e produtos
const detalhe = await db
  .select({
    pedidoId:    orders.id,
    clienteNome: users.nome,
    produtoNome: products.nome,
    quantidade:  orderItems.quantidade,
    precoUnit:   orderItems.precoUnit,
  })
  .from(orders)
  .innerJoin(users,      eq(users.id,         orders.userId))
  .innerJoin(orderItems, eq(orderItems.orderId, orders.id))
  .innerJoin(products,   eq(products.id,      orderItems.productId))
  .where(eq(orders.id, 100));

// detalhe: uma linha por item do pedido — N itens = N linhas
Explosão cartesiana
Um usuário com 10 pedidos, cada um com 5 itens, retorna 50 linhas em um JOIN encadeado — o usuário aparece repetido 50 vezes, cada pedido 5 vezes. Para listas pequenas é aceitável; para árvores grandes, prefira db.query com with (Capítulo 17), que usa subqueries lateralizadas e devolve uma estrutura aninhada sem multiplicação. Quando ainda precisar do JOIN explícito por outras razões — agregação, EXPLAIN específico — agrupe em árvore manualmente no código.

# Self-join com alias()

Quando a mesma tabela aparece duas vezes no JOIN — categorias com seu pai, funcionários com gestor — é preciso criar um alias para a segunda referência. Sem isso, o SQL gerado teria duas vezes FROM categories e não saberia distinguir categories.id entre os dois usos:

query/self-join.ts
import { alias } from 'drizzle-orm/pg-core';
import { eq } from 'drizzle-orm';

// Cria dois aliases distintos para a mesma tabela
const filho = alias(categories, 'filho');
const pai   = alias(categories, 'pai');

const arvore = await db
  .select({
    nomeFilho: filho.nome,
    nomePai:   pai.nome,
  })
  .from(filho)
  .leftJoin(pai, eq(pai.id, filho.parentId));

// SQL: FROM categories AS filho LEFT JOIN categories AS pai ON pai.id = filho.parent_id

# Agrupando em árvore manualmente

Quando o JOIN explícito é a ferramenta certa mas o consumidor precisa de uma estrutura aninhada — pedido com seus itens, por exemplo — o agrupamento fica por conta do código TypeScript. O padrão usual é reduce com um Map indexando pelo id da entidade pai:

query/join-para-arvore.ts
const linhas = await db
  .select({ order: orders, item: orderItems })
  .from(orders)
  .leftJoin(orderItems, eq(orderItems.orderId, orders.id))
  .where(eq(orders.userId, 42));

// Agrupa em pedido → itens[]
const agrupado = linhas.reduce((map, linha) => {
  const id = linha.order.id;
  if (!map.has(id)) map.set(id, { ...linha.order, items: [] });
  if (linha.item) map.get(id)!.items.push(linha.item);
  return map;
}, new Map());

const resultado = [...agrupado.values()];
// resultado: pedidos com seus itens aninhados — sem repetições
Quando vale o esforço
Esse padrão de agrupamento manual é exatamente o trabalho que db.query.orders.findMany({ with: { items: true } }) faz automaticamente. Para leituras puras de árvore (sem agregação ou EXPLAIN específico), prefira db.query. Reserve o JOIN explícito + reduce para situações onde você precisa de agregações horizontais, controle fino sobre o plano de execução, ou estruturas que não mapeiam diretamente para relações declaradas em relations().

# JOIN vs relational query

A escolha entre db.select().leftJoin() e db.query.X.findMany({ with: ... }) não é dogmática. Os critérios práticos:

Critério de escolha
Use JOIN explícito quando: a query envolve agregação (COUNT, SUM, GROUP BY); o resultado naturalmente é uma forma achatada; você precisa de controle fino sobre o SQL gerado (otimizando EXPLAIN); a estrutura não corresponde a uma relação declarada.
Use db.query quando: a query é navegação pura de relações pai-filho; o consumidor quer uma árvore aninhada e tipada; o volume de filhos por pai é alto (a subquery lateral evita explosão cartesiana). O Capítulo 16 detalha esse critério.

Capítulo 16

findMany e findFirst

As relational queries são a segunda API de leitura de Drizzle, exposta como db.query.<tabela>.findMany() e findFirst(). Em vez de descrever como obter os dados (joins, projeções, agrupamento), você descreve o que quer ler — colunas, condições, relações navegadas. O Drizzle decide a estratégia de execução (subqueries lateralizadas, na maior parte dos casos) e devolve uma árvore tipada, sem explosão cartesiana. Este capítulo cobre os pré-requisitos, as opções de cada find, e — o ponto que mais gera dúvida — quando usar relational queries em vez do query builder.

# Pré-requisitos

Duas coisas precisam estar no lugar para que db.query funcione. Primeiro, o schema completo precisa ter sido passado ao construir a instância db (Capítulo 2). Segundo, as relações entre tabelas precisam estar declaradas com relations() (Capítulo 7) — sem isso, with não tem por onde navegar.

src/db/index.ts — pré-requisito do db.query
import { drizzle } from 'drizzle-orm/postgres-js';
import * as schema from './schema';

// schema/index.ts re-exporta tabelas E os blocos relations()
export const db = drizzle(client, { schema });

// Agora disponível:
// db.query.users, db.query.products, db.query.orders, db.query.orderItems, db.query.categories

# findMany vs findFirst

As duas funções aceitam exatamente o mesmo objeto de opções — diferem apenas no retorno e no SQL gerado. findMany retorna um array (pode ser vazio); findFirst adiciona LIMIT 1 e retorna o primeiro elemento ou undefined. Sem opções, findMany retorna todas as linhas da tabela:

query/find-basico.ts
import { eq } from 'drizzle-orm';

// findMany — sempre array
const todos = await db.query.users.findMany();
// todos: User[]

const ativos = await db.query.users.findMany({
  where: eq(users.ativo, true),
});
// ativos: User[] — array vazio se nenhum bate

// findFirst — registro ou undefined
const u = await db.query.users.findFirst({
  where: eq(users.id, 1),
});
// u: User | undefined

# columns — projeção parcial declarativa

A opção columns é o equivalente do objeto de projeção do select(), com uma diferença de sintaxe: você marca cada coluna como true (incluir) ou false (omitir). Os dois modos não se misturam — ou você lista tudo o que quer com true, ou lista o que não quer com false:

query/find-columns.ts
// Modo include — apenas os campos listados
const nomes = await db.query.users.findMany({
  columns: {
    id:   true,
    nome: true,
  },
});
// nomes: { id: number; nome: string }[]

// Modo omit — tudo exceto o que for false
const resumido = await db.query.users.findMany({
  columns: {
    criadoEm: false,
  },
});
// resumido: { id, email, nome }[] — sem criadoEm

# where, orderBy, limit e offset

Os mesmos operadores do Capítulo 11 funcionam em where. orderBy recebe um array de expressões (não argumentos variádicos como no query builder). limit e offset são números diretos:

query/find-condicoes.ts
import { and, eq, gt, desc, asc } from 'drizzle-orm';

const recentes = await db.query.orders.findMany({
  where: and(
    eq(orders.status, 'pendente'),
    gt(orders.criadoEm, new Date('2024-01-01')),
  ),
  orderBy: [desc(orders.criadoEm), asc(orders.id)],
  limit:  20,
  offset: 0,
});

# with — navegação de relações

A opção with é o coração das relational queries — declara que filhos de uma relação devem ser carregados junto. true traz todos os campos e todas as linhas filhas; um objeto permite restringir colunas, filtrar, ordenar e limitar dentro do filho. O Capítulo 17 cobre cada opção em detalhe; aqui o ponto é mostrar o shape geral:

query/find-with.ts
// Forma mais simples — todos os pedidos de cada usuário
const comPedidos = await db.query.users.findMany({
  with: {
    orders: true,
  },
});
// comPedidos: (User & { orders: Order[] })[]

// Aninhado — árvore completa de e-commerce em uma query
const arvore = await db.query.users.findFirst({
  where: eq(users.id, 1),
  with: {
    orders: {
      with: {
        items: {
          with: { product: true },
        },
      },
    },
  },
});
// arvore?.orders[0].items[0].product.nome — tipo navegável até a folha
Atenção — with: true sem filtro
orders: true carrega todos os pedidos de cada usuário — para um usuário com 5.000 pedidos, é tudo. Em produção, sempre considere se isso é o desejado. Para limitar o eager loading, use a forma de objeto: orders: { limit: 10, orderBy: [desc(orders.criadoEm)] }. O Capítulo 17 detalha esse padrão.

# extras — campos calculados

A opção extras adiciona colunas calculadas ao resultado — útil para totais, contagens ou expressões que dependem de outras tabelas. O valor é uma expressão sql com alias via .as(); o parâmetro de tipo do sql informa o tipo TypeScript do retorno.

query/find-extras.ts
import { sql } from 'drizzle-orm';

const pedidosComTotal = await db.query.orders.findMany({
  extras: {
    valorTotal: sql<string>`(
      SELECT COALESCE(SUM(preco_unit * quantidade), 0)
      FROM order_items
      WHERE order_items.order_id = orders.id
    )`.as('valor_total'),
  },
});
// pedidosComTotal: (Order & { valorTotal: string })[]

# Como o Drizzle resolve a query

Para uma query relacional com with, o Drizzle gera SQL com subqueries lateralizadas — não JOINs. Cada filho é uma subquery que retorna um array agregado em JSON, anexado a cada linha do pai. O resultado: uma linha por entidade pai (não pais × filhos), com a árvore inteira em estrutura JSON dentro da própria linha. Isso é o que elimina a explosão cartesiana mencionada no Capítulo 15.

Subqueries lateralizadas em detalhe
A estratégia paga um custo fixo de serialização JSON no banco, mas evita multiplicação de linhas. Para um usuário com 100 pedidos de 10 itens, um JOIN encadeado retornaria 1.000 linhas pelo wire; a subquery lateral retorna 1 linha com um campo JSON estruturado. Em testes práticos, é mais rápido em quase todos os casos de leitura aninhada — mais lento apenas em queries que combinam navegação com agregações horizontais (caso para o query builder).

# Quando usar relational query vs query builder

O critério é raramente sobre preferência — é sobre a forma natural do resultado. Se o que você quer é uma árvore aninhada, relational query. Se o que você quer é uma tabela achatada com colunas agregadas, query builder. Os exemplos a seguir explicitam o critério em casos comuns:

decidindo entre os dois
// CASO 1: "usuário com seus pedidos e itens"
// → árvore natural → db.query.users.findFirst({ with: ... })

// CASO 2: "total de vendas por categoria nos últimos 30 dias"
// → agregação com GROUP BY → db.select().from(...).groupBy(...) (Cap 18)

// CASO 3: "produtos com a categoria preenchida"
// → pai com um filho 1:1 → db.query.products.findMany({ with: { categoria: true } })

// CASO 4: "tabela de pedido x produto x quantidade para um CSV"
// → achatado por natureza → db.select().from().innerJoin(...) (Cap 15)

// CASO 5: "pedido + total calculado"
// → entidade com cálculo → db.query.orders.findMany({ extras: { total: ... } })
Regra prática
Comece sempre tentando expressar a query como db.query. Se o que sai não é a forma que o consumidor precisa — porque envolve agregação, achatamento intencional, ou subqueries complexas — volte para o query builder. As duas APIs convivem no mesmo arquivo, no mesmo módulo, na mesma transação: não há custo de mudar.

Capítulo 17

with — eager loading

O with introduzido no Capítulo 16 aceita duas formas: true traz todos os filhos sem filtro, ou um objeto que aceita as mesmas opções de um findMany aninhado — columns, where, orderBy, limit, with recursivo e extras. Este capítulo detalha cada opção dentro de with, com atenção especial a duas peculiaridades que diferem do SQL puro: limit que vale por pai (não global) e where que filtra apenas filhos (não exclui pais).

# columns dentro de with

Projetar apenas as colunas necessárias dos filhos segue exatamente a mesma sintaxe da opção columns de primeiro nível: modo include (true) ou modo omit (false), nunca os dois misturados.

query/with-columns.ts
const usuarios = await db.query.users.findMany({
  columns: { id: true, nome: true },
  with: {
    orders: {
      columns: { id: true, status: true, criadoEm: true },
    },
  },
});
// usuarios: { id; nome; orders: { id; status; criadoEm }[] }[]

# where — filtros nos filhos

Um where dentro de with filtra apenas as linhas filhas carregadas — não exclui pais sem filhos correspondentes. Um usuário sem pedidos pendentes aparece no resultado com orders: [], não some da lista. Esse é o comportamento natural de uma subquery lateral, e o oposto de um INNER JOIN:

query/with-where.ts
import { eq, gt } from 'drizzle-orm';

const usuariosComPendentes = await db.query.users.findMany({
  with: {
    orders: {
      where: eq(orders.status, 'pendente'),
    },
  },
});
// Todos os usuários aparecem.
// Usuários sem pedidos pendentes: orders = []
// Usuários com pedidos pendentes: orders = [...apenas os pendentes]
where em with NÃO exclui pais
Para listar apenas usuários que têm pedidos pendentes, o filtro precisa estar também no where do pai, geralmente com exists. O where dentro de with sozinho não cumpre esse papel — ele apenas restringe os filhos retornados, mantendo todos os pais. O padrão correto está mais adiante neste capítulo, na seção "Filtrando pai com base em filhos".

# orderBy e limit em filhos

Aqui está uma das características mais úteis das relational queries: limit dentro de with é aplicado por pai, não global. Para "últimos 3 pedidos de cada usuário", basta declarar limit: 3 dentro de with. Em SQL puro, isso exigiria window functions com ROW_NUMBER(); aqui é trivial.

query/with-limit-per-parent.ts
import { desc } from 'drizzle-orm';

const usuariosUltimos3 = await db.query.users.findMany({
  with: {
    orders: {
      orderBy: [desc(orders.criadoEm)],
      limit:   3, // últimos 3 POR USUÁRIO — não global
    },
  },
});
// Cada user.orders tem no máximo 3 elementos — os mais recentes
Como Drizzle implementa limit por pai
A subquery lateral correlacionada inclui ORDER BY ... LIMIT n dentro do escopo de cada pai, antes de agregar em JSON. Internamente, o PostgreSQL executa essa subquery uma vez por linha do pai — então o custo escala linearmente com o número de pais. Para conjuntos com milhares de pais e limit em filhos, prefira separar em duas queries (uma para os pais, outra para os filhos) quando o ganho de cache compensar.

# with aninhado profundo

O with aceita with recursivo, sem profundidade fixa. Cada nível recebe o mesmo conjunto de opções — você pode combinar filtros, ordenação e projeção em cada degrau da árvore:

query/with-profundo.ts
const arvore = await db.query.users.findFirst({
  where: eq(users.id, 1),
  columns: { id: true, nome: true },
  with: {
    orders: {
      where:   gt(orders.criadoEm, new Date('2024-01-01')),
      orderBy: [desc(orders.criadoEm)],
      limit:   10,
      with: {
        items: {
          columns: { quantidade: true, precoUnit: true },
          with: {
            product: {
              columns: { id: true, nome: true },
              with: { categoria: true },
            },
          },
        },
      },
    },
  },
});

# extras dentro de with

A opção extras também funciona em qualquer nível de with, adicionando colunas calculadas a cada filho. O caso clássico é o total de cada pedido calculado a partir dos itens:

query/with-extras.ts
import { sql } from 'drizzle-orm';

const usersComTotal = await db.query.users.findMany({
  with: {
    orders: {
      extras: {
        total: sql<string>`(
          SELECT COALESCE(SUM(preco_unit * quantidade), 0)
          FROM order_items
          WHERE order_items.order_id = orders.id
        )`.as('total'),
      },
    },
  },
});
// Cada order agora tem .total calculado pelo banco

# Filtrando pai com base em filhos

O where dentro de with não exclui pais sem filhos correspondentes — para isso, o filtro precisa estar também no where do pai, normalmente expresso como exists sobre uma subquery na tabela filha:

query/pai-com-base-em-filhos.ts
import { exists, eq, and } from 'drizzle-orm';

// Apenas usuários que TÊM pedidos pagos, e só os pedidos pagos
const compradores = await db.query.users.findMany({
  where: exists(
    db.select({ _: orders.id })
      .from(orders)
      .where(and(
        eq(orders.userId, users.id),
        eq(orders.status, 'pago'),
      )),
  ),
  with: {
    orders: {
      where: eq(orders.status, 'pago'),
    },
  },
});
Dica
A condição precisa aparecer duas vezes — uma no exists do pai, outra no with dos filhos — porque cada uma resolve um problema distinto. Sem o exists, pais sem pedidos pagos apareceriam com orders: []. Sem o where no with, todos os pedidos seriam carregados (incluindo pendentes). Encapsule essa lógica em uma função quando o padrão se repetir muitas vezes — o custo de manter duas condições sincronizadas é a desvantagem real desse padrão.

# Quando o eager loading não compensa

A subquery lateral é eficiente para a maioria dos casos, mas não é gratuita. Em três cenários específicos, vale considerar alternativas:

Agregação — count, sum, avg e groupBy

Drizzle disponibiliza as funções de agregação mais comuns — count, sum, avg, min, max — como funções importáveis que compõem naturalmente com o query builder. Para qualquer coisa além disso (window functions, percentis, arrays agregados), o template sql cobre o restante. Este capítulo percorre cada função, o uso de groupBy e having, e os padrões mais comuns de relatórios e contagens do schema de e-commerce.

# count — contando linhas

count() sem argumento gera COUNT(*) e conta todas as linhas. count(coluna) gera COUNT(coluna) e exclui os valores NULL nessa coluna — a diferença importa em tabelas com colunas nullable:

query/count.ts
import { count, eq } from 'drizzle-orm';

// COUNT(*) — conta todas as linhas
const [{ total }] = await db
  .select({ total: count() })
  .from(users);
// total: number

// COUNT(col) — exclui NULLs na coluna
const [{ comCategoria }] = await db
  .select({ comCategoria: count(products.categoriaId) })
  .from(products);
// Conta apenas produtos com categoriaId IS NOT NULL

// COUNT DISTINCT — via sql template
import { sql } from 'drizzle-orm';

const [{ dominios }] = await db
  .select({
    dominios: sql<number>`COUNT(DISTINCT split_part(${users.email}, '@', 2))`,
  })
  .from(users);
count() vs count(col)
count() é quase sempre o que você quer — conta linhas independente de qualquer valor. count(col) é útil especificamente quando você precisa saber quantas linhas têm um valor numa coluna nullable. Em relatórios, combine os dois para descobrir a diferença: count() − count(col) = número de NULLs.

# sum, avg, min, max

As quatro funções numéricas retornam string | null — string porque o driver PostgreSQL serializa valores numeric/decimal como string para evitar perda de precisão, e null porque retornam NULL quando nenhuma linha satisfaz o filtro. Converta para número explicitamente quando necessário:

query/agregacao-numerica.ts
import { sum, avg, min, max, count, eq } from 'drizzle-orm';

const [stats] = await db
  .select({
    totalProdutos: count(),
    somaPrecos:    sum(products.preco),   // string | null
    mediaPreco:    avg(products.preco),   // string | null
    menorPreco:    min(products.preco),   // string | null
    maiorPreco:    max(products.preco),   // string | null
  })
  .from(products)
  .where(eq(products.ativo, true));

// Converter para número quando necessário:
const media = stats.mediaPreco ? parseFloat(stats.mediaPreco) : 0;
Por que string | null
O tipo NUMERIC do PostgreSQL tem precisão arbitrária — maior que Number.MAX_SAFE_INTEGER em JavaScript. O driver retorna o valor como string para não perder precisão. Converta com parseFloat para cálculos simples ou use a biblioteca decimal.js quando precisão total for crítica (valores financeiros, por exemplo).

# groupBy

.groupBy() aceita qualquer combinação de colunas e expressões. As colunas em groupBy devem aparecer na projeção do select (ou em funções de agregação) — o PostgreSQL rejeita a query caso contrário:

query/group-by.ts
import { count, avg, desc } from 'drizzle-orm';

// Estatísticas por categoria
const porCategoria = await db
  .select({
    categoriaId:   products.categoriaId,
    totalProdutos: count(products.id),
    precoMedio:    avg(products.preco),
    maiorPreco:    max(products.preco),
  })
  .from(products)
  .where(eq(products.ativo, true))
  .groupBy(products.categoriaId)
  .orderBy(desc(count(products.id)));

// porCategoria: { categoriaId: number | null; totalProdutos: number; precoMedio: string | null; maiorPreco: string | null }[]

# groupBy com JOIN

Para combinar dados de múltiplas tabelas em um agrupamento — vendas por usuário, por exemplo — encadeie JOINs antes do groupBy. Todas as colunas não-agregadas que aparecem no select precisam estar também no groupBy:

query/group-by-join.ts
import { count, sum, desc, eq } from 'drizzle-orm';

const rankVendas = await db
  .select({
    userId:       orders.userId,
    nomeUser:     users.nome,
    totalPedidos: count(orders.id),
    valorTotal:   sum(orderItems.precoUnit),
  })
  .from(orders)
  .innerJoin(users,      eq(users.id,          orders.userId))
  .innerJoin(orderItems, eq(orderItems.orderId, orders.id))
  .groupBy(orders.userId, users.nome)
  .orderBy(desc(sum(orderItems.precoUnit)))
  .limit(10);

# having — filtro pós-agrupamento

.having() filtra grupos depois do agrupamento — equivalente ao HAVING do SQL. Qualquer operador do Capítulo 11 funciona aqui, inclusive sobre funções de agregação. Não use having para filtros que poderiam estar no where — o banco aplica o where antes de agrupar, reduzindo o conjunto processado:

query/having.ts
import { count, avg, gt, and } from 'drizzle-orm';

// Categorias com mais de 5 produtos ativos e preço médio acima de 50
const categoriasRicas = await db
  .select({
    categoriaId: products.categoriaId,
    total:       count(products.id),
    mediaPreco:  avg(products.preco),
  })
  .from(products)
  .where(eq(products.ativo, true))        // filtra ANTES de agrupar
  .groupBy(products.categoriaId)
  .having(and(
    gt(count(products.id), 5),              // grupos com mais de 5
    gt(avg(products.preco), '50'),           // média acima de 50
  ));
WHERE antes do HAVING
Filtros sobre colunas não-agregadas pertencem ao where, nunca ao having. having(eq(products.ativo, true)) funciona mas faz o banco processar todos os produtos para depois descartar — o where reduz o conjunto de entrada antes do agrupamento. Só use having para condições sobre o resultado de funções de agregação.

Transações — atomicidade controlada

Uma transação agrupa várias operações como uma unidade atômica: ou todas se confirmam, ou nenhuma deixa efeito visível. Em Drizzle, transações são expressas com db.transaction(callback) — o callback recebe um objeto tx que substitui o db para todas as operações dentro daquela transação. Este capítulo cobre rollback automático e manual, savepoints aninhados, níveis de isolamento e o padrão de retry para conflitos de serialização.

# db.transaction — o básico

O callback recebe tx, que tem todos os mesmos métodos de db — select, insert, update, delete, query. Toda operação executada via tx dentro do callback faz parte da transação. O valor de retorno do callback é o valor de retorno da chamada externa:

query/transacao-basica.ts
const resultado = await db.transaction(async (tx) => {
  // 1. Cria o usuário
  const [user] = await tx
    .insert(users)
    .values({ email: 'novo@ex.com', nome: 'Novo' })
    .returning();

  // 2. Cria o pedido vinculado ao usuário recém-criado
  const [order] = await tx
    .insert(orders)
    .values({ userId: user.id, status: 'pendente' })
    .returning();

  // 3. Adiciona itens ao pedido
  await tx.insert(orderItems).values([
    { orderId: order.id, productId: 1, quantidade: 2, precoUnit: '50.00' },
    { orderId: order.id, productId: 2, quantidade: 1, precoUnit: '30.00' },
  ]);

  return { user, order };
});

// resultado: { user, order } — tipos completos inferidos
Atenção — sempre use tx, nunca db
Dentro do callback de transação, todas as operações precisam usar o parâmetro tx. Se você acidentalmente chamar db.insert(...) em vez de tx.insert(...), essa operação roda fora da transação — sem rollback, sem atomicidade. O TypeScript não detecta esse erro porque db existe no escopo externo. A revisão de código é a principal defesa.

# Rollback automático em throw

Se o callback lançar uma exceção, a transação inteira é revertida — automaticamente, sem ação adicional. O erro continua propagando para fora de db.transaction(), permitindo que o chamador lide como achar melhor:

query/transacao-throw.ts
try {
  await db.transaction(async (tx) => {
    await tx.update(users)
      .set({ saldo: sql`${users.saldo} - 100` })
      .where(eq(users.id, 1));

    const [u] = await tx.select().from(users).where(eq(users.id, 1));

    // Validação após o update — se falhar, o update é revertido
    if (Number(u.saldo) < 0) {
      throw new Error('Saldo insuficiente');
    }

    await tx.insert(orders).values({ userId: 1, status: 'pago' });
  });
} catch (err) {
  // Update e insert revertidos. Saldo do usuário 1 inalterado.
  console.error('Operação revertida:', err);
}

# Rollback manual via tx.rollback()

Para reverter uma transação sem propagar erro como exceção semântica, use tx.rollback(). Internamente, o método lança uma exceção controlada que Drizzle reconhece e trata como rollback intencional — então a chamada externa não recebe o erro:

query/rollback-manual.ts
const sucesso = await db.transaction(async (tx) => {
  const [produto] = await tx.select()
    .from(products)
    .where(eq(products.id, 42));

  if (produto.estoque < 1) {
    await tx.rollback();
    // Linha abaixo nunca executa — rollback() lança internamente
  }

  await tx.update(products)
    .set({ estoque: sql`${products.estoque} - 1` })
    .where(eq(products.id, 42));

  return true;
});

# Savepoints — transações aninhadas

tx.transaction() dentro de uma transação cria um savepoint — um ponto de checkpoint que pode ser revertido sozinho, sem afetar a transação externa. O comportamento depende de como você lida com erros do bloco interno:

query/savepoint.ts
await db.transaction(async (tx) => {
  await tx.insert(users).values({ email: 'a@ex.com', nome: 'A' });

  // Tentativa que pode falhar — captura o erro localmente
  try {
    await tx.transaction(async (sp) => {
      await sp.insert(users).values({ email: 'a@ex.com', nome: 'A2' });
      // Falha por email duplicado
    });
  } catch {
    // Apenas o savepoint reverteu — o insert externo de A permanece
  }

  await tx.insert(orders).values({ userId: 1, status: 'pendente' });
  // Esta operação faz parte da transação externa, que ainda está viva
});
Sem captura, o erro propaga
Se você não capturar o erro do savepoint com try/catch, ele propaga para a transação externa — que então reverte tudo, inclusive as operações antes do savepoint. A captura local é o que torna o savepoint útil: ele permite tentar algo opcional sem comprometer o trabalho já feito.

# Níveis de isolamento

O segundo argumento de db.transaction() aceita configurações de isolamento do PostgreSQL. O nível padrão é read committed; para garantias mais fortes, especifique:

query/isolation-level.ts
await db.transaction(
  async (tx) => {
    // operações que precisam de garantia forte de consistência
    const [carrinho] = await tx.select()
      .from(carrinhos)
      .where(eq(carrinhos.id, 1));

    // outra transação não pode alterar carrinhos.id=1 entre o select e o update
    await tx.update(carrinhos)
      .set({ total: recalcular(carrinho) })
      .where(eq(carrinhos.id, 1));
  },
  {
    isolationLevel: 'serializable',  // mais forte; pode lançar 40001
    accessMode:     'read write',
    deferrable:     true,
  }
);

# Conflitos de serialização e retry

Em serializable, o PostgreSQL pode rejeitar a transação no commit com o erro 40001 (serialization failure) quando detecta que executar concorrentemente violaria a serialização. A solução é detectar o erro e retentar — com backoff exponencial para evitar tempestades de retries:

query/retry-pattern.ts
async function comRetry(
  callback: (tx: unknown) => Promise<unknown>,
  maxTentativas = 3,
) {
  let ultimoErro;
  for (let i = 0; i < maxTentativas; i++) {
    try {
      return await db.transaction(callback, {
        isolationLevel: 'serializable',
      });
    } catch (err: any) {
      if (err.code !== '40001') throw err; // não é deadlock — propaga
      ultimoErro = err;
      // backoff exponencial: 50, 100, 200 ms
      await new Promise((r) => setTimeout(r, 50 * 2 ** i));
    }
  }
  throw ultimoErro;
}
Quando usar serializable
Reserve serializable para operações que envolvem leitura seguida de escrita baseada na leitura — débito de saldo, ajuste de estoque, atribuição de número sequencial customizado. Para a maioria dos casos, read committed (padrão) é suficiente: oferece atomicidade dentro da transação sem o custo do retry pattern. O Volume X (Capítulo 14 de SQL/PostgreSQL) detalha os trade-offs entre os quatro níveis.

# Quando usar transações

A regra é simples: sempre que duas ou mais operações precisam ser logicamente atômicas. Casos típicos no schema de e-commerce:

casos de uso
// 1. Checkout: criar pedido + reservar estoque + cobrar saldo
//    Se qualquer etapa falhar, nada deve persistir.

// 2. Cancelamento: marcar pedido como cancelado + restaurar estoque
//    + estornar saldo + emitir evento de domínio.

// 3. Transferência entre contas: débito em uma + crédito em outra.
//    O caso clássico — sem transação, dinheiro pode sumir ou se duplicar.

// 4. Sincronização de pais e filhos: atualizar order + recriar order_items.
//    Se a recriação falhar, o order não deve ficar com itens parciais.

// CASOS SEM transação: leitura pura, operação isolada de uma única tabela,
// quando a falha parcial é aceitável (logs, métricas, audit trail).
Performance e locks
Transações longas mantêm locks por todo o seu tempo de execução — outras conexões que tentam modificar as mesmas linhas ficam bloqueadas. Mantenha transações curtas e focadas: faça preparação (validações, cálculos) antes de db.transaction(), e leve apenas as operações de banco essenciais para dentro do callback. Em ambientes de alta concorrência, transações de mais de centenas de milissegundos viram fonte de contenção.

Migrations — schema versionado

O Capítulo 4 introduziu os comandos do Drizzle Kit. Este capítulo aprofunda o que acontece em cada um deles e como construir um fluxo de migrations seguro para produção — incluindo expand/contract para zero-downtime, o problema das renomeações detectadas como DROP + ADD, migrations com transformação de dados, e o caminho para Drizzle 1.0. A premissa é simples: migrations precisam ser previsíveis, revisáveis e — quando possível — reversíveis.

# generate, push e migrate — recapitulação

Os três comandos cobrem situações diferentes, e misturar os papéis é a principal fonte de problemas em produção. A separação correta é a seguinte:

três comandos, três ambientes
# DESENVOLVIMENTO LOCAL — iteração rápida, sem histórico
npx drizzle-kit push
# Aplica direto no banco local. Útil enquanto o schema ainda muda muito.

# MOMENTO DE CONSOLIDAR — fechou a feature, hora de gerar a migration
npx drizzle-kit generate --name add_status_pedido
# Gera drizzle/000N_add_status_pedido.sql + snapshot. Inspecione e commite.

# STAGING / PRODUÇÃO — aplica migrations versionadas
npx drizzle-kit migrate
# Lê drizzle/, aplica o que ainda não foi registrado em __drizzle_migrations.

# Como funcionam journal e snapshots

O kit mantém duas representações paralelas do schema. Os arquivos .sql em drizzle/ são a sequência aplicada — cada um descreve a mudança incremental sobre o estado anterior. Os arquivos meta/000N_snapshot.json guardam o estado completo do schema após cada migration, e meta/_journal.json indexa todos eles com hashes para detectar adulterações.

anatomia da pasta drizzle/
drizzle/
├── 0000_initial.sql                # CREATE TABLE users, products, ...
├── 0001_add_categoria_id.sql       # ALTER TABLE products ADD COLUMN ...
├── 0002_create_orders.sql          # CREATE TABLE orders, order_items
└── meta/
    ├── 0000_snapshot.json          # schema completo após 0000
    ├── 0001_snapshot.json          # schema completo após 0001
    ├── 0002_snapshot.json          # schema completo após 0002
    └── _journal.json               # índice ordenado de todas as migrations

Quando você roda generate, o kit lê o snapshot mais recente, compara com o schema TS atual, calcula o diff em DDL, e cria o próximo arquivo .sql + snapshot. O migrate não usa snapshots — consulta apenas o journal contra a tabela __drizzle_migrations no banco para saber quais arquivos ainda não foram aplicados.

# O problema da renomeação

Drizzle Kit não tem como saber, lendo apenas o schema TS, se você renomeou uma coluna ou se deletou uma antiga e criou uma nova. Sem ajuda explícita, o diff é interpretado como DROP + ADD — e os dados da coluna antiga são perdidos:

renomeação cega: DROP + ADD
// ANTES
export const users = pgTable('users', {
  nome: varchar('nome', { length: 120 }).notNull(),
});

// DEPOIS — só renomei a coluna no schema
export const users = pgTable('users', {
  nomeCompleto: varchar('nome_completo', { length: 120 }).notNull(),
});

// generate sem confirmação produz:
// ALTER TABLE users DROP COLUMN nome;
// ALTER TABLE users ADD COLUMN nome_completo VARCHAR(120) NOT NULL;
// → perde todos os dados de nome
Use o prompt interativo
Quando o generate detecta colunas removidas e colunas novas no mesmo passo, ele exibe um prompt: "Is column nome_completo in users created or renamed from nome?". Responda sempre com atenção — o "y" para renomear gera ALTER TABLE users RENAME COLUMN nome TO nome_completo, preservando os dados. Em pipelines CI sem TTY, configure strict: true e gere a migration localmente antes de commitar.

# Migrations com transformação de dados

O generate só produz DDL — alteração de estrutura. Migrações que precisam transformar dados existentes (preencher uma nova coluna, normalizar valores, recalcular totais) exigem edição manual do .sql gerado. Drizzle não impede:

drizzle/0005_split_nome.sql — editado à mão
-- DDL gerada pelo kit
ALTER TABLE users ADD COLUMN primeiro_nome VARCHAR(60);
ALTER TABLE users ADD COLUMN ultimo_nome   VARCHAR(60);

-- Backfill manual — divide o campo nome existente
UPDATE users
   SET primeiro_nome = split_part(nome, ' ', 1),
       ultimo_nome   = split_part(nome, ' ', 2);

-- Agora as colunas estão preenchidas — só então aplicamos NOT NULL
ALTER TABLE users ALTER COLUMN primeiro_nome SET NOT NULL;

# Expand/contract — zero-downtime

Migrations destrutivas em uma única etapa quebram a aplicação enquanto ela executa. Para mudar uma estrutura sem indisponibilidade, o padrão é fragmentar a mudança em três fases (expand, backfill, contract), com deploys da aplicação entre elas. O caso clássico é renomear um campo:

expand/contract para renomear nome → nome_completo
-- FASE 1 (EXPAND): adicionar a nova coluna sem remover a antiga
ALTER TABLE users ADD COLUMN nome_completo VARCHAR(120);
-- Deploy da aplicação que ESCREVE em ambas as colunas e LÊ da antiga

-- FASE 2 (BACKFILL): preencher a nova coluna com base na antiga
UPDATE users SET nome_completo = nome WHERE nome_completo IS NULL;
ALTER TABLE users ALTER COLUMN nome_completo SET NOT NULL;
-- Deploy da aplicação que ESCREVE só em nome_completo e LÊ de nome_completo

-- FASE 3 (CONTRACT): remover a coluna antiga após validar
ALTER TABLE users DROP COLUMN nome;
Regras do expand/contract
Expand sempre pode ser revertido sem perda — é apenas adicionar coisas (colunas novas, tabelas novas, índices novos).
Backfill é a parte longa em tabelas grandes — execute em chunks dentro de uma transação por chunk, com pausa entre os chunks para não saturar o I/O.
Contract é irreversível — só execute depois de confirmar que nenhuma versão antiga da aplicação ainda está rodando em algum nó.

# Migrations em CI/CD

O padrão recomendado para deploys em ambientes gerenciados separa a aplicação de migrations da subida da aplicação. Isso evita corridas entre processos e garante que o banco está no estado esperado antes de qualquer instância da aplicação começar a servir tráfego:

pipeline de deploy

npm test

## ESTÁGIO 2 — Migrate (job único, antes do deploy)

# Cada instância nova já encontra o schema esperado.

Locks e migrations em tabelas grandes
Alguns comandos DDL adquirem locks exclusivos sobre a tabela inteira — ALTER TABLE ADD COLUMN com default não-constante e ALTER TABLE ADD CONSTRAINT sem NOT VALID são os culpados frequentes. Em tabelas com bilhões de linhas, isso pode parar a aplicação por minutos. Em PostgreSQL moderno, prefira: ADD COLUMN sem default → UPDATE em chunks → SET DEFAULT separado; ADD CONSTRAINT ... NOT VALID → VALIDATE CONSTRAINT separado. Cada etapa é rápida; a longa fica em background.

# Rollback manual

Drizzle não gera "down migrations" automaticamente — não há um drizzle-kit migrate down. A decisão de design parte de uma observação prática: rollbacks raramente são triviais em produção (uma coluna deletada não pode ser desfeita após inserções; um split de tabela não tem unscrambling automático). Em vez de prometer reversibilidade que não existe, o kit pede que você crie uma nova migration que desfaça a anterior:

# 3. Inspecionar drizzle/0008_revert_nova_coluna.sql
#    Deve conter: ALTER TABLE ... DROP COLUMN ...

SQL raw e prepared statements

O template sql de Drizzle apareceu brevemente em vários capítulos anteriores — em expressões de select, no set de updates, em check constraints e window functions. Este capítulo consolida o que o template faz internamente, cobre os casos de uso que exigem SQL completamente livre de query builder — DDL customizado, EXPLAIN ANALYZE, TRUNCATE — e apresenta prepared statements via prepare() e sql.placeholder().

# Como o template sql funciona

O sql é uma tagged template function. Quando você escreve sql\`WHERE id = ${id}\`, o resultado não é uma string — é um objeto que carrega separadamente os literais SQL e os valores interpolados. Quando esse objeto chega ao driver, o Drizzle monta uma query parametrizada com $1, $2 etc., e envia os valores como parâmetros separados. Nenhum valor é interpolado como string na query — isso é o que garante segurança contra injeção:

como o template separa literal de valor
import { sql } from 'drizzle-orm';

const id = 42;

// sql`...` cria um objeto, não uma string
const expr = sql`SELECT * FROM users WHERE id = ${id}`;

// O que é enviado ao banco:
// query: SELECT * FROM users WHERE id = $1
// params: [42]

// Interpolação de coluna — referência à própria coluna do schema
const filtro = sql`${orders.criadoEm} > NOW() - INTERVAL '7 days'`;
// query: "criado_em" > NOW() - INTERVAL '7 days'   (sem $1 — é identificador)
Valores vs identificadores
Quando você interpola um valor (número, string, Date) no template sql, ele vira um parâmetro $N. Quando você interpola uma coluna do schema (como ${orders.criadoEm}), o Drizzle reconhece o tipo e insere o nome escapado como identificador SQL — não como parâmetro. Isso é o que permite misturar referências a colunas com valores literais no mesmo template.

# sql dentro do query builder

A maioria dos usos de sql já foi vista nos capítulos anteriores — a referência resumida a seguir serve como índice de consulta rápida:

usos comuns revisitados
// Em projeção de select — coluna calculada tipada
db.select({ total: sql<number>`COUNT(*)` }).from(users)

// Em where — expressão arbitrária
db.select().from(orders)
  .where(sql`${orders.criadoEm} > NOW() - INTERVAL '30 days'`)

// Em set de update — operação atômica
db.update(products)
  .set({ estoque: sql`${products.estoque} + 1` })

// Em window function (Cap 18)

# db.execute() — SQL completamente livre

Para comandos que não se encaixam no query builder — DDL customizado, TRUNCATE, COPY, VACUUM, chamadas a funções PostgreSQL — use db.execute() com um template sql. O método retorna o resultado raw do driver:

query/execute.ts
// DDL que o kit não gera automaticamente
await db.execute(
  sql`CREATE EXTENSION IF NOT EXISTS pg_trgm`
);

// Limpar tabela em testes
await db.execute(
  sql`TRUNCATE TABLE order_items, orders, products, users RESTART IDENTITY CASCADE`
);

// Chamar função PostgreSQL com valor parametrizado
const userId = 42;
await db.execute(
  sql`SELECT pg_notify('pedido_novo', ${String(userId)})`
);

Uma das aplicações mais úteis do execute() é inspecionar o plano de execução de uma query Drizzle sem sair do TypeScript. Passe a query como interpolação do template — o Drizzle expande seu SQL interno:

query/explain.ts
const query = db
  .select()

  .where(eq(products.ativo, true))
  .orderBy(desc(products.preco))
  .limit(20);

const plano = await db.execute(

// plano.rows[0] contém o JSON do plano de execução do PostgreSQL

# prepare() — prepared statements

Prepared statements enviam a query para o PostgreSQL uma vez para parse e planejamento; execuções subsequentes passam apenas os parâmetros. Isso economiza tempo de parse em queries de alta frequência e melhora a segurança ao separar estrutura de dados. Em Drizzle, qualquer query do query builder pode virar um prepared statement com .prepare('nome'):

query/prepared.ts
import { sql } from 'drizzle-orm';

// Declara o statement com placeholder — executado fora daqui
const buscarUser = db
  .select()
  .from(users)
  .where(eq(users.id, sql.placeholder('id')))
  .prepare('buscar_user_por_id');

// Execuções subsequentes — apenas parâmetros viajam
const u1 = await buscarUser.execute({ id: 1 });
const u2 = await buscarUser.execute({ id: 2 });

// Múltiplos placeholders
const buscarProdutos = db
  .select()
  .from(products)
  .where(and(
    eq(products.categoriaId, sql.placeholder('catId')),
    eq(products.ativo,      sql.placeholder('ativo')),
  ))
  .prepare('produtos_por_categoria');

const lista = await buscarProdutos.execute({ catId: 3, ativo: true });
Prepared statements e poolers
Prepared statements são armazenados por conexão no PostgreSQL — não sobrevivem a reconexões ou troca de conexão no pool. Com PgBouncer em Transaction mode, cada query pode ir para uma conexão diferente, o que significa que o statement preparado em uma conexão não existe na próxima. Para usar prepare() com pooler, configure PgBouncer em Session mode, ou use Neon/Supabase Session mode (porta 5432). Em Transaction mode, defina prepare: false no driver (como visto no Capítulo 3).

# sql.raw() — identificadores dinâmicos

sql.raw() insere uma string literalmente no SQL, sem parametrizar como valor e sem escapar como identificador. É necessário em casos raros onde o nome do objeto (tabela, coluna, schema) é determinado em runtime e não pode ser expresso como referência estática do schema:

sql.raw() — com cuidado
import { sql } from 'drizzle-orm';

// Coluna de ordenação vinda de configuração interna (não de input do usuário)
const colunaOrdem: 'criado_em' | 'preco' | 'nome' = 'criado_em';

const resultado = await db.execute(
  sql`SELECT * FROM products ORDER BY ${sql.raw(colunaOrdem)} DESC`
);
sql.raw() não escapa — nunca use com input externo
sql.raw('users') insere users literalmente. sql.raw(req.body.tabela) é injeção de SQL. Sempre valide a string contra uma lista de valores permitidos antes de passá-la para sql.raw() — ou, melhor, use um mapa de opções seguras: const colunas = { nome: products.nome, preco: products.preco }; const col = colunas[req.query.sort].

# Pool de conexões: dimensionamento por ambiente

O Capítulo 3 introduziu os drivers e os modos de conexão. Em produção, a escolha de max no pool é tão importante quanto a escolha do driver. PostgreSQL tem um limite global de conexões (max_connections, por padrão 100). Cada processo da aplicação consome do mesmo orçamento:

dimensionamento por ambiente
// Node.js longo (API, servidor) — pool por processo
const client = postgres(process.env.DATABASE_URL!, {
  max: 10,                 // 10 conexões por processo
  idle_timeout: 20,        // fecha após 20s ociosos
  connect_timeout: 10,
});
// 4 processos × 10 = 40 conexões no PostgreSQL
// Resta orçamento para outras aplicações e operações administrativas

// Serverless com pooler externo — uma conexão por invocação
const client = postgres(process.env.DATABASE_URL!, {
  max: 1,                  // pooler externo lida com a multiplexação
  idle_timeout: 10,
  max_lifetime: 60 * 30,    // recicla a cada 30 min
});
A regra do orçamento
Calcule max_connections do Postgres ÷ número de processos da aplicação ÷ 2 como o teto seguro do max do pool. O fator 2 deixa margem para conexões administrativas (replicação, monitoramento, backups). Em ambientes serverless, sempre ponha um pooler externo na frente do banco — PgBouncer, ou o pooler nativo de Neon/Supabase. Sem ele, 100 invocações simultâneas esgotam o banco em segundos.

# N+1: detecção e prevenção

O clássico N+1 — onde uma query do pai dispara N queries adicionais para filhos — é raro em Drizzle pelas relational queries com subqueries lateralizadas (Capítulo 16). Mas o problema reaparece quando o código mistura os dois modos sem necessidade:

N+1 em ação — e como corrigir
// PROBLEMA — uma query para o pai, N queries para os filhos
const lista = await db.select().from(users);
const resultado = [];

for (const u of lista) {
  const ordersDoUser = await db
    .select()
    .from(orders)
    .where(eq(orders.userId, u.id));
  resultado.push({ ...u, orders: ordersDoUser });
}
// 1 + N queries — desastre em listagens grandes

// SOLUÇÃO — relational query com with
const resultado = await db.query.users.findMany({
  with: { orders: true },
});
// 1 query — uma subquery lateral resolve tudo
Detectando N+1 em desenvolvimento
Ative o logger do Drizzle em desenvolvimento (drizzle(client, { schema, logger: true })) — toda query aparece no console. Listagens de página com dezenas de queries idênticas variando apenas o parâmetro são o sintoma. Em produção, instrumente o driver para emitir métricas de contagem de queries por requisição HTTP — passar de 5 ou 10 queries por request geralmente indica um N+1 a investigar.

# A fronteira do type-safety: Drizzle + Zod

Drizzle entrega type-safety em compilação: o TypeScript sabe o tipo de cada coluna, garante que queries referenciam colunas existentes, e infere o shape do resultado a partir do schema. Mas isso vale apenas dentro do código TypeScript compilado. Tudo que cruza a fronteira da aplicação — requisições HTTP, variáveis de ambiente, mensagens de fila, JSONB inserido por outro processo — chega como unknown ou any, sem garantia em runtime.

É aí que entra a complementaridade com validação de runtime. O padrão é validar uma vez na borda (entrada da aplicação) e confiar nos tipos dali em diante:

a fronteira que Zod resolve
import { z } from 'zod';

// Schema de validação para o body do POST /users
const criarUserInput = z.object({
  email: z.string().email(),
  nome:  z.string().min(2).max(120),
});

// No handler do endpoint:
export async function handler(req) {
  // Valida em runtime — lança ZodError se o shape não bater
  const dados = criarUserInput.parse(req.body);
  // dados: { email: string; nome: string } — garantido em runtime

  // Daqui em diante o TypeScript do Drizzle assume — fluxo unificado
  const [criado] = await db.insert(users).values(dados).returning();
  return criado;
}

A integração entre os dois ecossistemas é direta via drizzle-zod — um pacote que gera schemas Zod automaticamente a partir das tabelas Drizzle, eliminando a duplicação de definir o tipo duas vezes:

drizzle-zod — schemas gerados
import { createInsertSchema, createSelectSchema } from 'drizzle-zod';
import { users } from './schema';

// Gera schema Zod a partir da tabela Drizzle
const insertUserSchema = createInsertSchema(users, {
  // Refinamentos extras opcionais por coluna
  email: (schema) => schema.email(),
  nome:  (schema) => schema.min(2),
});

// Agora usável em qualquer endpoint que aceite criação de usuário
const dados = insertUserSchema.parse(req.body);
await db.insert(users).values(dados);

# Onde este manual termina

Os capítulos deste volume cobriram Drizzle como uma camada fina sobre SQL: schema declarativo em TypeScript, query builder que se traduz literalmente para SQL, relational queries com subqueries lateralizadas, migrations versionadas, transações, integração com PostgreSQL via os drivers principais. O fio que conecta tudo é a previsibilidade — saber, em cada operação, exatamente o que vai chegar ao banco e o que vai voltar.

Drizzle resolve uma parte do problema de type-safety: a parte que vive dentro do código TypeScript compilado. A outra parte — o que cruza a fronteira da aplicação — pede uma ferramenta complementar. Os dois juntos fecham o loop: Drizzle garante o que está armazenado e como é lido; Zod garante o que entra e o que sai. A combinação é o estado da arte em type-safety de aplicações TypeScript modernas.
