Docker

O Git versionou o código no tempo; o Docker o empacota no espaço — junto de tudo que ele precisa para rodar igual em qualquer máquina. Onde "funciona na minha máquina" era uma desculpa, o container é a resposta: um recorte reproduzível do sistema operacional, isolado e portátil, que sobe idêntico no laptop, no CI e em produção. Este volume trata o Docker como um modelo de camadas e isolamento, não como uma lista de comandos: o que é uma imagem e o que é um container, como o Dockerfile constrói layers cacheáveis, multi-stage builds, volumes e redes, Compose para orquestrar serviços, e os padrões de segurança e enxugamento que separam uma imagem de brinquedo de uma imagem de produção.

Capítulo 1

O que é conteinerização

O Volume XIV fechou colocando todo o código da coleção sob versionamento: o Git deu a ele uma história navegável e uma forma de colaborar. Mas versionar o código resolve só metade do problema de "funciona na minha máquina". A outra metade é o ambiente — a versão exata do Node, as bibliotecas do sistema, as variáveis, o sistema operacional inteiro em volta do seu código. O Docker ataca essa segunda metade: se o Git empacota o código no tempo, o Docker o empacota no espaço, junto de tudo que ele precisa para rodar idêntico em qualquer lugar. Este capítulo estabelece o modelo mental antes de qualquer comando: o que é um container (e por que ele não é uma máquina virtual), como o isolamento no nível do sistema operacional torna containers leves, e a distinção entre imagem e container que organiza todo o resto do volume. Conteinerização não é uma ferramenta mágica de deploy — é uma forma precisa de empacotar um ambiente, e entender isso é o que torna o Docker previsível.

# O problema: "funciona na minha máquina"

A frase é um clichê porque o problema é universal. Você desenvolve a aplicação no seu laptop, ela roda perfeitamente, e ao subir para o servidor — ou para a máquina de um colega — ela quebra. As causas são sempre ambientais: a versão do Node é outra, uma biblioteca do sistema falta, uma variável de ambiente não está setada, o sistema operacional difere. O código é idêntico (o Git garante isso), mas o contexto em que ele roda não é. Cada máquina é um ambiente ligeiramente diferente, e essas diferenças se acumulam em bugs que só aparecem "lá", nunca "aqui".

A solução tradicional era documentar o ambiente — um README com "instale Node 22, Postgres 16, estas libs..." — e torcer para que todos reproduzissem os passos igual. Não funciona em escala: a documentação envelhece, os passos divergem, e "reproduzir manualmente" é exatamente o tipo de processo que erra. A conteinerização troca a documentação por um artefato executável: em vez de descrever o ambiente, você o empacota e o envia junto com o código.

# A ideia central: empacotar o ambiente junto

Um container é o código da sua aplicação mais todo o ambiente de que ele precisa — runtime, bibliotecas, dependências, configuração do sistema — empacotados numa unidade isolada e portátil que roda igual em qualquer máquina com Docker. Em vez de "instale estas dez coisas na ordem certa", você entrega um pacote que já contém as dez coisas, montadas exatamente como devem estar. O mesmo container que roda no seu laptop roda, byte por byte do ambiente, no CI e em produção.

Git empacota no tempo; Docker, no espaço
Os dois volumes se complementam diretamente. O Git versiona o código: cada estado recuperável, cada mudança rastreável ao longo do tempo. O Docker versiona o ambiente: um recorte reproduzível do sistema operacional e suas dependências, idêntico em qualquer espaço onde rode. Juntos, eliminam as duas fontes de "funciona na minha máquina" — o Git garante que o código é o mesmo, o Docker garante que o ambiente é o mesmo. É por isso que o Dockerfile vive versionado no repositório (Cap 9 do Vol XIV): o ambiente também é código.

# Container não é máquina virtual

A confusão mais comum é equiparar containers a máquinas virtuais. Ambos isolam aplicações, mas o mecanismo — e o custo — são radicalmente diferentes. Uma máquina virtual emula um computador inteiro: ela roda um sistema operacional completo (kernel próprio, e tudo acima) sobre um hypervisor. Isso é pesado — cada VM carrega gigabytes de SO e leva minutos para iniciar. Um container não emula nada: ele compartilha o kernel do sistema operacional hospedeiro e isola apenas o necessário acima dele — o sistema de arquivos, os processos, a rede. Não há SO convidado, não há emulação. Por isso um container inicia em milissegundos e pesa megabytes, não gigabytes.

VM vs container
# MÁQUINA VIRTUAL: cada uma carrega um SO completo (pesado, lento)
┌─────────┐ ┌─────────┐
│  App A  │ │  App B  │
│ libs    │ │ libs    │
│ SO conv.│ │ SO conv.│   <- cada VM tem um SO inteiro (GBs)
├─────────┴─┴─────────┤
│     Hypervisor      │
│   SO hospedeiro     │
│      Hardware       │
└─────────────────────┘

# CONTAINERS: compartilham o kernel do host (leve, rápido)
┌─────────┐ ┌─────────┐
│  App A  │ │  App B  │
│ libs    │ │ libs    │   <- só app + libs (MBs), sem SO convidado
├─────────┴─┴─────────┤
│   Docker Engine     │
│ Kernel do host (1)  │   <- UM kernel, compartilhado por todos
│      Hardware       │
└─────────────────────┘
Um container é um processo isolado
No fundo, um container é apenas um processo comum do sistema operacional hospedeiro, rodando com uma visão restrita do mundo. O kernel oferece mecanismos de isolamento — namespaces (que dão ao processo a ilusão de ter seu próprio sistema de arquivos, rede e lista de processos) e cgroups (que limitam quanta CPU e memória ele usa). O Docker orquestra esses mecanismos do kernel. Não há mágica nem emulação: é um processo do host, "convencido" de que está sozinho num sistema só dele. Entender isso desmistifica por que containers são tão leves — eles não são computadores, são processos com fronteiras.

# Imagem e container: molde e instância

Duas palavras aparecem o tempo todo e precisam ser distinguidas desde já (o Capítulo 2 aprofunda). Uma imagem é o pacote estático, somente-leitura: o sistema de arquivos com o código, o runtime e as dependências, congelado e pronto para rodar. Um container é uma instância em execução dessa imagem — a imagem ganhando vida como um processo. A relação é a de molde e produto: de uma imagem você cria quantos containers quiser, todos partindo do mesmo estado, como vários objetos instanciados de uma mesma classe (Vol I).

terminal
# Rodar o container de teste do Docker: baixa a imagem e a executa
docker run hello-world
# Hello from Docker! (a imagem rodou como um container e terminou)

# Rodar um container interativo a partir da imagem do Ubuntu
docker run -it ubuntu bash
# root@a1b2c3:/#  <- um shell DENTRO do container, isolado do seu SO
# (-i interativo, -t aloca um terminal; 'bash' é o comando a rodar)

# Vendo containers e imagens

Os dois comandos de inspeção mais básicos refletem a distinção imagem/container. docker images lista os moldes baixados na sua máquina; docker ps lista os containers em execução (as instâncias vivas). Dominar essa dupla é o primeiro passo prático — elas respondem "o que eu tenho disponível?" e "o que está rodando agora?".

terminal
# Imagens baixadas (os moldes disponíveis localmente)
docker images
# REPOSITORY   TAG       IMAGE ID       SIZE
# ubuntu       latest    a1b2c3d4...    78MB

# Containers em execução (as instâncias vivas)
docker ps
# CONTAINER ID   IMAGE     STATUS         NAMES

# Incluir também os containers já parados (-a = all)
docker ps -a

# Por que isso transforma o deploy

A consequência prática da conteinerização é profunda. Quando o ambiente vai empacotado junto, "deploy" deixa de ser "configurar um servidor para parecer com a minha máquina" e vira "rodar o mesmo container que eu testei". O artefato que você testa localmente é literalmente o que vai para produção — não uma reconstrução aproximada. Isso elimina toda uma classe de bugs de ambiente, torna o deploy reproduzível e reversível (rode a imagem da versão anterior), e permite escalar horizontalmente subindo cópias idênticas do mesmo container. É a fundação sobre a qual CI/CD (Cap 20) e orquestração (Cap 21) se constroem.

Isolamento não é, por si só, segurança total
Containers isolam processos, mas é um isolamento mais fraco que o de uma VM — todos compartilham o kernel do host. Um container comprometido com privilégios excessivos pode, em certos cenários, escapar para o hospedeiro. Por isso "está num container" não significa "está seguro" automaticamente. As práticas de segurança do Cap 17 — rodar como usuário não-root, limitar capacidades, imagens mínimas — existem justamente porque o isolamento de container é uma fronteira a ser endurecida, não uma muralha pronta. Os princípios de menor privilégio e defesa em profundidade do Vol XIII (Cap 21) reaparecem aqui aplicados a containers.

# Onde o Docker se encaixa no stack

Este volume conteineriza, ao longo dos capítulos, exatamente o stack que a coleção construiu: a aplicação Hono (Vol IX) com Drizzle (Vol XI) e a autenticação do Vol XIII, falando com um Postgres (Vol X) e um Redis (Vol XIII, Cap 6). Conteinerizar esse conjunto — a app numa imagem, o banco e o cache em seus próprios containers, todos orquestrados juntos (Cap 14, Docker Compose) — é o fio condutor prático que atravessa o volume. O modelo mental deste capítulo é a base; a partir do Cap 2, começamos a construir.

Capítulo 2

Imagens vs containers

O Capítulo 1 introduziu a distinção molde/instância: imagem é o pacote estático, container é a instância em execução. Esse par é a estrutura conceitual mais importante do Docker, e merece um capítulo dedicado, porque entendê-lo a fundo explica comportamentos que de outra forma parecem arbitrários — por que mudanças num container somem quando ele é removido, por que dezenas de containers da mesma imagem ocupam pouco espaço, por que uma imagem é imutável mas um container muda. A chave é que uma imagem não é um blob monolítico: é uma pilha de camadas somente-leitura, e um container adiciona apenas uma fina camada gravável no topo. Este capítulo desmonta essa estrutura de camadas, segue o ciclo de vida de um container do nascimento à remoção, e estabelece como imagens são nomeadas e identificadas — a base para tudo o que vem nos capítulos de construção de imagens.

# A imagem é uma pilha de camadas

Uma imagem não é um arquivo único — é uma pilha de camadas (layers) empilhadas, cada uma somente-leitura. Cada camada representa um conjunto de mudanças no sistema de arquivos: uma camada traz o sistema base, outra instala o runtime, outra copia o seu código, outra instala dependências. As camadas se empilham e o Docker as combina numa visão unificada — o sistema de arquivos que o container enxerga. Essa estrutura em camadas, que o Capítulo 6 explora em detalhe, é o que torna o Docker eficiente: camadas são compartilhadas entre imagens e cacheadas entre builds.

estrutura em camadas
# Uma imagem = pilha de camadas somente-leitura (read-only)
┌───────────────────────────┐
│  camada: COPY código       │  <- o seu app
│  camada: npm install       │  <- dependências
│  camada: instala Node      │  <- runtime
│  camada: SO base (alpine)  │  <- sistema mínimo
└───────────────────────────┘   todas READ-ONLY

# Ver as camadas de uma imagem e o que cada uma adicionou
docker history node:22-alpine

# O container adiciona uma camada gravável

Aqui está o mecanismo que explica quase tudo. Quando você cria um container de uma imagem, o Docker não copia a imagem — ele empilha uma fina camada gravável (writable layer) por cima das camadas somente-leitura da imagem. Tudo que o container escreve — arquivos criados, modificados, logs — vai para essa camada de cima. As camadas da imagem permanecem intocadas e compartilhadas. É por isso que cem containers da mesma imagem ocupam quase o mesmo espaço que um: todos compartilham as mesmas camadas read-only, e cada um só tem sua própria camadinha gravável.

imagem + container
┌───────────────────────────┐
│  camada GRAVÁVEL           │  <- só deste container (mudanças vão aqui)
├───────────────────────────┤
│  camada: COPY código       │  ┐
│  camada: npm install       │  │ camadas da IMAGEM
│  camada: instala Node      │  │ (read-only, COMPARTILHADAS
│  camada: SO base           │  ┘  entre todos os containers)
└───────────────────────────┘

# Mil containers da mesma imagem = mil camadas graváveis finas
# + UMA cópia compartilhada das camadas pesadas da imagem
A camada gravável morre com o container
Esta é a consequência mais importante — e a fonte do erro mais comum de iniciantes. Como tudo que o container escreve vai para a camada gravável, e essa camada é exclusiva daquele container, remover o container apaga tudo que ele escreveu. Dados num banco rodando dentro do container, arquivos enviados por usuários, qualquer estado — somem quando o container é removido. Containers são efêmeros por natureza. Dados que precisam sobreviver ao container têm que viver fora dele, em volumes (Cap 11). Tratar o sistema de arquivos do container como armazenamento permanente é o caminho garantido para perder dados.

# Imutável vs mutável

A distinção imagem/container se resume a uma propriedade: a imagem é imutável, o container é mutável e descartável. Você nunca altera uma imagem — você constrói uma nova (Cap 5). O container, ao contrário, muda o tempo todo na sua camada gravável enquanto roda, e é jogado fora quando termina. Essa assimetria espelha a do Git (Vol XIV): objetos imutáveis (a imagem, como um commit) e estados de trabalho mutáveis (o container, como a working tree). A imagem é o registro permanente e reproduzível; o container é a execução transitória.

Imagens são imutáveis, como commits
O paralelo com o Git é instrutivo. Uma imagem, como um commit (Vol XIV, Cap 1), é identificada por um hash do seu conteúdo, é imutável depois de criada, e é compartilhável de forma reproduzível. "Modificar" uma imagem na verdade cria uma imagem nova com hash novo, exatamente como "modificar" um commit cria um commit novo. Essa imutabilidade é o que garante a reprodutibilidade: a imagem app:1.0.0 contém sempre exatamente o mesmo ambiente, em qualquer máquina, para sempre — a base de um deploy confiável.

# O ciclo de vida de um container

Um container passa por estados, e conhecê-los desfaz a confusão entre "parar" e "remover". docker run cria e inicia um container a partir de uma imagem. docker stop para o processo, mas o container continua existindo (parado, com sua camada gravável intacta) — pode ser reiniciado com docker start. Só docker rm remove o container de vez, apagando sua camada gravável. Confundir stop com rm é a origem de "achei que tinha apagado, mas ainda está lá" e de "reiniciei e meus dados sumiram".

terminal
# Criar e iniciar; -d roda em background (detached), --name dá um nome
docker run -d --name web nginx

# Parar (o container persiste, parado) e reiniciar (mantém a camada gravável)
docker stop web
docker start web

# Ver TODOS os containers, inclusive os parados
docker ps -a

# Remover de vez (apaga a camada gravável; precisa estar parado)
docker rm web
# Atalho: --rm no run remove automaticamente ao terminar
docker run --rm hello-world

# Nomes, tags e IDs de imagem

Imagens são identificadas por um nome no formato repositório:tag — por exemplo node:22-alpine, onde node é o repositório e 22-alpine a tag (geralmente indicando versão e variante). A tag latest é o padrão quando você omite a tag, mas confiar nela é arriscado: latest aponta para "a mais recente no momento", que muda com o tempo. Por baixo do nome, cada imagem tem um ID — o hash do conteúdo (Cap 1) — que é a identidade imutável de verdade.

terminal
# repositório:tag — a tag costuma indicar versão e variante
node:22-alpine
postgres:16
#  ^repo  ^tag

# Sem tag, assume :latest (cuidado — aponta para alvo móvel)
docker pull ubuntu        # = ubuntu:latest

# Dar um nome/tag a uma imagem (cria uma nova referência ao mesmo ID)
docker tag minha-app minha-app:1.0.0
Nunca use :latest em produção
A tag latest não significa "a versão estável mais recente" — significa "o que quer que tenha sido marcado como latest por último", um alvo móvel. Uma imagem que funcionava ontem pode mudar hoje sob o mesmo latest, quebrando builds e deploys de forma misteriosa. Fixe versões específicas (node:22-alpine, não node:latest), exatamente como você fixa versões de dependências no package.json (toda a coleção) e como uma tag Git v1.0.0 (Vol XIV, Cap 16) marca um ponto imutável. Reprodutibilidade exige versões fixas; latest é o oposto disso.

Capítulo 3

A arquitetura do Docker Engine

Você digita docker run e um container nasce. Mas o que acontece entre o comando e o container revela uma arquitetura que vale entender — não por curiosidade, mas porque ela explica comportamentos práticos: por que o Docker precisa de um serviço rodando em segundo plano, por que no Windows ele depende de uma camada Linux, e o que de fato faz o trabalho de isolar processos. Este capítulo abre o Docker Engine: a separação entre o cliente (a CLI que você usa) e o daemon (o serviço que faz o trabalho), os componentes de runtime que criam os containers de verdade, o papel dos registries de onde imagens vêm, e a particularidade de rodar Docker no Windows. É um capítulo de modelo mental sobre a infraestrutura — o tipo de entendimento que transforma erros crípticos ("Cannot connect to the Docker daemon") em diagnósticos óbvios.

# Cliente e daemon: uma arquitetura dividida

O Docker não é um programa único — são duas partes que conversam. O cliente (a CLI docker que você digita) não cria containers; ele apenas envia comandos. Quem faz o trabalho é o daemon (dockerd), um serviço que roda continuamente em segundo plano, recebe os comandos do cliente por uma API, e gerencia imagens, containers, redes e volumes. Quando você roda docker run, a CLI traduz isso numa chamada de API ao daemon, e é o daemon que de fato baixa a imagem, cria o container e o inicia.

arquitetura cliente-daemon
docker run ...        # você digita no CLIENTE (a CLI)
      │
      │ chamada de API (socket/rede)
      ▼
  ┌─────────────────────────────────┐
  │  dockerd (DAEMON)               │  <- o serviço que faz o trabalho
  │   ├─ gerencia imagens          │
  │   ├─ cria/roda containers      │
  │   ├─ redes e volumes           │
  │   └─ fala com o registry       │  <- baixa imagens de fora
  └─────────────────────────────────┘
"Cannot connect to the Docker daemon"
O erro mais comum de quem começa tem explicação direta nesta arquitetura: a CLI (cliente) está funcionando, mas o daemon não está rodando, então não há ninguém para receber os comandos. A solução é iniciar o serviço do Docker (no Windows e Mac, abrir o Docker Desktop; no Linux, systemctl start docker). Entender que cliente e daemon são separados transforma esse erro de um mistério num diagnóstico de uma linha: "o serviço não está de pé". A separação também permite que um cliente fale com um daemon remoto, em outra máquina — embora isso seja menos comum no dia a dia.

# Por baixo do daemon: containerd e runc

O daemon não cria containers diretamente — ele delega a componentes especializados, numa pilha em camadas. O containerd é o gerenciador de containers de alto nível: cuida do ciclo de vida (criar, iniciar, parar) e de imagens. Abaixo dele, o runc é quem efetivamente conversa com o kernel, configurando os namespaces e cgroups (Cap 1) que criam o container. Essa separação em camadas existe por padronização — runc implementa uma especificação aberta (OCI), o que significa que o Docker não é a única forma de rodar containers; é uma das implementações sobre fundações comuns.

OCI: o padrão por baixo do Docker
O Docker popularizou containers, mas o formato de imagens e o runtime são hoje padrões abertos da Open Container Initiative (OCI). Isso tem uma consequência prática importante: uma imagem que você constrói com o Docker segue um formato padronizado que roda em outros runtimes (containerd sozinho, Podman, e — crucialmente — o Kubernetes, Cap 21). Você não está preso ao Docker; está produzindo artefatos OCI portáteis. É por isso que "imagem Docker" e "imagem de container" viraram quase sinônimos, e por que o conhecimento deste volume transfere para todo o ecossistema de containers, não só para a ferramenta Docker.

# Registries: de onde as imagens vêm

As imagens não nascem na sua máquina — elas vêm de um registry, um repositório remoto de imagens (o Cap 9 aprofunda). Quando você roda docker run nginx e a imagem não está local, o daemon a baixa (pull) do registry padrão, o Docker Hub. O registry está para imagens Docker assim como o GitHub está para repositórios Git (Vol XIV, Cap 10): um lugar central de onde se baixa e para onde se envia. Há registries públicos (Docker Hub) e privados (de empresas, ou os oferecidos por GitHub, AWS, Google).

terminal
# Baixar uma imagem do registry (Docker Hub é o padrão)
docker pull nginx:1.27

# Um nome completo de imagem inclui o registry (omitido = Docker Hub)
# docker.io/library/nginx:1.27       (Docker Hub, implícito)
# ghcr.io/usuario/minha-app:1.0.0    (GitHub Container Registry)

# Ver de onde o daemon puxou e quanto ocupa
docker image inspect nginx:1.27

# Docker no Windows: a camada Linux

Aqui mora uma particularidade essencial — especialmente relevante porque você está no Windows. Containers Linux precisam de um kernel Linux (Cap 1: eles compartilham o kernel do host). Mas o Windows não tem um kernel Linux. Como o Docker roda no Windows, então? Através de uma máquina virtual Linux leve, gerenciada pelo WSL 2 (Windows Subsystem for Linux). O Docker Desktop roda o daemon dentro dessa VM Linux; a CLI no Windows fala com ele. Na prática você nem percebe, mas é por isso que o Docker Desktop no Windows depende do WSL 2 habilitado.

terminal (Windows)
# O Docker Desktop usa o WSL 2 como o "host Linux" que provê o kernel.
# Verificar a integração (PowerShell):
wsl -l -v
# NAME              STATE     VERSION
# docker-desktop    Running   2

# A CLI funciona igual ao Linux; o daemon roda na VM do WSL 2
docker version
# Client: ... (Windows)   Server: ... (rodando no WSL 2)
Containers Linux vs Windows
Existem containers Windows nativos (que rodam o kernel Windows), mas a esmagadora maioria do ecossistema — e tudo neste volume — usa containers Linux, porque é onde vivem as imagens de Node, Postgres, Redis e praticamente todo o stack de backend. No Windows, isso significa que o Docker roda via WSL 2. Um efeito prático: arquivos do seu projeto Windows acessados por containers atravessam a fronteira Windows↔WSL, o que pode ser lento. Para projetos com muita I/O de arquivos, manter o código dentro do sistema de arquivos do WSL 2 (não em C:\) melhora bastante a performance — uma dica que se conecta aos volumes do Cap 11.

# Anatomia de um docker run

Juntando as peças, vale rastrear o que acontece num docker run nginx quando a imagem ainda não está local. A CLI envia o comando ao daemon; o daemon não encontra a imagem localmente e a baixa do registry; com a imagem em mãos, ele pede ao containerd para criar o container, que por sua vez usa o runc para configurar namespaces e cgroups no kernel; o processo inicia, isolado. Cada componente do capítulo desempenha seu papel nessa cadeia.

# 2. daemon: imagem não está local -> pull do registry (Docker Hub)
# 3. daemon -> containerd: "crie um container desta imagem"
# 4. containerd -> runc: configura namespaces + cgroups no kernel
# 5. processo isolado inicia -> o container está rodando
docker run nginx

# docker run: as variações essenciais

O docker run tem muitas flags, mas algumas aparecem em quase todo uso. -d (detached) roda o container em segundo plano, devolvendo o terminal. -it (interativo + terminal) conecta você a um shell dentro do container. --name dá um nome legível em vez do hash aleatório. --rm remove o container automaticamente quando ele termina, evitando acúmulo de containers parados. Combinar essas flags cobre a maioria dos casos.

terminal
# Em segundo plano (-d), nomeado: típico para serviços (servidor web, banco)
docker run -d --name web nginx

# Interativo (-it): um shell dentro do container, para explorar
docker run -it --rm ubuntu bash
# root@a1b2c3:/#  <- você está dentro; 'exit' encerra e --rm o remove

# Rodar um comando único e sair (com --rm, não deixa rastro)
docker run --rm node:22-alpine node -e 'console.log(1+1)'

# Mapeando portas: -p

Um container é isolado também na rede (Cap 12): um servidor rodando na porta 80 dentro do container não está acessível da sua máquina por padrão. Para alcançá-lo, você mapeia uma porta do host para uma porta do container com -p host:container. Sem esse mapeamento, o serviço roda mas você não consegue chegar nele — uma das primeiras pegadinhas de quem começa.

terminal
# Mapeia a porta 8080 do HOST para a porta 80 do CONTAINER
docker run -d -p 8080:80 --name web nginx
# Agora http://localhost:8080 chega ao nginx na porta 80 do container
#         ^host        ^container

# Mapear a mesma porta dos dois lados (comum em dev)
docker run -d -p 3000:3000 minha-app

# Ver os mapeamentos de porta de um container
docker port web
Esqueceu o -p? O serviço roda, mas você não o alcança
O erro clássico: você roda docker run -d minha-app, o container sobe, mas http://localhost:3000 não responde. A causa é quase sempre a falta do -p: o servidor está escutando dentro do container, na rede isolada dele, sem ponte para o host. Adicione -p 3000:3000 e funciona. Uma segunda pegadinha relacionada: dentro do container, o serviço precisa escutar em 0.0.0.0 (todas as interfaces), não em 127.0.0.1 (só o loopback interno) — senão o mapeamento de porta não alcança o processo. Servidor que só escuta localhost dentro do container é invisível mesmo com -p correto.

# Entrando num container vivo: exec

Diferente do run (que cria um container novo), o docker exec roda um comando dentro de um container já em execução. É como você inspeciona um serviço rodando — abrir um shell dentro dele para olhar arquivos, checar processos, rodar um comando de diagnóstico. É a ferramenta de depuração número um: o container está se comportando estranho? Entre nele e veja.

terminal
# Abrir um shell DENTRO de um container que já está rodando
docker exec -it web sh
# (sh em imagens alpine/mínimas; bash em imagens completas)

# Rodar um comando único dentro do container sem abrir shell
docker exec web ls /usr/share/nginx/html

# Útil para diagnóstico: ver variáveis de ambiente do processo
docker exec web env

# Logs: vendo o que o container diz

Um container em segundo plano (-d) não mostra sua saída no terminal — ela vai para os logs do Docker. docker logs recupera o que o container escreveu em stdout/stderr, e com -f (follow) você acompanha em tempo real, como um tail -f. Para serviços, é a janela principal para o que está acontecendo dentro.

terminal
# Ver os logs de um container
docker logs web

# Acompanhar em tempo real (-f) e mostrar só as últimas 50 linhas
docker logs -f --tail 50 web

# Com timestamps
docker logs -t web
Logue para stdout, não para arquivos
Containers seguem uma convenção importante: a aplicação deve escrever logs em stdout/stderr, não em arquivos dentro do container. Há duas razões. Primeira, a camada gravável é efêmera (Cap 2) — logs em arquivo somem com o container. Segunda, o Docker (e orquestradores) captura stdout/stderr automaticamente, integrando com ferramentas de coleta de logs centralizadas. Isso conecta à observabilidade do Vol XIII (Cap 22): a mesma disciplina de "logue eventos estruturados, sem dados sensíveis" se aplica, agora com o destino sendo o stdout que o Docker coleta. O Cap 19 detalha logging em produção.

# Limpando: a higiene do dia a dia

Containers parados, imagens não usadas e camadas órfãs se acumulam e ocupam disco. O Docker oferece comandos de limpeza, do cirúrgico ao abrangente. Remover containers e imagens individuais é rotineiro; o prune faz faxina em massa do que não está em uso. Vale conhecer ambos — e o cuidado com o prune agressivo.

terminal
# Parar e remover um container específico
docker stop web && docker rm web

# Remover uma imagem (precisa não estar em uso por nenhum container)
docker rmi nginx:1.27

# Faxina: remove containers parados, redes e imagens não usadas
docker system prune

# Limpar espaço: ver quanto o Docker está ocupando
docker system df
Cuidado com prune -a e volumes
O docker system prune é útil, mas tem versões agressivas. docker system prune -a remove todas as imagens não usadas por um container ativo — incluindo as que você baixou e vai querer de novo, forçando re-downloads. E adicionar --volumes remove volumes não usados, que podem conter dados que você quer manter (Cap 11) — bancos de dados, uploads. O prune básico é seguro; os agressivos exigem certeza. Como nos comandos destrutivos do Git (Vol XIV), pare e leia o que vai ser removido antes de confirmar — aqui não há reflog para recuperar.

Capítulo 5

Dockerfile construindo imagens

Até aqui você rodou imagens prontas — nginx, ubuntu, node. Mas o objetivo do Docker é empacotar a sua aplicação, e para isso você constrói a sua própria imagem. O Dockerfile é a receita dessa construção: um arquivo de texto com instruções que o Docker executa em sequência para montar a imagem, camada por camada (Cap 2). Este capítulo é o coração prático do volume — as instruções essenciais do Dockerfile, a ordem em que aparecem, e como cada uma constrói uma camada. Vamos conteinerizar uma aplicação Node real (o backend da coleção: Hono + Drizzle), do FROM que escolhe a base ao CMD que define o que roda. É também aqui que o Dockerfile se revela como código versionado (Vol XIV): a receita do ambiente vive no repositório, ao lado do código, evoluindo com ele.

# O Dockerfile como receita de camadas

Um Dockerfile é uma sequência de instruções, e — ponto central — cada instrução cria uma camada (Cap 2). FROM estabelece a camada base; COPY adiciona uma camada com arquivos; RUN executa um comando e a mudança resultante vira uma camada. O Docker lê o arquivo de cima para baixo, executa cada instrução, e empilha as camadas na imagem final. Essa correspondência um-para-um entre instrução e camada é o que torna o cache de build (Cap 6) possível e o que guia a forma de escrever um bom Dockerfile.

Dockerfile
# Cada instrução vira uma camada da imagem final
FROM node:22-alpine        # camada base: SO mínimo + Node 22
WORKDIR /app               # define o diretório de trabalho
COPY package*.json ./      # camada: manifests de dependência
RUN npm ci                 # camada: dependências instaladas
COPY . .                   # camada: o código da aplicação
RUN npm run build          # camada: build (TS -> JS)
EXPOSE 3000               # documenta a porta usada
CMD ["node", "dist/index.js"]  # o que roda ao iniciar o container

# FROM: a imagem base

Todo Dockerfile começa com FROM, que define a imagem de partida — a fundação sobre a qual você constrói. A escolha da base importa muito: ela determina o tamanho final, as ferramentas disponíveis e a superfície de segurança. Para Node, node:22-alpine (baseada no Alpine Linux, mínima) é uma escolha comum e enxuta; node:22-slim é um meio-termo; node:22 (completa) é maior mas tem mais ferramentas. Fixe sempre a versão (Cap 2): a base é a primeira garantia de reprodutibilidade.

Alpine: pequena, mas com pegadinhas
Imagens alpine são minúsculas (megabytes, não centenas deles) porque usam o Alpine Linux, uma distribuição enxuta. Para a maioria das aplicações Node, são a escolha certa — menos espaço, menos superfície de ataque (Cap 17). Mas o Alpine usa musl em vez da glibc padrão, o que ocasionalmente quebra dependências nativas que esperam glibc (alguns pacotes com binários compilados). Quando uma dependência nativa não funciona no Alpine, -slim (baseada em Debian, com glibc) costuma resolver ao custo de alguns MB. Comece com Alpine; troque para slim só se algo quebrar.

# COPY e WORKDIR: trazendo o código

WORKDIR define o diretório dentro da imagem onde os comandos seguintes rodam (e o cria se não existir) — evita cd repetidos e dá um lugar previsível para o código. COPY traz arquivos do seu projeto (o contexto de build) para dentro da imagem. A ordem dos COPY é estratégica e conecta diretamente ao cache (Cap 6): copiar primeiro só os manifests de dependência, instalar, e só depois copiar o resto do código é o padrão que faz o cache trabalhar a seu favor.

Dockerfile (ordem que aproveita o cache)
WORKDIR /app

# 1. Copiar APENAS os manifests primeiro...
COPY package.json package-lock.json ./
# 2. ...e instalar. Esta camada só refaz se os manifests mudarem (Cap 6)
RUN npm ci

# 3. Só então copiar o código (que muda toda hora)
COPY . .
# Resultado: editar código NÃO reinstala dependências (cache preservado)

# RUN: executando comandos no build

RUN executa um comando durante a construção da imagem — instalar dependências, compilar, gerar arquivos. O resultado do comando fica congelado numa camada. Um detalhe importante de eficiência: cada RUN cria uma camada, então comandos relacionados são frequentemente encadeados com && num único RUN para evitar camadas desnecessárias (e para que limpezas surtam efeito — apagar um cache num RUN separado não reduz a imagem, pois a camada anterior já o contém).

Dockerfile
# Um RUN por passo lógico. Para instalar pacotes do sistema, encadeie
# com && e limpe na MESMA camada, senão a limpeza não reduz tamanho:
RUN apk add --no-cache curl && \
    curl -o /tmp/dado.json https://exemplo.com/dado && \
    rm -rf /var/cache/apk/*

# npm ci (não npm install): instalação limpa e reproduzível do lock
RUN npm ci --omit=dev

# CMD e ENTRYPOINT: o que roda

As instruções anteriores constroem a imagem; CMD e ENTRYPOINT definem o que acontece quando um container dela é iniciado. CMD especifica o comando padrão — o que roda se você não passar nada no docker run. ENTRYPOINT define um executável fixo, com CMD fornecendo argumentos padrão. Para a maioria das aplicações, um CMD com o comando de iniciar o servidor basta. Use sempre a forma de array (exec form), que executa o processo diretamente, sem um shell intermediário.

Dockerfile
# Exec form (array): executa direto, sem shell. PREFIRA esta.
CMD ["node", "dist/index.js"]

# ENTRYPOINT fixa o executável; CMD vira o argumento padrão (substituível)
ENTRYPOINT ["node"]
CMD ["dist/index.js"]
# docker run img dist/outro.js  -> roda 'node dist/outro.js'
Exec form vs shell form: o sinal que não chega
Há duas formas de escrever CMD/ENTRYPOINT: a exec form (array JSON, ["node", "app.js"]) e a shell form (string, node app.js). Prefira sempre a exec form, por um motivo prático sério: na shell form, o comando roda dentro de um /bin/sh -c, e os sinais do sistema (como o SIGTERM de um docker stop) vão para o shell, não para o seu processo — que então não recebe o aviso para encerrar graciosamente e é morto à força após um timeout. Na exec form, o seu processo é o PID 1 e recebe os sinais diretamente, podendo fazer shutdown limpo (fechar conexões, terminar requisições em curso). Para um servidor, isso é a diferença entre desligar limpo e ser morto no meio de uma requisição.

# Construindo a imagem: docker build

Com o Dockerfile pronto, docker build executa a receita e produz a imagem. O -t dá um nome e tag (Cap 2); o ponto final é o contexto de build — a pasta enviada ao daemon, de onde os COPY puxam arquivos. Um .dockerignore (irmão do .gitignore, Vol XIV Cap 17) exclui do contexto o que não deve entrar — node_modules, .git, .env — acelerando o build e evitando vazar segredos para a imagem.

terminal + .dockerignore

docker build -t minha-app:1.0.0 .

# .dockerignore (mesma ideia do .gitignore): fora do contexto de build
#   node_modules    (reinstalado no build; não copie o local)
#   .git            (history não pertence à imagem)
#   .env            (segredos NUNCA na imagem — Vol XIII)
#   dist            (gerado no build)

Capítulo 6

Layers e cache de build

O Capítulo 5 mostrou que cada instrução do Dockerfile cria uma camada. Este capítulo explora a consequência mais valiosa desse fato: o cache de build. Construir uma imagem do zero pode levar minutos — baixar a base, instalar dezenas de dependências, compilar. Mas o Docker raramente faz tudo de novo: ele reaproveita camadas de builds anteriores quando nada que as afeta mudou. Entender como esse cache funciona — quando uma camada é reaproveitada e quando é invalidada — é a diferença entre builds de segundos e builds de minutos, e entre um Dockerfile que ajuda o cache e um que o sabota a cada mudança trivial. Este é um capítulo de otimização fundamentada: não truques soltos, mas o modelo de como o cache decide, do qual todas as boas práticas derivam naturalmente.

# Como o cache de camadas funciona

Quando o Docker constrói uma imagem, ele processa as instruções em ordem e, para cada uma, pergunta: "já construí esta exata camada antes, a partir da mesma camada anterior?". Se sim, reaproveita a camada cacheada em vez de executar a instrução de novo. A regra é sequencial e tem uma propriedade crucial: assim que uma camada é invalidada, todas as seguintes também são, porque cada camada se constrói sobre a anterior. O cache é uma cadeia — quebrou um elo, todos os elos abaixo se refazem.

o efeito cascata do cache
# Build: o Docker reaproveita camadas até a primeira que mudou,
# e reconstrói essa e TODAS as seguintes.

FROM node:22-alpine     # CACHED  (base não mudou)
COPY package*.json ./   # CACHED  (manifests iguais)
RUN npm ci             # CACHED  (depende do passo acima)
COPY . .              # MUDOU   (você editou um arquivo)
RUN npm run build      # REFAZ   (vem depois do que mudou)
#                          ^ tudo a partir daqui é reconstruído

# O que invalida uma camada

Cada tipo de instrução tem uma regra de invalidação. Para RUN, o cache quebra se o texto do comando muda. Para COPY e ADD, quebra se o conteúdo dos arquivos copiados muda (o Docker compara um hash dos arquivos). Para FROM, quebra se a imagem base muda. Entender essas regras explica por que a ordem das instruções (Cap 5) importa tanto: você quer que as coisas que mudam raramente venham antes das que mudam sempre.

A regra de ouro: do que muda menos para o que muda mais
Toda otimização de cache de build deriva de um princípio: ordene as instruções da que muda com menos frequência para a que muda com mais. A imagem base muda raramente — vai no topo. As dependências mudam às vezes (quando você adiciona um pacote) — vêm em seguida. O código-fonte muda a cada commit — vai por último. Assim, uma edição de código (o evento mais frequente) só invalida as últimas camadas, preservando o caro npm ci. Inverter essa ordem — copiar o código antes de instalar dependências — faria cada edição reinstalar tudo. A ordem não é estética; é minutos de build a cada mudança.

# O padrão que todo Dockerfile Node usa

A aplicação concreta da regra de ouro é o padrão mais reconhecível dos Dockerfiles Node, já visto no Capítulo 5: separar a cópia dos manifests da cópia do código. Os arquivos package.json e package-lock.json mudam raramente (só quando você mexe em dependências); o código muda o tempo todo. Copiá-los separadamente e instalar antes de copiar o código faz com que editar o código não dispare uma reinstalação.

Dockerfile (cache otimizado vs ingênuo)
# ✅ OTIMIZADO: manifests primeiro, install, depois o código
COPY package*.json ./
RUN npm ci              # só refaz se package*.json mudar
COPY . .               # editar código não toca o npm ci acima

# ❌ INGÊNUO: copia tudo de uma vez
COPY . .               # qualquer arquivo muda...
RUN npm ci              # ...e o npm ci INTEIRO refaz toda vez

# Inspecionando e quebrando o cache

Às vezes você precisa ver as camadas ou forçar uma reconstrução. docker history mostra as camadas de uma imagem e o tamanho de cada uma — útil para descobrir o que está inflando a imagem. E --no-cache força o build a ignorar o cache inteiro, reconstruindo tudo — necessário quando uma camada depende de algo externo que mudou sem o Docker perceber (um apt-get que busca a versão mais recente, por exemplo).

terminal
# Ver as camadas de uma imagem e o peso de cada uma
docker history minha-app:1.0.0

# Forçar reconstrução total, ignorando o cache
docker build --no-cache -t minha-app:1.0.0 .

# Saída do build mostra o que veio do cache:
# => CACHED [2/6] COPY package*.json ./
# => [3/6] RUN npm ci          <- sem CACHED = foi reexecutado
Cache pode esconder dependências externas desatualizadas
O cache assume que a mesma instrução produz o mesmo resultado — o que nem sempre é verdade para comandos que buscam coisas de fora. Um RUN apt-get update && apt-get install curl cacheado vai continuar instalando a versão de curl de quando a camada foi criada, mesmo que uma atualização de segurança tenha saído depois — porque o texto do comando não mudou, então o Docker reaproveita a camada antiga. Para builds de produção, periodicamente reconstrua com --no-cache ou ancore versões explícitas. O cache é seu amigo na velocidade, mas pode silenciosamente perpetuar pacotes desatualizados — uma consideração de segurança (Cap 17).

# BuildKit: o builder moderno

O Docker moderno usa o BuildKit como motor de build padrão — um sistema mais inteligente que o antigo. Ele constrói camadas independentes em paralelo, tem um cache mais eficiente, e oferece recursos avançados como montagens de cache (que persistem o cache do gerenciador de pacotes entre builds, sem incluí-lo na imagem) e montagens de segredo (que dão acesso a um segredo durante o build sem deixá-lo na imagem final — relevante para o Vol XIII). Na maioria das instalações ele já está ativo; vale conhecer os recursos que ele habilita.

Dockerfile (recursos do BuildKit)
# Cache mount: persiste o cache do npm entre builds, FORA da imagem
# (acelera reinstalações sem inflar a imagem final)
RUN --mount=type=cache,target=/root/.npm \
    npm ci

# Secret mount: usa um segredo no build sem gravá-lo numa camada (Vol XIII)
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci   # o .npmrc com token NÃO fica na imagem

Capítulo 7

Multi-stage builds

Construir uma aplicação e rodá-la exigem coisas diferentes. Para construir um backend TypeScript, você precisa do compilador, das devDependencies, das ferramentas de build. Para rodar o resultado, você precisa só do JavaScript compilado e das dependências de produção. Se a sua imagem final carrega tudo o que foi necessário para construir, ela fica inchada — centenas de megabytes de ferramentas que nunca rodam em produção, ampliando o tamanho e a superfície de ataque. O multi-stage build resolve isso elegantemente: você usa um estágio para construir e outro, limpo, para rodar, copiando entre eles apenas o que importa. Este capítulo mostra o padrão que transforma imagens de 1GB em imagens de 150MB, aplicado ao stack da coleção — e por que ele se tornou prática padrão para qualquer aplicação compilada.

# O problema: build e runtime são diferentes

Pense no que entra numa imagem Node construída de forma ingênua (Cap 5): a imagem base, todas as dependências (incluindo as de desenvolvimento — TypeScript, tipos, ferramentas de teste), o código-fonte, e o resultado compilado. Mas em produção, só o último item e as dependências de runtime são usados. O compilador TypeScript, os @types/*, o ESLint — tudo isso foi necessário para produzir o dist/, e depois vira peso morto. Uma imagem que carrega o ambiente de build inteiro para rodar uns poucos arquivos JS é desperdício em todas as dimensões: disco, transferência, segurança.

Build-time vs run-time dependencies
A distinção que organiza o capítulo: dependências de build existem só para produzir o artefato final — o compilador, os tipos, os bundlers. Dependências de runtime são as que o código de fato importa e usa ao executar. No package.json, isso mapeia aproximadamente para devDependencies (build) e dependencies (runtime). O multi-stage build materializa essa separação na imagem: o estágio de build tem as devDependencies; o estágio final, só as de runtime. O resultado compilado atravessa a fronteira; as ferramentas de build, não.

# A solução: múltiplos estágios, um FROM cada

Um multi-stage build tem vários FROM no mesmo Dockerfile, cada um iniciando um estágio independente. Você nomeia os estágios (AS builder) e, no estágio final, copia seletivamente artefatos dos estágios anteriores com COPY --from. A imagem final é construída apenas a partir do último estágio — tudo o que ficou nos estágios anteriores e não foi copiado adiante é descartado. Você ganha o melhor dos dois mundos: um ambiente completo para construir, e uma imagem mínima para rodar.

Dockerfile (multi-stage)
# ===== ESTÁGIO 1: build (tem tudo para compilar) =====
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                  # TODAS as deps (inclui devDependencies)
COPY . .
RUN npm run build           # compila TS -> dist/

# ===== ESTÁGIO 2: runtime (mínimo, só o necessário) =====
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev        # SÓ dependências de produção
# Copia apenas o resultado compilado do estágio anterior:
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/index.js"]

Observe o que cruza a fronteira: apenas /app/dist (o JavaScript compilado), via COPY --from=builder. O TypeScript, os @types, todo o ferramental de build ficaram no estágio builder e foram descartados. O estágio final reinstala só as dependências de produção (--omit=dev) e recebe o build pronto. A imagem resultante não tem ideia de que um dia houve um compilador.

# O impacto no tamanho

A diferença é dramática e mensurável. Uma imagem Node single-stage típica, carregando devDependencies e fonte, facilmente passa de 500MB a 1GB. A mesma aplicação em multi-stage, com só o runtime e o build, cabe em 150–200MB — e com bases ainda menores (distroless, Cap 18), em menos. Não é só economia de disco: imagens menores transferem mais rápido (pull/push), iniciam mais rápido em orquestradores, e têm menos componentes para uma vulnerabilidade explorar (Cap 17).

terminal
# Comparar tamanhos: single-stage vs multi-stage da mesma app
docker images minha-app
# REPOSITORY  TAG           SIZE
# minha-app   single        980MB    <- carrega o ambiente de build inteiro
# minha-app   multi         165MB    <- só runtime + dist (6x menor)

# Padrões úteis de multi-stage

O padrão básico (build → runtime) é o mais comum, mas a técnica é flexível. Você pode ter um estágio só para dependências (reaproveitado por outros), um estágio de testes que roda no CI e não vai para a imagem final, ou copiar de uma imagem externa (--from=nginx). E o --target permite construir só até um estágio específico — útil para gerar uma imagem de desenvolvimento (com ferramentas) e outra de produção (mínima) do mesmo Dockerfile.

terminal + Dockerfile
# Construir só até um estágio nomeado (ex.: imagem de dev com tudo)
docker build --target builder -t minha-app:dev .

# Um estágio de testes que NÃO entra na imagem final:
# FROM builder AS test
# RUN npm test          (roda no CI via --target test; descartado em prod)

# Copiar de uma imagem externa (não só de estágios deste Dockerfile)
# COPY --from=nginx:alpine /etc/nginx/nginx.conf ./
Multi-stage é a prática padrão, não otimização avançada
É tentador ver multi-stage como uma otimização opcional "para depois". Na verdade, para qualquer aplicação que tem uma etapa de build — TypeScript, bundlers de frontend, binários compilados —, ele é o ponto de partida correto, não um refinamento. A complexidade extra é mínima (mais alguns FROM), e os ganhos são imediatos e em todas as dimensões. Comece multi-stage desde o primeiro Dockerfile de uma app compilada. O único caso em que não se justifica é uma aplicação sem etapa de build — um script Python ou JS puro que roda direto, sem compilação —, onde não há "ferramentas de build" a descartar.

# Combinando com o cache

Multi-stage e cache de build (Cap 6) trabalham juntos. Dentro de cada estágio, a regra de ouro continua valendo — ordene do que muda menos ao que muda mais. E como o BuildKit constrói estágios independentes em paralelo, um multi-stage bem estruturado pode até ser mais rápido de construir, além de produzir uma imagem menor. A ordem dos COPY package*.json antes do código, em cada estágio, preserva o cache das dependências exatamente como no Capítulo 6.

Capítulo 8

Otimização de imagens

Os capítulos sobre cache (6) e multi-stage (7) já entregaram as duas maiores alavancas de otimização. Este capítulo reúne o restante das técnicas que tornam imagens menores, mais rápidas e mais seguras — não como uma lista de truques, mas organizadas por princípio. Imagens menores não são só uma questão de economia de disco: elas transferem mais rápido (importa a cada deploy e a cada escala horizontal), iniciam mais rápido, e — crucialmente — têm menos componentes onde uma vulnerabilidade pode morar. Cada megabyte a menos é menos superfície de ataque e menos tempo de pull. Vamos cobrir a escolha de base, o .dockerignore, a consolidação de camadas, a ordem de instruções, e como medir o que está inflando uma imagem — fechando o conjunto de boas práticas que separam um Dockerfile amador de um de produção.

# Por que tamanho importa

Antes das técnicas, o porquê. Uma imagem é transferida toda vez que um servidor novo a baixa — a cada deploy, a cada nó adicionado num cluster, a cada escala horizontal. Uma imagem de 1GB versus 150MB é a diferença entre um deploy que leva minutos e um que leva segundos, multiplicado por cada réplica. Imagens menores também iniciam mais rápido (menos para descomprimir e montar) e — o ponto de segurança — contêm menos software: menos bibliotecas, menos binários, menos CVEs potenciais para um atacante explorar. Otimizar tamanho é simultaneamente otimizar velocidade e segurança.

# A base: a maior alavanca isolada

A escolha da imagem base (Cap 5) é, sozinha, o fator que mais influencia o tamanho final. A diferença entre node:22 (completa, ~1GB) e node:22-alpine (~130MB) é quase um gigabyte antes de você adicionar uma linha de código. Para a maioria das aplicações, a progressão é: comece com Alpine; se uma dependência nativa quebrar (Cap 5), suba para -slim; reserve a base completa para casos que realmente precisam do ferramental extra. O Capítulo 18 leva isso ao limite com distroless.

comparação de bases (Node 22)
# Tamanho da base ANTES de adicionar seu código:
node:22            # ~1.1GB   completa (Debian + ferramentas)
node:22-slim       # ~250MB   Debian mínimo + glibc
node:22-alpine     # ~130MB   Alpine (musl), a mais enxuta comum
gcr.io/distroless  # ~50MB    só o runtime, sem shell (Cap 18)

# .dockerignore: não envie lixo ao build

O .dockerignore (Cap 5) merece destaque como otimização. Sem ele, o COPY . . arrasta para a imagem (e o contexto de build inteiro para o daemon) coisas que não deveriam estar lá: node_modules local (que será reinstalado), a pasta .git com toda a história, logs, e — risco de segurança — o .env com segredos. Um .dockerignore bem feito acelera o build (menos dados ao daemon), reduz a imagem, e fecha um vetor de vazamento de segredos.

.dockerignore
# Dependências e build (reinstalados/regerados na imagem)

# Versionamento e CI (não pertencem à imagem)

# Segredos e ambiente — NUNCA na imagem (Vol XIII, Cap 22)

# Ruído local

README.md
Sem .dockerignore, segredos vazam para a imagem
A conexão de segurança é direta e séria. Um COPY . . sem .dockerignore copia o .env para dentro da imagem. Mesmo que sua aplicação leia variáveis de outra forma em produção, o arquivo com os segredos agora vive numa camada da imagem — e camadas são imutáveis e distribuíveis (Cap 2). Qualquer um com a imagem pode extrair o .env com docker history ou montando a camada. É o equivalente Docker de commitar o .env no Git (Vol XIV, Cap 17). A defesa é a mesma: o .dockerignore deve excluir .env desde o primeiro build, e segredos chegam ao container em runtime (Cap 13), nunca embutidos na imagem.

# Consolidar camadas e limpar na mesma camada

Cada RUN cria uma camada (Cap 2), e — crucialmente — uma camada não pode ser "encolhida" por uma camada posterior. Se um RUN instala um cache de 100MB e um RUN seguinte o apaga, a imagem ainda carrega os 100MB, porque a camada que os criou continua na pilha. A regra: instale e limpe na mesma instrução RUN, encadeando com &&. Assim a limpeza acontece antes de a camada ser selada, e os arquivos temporários nunca entram na imagem.

Dockerfile
# ❌ ERRADO: a limpeza num RUN separado não reduz nada
RUN apk add --no-cache curl
RUN rm -rf /var/cache/apk/*   # tarde demais: a camada acima já selou o cache

# ✅ CERTO: instalar e limpar na MESMA camada
RUN apk add --no-cache curl && \
    curl -o /app/dado.json https://exemplo.com/dado && \
    rm -rf /tmp/* /var/cache/apk/*

# Em Alpine, --no-cache no apk já evita o cache de índice de pacotes

Otimizar às cegas é desperdício; meça primeiro. docker history mostra o tamanho de cada camada, revelando qual instrução inflou a imagem. docker images dá o tamanho total. E ferramentas externas como o dive exploram interativamente o conteúdo de cada camada, mostrando exatamente quais arquivos ocupam espaço — indispensável para encontrar aquele cache ou pasta esquecida que está pesando.

# Tamanho total das imagens

# Quanto o Docker ocupa no total (imagens, containers, volumes, cache)

Quando for otimizar, ataque na ordem de impacto. 1. Multi-stage (Cap 7) — o maior ganho, descarta o ambiente de build inteiro. 2. Ordem para o cache (Cap 6) — não reduz tamanho, mas acelera builds. As duas primeiras entregam 90% do resultado; as demais refinam. Não invista em consolidar camadas se ainda nem usa multi-stage — comece pelo topo da lista.

Capítulo 9

Registries e tags

Uma imagem construída na sua máquina (Caps 5–8) só é útil ali até você compartilhá-la. O registry é onde imagens vivem para serem distribuídas — o servidor de onde se baixam (pull) e para onde se enviam (push). O Capítulo 3 o introduziu como "o GitHub das imagens"; este capítulo o detalha: como nomear imagens para um registry, como autenticar e enviar, como tags organizam versões, e — o ponto que conecta tudo — como o registry fecha o ciclo entre o Git, o CI e o deploy. É aqui que a imagem deixa de ser um artefato local e vira parte de um pipeline: um commit dispara um build, que produz uma imagem versionada, que é enviada ao registry, de onde produção a baixa. Entender o registry é entender como o Docker se integra ao fluxo de entrega que o Vol XIV começou a montar.

# O nome completo de uma imagem

O Capítulo 2 mostrou repositório:tag; a forma completa inclui o registry na frente: registry/namespace/repositório:tag. Quando você omite o registry, o Docker assume o Docker Hub (docker.io). Entender a estrutura completa é o que permite usar registries privados — do GitHub, da AWS, da empresa — em vez de só o Hub público. Cada parte do nome diz onde a imagem mora e como alcançá-la.

anatomia do nome de uma imagem
ghcr.io / vitormattos / minha-app : 1.0.0
  │           │            │         │
  │           │            │         └─ tag (versão/variante)
  │           │            └─────────── repositório (a imagem)
  │           └──────────────────────── namespace (usuário/org)
  └──────────────────────────────────── registry (servidor)

# Sem registry, assume Docker Hub:
nginx              # = docker.io/library/nginx:latest
usuario/app:1.0    # = docker.io/usuario/app:1.0

# Push: enviando uma imagem

Para enviar uma imagem a um registry, ela precisa estar nomeada com o endereço daquele registry — daí o docker tag entrar em cena (Cap 2). Você dá à sua imagem local um nome que aponta para o registry, autentica com docker login, e faz docker push. O fluxo é o espelho do pull: assim como você baixa nginx do Hub, você envia seu-usuario/sua-app para o seu espaço.

terminal
# 1. Autenticar no registry (token, não senha — ver callout)
docker login ghcr.io -u vitormattos

# 2. Nomear a imagem local com o endereço do registry
docker tag minha-app:1.0.0 ghcr.io/vitormattos/minha-app:1.0.0

# 3. Enviar
docker push ghcr.io/vitormattos/minha-app:1.0.0

# Em outra máquina/produção, basta baixar:
docker pull ghcr.io/vitormattos/minha-app:1.0.0
Login com token, não com senha
O docker login não deve usar a senha da sua conta. Como nos pushes do Git (Vol XIV, Cap 10), a autenticação correta usa um token de acesso pessoal com escopo limitado — permissão só para registries, revogável independentemente, sem expor a senha principal. E o token é um segredo (Vol XIII, Cap 22): nunca o coloque no Dockerfile, no código, ou num comando que vá para a história do shell de forma visível. Em CI, ele vem de um secret do pipeline; localmente, do docker login que o guarda de forma segura no sistema. Tratar credenciais de registry com o mesmo cuidado de qualquer segredo é parte da higiene de segurança.

# Estratégia de tags

Uma mesma imagem costuma ter várias tags ao mesmo tempo, e uma boa estratégia de tags torna o registry navegável. O padrão comum: uma tag SemVer imutável e específica (1.4.2, conectando à tag Git do Vol XIV Cap 16), tags móveis de conveniência (1.4, 1) que apontam para a última correção daquela linha, e talvez latest para a mais recente estável. A imutável é a que produção referencia; as móveis são atalhos. Frequentemente também se marca a imagem com o hash do commit Git, ligando cada imagem ao código exato que a gerou.

terminal
# Uma imagem, várias tags: específica (imutável) + móveis + commit
docker tag minha-app ghcr.io/org/app:1.4.2      # imutável (produção usa esta)
docker tag minha-app ghcr.io/org/app:1.4        # móvel: última 1.4.x
docker tag minha-app ghcr.io/org/app:latest      # móvel: última estável
docker tag minha-app ghcr.io/org/app:sha-a1b2c3d  # liga ao commit Git

docker push --all-tags ghcr.io/org/app
Tag móvel para conveniência, imutável para produção
A mesma lição da tag latest (Cap 2) vale para todas as tags móveis: elas são ponteiros que mudam. 1.4 hoje pode apontar para 1.4.2 e amanhã para 1.4.3. Isso é ótimo para "me dê a última correção da 1.4" em desenvolvimento, mas perigoso em produção, onde você quer reprodutibilidade absoluta. Produção deve referenciar a tag imutável e específica (1.4.2), ou — para garantia máxima — o digest da imagem (o hash sha256:...), que é imutável por definição. Tags móveis para humanos navegarem; tags imutáveis ou digests para máquinas implantarem.

# O digest: a identidade imutável

Abaixo das tags (que são apelidos móveis) está o digest: o hash SHA-256 do conteúdo da imagem, exatamente como o ID de um commit no Git (Vol XIV, Cap 1). O digest é a identidade verdadeira e imutável da imagem — duas imagens com o mesmo digest são byte por byte idênticas, e nenhuma tag pode "mover" um digest. Referenciar uma imagem pelo digest em produção é a forma mais forte de reprodutibilidade: você implanta exatamente aquela imagem, sem qualquer ambiguidade de tag.

terminal
# Ver o digest de uma imagem
docker inspect --format='{{index .RepoDigests 0}}' minha-app:1.0.0
# ghcr.io/org/app@sha256:9f8e7d6c...

# Referenciar pelo digest (imutável, à prova de re-tag): o deploy mais seguro
docker pull ghcr.io/org/app@sha256:9f8e7d6c...

# Fechando o ciclo Git → imagem → deploy

Aqui as pontas se unem. O fluxo completo de entrega moderna encadeia tudo que os volumes construíram: um commit (Vol XIV) dispara o CI (Vol XIV, Cap 19), que constrói a imagem (Caps 5–8), a marca com a versão e o hash do commit, e a envia (push) ao registry. O deploy então puxa essa imagem específica do registry e a roda. Uma tag Git v1.4.2 (Vol XIV, Cap 16) corresponde a uma imagem app:1.4.2 no registry, que corresponde ao que roda em produção — uma cadeia rastreável do código-fonte ao container vivo.

o pipeline, conceitualmente

# docker build -t ghcr.io/org/app:1.4.2 .   (Caps 5-8)
# docker push ghcr.io/org/app:1.4.2          -> registry
#         │

# docker pull ghcr.io/org/app:1.4.2  &&  docker run ...
# Código -> imagem -> container: cadeia rastreável e reproduzível

Capítulo 10

Ciclo de vida de containers

O Capítulo 2 tocou no ciclo de vida; agora o aprofundamos, porque entender os estados de um container e como ele inicia e para corretamente é o que separa containers que se comportam bem em produção dos que vazam recursos, ignoram comandos de desligamento ou viram zumbis. Um container é, no fundo, um processo (Cap 1) — e como todo processo, ele nasce, roda, recebe sinais e morre. O que é específico do Docker é como esse ciclo se mapeia em estados gerenciáveis, o que define quando um container "termina", e a sutileza do PID 1 e do tratamento de sinais que decide se um shutdown é gracioso ou violento. Este capítulo cobre os estados, as políticas de reinício que mantêm serviços de pé, os healthchecks que distinguem "rodando" de "saudável" (preparando o Cap 16), e o encerramento limpo — o conhecimento que torna seus containers cidadãos confiáveis de um sistema de produção.

# Os estados de um container

Um container transita por estados bem definidos. Created: criado mas ainda não iniciado. Running: o processo principal está executando. Paused: congelado (raro). Exited: o processo terminou (com um código de saída). Removed: deixou de existir. A transição mais importante de entender é o que leva de Running a Exited: um container roda enquanto o seu processo principal (o CMD, Cap 5) está vivo. Quando esse processo termina — por conclusão, erro ou sinal —, o container para. Não há "container vazio rodando"; ele existe enquanto seu processo existe.

O container vive enquanto o PID 1 vive
A causa nº 1 de "meu container para sozinho na hora que sobe" é um mal-entendido deste princípio. O container roda enquanto o processo definido no CMD (que é o PID 1 dentro dele) estiver vivo. Se esse processo termina imediatamente — um script que roda e sai, um servidor que crasha na inicialização, um comando que era de uma tarefa única —, o container "para" porque cumpriu seu papel. Não é bug; é o design. Um servidor web roda indefinidamente porque seu processo fica escutando; um echo hello para na hora porque o processo termina. Para manter um container vivo, seu processo principal precisa ser algo que não termina sozinho.

# Código de saída: por que parou

Quando um container vai para Exited, ele carrega o código de saída do seu processo principal — a mesma convenção de qualquer programa: 0 significa sucesso, qualquer outro número significa erro. Esse código é a primeira pista ao diagnosticar por que um container parou. 0 indica que o processo terminou normalmente (talvez o container não devesse parar — talvez fosse para ser um serviço); um código diferente de zero aponta uma falha, e o número específico às vezes identifica a causa (137 = morto por SIGKILL, frequentemente falta de memória).

terminal
# Ver containers parados e seus códigos de saída
docker ps -a
# STATUS                       NAMES
# Exited (0) 2 minutes ago     tarefa     <- terminou ok
# Exited (137) 1 minute ago    web        <- morto (137 = SIGKILL/OOM)

# O código de saída de um container específico
docker inspect --format='{{.State.ExitCode}}' web

# Combinar com logs para entender a causa
docker logs web

# Políticas de reinício

Em produção, um serviço que cai deve voltar sozinho. As restart policies dizem ao Docker o que fazer quando um container para. no (padrão): não reinicia. on-failure: reinicia só se saiu com erro (código ≠ 0). always: reinicia sempre, inclusive ao ligar a máquina. unless-stopped: como always, mas respeita uma parada manual. Para serviços de produção, unless-stopped costuma ser a escolha: o serviço se recupera de crashes e reinícios da máquina, mas fica parado se você o parou de propósito.

terminal
# Reiniciar sempre, exceto se eu parar manualmente (típico p/ serviços)
docker run -d --restart unless-stopped --name web nginx

# Reiniciar só em caso de falha, até 5 tentativas
docker run -d --restart on-failure:5 minha-app

# As políticas: no | on-failure | always | unless-stopped

# Healthchecks: rodando vs saudável

"Running" não significa "funcionando". Um servidor pode estar com o processo vivo mas travado, sem responder a requisições — o Docker o vê como Running, mas ele está, na prática, quebrado. O healthcheck fecha essa lacuna: um comando que o Docker roda periodicamente para verificar se o container está realmente saudável, não só vivo. Definido no Dockerfile ou no run, ele adiciona um estado de saúde (healthy/unhealthy) que orquestradores e o Compose (Cap 16) usam para decidir se o container deve receber tráfego.

Dockerfile
# Verifica a saúde a cada 30s: se o endpoint /health não responde, unhealthy
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget --spider -q http://localhost:3000/health || exit 1

# O estado aparece no docker ps:
# STATUS: Up 2 minutes (healthy)   ou   Up 1 minute (unhealthy)
Um /health que verifica de verdade
Um healthcheck só vale se checa algo significativo. Um endpoint /health que sempre retorna 200 sem verificar nada dá uma falsa sensação de saúde — ele diz "o processo responde", não "a aplicação funciona". Um bom healthcheck verifica as dependências críticas: consegue falar com o banco? com o Redis? Se o backend da coleção (Vol XIII) perde a conexão com o Postgres, ele está efetivamente quebrado mesmo com o processo vivo — e um /health que testa a conexão com o banco capturaria isso. O Cap 16 detalha healthchecks e dependências no Compose; o princípio é: cheque o que de fato precisa funcionar.

# Encerramento gracioso: o sinal que importa

Quando você roda docker stop, o Docker envia ao processo principal um SIGTERM — um pedido educado: "termine quando puder". O processo deveria usar esse momento para fechar limpo: parar de aceitar requisições novas, terminar as em andamento, fechar conexões de banco. Se ele não terminar dentro de um prazo (10 segundos por padrão), o Docker manda um SIGKILL, que mata na hora, sem chance de limpeza. Aplicações bem-comportadas tratam o SIGTERM; ignorá-lo significa ser morto à força, possivelmente no meio de uma operação.

graceful-shutdown.ts
// O processo deve tratar SIGTERM para um shutdown limpo (Vol VIII/IX)
process.on('SIGTERM', async () => {
  console.log('SIGTERM recebido: encerrando graciosamente')
  await server.close()       // para de aceitar novas requisições
  await db.end()             // fecha o pool de conexões (Vol X)
  process.exit(0)
})
Exec form para o sinal chegar (de novo)
O Cap 5 alertou: na shell form do CMD, seu processo roda como filho de um /bin/sh, que vira o PID 1 e não repassa o SIGTERM ao seu processo — então o handler acima nunca dispara, e o container é morto por SIGKILL após o timeout. Na exec form (["node", "dist/index.js"]), seu processo é o PID 1 e recebe o sinal diretamente. Esta é a razão concreta pela qual a exec form importa: sem ela, todo o seu cuidado de shutdown gracioso é ignorado. Se mesmo na exec form os sinais não propagam para subprocessos, um init mínimo como tini (ou docker run --init) resolve o problema clássico do PID 1.

Capítulo 11

Volumes e persistência

O Capítulo 2 plantou um aviso que agora colhemos: a camada gravável de um container é efêmera, e tudo que ele escreve morre quando ele é removido. Isso é exatamente o que se quer para a maioria dos containers — eles devem ser descartáveis. Mas alguns dados não podem morrer: o banco de dados, os arquivos enviados por usuários, o estado que precisa sobreviver a reinícios e atualizações. A solução do Docker para persistência é manter esses dados fora do container, em volumes e bind mounts — armazenamento que existe independentemente do ciclo de vida do container. Este capítulo distingue os dois mecanismos, mostra quando usar cada um (volume para dados de produção, bind mount para desenvolvimento), e conecta diretamente ao stack da coleção: como conteinerizar o Postgres (Vol X) sem perder os dados a cada recriação do container. É o capítulo que separa "container como caixa descartável" de "dados que duram".

# O problema: dados que precisam sobreviver

Recapitulando o Capítulo 2: o que um container escreve vai para sua camada gravável, exclusiva dele, que é apagada no docker rm. Para um servidor web sem estado, isso é perfeito — você atualiza a imagem, recria o container, e nada se perde porque não havia nada para guardar. Mas coloque um Postgres num container, e o problema fica óbvio: recriar o container para atualizar a versão do Postgres apagaria todo o banco. Os dados precisam viver num lugar que o ciclo de vida do container não toca.

Banco de dados na camada gravável = perda garantida
O erro mais grave de quem começa: rodar um banco de dados em container sem volume, deixando os dados na camada gravável. Funciona nos testes — até a primeira vez que você precisa recriar o container (atualizar a imagem, mudar uma configuração, ou simplesmente um docker rm acidental). Aí todos os dados somem, irrecuperáveis (não há reflog aqui, ao contrário do Git). Qualquer dado que precise sobreviver a recriações — banco, uploads, estado — tem que estar num volume. A regra é absoluta: container é descartável; dados ficam fora dele.

# Volumes: a forma gerenciada

Um volume é um espaço de armazenamento gerenciado pelo Docker, separado dos containers, que você monta num caminho dentro do container. O Docker cuida de onde ele fica fisicamente (numa área própria no host); você só o referencia por nome. Quando um container escreve no caminho montado, os dados vão para o volume — e permanecem lá mesmo que o container seja removido. Outro container pode montar o mesmo volume e ver os dados. Volumes são a forma recomendada de persistir dados de produção.

terminal
# Criar um volume nomeado (gerenciado pelo Docker)
docker volume create pgdata

# Montar o volume no caminho onde o Postgres guarda os dados.
# -v nome_volume:caminho_no_container
docker run -d --name db \
  -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=segredo \
  postgres:16

# Agora 'docker rm db' NÃO apaga os dados — eles vivem em pgdata.
# Um novo container montando pgdata reencontra todo o banco.
docker volume ls

# Bind mounts: mapeando uma pasta do host

Um bind mount monta uma pasta do seu sistema de arquivos host diretamente dentro do container. Diferente do volume (gerenciado pelo Docker, em local opaco), o bind mount aponta para um caminho que você controla — ./src do seu projeto, por exemplo. Sua utilidade principal é o desenvolvimento: montando o código-fonte do host no container, mudanças que você edita no editor aparecem instantaneamente dentro do container, sem rebuild. É o que permite hot-reload de um container de desenvolvimento.

terminal
# Bind mount: a pasta atual do host vira /app no container.
# Editar arquivos no host reflete na hora dentro do container (dev).
docker run -d --name dev \
  -v "$(pwd)":/app \
  -p 3000:3000 \
  minha-app:dev

# Truque comum em dev: bind mount do código, MAS volume anônimo
# para node_modules, para não sobrescrever os do container com os do host
docker run -v "$(pwd)":/app -v /app/node_modules minha-app:dev
Volume vs bind mount: produção vs desenvolvimento
A distinção prática que organiza a escolha. Volume (gerenciado pelo Docker): para dados de produção que precisam persistir — bancos, uploads. O Docker controla o armazenamento, é portátil entre máquinas, e tem ferramentas de backup. Bind mount (pasta do host): para desenvolvimento — montar o código-fonte para edição ao vivo, ou expor um arquivo de config do host. Depende de um caminho específico da sua máquina, então não é portátil. Regra: dados que a aplicação produz e precisa guardar → volume; arquivos que você quer compartilhar entre host e container durante o desenvolvimento → bind mount.

# Gerenciando e fazendo backup de volumes

Como volumes guardam dados valiosos, saber inspecioná-los e copiá-los é essencial. O Docker oferece comandos para listar, inspecionar e remover volumes. Backup de um volume é feito rodando um container temporário que monta o volume e copia seu conteúdo para fora (um arquivo tar no host) — um padrão idiomático que vale conhecer, porque volumes não têm um "exportar" de um clique.

terminal
# Inspecionar um volume (onde fica, quando foi criado)
docker volume inspect pgdata

# Backup: um container temporário monta o volume e o tar vai para o host
docker run --rm -v pgdata:/dados -v "$(pwd)":/backup \
  alpine tar czf /backup/pgdata.tar.gz -C /dados .

# Remover volumes não usados (CUIDADO: dados somem — Cap 4)
docker volume prune
Volume não é estratégia de backup
Um volume protege os dados do ciclo de vida do container, mas não do disco da máquina: se o host morre, o volume morre com ele. Volumes resolvem persistência, não durabilidade. Dados que importam de verdade — o banco de produção — precisam de backups regulares para fora do host (outro servidor, um storage gerenciado), exatamente como o reflog do Git não substitui um remoto (Vol XIV, Cap 14). Para bancos, a prática correta combina o volume (persistência operacional) com dumps periódicos enviados a um armazenamento externo (durabilidade). "Está num volume" significa "sobrevive ao container", não "está seguro contra perda".

# Onde isso se encaixa no stack

Para o backend da coleção, o mapeamento é claro: a aplicação Hono (Vol IX) é sem estado — roda sem volume, descartável e escalável. O Postgres (Vol X) e o Redis usado para sessões e rate limiting (Vol XIII, Caps 6 e 19) são com estado — cada um precisa do seu volume para que os dados sobrevivam. Essa separação entre serviços sem estado (sem volume) e com estado (com volume) é um princípio de arquitetura que o Compose (Cap 14) materializa, e que orquestradores (Cap 21) levam a sério ao decidir o que pode ser movido livremente e o que está ancorado a dados.

Capítulo 12

Redes entre containers

Uma aplicação real não é um container só — é vários conversando: a API fala com o banco, com o cache, talvez com uma fila. O Capítulo 4 mostrou o -p para acessar um container de fora; este capítulo trata da outra metade, mais sutil: como containers conversam entre si. O Docker dá a cada container uma rede isolada (Cap 1), e o que torna a comunicação entre eles possível e elegante é o conceito de redes definidas pelo usuário com resolução de nomes — onde um container alcança outro simplesmente pelo nome, sem IPs fixos. Este capítulo desmonta os tipos de rede, mostra por que a DNS interna do Docker é a peça-chave para conectar a app ao Postgres, e esclarece a confusão recorrente entre portas internas e mapeadas. É a fundação de rede sobre a qual o Compose (Cap 14) constrói, automatizando tudo isto.

# Cada container tem sua própria rede

Por isolamento (Cap 1), cada container recebe sua própria interface de rede e seu próprio IP interno, separados do host e, por padrão, dos outros containers. Isso explica duas coisas já vistas: por que você precisa do -p para alcançar um container de fora (Cap 4), e por que dois containers não se enxergam automaticamente só por estarem na mesma máquina. A comunicação entre containers precisa de uma rede compartilhada que os conecte — e é aí que entram as redes do Docker.

# Os tipos de rede

O Docker oferece alguns drivers de rede, mas três importam no dia a dia. bridge é o padrão: uma rede virtual no host à qual containers se conectam, podendo falar entre si e com o exterior via mapeamento de portas. host remove o isolamento de rede — o container usa a rede do host diretamente (sem -p, mas sem isolamento). none desliga a rede completamente. A esmagadora maioria dos casos usa bridge, e especificamente uma bridge definida pelo usuário, que tem um superpoder que a bridge padrão não tem.

terminal
# Listar as redes (bridge, host, none vêm por padrão)
docker network ls

# Criar uma rede bridge definida pelo usuário (com DNS interno!)
docker network create app-net

# Inspecionar quem está conectado a uma rede
docker network inspect app-net

# A peça-chave: DNS por nome de container

Aqui está o conceito que faz tudo funcionar de forma elegante. Numa rede bridge definida pelo usuário, o Docker fornece resolução de DNS automática: um container pode alcançar outro pelo nome do container, e o Docker resolve esse nome para o IP interno certo. Isso elimina o pesadelo de IPs fixos — que mudam toda vez que um container reinicia. A API não precisa saber o IP do Postgres; ela conecta em db (o nome do container do banco), e o Docker faz a tradução.

terminal
# 1. Criar a rede e subir o Postgres nela, nomeado 'db'
docker network create app-net
docker run -d --name db --network app-net \
  -v pgdata:/var/lib/postgresql/data -e POSTGRES_PASSWORD=segredo postgres:16

# 2. Subir a app na MESMA rede
docker run -d --name api --network app-net -p 3000:3000 minha-app

# 3. A app conecta no banco pelo NOME 'db', não por IP:
#    DATABASE_URL=postgres://user:segredo@db:5432/meudb
#                                        ^^ nome do container = hostname
O nome do container vira o hostname
Esta é a ideia que destrava a comunicação entre serviços. Numa rede definida pelo usuário, --name db não é só um rótulo de conveniência (Cap 4) — vira um hostname resolvível. A connection string da aplicação usa db onde, fora do Docker, usaria localhost ou um IP. Isso torna a configuração portátil e estável: não importa qual IP o Postgres recebeu nem se ele reiniciou, db sempre aponta para ele. É exatamente assim que o Compose (Cap 14) conecta os serviços — ele cria uma rede e usa os nomes dos serviços como hostnames, automaticamente.

# Porta interna vs porta mapeada

Uma confusão recorrente: a relação entre a porta interna de um serviço e o mapeamento -p (Cap 4). São coisas diferentes para públicos diferentes. A porta interna (ex.: o Postgres na 5432) é como outros containers na mesma rede o alcançam — eles usam db:5432 diretamente, sem precisar de -p. O mapeamento -p é só para acessar o container do host. Ou seja: a app fala com o banco pela rede interna (porta interna, sem -p); você só precisa de -p no banco se quiser conectar nele a partir da sua máquina (com um cliente de SQL, por exemplo).

interno vs mapeado
# A app alcança o banco pela rede INTERNA, na porta interna 5432.
# NÃO precisa de -p no banco para isso funcionar:
#   api  --(rede app-net)-->  db:5432   ✓ (comunicação interna)

# -p só é necessário para acessar DO HOST (sua máquina):
docker run -d --name db --network app-net -p 5432:5432 postgres:16
#   seu cliente SQL no host -> localhost:5432 -> db   (só com -p)

# Em produção, NÃO exponha o banco com -p: deixe-o só na rede interna
Não exponha o banco ao host em produção
Uma decisão de segurança importante deriva da distinção acima. Em produção, o banco de dados deve ser alcançável apenas pela rede interna (pelos containers que precisam dele), nunca mapeado para o host com -p. Mapear a porta 5432 do Postgres para o host a expõe à rede da máquina — potencialmente à internet, se o firewall falhar —, um vetor de ataque sério. A app fala com o banco pela rede interna sem -p nenhum; só serviços que precisam ser acessados de fora (o servidor web, na 80/443) recebem mapeamento de porta. É o princípio do menor privilégio (Vol XIII, Cap 21) aplicado à rede: exponha o mínimo.

# Conectando e isolando

Containers podem ser conectados a redes na criação ou depois, e um container pode estar em várias redes ao mesmo tempo — um padrão usado para isolar grupos de serviços. Por exemplo: a app numa rede com o banco e em outra com um proxy reverso, sem que o proxy alcance o banco diretamente. Segmentar a rede assim limita o que cada serviço pode acessar, reduzindo a superfície de movimento lateral se um for comprometido.

terminal
# Conectar um container já rodando a outra rede
docker network connect outra-net api

# Desconectar de uma rede
docker network disconnect app-net api

# Segmentação: db só na rede interna; proxy só na rede de borda;
# a app nas duas (ponte) — o proxy nunca alcança o db diretamente

Capítulo 13

Variáveis de ambiente e secrets

Uma imagem deve ser a mesma em todos os ambientes — é o ponto inteiro da reprodutibilidade (Cap 1). Mas a configuração muda entre ambientes: a URL do banco em desenvolvimento não é a de produção, a chave de API de teste não é a real. A solução é o princípio que o Vol XIII já praticava: a imagem é fixa, a configuração entra de fora, em runtime, via variáveis de ambiente. Este capítulo trata de como configurar containers sem rebuildar a imagem, e — o ponto mais delicado — como lidar com segredos (senhas, tokens, chaves) sem jamais deixá-los vazar para dentro de uma camada da imagem. É onde toda a disciplina de segredos do Vol XIII (Caps 17 e 22) encontra o Docker: o JWT_SECRET e o DATABASE_URL precisam chegar ao container, mas nunca podem morar na imagem nem no Dockerfile. Acertar isso é a diferença entre uma configuração segura e um vazamento permanente.

# Configuração vem de fora, em runtime

O princípio organizador, conhecido como parte do "doze fatores": a configuração que varia entre ambientes não pertence à imagem — ela é injetada quando o container roda. A mesma imagem minha-app:1.0.0 roda em desenvolvimento, staging e produção; o que muda é o conjunto de variáveis de ambiente que cada ambiente fornece. Isso mantém a imagem reproduzível e única (uma só imagem por versão, testada e promovida entre ambientes) e a configuração flexível (sem rebuild para mudar uma URL).

terminal
# Passar variáveis individualmente com -e
docker run -d -e NODE_ENV=production -e PORT=3000 minha-app

# Passar um arquivo inteiro de variáveis com --env-file
docker run -d --env-file .env.production minha-app

# A app lê via process.env, como sempre (Vol VIII):
#   const dbUrl = process.env.DATABASE_URL

# ENV e ARG no Dockerfile: a distinção crítica

O Dockerfile tem duas instruções para variáveis, e confundi-las tem consequências de segurança. ENV define uma variável que fica na imagem e estará presente no container em runtime — boa para configuração padrão não-sensível (a porta padrão, NODE_ENV). ARG define uma variável disponível apenas durante o build, passada com --build-arg — boa para parametrizar a construção (qual versão baixar). O ponto crucial: nem ENV nem ARG servem para segredos, porque ambos ficam gravados em camadas inspecionáveis.

Dockerfile
# ENV: fica na imagem, presente em runtime. Para config NÃO sensível.
ENV NODE_ENV=production
ENV PORT=3000

# ARG: só no build, parametriza a construção. Também NÃO para segredos.
ARG NODE_VERSION=22
FROM node:${NODE_VERSION}-alpine

# ❌ NUNCA faça isto — o segredo fica GRAVADO numa camada para sempre:
# ENV JWT_SECRET=abc123        (visível em docker history / docker inspect)
# ARG API_KEY=...              (idem; ARG também vaza em camadas)
Segredo no Dockerfile = vazamento permanente
Este é o erro de segurança mais perigoso com Docker, e o mesmo do .env commitado no Git (Vol XIV, Cap 17). Qualquer segredo posto com ENV ou ARG no Dockerfile fica gravado numa camada imutável da imagem — recuperável por qualquer um com a imagem, via docker history ou docker inspect, mesmo que uma instrução posterior "apague" a variável (a camada anterior a contém, Cap 8). Como camadas são distribuídas no registry (Cap 9), publicar a imagem publica o segredo. Apagar do Dockerfile depois não resolve — assim como no Git, o segredo precisa ser rotacionado. A regra é inviolável: segredos nunca entram na imagem; chegam ao container em runtime.

# O caminho certo para segredos em runtime

Se segredos não vão na imagem, como chegam ao container? Em runtime, por canais que não persistem na imagem. O mais simples é --env-file apontando para um arquivo que vive só no servidor (e está no .gitignore e .dockerignore). Melhor ainda, em produção, são os mecanismos de secrets dos orquestradores, que entregam o segredo ao container como um arquivo em memória, sem passar por variável de ambiente (que pode vazar em logs ou docker inspect). O princípio: o segredo existe no ambiente de execução, não no artefato.

terminal
# Dev/simples: arquivo de segredos no servidor, fora do Git e da imagem
docker run -d --env-file /etc/minha-app/secrets.env minha-app
# secrets.env contém DATABASE_URL, JWT_SECRET... e está no .gitignore

# Produção: Docker secrets (Swarm) ou do orquestrador (Cap 21)
# O segredo é montado como arquivo em /run/secrets/, não em env
docker secret create jwt_secret ./jwt_secret.txt
# a app lê de /run/secrets/jwt_secret (não fica em docker inspect)

# Segredos durante o build: o secret mount

Às vezes você precisa de um segredo durante o build — um token para baixar de um registry npm privado, por exemplo. Pôr esse token num ARG o vazaria (já vimos). A solução do BuildKit (Cap 6) é o secret mount: o segredo é disponibilizado num arquivo temporário durante aquele RUN específico, e não é gravado em nenhuma camada. O build usa o segredo e ele desaparece, sem deixar rastro na imagem final.

Dockerfile + terminal
# No Dockerfile: o segredo é montado só durante este RUN, sem virar camada
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci
# Após o RUN, o token some — não fica na imagem

# No build: fornecer o segredo (BuildKit)
docker build --secret id=npm_token,src=./npm_token.txt -t app .
Variável de ambiente vs arquivo de segredo
Há uma hierarquia de segurança até entre os jeitos "corretos". Variáveis de ambiente em runtime (-e, --env-file) são aceitáveis e comuns, mas têm fraquezas: aparecem em docker inspect, podem ser herdadas por subprocessos, e às vezes vazam em logs ou mensagens de erro que despejam o ambiente. Segredos montados como arquivos (via Docker secrets ou o secret mount) são mais seguros — ficam em memória (tmpfs), não aparecem na inspeção do container, e não são herdados acidentalmente. Para a maioria dos casos, --env-file com um arquivo bem protegido basta; para os segredos mais sensíveis em produção, prefira o mecanismo de arquivos. O essencial, em qualquer caso: fora da imagem.

# Conectando ao stack da coleção

Para o backend dos volumes anteriores, isso se traduz direto. A imagem da app Hono é construída uma vez, sem nenhum segredo dentro. Em runtime, ela recebe DATABASE_URL (apontando para db:5432 na rede interna, Cap 12), JWT_SECRET (Vol XIII, Cap 9), as credenciais OAuth (Vol XIII, Cap 12), a URL do Redis — todos por variáveis de ambiente ou secrets, nunca embutidos. O .env.example versionado documenta quais variáveis existem (Vol XIV, Cap 17); o .env real, com os valores, vive só onde o container roda. A imagem é pública e reproduzível; a configuração é privada e por ambiente.

Capítulo 14

Docker Compose

Os capítulos anteriores subiram containers um a um, com longas linhas de docker run cheias de flags — -p, -v, --network, -e. Para uma aplicação real, com vários serviços que precisam ser criados na rede certa, com os volumes certos e na ordem certa, fazer isso à mão é tedioso e propenso a erro. O Docker Compose resolve isso declarativamente: um arquivo YAML descreve todos os serviços, redes e volumes da aplicação, e um único comando sobe tudo. Este capítulo introduz o Compose como a forma idiomática de orquestrar uma aplicação multi-container em desenvolvimento e em deploys simples — exatamente o stack da coleção (app + Postgres + Redis) num só arquivo versionado. É onde tudo dos capítulos anteriores — imagens, volumes, redes, variáveis — se reúne numa descrição declarativa, e onde "subir o ambiente inteiro" vira um comando.

# Do docker run ao YAML declarativo

O Compose troca comandos imperativos por uma descrição. Em vez de você dizer "rode este container com estas flags, depois aquele com aquelas", você descreve o estado desejado — "a aplicação consiste nestes serviços, conectados assim, com estes volumes" — e o Compose o realiza. Essa mudança do imperativo para o declarativo é a mesma filosofia do schema-as-code (Vol XI) e do Dockerfile: o ambiente vira um artefato de texto, versionado, revisável, reproduzível. O arquivo compose.yaml (ou docker-compose.yml) vive no repositório, ao lado do código.

compose.yaml
# Descreve a aplicação inteira: serviços, rede e volumes
services:
  api:
    build: .                  # constrói do Dockerfile local
    ports:
      - "3000:3000"           # o -p do Cap 4
    environment:
      DATABASE_URL: postgres://app:segredo@db:5432/meudb
    depends_on:
      - db                    # sobe o db antes (Cap 16 refina)

  db:
    image: postgres:16         # usa imagem pronta
    volumes:
      - pgdata:/var/lib/postgresql/data   # persistência (Cap 11)
    environment:
      POSTGRES_PASSWORD: segredo

volumes:
  pgdata:                     # declara o volume nomeado

# up e down: o ambiente inteiro num comando

Com o arquivo pronto, dois comandos governam tudo. docker compose up lê o YAML e cria (ou recria) todos os serviços, a rede e os volumes — sobe a aplicação inteira de uma vez, na ordem de dependência. docker compose down derruba e remove tudo que foi criado. A diferença em relação aos capítulos anteriores é enorme: o que era uma sequência frágil de comandos vira um up.

terminal
# Subir tudo (em background com -d); constrói imagens se necessário
docker compose up -d

# Ver os serviços do projeto e seu estado
docker compose ps

# Logs de todos os serviços juntos (ou de um: ... logs -f api)
docker compose logs -f

# Derrubar tudo (containers + rede). Adicione -v para apagar volumes também
docker compose down
Compose v2: "docker compose", sem hífen
Uma nota de versão importante. O Compose original era uma ferramenta Python separada, chamada com hífen: docker-compose (v1). O Compose moderno (v2) é um plugin integrado ao Docker, chamado sem hífen: docker compose (subcomando). A v1 está descontinuada; use a v2. O formato do arquivo é praticamente o mesmo, e o campo version: no topo do YAML — obrigatório na v1 — hoje é obsoleto e pode ser omitido. Se você vir tutoriais com docker-compose e version: "3.8" no topo, são da era v1; o equivalente atual é docker compose sem o campo version.

# O que o Compose automatiza

O Compose não é só conveniência de digitação — ele automatiza os conceitos dos capítulos anteriores. Ele cria uma rede para o projeto automaticamente, e conecta todos os serviços a ela, com os nomes dos serviços virando hostnames (Cap 12) — por isso a api alcança o banco em db:5432 sem nenhuma configuração de rede explícita. Ele gerencia os volumes declarados (Cap 11). Ele constrói imagens a partir dos build: (Cap 5). Tudo o que você fazia à mão com flags, o Compose deriva do arquivo.

Os nomes dos serviços são os hostnames
A conexão mais elegante com o Capítulo 12: no Compose, o nome do serviço (a chave sob services:) é o hostname pelo qual os outros serviços o alcançam. O serviço db é acessível em db; o redis, em redis. Por isso a DATABASE_URL no exemplo usa @db:5432 — db é o nome do serviço, e o Compose configura a DNS interna para resolvê-lo. Isso torna o arquivo portátil: não há IPs nem hostnames específicos de máquina, só os nomes lógicos dos serviços. Mudar de máquina ou de ambiente não quebra nada, porque a referência é ao serviço, não ao endereço.

# build vs image, e o ciclo de desenvolvimento

Um serviço no Compose ou constrói sua imagem (build: ., para a sua aplicação) ou usa uma imagem pronta (image: postgres:16, para serviços de terceiros). Em desenvolvimento, o Compose brilha combinando isso com bind mounts (Cap 11) para hot-reload: você monta o código-fonte no container da app, e edições aparecem na hora. Comandos como build (reconstruir), up --build (subir reconstruindo) e exec (entrar num serviço) compõem o fluxo diário.

terminal
# Reconstruir as imagens (após mudar o Dockerfile ou dependências)
docker compose build

# Subir reconstruindo o que mudou
docker compose up -d --build

# Entrar num serviço rodando (o exec do Cap 4, por nome de serviço)
docker compose exec api sh

# Rodar um comando único num serviço (ex.: migrations do Drizzle, Vol XI)
docker compose exec api npm run db:migrate
down -v apaga os volumes — e os dados
Cuidado com uma pegadinha comum no fluxo de desenvolvimento. docker compose down remove containers e a rede, mas preserva os volumes nomeados (e portanto os dados do banco). Já docker compose down -v remove também os volumes — apagando o banco inteiro (Cap 11). O -v é útil para "começar do zero, banco limpo" em desenvolvimento, mas devastador se rodado por engano com dados que importam. Como em todos os comandos destrutivos (do Git ao Docker), leia o que vai sumir antes de confirmar. Em produção, jamais rode down -v sem ter certeza absoluta e backups.

Capítulo 15

Compose múltiplos serviços

O Capítulo 14 montou um Compose de dois serviços. Aplicações reais têm mais, e organizá-las bem é o tema aqui. Este capítulo constrói o stack completo da coleção num único compose.yaml — a aplicação Hono, o Postgres, o Redis (para sessões e rate limiting do Vol XIII), e um proxy reverso na borda — mostrando os recursos do Compose que tornam isso limpo e manutenível: variáveis de ambiente vindas de arquivos, configurações compartilhadas entre serviços, perfis para separar desenvolvimento de produção, e a organização que mantém um arquivo de muitos serviços legível. É o capítulo onde toda a arquitetura dos volumes anteriores ganha forma conteinerizada concreta — não um exemplo de brinquedo, mas o esqueleto de um backend real rodando em containers coordenados.

# O stack completo em um arquivo

Vamos ao alvo direto: o backend da coleção, conteinerizado. Quatro serviços trabalham juntos — a api (Hono + Drizzle + autenticação), o db (Postgres, Vol X), o redis (cache de sessões e rate limiting, Vol XIII), e um proxy (nginx na borda, terminando HTTPS). Cada um é um serviço no Compose, conectado pela rede automática (Cap 12), com volumes onde há estado (Cap 11) e configuração por ambiente (Cap 13).

compose.yaml
services:
  api:
    build: .
    env_file: .env             # variáveis do arquivo (Cap 13)
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/meudb
      REDIS_URL: redis://redis:6379
    depends_on:
      - db
      - redis
    restart: unless-stopped     # Cap 10

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: meudb
    volumes:
      - pgdata:/var/lib/postgresql/data
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    volumes:
      - redisdata:/data
    restart: unless-stopped

  proxy:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"            # só o proxy é exposto ao mundo
    depends_on:
      - api

volumes:
  pgdata:
  redisdata:

Repare na arquitetura de exposição: apenas o proxy publica portas para o host (80/443). A api, o db e o redis não têm ports: — eles só são acessíveis na rede interna (Cap 12). O mundo externo chega ao proxy, que encaminha para a api; a api fala com db e redis internamente; o banco nunca é exposto. Essa é a aplicação direta do menor privilégio de rede (Cap 12) materializada na estrutura do Compose.

# Variáveis e o arquivo .env do Compose

O Compose tem dois usos de variáveis que vale distinguir. O env_file/environment dentro de um serviço define as variáveis que aquele container recebe (Cap 13). Mas há também a interpolação no próprio YAML: um .env na pasta do Compose fornece valores para os ${...} usados no arquivo. É por isso que ${DB_PASSWORD} funciona — o Compose lê um .env e substitui antes de subir. Isso mantém senhas fora do YAML versionado: o compose.yaml referencia ${DB_PASSWORD}, e o valor real vive no .env ignorado pelo Git.

.env (na pasta do compose, no .gitignore)
# O Compose interpola estes valores nos ${...} do compose.yaml
DB_PASSWORD=uma-senha-forte-aqui
JWT_SECRET=outro-segredo

# compose.yaml referencia ${DB_PASSWORD}; o valor real fica aqui,
# fora do YAML versionado. Versione um .env.example sem os valores.
O compose.yaml é versionado; o .env não
A divisão é a mesma de sempre (Vol XIII e XIV): a estrutura vai para o Git, os segredos não. O compose.yaml descreve a arquitetura e é versionado — qualquer um deve poder lê-lo. Mas ele referencia segredos por ${...}, nunca os contém. O .env com os valores reais fica no .gitignore e no .dockerignore. Um .env.example versionado lista as chaves necessárias sem os valores, documentando o que precisa ser configurado. Colocar uma senha literal no compose.yaml é o mesmo erro de commitar um segredo — ele entra na história do Git para sempre.

# Configuração compartilhada com âncoras YAML

Quando vários serviços compartilham configuração — a mesma política de restart, as mesmas variáveis de logging —, repetir é convite a divergência. O YAML oferece âncoras (&) e aliases (*) para definir um bloco uma vez e reusá-lo, e o Compose os suporta. É a forma de manter um arquivo de muitos serviços DRY, sem copiar e colar configurações que deveriam ser idênticas.

compose.yaml (âncoras)
# Define um bloco comum uma vez, com uma âncora (&)
x-comum: &comum
  restart: unless-stopped
  logging:
    driver: json-file
    options: { max-size: "10m", max-file: "3" }

services:
  api:
    <<: *comum               # reusa o bloco (alias *)
    build: .
  db:
    <<: *comum               # mesma config comum, sem repetir
    image: postgres:16

# Perfis: dev e prod no mesmo arquivo

Às vezes alguns serviços só fazem sentido em certos contextos — uma ferramenta de administração de banco em desenvolvimento, que não deve subir em produção. Os profiles permitem marcar serviços para que só subam quando o perfil correspondente é ativado. Assim um único compose.yaml serve a dev e prod, com os serviços extras de desenvolvimento ficando dormentes a menos que explicitamente pedidos.

compose.yaml + terminal
# Um serviço só de dev: ferramenta de admin do banco
# services:
#   adminer:
#     image: adminer
#     profiles: [dev]      <- só sobe se o perfil 'dev' for ativado

# Subir só o stack base (sem os serviços de perfil)
docker compose up -d

# Subir incluindo os serviços do perfil 'dev'
docker compose --profile dev up -d
Compose é ótimo para dev; produção é outra conversa
O Compose é a ferramenta ideal para desenvolvimento local e para deploys simples num único servidor — sobe o stack inteiro com um comando, reproduzível. Mas ele não é, por si só, uma plataforma de produção robusta para escala: não distribui containers por várias máquinas, não faz balanceamento entre réplicas em nós diferentes, não recupera de falha de hardware. Para isso entram os orquestradores (Cap 21, Kubernetes). Muitas equipes usam Compose em dev e em servidores únicos pequenos, e migram para um orquestrador quando a escala exige. O conhecimento transfere: os conceitos — serviços, redes, volumes, dependências — são os mesmos; muda a camada que os gerencia em escala.

Capítulo 16

Healthchecks e dependências

O Capítulo 15 montou o stack com depends_on ditando a ordem de inicialização. Mas há uma armadilha sutil escondida ali: "iniciar o banco antes da api" não é o mesmo que "o banco está pronto para receber conexões antes de a api tentar conectar". Um container Postgres pode estar rodando sem ainda estar aceitando conexões — e a api, subindo logo atrás, tenta conectar, falha, e crasha. Este capítulo resolve esse problema clássico de coordenação juntando dois conceitos: os healthchecks (Cap 10), que distinguem "rodando" de "pronto", e as dependências condicionais do Compose, que esperam não só o container subir, mas ficar saudável. É um capítulo sobre fazer serviços coordenarem corretamente — o tipo de detalhe que separa um stack que sobe de primeira de um que falha aleatoriamente na inicialização.

# "Iniciado" não é "pronto"

A distinção central, antecipada no Capítulo 10: um container estar no estado Running significa que seu processo principal começou — não que o serviço dentro dele está pronto para trabalhar. Um Postgres leva alguns segundos entre iniciar o processo e estar aceitando conexões (ele precisa inicializar o banco, recuperar do log, abrir o socket). Durante essa janela, o container está "rodando" mas o banco está indisponível. Qualquer serviço que dependa dele e tente conectar nessa janela vai falhar.

depends_on sozinho não espera o serviço ficar pronto
A pegadinha que pega quase todo mundo: depends_on: [db] garante que o Compose inicia o db antes da api — mas não espera o Postgres estar aceitando conexões. O Compose considera a dependência satisfeita assim que o container do db começa, não quando o banco está pronto. Resultado: a api sobe, tenta conectar num Postgres que ainda está inicializando, recebe "connection refused", e (se não tratar isso) crasha. O sintoma é traiçoeiro porque é intermitente — às vezes o db está pronto a tempo, às vezes não, dependendo de timing. A solução combina healthcheck + dependência condicional.

# Healthcheck: definindo "pronto"

O healthcheck (Cap 10) é o que dá ao Docker uma definição de "pronto" para cada serviço. Para o Postgres, "pronto" é "aceita conexões" — verificável com pg_isready. Para a sua api, é "responde no endpoint de saúde". Cada serviço declara seu próprio healthcheck no Compose, e o Docker passa a rastrear o estado healthy/unhealthy além de apenas running.

compose.yaml (healthchecks)
services:
  db:
    image: postgres:16
    healthcheck:
      # pg_isready: "pronto" = aceita conexões
      test: ["CMD-SHELL", "pg_isready -U app -d meudb"]
      interval: 5s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      retries: 5

# Dependência condicional: esperar ficar saudável

Com healthchecks definidos, o depends_on pode ser elevado de "espere iniciar" para "espere ficar saudável". A forma estendida do depends_on aceita uma condição: service_healthy diz ao Compose para só iniciar o serviço dependente depois que a dependência passar no healthcheck. Agora a api só sobe quando o db está de fato aceitando conexões — o problema de coordenação resolvido na origem.

compose.yaml (depends_on condicional)
services:
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy   # espera o db passar no healthcheck
      redis:
        condition: service_healthy   # idem para o redis
    # Agora a api só inicia quando db E redis estão prontos de verdade
Defesa em profundidade: healthcheck + retry na aplicação
A dependência condicional resolve a inicialização, mas não cobre tudo: durante a operação, o banco pode reiniciar, a rede pode oscilar, e a api precisa sobreviver a uma perda temporária de conexão sem crashar. Por isso a prática robusta combina duas camadas. O healthcheck + condition: service_healthy cuida da partida ordenada. E a aplicação deve ter retry com backoff na sua lógica de conexão — tentar reconectar ao banco algumas vezes antes de desistir (a mesma ideia de resiliência do Vol X/XI). É defesa em profundidade (Vol XIII, Cap 21): nenhuma camada sozinha basta, mas juntas tornam o sistema resiliente tanto na partida quanto na operação.

# Healthcheck da própria aplicação

A api também merece um healthcheck — não só para coordenar quem depende dela, mas para que orquestradores (Cap 21) e proxies saibam se devem mandar tráfego. O endpoint /health da aplicação (Vol IX/XIII) é o alvo natural, e — recuperando a lição do Cap 10 — ele deve verificar as dependências críticas, não só responder 200. Um /health que confirma a conexão com o banco e o Redis dá uma leitura honesta de "a aplicação consegue trabalhar".

compose.yaml + health.ts
# compose.yaml: healthcheck da api apontando para seu /health
#   healthcheck:
#     test: ["CMD", "wget", "--spider", "-q", "http://localhost:3000/health"]
#     interval: 10s

// health.ts — verifica dependências, não só responde 200 (Cap 10)
app.get('/health', async (c) => {
  try {
    await db.execute('SELECT 1')        // banco responde? (Vol X)
    await redis.ping()                   // redis responde? (Vol XIII)
    return c.json({ status: 'ok' })
  } catch {
    return c.json({ status: 'unhealthy' }, 503)
  }
})

# Ordem de desligamento e dependências

As dependências também influenciam o desligamento. Quando você roda docker compose down, o Compose para os serviços na ordem inversa das dependências — primeiro quem depende, depois de quem se depende —, dando a cada um a chance de encerrar limpo (o SIGTERM do Cap 10) antes que suas dependências sumam. Combinado com o shutdown gracioso da aplicação (Cap 10), isso garante que a api termine suas requisições em andamento e feche as conexões com o banco antes de o banco ser parado.

Capítulo 17

Segurança de containers

O Capítulo 1 deixou um aviso: o isolamento de container é mais fraco que o de uma VM, e "está num container" não significa "está seguro". Este capítulo desenvolve esse aviso numa prática. Containers introduzem uma superfície de ataque própria — uma imagem com vulnerabilidades conhecidas, um processo rodando como root que escapa para o host, um segredo embutido numa camada — e endurecê-los é trabalho deliberado, não algo que vem de graça. Os princípios não são novos: são os mesmos do Vol XIII (Cap 21) — menor privilégio, defesa em profundidade, falhar fechado — aplicados ao mundo dos containers. Este capítulo reúne as práticas essenciais: rodar como usuário não-root, usar imagens base mínimas e atualizadas, escanear vulnerabilidades, limitar recursos e capacidades, e manter segredos fora da imagem. Cada uma fecha um vetor; juntas, transformam um container ingênuo num cidadão de produção defensável.

# O problema do root: o padrão perigoso

Por padrão, processos dentro de um container rodam como root — o usuário com todos os poderes. Isso é conveniente (nada de problemas de permissão) e perigoso. Lembrando o Capítulo 1: um container é um processo isolado que compartilha o kernel do host. Se uma vulnerabilidade permite que um processo root dentro do container escape do isolamento, ele escapa como root no host — controle total da máquina. Rodar como root dentro do container amplia drasticamente o dano de qualquer comprometimento. A primeira e mais importante prática de segurança é simplesmente não rodar como root.

Dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .

# Criar um usuário sem privilégios e mudar para ele.
# (imagens node já trazem um usuário 'node'; basta usá-lo)
USER node

# A partir daqui, o processo roda como 'node', não como root.
# Se ele for comprometido, o atacante NÃO tem root.
CMD ["node", "dist/index.js"]
Menor privilégio, agora no container
O USER node é a aplicação direta do princípio do menor privilégio (Vol XIII, Cap 21) ao Docker. O processo deve ter o mínimo de poder necessário para funcionar — e quase nenhuma aplicação web precisa de root. Rodar como usuário comum não impede a aplicação de servir requisições, conectar ao banco, ou ler seu código; só remove os superpoderes que um atacante adoraria herdar. É barato (uma linha no Dockerfile) e fecha o vetor mais grave de escalada container→host. Se você adotar uma só prática deste capítulo, que seja esta.

# Imagens mínimas: menos código, menos risco

A escolha de base (Caps 5, 8) é também uma decisão de segurança. Cada binário, biblioteca e ferramenta numa imagem é código que pode ter uma vulnerabilidade. Uma imagem node:22 completa traz um sistema Debian inteiro — compiladores, shells, utilitários — a maioria irrelevante para rodar a sua app, e cada um uma porta potencial. Imagens mínimas (Alpine, e especialmente distroless, Cap 18) reduzem essa superfície ao essencial. Menos software não é só menos espaço (Cap 8); é menos coisa para um atacante explorar e menos CVEs para acompanhar.

# Escaneando vulnerabilidades

Você não sabe o que não mede. Imagens — mesmo as oficiais — contêm dependências que ganham vulnerabilidades conhecidas (CVEs) com o tempo. Ferramentas de scan analisam uma imagem e listam as vulnerabilidades dos seus componentes, com severidade. Rodar um scan no CI (Vol XIV, Cap 19) a cada build, e periodicamente nas imagens em produção, é a forma de descobrir que aquela base que era segura há três meses agora tem um CVE crítico — e precisa ser reconstruída sobre uma base atualizada.

terminal
# Escanear uma imagem em busca de vulnerabilidades conhecidas (CVEs)
docker scout cves minha-app:1.0.0

# Alternativa popular: trivy
trivy image minha-app:1.0.0
# Lista CVEs por severidade; integre no CI para falhar em crítico/alto

# A correção quase sempre é: reconstruir sobre uma base atualizada
docker build --no-cache -t minha-app:1.0.1 .
Imagens são código com prazo de validade
Uma imagem não é segura "para sempre" só porque era no dia do build. O mundo descobre vulnerabilidades continuamente nos componentes que ela contém — o mesmo princípio do "segurança é processo, não estado" do Vol XIII (Cap 21). Isso significa duas disciplinas: reconstruir imagens regularmente sobre bases atualizadas (não deixar uma imagem rodar por anos), e fixar versões mas atualizá-las deliberadamente (não latest cego, mas também não node:22.0.0 congelado para sempre). O cache de build (Cap 6) pode até perpetuar camadas antigas com CVEs — daí o --no-cache periódico. Manter imagens atualizadas é manutenção contínua, igual a manter dependências do package.json em dia.

# Limitando recursos e capacidades

Dois outros controles endurecem o container. Limites de recursos (CPU, memória) impedem que um container — por bug ou ataque — consuma toda a máquina, derrubando os vizinhos; são os cgroups do Capítulo 1 expostos como flags. Capacidades são poderes granulares do kernel (montar sistemas de arquivos, mexer na rede, etc.); por padrão containers recebem um conjunto, mas você pode remover os que a aplicação não usa, reduzindo o que um processo comprometido consegue fazer. Remover todas e adicionar só as necessárias é menor privilégio levado ao kernel.

terminal / compose.yaml
# Limitar memória e CPU (evita que um container derrube a máquina)
docker run -d --memory="512m" --cpus="1.0" minha-app

# Sistema de arquivos somente-leitura: o container não pode escrever
# em lugar nenhum exceto onde você permite explicitamente
docker run -d --read-only --tmpfs /tmp minha-app

# Remover TODAS as capacidades e re-adicionar só as necessárias
docker run -d --cap-drop=ALL --cap-add=NET_BIND_SERVICE minha-app

# A checklist de segurança de container

Reunindo, as práticas formam uma checklist que ecoa o Vol XIII. Cada item fecha um vetor; nenhum sozinho basta (defesa em profundidade), e juntos tornam o comprometimento difícil e contido. Vale percorrê-la antes de levar uma imagem a produção.

checklist de produção
# [ ] USER não-root no Dockerfile (não rodar como root)
# [ ] Base mínima e atualizada (alpine/distroless; Cap 18)
# [ ] Scan de CVEs no CI; reconstruir sobre base atualizada
# [ ] Segredos FORA da imagem; injetados em runtime (Cap 13)
# [ ] .dockerignore exclui .env, .git (Cap 8)
# [ ] Limites de memória/CPU (não derrubar a máquina)
# [ ] --read-only + --cap-drop quando viável
# [ ] Banco só na rede interna, nunca exposto (Cap 12)

Capítulo 18

Imagens enxutas e distroless

Os capítulos de otimização (8) e segurança (17) convergem aqui, numa ideia que leva ambos ao limite: e se a imagem não tivesse nada além do estritamente necessário para rodar a aplicação? Sem shell, sem gerenciador de pacotes, sem utilitários — só o runtime e o seu código. É a proposta das imagens distroless: imagens base que removem o sistema operacional tradicional, deixando apenas o que a aplicação precisa para executar. O resultado é o menor tamanho e a menor superfície de ataque possíveis — uma imagem que um atacante, mesmo dentro dela, não consegue fazer muita coisa, porque não há ferramentas para usar. Este capítulo explica o que distroless é, como usá-la com multi-stage builds (Cap 7), os trade-offs reais (depurar sem shell é diferente), e quando ela é a escolha certa. É o capítulo que fecha o tema de construção de imagens com a configuração mais enxuta e segura disponível.

# A ideia: remover o sistema operacional

Uma imagem Alpine já é mínima, mas ainda traz um sistema operacional funcional: um shell (sh), um gerenciador de pacotes (apk), utilitários básicos. Distroless vai além — remove tudo isso. Uma imagem distroless contém apenas o runtime da linguagem (a máquina virtual do Node, por exemplo), as bibliotecas de sistema que ele precisa, certificados, e o seu código. Não há shell para abrir, não há apt ou apk, não há ls ou cat. É o ambiente mínimo absoluto onde a aplicação ainda roda.

Sem shell = muito menos para atacar
A ausência de shell não é só economia de espaço — é a maior vitória de segurança da distroless. Boa parte dos ataques pós-comprometimento depende de ferramentas do sistema: abrir um shell, baixar um payload com curl, explorar o sistema de arquivos com utilitários. Numa imagem distroless, mesmo que um atacante consiga executar código no contexto da aplicação, ele encontra um ambiente quase vazio — sem shell para escalar, sem curl para exfiltrar, sem ferramentas para se mover. Reduzir a imagem ao runtime puro remove o arsenal que um invasor esperaria encontrar. É menor privilégio (Cap 17) levado ao extremo: não dá para usar o que não existe.

# Distroless com multi-stage

Distroless não tem ferramentas de build (nem npm), então ela só funciona como estágio final de um multi-stage build (Cap 7). Você usa uma imagem completa para construir — instalar dependências, compilar — e copia o resultado para uma imagem distroless mínima que só roda. É a combinação perfeita: o estágio de build tem tudo; o estágio final, só o runtime e o artefato.

Dockerfile (multi-stage + distroless)
# ===== build: imagem completa, com todas as ferramentas =====
FROM node:22 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build && npm prune --omit=dev

# ===== runtime: distroless, só o Node e o necessário =====
FROM gcr.io/distroless/nodejs22-debian12
WORKDIR /app
# Copia o build e as deps de produção do estágio anterior
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
# distroless/nodejs já tem 'node' como entrypoint:
CMD ["dist/index.js"]
# Imagem final: ~50-100MB, sem shell, rodando como não-root por padrão

# O trade-off: depurar sem ferramentas

Distroless tem um custo real, e ignorá-lo causa frustração. Sem shell, você não pode fazer docker exec -it container sh (Cap 4) para entrar e investigar — não há sh para executar. As técnicas de depuração que dependem de abrir um terminal dentro do container não funcionam. Isso não torna a depuração impossível, mas muda as técnicas: você inspeciona via logs (que devem ir para stdout, Cap 4), via healthchecks, e — quando precisa mesmo de um shell — usando containers de depuração efêmeros que se anexam ao mesmo namespace, sem que a imagem de produção precise carregar as ferramentas.

terminal
# Isto NÃO funciona em distroless — não há shell:
#   docker exec -it api sh    ->  erro: executable file not found

# Depuração: anexar um container EFÊMERO com ferramentas ao mesmo
# namespace do container alvo (a imagem de prod continua mínima)
docker debug api                # Docker Desktop: shell temporário no container

# Em Kubernetes (Cap 21): kubectl debug com um container efêmero
# A imagem de produção fica enxuta; as ferramentas vêm só quando preciso
Variantes :debug existem, mas derrotam o propósito em produção
As imagens distroless oferecem variantes :debug que incluem um shell mínimo (BusyBox) — úteis durante o desenvolvimento ou para diagnóstico pontual. Mas usar a variante :debug em produção derrota o ganho de segurança: você reintroduz exatamente o shell que a distroless removeu. A prática correta é produção com a imagem distroless pura (sem shell), e depuração via containers efêmeros anexados ou logs. Se você se vê tentado a usar :debug em produção "para conseguir entrar e investigar", o sinal é que a observabilidade (logs, métricas, healthchecks — Cap 19) precisa melhorar, não que a imagem precisa de shell.

# O espectro de bases

Distroless é uma extremidade de um espectro, e a escolha certa depende do contexto. Do mais completo ao mais enxuto: a base completa (node:22) tem tudo, é grande, boa para desenvolvimento; slim corta o supérfluo mantendo glibc e um shell; Alpine é bem menor (musl, shell mínimo); distroless remove o SO, deixando só o runtime. Quanto mais à direita, menor e mais seguro, mas menos ferramentas para depurar. Para produção de uma aplicação madura, com boa observabilidade, distroless é o ideal; para começar ou depurar muito, Alpine costuma ser o ponto de equilíbrio.

Capítulo 19

Logging e observabilidade

Containers são efêmeros (Cap 2) e numerosos — quando algo dá errado num sistema de dezenas de containers que vão e voltam, "entrar na máquina e olhar o log" não escala, e na distroless (Cap 18) nem é possível. A observabilidade — a capacidade de entender o que está acontecendo dentro do sistema a partir de fora — precisa ser projetada, não improvisada. Este capítulo cobre como containers produzem e o Docker coleta logs, a convenção de logar para stdout (já antecipada no Cap 4) e por que ela é fundamental, os logging drivers que enviam logs para sistemas centralizados, e os três pilares da observabilidade — logs, métricas e traces — aplicados a containers. Conecta diretamente à observabilidade do Vol XIII (Cap 22): a mesma disciplina de "logue eventos estruturados, sem dados sensíveis" agora tem o Docker como o mecanismo de coleta. É o capítulo que torna um sistema conteinerizado diagnosticável.

# A convenção: logar para stdout

O Capítulo 4 estabeleceu a regra; aqui está o porquê completo. Em containers, a aplicação deve escrever logs para stdout/stderr, nunca para arquivos dentro do container. Duas razões fundamentais. Primeira: a camada gravável é efêmera (Cap 2), então logs em arquivo somem com o container — exatamente quando você mais precisa deles (depois de um crash). Segunda: o Docker captura automaticamente stdout/stderr de cada container, transformando os logs num fluxo gerenciável que pode ser coletado, roteado e centralizado. A aplicação não deve se preocupar com onde o log vai parar — só emite para stdout, e a infraestrutura cuida do resto.

logger.ts
// Em containers: logue para stdout, em JSON estruturado (Vol XIII, Cap 22)
// O Docker captura; a app não escreve arquivos.
function log(event: string, meta: Record<string, unknown>) {
  console.log(JSON.stringify({
    event,
    ...meta,
    at: new Date().toISOString(),
  }))
  // NUNCA logar senha, token, OTP (Vol XIII, Cap 22) — vale igual aqui
}

# Coletando logs do Docker

Com a aplicação logando para stdout, o Docker oferece o acesso. docker logs (Cap 4) lê os logs de um container; no Compose, docker compose logs agrega os de todos os serviços, identificando cada linha pelo serviço de origem. Para desenvolvimento e diagnóstico pontual, isso basta. O -f acompanha em tempo real, e filtros de tempo ajudam a focar numa janela de interesse.

terminal
# Logs agregados de todos os serviços, em tempo real
docker compose logs -f

# Só de um serviço, últimas 100 linhas, desde 10 min atrás
docker compose logs --tail 100 --since 10m api

# Logs de um container avulso (fora do Compose)
docker logs -f --timestamps meu-container

# Logging drivers e centralização

Ver logs com docker logs não escala para produção com muitos containers em muitas máquinas. O Docker resolve isso com logging drivers: configurações que dizem para onde os logs de stdout/stderr vão. O driver padrão (json-file) guarda no host; mas você pode configurar drivers que enviam os logs para sistemas centralizados de agregação, onde logs de todos os containers se juntam, ficam pesquisáveis, e podem disparar alertas. A aplicação continua só logando para stdout — o driver decide o destino.

compose.yaml (logging)
services:
  api:
    build: .
    logging:
      driver: json-file
      options:
        # Rotação: evita que logs encham o disco do host (importante!)
        max-size: "10m"
        max-file: "3"
# Em produção, drivers como fluentd/gelf/awslogs enviam para
# agregadores centralizados (Loki, ELK, CloudWatch...)
Sem rotação, os logs enchem o disco
Uma pegadinha operacional clássica: o driver padrão json-file guarda os logs no host sem limite por padrão. Um container que loga muito, por dias, pode encher o disco da máquina inteira — derrubando não só ele, mas todos os outros containers e o próprio host. Sempre configure rotação de logs (max-size e max-file) para que logs antigos sejam descartados automaticamente. É o equivalente Docker de um logrotate. Esquecer isso é uma das causas mais comuns de "o servidor parou do nada" — não foi a aplicação, foi o disco lotado de logs.

# Os três pilares: logs, métricas, traces

Logs são um dos três pilares da observabilidade, e produção madura usa os três juntos. Logs são eventos discretos ("usuário X fez login", "erro ao conectar ao banco") — bons para entender o que aconteceu. Métricas são números agregados ao longo do tempo (requisições por segundo, uso de memória, latência) — boas para ver tendências e disparar alertas. Traces seguem uma requisição através de vários serviços — bons para entender onde o tempo foi gasto num sistema distribuído. Cada um responde a uma pergunta diferente; juntos, dão uma visão completa.

os três pilares
# LOGS    — eventos discretos          "o que aconteceu?"
#           console.log estruturado -> stdout -> agregador

# MÉTRICAS — números no tempo           "qual a tendência? alertar?"
#           req/s, latência, memória -> Prometheus -> alertas

# TRACES  — caminho de uma requisição   "onde foi gasto o tempo?"
#           span por serviço         -> OpenTelemetry -> visualização

# Inspeção e métricas de container

Além dos logs da aplicação, o Docker expõe métricas dos próprios containers — uso de CPU, memória, rede — úteis para diagnosticar problemas de recurso (aquele container morto com código 137/OOM do Cap 10). docker stats mostra isso ao vivo; docker inspect revela toda a configuração e estado de um container. São as ferramentas de primeira linha quando algo está lento ou morrendo.

terminal
# Uso de recursos ao vivo (CPU, memória, rede) por container
docker stats
# CONTAINER   CPU %   MEM USAGE / LIMIT   NET I/O
# api         2.5%    180MiB / 512MiB     1.2MB / 800kB

# Estado e configuração completos de um container (JSON)

# Os eventos do daemon em tempo real (criação, parada, oom...)

Observabilidade é projetada, não improvisada
A grande lição, ecoando o Vol XIII (Cap 22): você não consegue depurar em produção o que não instrumentou. Num sistema de containers efêmeros, quando um problema aparece, o container culpado pode já ter sido recriado — e se ele não logou o suficiente, para stdout, com contexto estruturado, a evidência se foi. Projete a observabilidade antes de precisar dela: logs estruturados com IDs de correlação, métricas dos caminhos críticos, healthchecks significativos (Cap 16), e rotação configurada. O esforço investido em instrumentação se paga no primeiro incidente — a diferença entre diagnosticar em minutos e adivinhar por horas.

Capítulo 20

CI/CD com Docker

O Capítulo 9 esboçou o ciclo Git → imagem → deploy; este o constrói por inteiro, automatizado. A integração contínua e a entrega contínua (CI/CD) são o que transforma "eu construo a imagem na minha máquina e faço deploy à mão" num pipeline automático: cada commit dispara testes, constrói a imagem, e — quando apropriado — a implanta. O Docker é a peça que torna esse pipeline confiável, porque o artefato que atravessa cada etapa é o mesmo container imutável, do teste à produção. Este capítulo monta o pipeline completo usando GitHub Actions (o CI que o Vol XIV introduziu no Cap 19), reunindo tudo: o build de imagem dos capítulos anteriores, o registry (Cap 9), as tags versionadas, e a estratégia de deploy. É onde a conteinerização cumpre sua promessa final — o código testado vira, automaticamente, o container que roda em produção, sem intervenção manual e sem "funciona na minha máquina".

# CI vs CD: integração e entrega

Os dois termos se confundem mas têm papéis distintos. CI (Integração Contínua) é o que acontece a cada commit/PR: rodar testes, lint, build — garantir que o código novo se integra sem quebrar (Vol XIV, Cap 19). CD (Entrega/Implantação Contínua) é o passo seguinte: pegar o que passou no CI, construir o artefato (a imagem Docker), e implantá-lo — em staging automaticamente, em produção automaticamente ou com aprovação. O Docker é a ponte entre os dois: o CI valida o código, o CD empacota esse código validado numa imagem e a entrega.

o pipeline, em fases
# push / PR  (Vol XIV)
#    │
#    ▼  CI: valida o código
# lint -> typecheck -> testes        (falhou? para aqui)
#    │
#    ▼  CD: empacota e entrega
# docker build -> scan CVEs (Cap 17) -> push ao registry (Cap 9)
#    │
#    ▼  deploy
# produção puxa a imagem versionada e a roda

# O workflow de build e push

O coração do pipeline de CD é um workflow que constrói a imagem e a envia ao registry. Em GitHub Actions, isso usa as actions oficiais do Docker, autenticando no registry com um token (Cap 9) que vem dos secrets do repositório — nunca no código (Vol XIII). O workflow tipicamente roda quando uma tag de versão é criada (Vol XIV, Cap 16) ou em pushes para a branch principal.

.github/workflows/deploy.yml
name: build-and-push
on:
  push:
    tags: ['v*']            # dispara em tags de versão (Vol XIV, Cap 16)

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Autentica no registry com um SECRET (nunca no código)
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Constrói e envia, marcando com a versão da tag Git
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/org/app:${{ github.ref_name }}
O mesmo artefato do teste à produção
A garantia que o Docker traz ao CI/CD: o que você implanta é byte por byte o que foi testado. Sem containers, o CI testa numa máquina e o deploy reconstrói o ambiente em outra — duas reconstruções que podem divergir. Com Docker, o CI constrói uma imagem, os testes rodam nessa imagem, e essa mesma imagem (o mesmo digest, Cap 9) é a que vai para produção. Não há reconstrução, não há "será que o ambiente de prod é igual?". A imagem é o contrato imutável que atravessa todo o pipeline — a materialização final da promessa de reprodutibilidade do Capítulo 1.

# Cache de build no CI

Builds no CI partem de uma máquina limpa toda vez, o que anularia o cache de camadas (Cap 6) — cada build reconstruiria tudo, desperdiçando minutos. As actions de build do Docker resolvem isso com cache externo: o cache de camadas é guardado entre execuções (no próprio registry ou no cache do CI) e restaurado no início de cada build. Assim, mesmo numa máquina nova, o build reaproveita as camadas que não mudaram, mantendo o pipeline rápido.

.github/workflows (cache)
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/org/app:${{ github.ref_name }}
          # Cache de camadas entre builds do CI (Cap 6 numa máquina limpa)
          cache-from: type=gha
          cache-to: type=gha,mode=max
          # gha = GitHub Actions cache; restaura camadas não alteradas

# Estratégias de deploy

Ter a imagem no registry é metade do CD; a outra é como colocá-la em produção sem derrubar o serviço. As estratégias comuns minimizam ou eliminam o downtime. Rolling update: substitui as réplicas aos poucos, uma de cada vez, mantendo o serviço no ar. Blue-green: sobe a versão nova (green) em paralelo à atual (blue), e troca o tráfego de uma vez quando a nova está pronta. Canary: manda só uma fração do tráfego para a versão nova, observa, e amplia gradualmente. A escolha depende da infraestrutura — o Compose faz rolling simples; orquestradores (Cap 21) fazem as três sofisticadamente.

A imutabilidade torna o rollback trivial
Um benefício enorme e fácil de subestimar: como cada deploy é uma imagem imutável e versionada (Cap 9), o rollback é apenas "rode a imagem da versão anterior". Deu problema na v1.4.2? Implante de novo a v1.4.1 — a imagem ainda está no registry, idêntica ao que rodava antes, sem reconstruir nada. Compare com deploys sem containers, onde "voltar" exige reverter código, reinstalar, reconfigurar — propenso a erro e lento. Com Docker, avançar e recuar são a mesma operação (trocar qual imagem roda), e ambas são instantâneas e confiáveis. É o equivalente em deploy da reversibilidade que o Git deu ao código (Vol XIV) — e a razão de tags imutáveis importarem tanto.

# O pipeline completo, juntando tudo

Reunindo todos os fios da coleção: um desenvolvedor faz commit (Vol XIV); o PR dispara o CI que roda testes (Vol XIV, Cap 19); ao mergear e criar uma tag de versão (Cap 16), o CD constrói a imagem multi-stage (Cap 7), enxuta e segura (Caps 17-18), escaneia CVEs (Cap 17), e a envia ao registry com a versão (Cap 9); o deploy puxa essa imagem específica e a implanta com rolling update; healthchecks (Cap 16) confirmam que está saudável antes de receber tráfego; logs vão para o agregador (Cap 19). Cada peça que os volumes construíram tem seu lugar nesse fluxo automatizado, do código-fonte ao container servindo requisições.

Capítulo 21

Orquestração além do Compose

O Compose (Caps 14–16) orquestra containers numa única máquina, e isso cobre desenvolvimento e deploys modestos. Mas quando uma aplicação precisa rodar em várias máquinas — para suportar mais tráfego do que um servidor aguenta, ou para sobreviver à falha de um servidor inteiro —, surge uma classe de problemas que o Compose não resolve: como distribuir containers por um cluster de máquinas, como balancear carga entre réplicas em nós diferentes, como recuperar automaticamente quando um nó morre, como atualizar sem downtime em escala. Essa é a tarefa dos orquestradores de containers, e o Kubernetes é o padrão dominante. Este capítulo é um capítulo de panorama e modelo mental — não um tutorial de Kubernetes (que mereceria um volume próprio), mas uma orientação: que problemas a orquestração resolve, os conceitos centrais do Kubernetes, e — importante — quando você não precisa dela. O objetivo é que você saiba o que existe além do Compose e quando é hora de cruzar essa fronteira.

# O que a orquestração resolve

Um orquestrador gerencia containers através de um cluster de máquinas, automatizando o que seria impossível de coordenar à mão em escala. Ele faz scheduling — decide em qual máquina cada container roda, conforme recursos disponíveis. Faz self-healing — se um container ou uma máquina inteira morre, ele recria os containers afetados em outro lugar. Faz scaling — sobe ou derruba réplicas conforme a demanda. Faz load balancing — distribui requisições entre as réplicas. E faz rolling updates em escala — atualiza a aplicação gradualmente, sem downtime, por todo o cluster. É a diferença entre "rodar containers" e "operar um sistema de containers resiliente e escalável".

Compose é um host; orquestrador é um cluster
A distinção fundamental, já antecipada no Cap 15. O Compose orquestra containers em uma máquina — ótimo para dev e servidores únicos, mas se aquela máquina cai, tudo cai, e ela só aguenta a carga que um servidor aguenta. Um orquestrador gerencia containers em muitas máquinas tratadas como um pool unificado de recursos. A falha de uma máquina é absorvida (os containers migram para outras); a carga é distribuída além do limite de um servidor. Você descreve o estado desejado ("quero 5 réplicas da api saudáveis") e o orquestrador trabalha continuamente para manter esse estado, recuperando de falhas sozinho. É a passagem de "um host gerenciado" para "um cluster auto-gerenciado".

# Kubernetes: o vocabulário essencial

O Kubernetes (frequentemente abreviado k8s) tem um vocabulário próprio que vale conhecer mesmo sem operá-lo. Um Pod é a menor unidade — um ou mais containers que rodam juntos (geralmente um). Um Deployment descreve o estado desejado de um conjunto de Pods (quantas réplicas, qual imagem) e mantém esse estado. Um Service dá um endereço estável e balanceamento a um grupo de Pods (a DNS interna do Cap 12, em escala de cluster). E o Ingress roteia tráfego externo para os Services (o papel do proxy do Cap 15). Esses quatro conceitos cobrem o essencial de como uma aplicação vive no Kubernetes.

deployment.yaml (Kubernetes, conceitual)
apiVersion: apps/v1
kind: Deployment              # "mantenha N Pods desta imagem rodando"
metadata:
  name: api
spec:
  replicas: 5                 # estado desejado: 5 réplicas saudáveis
  selector:
    matchLabels: { app: api }
  template:
    spec:
      containers:
        - name: api
          image: ghcr.io/org/app:1.4.2   # a mesma imagem do Cap 9
          # o k8s recria os Pods que falharem para manter os 5

# O estado desejado e a reconciliação

O conceito que define o Kubernetes é o estado desejado. Você não dá comandos imperativos ("crie este container"); você declara o estado que quer ("quero 5 réplicas da versão 1.4.2") e o orquestrador faz um loop de reconciliação contínuo: compara o estado atual com o desejado e age para aproximá-los. Caiu uma réplica? Ele sobe outra. Você mudou para 8 réplicas? Ele sobe 3. Atualizou a imagem? Ele substitui os Pods gradualmente. É a mesma filosofia declarativa do Compose (Cap 14) e do schema-as-code (Vol XI), levada a um sistema que ativamente mantém o estado, não só o estabelece uma vez.

terminal (kubectl, conceitual)
# Declarar o estado desejado (aplica o YAML ao cluster)
kubectl apply -f deployment.yaml

# Escalar = mudar o estado desejado; o k8s reconcilia
kubectl scale deployment/api --replicas=8

# Atualizar a imagem = rolling update automático
kubectl set image deployment/api api=ghcr.io/org/app:1.4.3

# Ver o estado atual sendo reconciliado
kubectl get pods

# O que o Docker preparou para a orquestração

Tudo o que este volume ensinou é pré-requisito para a orquestração, não desperdício. O Kubernetes roda imagens de container (OCI, Cap 3) — as mesmas que você constrói com Dockerfile (Caps 5–8). Ele usa healthchecks (Cap 16) para saber quais Pods estão prontos. Ele injeta configuração e segredos em runtime (Cap 13) via ConfigMaps e Secrets. Ele coleta logs de stdout (Cap 19). Ele monta volumes para dados persistentes (Cap 11). A orquestração não substitui o conhecimento de containers — ela o pressupõe e o opera em escala. Uma imagem bem construída, segura e observável é tão valiosa no Kubernetes quanto no Docker; aliás, mais.

Você provavelmente não precisa de Kubernetes (ainda)
O aviso mais importante do capítulo. O Kubernetes é poderoso e complexo — operá-lo exige conhecimento significativo e introduz muitas peças móveis. Para a maioria dos projetos, ele é excesso: uma aplicação que roda confortavelmente num ou dois servidores não precisa de um cluster, e adotar k8s cedo demais é trocar problemas que você tem por problemas mais difíceis que você não tem. Comece simples — Compose num servidor, ou plataformas gerenciadas (Cloud Run, Fly.io, Render, App Runner) que rodam seus containers sem você gerenciar um cluster. Migre para orquestração plena quando a escala real exigir — múltiplas máquinas, alta disponibilidade crítica, times grandes. A pergunta não é "Kubernetes é melhor?", mas "eu tenho o problema que ele resolve?". Como nos workflows do Git (Vol XIV, Cap 18), a ferramenta deve servir à necessidade, não ao prestígio.

Capítulo 22

Boas práticas e encerramento

Vinte e um capítulos construíram o Docker peça por peça — do que é um container ao cluster que orquestra milhares. Este último reúne os princípios numa síntese e fecha a Onda 4. O fio condutor do volume foi consistente: containers empacotam um ambiente reproduzível, e quase toda boa prática deriva de duas ideias — a imagem é imutável e mínima, o container é efêmero e descartável. Aqui consolidamos as regras que emergiram capítulo a capítulo: imagens enxutas e versionadas, segredos fora da imagem, dados em volumes, configuração em runtime, segurança por menor privilégio. É também o encerramento da Onda 4 — Ferramentas do ofício — e da jornada que o Git abriu: o código versionado no tempo, o ambiente empacotado no espaço, ambos a serviço de transformar software que funciona "na minha máquina" em software que se entrega com confiança em qualquer lugar. Fechamos olhando para trás, para o arco completo, e para frente, para o que vem.

# Os dois princípios que organizam tudo

Se o Vol XIV tinha "objetos imutáveis + refs móveis", o Docker tem um par análogo: a imagem é imutável e mínima; o container é efêmero e descartável. Quase toda decisão correta deriva de um desses. Por que segredos não vão na imagem? Porque a imagem é imutável e distribuível — o segredo ficaria gravado para sempre (Cap 13). Por que dados vão em volumes? Porque o container é efêmero — o que ele escreve morre com ele (Cap 11). Por que multi-stage? Porque a imagem deve ser mínima — só o que roda, não o que constrói (Cap 7). Quando uma prática parecer arbitrária, pergunte qual dos dois princípios ela serve.

A pergunta que resolve quase tudo
Diante de uma dúvida no Docker — onde guardar isto? por que aquilo vazou? como configurar aquele serviço? — volte aos dois princípios. Isto precisa sobreviver ao container? Se sim, vai num volume, fora dele (Cap 11). Isto é segredo ou configuração que muda por ambiente? Se sim, entra em runtime, não na imagem (Cap 13). Isto é necessário para rodar, ou só para construir? Se só para construir, fica num estágio anterior (Cap 7). A imutabilidade da imagem e a efemeridade do container, somadas ao modelo de camadas (Cap 2) e à rede isolada (Cap 12), explicam praticamente todo comportamento do Docker. Nenhum estado é misterioso — só ainda não examinado à luz desses princípios.

# Imagens: enxutas, versionadas, seguras

A qualidade de um sistema conteinerizado começa na qualidade das imagens, e três disciplinas a sustentam. Enxutas: multi-stage (Cap 7) e bases mínimas (Caps 8, 18) — menos tamanho, menos superfície de ataque, deploys mais rápidos. Versionadas: tags imutáveis e específicas (Caps 2, 9), nunca latest em produção — reprodutibilidade absoluta, ligada às tags Git (Vol XIV, Cap 16). Seguras: usuário não-root, scan de CVEs, segredos fora (Cap 17) — menor privilégio aplicado ao container. Uma imagem que segue as três é um artefato confiável; ignorar qualquer uma é dívida que se cobra em produção.

Dockerfile de referência (consolidado)
# Multi-stage (Cap 7): build completo, runtime mínimo
FROM node:22 AS builder
WORKDIR /app
COPY package*.json ./           # cache de deps primeiro (Cap 6)
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine             # base enxuta (Cap 8); distroless p/ mais (Cap 18)
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=builder /app/dist ./dist
USER node                       # não-root (Cap 17)
HEALTHCHECK CMD wget --spider -q http://localhost:3000/health || exit 1
CMD ["node", "dist/index.js"]   # exec form p/ sinais (Caps 5,10)

# Containers: efêmeros e sem estado, quando possível

O ideal de design é o container sem estado (stateless): ele não guarda nada que precise durar, então pode ser morto, recriado e replicado livremente. A app Hono da coleção é assim — escala horizontalmente subindo cópias idênticas (Cap 21). O estado que precisa durar é empurrado para fora: o banco e o cache, com seus volumes (Cap 11), são os serviços com estado, tratados com mais cuidado. Essa separação — lógica sem estado, dados isolados em serviços com estado — é o que torna um sistema escalável e resiliente. Quanto mais containers você puder tratar como descartáveis, mais fácil é operá-los.

# Checklist de produção

Antes de levar uma aplicação conteinerizada a produção, vale percorrer a checklist que o volume construiu — cada item remetendo a um capítulo. É a versão Docker da disciplina de produção do Vol XIII (Cap 22).

O checklist mínimo antes do deploy
Imagem multi-stage e enxuta (Caps 7-8). Tag imutável e versionada, ligada à tag Git (Cap 9; Vol XIV Cap 16). USER não-root e scan de CVEs sem críticos (Cap 17). Segredos injetados em runtime, nunca na imagem; .dockerignore excluindo .env (Caps 8, 13). Dados em volumes, com backup externo (Cap 11). Banco só na rede interna, nunca exposto (Cap 12). Healthcheck significativo e restart: unless-stopped (Caps 10, 16). Logs para stdout com rotação configurada (Cap 19). Shutdown gracioso tratando SIGTERM, exec form no CMD (Cap 10). Limites de memória/CPU (Cap 17). CI/CD construindo e publicando a imagem automaticamente (Cap 20). Cada "sim" é um vetor fechado.

# O arco completo: do código ao container em produção

Vale ver, uma última vez, como tudo se encaixa — não só este volume, mas a coleção inteira convergindo. O código nasce tipado (Vols I-II), na interface (Vols III-VII) ou no backend (Vols VIII-XIII); a autenticação o protege em runtime (Vol XIII). O Git o versiona no tempo, dá história e colaboração (Vol XIV). O Docker o empacota no espaço, com seu ambiente, num artefato imutável (este volume). O CI/CD (Cap 20) costura os dois: um commit vira uma imagem versionada que vira um container em produção, automaticamente. As duas fontes de "funciona na minha máquina" — código divergente e ambiente divergente — são eliminadas, uma por Git, outra por Docker. O resultado é software que se entrega com confiança.
