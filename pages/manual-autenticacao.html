Capítulo 1

Introdução: autenticação vs autorização

O Capítulo 22 do volume anterior fechou Zod com schemas em forma de autenticação — Sessao usando z.uuid() e z.iso.datetime(), TokenPayload com sub, exp e iat, papéis modelados como discriminated union. Aqueles tipos descreviam dados que existiam apenas no papel. Este volume constrói o sistema que de fato os produz e os valida em produção. Antes de qualquer linha sobre hashing, JWT ou OAuth, é preciso fixar a distinção que organiza todo o restante: autenticação e autorização são duas perguntas, e portanto dois sistemas.

# Duas perguntas, dois sistemas

Toda requisição que toca um recurso protegido passa por duas verificações em sequência. A primeira pergunta é quem está fazendo isto; a segunda é o que esta pessoa pode fazer. A primeira é autenticação (authN); a segunda, autorização (authZ). A ordem importa: não há como decidir o que alguém pode fazer sem antes saber quem é.

A confusão entre as duas vem do fato de que, em código, elas frequentemente moram em arquivos vizinhos — às vezes no mesmo middleware. Mas são problemas diferentes, resolvidos por mecanismos diferentes, com falhas diferentes. Tratar tudo como "auth" embaralhado é como confundir validação de cartão de crédito com avaliação de limite: ambos acontecem na compra, mas vêm de sistemas separados.

auth.ts
import { Hono } from 'hono'

const app = new Hono()

// Camada 1: AUTENTICAÇÃO — resolve quem é o request
app.use('*', async (c, next) => {
  const userId = await identifyUser(c)
  if (!userId) return c.json({ error: 'unauthenticated' }, 401)
  c.set('userId', userId)
  await next()
})

// Camada 2: AUTORIZAÇÃO — decide o que pode fazer
app.use('/admin/*', async (c, next) => {
  const isAdmin = await checkRole(c.get('userId'), 'admin')
  if (!isAdmin) return c.json({ error: 'forbidden' }, 403)
  await next()
})

O middleware '*' é horizontal: roda em toda requisição e tem uma única responsabilidade — resolver userId. O middleware '/admin/*' é vertical: roda em rotas específicas e decide se aquele userId pode prosseguir. Trocar a responsabilidade entre os dois — consultar papéis no primeiro, identificar usuário no segundo — é o caminho mais curto para um sistema confuso e inseguro.

# Identidade, credencial, sessão

Três conceitos são usados como sinônimos e não são. Identidade é o sujeito do sistema — uma linha em users, um UUID que deveria ser estável pela vida toda da conta. Credencial é a prova de que alguém é dono dessa identidade: uma senha, uma chave privada, um fator biométrico. Sessão (ou token) é um ticket temporário que o servidor emite depois de verificar a credencial, evitando que o usuário reautentique a cada requisição.

tipos.ts
// Identidade: o sujeito do sistema, idealmente imutável
type User = {
  id: string         // UUID, chave primária
  email: string      // identificador externo
  createdAt: Date
}

// Credencial: prova de posse — armazenada apenas como hash
type Credential = {
  userId: string
  passwordHash: string
  algorithm: 'argon2id' | 'bcrypt'
}

// Sessão: ticket temporário com expiração explícita
type Session = {
  id: string
  userId: string
  expiresAt: Date
  fresh: boolean     // criada nesta requisição?
}

Cada um tem ciclo de vida próprio. Identidades duram anos. Credenciais são trocadas eventualmente — reset de senha, rotação de chave, revogação de OTP. Sessões expiram em horas ou dias. Misturar os ciclos — guardar hash de senha junto da sessão, por exemplo — é um erro arquitetural comum que cria classes inteiras de bugs e brechas.

Convenção: authN e authZ
As abreviações authN (do inglês authentication) e authZ (de authorization) são padrão em literatura de segurança e nomeação de pacotes. Este volume usa "autenticação" e "autorização" no corpo do texto, mas as abreviações aparecem em comentários de código e referências cruzadas.

# O fluxo de uma requisição autenticada

Independente da tecnologia — cookie de sessão, JWT, OAuth — a forma do fluxo é a mesma. O cliente anexa uma prova de identidade ao request, geralmente um cookie ou um header Authorization. O servidor recebe essa prova, resolve qual usuário ela representa (lookup em store de sessão, ou verificação de assinatura do token), coloca o userId no contexto da requisição, e só então avalia autorização. Se ambas as camadas passam, o handler de negócio executa com a identidade já amarrada ao contexto.

A grande consequência prática: o handler de negócio nunca deveria precisar saber como o usuário foi identificado. Se a função que processa um pedido recebe userId via c.get('userId'), ela funciona idêntica para sessão de cookie, JWT em header e API key — porque tudo isso é responsabilidade do middleware de autenticação, não da regra de negócio. Trocar de mecanismo deveria ser uma reescrita de middleware, jamais uma reescrita de handlers.

# 401 e 403: a fronteira em HTTP

HTTP herdou nomes confusos. 401 Unauthorized deveria se chamar Unauthenticated — significa "não sei quem você é, ou a prova que apresentou é inválida". 403 Forbidden significa "sei quem você é, mas você não pode fazer isto". A diferença não é cosmética: o cliente reage de forma diferente a cada um.

status.ts
// 401 — sem identidade, ou identidade inválida
return c.json({ code: 'UNAUTHENTICATED' }, 401)

// 403 — identidade válida, mas sem permissão para esta ação
return c.json({ code: 'FORBIDDEN' }, 403)

// 404 — para recursos privados, prefira 404 a 403:
// não revela a existência do recurso a quem não pode vê-lo
return c.json({ code: 'NOT_FOUND' }, 404)

Em um SPA, 401 normalmente dispara redirect para login; 403 mostra uma mensagem de "acesso negado". Confundir os dois quebra essa lógica de cliente e, pior, contamina logs de auditoria — a métrica "tentativas de acesso negado" passa a contar usuários deslogados misturados com usuários sem permissão, e o sinal vira ruído.

404 acima de 403 para recursos privados
Retornar 403 em um recurso que pertence a outro usuário vaza a existência do recurso. Para um atacante, "este pedido existe mas não é seu" já é metade do trabalho de enumeração. Em rotas com modelo de propriedade — pedidos, mensagens, documentos privados — prefira 404: devolva o mesmo "não encontrado" tanto para IDs inexistentes quanto para IDs de outros donos.

# Onde a autorização realmente mora

Autenticação tende a ser horizontal: um único middleware no topo da aplicação que resolve userId uma vez. Autorização é vertical e poliforma — pode viver em middleware (papéis fixos por rota), em decorator (permissões granulares por endpoint) ou direto na query (modelo de propriedade, onde "você pode" é definido por "você é dono").

pedidos.ts
import { eq, and } from 'drizzle-orm'
import { orders } from './schema'

// AuthN já garantiu sessão válida; userId está no contexto.
// AuthZ vive na cláusula WHERE: filtramos pelo dono.
const [order] = await db
  .select()
  .from(orders)
  .where(
    and(
      eq(orders.id, orderId),
      eq(orders.userId, c.get('userId'))
    )
  )
  .limit(1)

if (!order) {
  // Não existe OU não é seu — a resposta é a mesma.
  return c.json({ code: 'NOT_FOUND' }, 404)
}

A query acima é autorização por propriedade implementada na cláusula WHERE. Em vez de buscar o pedido, conferir o userId em código e possivelmente vazar timing ou existência, a checagem é parte da consulta. Uma query, um round-trip, um resultado: ou aparece (você é dono) ou não aparece (não é seu, ou não existe — e o cliente não consegue distinguir).

Propriedade na cláusula WHERE
Sempre que a regra de autorização for "o usuário só pode ver ou editar o que é dele", filtre por userId direto na query em vez de SELECT seguido de verificação em código. Reduz round-trips, elimina vazamento por timing e transforma controle de acesso numa propriedade da camada de dados — onde é mais difícil de esquecer.

# Quatro armadilhas comuns

A primeira é confundir formato com mecanismo. "Tenho JWT, logo estou autenticado" é falso na mesma medida que "tenho um envelope, logo recebi uma carta". JWT é um formato de payload assinado; autenticação é o processo de verificar a assinatura e validar as claims. O Capítulo 9 volta a este ponto com detalhe.

A segunda é fazer autorização apenas no cliente. Esconder um botão de "deletar" para usuários comuns é UX; impedir a operação é responsabilidade exclusiva do servidor.

antipadrao.tsx
// ❌ Apenas no front — o botão some, mas a rota fica exposta
{user.role === 'admin' && <DeleteButton orderId={order.id} />}

// curl -X DELETE -H "Cookie: session=..." /api/orders/123
// continua funcionando se o backend não verificar.

// ✅ Front esconde, backend bloqueia:
app.delete('/orders/:id', requireRole('admin'), async (c) => {
  // só executa quando o middleware libera
})

A terceira é não expirar sessões. Sem TTL explícito, um cookie ou token roubado vira acesso vitalício — e nenhuma rotação de senha do usuário consegue revogá-lo, porque a sessão deixou de estar ligada à credencial atual. Toda sessão precisa de expiresAt, e toda operação sensível — mudança de senha, troca de e-mail, exclusão de conta — deveria invalidar todas as sessões existentes do usuário.

A quarta é tratar "logado como admin" como booleano global. Privilégios elevados deveriam ser contextuais: um usuário admin acessando o painel de administração é uma situação; o mesmo usuário acessando sua própria conta é outra. O Capítulo 16 (RBAC) e o Capítulo 18 (permissões granulares) tratam disso em profundidade.

Capítulo 2

Hashing de senhas

Senhas são o ponto onde identidade e credencial se encontram, e o servidor precisa verificar uma sem nunca armazenar a outra. A ferramenta é hashing — não criptografia, não codificação. Mas não qualquer hash: precisa ter sal, custo computacional propositadamente alto e parâmetros que envelhecem com graça. Este capítulo cobre os porquês antes das chamadas de função.

# Hash não é criptografia

Criptografia é reversível com uma chave; hash, idealmente, não é reversível por nada. O servidor não precisa saber a senha de ninguém — precisa apenas confirmar que a senha apresentada no login produz o mesmo valor derivado armazenado no cadastro. Encriptar a senha em vez de fazer hash parece equivalente, mas tem um defeito fatal: a chave de descriptografia precisa morar em algum lugar, e quem rouba o banco normalmente rouba a chave junto.

Hash criptográfico genérico (MD5, SHA-1, SHA-256, Blake2) tampouco resolve o problema. Esses algoritmos foram projetados para serem rápidos — quanto mais rápido o hash, melhor o checksum. Senha exige o oposto: queremos que cada verificação leve recursos significativos, o suficiente para tornar inviável testar bilhões de candidatos.

antipadrao.ts
import { createHash } from 'node:crypto'

// ❌ Hash criptográfico genérico não serve para senhas
function badHash(password: string): string {
  return createHash('sha256').update(password).digest('hex')
}

// SHA-256 em GPU moderna: ~10 bilhões de hashes por segundo.
// Vazamento de banco com SHA-256 puro vira lista de senhas em horas.
SHA-256 puro não é hash de senha
Hashes criptográficos genéricos foram projetados para serem rápidos. Em uma RTX 4090, SHA-256 ultrapassa 10 GH/s (dez bilhões de hashes por segundo). Mesmo com sal, um banco vazado com SHA-256 puro vira lista de senhas em claro em horas. Nunca use MD5, SHA-1, SHA-256, SHA-3 ou Blake2 puros para senhas — apenas para checksums, integridade e fingerprinting.

# Sal: cada senha com sua própria pimenta

Sal é uma sequência de bytes aleatórios concatenada à senha antes do hash. Sem sal, duas pessoas que escolhem a mesma senha (e há mais coincidências do que se imagina — "123456", "qwerty", "senha123") produzem o mesmo hash, o que permite ataques em massa via tabelas rainbow pré-computadas. Com sal único por usuário, cada senha vira um problema individual: o atacante precisa quebrar cada uma separadamente.

Três regras práticas: o sal precisa ser único por usuário, criptograficamente aleatório (não sequencial, não derivado do email), e armazenado junto com o hash — não em outro lugar, não escondido. O sal não é secreto; sua função é tornar cada hash único, não esconder informação. Bibliotecas modernas como argon2 e bcrypt geram o sal automaticamente e o embutem no hash final.

# Custo computacional é a defesa real

O modelo de ameaça realista hoje não é "atacante adivinha sua senha" — é "atacante rouba o banco e roda força bruta offline com hardware especializado". Contra isso, o que protege é o custo: queremos que verificar uma senha leve algo entre 100 e 500 ms num servidor de produção, o que faz o atacante levar séculos para testar bilhões de candidatos. A lentidão deixa de ser bug e vira feature de segurança.

O custo aparece de duas formas. Funções CPU-hard como PBKDF2 e bcrypt forçam o atacante a gastar ciclos de processador; podem ser aceleradas com FPGA e ASIC, mas com investimento alto. Funções memory-hard como scrypt e argon2id forçam o atacante a gastar também memória RAM — e RAM em paralelo é caro mesmo em hardware especializado. Memory-hard é hoje o padrão recomendado.

# Argon2id e bcrypt em 2026

Argon2id venceu a Password Hashing Competition em 2015 e foi formalizado pela RFC 9106 em 2021. É a recomendação padrão atual: memory-hard, com três parâmetros independentes (memória, iterações, paralelismo) que permitem ajustar o custo conforme a infraestrutura. A variante id combina resistência a ataques de canal lateral (do argon2i) com resistência a trade-off tempo/memória (do argon2d).

argon2.ts
import argon2 from 'argon2'

// Cadastro: parâmetros mínimos sugeridos pela RFC 9106
const passwordHash = await argon2.hash(password, {
  type: argon2.argon2id,
  memoryCost: 19456,    // 19 MiB
  timeCost: 2,           // 2 iterações
  parallelism: 1,
})

// Formato armazenado, autocontido com algoritmo, params e sal:
// $argon2id$v=19$m=19456,t=2,p=1$<sal>$<hash>

// Login: a string acima carrega todos os parâmetros necessários
const valid = await argon2.verify(passwordHash, password)

bcrypt é mais antigo (1999), mais simples e ainda perfeitamente aceitável em código existente. Tem um único parâmetro de custo (cost), onde o número de rounds é 2^cost. O mínimo recomendado em 2026 é cost = 12; em servidores modernos isso fica em torno de 250 ms por hash. O limite de bcrypt é que ele é CPU-hard mas não memory-hard, então hardware especializado consegue paralelizar mais agressivamente que com argon2id.

bcrypt.ts
import bcrypt from 'bcrypt'

const cost = 12  // 2^12 = 4096 rounds; ~250 ms em servidor moderno
const passwordHash = await bcrypt.hash(password, cost)

// Formato armazenado: $2b$12$<sal><hash> (60 caracteres total)

const valid = await bcrypt.compare(password, passwordHash)

// Atenção: bcrypt trunca silenciosamente senhas com mais de 72 bytes.
// Para senhas muito longas, pré-aplicar SHA-256 e codificar em Base64.
Default 2026: argon2id
Para sistemas novos, comece com argon2id e os parâmetros da RFC 9106 (m=19456, t=2, p=1). Em Node 22 LTS, as opções maduras são argon2 v0.44.0 (binding C nativo, compila via node-gyp) e @node-rs/argon2 v2.0.2 (binding Rust com binários prébuildados, sem etapa de compilação). Para bcrypt, as bibliotecas correntes são bcrypt v6.0.0 (nativa) e bcryptjs v3.0.3 (JS puro, compatível com Cloudflare Workers e outros runtimes edge).

# Comparação em tempo constante

Tanto argon2.verify() quanto bcrypt.compare() já fazem comparação em tempo constante internamente. Mas qualquer comparação manual de segredos — tokens de API, códigos de OTP, MACs — precisa do mesmo cuidado. A razão é sutil: comparação byte a byte com early return termina mais rápido quando os primeiros bytes diferem do que quando coincidem. Essa diferença de tempo, medida em microssegundos sobre milhares de tentativas, permite ao atacante reconstruir o segredo um byte por vez. É um ataque por canal lateral, e funciona em redes reais.

compare.ts
import { timingSafeEqual } from 'node:crypto'

// Compara dois segredos em tempo independente do conteúdo
function safeCompare(a: string, b: string): boolean {
  const bufA = Buffer.from(a)
  const bufB = Buffer.from(b)
  // timingSafeEqual exige buffers do mesmo tamanho — checar antes
  if (bufA.length !== bufB.length) return false
  return timingSafeEqual(bufA, bufB)
}

// Use em: tokens de API, códigos OTP, comparação de HMAC, CSRF tokens
// Não precisa para senhas — argon2.verify() e bcrypt.compare() já fazem.

# Pepper: segredo do servidor

Pepper é uma chave secreta global do servidor, concatenada à senha antes do hash. A ideia é elegante: se o banco vaza mas o servidor não, o atacante não consegue rodar ataque offline porque falta o pepper. Em teoria, defesa em profundidade gratuita. Na prática, o ganho marginal hoje é pequeno e o custo operacional alto.

O problema é gestão. Pepper guardado em variável de ambiente do mesmo servidor que tem o banco não protege contra praticamente nada — quem rouba o banco normalmente rouba o ambiente. Pepper em HSM ou KMS protege de verdade, mas adiciona dependência crítica: perda do pepper invalida todas as senhas; rotação exige re-hash de todos os usuários no próximo login. Com argon2id e parâmetros adequados, o custo do ataque offline já é alto o suficiente sem pepper para justificar pular essa complexidade na maioria dos sistemas.

Pepper: utilidade decrescente
Em sistemas com bcrypt e cost baixo, pepper agregava muito. Com argon2id nos parâmetros da RFC 9106, o ganho marginal é menor. Se for usar, armazene o pepper em HSM ou KMS separado do banco — pepper em .env ao lado da string de conexão do Postgres é teatro de segurança. E lembre que rotacionar pepper exige re-hash em massa.

# Rehash e migração de parâmetros

Parâmetros que pareciam fortes em 2020 ficam fracos em 2026, e isso vai continuar acontecendo. A estratégia padrão é embutir a migração no fluxo de login: depois de verificar a senha com sucesso, conferir se o hash armazenado usa parâmetros desatualizados e, se sim, re-hashear com os parâmetros atuais antes de retornar. O usuário não percebe nada — paga apenas um hash adicional num login bem-sucedido — e a base migra organicamente.

login.ts
import argon2 from 'argon2'
import { eq } from 'drizzle-orm'
import { users } from './schema'

const currentParams = {
  type: argon2.argon2id,
  memoryCost: 19456,
  timeCost: 2,
  parallelism: 1,
}

async function login(email: string, password: string) {
  const user = await db.query.users.findFirst({
    where: eq(users.email, email),
  })
  if (!user) return null

  const valid = await argon2.verify(user.passwordHash, password)
  if (!valid) return null

  // Hash com parâmetros antigos? Re-hashea de forma transparente.
  if (argon2.needsRehash(user.passwordHash, currentParams)) {
    const newHash = await argon2.hash(password, currentParams)
    await db.update(users)
      .set({ passwordHash: newHash })
      .where(eq(users.id, user.id))
  }

  return user
}

Migração entre algoritmos (bcrypt → argon2id, por exemplo) segue a mesma lógica, com uma coluna extra no schema (password_algo) ou um discriminador no próprio hash. No login, identifica o algoritmo do hash armazenado, valida com a biblioteca correspondente, e — se válido e for legado — gera um hash novo no algoritmo atual. Algumas equipes preferem aplicar argon2id por cima do bcrypt antigo (camada dupla) para evitar o pulo discreto e migrar a base inteira de uma vez; é mais trabalhoso, mas elimina o estado intermediário.

Capítulo 3

Sessões vs Tokens

A decisão entre sessão e token define a arquitetura de identidade da aplicação inteira. Não é escolha cosmética entre bibliotecas; muda onde vive a verdade sobre quem está logado, quanto custa cada requisição em I/O, e quanto tempo leva para revogar acesso quando algo dá errado. Os próximos oito capítulos detalham cada uma das duas abordagens — este fixa o modelo mental que torna a comparação possível.

# Duas filosofias de identidade

Há duas formas de o servidor lembrar que você está logado. A primeira: ele anota num caderno próprio — "a chave 7a3b pertence à Maria, expira amanhã" — e te entrega uma etiqueta com o número 7a3b. Toda vez que você volta, o servidor consulta o caderno. Essa é a sessão.

A segunda: ele te entrega uma carta selada que diz "portadora é a Maria, válida até amanhã" e assinada com um carimbo que só ele consegue produzir. Toda vez que você volta, o servidor confere o carimbo — não precisa de caderno nenhum, porque a informação está na carta. Esse é o token.

Cada abordagem desloca a verdade para um lugar diferente. Sessão centraliza: a verdade vive no servidor; o cliente carrega apenas um ponteiro. Token distribui: a verdade viaja no payload; qualquer servidor com a chave correta consegue lê-la. Tudo o que segue — performance, revogabilidade, escala — é consequência dessa diferença inicial.

# Sessões: identificador opaco com lookup

Numa sessão, o cookie carrega um identificador aleatório — geralmente um UUID ou 32 bytes de entropia codificados em base64url. O ID por si só não significa nada. Toda a informação útil (qual usuário, quando criada, quando expira, papéis, dados de "lembre-se de mim") vive num session store do lado do servidor: Redis, Postgres, ou uma tabela dedicada no banco principal.

sessao.ts
import { randomUUID } from 'node:crypto'

// No login: cria a sessão no store; o cookie carrega só o ID
const sessionId = randomUUID()
await sessionStore.set(sessionId, {
  userId: user.id,
  expiresAt: new Date(Date.now() + 7 * 24 * 3600 * 1000),
})
c.header('Set-Cookie', `sid=${sessionId}; HttpOnly; Secure; SameSite=Lax`)

// Em cada request: lookup obrigatório
const session = await sessionStore.get(sessionId)
if (!session || session.expiresAt < new Date()) {
  return c.json({ code: 'UNAUTHENTICATED' }, 401)
}
c.set('userId', session.userId)

A característica definidora é o lookup. Sem consulta ao store, o servidor não sabe nada — o ID poderia ser inventado pelo cliente e ele não notaria. Isso parece custoso, mas tem uma contrapartida poderosa: o estado da sessão pode mudar a qualquer momento sem o cliente saber. Marcar como revogada, prolongar a expiração, adicionar um flag de "exige reautenticação para ações sensíveis" — tudo isso é uma operação no servidor que se aplica instantaneamente ao próximo request.

# Tokens: declaração assinada e autocontida

Um token (no padrão JWT, formalizado pela RFC 7519) é o oposto: o cliente carrega o payload inteiro, e o servidor não armazena nada sobre ele. A confiabilidade vem de uma assinatura criptográfica — HMAC com segredo compartilhado, ou assinatura assimétrica RSA/ECDSA — que impede o cliente de alterar o conteúdo sem invalidar a assinatura.

token.ts
import { SignJWT, jwtVerify } from 'jose'

// No login: assina o payload, devolve a string ao cliente
const token = await new SignJWT({
  sub: user.id,
  role: user.role,
})
  .setProtectedHeader({ alg: 'HS256' })
  .setExpirationTime('15m')
  .sign(secret)

// Em cada request: verifica a assinatura, sem tocar banco
const { payload } = await jwtVerify(token, secret)
c.set('userId', payload.sub)

Note a diferença operacional: jwtVerify não faz I/O. Toda a checagem — assinatura, expiração, audiência — acontece em memória usando o segredo (ou a chave pública) carregado uma vez. Para uma função em Cloudflare Workers ou um sidecar de microsserviço, isso significa zero dependência de um banco compartilhado: cada réplica verifica autonomamente. Para uma API monolítica com Postgres, significa economizar uma query — pode ser irrelevante, ou pode importar muito sob carga.

"Session token" é termo ambíguo
No vocabulário do dia a dia, "token" é usado tanto para o ID opaco da sessão quanto para o JWT autocontido. Quando alguém escreve "JWT session token", normalmente quer dizer JWT mesmo. Quando escreve "session cookie", normalmente é sessão clássica. Quando escreve só "token", desconfie e pergunte. A confusão de vocabulário esconde decisões arquiteturais completamente diferentes.

# Revogabilidade: o trade-off central

Se houvesse uma única razão para escolher sessão sobre token, seria revogação. Numa sessão, deletar a entrada do store invalida imediatamente todas as requisições subsequentes — o próximo lookup vai falhar e o usuário cai. Em um token assinado, a assinatura continua matematicamente válida até o exp; o servidor não tem como rejeitar um token cuja matemática está correta, a menos que consulte uma lista externa de revogados.

revogacao.ts
// Sessão: revogação é uma operação local, instantânea
await sessionStore.delete(sessionId)
// Próximo request com este sessionId falha no lookup → 401

// Token: a assinatura segue válida até exp.
// Para revogar antes, é preciso uma denylist consultada a cada verify:
await denylist.add(payload.jti, payload.exp)

// E o middleware de auth passa a precisar consultá-la:
const { payload } = await jwtVerify(token, secret)
if (await denylist.has(payload.jti)) {
  return c.json({ code: 'TOKEN_REVOKED' }, 401)
}

A denylist resolve revogação em tokens, mas destrói a propriedade que justificava usar token em primeiro lugar: a verificação deixa de ser stateless. Agora cada request faz a consulta criptográfica e um lookup à denylist. Em termos de I/O, equivale à sessão; em termos de complexidade, é pior. Por isso a denylist costuma ser reservada para casos críticos (comprometimento confirmado), enquanto operações comuns (logout, troca de senha) aceitam a janela de exposição até o token expirar naturalmente.

# Performance, escala e o custo do estado

Sessão paga um lookup por requisição autenticada. Em Redis local, isso é da ordem de 0.5–1 ms; em Postgres com índice quente, 1–5 ms; em store remoto entre regiões, pode chegar a dezenas. Token paga uma verificação criptográfica — HMAC-SHA256 sobre alguns kilobytes leva microssegundos, totalmente em CPU. Para uma API monolítica próxima do banco, o lookup é praticamente grátis. Para edge functions distribuídas globalmente, o lookup vira a parte mais lenta da requisição.

A escala muda o cálculo. Microsserviços que precisam autenticar entre si naturalmente preferem token: cada serviço verifica com a chave pública, sem precisar de um auth service no caminho crítico. Aplicações monolíticas com poucos clientes raramente sentem o custo do lookup, e ganham a revogabilidade de graça. A "regra" comum — "use JWT" — está enviesada por casos de uso de microsserviços e edge, e nem sempre se aplica.

# O modelo híbrido: access curto + refresh longo

A resposta da indústria para o trade-off é combinar os dois. Um access token curto (5–15 minutos) e autocontido viaja em todas as requisições da API; ele é verificado sem I/O. Um refresh token longo (dias ou semanas) é opaco e armazenado num server store; ele só aparece numa rota dedicada de renovação. O cliente usa o access token até ele expirar, então troca o refresh por um novo access — esse refresh é o ponto onde a revogabilidade entra.

hibrido.ts
// No login: emite os dois
const accessToken = await new SignJWT({ sub: user.id, role: user.role })
  .setProtectedHeader({ alg: 'HS256' })
  .setExpirationTime('15m')
  .sign(secret)

const refreshId = randomUUID()
await db.insert(refreshTokens).values({
  id: refreshId,
  userId: user.id,
  expiresAt: new Date(Date.now() + 30 * 24 * 3600 * 1000),
})

// access vai no body; refresh vai em cookie HttpOnly Secure SameSite=Strict
c.header('Set-Cookie', `rt=${refreshId}; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh`)

// Em /auth/refresh: troca refresh por novo access
const stored = await db.query.refreshTokens.findFirst({
  where: eq(refreshTokens.id, refreshId),
})
if (!stored || stored.expiresAt < new Date()) {
  return c.json({ code: 'REFRESH_INVALID' }, 401)
}
// emite novo access; opcionalmente rotaciona o refresh (Cap 10)

O padrão equilibra os trade-offs: a verificação de cada request continua stateless (rápida, edge-friendly); a revogação acontece deletando o refresh token do store, com janela de exposição limitada ao TTL do access. Um logout faz DELETE FROM refresh_tokens WHERE id = ?, e em no máximo quinze minutos todas as sessões do usuário caem sem precisar de denylist. O Capítulo 10 entra nos detalhes de rotação, reuso e detecção de comprometimento.

Refresh token nunca em localStorage
Refresh token em localStorage ou sessionStorage é leitura trivial para qualquer XSS bem-sucedido — um único <script> injetado em qualquer parte da SPA exfiltra a credencial de longa duração e o atacante ganha acesso pelo período inteiro do refresh. Armazene refresh tokens em cookies HttpOnly Secure SameSite=Strict, com Path restrito à rota de refresh. Access tokens curtos podem viver em memória da SPA; o risco de XSS lá é limitado ao TTL.

# Como escolher na prática

Não há resposta universal, mas há sinais claros. Aplicações monolíticas com banco próximo e necessidade alta de revogabilidade (banco, saúde, painéis administrativos) ganham pouco com tokens e perdem garantias importantes; sessão pura tende a ser a escolha mais defensável. APIs públicas, microsserviços com auth descentralizada, deployments edge e aplicações móveis offline-tolerantes empurram para tokens — e quase sempre para o híbrido, porque revogação total via TTL é caro demais sem o refresh.

comparacao.ts
// Modelo mental: três formas, mesmas dimensões
type SessionAuth = {

type HybridAuth = TokenAuth & {

Existe uma escolha errada comum: JWT puro (sem refresh) em SPA com sessão "longa" — TTL de dias para evitar atrito de UX. Esse padrão herda o pior de cada mundo: perde revogabilidade (token longo é irrevogável na prática) e não ganha o stateless real (a aplicação acaba mantendo denylist por causa de logouts). Se a vida do access vai passar de uma hora, vale a pena introduzir refresh; abaixo disso, o trade-off de complexidade pode não compensar.

TTL do access define o pior caso
No modelo híbrido, o intervalo entre revogar o refresh token e o usuário efetivamente perder acesso é exatamente o TTL do access em vigor. Para a maioria dos sistemas, 15 minutos é o número consensual — equilibra atrito de refresh com janela de exposição aceitável. Sistemas mais sensíveis (banco, admin de produção) costumam descer para 5 minutos. Sistemas com renovação invisível e custo baixo de chamar refresh podem chegar a 1 minuto.

Capítulo 4

Cookies de sessão

O Capítulo 3 mostrou que uma sessão é um ID opaco armazenado no servidor. Esse ID precisa de um veículo confiável de ida e volta entre cliente e servidor — esse veículo é o cookie. O header Set-Cookie carrega uma série de diretivas que controlam quem pode ler o cookie, quando é transmitido, para quais domínios e caminhos, e por quanto tempo. Ignorar ou configurar mal qualquer uma delas abre vetores que o Capítulo 7 (CSRF) vai explorar em detalhe.

# Anatomia de um Set-Cookie

Um cookie chega ao cliente como o valor de um header Set-Cookie na resposta HTTP. O formato é nome=valor seguido de ponto-e-vírgula e zero ou mais diretivas. O navegador armazena o par nome/valor e o reenvia automaticamente em cada requisição subsequente que satisfaça o escopo definido pelas diretivas — domínio, caminho, protocolo e contexto de origem.

set-cookie.ts
// Header completo de um cookie de sessão seguro
// Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800

// Construído manualmente — útil para entender cada parte
c.header(
  'Set-Cookie',
  `sid=${sessionId}; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800`
)

// Ou via helper do Hono (preferido — escapa o valor, trata edge cases)
import { setCookie } from 'hono/cookie'

setCookie(c, 'sid', sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: 'Lax',
  path: '/',
  maxAge: 60 * 60 * 24 * 7,  // 7 dias em segundos
})

O valor do cookie — o sessionId — é a parte que transita e precisa ser opaca, imprevisível e suficientemente longa para resistir a força bruta. As diretivas ao redor dele determinam o nível de proteção que o navegador vai aplicar.

# HttpOnly e Secure: os dois obrigatórios

HttpOnly impede que JavaScript acesse o cookie via document.cookie. Um script injetado via XSS não consegue ler o session ID nem exfiltrá-lo — o navegador transmite o cookie apenas em requisições HTTP, nunca o expõe para scripts. Para cookies de sessão, HttpOnly não é opcional; é a linha de defesa que separa XSS de comprometimento de sessão.

Secure instrui o navegador a transmitir o cookie apenas em conexões HTTPS. Sem essa diretiva, o cookie trafega em texto puro sobre HTTP, e qualquer observador na rede consegue copiá-lo. Em desenvolvimento local (localhost), a maioria dos browsers relaxa essa exigência, mas em produção Secure é tão obrigatório quanto HttpOnly.

# SameSite: o espectro de proteção CSRF

SameSite controla se o navegador envia o cookie em requisições iniciadas por sites de terceiros. O modelo de ameaça é CSRF: uma página maliciosa em evil.com faz uma requisição para seuapp.com e o navegador, por padrão, envia todos os cookies de seuapp.com junto — incluindo a sessão autenticada. Os três valores operam em espectros diferentes:

samesite.ts
// Strict: cookie não vai em nenhum request cross-site.
// Máxima proteção CSRF; pode quebrar fluxos via link externo
// (ex: email com link direto para dashboard autenticado).
setCookie(c, 'sid', sessionId, { sameSite: 'Strict' /* ... */ })

// Lax: cookie vai em navegações top-level (link, redirect GET),
// mas não em fetches, POSTs ou subrecursos cross-site iniciados por scripts.
// Default implícito desde 2020 — proteção adequada para a maioria dos casos.
setCookie(c, 'sid', sessionId, { sameSite: 'Lax' /* ... */ })

// None: cookie vai em todos os requests cross-site.
// Necessário para embeds, widgets OAuth em popup, autenticação em iframe.
// Secure=true é obrigatório — sem ele, browsers modernos ignoram o cookie.
setCookie(c, 'sid', sessionId, { sameSite: 'None', secure: true /* ... */ })

Para a maioria das aplicações web, SameSite=Lax é o mínimo aceitável — cobre os vetores CSRF mais comuns sem quebrar fluxos legítimos de link externo. Strict é preferível quando a sessão não precisa sobreviver a um clique vindo de e-mail ou de outro site. O Capítulo 7 detalha por que SameSite é uma camada de defesa, não proteção completa contra CSRF.

SameSite=None exige Secure
Browsers modernos (Chrome 80+, Firefox, Safari) ignoram cookies com SameSite=None se Secure não estiver presente. O comportamento varia por versão — alguns tratam como Lax, outros descartam silenciosamente. Em produção, SameSite=None sem Secure resulta em cookies que somem, com erros difíceis de diagnosticar. Se precisar de None, Secure é parte do contrato.

# Domain e Path: escopo de transmissão

Path restringe para quais caminhos o navegador envia o cookie. Path=/ cobre toda a aplicação; Path=/api restringe apenas às rotas sob /api. Para cookies de sessão de uso geral, Path=/ é o valor correto. Cookies mais específicos — como um refresh token que só deve ser enviado para /auth/refresh — se beneficiam de um Path restrito: o cookie não viaja em todas as requisições, reduzindo a superfície de exposição.

Domain controla em quais domínios o cookie é transmitido. Quando omitido, o cookie pertence exatamente ao host que o criou — sem subdomínios. Quando definido explicitamente como Domain=exemplo.com, o cookie também vai para todos os subdomínios (app.exemplo.com, api.exemplo.com). Para cookies de sessão, omitir o atributo Domain é mais seguro: impede que um subdomínio comprometido ou controlado por terceiros colete cookies da raiz.

# Expiração: Max-Age, Expires e cookie de sessão

Sem Max-Age ou Expires, o cookie é um session cookie do navegador: persiste até o browser ser fechado (não a aba — a janela ou processo inteiro). Isso não se traduz em expiração no servidor: o session store pode ter o registro em aberto por semanas, e o servidor não recebe nenhuma notificação quando o navegador descarta o cookie. A implicação prática é que expiração real precisa ser controlada pelo expiresAt no server store, não pelo comportamento do navegador.

expiracao.ts
// Max-Age (preferido): duração em segundos a partir de agora
setCookie(c, 'sid', sessionId, {
  maxAge: 604800,   // 7 dias = 7 × 24 × 3600
  // ...demais atributos
})

// Expires (legado): data absoluta UTC — depende do relógio do cliente
setCookie(c, 'sid', sessionId, {
  expires: new Date(Date.now() + 604800 * 1000),
})

// Sem Max-Age nem Expires: cookie some quando o browser fecha.
// A sessão no store pode continuar aberta — server store tem o TTL real.

// Logout: deleta o cookie E o registro do store
import { deleteCookie } from 'hono/cookie'
deleteCookie(c, 'sid', { path: '/' })
await sessionStore.delete(sessionId)

Prefira Max-Age sobre Expires: Max-Age é relativo ao momento do request, portanto independente do relógio do cliente; Expires é uma data absoluta e fica errado quando o relógio do cliente está desincronizado. Quando ambos estão presentes, Max-Age tem precedência nos browsers modernos.

# Prefixos __Host- e __Secure-

Prefixos de cookie são uma convenção da especificação RFC 6265bis que os browsers impõem na borda: se o nome do cookie começa com __Host- ou __Secure-, o browser rejeita o cookie se os atributos não satisfizerem as restrições correspondentes.

prefixos.ts
// __Secure-: exige Secure=true
// Browser rejeita silenciosamente se Secure estiver ausente.
setCookie(c, '__Secure-sid', sessionId, {
  secure: true,
  httpOnly: true,
  sameSite: 'Lax',
  path: '/',
})

// __Host-: a configuração mais restritiva — exige tudo:
//   Secure=true, Path=/ e Domain OMITIDO.
// Impede subdomínios de setarem ou sobreescreverem o cookie.
setCookie(c, '__Host-sid', sessionId, {
  secure: true,
  httpOnly: true,
  sameSite: 'Lax',
  path: '/',
  // domain: intencionalmente omitido — __Host- exige isso
})

__Host- é a restrição máxima: o cookie só pode ser setado pelo host exato (sem subdomínios), apenas por HTTPS, e vale para todo o site (Path=/). Um subdomínio comprometido ou um script injetado em cdn.exemplo.com não consegue criar ou sobrescrever o cookie. Para cookies de sessão em produção, __Host- é a configuração mais defensável quando não há necessidade de compartilhar o cookie entre subdomínios.

__Host- como barra máxima
Para cookies de sessão em aplicações que rodam em subdomínio dedicado (app.exemplo.com) ou no domínio raiz sem necessidade de compartilhar cookies, __Host- é a configuração mais segura disponível. Ela elimina toda uma categoria de ataques de subdomínio sem custo operacional. Lembre que o nome completo é o cookie — ao ler, use getCookie(c, '__Host-sid').

# Lendo e validando cookies em Hono

O helper getCookie do Hono lê um cookie específico da requisição por nome. Para validar estrutura e tipo antes de usar, a abordagem natural é safeParse com Zod — o mesmo padrão do zValidator('cookie', ...) do Volume XII. A diferença é que zValidator trabalha no nível do handler e retorna 400 automaticamente; no middleware de autenticação global, você quer controle manual para devolver 401.

auth-middleware.ts
import { getCookie } from 'hono/cookie'
import { z } from 'zod'

const SessionCookie = z.object({
  __Host-sid: z.string().uuid(),
})

app.use('*', async (c, next) => {
  const raw = { '__Host-sid': getCookie(c, '__Host-sid') }
  const parsed = SessionCookie.safeParse(raw)

  if (!parsed.success) {
    return c.json({ code: 'UNAUTHENTICATED' }, 401)
  }

  const sessionId = parsed.data['__Host-sid']
  const session = await sessionStore.get(sessionId)

  if (!session || session.expiresAt < new Date()) {
    return c.json({ code: 'UNAUTHENTICATED' }, 401)
  }

  c.set('userId', session.userId)
  await next()
})

Em rotas onde o cookie é parâmetro de entrada de negócio (não de autenticação), zValidator('cookie', schema) funciona diretamente no handler — o resultado fica em c.req.valid('cookie') já tipado. A distinção entre os dois contextos é a mesma do Capítulo 1: middleware horizontal resolve identidade; handler vertical usa o dado validado.

Os capítulos anteriores mostraram que sessão é um ID opaco armazenado no servidor (Cap 3) e que esse ID viaja em cookie HttpOnly (Cap 4). # Ciclo de vida de uma sessão

Uma sessão passa por quatro estados ao longo do tempo. É criada no login bem-sucedido — o servidor gera um ID aleatório, persiste o par (id, userId, expiresAt) e devolve o ID via cookie. É validada em cada requisição subsequente — o servidor lê o ID do cookie, consulta o store, confere a expiração e injeta userId no contexto. É renovada quando a aplicação usa sliding expiration — o TTL é prorrogado conforme o usuário age. E é invalidada explicitamente no logout, ou em massa quando a senha muda.

A implementação a seguir segue o blueprint de código que a biblioteca Lucia documentou antes de se tornar recurso educacional. Lucia foi descontinuada como pacote npm em março de 2025, mas o guia de implementação de sessão que ela deixou continua sendo a referência mais clara e direta de "como fazer sessões do zero em TypeScript" — e a estrutura de tabela que usaremos aqui reflete exatamente esse modelo.

# Schema Drizzle: tabela sessions

O schema e-commerce criado no Volume XI tem tabelas users, products, orders e categories. A tabela sessions entra como extensão direta: uma linha por sessão ativa, com chave estrangeira para users e deleção em cascata — quando um usuário é removido, todas as sessões somem automaticamente.

schema.ts
import { pgTable, text, timestamp, uuid } from 'drizzle-orm/pg-core'
import { users } from './users'

export const sessions = pgTable('sessions', {
  // ID aleatório de alta entropia — não UUID, explicado abaixo
  id: text('id').primaryKey(),

  userId: uuid('user_id')
    .notNull()
    .references(() => users.id, { onDelete: 'cascade' }),

  expiresAt: timestamp('expires_at', { withTimezone: true })
    .notNull(),

  createdAt: timestamp('created_at', { withTimezone: true })
    .defaultNow()
    .notNull(),

  // Contexto de auditoria — opcional, recomendado
  userAgent: text('user_agent'),
  ipAddress: text('ip_address'),
})

O ID da sessão é text, não uuid. UUID v4 tem 122 bits de entropia — suficiente na prática, mas a escolha comum é 32 bytes de entropia codificados em base64url (256 bits), gerados com o módulo node:crypto. A diferença importa menos do que a fonte: o ID deve vir de crypto.getRandomValues ou randomBytes, nunca de Math.random().

# Criar sessão no login

A criação acontece imediatamente após verificar a senha com sucesso. Gera o ID, insere no banco com TTL calculado, e devolve o ID para ser setado como cookie. O TTL varia conforme o usuário marcou "lembre-me": sessão curta para uso em dispositivo compartilhado, sessão longa para dispositivo pessoal. Os dois caminhos usam a mesma função — só o TTL muda.

session.ts
import { randomBytes } from 'node:crypto'
import { sessions } from './schema'

const TTL = {
  short:  1  * 24 * 60 * 60 * 1000,  // 1 dia  (dispositivo compartilhado)
  long:   30 * 24 * 60 * 60 * 1000,  // 30 dias (lembre-me)
} as const

function generateSessionId(): string {
  return randomBytes(32).toString('base64url')  // 256 bits de entropia
}

export async function createSession(
  userId: string,
  opts: { rememberMe: boolean; userAgent?: string; ipAddress?: string }
) {
  const id = generateSessionId()
  const ttlMs = opts.rememberMe ? TTL.long : TTL.short
  const expiresAt = new Date(Date.now() + ttlMs)

  await db.insert(sessions).values({
    id, userId, expiresAt,
    userAgent: opts.userAgent,
    ipAddress: opts.ipAddress,
  })

  return { id, expiresAt, maxAge: Math.floor(ttlMs / 1000) }
}

# Validar sessão em cada request

A validação resolve o ID do cookie numa linha do store. Se a sessão não existe ou já expirou, retorna null e deleta o registro expirado para não acumular lixo. Se existir e for válida, retorna o userId que o middleware de autenticação do Capítulo 4 injeta no contexto.

session.ts
import { eq } from 'drizzle-orm'

export async function validateSession(sessionId: string) {
  const [session] = await db
    .select({
      userId:    sessions.userId,
      expiresAt: sessions.expiresAt,
    })
    .from(sessions)
    .where(eq(sessions.id, sessionId))
    .limit(1)

  if (!session) return null

  if (session.expiresAt < new Date()) {
    // Expirada — limpar proativamente, não esperar job de limpeza
    await db.delete(sessions).where(eq(sessions.id, sessionId))
    return null
  }

  return session  // { userId, expiresAt }
}
Não cache roles ou email no row de sessão
A sessão carrega só userId e expiresAt. Não armazene papéis, email, nome ou qualquer dado que pode mudar. Se o admin promove um usuário, revoga um papel, ou troca o email, e a sessão tem uma cópia antiga desses dados, a aplicação passa a trabalhar com informação desatualizada sem perceber. Busque esses campos frescos da tabela users no validate — com o userId em mãos, um findFirst no Drizzle é barato.

# Sliding expiration

Sliding expiration prorroga o TTL conforme o usuário age, em vez de deixar a sessão expirar em data fixa desde o login. A consequência desejada: um usuário ativo nunca é deslogado por inatividade; um usuário que sumiu é deslogado naturalmente após o TTL da última ação.

Renovar em toda request criaria um UPDATE por requisição — custoso em alta frequência. O padrão eficiente é renovar apenas quando a sessão cruzou a metade do seu ciclo de vida: se o TTL é 7 dias e a expiração é daqui a 3 dias (menos da metade restante), renova para mais 7 dias a partir de agora.

session.ts
export async function renewSessionIfNeeded(
  sessionId: string,
  expiresAt: Date,
  ttlMs: number
): Promise<Date> {
  const halfLife = new Date(Date.now() + ttlMs / 2)

  // Renova só se a sessão vai expirar antes da metade do TTL
  if (expiresAt < halfLife) {
    const newExpiry = new Date(Date.now() + ttlMs)

    await db
      .update(sessions)
      .set({ expiresAt: newExpiry })
      .where(eq(sessions.id, sessionId))

    return newExpiry
  }

  return expiresAt
}

Quando o TTL é renovado, o cookie também precisa ser atualizado com novo Max-Age — caso contrário o browser descarta o cookie antes da sessão no banco. No middleware de validação, após chamar renewSessionIfNeeded, use setCookie com a nova expiração se ela mudou. O cliente não percebe a renovação; do ponto de vista dele, o cookie simplesmente continua válido.

# Invalidação: logout e troca de credencial

Logout invalida apenas a sessão corrente — o usuário pode ter várias sessões abertas em dispositivos diferentes, e o padrão seguro é deixar as demais intactas salvo decisão explícita ("sair de todos os dispositivos"). Troca de senha, mudança de email e detecção de comprometimento invalidam todas as sessões do usuário sem exceção: qualquer sessão aberta pode pertencer ao atacante.

session.ts
// Logout simples: invalida só a sessão ativa
export async function invalidateSession(sessionId: string) {
  await db.delete(sessions).where(eq(sessions.id, sessionId))
}

// Troca de senha / comprometimento: apaga TODAS as sessões do usuário
export async function invalidateAllSessions(userId: string) {
  await db.delete(sessions).where(eq(sessions.userId, userId))
}

// Handler de logout: deleta do store + limpa o cookie
app.post('/auth/logout', async (c) => {
  const sessionId = getCookie(c, '__Host-sid') ?? ''
  await invalidateSession(sessionId)
  deleteCookie(c, '__Host-sid', { path: '/' })
  return c.json({ ok: true })
})
Invalidação em massa em operações sensíveis
Toda operação que altera credencial ou identidade deve chamar invalidateAllSessions — troca de senha, troca de email, revogação de conta, demoção de papel. Manter sessões abertas após uma dessas operações cria um estado inconsistente: o usuário "mudou a senha" mas a sessão do atacante continua válida. O fluxo correto é: alterar credencial → invalidateAllSessions → criar nova sessão para o usuário corrente.

# Limpeza de sessões expiradas

A deleção proativa no validateSession limpa uma sessão quando é acessada, mas sessões de usuários que simplesmente pararam de usar a aplicação ficam no banco indefinidamente. Para produção, um job periódico de limpeza evita o crescimento irrestrito da tabela.

cleanup.ts
import { lt } from 'drizzle-orm'

// Deletar sessões expiradas — rodar via cron ou pg_cron
export async function cleanExpiredSessions() {
  const result = await db
    .delete(sessions)
    .where(lt(sessions.expiresAt, new Date()))
    .returning({ id: sessions.id })

  return result.length  // número de sessões removidas
}

// Via pg_cron no Postgres — roda sem depender da aplicação:
-- SELECT cron.schedule('cleanup-sessions', '0 3 * * *',

Capítulo 6

Session stores

O Capítulo 5 implementou o ciclo de vida da sessão usando db.insert e db.delete diretamente. Em produção, a escolha de onde esse estado vive muda radicalmente o perfil de latência, escala e operação. Este capítulo compara os três stores mais comuns — memória, Redis e Postgres — e define uma interface que permite trocar o store sem reescrever a lógica de autenticação.

# Por que o store importa

Em desenvolvimento, um único processo Node guarda tudo em memória e parece funcionar perfeitamente. Em produção, a aplicação roda em múltiplas réplicas atrás de um load balancer. Se cada réplica tem seu próprio mapa de sessões em memória, a sessão criada na réplica A não existe na réplica B — o usuário se autentica e, no próximo request roteado para outra instância, recebe 401. O session store precisa ser compartilhado entre todas as réplicas.

Além de compartilhamento, o store precisa de expiração automática. Sem ela, sessões expiradas se acumulam indefinidamente — o Capítulo 5 mostrou deleção proativa no validate e job de limpeza periódica, mas ambas dependem de código de aplicação. Stores como Redis oferecem TTL nativo: o dado some automaticamente no tempo certo, sem job externo.

# In-memory: apenas para desenvolvimento

Um Map simples funciona como store durante desenvolvimento e testes unitários. É zero configuração, zero latência de rede, zero dependência externa. O único requisito é nunca usá-lo em produção ou em qualquer ambiente com mais de um processo.

stores/memory.ts
type SessionData = { userId: string; expiresAt: Date }

// ⚠️ Apenas para desenvolvimento — não funciona com múltiplas réplicas
const store = new Map<string, SessionData>()

export const memoryStore = {
  async get(id: string) {
    const s = store.get(id)
    if (!s || s.expiresAt < new Date()) {
      store.delete(id)
      return null
    }
    return s
  },
  async set(id: string, data: SessionData) {
    store.set(id, data)
  },
  async delete(id: string) {
    store.delete(id)
  },
}
In-memory não escala horizontalmente
Um store baseado em Map está preso no processo Node que o criou. Em qualquer deploy com mais de uma réplica — Kubernetes, PM2 com cluster, Fly.io com múltiplas machines — sessões criadas numa réplica são invisíveis para as outras. O resultado é autenticação que funciona localmente e quebra em staging ou produção, às vezes de forma intermitente dependendo do roteamento. Use apenas em testes unitários isolados ou em scripts CLI.

# Redis: o padrão de produção

Redis é a escolha padrão para session stores em produção por três razões. Primeiro, latência sub-milissegundo na mesma região — o lookup que custa 1–5 ms no Postgres custa 0,2–0,5 ms no Redis. Segundo, TTL nativo e atômico: SET key value EX seconds armazena o dado e agenda a expiração numa única operação — sem race condition, sem job de limpeza. Terceiro, estruturas de dados adicionais (sets, hashes) permitem construir índices auxiliares como "todas as sessões de um usuário" de forma eficiente.

stores/redis.ts
import { Redis } from 'ioredis'

const redis = new Redis(process.env.REDIS_URL!)
const PREFIX = 'session:'

function ttlSecs(expiresAt: Date): number {
  return Math.max(1, Math.floor((expiresAt.getTime() - Date.now()) / 1000))
}

export const redisStore = {
  async get(id: string) {
    const raw = await redis.get(PREFIX + id)
    if (!raw) return null
    return JSON.parse(raw) as SessionData
  },
  async set(id: string, data: SessionData) {
    // SET … EX é atômico: dado + TTL em uma única operação
    await redis.set(PREFIX + id, JSON.stringify(data), 'EX', ttlSecs(data.expiresAt))
  },
  async delete(id: string) {
    await redis.del(PREFIX + id)
  },
  async deleteByUserId(userId: string) {
    // Índice auxiliar: SET do Redis rastreia sessões por usuário
    const keys = await redis.smembers(`session:user:${userId}`)
    if (keys.length > 0) await redis.del(...keys)
    await redis.del(`session:user:${userId}`)
  },
}

O prefixo session: no nome da chave isola sessões de outros dados no mesmo Redis, facilita inspeção (SCAN 0 MATCH session:*) e permite políticas de eviction por prefixo em Redis 7+. O índice session:user:{userId} no método deleteByUserId é opcional mas necessário se a aplicação precisar de invalidação total — sem ele, a única alternativa seria SCAN em toda a keyspace, custoso em produção.

# Postgres: sem dependência extra

Quando a aplicação já tem Postgres e o volume de sessões é gerenciável (até algumas centenas de milhares de sessões ativas simultâneas), usar a própria tabela sessions do Capítulo 5 elimina uma dependência de infraestrutura inteira. Não há Redis para provisionar, monitorar ou pagar. A troca é latência: um SELECT em Postgres com índice fica em 1–5 ms contra 0,2–0,5 ms do Redis — irrelevante para a maioria das aplicações, relevante em APIs de baixíssima latência.

stores/postgres.ts
import { eq } from 'drizzle-orm'
import { sessions } from './schema'
import { validateSession } from './session'  // Cap 5

export const postgresStore = {
  async get(id: string) {
    return validateSession(id)   // já limpa expiradas proativamente
  },
  async set(id: string, data: SessionData) {
    await db
      .insert(sessions)
      .values({ id, userId: data.userId, expiresAt: data.expiresAt })
      .onConflictDoUpdate({
        target: sessions.id,
        set: { expiresAt: data.expiresAt },
      })
  },
  async delete(id: string) {
    await db.delete(sessions).where(eq(sessions.id, id))
  },
  async deleteByUserId(userId: string) {
    await db.delete(sessions).where(eq(sessions.userId, userId))
  },
}

Um índice em (user_id) e outro em (expires_at) são obrigatórios nessa tabela. O primeiro torna deleteByUserId eficiente; o segundo torna o job de limpeza do Capítulo 5 eficiente. Sem eles, ambas as operações viram sequential scans à medida que a tabela cresce.

# Interface abstrata: troca sem reescrita

Definir uma interface SessionStore que ambos os stores implementam desacopla a lógica de autenticação da infraestrutura. O middleware de auth do Capítulo 4 recebe um store por injeção — trocar de Redis para Postgres (ou vice-versa) é uma linha no bootstrap da aplicação, não uma refatoração.

stores/interface.ts
export interface SessionStore {
  get(id: string):                             Promise<SessionData | null>
  set(id: string, data: SessionData):          Promise<void>
  delete(id: string):                           Promise<void>
  deleteByUserId?(userId: string):             Promise<void>
}

// Middleware recebe o store por injeção
export function sessionMiddleware(store: SessionStore) {
  return async (c: Context, next: Next) => {
    const id = getCookie(c, '__Host-sid') ?? ''
    const session = await store.get(id)
    if (!session) return c.json({ code: 'UNAUTHENTICATED' }, 401)
    c.set('userId', session.userId)
    await next()
  }
}

// Bootstrap: escolha do store em um só lugar
const store: SessionStore =
  process.env.REDIS_URL ? redisStore : postgresStore

app.use('*', sessionMiddleware(store))

# Segurança dos dados no store

O store contém informação de identidade sensível. No Redis, as chaves de sessão ficam em texto plano por padrão — acesso não autorizado ao Redis equivale a acesso a todas as sessões ativas. Medidas mínimas de produção: Redis com requirepass (senha forte), acesso restrito à rede privada (sem exposição pública), e TLS ativado (rediss:// no URL de conexão). Se a sessão contiver dados além de userId — preferências, permissões cacheadas, dados temporários — avaliar se esses dados valem encriptação em repouso.

No Postgres, a tabela sessions se beneficia do controle de acesso nativo do banco: o usuário da aplicação pode ter acesso à tabela sessions mas não às demais, limitando o impacto de uma injeção SQL localizada. O Capítulo 21 (OWASP) revisita essas configurações no contexto de segurança de produção.

Capítulo 7

CSRF: cross-site request forgery

CSRF existe por causa de uma má-feature acidental do design original da web: o navegador anexa cookies automaticamente em qualquer requisição que satisfaça o escopo do cookie, independente de quem iniciou a requisição. Uma página em outro domínio dispara um POST para sua aplicação e o navegador, obediente, envia os cookies de sessão junto — autenticando uma operação que o usuário nunca pediu. Este capítulo dissecciona o problema e cobre as camadas de defesa modernas, da mais simples (Origin header) à mais robusta (Signed Double Submit).

# O ataque: autoridade ambiente do cookie

O termo técnico para o que cookies fazem é autoridade ambiente: a credencial está disponível ao navegador o tempo inteiro, e o navegador a usa sem perguntar. Para uma requisição que o próprio usuário inicia, isso é conveniente. Para uma requisição iniciada por código de outra origem, é uma ponte para o atacante operar como o usuário.

evil.html
<!-- Hospedado em evil.com, a vítima só precisa visitar a página -->
<body>
  <form action="https://banco.com/transfer" method="POST">
    <input type="hidden" name="to" value="atacante" />
    <input type="hidden" name="amount" value="10000" />
  </form>
  <script>document.forms[0].submit()</script>
</body>

A sequência: a vítima já está logada em banco.com (cookie de sessão válido no navegador). Visita evil.com — qualquer pretexto, banner, link, e-mail. O script da página maliciosa submete o form automaticamente. O navegador dispara o POST para banco.com/transfer e anexa o cookie de sessão porque o request satisfaz o escopo do cookie. O servidor vê uma requisição autenticada vinda de uma usuária autenticada e processa a transferência. A vítima nunca soube que houve uma requisição.

Três detalhes definem o problema: a requisição é cross-site (originada em domínio diferente do alvo), a credencial é ambiente (cookie, anexado automaticamente), e o atacante não precisa ler a resposta (basta que a operação execute). Cada defesa que vamos ver ataca pelo menos uma dessas três propriedades.

# Origin header e SameSite: a primeira linha

A defesa mais simples não usa token algum. Quando um navegador faz uma requisição POST, PUT, DELETE ou PATCH cross-origin, ele inclui um header Origin indicando qual site iniciou o request. Diferente de Referer — que o usuário pode desabilitar ou o navegador pode omitir por privacidade — Origin é enviado de forma confiável em todos os requests modificadores cross-origin. O servidor compara o valor recebido contra uma allowlist e rejeita o que não bater.

origin-check.ts
const ALLOWED_ORIGINS = ['https://app.exemplo.com']
const SAFE_METHODS = ['GET', 'HEAD', 'OPTIONS']

app.use('*', async (c, next) => {
  // Métodos seguros (por convenção REST) não precisam de proteção CSRF.
  if (SAFE_METHODS.includes(c.req.method)) return next()

  const origin = c.req.header('origin')
  const referer = c.req.header('referer')
  const source = origin ?? (referer ? new URL(referer).origin : null)

  if (!source || !ALLOWED_ORIGINS.includes(source)) {
    return c.json({ code: 'CSRF_BLOCKED' }, 403)
  }

  await next()
})

A segunda camada é o atributo SameSite do Capítulo 4. SameSite=Lax instrui o navegador a omitir o cookie em quase todos os requests cross-site — fetch, XHR, form POST, subrecursos. A combinação SameSite=Lax + Origin check elimina a maioria absoluta dos vetores CSRF, e é o mínimo que qualquer aplicação séria deveria ter em 2026.

Os pontos cegos do SameSite=Lax são poucos, mas importantes. Requisições GET que mudam estado (anti-padrão REST, mas comuns em código legado) ainda passam — o navegador envia o cookie em navegações top-level. Bugs em browsers ou em runtimes embarcados ocasionalmente relaxam a regra. E, mais relevante, Lax não protege contra ataques same-site: um subdomínio comprometido (cdn.exemplo.com servindo conteúdo malicioso) ainda envia cookies da raiz. Para sistemas com superfície grande de subdomínios, a defesa precisa ir além.

SameSite=Lax não é proteção completa
A combinação SameSite + Origin check cobre o caso geral, mas não fecha todos os vetores. GET com side-effect, subdomínios comprometidos, e detalhes específicos de implementação de navegador deixam brechas. Em sistemas sensíveis (financeiro, administrativo, saúde), uma terceira camada de tokens CSRF continua sendo a recomendação OWASP. Defesa em profundidade não é redundância — é a aceitação de que cada camada falha eventualmente.

# Synchronizer e Double Submit: tokens com estado

O padrão tradicional, Synchronizer Token, gera um valor aleatório no login e o associa à sessão no server store. O cliente recebe o token (via cookie acessível ao JS, ou inline no HTML) e o devolve no header X-CSRF-Token em cada requisição modificadora. O servidor compara o token recebido com o que tem na sessão usando comparação em tempo constante (Cap 2). O atacante em evil.com não consegue ler o token — a política de origem (Same-Origin Policy) impede que código de uma origem leia recursos de outra — então não consegue forjar o header.

A variação Double Submit Cookie evita o store: emite um token aleatório, coloca em cookie acessível ao JS, e exige que o cliente envie o mesmo valor em header ou body. O servidor compara os dois lados. Não há estado no servidor, mas a defesa tem uma fraqueza: um subdomínio controlado por atacante pode setar cookies na raiz do domínio, plantando um token e depois enviando o mesmo token no header. Quem se beneficia mais é o Signed Double Submit.

# Signed Double Submit: a recomendação atual

A evolução moderna, recomendada pela OWASP em sua Cheat Sheet de CSRF, é o Signed Double Submit: o token entregue ao cliente carrega uma assinatura HMAC do sessionId com um segredo do servidor. O servidor verifica a assinatura — não precisa de store, mas o token está criptograficamente amarrado à sessão específica. Plantar um cookie de subdomínio não funciona: a sessão do atacante tem outro sessionId, e a assinatura do token vai falhar quando comparada à sessão da vítima.

signed-double-submit.ts
import { createHmac, randomBytes, timingSafeEqual } from 'node:crypto'

const CSRF_SECRET = process.env.CSRF_SECRET!  // 32+ bytes, segredo dedicado

// Emissão: amarra um nonce aleatório ao sessionId via HMAC
export function issueCsrfToken(sessionId: string): string {
  const nonce = randomBytes(16).toString('base64url')
  const sig = createHmac('sha256', CSRF_SECRET)
    .update(`${sessionId}.${nonce}`)
    .digest('base64url')
  return `${nonce}.${sig}`
}

// Verificação: HMAC com segredo + comparação timing-safe
export function verifyCsrfToken(token: string, sessionId: string): boolean {
  const [nonce, sig] = token.split('.')
  if (!nonce || !sig) return false

  const expected = createHmac('sha256', CSRF_SECRET)
    .update(`${sessionId}.${nonce}`)
    .digest('base64url')

  const a = Buffer.from(sig)
  const b = Buffer.from(expected)
  return a.length === b.length && timingSafeEqual(a, b)
}

O token resultante tem o formato nonce.assinatura e é seguro para colocar em cookie acessível ao JavaScript (sem HttpOnly) — o atacante de outra origem não consegue lê-lo pela política do navegador, e o segredo do HMAC nunca deixa o servidor. O cookie de sessão (__Host-sid) continua HttpOnly; o cookie CSRF (__Host-csrf) fica acessível para o frontend ler e enviar via header.

# Integração no middleware Hono

O middleware de CSRF roda depois do middleware de sessão (que estabelece userId e sessionId no contexto) e antes dos handlers de negócio. Métodos seguros pulam a verificação. Para os demais, o token chega no header X-CSRF-Token ou no cookie acessível __Host-csrf; é validado contra o sessionId em contexto via verifyCsrfToken.

csrf-middleware.ts
import { getCookie, setCookie } from 'hono/cookie'

const SAFE = ['GET', 'HEAD', 'OPTIONS']

// 1) No login (ou GET inicial), emite e envia o cookie do token
app.get('/auth/csrf', async (c) => {
  const sessionId = c.get('sessionId')
  const token = issueCsrfToken(sessionId)
  setCookie(c, '__Host-csrf', token, {
    secure: true,
    sameSite: 'Lax',
    path: '/',
    // httpOnly: false — JS precisa ler para enviar no header
  })
  return c.json({ token })   // também devolvido no body para SPAs sem leitura de cookie
})

// 2) Middleware de validação para métodos modificadores
app.use('*', async (c, next) => {
  if (SAFE.includes(c.req.method)) return next()

  const sessionId = c.get('sessionId')
  const token = c.req.header('x-csrf-token') ?? getCookie(c, '__Host-csrf')

  if (!sessionId || !token || !verifyCsrfToken(token, sessionId)) {
    return c.json({ code: 'CSRF_INVALID' }, 403)
  }

  await next()
})

Hono também oferece um middleware built-in csrf() em hono/csrf que faz a verificação por Origin header — útil como camada rápida sem token. Em produção, combinar os dois (Origin check + Signed Double Submit) é a configuração mais robusta sem custo operacional significativo.

Defesa em camadas: a receita 2026
A configuração defensável hoje combina três medidas independentes: (1) cookie de sessão com SameSite=Lax e prefixo __Host- — bloqueia a maioria dos vetores na borda do navegador; (2) verificação de Origin contra allowlist no middleware — captura o que escapa da camada anterior; (3) Signed Double Submit em rotas modificadoras — defesa final contra subdomínios comprometidos e edge cases de navegador. Cada camada cobre as falhas das outras.

# Quando CSRF não se aplica

A premissa do ataque é a credencial ambiente. APIs autenticadas exclusivamente via Authorization: Bearer <token> não têm credencial ambiente — o token precisa ser explicitamente enviado pelo código, e código de outra origem não tem acesso ao token (a SPA o guarda em memória, não em cookie). Para essas APIs, CSRF não é vetor.

O mesmo vale para aplicações mobile nativas, que não rodam num navegador e não anexam credenciais automaticamente. E para SPAs que usam o modelo híbrido access+refresh do Capítulo 3, onde o access token vive em memória da SPA e viaja em header Authorization: as requisições da API são imunes a CSRF, e o único endpoint que ainda usa cookie é /auth/refresh — esse sim precisa de proteção CSRF, mas é um endpoint só.

Identifique a superfície de cookie
A pergunta operacional é: quais endpoints da minha aplicação aceitam credencial automática do navegador? Se a resposta é "nenhum" (API pura com Bearer), CSRF não se aplica. Se é "todos" (sessão clássica via cookie), proteção CSRF é obrigatória em todos os endpoints modificadores. Se é "só /auth/refresh" (híbrido), a proteção fica concentrada nesse endpoint. Mapear essa superfície é o primeiro passo de qualquer auditoria de CSRF.

JWT: estrutura

JWT (JSON Web Token, RFC 7519) é o formato dominante de token na web em 2026. Não é um protocolo nem uma biblioteca — é um modo de empacotar declarações em uma string compacta, assinada criptograficamente, que cabe em headers HTTP. Este capítulo abre a caixa: as três partes que compõem cada JWT, as claims padronizadas, o encoding usado, e a distinção crítica entre decodificar e verificar.

# Anatomia: três partes separadas por ponto

Todo JWT tem a forma xxxxx.yyyyy.zzzzz: três strings separadas por ponto. A primeira é o header, a segunda é o payload, a terceira é a assinatura. Header e payload são JSON codificados em base64url; a assinatura é bytes brutos codificados em base64url. Os pontos são literais; não há outros separadores.

jwt-anatomy.txt
// Um JWT real tem este formato:
//   header . payload . signature

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
  .eyJzdWIiOiJtYXJpYUBleGVtcGxvLmNvbSIsIm5hbWUiOiJNYXJpYSIsImlhdCI6MTUxNjIzOTAyMn0
  .SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

// Header decodificado (base64url → JSON):
//   { "alg": "HS256", "typ": "JWT" }

// Payload decodificado:
//   { "sub": "maria@exemplo.com", "name": "Maria", "iat": 1516239022 }

// Signature (HMAC-SHA256, neste caso):
//   HMACSHA256( base64url(header) + "." + base64url(payload), SECRET )

A assinatura cobre tanto o header quanto o payload — o cliente não pode trocar o algoritmo de HS256 para none sem invalidar a assinatura, nem alterar qualquer claim sem o mesmo efeito. O token inteiro é tamper-evident: qualquer mudança de um byte quebra a verificação. O segredo (em HMAC) ou a chave privada (em RSA/ECDSA) nunca sai do servidor.

# Header: alg, typ e kid

O header carrega metadados necessários para verificar o token. Os campos relevantes são poucos: alg indica o algoritmo de assinatura (HS256, RS256, ES256, EdDSA), typ é convencionalmente "JWT", e kid identifica qual chave foi usada — essencial em sistemas com rotação de chaves (detalhado no Capítulo 9).

O valor de alg precisa ser tratado com desconfiança no servidor: aceitar o algoritmo que o cliente declara abre uma classe inteira de ataques (downgrade para none, confusão entre HMAC e RSA). A regra prática é declarar no código o algoritmo esperado, e rejeitar qualquer token cujo alg não bata.

# Payload: claims registradas e customizadas

O payload é um JSON arbitrário, mas a RFC 7519 padroniza um conjunto de claims com nomes curtos de três letras. Não são obrigatórias, mas usá-las garante interoperabilidade com bibliotecas e provedores. Claims customizadas são livres — qualquer chave que não colida com as reservadas. A regra é ser parcimonioso: cada byte no payload viaja em todo request.

payload-shape.ts
// Shape típico de um payload em produção (preview para Cap 11)
type AppJwtPayload = {
  // Registered (RFC 7519) — nomes curtos, validação automática
  sub: string          // subject: tipicamente o userId
  iss: string          // issuer: quem emitiu o token
  aud: string          // audience: para quem o token vale
  iat: number          // issued at: timestamp Unix em segundos
  exp: number          // expiration: timestamp Unix em segundos
  jti: string          // JWT ID único — usado em denylist

  // Custom claims — específicas da aplicação
  role: 'user' | 'admin'
  email: string
}

Não coloque dados sensíveis no payload: ele não é criptografado, apenas assinado. Qualquer um que veja o token vê o conteúdo. Senha, número de cartão, dados pessoais sensíveis ficam fora — para isso existe JWE (encriptado), discutido brevemente ao final deste capítulo.

# Criando um JWT com jose

A biblioteca jose é a implementação de referência em Node 22 LTS, com suporte completo à família JOSE (JWS, JWE, JWK, JWKS) e compatibilidade total com runtimes edge (Workers, Deno, Bun). A API de assinatura é construída por encadeamento de métodos — cada setX adiciona uma claim, e sign finaliza com o segredo ou chave.

create.ts
import { SignJWT } from 'jose'
import { randomUUID } from 'node:crypto'

const secret = new TextEncoder().encode(process.env.JWT_SECRET!)

const token = await new SignJWT({
  // Claims customizadas no payload
  role: user.role,
  email: user.email,
})
  .setProtectedHeader({ alg: 'HS256', typ: 'JWT' })
  .setIssuer('https://api.exemplo.com')
  .setSubject(user.id)
  .setAudience('api.exemplo.com')
  .setIssuedAt()
  .setExpirationTime('15m')
  .setJti(randomUUID())
  .sign(secret)

// Resultado: string no formato xxxxx.yyyyy.zzzzz

O encadeamento traduz diretamente para as claims geradas: setSubject(id) → sub: id; setExpirationTime('15m') → exp: now + 15m; setIssuedAt() → iat: now. Para sistemas com microsserviços, definir iss e aud de forma estrita permite que cada serviço valide se o token foi emitido para ele especificamente — não para outro serviço da mesma organização.

# Decodificar não é verificar

O passo mais importante deste capítulo: decodificar um JWT não valida nada. As três partes são base64url, qualquer um decodifica trivialmente — incluindo o atacante que interceptou o token. A verificação criptográfica é uma operação separada, que confere a assinatura usando o segredo (ou chave pública).

decode-vs-verify.ts
import { decodeJwt, decodeProtectedHeader, jwtVerify } from 'jose'

// ⚠️ APENAS para debug — não valida assinatura nem expiração
const header = decodeProtectedHeader(token)
const payload = decodeJwt(token)

console.log(header)   // { alg: 'HS256', typ: 'JWT' }
console.log(payload)  // { sub: '...', role: 'admin', exp: ..., iat: ... }

// ❌ NUNCA use payload assim para autorização — qualquer um cria essa string.

// ✅ Verificação real — confere assinatura, exp, iss, aud automaticamente
const { payload: verified } = await jwtVerify(token, secret, {
  issuer:   'https://api.exemplo.com',
  audience: 'api.exemplo.com',
})

// verified.sub é confiável; nada foi adulterado.
Nunca use decodeJwt em autorização
O site jwt.io oferece um "decoder" que mostra o conteúdo de qualquer JWT colado na caixa — isso é decodificação, não verificação. Em código de produção, decodeJwt da biblioteca jose é equivalente: apenas parsing. Tomar decisões de autorização baseadas no payload decodificado é como aceitar um documento de identidade só pela foto, sem conferir o chip. Sempre use jwtVerify antes de confiar em qualquer valor do payload.

# Base64url: por que não Base64 padrão

JWT usa base64url, uma variação da base64 padrão definida na RFC 4648. A diferença está em três caracteres: base64 usa +, / e = (padding) — todos problemáticos em URLs e headers HTTP. + vira espaço quando decodificado como query string; / conflita com paths; = precisa de escape em URLs. Base64url troca + por -, / por _, e omite o padding =.

Bibliotecas como jose tratam o encoding transparentemente. A única razão prática de saber disso é depuração: ao copiar um JWT de um log para o jwt.io, certifique-se de copiar a string inteira (sem quebras de linha) e sem confundir +// com -/_. Tentativas de "consertar" um JWT trocando esses caracteres manualmente quebram a assinatura.

# A família JOSE: JWS, JWE e além

JWT é parte da família JOSE (JSON Object Signing and Encryption), padronizada nas RFCs 7515–7519. Vale conhecer os outros membros para entender o que JWT é e o que não é. JWS (JSON Web Signature) é o formato assinado — todo JWT que você vê em produção é um JWS na sua serialização compacta (a forma com pontos). JWE (JSON Web Encryption) é o formato encriptado: o payload fica ilegível para qualquer um sem a chave de decriptação, não apenas tamper-evident.

JWK (JSON Web Key) padroniza como representar chaves criptográficas em JSON, e JWKS (JWK Set) é um conjunto delas — formato usado por provedores OAuth/OIDC para publicar suas chaves públicas em endpoints como /.well-known/jwks.json. O Capítulo 9 entra em rotação de chaves usando esse padrão; os Capítulos 12 e 13 (OAuth, OIDC) usam JWKS para verificar tokens emitidos por provedores externos.

kid habilita rotação de chaves
Quando o header inclui kid ("key ID"), o servidor sabe qual chave usar para verificar — o que permite manter várias chaves ativas simultaneamente. Sem kid, rotacionar a chave invalida todos os tokens emitidos antes da rotação. Com kid, dá para emitir tokens com a chave nova enquanto ainda se valida tokens com a chave antiga, fazendo a transição suave. O Capítulo 9 detalha o fluxo completo.
Tamanho do JWT importa
Cada byte do JWT viaja em todo request autenticado, em todos os logs, em todos os caches. Um JWT de 200 bytes é trivial; um de 2 KB com claims redundantes começa a aparecer em latência e em limites de header HTTP (a maioria dos servidores corta em 8 KB). Use claims customizadas com parcimônia: userId e role bastam — busque o resto no banco. O JWT é credencial, não cache de perfil.

# Simétrico vs assimétrico: dois modelos de confiança

Há duas formas de assinar um JWT, e elas correspondem a duas suposições diferentes sobre confiança. Em criptografia simétrica (HMAC), há um único segredo compartilhado entre quem assina e quem verifica. O mesmo valor produz a assinatura e a confere — qualquer parte que possa verificar também consegue forjar. Em criptografia assimétrica, são duas chaves matematicamente relacionadas: a privada assina, a pública verifica. Quem tem só a chave pública consegue conferir que algo foi assinado pelo dono da privada, mas não consegue produzir uma assinatura nova.

A escolha entre os dois modelos é a primeira pergunta arquitetural sobre tokens. Se a aplicação inteira é um único serviço — o mesmo processo que emite tokens também os verifica — HMAC é o suficiente: ninguém de fora precisa verificar, então ninguém de fora precisa do segredo. Se há múltiplos serviços envolvidos — uma autenticação centralizada que emite tokens consumidos por dezenas de APIs, ou um provedor OAuth externo — assimétrico é obrigatório: a chave de verificação precisa ser distribuída sem dar aos consumidores o poder de emitir.

simetrico-vs-assimetrico.ts
import { SignJWT, jwtVerify, generateKeyPair } from 'jose'

// HS256 (simétrico): o mesmo segredo nos dois lados
const secret = new TextEncoder().encode(process.env.JWT_SECRET!)

const tokenHs = await new SignJWT({ sub: user.id })
  .setProtectedHeader({ alg: 'HS256' })
  .sign(secret)                            // quem assina: tem o segredo

await jwtVerify(tokenHs, secret, {
  algorithms: ['HS256'],
})                                          // quem verifica: mesmo segredo

// EdDSA (assimétrico): chaves distintas para cada papel
const { publicKey, privateKey } = await generateKeyPair('EdDSA', {
  crv: 'Ed25519',
})

const tokenEd = await new SignJWT({ sub: user.id })
  .setProtectedHeader({ alg: 'EdDSA' })
  .sign(privateKey)                        // emissor: chave privada

await jwtVerify(tokenEd, publicKey, {     // verificador: chave pública
  algorithms: ['EdDSA'],
})

# Os algoritmos em 2026: HS256, RS256, ES256, EdDSA

O ecossistema JWT padronizou meia dúzia de algoritmos, mas na prática quatro dominam. HS256 é HMAC com SHA-256: rápido, simples, simétrico — segredo precisa ter pelo menos 32 bytes (256 bits) de entropia, gerado com randomBytes. Segredos menores caem a brute force; segredos baseados em senha são vulneráveis a dicionário.

RS256 é RSA-SHA256 com padding PKCS#1 v1.5, o padrão assimétrico histórico do JWT. Chaves de 2048 bits são o mínimo aceitável; 3072 ou 4096 para novos sistemas. RS256 é mais lento que HMAC por uma ordem de grandeza (microssegundos por verificação versus nanossegundos), mas é universalmente suportado — provedores legados como Auth0, AWS Cognito e Active Directory Federation Services emitem em RS256 por default.

ES256 usa ECDSA com a curva P-256 (também chamada secp256r1). A vantagem direta sobre RS256 é tamanho: uma chave ES256 de 256 bits oferece segurança equivalente a uma chave RSA de 3072 bits. Verificação é mais rápida, tokens são menores, geração de chaves é mais leve. É a opção padrão moderna em provedores que migraram do RS256.

EdDSA com curva Ed25519 é o estado da arte em 2026. Foi projetado para evitar as armadilhas de implementação que historicamente atingiram ECDSA (geração de nonce, ataques de canal lateral). É mais rápido que ES256, tem chaves do mesmo tamanho, e é a recomendação tanto da IETF quanto da maior parte das auditorias de segurança modernas. Node 22 LTS e a biblioteca jose suportam EdDSA nativamente.

gerar-chaves-eddsa.ts
import { generateKeyPair, exportJWK } from 'jose'

const { publicKey, privateKey } = await generateKeyPair('EdDSA', {
  crv: 'Ed25519',
  extractable: true,             // necessário para exportar/persistir
})

// Exportar em JWK (JSON Web Key) para armazenar ou publicar
const publicJwk  = await exportJWK(publicKey)
const privateJwk = await exportJWK(privateKey)

console.log(publicJwk)
// {
//   kty: 'OKP',         ← "Octet Key Pair" (família Edwards-curve)
//   crv: 'Ed25519',     ← curva específica

// }

# Como escolher na prática

Três sinais práticos guiam a escolha. Primeiro: quem precisa verificar? Se a resposta é "só o próprio serviço que emite", HS256 é a opção mais simples e a mais rápida. Se a resposta envolve qualquer outro processo — sidecar, gateway, microsserviço — assimétrico é obrigatório.

Segundo: há restrição de compatibilidade? Provedores OAuth maduros, especialmente em ambientes enterprise, podem emitir apenas RS256. Verificar tokens de um Auth0 ou Cognito significa aceitar o que o provedor oferece — geralmente RS256, eventualmente ES256. Para sistemas novos onde a equipe controla o emissor e os verificadores, EdDSA é a escolha defensável.

Terceiro: onde o código roda? Edge runtimes (Cloudflare Workers, Vercel Edge) suportam Web Crypto, e a jose usa Web Crypto nativamente — todos os algoritmos modernos funcionam, inclusive EdDSA. Em runtimes Node tradicionais, qualquer escolha funciona; em edge, a leveza do EdDSA aparece tanto em performance quanto em bundle size.

# Rotação de chaves com kid

Chaves criptográficas envelhecem. Podem vazar em log, podem aparecer num repositório público, podem pertencer a um ex-funcionário, podem simplesmente exceder o limite de uso da política de segurança. A solução é rotação: substituir a chave em uso por uma nova, sem interromper a aplicação. O problema técnico é que tokens já emitidos foram assinados com a chave antiga — se a chave nova for incompatível com eles, todos os usuários são deslogados.

O parâmetro kid ("key ID") do header resolve isso. Quando o token carrega um kid, o verificador sabe qual chave usar para conferir aquela assinatura específica. O servidor mantém um mapa de chaves indexadas por kid: a chave atual (usada para emitir) e a anterior (ainda usada para verificar tokens antigos que ainda não expiraram).

rotacao.ts
import { SignJWT, jwtVerify, decodeProtectedHeader } from 'jose'
import type { KeyLike } from 'jose'

// Conjunto de chaves ativas, indexado por kid
const keys: Record<string, { priv?: KeyLike; pub: KeyLike }> = {
  '2026-01': { priv: keyOldPriv, pub: keyOldPub },
  '2026-06': { priv: keyNewPriv, pub: keyNewPub },  // chave atual
}

const CURRENT_KID = '2026-06'

// Emissão: sempre com a chave atual
async function issue(payload: JWTPayload) {
  return new SignJWT(payload)
    .setProtectedHeader({ alg: 'EdDSA', kid: CURRENT_KID })
    .sign(keys[CURRENT_KID].priv!)
}

// Verificação: descobre a chave pelo kid do token
async function verify(token: string) {
  const { kid } = decodeProtectedHeader(token)
  const entry = keys[kid as string]
  if (!entry) throw new Error('unknown kid')

  return jwtVerify(token, entry.pub, {
    algorithms: ['EdDSA'],
  })
}

// Após o TTL máximo da chave antiga, remover sua entrada do mapa.

O ciclo de vida típico: chave nova é introduzida no mapa antes de virar a corrente; depois de algum tempo (para deploys propagarem em todas as instâncias), CURRENT_KID aponta para a nova; tokens novos passam a ser emitidos com ela enquanto verificação aceita ambas; finalmente, quando todos os tokens emitidos com a chave antiga já expiraram (passados o TTL máximo de access token), a entrada antiga é removida.

# JWKS: chaves públicas como recurso público

Quando o emissor e os verificadores são serviços separados, há um problema operacional: como distribuir a chave pública? Hardcoding no código de cada consumidor é frágil e impede rotação. A solução padronizada é o JWKS (JSON Web Key Set): o emissor expõe um endpoint público — convencionalmente /.well-known/jwks.json — que lista todas as chaves públicas ativas em formato JWK, cada uma com seu kid.

jwks-remote.ts
import { createRemoteJWKSet, jwtVerify } from 'jose'

// O emissor publica um endpoint público:
// GET https://auth.exemplo.com/.well-known/jwks.json
// {
//   "keys": [
//     { "kid": "2026-01", "kty": "OKP", "crv": "Ed25519", "x": "..." },
//     { "kid": "2026-06", "kty": "OKP", "crv": "Ed25519", "x": "..." }
//   ]
// }

// O verificador cria um JWKS remoto — cache automático, refresh ao ver kid novo
const JWKS = createRemoteJWKSet(
  new URL('https://auth.exemplo.com/.well-known/jwks.json'),
  { cacheMaxAge: 600_000 }  // 10 min de cache
)

const { payload } = await jwtVerify(token, JWKS, {
  issuer:     'https://auth.exemplo.com',
  audience:   'api.exemplo.com',
  algorithms: ['EdDSA'],
})

O fluxo automatizado: na primeira verificação, jose busca o JWKS e cacheia em memória; nas subsequentes, usa o cache; se um token chega com kid desconhecido, refresha o cache antes de falhar. O resultado é rotação totalmente transparente: o emissor publica a chave nova, os verificadores a descobrem automaticamente na primeira vez que aparece, sem deploy nenhum no lado consumidor.

# Os ataques clássicos: alg=none e algorithm confusion

Duas vulnerabilidades de implementação perseguiram JWT por uma década inteira e ainda aparecem em código novo. Vale conhecer ambas — não para implementá-las, mas para reconhecer configurações que as deixam abertas.

O primeiro é o ataque alg: none. A especificação original previu o valor "none" para indicar que o token não tem assinatura — uso legítimo era restrito a contextos onde outro canal garantia integridade. Bibliotecas antigas implementaram literalmente: se o header dizia alg: none, pulavam a verificação e aceitavam o payload como válido. O atacante construía um JWT com header {"alg":"none"}, payload arbitrário, e assinatura vazia. O servidor aceitava. CVEs históricas em bibliotecas mainstream aconteceram exatamente por isso.

O segundo é algorithm confusion, mais sutil. Suponha um servidor que verifica tokens em RS256 — tem a chave pública do emissor configurada. O atacante intercepta a chave pública (que é, por definição, pública), e cria um JWT cujo header diz alg: HS256. Em bibliotecas que aceitam o alg do header sem questionar, o servidor tenta verificar o token usando a chave pública como segredo HMAC — e como ele mesmo gerou a "assinatura" com essa mesma chave pública, o HMAC bate. O atacante consegue forjar tokens válidos usando informação pública.

verificacao-defensiva.ts
// ❌ ANTI-PADRÃO: deixar o cliente escolher o algoritmo
await jwtVerify(token, key)
// jose moderna exige algorithms desde 2022, mas variantes antigas e wrappers

EdDSA é a escolha defensável em 2026
Para sistemas novos onde a equipe controla emissor e verificadores, EdDSA com Ed25519 é a recomendação consensual em 2026. É mais rápido que ES256, tem chaves do mesmo tamanho compacto, e foi projetado para evitar as armadilhas de implementação que historicamente atingiram ECDSA. RS256 continua aceitável por compatibilidade com provedores legados; ES256 é alternativa razoável quando EdDSA não é suportado. HS256 é correto para o caso específico de emissor único — não há vantagem em complicar o setup se nenhum outro processo precisa verificar.
Segredo HS256: 32 bytes ou nada
Se for usar HS256, o segredo precisa ser gerado por randomBytes(32) ou equivalente em Web Crypto — 32 bytes (256 bits) de entropia real. Senhas humanas como "meu-secret-jwt-2026", mesmo longas, têm entropia muito menor e caem a ataques de dicionário acelerados por GPU. Armazene o segredo em variável de ambiente fornecida por gerenciador de segredos (Doppler, AWS Secrets Manager, Vault), nunca em .env comitado.

Capítulo 10

Access e refresh tokens

O Capítulo 3 apresentou o modelo híbrido como resposta ao trade-off entre revogabilidade e escala: access curto e stateless, refresh longo e em store. Aquela apresentação tratou o refresh como sessão escondida. Este capítulo desce um nível: para que o modelo seja realmente seguro, o refresh precisa de rotação a cada uso e detecção de reuso. Sem essas duas propriedades simultâneas, um refresh roubado vale o TTL inteiro do refresh — e o modelo híbrido inteiro deixa de ter sentido como ganho de segurança.

# O que o modelo híbrido precisa entregar

Recapitulando do Capítulo 3: o access token tem TTL curto (5–15 minutos) e é verificado sem I/O em cada request da API. O refresh token tem TTL longo (dias ou semanas), é opaco e armazenado em store, e aparece apenas em uma rota dedicada (/auth/refresh). O cliente usa o access em todas as requisições; quando o access expira, troca o refresh por um novo par.

A propriedade que justifica o modelo é a janela de revogação: deletar o refresh do store invalida a sessão em ≤ TTL do access, mesmo sem denylist no caminho crítico. Mas há um detalhe escondido: se o refresh for roubado e não houver mecanismo para detectar o roubo, o atacante tem o TTL inteiro do refresh para operar. Um refresh com 30 dias de validade, sem rotação, é equivalente a uma sessão de 30 dias irrevogável — exatamente o que queríamos evitar.

# Rotação: um novo refresh a cada uso

A primeira metade da defesa é rotação. Cada chamada bem-sucedida a /auth/refresh não apenas emite um novo access — também emite um novo refresh, invalidando o anterior. Do ponto de vista do cliente, é apenas substituir os dois tokens armazenados. Do ponto de vista do servidor, o refresh anterior fica marcado como "já usado" e nunca mais é aceito.

O ganho imediato: a janela de uso de cada refresh individual é tipicamente o TTL do access — minutos, não dias. Se um refresh é roubado depois da rotação, o atacante tem apenas até a próxima vez que o cliente legítimo fizer refresh; nesse momento, o token roubado deixa de funcionar.

Há um problema: rotação sozinha é cosmética. Suponha que o atacante roube o refresh atual e use primeiro, antes do cliente legítimo. O servidor emite um novo par para o atacante e marca o refresh anterior como usado. Quando o cliente legítimo tenta usar o mesmo refresh (que ele ainda tem), recebe uma falha — mas o servidor não sabe se a falha é replay malicioso, retry de rede, ou abuso. Sem mais sinais, ele apenas rejeita. O atacante continua tendo o token novo e renova indefinidamente.

# Detecção de reuso: o ponto que fecha o ciclo

A segunda metade da defesa é detecção de reuso. Quando um refresh marcado como "já usado" é apresentado novamente, o servidor sabe que algo está errado — ou alguém está tentando replay, ou houve um problema de sincronização que vale o mesmo tratamento. A reação não é apenas rejeitar a requisição: é invalidar toda a linhagem de refresh tokens que descende daquela cadeia de rotação. O usuário cai; o atacante também. Ambos precisam reautenticar.

Por que invalidar tudo, em vez de apenas rejeitar o token reusado? Porque, no instante em que um refresh aparece duas vezes, pelo menos uma das duas partes apresentando o token é maliciosa — e sem mais informações, é impossível distinguir qual. A resposta defensiva é assumir o pior e cortar a cadeia inteira. O custo é uma reautenticação ocasional para o usuário legítimo. O ganho é eliminar a janela em que o atacante pode operar silenciosamente.

# Famílias de refresh tokens

O conceito formal que organiza a detecção é o de família: cada login cria uma família nova (identificada por um familyId UUID), e cada rotação emite um novo refresh dentro da mesma família. Famílias são o equivalente lógico de "sessões": uma família = um dispositivo logado. Logout deste dispositivo invalida a família; reuso detectado também invalida a família.

Múltiplos dispositivos do mesmo usuário viram múltiplas famílias independentes. Logout no celular não derruba a sessão do laptop. Detecção de reuso no celular não derruba o laptop. Cada família tem seu ciclo de vida próprio, e o usuário enxerga isso como "minhas sessões ativas" no painel da conta.

schema.ts
import { pgTable, text, timestamp, uuid } from 'drizzle-orm/pg-core'
import { users } from './users'

export const refreshTokens = pgTable('refresh_tokens', {
  // Armazenamos o HASH do token, não o token em si — defesa em profundidade
  id: text('id').primaryKey(),

  // Linhagem: todos os refreshes de uma sessão compartilham familyId
  familyId: uuid('family_id').notNull(),

  userId: uuid('user_id')
    .notNull()
    .references(() => users.id, { onDelete: 'cascade' }),

  expiresAt: timestamp('expires_at', { withTimezone: true }).notNull(),

  // null = token ainda corrente; data = token já rotacionado (sinal de reuso)
  usedAt: timestamp('used_at', { withTimezone: true }),

  createdAt: timestamp('created_at', { withTimezone: true })
    .defaultNow()
    .notNull(),
})

// Índices recomendados (no migration, fora do schema declarativo):
//   CREATE INDEX ON refresh_tokens (family_id);
//   CREATE INDEX ON refresh_tokens (user_id, expires_at);

Note três decisões deliberadas no schema. Primeiro, id é o hash do refresh token, não o token cru — em caso de vazamento do banco, o atacante recebe hashes inúteis. Segundo, familyId é independente do id, permitindo deleção em cascata da família inteira sem afetar outras sessões. Terceiro, usedAt não é booleano: o timestamp permite ordenação de eventos e auditoria forense em incidentes.

Rotação sem detecção é apenas teatro
Rotação reduz a janela de uso de cada refresh individual; detecção de reuso fecha o ciclo. Sozinhas, elas são desbalanceadas: rotação sem detecção rejeita apresentações duplicadas mas não invalida o token novo que o atacante já obteve, permitindo acesso silencioso pelo TTL do refresh. Detecção sem rotação não tem nada para detectar. Ambas precisam estar implementadas para o modelo entregar a propriedade de segurança que justifica sua complexidade.

# Implementação: login, refresh e logout

O login emite o primeiro par e cria a família. O fluxo de refresh é onde a lógica concentra: lookup do token, checagem de reuso, rotação, emissão do novo par. O logout apaga a família inteira. Os três caminhos compartilham helpers de hashing e geração de token.

  const familyId = randomUUID()

refresh.ts
// === REFRESH: rotação + detecção de reuso ===
export async function refresh(presented: string) {
  const tokenHash = hashToken(presented)

  const [stored] = await db
    .select()
    .from(refreshTokens)
    .where(eq(refreshTokens.id, tokenHash))
    .limit(1)

  // Não existe — token forjado ou já purgado por reuso anterior
  if (!stored) return null

  // Expirado naturalmente — limpa e rejeita
  if (stored.expiresAt < new Date()) {
    await db.delete(refreshTokens).where(eq(refreshTokens.id, tokenHash))
    return null
  }

  // REUSO DETECTADO: este token já foi rotacionado antes
  if (stored.usedAt !== null) {
    // Mata a família inteira — atacante e usuário caem juntos
    await db.delete(refreshTokens)
      .where(eq(refreshTokens.familyId, stored.familyId))
    return null
  }

  // Marca o token atual como usado e emite o sucessor na mesma família
  await db.update(refreshTokens)
    .set({ usedAt: new Date() })
    .where(eq(refreshTokens.id, tokenHash))

  const newRefresh = randomBytes(32).toString('base64url')
  await db.insert(refreshTokens).values({
    id: hashToken(newRefresh),
    familyId: stored.familyId,
    userId: stored.userId,
    expiresAt: new Date(Date.now() + REFRESH_TTL_MS),
  })

  return {
    accessToken: await issueAccessToken(stored.userId),
    refreshToken: newRefresh,
  }
}

// === LOGOUT: deleta a família inteira deste dispositivo ===
export async function logout(presented: string) {
  const tokenHash = hashToken(presented)

  const [stored] = await db
    .select({ familyId: refreshTokens.familyId })
    .from(refreshTokens)
    .where(eq(refreshTokens.id, tokenHash))
    .limit(1)

  if (stored) {
    await db.delete(refreshTokens)
      .where(eq(refreshTokens.familyId, stored.familyId))
  }
  // Access token segue válido até expirar (≤15min) — aceitar a janela
}

// === LOGOUT GLOBAL: troca de senha, comprometimento, "sair de todos" ===
export async function logoutAllDevices(userId: string) {
  await db.delete(refreshTokens)
    .where(eq(refreshTokens.userId, userId))
}
Hash o refresh antes de gravar
O token devolvido ao cliente é a string aleatória crua de 32 bytes; o que vai para o banco é SHA-256 dessa string. Em caso de vazamento do banco (SQL injection, backup mal protegido, leitura indevida), o atacante recebe hashes que não podem ser apresentados como tokens — o lookup em refresh e logout aplica o mesmo hash sobre o que o cliente envia, então a verificação continua funcionando. Custo zero, ganho material.

# Edge cases: race conditions e retries

O caso mais comum de falso positivo em detecção de reuso vem de race conditions do cliente. Um usuário com duas abas abertas pode disparar dois refreshes quase simultâneos — ambos com o mesmo token, ambos chegando antes do usedAt ser atualizado. Sob lock pessimista no Postgres ou transação serializável, apenas um vence; o outro vê usedAt definido e dispara o alarme. Sem proteção, mata a família por nada.

Duas técnicas mitigam. A primeira é janela de carência: aceitar o token como válido se usedAt foi setado nos últimos poucos segundos (5 a 30, dependendo do caso). Nesse intervalo, devolver os mesmos tokens novos emitidos pela primeira chamada — o que exige guardá-los, geralmente em coluna adicional nextHash. A segunda é coordenação no cliente: bibliotecas de auth como Auth.js e Better Auth implementam uma fila local para que múltiplas chamadas concorrentes a /refresh sejam coalescidas em uma só.

Carência sem complacência
A janela de carência (alguns segundos de tolerância em usedAt) precisa ser curta. 5 a 30 segundos cobre praticamente todos os retries legítimos por race ou rede. Janela mais longa cobre mais cenários de UX, mas amplia a janela em que um atacante pode reusar um token "logo após" o legítimo. O padrão defensivo é não ter carência nenhuma (rejeitar e matar a família ao primeiro reuso) e aceitar a reautenticação ocasional como custo justo da garantia.

Capítulo 11

Validação de tokens com Zod

O Volume XII fechou com um TokenPayload construído em Zod e um z.jwt() que valida formato. O que ficou pendente é a integração com jose: após jwtVerify confirmar a assinatura, o payload devolvido é JWTPayload — tipagem larga, quase tudo unknown. Zod entra nesse ponto para estreitar o tipo, validar as claims customizadas e tornar o payload seguro para o TypeScript consumir sem type assertions manuais.

# Por que Zod além do jwtVerify

jwtVerify cuida do que é criptográfico: confere a assinatura, valida exp, iss e aud, rejeita algoritmos não declarados. O que ele não faz é validar a forma do payload — se as claims customizadas existem, se têm os tipos certos, se role está em uma lista conhecida. Um token que passa em jwtVerify com role: 'superadmin' não existe no sistema teria payload criptograficamente válido mas semanticamente inválido, e o TypeScript não avisaria porque o tipo resultante é JWTPayload com campos unknown.

Zod fecha essa segunda camada: valida a forma do payload e estreita o tipo de uma vez. O resultado é que, depois do middleware, o handler recebe um payload totalmente tipado — payload.role é 'user' | 'admin', não unknown — e qualquer divergência entre o token emitido e o schema da aplicação é capturada em runtime, não silenciada.

# z.jwt(): formato sem assinatura

O refinamento z.jwt(), introduzido no Capítulo 11 do Volume XII, verifica se uma string tem o formato JWT bem formado: três segmentos separados por ponto, cada um decodificável como base64url válida. Não toca na assinatura, não consulta chave alguma. É útil para validar strings de entrada antes de tentar a verificação criptográfica — rejeitar no ponto de entrada um token claramente malformado antes de chegar ao overhead do jwtVerify.

format-check.ts
import { z } from 'zod'

// z.jwt() valida FORMATO — três segmentos base64url bem formados
// Não valida assinatura, expiração nem claims
const BearerInput = z.object({
  authorization: z.string().regex(/^Bearer /).transform(v => v.slice(7)).pipe(z.jwt()),
})

const result = BearerInput.safeParse({
  authorization: c.req.header('authorization'),
})

if (!result.success) {
  return c.json({ code: 'BAD_REQUEST' }, 400)
}

// result.data.authorization é agora o token sem "Bearer " — formato garantido
// Próximo passo: jwtVerify para validar assinatura

z.jwt() e jwtVerify são complementares
z.jwt() filtra lixo na entrada — strings vazias, tokens truncados, valores que não são JWT de forma alguma — antes de pagar o custo criptográfico do jwtVerify. Mas não é substituto: um JWT perfeitamente formado com assinatura forjada passa em z.jwt() e falha em jwtVerify. A ordem correta é sempre z.jwt() opcional → jwtVerify obrigatório → Zod payload schema.

# Schema do payload: claims registradas e customizadas

A primeira etapa é definir o schema Zod que representa o payload esperado da aplicação. Claims registradas têm tipos naturais: sub e jti são strings (UUIDs), exp, iat e nbf são timestamps Unix em segundos. Claims customizadas recebem as restrições da aplicação — role como z.enum garante que nenhum valor fora do conjunto chegue ao handler.

token-schema.ts
import { z } from 'zod'

const RegisteredClaims = z.object({
  sub: z.string().uuid(),                  // userId
  iss: z.string().url(),                   // issuer
  aud: z.string(),                          // audience
  iat: z.number().int().positive(),        // issued at (Unix s)
  exp: z.number().int().positive(),        // expiration (Unix s)
  jti: z.string().uuid(),                  // JWT ID único
})

const CustomClaims = z.object({
  role: z.enum(['user', 'admin']),
  email: z.string().email(),
})

export const AppTokenPayload = RegisteredClaims.merge(CustomClaims)
export type AppTokenPayload = z.infer<typeof AppTokenPayload>

Separar RegisteredClaims de CustomClaims em schemas distintos e combiná-los com merge facilita reuso — o schema de claims registradas pode ser compartilhado entre tokens de access e tokens de outros contextos (webhooks, emails de verificação) que têm claims customizadas diferentes mas o mesmo conjunto de campos padrão.

# A cadeia completa no middleware

O middleware de autenticação encadeia as três etapas em ordem estrita: jwtVerify primeiro (nunca parseie Zod em payload não verificado), safeParse depois, e por fim injeção no contexto. Erros em cada etapa têm semântica diferente e podem ser reportados separadamente ao cliente quando conveniente.

auth-middleware.ts
import { jwtVerify, JWTExpired } from 'jose'
import { AppTokenPayload } from './token-schema'

app.use('*', async (c, next) => {
  const raw = c.req.header('authorization')
  const token = raw?.startsWith('Bearer ') ? raw.slice(7) : null
  if (!token) return c.json({ code: 'UNAUTHENTICATED' }, 401)

  // Passo 1: jose confirma assinatura, exp, iss, aud
  let rawPayload: unknown
  try {
    const { payload } = await jwtVerify(token, publicKey, {
      algorithms: ['EdDSA'],
      issuer:     'https://api.exemplo.com',
      audience:   'api.exemplo.com',
    })
    rawPayload = payload
  } catch (err) {
    const code = err instanceof JWTExpired ? 'TOKEN_EXPIRED' : 'UNAUTHENTICATED'
    return c.json({ code }, 401)
  }

  // Passo 2: Zod valida forma e estreita o tipo
  const parsed = AppTokenPayload.safeParse(rawPayload)
  if (!parsed.success) {
    // Assinatura válida, mas payload não bate com o schema — token antigo?
    return c.json({ code: 'UNAUTHENTICATED' }, 401)
  }

  c.set('userId', parsed.data.sub)
  c.set('tokenPayload', parsed.data)
  await next()
})
Sempre jwtVerify antes do safeParse
Nunca passe para o Zod um payload extraído de um token não verificado. Um atacante pode construir um token com qualquer payload, e z.jwt() mais safeParse aceitariam — o Zod não sabe se a assinatura é válida. A sequência obrigatória é: jwtVerify primeiro (garante autenticidade), safeParse depois (garante forma e tipo). Inverter ou omitir o primeiro elimina toda a proteção criptográfica.

# Tratamento de erros: discriminando falhas

Falhas no pipeline de verificação têm origens diferentes e merecem respostas diferentes. Um token expirado é condição normal de operação — o cliente deve tentar o refresh. Um token com assinatura inválida é potencialmente malicioso. Um token com payload de shape errado pode ser um token legítimo emitido por uma versão antiga do sistema. Discriminar esses casos nos logs (mesmo que a resposta HTTP seja sempre 401) ajuda a identificar problemas antes que escalem.

error-handling.ts
import {
  JWTExpired,
  JWTClaimValidationFailed,
  JWTInvalid,
  JOSEAlgNotAllowed,
} from 'jose'

try {
  const { payload } = await jwtVerify(token, publicKey, {
    algorithms: ['EdDSA'],
  })
  // Continua para Zod parse...
} catch (err) {
  if (err instanceof JWTExpired) {
    // Condição normal — cliente deve usar o refresh token
    return c.json({ code: 'TOKEN_EXPIRED' }, 401)
  }
  if (err instanceof JWTClaimValidationFailed) {
    // Assinatura OK, mas iss/aud/nbf inválidos — token de outro contexto?
    return c.json({ code: 'TOKEN_INVALID_CLAIM' }, 401)
  }
  if (err instanceof JOSEAlgNotAllowed) {
    // Tentativa de algorithm confusion — logar como alerta
    console.warn('Algorithm confusion attempt detected', { token })
    return c.json({ code: 'UNAUTHENTICATED' }, 401)
  }
  // JWTInvalid, JWTMalformed, erro de chave — genérico por segurança
  return c.json({ code: 'UNAUTHENTICATED' }, 401)
}
z.enum para roles habilita narrowing
Definir role como z.enum(['user', 'admin']) em vez de z.string() tem duas consequências práticas. Primeiro, tokens com role fora do conjunto são rejeitados em runtime — proteção contra tokens fabricados ou emitidos por versão antiga. Segundo, o TypeScript infere payload.role como 'user' | 'admin', e narrowing com if (payload.role === 'admin') funciona sem type assertions. Isso se estende para discriminated unions do Cap 7 do Vol XII — um schema de payload pode usar z.discriminatedUnion('role', [...]) para payloads estruturalmente diferentes por papel.

OAuth 2.0 e PKCE

Os primeiros onze capítulos trataram autenticação como algo que a aplicação implementa de ponta a ponta: usuário cria conta, define senha, recebe sessão ou token, faz logout. OAuth 2.0 introduz um modelo diferente — a aplicação delega a verificação de identidade a um provedor externo (Google, GitHub, Active Directory corporativo) e recebe de volta uma autorização limitada e contextualizada. Este capítulo desconstrói o protocolo: as quatro partes envolvidas, o fluxo Authorization Code com PKCE (o único fluxo recomendado em 2026), as proteções de state e nonce, e por que tantos outros fluxos foram descontinuados nas atualizações recentes da especificação.

# OAuth é delegação, não autenticação

O ponto que mais gera confusão sobre OAuth: ele não foi feito para login. Foi feito para que um usuário pudesse permitir que uma aplicação acesse um recurso protegido em nome dele — sem entregar a senha. O exemplo histórico clássico é a Twitter API: o usuário queria deixar um cliente de terceiros postar em sua conta sem dar a senha do Twitter para o cliente. OAuth resolveu isso: o usuário se autentica no Twitter, autoriza o cliente a postar em seu nome, e o Twitter emite um token específico para esse acesso delegado.

"Login com Google" usa OAuth como mecanismo de transporte porque o fluxo é conveniente — redireciona, faz consent, devolve algo — mas o que de fato faz autenticação nesse caso é uma camada construída por cima de OAuth: OpenID Connect (OIDC), assunto do Capítulo 13. A distinção importa porque um access token de OAuth diz "este token autoriza acesso a estes recursos" — não diz quem é o usuário. Confundir os dois leva à classe de vulnerabilidades onde aplicações usam o userId retornado pelo endpoint /userinfo do OAuth como se fosse identidade verificada, sem perceber que o provedor original do token pode não ser o que a aplicação espera.

# As quatro partes

OAuth 2.0 (RFC 6749) define quatro papéis. Resource Owner é a pessoa dona dos dados — a usuária Maria. Client é a aplicação que quer acessar dados em nome dela — uma app de tarefas que quer ler o calendário do Google. Authorization Server é quem autentica a Maria e emite tokens — o servidor do Google que cuida do consentimento. Resource Server é quem expõe os dados protegidos — a Google Calendar API. Em muitos provedores, AS e RS são o mesmo serviço.

Há ainda uma distinção entre dois tipos de cliente. Confidential clients são aplicações server-side que conseguem guardar um client_secret em segredo — um backend Node que faz a troca de code por token. Public clients são SPAs, apps mobile e desktop — não há como guardar segredo no código que roda no dispositivo do usuário. A distinção mudava radicalmente o fluxo recomendado até OAuth 2.0; em OAuth 2.1, com PKCE obrigatório para todos, a diferença ficou menor.

# Authorization Code Flow: passo a passo

O fluxo Authorization Code, com PKCE, é o único recomendado pela especificação OAuth 2.1 (publicada em 2023). Funciona em cinco etapas: o cliente redireciona o usuário para o Authorization Server, o usuário se autentica e dá consentimento, o AS redireciona de volta com um code, o cliente troca o code por tokens, e usa os tokens para acessar a Resource Server.

O detalhe que define a segurança do fluxo: o code que volta na URL é apenas um marcador temporário. Quem possui o code não consegue trocá-lo por tokens — para isso é preciso apresentar o code_verifier que só o cliente original conhece. Sem PKCE, o code era todo o segredo; com PKCE, o code virou referência, e o verifier é o segredo.

# PKCE: o segredo que só o cliente original tem

PKCE (Proof Key for Code Exchange, RFC 7636) protege contra interceptação do code. O cenário de ameaça: um app malicioso registra o mesmo URL scheme do app legítimo num dispositivo móvel; um proxy corporativo grava URLs em log; uma extensão de navegador comprometida vê o redirect. Em qualquer desses casos, sem PKCE, capturar o code basta para trocar por tokens. Com PKCE, ter o code não adianta — sem o verifier, o /token rejeita.

pkce.ts
import { randomBytes, createHash } from 'node:crypto'

// code_verifier: 43-128 caracteres URL-safe, alta entropia
export function generateCodeVerifier(): string {
  return randomBytes(32).toString('base64url')  // 43 chars
}

// code_challenge: SHA-256 do verifier, em base64url
// Apenas o challenge é enviado no /authorize — o verifier fica no cliente
export function codeChallengeS256(verifier: string): string {
  return createHash('sha256').update(verifier).digest('base64url')
}

// O AS guarda o challenge associado ao code emitido.
// No /token, o cliente apresenta o verifier original.
// AS verifica: SHA-256(verifier) === challenge → libera os tokens.

O método S256 (SHA-256) é o único recomendado em 2026. Existe um modo plain onde challenge = verifier (sem hash), mantido na especificação apenas para compatibilidade com clientes muito antigos. Em qualquer implementação nova, use S256 e rejeite plain — o ganho do PKCE depende de o challenge ser uma derivação irreversível.

# State e nonce: CSRF e replay no fluxo OAuth

Dois parâmetros adicionais protegem o fluxo contra ataques que PKCE não cobre. O state é um valor aleatório que o cliente envia no /authorize e que o AS reflete de volta no callback. O cliente verifica que o state recebido é exatamente o que enviou — se não bate, o fluxo é abortado. Sem state, um atacante pode iniciar um fluxo OAuth na conta dele, copiar o code, e fazer a vítima clicar em uma URL de callback contendo esse code; a vítima acaba "logada" como o atacante. State é CSRF protection para o fluxo OAuth.

O nonce é específico do OIDC (volta no Cap 13): um valor que o cliente envia no /authorize e que o AS embute no id_token. Quando o cliente recebe o id_token, verifica que o nonce dentro dele bate com o que enviou. Protege contra replay de id_tokens — alguém não consegue reusar um id_token capturado em outra sessão.

authorize-handler.ts
import { randomBytes } from 'node:crypto'
import { generateCodeVerifier, codeChallengeS256 } from './pkce'

const CLIENT_ID    = process.env.GOOGLE_CLIENT_ID!
const REDIRECT_URI = 'https://app.exemplo.com/auth/callback'

// Inicia o fluxo: redireciona o usuário para o Google
app.get('/auth/login', async (c) => {
  const codeVerifier = generateCodeVerifier()
  const state        = randomBytes(16).toString('base64url')

  // Guarda os valores temporariamente, indexados por state
  await sessionStore.set(`oauth:${state}`, {
    codeVerifier,
    returnTo: c.req.query('returnTo') ?? '/',
  }, { ttlSeconds: 600 })  // 10 min para completar o fluxo

  const url = new URL('https://accounts.google.com/o/oauth2/v2/auth')
  url.searchParams.set('client_id',             CLIENT_ID)
  url.searchParams.set('redirect_uri',          REDIRECT_URI)
  url.searchParams.set('response_type',         'code')
  url.searchParams.set('scope',                 'openid email profile')
  url.searchParams.set('state',                 state)
  url.searchParams.set('code_challenge',        codeChallengeS256(codeVerifier))
  url.searchParams.set('code_challenge_method', 'S256')

  return c.redirect(url.toString())
})

# Troca de code por tokens

Quando o usuário termina a autenticação no Google e dá consentimento, o AS redireciona para o redirect_uri registrado com dois parâmetros: code e state. O handler de callback faz três coisas em ordem: confirma que o state é o esperado (CSRF), recupera o code_verifier guardado na sessão temporária, e faz o POST para o /token do AS trocando o code pelos tokens reais.

callback-handler.ts
const CLIENT_SECRET = process.env.GOOGLE_CLIENT_SECRET!

app.get('/auth/callback', async (c) => {
  const code  = c.req.query('code')
  const state = c.req.query('state')
  if (!code || !state) return c.json({ code: 'BAD_REQUEST' }, 400)

  // Verifica que o state existe e ainda está pendente
  const pending = await sessionStore.get(`oauth:${state}`)
  if (!pending) return c.json({ code: 'OAUTH_STATE_INVALID' }, 400)
  await sessionStore.delete(`oauth:${state}`)  // usa uma vez só

  // POST /token — troca code + verifier por tokens reais
  const body = new URLSearchParams({
    grant_type:    'authorization_code',
    code,
    code_verifier: pending.codeVerifier,
    redirect_uri:  REDIRECT_URI,
    client_id:     CLIENT_ID,
    client_secret: CLIENT_SECRET,    // só em confidential clients
  })

  const resp = await fetch('https://oauth2.googleapis.com/token', {
    method:  'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body,
  })

  if (!resp.ok) return c.json({ code: 'OAUTH_EXCHANGE_FAILED' }, 401)
  const tokens = await resp.json()

})

O response do /token retorna access_token (e refresh_token se o scope incluir offline_access) prontos para serem usados em chamadas à Resource Server. Se o scope incluiu openid, também volta um id_token — esse é o objeto do OIDC, detalhado no próximo capítulo. A partir do callback, a aplicação tipicamente cria uma sessão local própria (com o session ou refresh token dos Capítulos 5–10) e armazena o access token do provedor para chamadas futuras à API externa.

# Por que outros fluxos morreram

OAuth 2.0 original (2012) definia cinco fluxos. OAuth 2.1 (2023) reduziu a dois: Authorization Code com PKCE para fluxos com usuário, e Client Credentials para máquina-a-máquina. Os outros três foram explicitamente removidos por terem vulnerabilidades estruturais que não dá para mitigar.

O Implicit Flow devolvia os tokens diretamente no fragment da URL (#access_token=...) em vez do code. O motivo histórico: SPAs não conseguiam fazer POST /token com client_secret. O problema: o token aparecia no browser history, em logs de servidores intermediários, em referrer headers, e em qualquer lugar onde a URL era armazenada. PKCE eliminou a justificativa para Implicit — SPAs hoje usam Authorization Code com PKCE como qualquer outro cliente.

O Resource Owner Password Credentials Flow (ROPC) coletava a senha do usuário diretamente no cliente. Era usado em apps mobile early days "para evitar redirect". Mas ele quebra o ponto inteiro do OAuth: o cliente passa a ter a senha do usuário, o que destrói a delegação. ROPC foi removido em OAuth 2.1.

O Authorization Code sem PKCE ainda existe formalmente para confidential clients tradicionais, mas a recomendação OWASP e OAuth 2.1 é que todos os clientes — públicos ou confidenciais — usem PKCE. Não há custo significativo e fecha uma classe de ataque. Em código novo, não há razão para pular.

Implicit Flow está oficialmente morto
Se algum SDK ou tutorial antigo ainda recomenda Implicit Flow (response_type=token em vez de response_type=code), ignore. A OAuth 2.1 (2023) o removeu da especificação e a OWASP recomenda explicitamente não implementar. Provedores modernos como Auth0, Okta e Cognito já marcaram Implicit como deprecated; alguns nem oferecem mais. Para SPAs, o padrão correto é Authorization Code com PKCE, exatamente como para qualquer outro cliente.
OAuth versus OIDC
OAuth 2.0 é sobre autorização — emitir tokens que permitem acesso a recursos. Não foi feito para login. OpenID Connect é uma camada que foi feita para login, construída em cima de OAuth: usa o mesmo fluxo Authorization Code, mas adiciona um id_token (JWT contendo identidade do usuário) e endpoints padrão de descoberta (/.well-known/openid-configuration) e de informação do usuário (/userinfo). Capítulo 13

OpenID Connect identidade sobre OAuth

O Capítulo 12 terminou com uma advertência: OAuth 2.0 autoriza acesso a recursos, não prova quem é o usuário. Um access token diz "o portador deste token pode ler o calendário de alguém" — não diz de quem. OpenID Connect (OIDC) é a camada de autenticação construída por cima de OAuth justamente para fechar essa lacuna. Ele padroniza um segundo token — o id_token, um JWT assinado pelo provedor — que carrega a identidade verificada do usuário em claims previsíveis. Este capítulo mostra como OIDC reaproveita o fluxo Authorization Code + PKCE do Cap 12, o que o id_token contém e como validá-lo corretamente, o papel da descoberta automática via /.well-known/openid-configuration, e como openid-client@6.8.4 encadeia tudo isso de forma segura.

# O que OIDC adiciona ao OAuth

OIDC não substitui OAuth — ele é um perfil de OAuth 2.0. O mesmo redirect para /authorize, o mesmo code exchange no /token, o mesmo PKCE. A diferença começa no escopo: ao incluir openid na lista de scopes, o cliente sinaliza ao provedor "além de autorizar acesso, quero uma asserção de identidade". O provedor responde, no token endpoint, com um campo extra ao lado do access_token: o id_token.

Essa é a separação conceitual que organiza todo o capítulo. O access token é opaco para o cliente — destina-se ao resource server, que o valida e decide o que liberar. O id_token é destinado ao cliente: é um JWT (Cap 8) que o próprio cliente abre, valida e lê para saber quem fez login. OAuth pergunta "o que este token pode acessar?"; OIDC responde "quem é este usuário?". Tratar um access token como se fosse prova de identidade — abrir o /userinfo e confiar no sub sem validar a origem — é a vulnerabilidade que o Cap 12 antecipou e que OIDC existe para eliminar.

authN vs authZ, de novo
O Capítulo 1 separou autenticação (quem você é) de autorização (o que você pode). OAuth e OIDC encarnam essa divisão em protocolos distintos sobre o mesmo fluxo: OAuth carrega autorização (access token), OIDC carrega autenticação (id_token). "Login social" — Cap 14 — é, na prática, OIDC usado para autenticar. Quando alguém diz que faz "login com OAuth", quase sempre quer dizer OIDC.

# Anatomia do id_token

O id_token é um JWT assinado (JWS) cujo payload segue claims padronizadas pela especificação OIDC. Diferente de um access token — que cada provedor formata como quiser — o conteúdo do id_token é previsível entre provedores, o que permite validá-lo com um único conjunto de regras.

id-token-claims.ts
// Payload decodificado de um id_token (claims OIDC padronizadas)
interface IdTokenClaims {
  iss: string      // Issuer: URL do provedor. DEVE bater com o esperado
  sub: string      // Subject: ID estável e único do usuário NESTE provedor
  aud: string      // Audience: seu client_id. DEVE ser o seu
  exp: number      // Expiração (Unix). Token vencido = rejeitar
  iat: number      // Emitido em (Unix)
  nonce?: string   // Eco do nonce enviado no /authorize (anti-replay, Cap 12)
  // Claims de perfil (dependem dos scopes pedidos)
  email?: string
  email_verified?: boolean
  name?: string
  picture?: string
}

// REGRA DE OURO: a identidade do usuário é (iss, sub) — nunca sub sozinho.
// O mesmo sub pode existir em provedores diferentes; só o par é único.
function userKey(claims: IdTokenClaims): string {
  return `${claims.iss}|${claims.sub}`
}

O sub (subject) é o identificador estável do usuário dentro daquele provedor. Ele não muda quando o usuário troca o e-mail ou o nome, o que o torna a chave correta para relacionar a conta externa com a conta local — assunto central do Cap 14. O erro recorrente é usar o email como chave de identidade: e-mails mudam de dono, podem não estar verificados (email_verified: false) e nem todo provedor garante unicidade. O par (iss, sub) é o que a especificação garante imutável e único.

# Descoberta: /.well-known/openid-configuration

Cada provedor OIDC publica um documento de metadados num caminho fixo: {issuer}/.well-known/openid-configuration. Esse JSON lista todos os endpoints e capacidades do provedor — token endpoint, authorization endpoint, o jwks_uri com as chaves públicas de assinatura, os algoritmos suportados. Em vez de codificar URLs à mão (que mudam e quebram), o cliente descobre tudo em runtime a partir de uma única URL: a do issuer.

  "issuer": "https://accounts.google.com",
  "authorization_endpoint": "https://accounts.google.com/o/oauth2/v2/auth",
  "token_endpoint": "https://oauth2.googleapis.com/token",
  "userinfo_endpoint": "https://openidconnect.googleapis.com/v1/userinfo",
  "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
  "id_token_signing_alg_values_supported": ["RS256"],
  "scopes_supported": ["openid", "email", "profile"]
}

O jwks_uri é o ponto que torna a validação de assinatura possível sem segredos compartilhados. O provedor assina o id_token com sua chave privada (RS256 ou ES256); o cliente busca o conjunto de chaves públicas (JWKS) nessa URL e verifica a assinatura. As chaves rotacionam periodicamente, então o cliente nunca as fixa — sempre as resolve a partir do jwks_uri, com cache respeitando os headers HTTP. O Cap 9 introduziu JWKS para tokens próprios; aqui o mesmo mecanismo valida tokens de terceiros.

Nunca confie num id_token sem validar a assinatura
Um JWT é apenas base64 — qualquer um forja um payload com sub de administrador. A segurança vem inteiramente de: (1) verificar a assinatura contra a chave pública do jwks_uri, (2) conferir iss, aud, exp e nonce. Pular qualquer um desses passos transforma "login com Google" numa porta destrancada. Use uma biblioteca que faça todos eles — não decodifique o id_token à mão.

# Validando o id_token

A validação tem uma ordem que importa. Primeiro a assinatura — sem ela, nada no payload é confiável. Depois as claims de segurança, cada uma fechando um vetor de ataque específico.

validate-id-token.ts
import { jwtVerify, createRemoteJWKSet } from 'jose'

// JWKS remoto com cache automático (jose@6.2.3) — resolve a rotação de chaves
const JWKS = createRemoteJWKSet(
  new URL('https://www.googleapis.com/oauth2/v3/certs'),
)

async function validateIdToken(
  idToken: string,
  expectedNonce: string,
): Promise<IdTokenClaims> {
  const { payload } = await jwtVerify(idToken, JWKS, {
    // iss e aud validados pela própria jose — falha lança erro
    issuer: 'https://accounts.google.com',
    audience: process.env.GOOGLE_CLIENT_ID!,
    // exp e nbf checados automaticamente; só RS256 aceito
    algorithms: ['RS256'],
  })

  // nonce: defesa anti-replay. Deve bater com o gerado no /authorize (Cap 12)
  if (payload.nonce !== expectedNonce) {
    throw new Error('nonce inválido — possível replay')
  }

  return payload as IdTokenClaims
}

Cada checagem mapeia um ataque. O iss impede que um token de outro provedor (ou de um issuer malicioso) seja aceito. O aud garante que o token foi emitido para este cliente — um token legítimo destinado a outra aplicação não vale aqui. O exp limita a janela de uso. E o nonce, gerado no início do fluxo e ecoado pelo provedor dentro do id_token, prova que esta resposta corresponde à requisição que este cliente iniciou — bloqueando replay de um id_token capturado. O nonce protege o id_token assim como o state protege o callback de OAuth: são defesas complementares, não intercambiáveis.

# openid-client: o fluxo completo

A openid-client@6.8.4 é a biblioteca de referência para OIDC em Node. Ela faz a descoberta, monta a URL de autorização com PKCE + state + nonce, troca o code e — crucialmente — valida o id_token de ponta a ponta, incluindo a verificação de assinatura via JWKS e de todas as claims. É a opção certa quando o provedor é totalmente compatível com OIDC; arctic (Cap 12/14) cobre provedores OAuth puros ou com peculiaridades.

oidc-flow.ts
import * as client from 'openid-client'

// 1. Descoberta: resolve todos os endpoints a partir do issuer
const config = await client.discovery(
  new URL('https://accounts.google.com'),
  process.env.GOOGLE_CLIENT_ID!,
  process.env.GOOGLE_CLIENT_SECRET!,
)

// 2. Início do login — gerar e guardar verifier, state e nonce na sessão
function buildAuthUrl() {
  const codeVerifier = client.randomPKCECodeVerifier()
  const state = client.randomState()
  const nonce = client.randomNonce()

  const url = client.buildAuthorizationUrl(config, {
    scope: 'openid email profile',  // 'openid' ativa o id_token
    redirect_uri: 'https://app.exemplo.com/callback',
    code_challenge: await client.calculatePKCECodeChallenge(codeVerifier),
    code_challenge_method: 'S256',
    state,
    nonce,
  })
  return { url, codeVerifier, state, nonce }
}
oidc-callback.ts
// 3. Callback: trocar o code e validar o id_token numa só chamada.
// authorizationCodeGrant valida assinatura, iss, aud, exp e nonce.
async function handleCallback(
  currentUrl: URL,
  saved: { codeVerifier: string; state: string; nonce: string },
) {
  const tokens = await client.authorizationCodeGrant(config, currentUrl, {
    pkceCodeVerifier: saved.codeVerifier,
    expectedState: saved.state,
    expectedNonce: saved.nonce,
  })

  // claims() retorna o payload JÁ validado do id_token
  const claims = tokens.claims()!
  const identity = {
    provider: claims.iss,
    providerId: claims.sub,   // par (iss, sub) = identidade
    email: claims.email as string | undefined,
  }

  // A partir daqui: criar/relacionar conta local e emitir sessão (Cap 14)
  return identity
}

Repare que a validação do id_token não é um passo separado que o desenvolvedor precisa lembrar de fazer — authorizationCodeGrant a executa como parte do grant, recusando o login se a assinatura ou qualquer claim falhar. Esse é o ganho de usar uma biblioteca OIDC certificada em vez de costurar OAuth + decodificação manual de JWT: os passos de segurança ficam no caminho obrigatório, não numa checklist opcional.

# userinfo vs id_token: quando buscar mais

O id_token traz a identidade no momento do login. O endpoint /userinfo — acessado com o access token, não com o id_token — devolve o perfil atualizado do usuário sob demanda. A regra prática: use as claims do id_token para autenticar e estabelecer a sessão; chame /userinfo quando precisar de dados de perfil frescos depois, ou quando o provedor não inclui certas claims no id_token para mantê-lo enxuto.

Capítulo 14

Login social do callback à sessão

Os Capítulos 12 e 13 montaram a maquinaria: OAuth conduz o redirect e o consent, OIDC entrega uma identidade verificada no id_token. Falta a parte que transforma isso num login funcional do seu sistema — o que acontece no callback depois que a identidade externa chega. Este capítulo conecta o ponto: como modelar a tabela accounts que relaciona uma conta externa a um usuário local, como decidir entre criar conta nova, vincular a existente ou recusar, como lidar com o mesmo e-mail vindo de provedores diferentes, e como, ao final, emitir a sessão própria da aplicação (Cap 5) ou o par access/refresh (Cap 10). A identidade do provedor é o ponto de partida; a sessão local é o destino.

# O schema: users e accounts

O erro estrutural mais comum em login social é guardar o googleId direto na tabela users. Funciona para um provedor; quebra no segundo. Quando o mesmo usuário quer entrar com Google e GitHub, ou com Google e senha, a coluna única não comporta. A modelagem correta separa identidade (a pessoa, em users) de credenciais externas (cada vínculo com um provedor, em accounts) — relação um-para-muitos.

schema.ts
import { pgTable, uuid, text, timestamp, unique } from 'drizzle-orm/pg-core'

// A pessoa. Uma linha por usuário, independente de como ele faz login.
export const users = pgTable('users', {
  id: uuid('id').primaryKey().defaultRandom(),
  email: text('email').notNull().unique(),
  name: text('name'),
  passwordHash: text('password_hash'),  // null se só usa login social
  createdAt: timestamp('created_at').defaultNow().notNull(),
})

// Cada vínculo com um provedor externo. N contas por usuário.
export const accounts = pgTable('accounts', {
  id: uuid('id').primaryKey().defaultRandom(),
  userId: uuid('user_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
  provider: text('provider').notNull(),       // 'google', 'github', ...
  providerAccountId: text('provider_account_id').notNull(),  // o 'sub' do Cap 13
  createdAt: timestamp('created_at').defaultNow().notNull(),
}, (t) => [
  // (provider, providerAccountId) é único: um vínculo externo aponta para um usuário
  unique().on(t.provider, t.providerAccountId),
])

A constraint composta (provider, providerAccountId) é o coração do modelo: ela materializa o par (iss, sub) do Cap 13 como chave de busca. Dada uma identidade que volta do provedor, a pergunta "quem é esse usuário no meu sistema?" vira um lookup direto nessa tabela. O passwordHash nullable em users permite que uma conta nascida via Google ganhe senha depois, ou vice-versa — a identidade é uma só, os métodos de acesso são muitos.

# O callback: validar state e trocar o code

O callback é onde o state guardado no cookie é confrontado com o state que volta na query — a defesa CSRF do fluxo OAuth (Cap 12). Só depois disso o code é trocado por tokens.

auth.routes.ts (callback)
auth.get('/google/callback', async (c) => {
  const code = c.req.query('code')
  const state = c.req.query('state')
  const storedState = getCookie(c, 'g_state')
  const verifier = getCookie(c, 'g_verifier')

  // state ausente ou divergente = rejeitar (anti-CSRF)
  if (!code || !state || !storedState || state !== storedState || !verifier) {
    return c.text('Requisição inválida', 400)
  }

  // Troca o code por tokens (arctic valida o PKCE internamente)
  const tokens = await google.validateAuthorizationCode(code, verifier)

  // Google é OIDC: a identidade vem do id_token, validado com jose (Cap 13)
  const claims = await validateIdToken(tokens.idToken())
  const identity = {
    provider: 'google' as const,
    providerAccountId: claims.sub,
    email: claims.email,
    emailVerified: claims.email_verified === true,
    name: claims.name,
  }

  const user = await resolveUser(identity)
  await issueSession(c, user.id)   // Cap 5 ou Cap 10
  return c.redirect('/dashboard')
})

# resolveUser: criar, vincular ou recusar

Esta é a função onde mora a política de identidade da aplicação. Dada a identidade externa, há três caminhos. Primeiro: já existe um account com esse (provider, providerAccountId)? Então o usuário é conhecido — só retorná-lo. Segundo: é a primeira vez desse vínculo, mas já existe um user com o mesmo e-mail verificado? Então vincular a conta externa ao usuário existente (account linking). Terceiro: ninguém conhecido — criar usuário e conta novos.

resolve-user.ts
async function resolveUser(id: Identity): Promise<User> {
  return await db.transaction(async (tx) => {
    // 1. Vínculo já existe? Usuário conhecido.
    const existing = await tx.query.accounts.findFirst({
      where: and(
        eq(accounts.provider, id.provider),
        eq(accounts.providerAccountId, id.providerAccountId),
      ),
      with: { user: true },
    })
    if (existing) return existing.user

    // 2. E-mail verificado bate com um usuário existente? Vincular.
    if (id.emailVerified && id.email) {
      const byEmail = await tx.query.users.findFirst({
        where: eq(users.email, id.email),
      })
      if (byEmail) {
        await tx.insert(accounts).values({
          userId: byEmail.id, provider: id.provider,
          providerAccountId: id.providerAccountId,
        })
        return byEmail
      }
    }

    // 3. Novo usuário + novo vínculo.
    const [created] = await tx.insert(users).values({
      email: id.email!, name: id.name,
    }).returning()
    await tx.insert(accounts).values({
      userId: created.id, provider: id.provider,
      providerAccountId: id.providerAccountId,
    })
    return created
  })
}
Account linking automático só com e-mail verificado
O passo 2 vincula contas pelo e-mail — mas apenas se o provedor afirmar email_verified: true. Sem essa checagem surge uma escalada clássica: um atacante cria conta num provedor usando o e-mail da vítima sem verificá-lo; ao fazer login social, seria vinculado à conta real da vítima. Provedores sérios não emitem email_verified: true para e-mails não confirmados — confie nessa flag, e na sua ausência, force um fluxo de confirmação antes de vincular.

# O mesmo e-mail em provedores diferentes

Maria entra hoje com Google, amanhã com GitHub — mesmo e-mail. Com o modelo acima, o segundo login encontra o usuário pelo e-mail verificado (passo 2) e adiciona um segundo account, sem duplicar a pessoa. Resultado: um user, dois accounts. Da próxima vez, qualquer um dos dois provedores cai direto no passo 1. É exatamente o comportamento que a separação users/accounts foi desenhada para permitir — e que uma coluna googleId em users tornaria impossível.

# Emitir a sessão local

Resolvido o usuário, o login social termina como qualquer outro: a aplicação emite sua própria sessão. Os tokens do provedor já cumpriram o papel — provar a identidade — e não precisam mais circular. A partir daqui é o Cap 5 (sessão opaca com cookie) ou o Cap 10 (par access/refresh), conforme a arquitetura.

issue-session.ts
// Sessão opaca server-side (Cap 5/6): cria registro, devolve cookie httpOnly
async function issueSession(c: Context, userId: string) {
  const token = generateSessionToken()        // 32 bytes aleatórios
  await createSession(token, userId)         // hash do token no store (Cap 6)
  setCookie(c, 'session', token, {
    httpOnly: true, secure: true, sameSite: 'Lax',
    path: '/', maxAge: 60 * 60 * 24 * 30,  // 30 dias
  })
  // limpa os cookies temporários do fluxo OAuth
  deleteCookie(c, 'g_state'); deleteCookie(c, 'g_verifier')
}
Não persista access/refresh tokens do provedor sem motivo
Se a aplicação só quer autenticar, descarte os tokens do provedor após resolver a identidade — guardá-los aumenta a superfície de risco sem ganho. Persista-os (cifrados) apenas se for chamar a API do provedor depois em nome do usuário (ler calendário, repositórios). Nesse caso, a coluna vai em accounts, não em users, e o refresh token merece criptografia em repouso.

Capítulo 15

Magic links e OTP autenticação sem senha

Senhas são o pior dos dois mundos: difíceis de lembrar para humanos, fáceis de adivinhar para máquinas. O login social (Caps 12–14) elimina a senha delegando a identidade a um provedor — mas nem todo usuário quer entrar com Google, e nem toda aplicação quer depender de terceiros. A autenticação passwordless própria resolve isso provando que o usuário controla um canal — o e-mail ou o telefone — em vez de provar que ele memorizou um segredo. Este capítulo cobre os dois formatos: o magic link (um URL de uso único enviado por e-mail) e o OTP (um código numérico curto). Ambos repousam sobre a mesma ideia — um token de verificação efêmero, gerado com node:crypto, guardado como hash e comparado em tempo constante (Cap 2) — e sobre a mesma tabela verification_tokens.

# O modelo: prova de posse de um canal

Autenticação por senha é "prova de conhecimento": você sabe um segredo. Passwordless é "prova de posse": você controla uma caixa de entrada. O fluxo é sempre o mesmo em três tempos. A aplicação gera um token aleatório, guarda o seu hash com prazo de validade e envia o valor original pelo canal do usuário. O usuário, ao receber, devolve o token — clicando no link ou digitando o código. A aplicação procura o hash correspondente, confere que não expirou nem foi usado, e então autentica. O segredo nunca foi memorizado nem reutilizado: nasce, viaja uma vez e morre.

Magic link e OTP são o mesmo mecanismo
A diferença é só de formato de entrega. O magic link embute o token numa URL (/verify?token=...) — zero digitação, mas exige abrir o e-mail no mesmo dispositivo para uma boa UX. O OTP é um código curto (6 dígitos) que o usuário transcreve — funciona entre dispositivos (recebe no celular, digita no desktop) e por SMS, ao custo de menos entropia, o que exige limites de tentativa mais rígidos. Por baixo, ambos são um token efêmero na tabela verification_tokens.

# A tabela verification_tokens

Esta tabela já apareceu no schema estendido do Vol XI. Ela guarda o hash do token — nunca o valor original — junto do identificador do destinatário e do prazo. Guardar o hash significa que um vazamento do banco não entrega tokens utilizáveis, exatamente pela mesma razão que senhas são hasheadas (Cap 2).

schema.ts
import { pgTable, text, timestamp, integer } from 'drizzle-orm/pg-core'

export const verificationTokens = pgTable('verification_tokens', {
  id: text('id').primaryKey(),
  identifier: text('identifier').notNull(),   // e-mail ou telefone alvo
  tokenHash: text('token_hash').notNull(),  // SHA-256 do token — nunca o valor cru
  expiresAt: timestamp('expires_at').notNull(),
  attempts: integer('attempts').notNull().default(0),  // só relevante para OTP
})

Por que SHA-256 aqui e Argon2 nas senhas (Cap 2)? Porque a ameaça é diferente. Senhas têm baixa entropia e vivem por anos, então precisam de um hash deliberadamente lento que frustre força bruta offline. Tokens de verificação têm alta entropia (gerados por CSPRNG) e vivem por minutos — força bruta offline é inviável, e um hash rápido como SHA-256 basta. Usar Argon2 num token de 256 bits seria custo sem benefício.

# Gerando o token com node:crypto

O magic link usa um token de alta entropia — 32 bytes aleatórios em base64url. O OTP usa um código curto e numérico, mas a aleatoriedade precisa ser igualmente forte: randomInt do node:crypto, nunca Math.random(), que é previsível e jamais deve tocar nada de segurança.

tokens.ts
import { randomBytes, randomInt, createHash } from 'node:crypto'

// Magic link: 256 bits de entropia, URL-safe
export function generateMagicToken(): string {
  return randomBytes(32).toString('base64url')
}

// OTP: 6 dígitos. randomInt é uniforme e criptograficamente seguro.
// padStart preserva zeros à esquerda (ex.: '042315').
export function generateOtp(): string {
  return randomInt(0, 1_000_000).toString().padStart(6, '0')
}

// Hash determinístico para guardar e comparar (rápido, alta entropia)
export function hashToken(token: string): string {
  return createHash('sha256').update(token).digest('hex')
}
6 dígitos = 1 em 1 milhão. Sem limite de tentativas, é frágil
Um OTP de 6 dígitos tem só ~20 bits de entropia. Sem trava, um atacante testa o espaço inteiro em minutos. Três defesas obrigatórias: validade curta (5–10 min), limite rígido de tentativas (a coluna attempts; invalidar após 5 erros) e rate limiting por identifier (Cap 19). O magic link, com 256 bits, não precisa de limite de tentativas — adivinhá-lo é computacionalmente impossível — mas ainda se beneficia de validade curta.

# Verificar: comparação timing-safe e consumo

A verificação tem três armadilhas a evitar. Primeiro, a comparação do token deve ser em tempo constante — embora aqui se compare o hash do token recebido contra o hash guardado, usar timingSafeEqual (Cap 2) mantém a disciplina e protege contra vazamentos de timing. Segundo, o token é de uso único: deve ser deletado assim que validado, dentro da mesma transação, para impedir replay. Terceiro, expiração e tentativas são verificadas antes de autenticar.

verify.ts
import { timingSafeEqual } from 'node:crypto'

// Compara dois hex de mesmo tamanho em tempo constante
function safeEqual(a: string, b: string): boolean {
  const ba = Buffer.from(a), bb = Buffer.from(b)
  return ba.length === bb.length && timingSafeEqual(ba, bb)
}

app.get('/auth/verify', async (c) => {
  const token = c.req.query('token')
  if (!token) return c.text('Token ausente', 400)
  const hash = hashToken(token)

  const user = await db.transaction(async (tx) => {
    const row = await tx.query.verificationTokens.findFirst({
      where: eq(verificationTokens.tokenHash, hash),
    })
    // inexistente, expirado ou divergente → falha uniforme
    if (!row || row.expiresAt < new Date() || !safeEqual(row.tokenHash, hash)) {
      return null
    }
    // uso único: consome o token na mesma transação (anti-replay)
    await tx.delete(verificationTokens).where(eq(verificationTokens.id, row.id))
    // upsert: cria a conta no primeiro login, ou recupera a existente
    return await upsertUserByEmail(tx, row.identifier)
  })

  if (!user) return c.text('Link inválido ou expirado', 400)
  await issueSession(c, user.id)   // Cap 5/10, igual ao login social
  return c.redirect('/dashboard')
})

# A variação OTP: tentativas e bloqueio

O fluxo OTP é idêntico no envio, mas a verificação incrementa attempts a cada palpite errado e invalida o token ao estourar o limite. Como o usuário digita o código (em vez de clicar num link), a busca não pode ser pelo hash do token sozinho — é pelo identifier, e então compara-se o hash do código informado.

verify-otp.ts
const MAX_ATTEMPTS = 5

app.post('/auth/otp/verify', async (c) => {
  const { email, code } = await c.req.json<{ email: string; code: string }>()

  const user = await db.transaction(async (tx) => {
    const row = await tx.query.verificationTokens.findFirst({
      where: eq(verificationTokens.identifier, email),
    })
    if (!row || row.expiresAt < new Date()) return null

    // limite estourado: queima o token e recusa
    if (row.attempts >= MAX_ATTEMPTS) {
      await tx.delete(verificationTokens).where(eq(verificationTokens.id, row.id))
      return null
    }
    if (!safeEqual(row.tokenHash, hashToken(code))) {
      // palpite errado: incrementa e segue (sem revelar nada além de "inválido")
      await tx.update(verificationTokens)
        .set({ attempts: row.attempts + 1 })
        .where(eq(verificationTokens.id, row.id))
      return null
    }
    await tx.delete(verificationTokens).where(eq(verificationTokens.id, row.id))
    return await upsertUserByEmail(tx, email)
  })

  if (!user) return c.json({ error: 'Código inválido' }, 400)
  await issueSession(c, user.id)
  return c.json({ ok: true })
})
Um token ativo por identifier
Antes de gerar um novo OTP/magic link, delete os anteriores do mesmo identifier. Isso evita que vários códigos válidos coexistam (ampliando a janela de adivinhação) e dá ao usuário um comportamento previsível: "o último que pedi é o que vale". Combine com rate limiting de envio (Cap 19) para que ninguém use seu endpoint como canhão de spam contra terceiros.

Capítulo 16

RBAC papéis e permissões

Os quinze capítulos anteriores responderam a uma pergunta: quem é você? A partir daqui a pergunta muda para o que você pode fazer? — a autorização que o Capítulo 1 separou da autenticação e que distingue um 401 (não sei quem você é) de um 403 (sei quem você é, e você não pode). O Role-Based Access Control é a forma mais difundida de organizar essa decisão: em vez de atribuir permissões a cada usuário individualmente, agrupa-se usuários em papéis (admin, editor, viewer) e atribui-se permissões aos papéis. Este capítulo constrói o modelo mental do RBAC — a indireção usuário→papel→permissão e por que ela escala —, modela o role com tipos exatos em TypeScript (o z.enum do Cap 11), e estabelece o princípio que governa todos os próximos capítulos: a autorização decide no servidor, sempre, e o cliente apenas reflete a decisão.

# A indireção que faz o RBAC escalar

A forma ingênua de autorizar é amarrar permissões direto ao usuário: "Maria pode deletar posts, João pode editar". Funciona para dez usuários e colapsa em cem — toda mudança de política vira uma varredura de linhas, e ninguém consegue responder "quem pode deletar posts?" sem inspecionar cada conta. O RBAC insere uma camada entre os dois. O usuário tem um papel; o papel concede permissões. A relação usuário→permissão deixa de ser direta e passa a ser computada: as permissões de Maria são as permissões do papel dela.

Essa indireção é o ponto inteiro. Promover Maria a editor é trocar um campo. Decidir que editores agora podem publicar é alterar a definição do papel — e todos os editores ganham a permissão de uma vez. A pergunta "quem pode publicar?" responde-se listando quem tem o papel editor. O sistema cresce em usuários sem crescer em complexidade de política, porque a política vive nos papéis, que são poucos e estáveis, não nos usuários, que são muitos e voláteis.

Os três elementos
Usuário — a identidade autenticada (Caps 1–15). Papel (role) — um rótulo que agrupa capacidades: admin, editor, viewer. Permissão — uma ação concreta sobre um recurso: post:delete, user:ban. RBAC liga os três numa cadeia: o usuário recebe um papel, o papel carrega um conjunto de permissões, e autorizar é perguntar se o papel do usuário inclui a permissão exigida pela rota.

# Modelando o role com tipos exatos

O role não é uma string qualquer — é um conjunto fechado de valores conhecidos. Modelá-lo como string é abrir mão da única vantagem do TypeScript: um typo ("admnin") compila, e a checagem de autorização falha em silêncio, liberando ou negando errado. O Cap 11 estabeleceu o padrão — z.enum como fonte única, do qual se deriva o tipo e a validação de runtime.

roles.ts
import { z } from 'zod'

// Fonte única: o enum gera o schema de runtime E o tipo estático
export const roleSchema = z.enum(['admin', 'editor', 'viewer'])
export type Role = z.infer<typeof roleSchema>
// type Role = 'admin' | 'editor' | 'viewer'

// O catálogo de permissões — também fechado e tipado
export const permissionSchema = z.enum([
  'post:read', 'post:create', 'post:update', 'post:delete',
  'user:read', 'user:ban', 'settings:manage',
])
export type Permission = z.infer<typeof permissionSchema>

Com Role e Permission como uniões literais, o compilador passa a participar da autorização. Uma função que recebe Role recusa qualquer string fora das três; um switch sobre Role pode ser checado por exaustividade (o never do Cap 11), de modo que adicionar um quarto papel quebra a compilação em todos os pontos que precisam tratá-lo. O erro de digitação vira erro de build, não vulnerabilidade de runtime.

# O mapa papel→permissões

O coração do RBAC é uma estrutura que, dado um papel, devolve suas permissões. Para a maioria das aplicações ela é estática — definida em código, versionada, revisável em pull request. Um Record tipado expressa isso e ainda garante, em tempo de compilação, que todo papel tem uma entrada (cobertura via satisfies).

policy.ts
import { type Role, type Permission } from './roles'

// satisfies força: toda chave de Role presente, todo valor um Permission[] válido.
// Esquecer um papel = erro de compilação.
export const rolePermissions = {
  admin: [
    'post:read', 'post:create', 'post:update', 'post:delete',
    'user:read', 'user:ban', 'settings:manage',
  ],
  editor: ['post:read', 'post:create', 'post:update', 'user:read'],
  viewer: ['post:read', 'user:read'],
} as const satisfies Record<Role, Permission[]>

// A pergunta central do RBAC, em uma função pura e testável
export function can(role: Role, permission: Permission): boolean {
  return (rolePermissions[role] as readonly Permission[]).includes(permission)
}

A função can isola a decisão de autorização num ponto único, puro e sem efeitos colaterais — recebe papel e permissão, devolve booleano. Essa pureza é o que torna a política testável exaustivamente: um teste pode varrer todas as combinações papel×permissão e fixá-las, transformando a matriz de acesso num artefato verificado em vez de uma suposição espalhada pelo código. Todos os capítulos seguintes — middleware (17), permissões granulares (18) — constroem sobre essa função.

A autorização é sempre uma decisão do servidor
Esconder o botão "deletar" para um viewer no frontend é UX, não segurança. O cliente está inteiramente sob controle do usuário: ele pode forjar a requisição direto na API. Toda rota que exige permissão precisa chamar can() no servidor antes de agir — a checagem no cliente é um espelho da decisão do servidor, jamais a decisão em si. Um RBAC que confia no frontend não é controle de acesso; é uma sugestão.

# Onde o role vive

O papel pertence ao usuário e mora no banco — uma coluna em users, tipada pelo mesmo enum. A partir daí ele precisa estar disponível em cada requisição. Em sessão opaca (Cap 5), o papel é lido do banco junto da sessão. Em JWT (Caps 8–11), pode ser um claim embutido no token — com a ressalva de que mudanças de papel só refletem na próxima emissão, a menos que se consulte o banco.

user-schema.ts
import { pgTable, uuid, text } from 'drizzle-orm/pg-core'

export const users = pgTable('users', {
  id: uuid('id').primaryKey().defaultRandom(),
  email: text('email').notNull().unique(),
  // enum do Postgres alinhado ao z.enum — o banco também recusa valores inválidos
  role: text('role', { enum: ['admin', 'editor', 'viewer'] })
    .notNull().default('viewer'),  // menor privilégio por padrão
})
Default = menor privilégio
O papel padrão de uma conta nova deve ser o mais restrito (viewer), nunca o mais permissivo. Privilégio se concede deliberadamente, não se herda por omissão. Um bug que esqueça de atribuir papel deve resultar em acesso de menos, não de mais — o sistema falha fechado. Esse é o princípio do menor privilégio aplicado ao default da coluna, e ele reaparece no Cap 21.

# Hierarquia de papéis (quando faz sentido)

Em muitos sistemas os papéis são naturalmente ordenados: admin contém tudo que editor pode, que contém tudo que viewer pode. Modelar isso explicitamente — como inclusão de conjuntos de permissões — evita repetir permissões em cada papel e torna a relação "admin é um superconjunto de editor" verdadeira por construção, não por coincidência de listas.

hierarchy.ts
// Cada papel herda as permissões do anterior e adiciona as suas
const viewer: Permission[] = ['post:read', 'user:read']
const editor: Permission[] = [...viewer, 'post:create', 'post:update']
const admin: Permission[] = [...editor, 'post:delete', 'user:ban', 'settings:manage']

export const rolePermissions = { viewer, editor, admin }
  satisfies Record<Role, Permission[]>
// admin ⊇ editor ⊇ viewer garantido pela composição, não por digitação manual

Nem todo domínio é hierárquico, porém. Um papel auditor que lê tudo mas não escreve nada não "está acima" nem "abaixo" de editor — são ortogonais. Quando os papéis deixam de formar uma linha e viram um reticulado de capacidades sobrepostas, o RBAC puro começa a estalar, e a granularidade do Cap 18 (permissões por recurso, atributos) passa a ser o caminho. RBAC é o ponto de partida certo; saber quando ele não basta é o que o Cap 18 trata.

Capítulo 17

Middleware de autorização

O Capítulo 16 entregou a decisão de autorização condensada numa função pura: can(role, permission). Falta o mecanismo que a invoca em cada requisição, antes que o handler toque o recurso. Esse mecanismo é o middleware — a camada do Hono (Vol XIII, Cap sobre Hono) que intercepta a requisição, valida a sessão, resolve o usuário e aplica a política, deixando passar ou cortando com 401/403 antes do handler existir. Este capítulo monta a pilha de middlewares de autenticação e autorização: como tipar o contexto do Hono para carregar o usuário com segurança de tipos, como compor um guard de autenticação seguido de guards de papel e de permissão, e por que a ordem importa — autenticar antes de autorizar, sempre.

# O middleware como portão

Um middleware é uma função que roda antes do handler e decide se a requisição prossegue. No Hono, ele recebe o contexto c e a função next: chamar await next() passa a vez ao próximo da cadeia; retornar uma resposta sem chamar next() interrompe ali. Essa estrutura é exatamente o que a autorização precisa — um ponto único onde, conhecida a identidade e a política, a requisição ou avança ou recebe 401/403. Espalhar a checagem dentro de cada handler é repetir-se e esquecer; concentrá-la num middleware é declará-la uma vez e aplicá-la consistentemente.

Dois portões, não um
Autenticação e autorização são middlewares distintos, encadeados nessa ordem. O de autenticação responde "quem é você?" — valida a sessão, resolve o usuário, ou retorna 401. O de autorização responde "você pode?" — assume um usuário já resolvido e aplica can(), ou retorna 403. Misturá-los num só é tentador e errado: a separação permite reutilizar o portão de autenticação em rotas que exigem login mas não papel específico, e deixa claro qual falhou.

# Tipando o contexto do Hono

O middleware de autenticação resolve o usuário e precisa entregá-lo ao handler. No Hono isso se faz por c.set/c.get sobre as Variables do contexto — e tipá-las é o que dá segurança: o handler lê c.get('user') com o tipo correto, e o compilador impede ler uma variável que o middleware não setou.

app-types.ts
import { Hono } from 'hono'
import { type Role } from './roles'

// O usuário autenticado, na forma mínima que a autorização precisa
export interface AuthUser {
  id: string
  role: Role
}

// Variables tipadas: o que os middlewares colocam no contexto
export type Env = {
  Variables: {
    user: AuthUser   // presente após o middleware de autenticação
  }
}

// A app e os routers usam esse Env — c.get('user') vem tipado como AuthUser
export const app = new Hono<Env>()

# O guard de autenticação

O primeiro portão valida a sessão e popula c.set('user', ...). Ele encapsula o que os Caps 5–10 montaram — ler o cookie de sessão ou o Bearer token, validar contra o store ou a assinatura, resolver o usuário — e termina em uma de duas saídas: 401 se a prova de identidade falha, ou next() com o usuário no contexto.

require-auth.ts
import { createMiddleware } from 'hono/factory'
import { getCookie } from 'hono/cookie'
import { type Env } from './app-types'

// createMiddleware<Env> propaga os tipos do contexto para dentro do guard
export const requireAuth = createMiddleware<Env>(async (c, next) => {
  const token = getCookie(c, 'session')
  if (!token) {
    return c.json({ error: 'Não autenticado' }, 401)
  }

  // validateSession: store opaco (Cap 6) ou jwtVerify (Cap 9)
  const user = await validateSession(token)
  if (!user) {
    return c.json({ error: 'Sessão inválida' }, 401)
  }

  c.set('user', { id: user.id, role: user.role })
  await next()   // identidade estabelecida — segue para o próximo portão
})

# O guard de autorização: papel e permissão

O segundo portão é uma fábrica de middlewares: recebe a exigência (um papel mínimo, ou uma permissão) e devolve um middleware que a aplica. Essa parametrização é o que torna o guard reutilizável — uma rota declara requirePermission('post:delete') e o mesmo código serve a todas as combinações, lendo o usuário que o portão anterior deixou no contexto.

require-permission.ts
import { createMiddleware } from 'hono/factory'
import { can } from './policy'
import { type Env } from './app-types'
import { type Permission } from './roles'

// Fábrica: a exigência entra como argumento, o middleware sai pronto
export function requirePermission(permission: Permission) {
  return createMiddleware<Env>(async (c, next) => {
    const user = c.get('user')   // garantido por requireAuth antes

    if (!can(user.role, permission)) {
      // autenticado, mas sem a permissão → 403 (não 401)
      return c.json({ error: 'Acesso negado' }, 403)
    }
    await next()
  })
}

// Variante por papel, para quando a granularidade de permissão é desnecessária
export function requireRole(...roles: Role[]) {
  return createMiddleware<Env>(async (c, next) => {
    if (!roles.includes(c.get('user').role)) {
      return c.json({ error: 'Acesso negado' }, 403)
    }
    await next()
  })
}
401 e 403 não são intercambiáveis
O guard de autenticação retorna 401 Unauthorized: "não sei quem você é" — o cliente deveria autenticar e tentar de novo. O guard de autorização retorna 403 Forbidden: "sei quem você é, e isso não é para você" — repetir não adianta. Trocar um pelo outro confunde clientes e mascara bugs: um 403 onde deveria ser 401 faz o usuário deslogado parecer banido; o inverso manda quem já está logado para a tela de login num laço. O Cap 1 fixou essa distinção; o middleware é onde ela se materializa.

# Compondo a pilha nas rotas

Com os dois guards prontos, proteger uma rota é encadeá-los antes do handler. O Hono aplica os middlewares na ordem em que aparecem — requireAuth primeiro (popula o usuário), depois o guard de autorização (lê o usuário), depois o handler. A ordem não é estética: inverter rodaria requirePermission com c.get('user') ainda indefinido.

routes.ts
import { app } from './app-types'
import { requireAuth } from './require-auth'
import { requirePermission, requireRole } from './require-permission'

// Aplicar requireAuth a todo um grupo de rotas de uma vez
app.use('/api/*', requireAuth)

// Leitura: basta estar autenticado (sem segundo guard)
app.get('/api/posts', (c) => {
  const user = c.get('user')   // tipado como AuthUser
  return c.json({ posts: [], viewer: user.id })
})

// Escrita: autenticação (do grupo) + permissão específica
app.delete(
  '/api/posts/:id',
  requirePermission('post:delete'),   // 403 se o papel não cobre
  (c) => {
    const id = c.req.param('id')
    // chega aqui só quem passou pelos dois portões
    return c.json({ deleted: id })
  },
)

// Rota só de admin, por papel
app.post('/api/settings', requireRole('admin'), (c) => {
  return c.json({ ok: true })
})
Proteja por grupo, não rota a rota
Aplicar requireAuth com app.use('/api/*', ...) protege o grupo inteiro de uma vez — uma rota nova sob /api nasce protegida por padrão. O risco oposto, declarar autenticação em cada rota individual, é o esquecimento: a única rota onde você esqueceu o guard é a brecha. Falhe fechado — exija autenticação por padrão no grupo e abra exceções explícitas (login, health check) fora dele, não o contrário.

# A decisão fina ainda falta

Este middleware decide por papel e por permissão de tipo — "editores podem deletar posts". Ele não decide por instância: "este usuário pode deletar este post porque é o autor dele". Essa pergunta depende de carregar o recurso e comparar atributos (dono, status, organização), e não cabe num guard que roda antes do handler conhecer o recurso. É a autorização granular — ownership e atributos — que o Cap 18 constrói por cima desta base.

Capítulo 18

Permissões granulares

O RBAC do Capítulo 16 e o middleware do Capítulo 17 respondem a uma pergunta de tipo: "editores podem deletar posts". Eles não respondem à pergunta de instância: "esta editora pode deletar este post — porque é dela, ou está no rascunho, ou pertence à organização dela?". Essa segunda pergunta é onde quase todo controle de acesso real vive, e onde quase toda falha grave de autorização nasce. Ela não cabe num guard que roda antes do handler conhecer o recurso, porque depende de carregar o recurso e comparar atributos. Este capítulo constrói a camada granular sobre a base do RBAC: ownership (o dono pode), ABAC (atributos decidem), a vulnerabilidade IDOR que a ausência dessa camada produz, e como derivar tipos do schema com drizzle-zod (Cap 18 do Vol XII) para que a decisão fina seja escrita uma vez, no servidor, sobre dados confiáveis.

# Por que o papel não basta

RBAC autoriza por classe de ação: "o papel editor inclui post:update". Mas num sistema multiusuário, dois editores não devem editar os posts um do outro só porque ambos têm o papel. O papel concede a capacidade de editar posts em geral; quem decide quais posts é a relação entre o usuário e a instância específica. RBAC é necessário e insuficiente — ele filtra quem chega à porta, mas não sabe se a chave abre aquela fechadura.

A consequência de parar no RBAC é a vulnerabilidade mais comum do OWASP: Broken Object Level Authorization (BOLA/IDOR). O usuário está autenticado, tem o papel certo, a rota está protegida pelo middleware do Cap 17 — e mesmo assim deleta o post de outro, porque ninguém verificou se o id na URL pertence a ele. A checagem de tipo passou; a de instância nunca aconteceu.

IDOR: o 403 que faltou
Considere DELETE /api/posts/42 protegido por requirePermission('post:delete'). Um editor mal-intencionado tem essa permissão, então o middleware libera — e o handler deleta o post 42, que é de outra pessoa. O número na URL é controlado pelo cliente; trocar 42 por 43 acessa outro recurso. A defesa não é esconder o id (são sequenciais, adivinháveis): é verificar a posse no servidor antes de agir. Todo handler que recebe um id de recurso deve provar que aquele usuário tem direito àquela instância.

# Tipos a partir do schema com drizzle-zod

A decisão granular opera sobre o recurso carregado do banco. Para que essa lógica seja tipada e validada sem duplicar a forma do recurso, drizzle-zod (Vol XII, Cap 18) deriva o schema Zod direto da tabela Drizzle — fonte única, do banco ao runtime.

post-schema.ts
import { pgTable, uuid, text, timestamp } from 'drizzle-orm/pg-core'
import { createSelectSchema } from 'drizzle-zod'
import { z } from 'zod'

export const posts = pgTable('posts', {
  id: uuid('id').primaryKey().defaultRandom(),
  authorId: uuid('author_id').notNull(),     // o dono — base do ownership
  orgId: uuid('org_id').notNull(),           // atributo de tenant
  status: text('status', { enum: ['draft', 'published'] }).notNull(),
  title: text('title').notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull(),
})

// Schema Zod derivado da tabela — não redigitamos os campos
export const postSchema = createSelectSchema(posts)
export type Post = z.infer<typeof postSchema>

# Ownership: o dono pode

A forma mais simples e comum de autorização de instância é a posse: o recurso tem um authorId, e a ação é permitida se ele bate com o usuário. A função de decisão recebe o usuário e o recurso já carregado — diferente do can() do Cap 16, que só via o papel. É essa dependência do recurso que obriga a checagem a viver dentro do handler, depois do load.

post-policy.ts
import { type AuthUser } from './app-types'
import { type Post } from './post-schema'
import { can } from './policy'

// Decisão de instância: combina papel (RBAC) com atributos do recurso (ABAC)
export function canUpdatePost(user: AuthUser, post: Post): boolean {
  // admin passa por cima do ownership (regra de negócio explícita)
  if (user.role === 'admin') return true

  // precisa da capacidade de tipo (RBAC) E ser o dono (ownership)
  return can(user.role, 'post:update') && post.authorId === user.id
}

// Delete só pelo dono ou admin; rascunho de outro nunca
export function canDeletePost(user: AuthUser, post: Post): boolean {
  if (user.role === 'admin') return true
  return can(user.role, 'post:delete') && post.authorId === user.id
}

Note que essas funções compõem as duas camadas: chamam can() (o RBAC do Cap 16, capacidade de tipo) e comparam atributos do recurso (ownership). A granularidade não substitui o RBAC — empilha sobre ele. O papel é o primeiro filtro; a posse é o segundo. E a exceção do admin é uma regra de negócio escrita explicitamente, não um vazamento acidental de privilégio.

# Aplicando no handler: load, decide, act

O padrão correto tem três tempos na ordem certa: carregar o recurso, decidir com a política de instância, e só então agir. Carregar antes de decidir é o que distingue esta camada do middleware — a decisão precisa dos dados. E a resposta para "não existe" e "existe mas não é seu" merece atenção: às vezes convém devolver 404 em ambos, para não revelar a existência de recursos alheios.

post-routes.ts
app.delete('/api/posts/:id', requirePermission('post:delete'), async (c) => {
  const user = c.get('user')
  const id = c.req.param('id')

  // 1. LOAD — carregar a instância real do banco
  const post = await db.query.posts.findFirst({ where: eq(posts.id, id) })
  if (!post) return c.json({ error: 'Não encontrado' }, 404)

  // 2. DECIDE — política de instância sobre o recurso carregado
  if (!canDeletePost(user, post)) {
    // 404 em vez de 403: não confirma que o post existe para quem não pode vê-lo
    return c.json({ error: 'Não encontrado' }, 404)
  }

  // 3. ACT — agora é seguro
  await db.delete(posts).where(eq(posts.id, id))
  return c.json({ deleted: id })
})
403 ou 404? Depende do que você quer revelar
Um 403 diz "este recurso existe, mas não é para você" — informação útil para um atacante enumerar recursos. Um 404 diz "não existe (para você)" — esconde a existência. Use 403 quando a presença do recurso não é segredo (um endpoint público de admin); use 404 quando revelar a existência já é vazamento (o documento privado de outro usuário). A escolha é de política, mas seja consistente: misturar 403 e 404 no mesmo endpoint cria o oráculo que você queria evitar.

# ABAC: quando os atributos decidem

Ownership é um caso particular de uma ideia mais geral: a decisão depende de atributos — do usuário, do recurso, do contexto. Attribute-Based Access Control generaliza isso. "Pode publicar se for o autor e o post estiver em rascunho e for da mesma organização" combina três atributos numa só regra. Modelar essas regras como funções puras que recebem (user, resource) mantém-nas testáveis e auditáveis.

abac.ts
// Multi-tenant: ninguém toca recurso de outra organização
function sameOrg(user: AuthUser & { orgId: string }, post: Post): boolean {
  return user.orgId === post.orgId
}

// Regra composta de atributos: dono + rascunho + mesma org
export function canPublish(
  user: AuthUser & { orgId: string },
  post: Post,
): boolean {
  return (
    sameOrg(user, post) &&
    post.authorId === user.id &&
    post.status === 'draft' &&
    can(user.role, 'post:update')
  )
}

# Filtrar na query, não na aplicação

Para listagens, há uma armadilha de performance e de segurança: carregar todos os recursos e filtrar por posse na aplicação. Isso traz dados alheios para a memória do processo (vazamento se um log ou erro os expõe) e desperdiça banco. A regra: empurre o critério de autorização para dentro da query. O banco devolve só o que o usuário pode ver.

list-posts.ts
app.get('/api/posts', async (c) => {
  const user = c.get('user')

  // O filtro de autorização vai na cláusula WHERE — não em .filter() depois.
  // admin vê tudo da org; demais veem só os próprios.
  const where = user.role === 'admin'
    ? eq(posts.orgId, user.orgId)
    : and(eq(posts.orgId, user.orgId), eq(posts.authorId, user.id))

  const rows = await db.select().from(posts).where(where)
  return c.json({ posts: rows })   // nenhum dado alheio chega à memória
})
Centralize a política, não a espalhe pelos handlers
As funções canUpdatePost, canDeletePost, canPublish ficam num módulo de política, não inline nos handlers. Três ganhos: testabilidade exaustiva (varrer combinações usuário×recurso num teste), auditabilidade (um único lugar onde a política mora, revisável em PR) e consistência (o mesmo recurso autorizado igual em toda rota que o toca). Política espalhada é política que diverge — uma rota esquece a checagem de org e abre a brecha. Quando as regras crescem, vale considerar uma engine dedicada (CASL, ou OPA para políticas externas), mas o princípio é o mesmo: a decisão num lugar só.

Capítulo 19

Rate limiting e brute force

Toda a autenticação construída até aqui pressupõe um atacante que tenta uma vez. A realidade é um atacante que tenta um milhão de vezes: força bruta de senhas (Cap 2), enumeração de OTPs de 6 dígitos (Cap 15), spray de tokens, abuso do endpoint de envio de magic links como canhão de spam. A defesa não está num hash mais forte ou num token mais longo — está em limitar quantas tentativas o atacante consegue fazer por unidade de tempo. Este capítulo cobre o rate limiting como camada transversal de autenticação: o algoritmo de janela deslizante sobre Redis (o store do Cap 6), os contadores por IP e por conta, o backoff exponencial e o lockout temporário contra brute force, e a regra de ouro — limitar sem virar uma ferramenta de negação de serviço contra usuários legítimos.

# O custo de cada tentativa

Sem rate limiting, o custo marginal de uma tentativa de login é zero para o atacante: ele dispara requisições na velocidade da rede. Um OTP de 6 dígitos (Cap 15) tem um milhão de combinações — adivinháveis em segundos se nada limita a cadência. Uma senha vazada em outro serviço é testada contra milhões de contas (credential stuffing) numa tarde. O rate limiting muda a aritmética: ao impor um teto de tentativas por janela de tempo, transforma "segundos" em "anos" e torna o ataque economicamente inviável.

O Cap 2 introduziu o hash lento como defesa contra brute force offline (quando o atacante já tem o banco). O rate limiting é a defesa contra brute force online (contra o seu endpoint, sem ter o banco). São complementares: o hash lento protege as senhas vazadas, o rate limiting protege o portão de entrada. Nenhum substitui o outro.

Por que no Redis, e não em memória
Um contador em memória do processo (Map) funciona com uma única instância e evapora num restart — e some quando você escala para vários processos, cada um com seu próprio contador, multiplicando o limite efetivo pelo número de instâncias. O rate limiting precisa de um estado compartilhado e atômico entre todas as instâncias: é exatamente o que o Redis (Cap 6) oferece, com operações atômicas (INCR, EXPIRE) que evitam condições de corrida sob concorrência.

# Janela deslizante com Redis

O algoritmo mais simples é a janela fixa: conte requisições por minuto, zere a cada minuto. O defeito é a borda — um atacante dispara o limite no fim de um minuto e de novo no início do seguinte, dobrando o teto na virada. A janela deslizante corrige isso mantendo os timestamps das requisições recentes num sorted set e contando apenas as que caem na janela móvel atual.

rate-limit.ts
import { Redis } from 'ioredis'
const redis = new Redis(process.env.REDIS_URL!)

interface LimitResult { allowed: boolean; remaining: number; resetMs: number }

// Janela deslizante via sorted set: score = timestamp, membro = id único.
async function slidingWindow(
  key: string, limit: number, windowMs: number,
): Promise<LimitResult> {
  const now = Date.now()
  const windowStart = now - windowMs

  const pipe = redis.pipeline()
  pipe.zremrangebyscore(key, 0, windowStart)        // expira os antigos
  pipe.zadd(key, now, `${now}-${Math.random()}`)   // registra esta
  pipe.zcard(key)                                  // conta na janela
  pipe.pexpire(key, windowMs)                       // TTL = limpa sozinho
  const res = await pipe.exec()

  const count = res![2][1] as number
  return {
    allowed: count <= limit,
    remaining: Math.max(0, limit - count),
    resetMs: windowMs,
  }
}

# Middleware de rate limit

Como a autorização (Cap 17), o rate limiting é um middleware do Hono — roda antes do handler e corta com 429 Too Many Requests quando o teto estoura. A chave do limite é o que distingue os casos: por IP para tráfego anônimo, por conta para proteção direcionada.

rate-limit-middleware.ts
import { createMiddleware } from 'hono/factory'

interface Options { limit: number; windowMs: number; keyPrefix: string }

export function rateLimit(opts: Options) {
  return createMiddleware(async (c, next) => {
    // IP real atrás de proxy: confiar só no header que SEU proxy injeta
    const ip = c.req.header('x-forwarded-for')?.split(',')[0]?.trim() ?? 'unknown'
    const key = `${opts.keyPrefix}:${ip}`

    const { allowed, remaining, resetMs } = await slidingWindow(key, opts.limit, opts.windowMs)

    // Headers padronizados informam o cliente legítimo sobre o limite
    c.header('RateLimit-Limit', String(opts.limit))
    c.header('RateLimit-Remaining', String(remaining))

    if (!allowed) {
      c.header('Retry-After', String(Math.ceil(resetMs / 1000)))
      return c.json({ error: 'Muitas requisições' }, 429)
    }
    await next()
  })
}
O IP atrás de proxy é falsificável
O header X-Forwarded-For é fornecido pelo cliente e pode ser forjado — um atacante manda um IP diferente a cada requisição e some do contador por IP. Só confie nesse header se um proxy reverso confiável (nginx, Cloudflare) o reescreve e descarta o valor do cliente. Configure o número de proxies confiáveis e leia o IP na posição certa. Sem isso, o rate limiting por IP é teatro. É por isso que limites por conta (que o cliente não escolhe) são uma defesa mais robusta para login.

# Duas chaves: IP e conta

Limitar só por IP falha contra botnets distribuídas (cada bot um IP) e pune NATs compartilhados (um escritório inteiro atrás de um IP). Limitar só por conta falha contra enumeração (o atacante varia o e-mail alvo). A defesa de login combina as duas: um limite por IP contém o volume bruto, e um limite por conta-alvo contém o foco num usuário específico — independente de quantos IPs o atacante usa.

login-route.ts
// IP: teto largo contra volume bruto
app.use('/auth/login', rateLimit({ limit: 20, windowMs: 60_000, keyPrefix: 'login:ip' }))

app.post('/auth/login', async (c) => {
  const { email, password } = await c.req.json()

  // Conta: teto estreito por e-mail alvo, imune à troca de IP
  const acct = await slidingWindow(`login:acct:${email}`, 5, 900_000)  // 5 / 15min
  if (!acct.allowed) {
    return c.json({ error: 'Conta temporariamente bloqueada' }, 429)
  }

  const user = await verifyCredentials(email, password)  // Argon2, timing-safe (Cap 2)
  if (!user) return c.json({ error: 'Credenciais inválidas' }, 401)

  // sucesso: zerar o contador da conta para não punir o uso legítimo seguinte
  await redis.del(`login:acct:${email}`)
  await issueSession(c, user.id)
  return c.json({ ok: true })
})

# Backoff exponencial e lockout

Um teto fixo trata a 1ª e a 50ª tentativa falha igual. O backoff exponencial endurece progressivamente: cada falha consecutiva aumenta o tempo de espera — 1s, 2s, 4s, 8s... — tornando o ataque cada vez mais lento sem nunca travar permanentemente o usuário legítimo, que acerta a senha em poucas tentativas e some da escalada.

backoff.ts
// Conta falhas consecutivas e calcula a espera exigida antes da próxima
async function requiredDelayMs(email: string): Promise<number> {
  const fails = Number(await redis.get(`fails:${email}`) ?? 0)
  if (fails < 3) return 0   // margem para erro humano honesto
  // 2^(fails-3) segundos, teto de 5 min para nunca virar lockout eterno
  return Math.min(2 ** (fails - 3) * 1000, 300_000)
}

async function recordFailure(email: string): Promise<void> {
  await redis.multi().incr(`fails:${email}`).expire(`fails:${email}`, 3600).exec()
}
Lockout permanente = DoS de presente para o atacante
Bloquear uma conta para sempre após N falhas parece seguro, mas entrega uma arma: o atacante trava deliberadamente a conta da vítima só errando a senha de propósito — negação de serviço sem nem conhecer a senha. Prefira lockout temporário (minutos) com backoff, ou desafios escalonados (CAPTCHA após X falhas). A trava deve frustrar a máquina sem refém o humano. Sempre haja um teto de tempo: a defesa não pode ser pior que o ataque.

# Onde aplicar além do login

O login é o alvo óbvio, mas todo endpoint de autenticação que dispara uma ação cara ou adivinhável precisa de limite. O refresh de token (Cap 10) — para conter replay de refresh tokens roubados. O envio de magic link/OTP (Cap 15) — para que ninguém use seu servidor de e-mail como canhão de spam contra terceiros, e para limitar a geração de códigos. A verificação de OTP — somando-se ao limite de attempts da própria tabela. Cada um com chave e teto adequados ao seu risco.

Falhe aberto com cautela quando o Redis cai
Se o Redis estiver indisponível, o middleware precisa decidir: bloquear tudo (fail closed — disponibilidade zero, mas seguro) ou liberar (fail open — disponível, mas sem limite). Para a maioria das rotas, falhar aberto com alarme é o trade-off aceitável: prefira atender usuários a derrubar o serviço por uma dependência auxiliar. Mas registre o evento e tenha um circuit breaker — um Redis cronicamente fora vira uma janela de brute force ilimitado. Decida conscientemente por rota; não deixe o comportamento ao acaso de um try/catch esquecido.

# Quando adotar e quando construir

Construir do zero, mesmo seguindo este volume corretamente, significa ser o único a auditar o seu código — e autenticação é o lugar onde um bug vira incidente. # Better Auth: a recomendação atual

Em 2026, better-auth@1.6.14 é a escolha de referência para TypeScript full-stack fora do casamento exclusivo com Next.js. Ela é framework-agnostic (Hono, Express, Next, SvelteKit, Nuxt), totalmente tipada, e adota um modelo de plugins: o núcleo cobre e-mail/senha e sessões, e cada capacidade adicional — social, 2FA, organizações, passkeys — entra como plugin explícito. Trabalha direto sobre o seu banco via adaptadores (Drizzle, Prisma, Kysely), então o schema de users/sessions/accounts que modelamos nos Caps 5, 14 e 16 é o que ela gerencia.

# Lucia: deprecada, mas o melhor professor

Lucia foi, por anos, a biblioteca de sessões mais querida do TypeScript — minimalista, transparente, sem mágica. Desde março de 2025 ela está deprecada (a última linha, lucia@3.2.2, marca o fim): o autor decidiu que o valor de Lucia estava em ensinar o padrão de sessões, não em ser mais uma dependência a manter. O projeto virou um recurso de aprendizado — um conjunto de guias e código de referência mostrando como implementar sessões à mão.

O desfecho é instrutivo. Lucia nunca escondeu nada: o seu padrão de sessão — token aleatório, hash no banco, cookie httpOnly, validação por lookup — é exatamente o que construímos nos Caps 5 e 6. Por isso ela continua valiosa desinstalada: como blueprint que você lê para entender ou replicar o mecanismo, não como pacote no package.json. Se você seguiu este volume, já implementou o coração da Lucia.

Não inicie projetos novos com Lucia
Pacote deprecado não recebe correções de segurança — adotá-lo em produção é assumir uma dívida sem manutenção. Use Lucia como blueprint: leia os guias, copie o padrão de sessão para o seu próprio código (você já sabe fazê-lo pelos Caps 5-6), ou adote Better Auth, que cobre o mesmo terreno mantido e tipado. O valor de Lucia hoje é pedagógico, não operacional.

A decisão se reduz a poucos eixos. Onde a app vive: Next.js puxa para Auth.js; backend agnóstico (Hono, Express) puxa para Better Auth. Segurança e OWASP

Os vinte capítulos anteriores trataram a segurança um mecanismo de cada vez — hashing aqui, CSRF ali, tokens acolá. Este capítulo inverte a lente: em vez de partir do mecanismo, parte do atacante. Vamos atravessar as categorias mais relevantes para auth, reconectando cada uma ao capítulo que a defende, e fechar com os princípios transversais — defesa em profundidade, menor privilégio, falhar fechado — que organizam tudo o que veio antes.

# Pensar como o atacante

O desenvolvedor pergunta "como faço isto funcionar?". O atacante pergunta "como faço isto funcionar de um jeito que você não previu?". Essa inversão é a habilidade central da segurança. Onde você vê um campo de e-mail, ele vê um oráculo de enumeração. Onde você vê um id na URL, ele vê o id do vizinho (Cap 18). Onde você vê uma mensagem de erro útil, ele vê informação vazada. Segurança não é uma feature que se adiciona no fim; é uma forma de ler cada decisão de design perguntando "o que acontece se o input for hostil?".

OWASP Top 10 e ASVS: os dois mapas
O OWASP Top 10 é a lista das dez categorias de risco mais críticas em aplicações web — uma priorização, ótima para saber o que olhar primeiro. O ASVS (Application Security Verification Standard) é um checklist exaustivo e verificável, organizado por níveis, ótimo para auditar sistematicamente. Use o Top 10 para focar a atenção e o ASVS para não esquecer nada. Nenhum dos dois é um substituto para entender o mecanismo — são roteiros, não receitas.

# A01 — Broken Access Control

A categoria nº 1 do Top 10, e a mais diretamente ligada a este volume. Engloba tudo que estudamos nos Caps 16-18: o usuário acessa o que não deveria. IDOR/BOLA (o id do vizinho), elevação de privilégio (virar admin), força browsing (acessar a rota de admin sem o papel), falta de checagem de instância. A defesa não é um truque, é disciplina: autorizar no servidor (Cap 16), em todo endpoint (Cap 17), por instância e não só por tipo (Cap 18), falhando fechado por padrão.

// O anti-padrão A01 clássico: confiar no id da requisição sem verificar posse
app.get('/api/orders/:id', async (c) => {
  const order = await getOrder(c.req.param('id'))
  return c.json(order)   // ❌ qualquer um lê o pedido de qualquer um
})

// Correto: carregar, verificar posse no servidor, então responder (Cap 18)

  const user = c.get('user')
  const order = await getOrder(c.req.param('id'))
  if (!order || order.userId !== user.id) {
    return c.json({ error: 'Não encontrado' }, 404)  // ✅ não revela existência
  }
  return c.json(order)
})

# A02 — Cryptographic Failures

Falhas no uso de criptografia: senhas em texto plano ou com hash fraco (MD5, SHA-1 cru), segredos no código, TLS ausente, tokens previsíveis. Os Caps 2 e 15 cobrem o núcleo: senhas com Argon2 (lento, salgado), tokens com CSPRNG (node:crypto, nunca Math.random), comparações em tempo constante (timingSafeEqual). O princípio operante: nunca invente criptografia, e use o algoritmo certo para a ameaça certa — hash lento para senhas, hash rápido para tokens de alta entropia.

Os erros criptográficos mais comuns em auth
Hash rápido em senha (SHA-256 sem stretching — quebrável em GPU) — use Argon2 (Cap 2). === em segredo (vaza timing) — use timingSafeEqual (Caps 2, 15). Math.random() em token (previsível) — use randomBytes (Cap 15). Segredo no repositório (JWT secret commitado) — use variáveis de ambiente e rotação. JWT alg: none ou algoritmo não fixado (assinatura ignorada) — fixe algorithms no verify (Cap 9). Cada um já foi tratado; A02 é a checklist de não tê-los esquecido.

# CSRF, XSS e o armazenamento de tokens

O Cap 7 tratou CSRF em profundidade; vale recolocá-lo no quadro do atacante. CSRF explora que o navegador anexa cookies automaticamente — o atacante faz seu navegador enviar uma requisição autenticada que você não quis. A defesa é dupla: SameSite nos cookies (Caps 7, 14) e tokens anti-CSRF onde necessário. XSS é o primo mais perigoso: se o atacante injeta script na sua página, ele rouba o que o script alcança — e é isso que decide onde guardar tokens.

Por que tokens vão em cookie httpOnly, não em localStorage
localStorage é acessível por qualquer JavaScript na página — um único XSS lê todos os tokens ali e os exfiltra. Um cookie httpOnly é invisível ao JavaScript: mesmo com XSS, o atacante não lê o token (embora ainda possa fazer requisições no contexto da vítima — daí CSRF e CSP importarem). A regra: tokens de sessão em cookie httpOnly + Secure + SameSite (Caps 5-7), nunca em localStorage. O custo de errar isso é que um XSS deixa de ser roubo de sessão temporário e vira comprometimento persistente.

# Os princípios transversais

Acima das categorias específicas estão três princípios que organizam toda decisão de segurança — e que reaparecem em quase todos os capítulos deste volume.

Defesa em profundidade: nenhum controle é a única linha. Rate limiting e hash lento e lockout protegem o login — se um falha, os outros seguram. A autorização acontece no middleware e no handler e na query (Cap 18). Camadas redundantes significam que uma falha isolada não vira brecha.

Menor privilégio: conceda o mínimo necessário, nunca o máximo conveniente. Papel padrão viewer (Cap 16), token com escopo estreito, sessão com expiração curta, permissão por instância. O que não foi explicitamente concedido é negado.

Falhar fechado: quando algo dá errado — exceção, dependência fora, caso não previsto — o sistema deve negar, não liberar. Um catch que retorna 500 é seguro; um que retorna 200 com dados é uma brecha. A ausência de uma regra de autorização deve bloquear, não passar.

fail-closed.ts
// Falhar fechado: o default do switch NEGA; um papel novo não tratado é barrado
function authorize(role: Role, action: Permission): boolean {
  switch (role) {
    case 'admin':  return true
    case 'editor': return can('editor', action)
    case 'viewer': return can('viewer', action)
    default:
      // papel desconhecido = negar, nunca cair em "permitir por omissão"
      return false
  }
}

// Falhar fechado num try/catch: erro inesperado vira negação, não vazamento
app.get('/api/secret', requireAuth, async (c) => {
  try {
    if (!authorize(c.get('user').role, 'settings:manage')) {
      return c.json({ error: 'Negado' }, 403)
    }
    return c.json(await loadSecret())
  } catch {
    return c.json({ error: 'Erro interno' }, 500)  // nega, não vaza
  }
})
Segurança é processo, não estado
Um sistema não "está seguro" de uma vez por todas — dependências ganham CVEs, requisitos mudam, código novo introduz falhas. Trate segurança como prática contínua: mantenha dependências atualizadas (Cap 20), rode varredura automática (a própria revisão de segurança que o Claude Code oferece), faça threat modeling em features sensíveis, e revise autorização em todo PR que toca dados. O conhecimento dos Caps 1-20 é o que torna essa revisão possível — você só protege o que entende.

# Ciclo de vida da sessão

Uma sessão não é só criada e validada — ela tem um ciclo completo que produção precisa fechar inteiro. Criação na autenticação, rotação ao elevar privilégio (anti session fixation, Cap 21), renovação deslizante para não deslogar o usuário ativo, expiração absoluta para limitar a janela de um token roubado, e invalidação no logout — que precisa ser real, apagando o registro no servidor, não só o cookie no cliente.

session-lifecycle.ts
// Expiração dupla: absoluta (teto rígido) + idle (inatividade)
interface SessionRecord {
  id: string
  userId: string
  createdAt: Date
  expiresAt: Date      // teto absoluto: ex. 30 dias, nunca estendido
  lastSeenAt: Date     // renovação deslizante por inatividade
}

const IDLE_MS = 7 * 24 * 60 * 60_000    // 7 dias sem uso = expira

async function validateAndRefresh(token: string): Promise<User | null> {
  const s = await getSession(token)
  const now = Date.now()
  if (!s) return null

  // expirada por qualquer um dos dois critérios = inválida
  if (s.expiresAt.getTime() < now || s.lastSeenAt.getTime() + IDLE_MS < now) {
    await deleteSession(s.id)   // limpa o registro morto
    return null
  }
  // renovação deslizante: marca atividade (throttle para não escrever a cada req)
  if (now - s.lastSeenAt.getTime() > 60_000) await touchSession(s.id, now)
  return await getUser(s.userId)
}

// Logout real: apaga no servidor — o cookie sozinho não basta
async function logout(c: Context, token: string) {
  await deleteSession(hashToken(token))   // invalida de fato (Cap 6)
  deleteCookie(c, 'session')
}
Logout que só apaga o cookie é teatro
Deletar o cookie no cliente não invalida a sessão — quem copiou o token antes (um XSS, um proxy, um log) continua autenticado até a expiração. Logout de verdade apaga o registro no servidor (sessão opaca, Cap 6) ou adiciona o token a uma denylist até expirar (JWT, Cap 10). Ofereça também "encerrar todas as sessões": liste as sessões do usuário e apague-as em massa — essencial após troca de senha ou suspeita de comprometimento.

# Observabilidade: ver o ataque acontecendo

Os controles dos capítulos anteriores bloqueiam ataques; a observabilidade os revela. Um pico de 401s num e-mail específico é brute force em curso (Cap 19). Um login de um país novo é credential stuffing bem-sucedido. Sem logar os eventos certos, o primeiro sinal de invasão é o usuário reclamando. Logue eventos de auth — sempre sem dados sensíveis no log — e alarme sobre os padrões anômalos.

audit-log.ts
// Eventos de auth como dados estruturados — nunca a senha, nunca o token
type AuthEvent =
  | 'login.success' | 'login.failure' | 'login.locked'
  | 'logout' | 'session.expired'
  | 'password.changed' | 'mfa.challenge'

function audit(event: AuthEvent, meta: { userId?: string; ip: string; ua?: string }) {
  logger.info({
    event,
    userId: meta.userId ?? null,
    ip: meta.ip,
    ua: meta.ua,
    at: new Date().toISOString(),
  })
  // Alarmes derivam daqui: N login.failure/min por conta -> notificar
}
O que NUNCA vai para o log
Senhas (nem com hash), tokens de sessão, JWTs, códigos OTP, secrets, refresh tokens — nada disso pode tocar um log, que é copiado, indexado e lido por muita gente. Logar um token é vazá-lo. Logue o evento e o identificador (userId, IP), nunca o segredo. Cuidado também com objetos inteiros em logger.info(user) — eles arrastam o passwordHash junto. Logue campos explícitos, não objetos completos.

# Segredos e rotação de chaves

Toda a segurança criptográfica do volume repousa sobre segredos — o JWT signing key (Cap 9), os client secrets de OAuth (Cap 12), a connection string do banco. Em produção eles vivem em variáveis de ambiente ou num gerenciador de segredos (Vault, AWS Secrets Manager), nunca no repositório, e precisam rotacionar sem derrubar sessões válidas.

    .setProtectedHeader({ alg: 'HS256', kid: keys.current.kid })

# Checklist de produção

Antes de um deploy que toca autenticação, vale percorrer uma lista — não por burocracia, mas porque a falha de auth mais cara é a que ninguém revisou. Cada item remete a um capítulo; a tabela ao final consolida.

O checklist mínimo antes do deploy
Senhas com Argon2 e comparação timing-safe (Cap 2). Cookies httpOnly+Secure+SameSite, HTTPS forçado (Caps 5-7). Rate limiting em login, refresh e envio de OTP (Cap 19). Autorização no servidor em todo endpoint, checada por instância (Caps 16-18). Sessões com expiração absoluta + idle, logout que invalida no servidor (este cap). Segredos fora do repositório, rotação de chaves prevista. Eventos de auth logados sem dados sensíveis. Dependências de auth atualizadas (Cap 20) e varredura de segurança rodada (Cap 21). Cada "sim" é um vetor fechado.
