Capítulo 1

O shell o que é e como funciona

O Volume XV empacotou o ambiente num container; mas é no terminal que você o opera — constrói a imagem, inspeciona o container, dispara o deploy. Na verdade, toda a coleção desemboca aqui: rodar testes, usar o git, automatizar o repetitivo, tudo acontece no shell. Ele não é uma relíquia anterior às interfaces gráficas; é a interface mais precisa e programável que existe, e dominá-lo multiplica a produtividade de tudo o que veio antes. Este capítulo estabelece o modelo mental antes de qualquer comando: o que é um shell, o ciclo de ler-expandir-executar que governa cada linha que você digita, a diferença entre usar o terminal interativamente e programá-lo em scripts, e onde rodar Bash no Windows. Entender o shell como um interpretador de uma linguagem — não uma lista de comandos a decorar — é o que torna todo o resto deste volume coerente.

# Terminal, shell, prompt: três coisas distintas

As palavras se confundem, mas nomeiam camadas diferentes. O terminal (ou emulador de terminal) é o programa de janela que exibe texto e captura o teclado — a moldura. O shell é o programa que roda dentro do terminal e de fato interpreta o que você digita, executando comandos — o motor. O prompt é o texto que o shell mostra esperando sua entrada (o $ ou %). Você digita no terminal, mas é o shell que lê, entende e age. O Bash (Bourne Again Shell) é um shell específico — o mais difundido em Linux e o foco deste volume.

terminal
# O prompt ($) é o shell dizendo "estou pronto, digite um comando"
$ echo "olá"
olá

# Qual shell está rodando agora?
$ echo $SHELL
/bin/bash

# Qual a versão do Bash?
$ bash --version
GNU bash, version 5.2...

# O ciclo do shell: ler, expandir, executar

Aqui está o modelo que organiza o volume inteiro. Para cada linha que você digita, o shell faz três coisas, sempre nessa ordem. Primeiro lê a linha e a divide em palavras (tokens). Depois expande — substitui variáveis pelos seus valores, expande curingas em nomes de arquivo, executa substituições de comando (Caps 8 e 14). Só então executa — encontra o programa correspondente à primeira palavra e o roda, passando as demais palavras como argumentos. A maioria das surpresas no shell ("por que isso não funcionou como eu esperava?") se resolve entendendo que a expansão acontece antes da execução — o comando recebe o resultado já expandido, não o que você digitou.

terminal
# Você digita:
$ echo $HOME/*.txt

# O shell EXPANDE antes de executar:
#   $HOME  -> /home/voce          (expansão de variável)
#   *.txt  -> notas.txt lista.txt (expansão de curinga, Cap 8)

# O 'echo' só recebe o resultado JÁ expandido:
#   echo /home/voce/notas.txt /home/voce/lista.txt
/home/voce/notas.txt /home/voce/lista.txt
A expansão acontece antes da execução
Esta é a ideia mais importante do capítulo. O comando que você digita não é o que o programa recebe — o shell o transforma primeiro. Quando um curinga * "funciona", não é o programa que o entende: o shell já o expandiu para a lista de arquivos antes de chamar o programa. Quando uma variável $x aparece num comando, o shell a substitui pelo valor antes de executar. Essa ordem — expandir, depois executar — explica praticamente todo comportamento "estranho" do shell, e é por isso que aspas (Cap 14) importam tanto: elas controlam o que é expandido e o que é tratado literalmente.

# Interativo vs script: a mesma linguagem

Há duas formas de usar o shell, e a percepção que destrava tudo é que são a mesma linguagem. No modo interativo, você digita comandos um a um e vê o resultado na hora — exploração, diagnóstico, tarefas pontuais. Num script, você escreve uma sequência de comandos num arquivo e o shell os executa em lote — automação, repetição confiável. Tudo que funciona interativamente funciona num script e vice-versa; o script é apenas comandos do shell salvos para rodar depois. Por isso aprender o shell interativamente já é aprender a programá-lo: a transição para scripts (Cap 13) é de empacotamento, não de linguagem.

terminal
# Interativo: um comando, resposta imediata
$ date
qua 07 jun 2026 14:30:00

# Os mesmos comandos num arquivo viram um script (Cap 13):
#   #!/bin/bash
#   date
#   echo "backup concluído"

# ...que se roda em lote, sempre igual:
$ bash meu-script.sh

# Comandos internos vs externos

Quando você digita um comando, o shell o resolve de uma de duas formas. Alguns comandos são internos (builtins) — fazem parte do próprio shell, como cd, echo, export. Outros são externos — programas independentes que vivem como arquivos no sistema (em pastas como /bin, /usr/bin), como ls, grep, git. O shell encontra os externos procurando-os nos diretórios listados na variável PATH (Cap 20). Saber se um comando é interno ou externo, e onde ele vive, é o primeiro passo de muitos diagnósticos.

terminal
# 'type' diz o que um comando é: builtin, arquivo, alias...
$ type cd
cd is a shell builtin

$ type ls
ls is /usr/bin/ls          # programa externo

# 'which' localiza o arquivo de um comando externo
$ which git
/usr/bin/git

# O shell procura externos nos diretórios do PATH (Cap 20)
$ echo $PATH
/usr/local/bin:/usr/bin:/bin

# Bash no Windows: Git Bash e WSL

O Bash é nativo de Linux e macOS, mas você está no Windows — onde há dois caminhos para rodá-lo, ambos já presentes no seu mundo de desenvolvimento. O Git Bash vem com o Git (Vol XIV): instala um ambiente Bash mínimo, suficiente para a maioria dos comandos e scripts. O WSL 2 (Windows Subsystem for Linux) — o mesmo que o Docker Desktop usa por baixo (Vol XV, Cap 3) — roda uma distribuição Linux completa dentro do Windows, com um Bash de verdade e todo o ecossistema. Para scripts e trabalho sério de shell no Windows, o WSL 2 é a opção mais fiel; o Git Bash resolve o dia a dia.

PowerShell é outro shell, não Bash
O Windows tem seu próprio shell poderoso, o PowerShell, com uma linguagem própria bem diferente do Bash — objetos em vez de texto, verbos-substantivo (Get-ChildItem em vez de ls), outra sintaxe de variáveis e controle de fluxo. Ele é excelente no contexto Windows, mas não é Bash: scripts .sh não rodam nele, e os comandos deste volume pressupõem Bash. Quando seguir este manual no Windows, use Git Bash ou WSL 2 — não o PowerShell. A boa notícia: o Bash que você aprende aqui é o mesmo que roda nos containers (Vol XV), nos servidores Linux e no CI, então o conhecimento transfere para todo lugar onde o software de fato é implantado.

Capítulo 2

Navegação e o sistema de arquivos

Antes de manipular arquivos, é preciso saber onde você está e como chegar onde quer — e no shell isso é literal. Toda sessão de terminal tem um diretório de trabalho atual, e quase todo comando opera em relação a ele. Este capítulo cobre a navegação: como o sistema de arquivos é organizado numa árvore única, a diferença crucial entre caminhos absolutos e relativos, os atalhos que tornam o movimento rápido (., .., ~, -), e como listar e entender o conteúdo dos diretórios. É um capítulo fundamental no sentido literal — sem um modelo claro de "onde estou e como me refiro a outros lugares", todo comando posterior fica confuso. Com ele, navegar vira reflexo, e os caminhos que você passa aos comandos param de ser tentativa e erro.

# A árvore única de diretórios

Diferente do Windows, com suas letras de unidade (C:, D:), sistemas Unix têm uma única árvore de diretórios, que começa na raiz, representada por /. Tudo pende dessa raiz: /home guarda as pastas dos usuários, /usr/bin os programas, /etc as configurações, e assim por diante. Não há "drives" separados — dispositivos adicionais são montados em algum ponto da mesma árvore. Essa unicidade simplifica o modelo: qualquer arquivo no sistema tem um caminho que parte de /.

terminal
# pwd (print working directory): onde estou agora?
$ pwd
/home/voce/projetos

# A árvore parte de / (a raiz). Alguns diretórios-padrão:
#   /home  -> pastas dos usuários
#   /usr   -> programas e bibliotecas
#   /etc   -> arquivos de configuração
#   /tmp   -> arquivos temporários

Repare que os exemplos acima escapam as setas em comentários — no shell, -> é só texto, mas a disciplina de pensar em "para onde aponta" ajuda a ler a hierarquia. O ponto prático: pwd é a primeira pergunta que você faz quando algo não funciona — "será que estou na pasta certa?".

# Caminhos absolutos vs relativos

Esta é a distinção que mais confunde no início e que, uma vez clara, resolve metade dos erros de "arquivo não encontrado". Um caminho absoluto começa em / e descreve a localização completa, independente de onde você está — /home/voce/projetos/app.js aponta para o mesmo arquivo sempre. Um caminho relativo não começa com / e é interpretado a partir do diretório atual — app.js significa "o app.js da pasta onde estou agora", então aponta para arquivos diferentes conforme o seu pwd.

terminal
# ABSOLUTO: começa em /, sempre o mesmo lugar
$ cat /home/voce/projetos/app.js

# RELATIVO: a partir do diretório atual (depende do pwd)
$ pwd
/home/voce/projetos
$ cat app.js          # = /home/voce/projetos/app.js

$ cd /tmp
$ cat app.js          # agora = /tmp/app.js (provavelmente não existe!)

# Os atalhos: . .. ~ -

Quatro símbolos tornam a navegação rápida, e aparecem em comandos o tempo todo. . é o diretório atual (útil para "aqui mesmo"). .. é o diretório pai (um nível acima). ~ (til) é o seu diretório home (/home/voce) — um atalho universal. E -, com o cd, volta ao diretório anterior, como um "voltar" do navegador. Combiná-los permite movimentos precisos sem digitar caminhos longos.

terminal
cd ~              # vai para o seu home (= cd sozinho também)
cd ..             # sobe um nível (para o diretório pai)
cd ../..          # sobe dois níveis
cd ~/projetos     # home + subpasta
cd -              # volta ao diretório anterior (alterna como um toggle)

# '.' aparece muito: "copie para AQUI", "rode o script daqui"
cp /tmp/dado.txt .   # copia o arquivo para o diretório atual
~ e $HOME são o mesmo lugar
O til ~ e a variável $HOME apontam ambos para o seu diretório pessoal, mas com uma diferença sutil: ~ é expandido pelo shell (Cap 1) antes da execução, e só no início de uma palavra; $HOME é uma variável de ambiente (Cap 20), expandida em qualquer posição. Na prática você usa ~ interativamente por ser curto, e $HOME em scripts por ser mais explícito e robusto dentro de aspas (Cap 14). Ambos resolvem para /home/voce. Saber que são equivalentes evita confusão ao ver os dois em comandos diferentes fazendo a mesma coisa.

# ls: listando o conteúdo

O ls lista o conteúdo de um diretório, e suas opções revelam diferentes níveis de detalhe. Sozinho, mostra os nomes. Com -l (long), mostra uma linha por item com permissões, dono, tamanho e data (a coluna de permissões é assunto do Cap 7). Com -a (all), inclui arquivos ocultos — os que começam com ., como .env e .gitignore (Vols XIII-XIV), que o ls normal esconde. Combinar opções é o normal: ls -la é talvez o comando mais digitado de todos.

terminal
ls                # só os nomes (arquivos visíveis)
ls -l             # formato longo: permissões, dono, tamanho, data
ls -a             # inclui ocultos (.env, .git, ...)
ls -la            # longo + ocultos (o mais usado)
ls -lh            # tamanhos legíveis (K, M, G em vez de bytes)

# Saída típica do -l:
# -rw-r--r-- 1 voce voce 1.2K jun  7 14:30 app.js
#  ^permissões  ^dono ^grupo ^tam  ^data    ^nome

# Autocompletar com Tab

O recurso mais valioso da navegação não é um comando, é uma tecla: Tab. Ao digitar parte de um nome de arquivo ou comando e apertar Tab, o shell completa automaticamente — e se houver ambiguidade, apertar Tab duas vezes lista as opções. Isso transforma a navegação: você nunca digita caminhos longos por inteiro, evita erros de digitação, e descobre o que existe numa pasta sem rodar ls. É um hábito que separa quem luta com o terminal de quem voa nele.

Tab é o recurso mais subestimado do shell
Pegue o hábito de apertar Tab constantemente — depois de algumas letras de qualquer nome. Digitou cd ~/proj e Tab? Vira cd ~/projetos/. Continuou com app e Tab? Completa o arquivo. Além de rápido, é uma rede de segurança: se o Tab não completa, o que você digitou não existe — você pegou o erro antes de rodar o comando. O autocompletar também funciona para nomes de comandos e, com configuração, para opções e argumentos de muitas ferramentas (git, docker). Dominar o Tab reduz drasticamente erros de digitação em caminhos, que são a causa nº 1 de "arquivo não encontrado".

Capítulo 3

Comandos, argumentos e opções

Todo comando que você digita segue uma gramática, e conhecê-la transforma o terminal de uma série de fórmulas mágicas memorizadas numa linguagem que você lê e compõe. O Capítulo 1 mostrou que o shell divide a linha em palavras; este capítulo explica o que cada palavra significa: a primeira é o comando, e as demais são opções (que modificam o comportamento) e argumentos (sobre o que o comando age). Entender essa estrutura — e as convenções que quase todos os comandos seguem para opções curtas, longas e combinadas — permite ler um comando desconhecido e adivinhar o que ele faz, e construir comandos novos sem decorar cada um. É a gramática que torna os milhares de utilitários do shell aprendíveis: você não memoriza cada um, aprende o padrão que quase todos compartilham.

# A anatomia de um comando

Um comando tem três partes, na ordem: o comando (o programa a executar), as opções (que ajustam como ele age, geralmente prefixadas por -), e os argumentos (sobre o que ele age — arquivos, textos, alvos). Nem todo comando usa as três partes, mas a ordem é convencional. Voltando ao ciclo do Capítulo 1: o shell divide tudo isso em palavras separadas por espaços, expande o que houver para expandir, e entrega ao programa a primeira palavra como o comando e as demais como uma lista de argumentos.

terminal
ls -l /home/voce
# │   │      │
# │   │      └─ argumento: sobre o que agir (o diretório a listar)
# │   └──────── opção: como agir (-l = formato longo)
# └──────────── comando: o programa a executar

cp -r origem/ destino/
# cp com a opção -r (recursivo) e DOIS argumentos (origem e destino)

# Opções curtas e longas

As opções vêm em dois estilos, e a maioria dos comandos oferece os dois para a mesma funcionalidade. As curtas são uma letra precedida de um hífen: -l, -a, -r — rápidas de digitar, ótimas no uso interativo. As longas são uma palavra precedida de dois hífens: --all, --recursive, --help — mais verbosas, mas autoexplicativas, ideais em scripts onde a clareza importa mais que a brevidade. Frequentemente -a e --all são a mesma opção com dois nomes.

terminal
# Curta e longa, mesma coisa:
ls -a
ls --all

# Opções longas que recebem valor usam = ou espaço:
grep --color=auto "erro" log.txt
sort --field-separator="," dados.csv

# Em scripts, prefira longas pela legibilidade (quem lê entende sem manual)
tar --create --gzip --file=backup.tar.gz pasta/

# Combinando opções curtas

Uma conveniência das opções curtas: várias podem ser agrupadas sob um único hífen. ls -l -a pode ser escrito ls -la — o shell entende que são duas opções, não uma chamada la. Isso explica os comandos compactos que você vê por aí: tar -xzvf são quatro opções (-x -z -v -f) agrupadas. Só funciona com opções curtas que não recebem valor; a última do grupo pode receber um valor (como o -f que pega o nome do arquivo).

terminal
# Estas três formas são equivalentes:
ls -l -a -h
ls -lah
ls -la -h

# Clássico do tar: -x -z -v -f agrupados em -xzvf
tar -xzvf backup.tar.gz
#     │││└─ f: o arquivo (recebe o nome a seguir)
#     ││└── v: verbose (mostra o progresso)
#     │└─── z: descomprime gzip
#     └──── x: extrai
A ordem das opções (quase sempre) não importa
Para a grande maioria dos comandos, a ordem das opções entre si é irrelevante — ls -la e ls -al fazem o mesmo. O que importa é a separação entre opções e argumentos: convencionalmente as opções vêm antes dos argumentos. Há exceções (alguns comandos param de aceitar opções após o primeiro argumento), e opções que recebem valor precisam do valor logo após elas. Mas como regra mental: opções modificam o comportamento e podem vir em qualquer ordem entre si; argumentos são posicionais e sua ordem costuma importar (em cp origem destino, trocar a ordem inverte o sentido).

# O separador -- : fim das opções

Há um truque importante para um problema sutil: e se um argumento começa com hífen, mas você quer que seja tratado como argumento, não como opção? Por exemplo, um arquivo chamado -arquivo.txt, ou buscar a string literal --erro. O separador -- (dois hífens sozinhos) diz ao comando "acabaram as opções; tudo depois disto é argumento". É uma defesa essencial em scripts, onde nomes de arquivo vêm de fontes que você não controla e podem começar com hífen.

terminal
# Problema: um arquivo cujo nome começa com hífen
rm -arquivo.txt        # ERRO: rm acha que -a é uma opção

# Solução: -- encerra as opções; o resto é argumento
rm -- -arquivo.txt     # agora -arquivo.txt é tratado como nome

# Buscar uma string que começa com hífen
grep -- "--erro" log.txt

# Vários comandos numa linha

Você pode encadear comandos numa só linha, com operadores que controlam a relação entre eles. O ; separa comandos que rodam em sequência, independentemente do resultado de cada um. O && só roda o próximo se o anterior teve sucesso (código de saída 0). O || só roda o próximo se o anterior falhou. Esses operadores — que reaparecem em todo script (Cap 15) e que você já viu nos Dockerfiles (Vol XV) — codificam lógica condicional de forma compacta.

terminal
# ; : rode um depois do outro, não importa o resultado
cd /tmp; ls

# && : rode o segundo SÓ SE o primeiro teve sucesso
cd projeto && npm test
# (se o cd falhar, o npm test NÃO roda — evita rodar no lugar errado)

# || : rode o segundo SÓ SE o primeiro falhou (plano B)
mkdir dados || echo "pasta já existe"
&& é a base de comandos seguros
O && não é só conveniência — é segurança. cd projeto && rm -rf build garante que o rm só roda se o cd deu certo; sem o &&, se a pasta projeto não existisse, o cd falharia mas o rm rodaria no diretório errado, apagando o build de outro lugar. Por isso você viu && em toda parte nos Dockerfiles (Vol XV): encadear com && garante que cada passo só prossegue se o anterior funcionou. É o mesmo "falhar cedo" que torna scripts robustos (Cap 21). Pegue o hábito de usar && em vez de ; sempre que o segundo comando dependa do sucesso do primeiro.

Capítulo 4

Ajuda e documentação

Ninguém decora os milhares de comandos do shell, nem todas as opções dos que usa. O que distingue quem domina o terminal não é memória, é saber consultar — encontrar rápido a opção que precisa, entender um comando desconhecido, descobrir o que está disponível. O Unix tem uma tradição forte de documentação embutida: cada comando carrega sua própria referência, acessível sem sair do terminal nem abrir um navegador. Este capítulo é curto e prático, mas talvez o mais útil do volume a longo prazo: as ferramentas de ajuda — man, --help, tldr, apropos —, como navegá-las, e como ler a notação que toda essa documentação compartilha. Aprender a pescar é melhor que receber o peixe: com estas ferramentas, você resolve sozinho dúvidas que de outra forma exigiriam uma busca na web.

# --help: a referência rápida

A forma mais rápida de ajuda: quase todo comando aceita a opção --help (ou -h), que imprime um resumo do uso, as opções disponíveis e exemplos — direto no terminal, em segundos. É o primeiro lugar para olhar quando você esqueceu uma opção ou quer ver rapidamente o que um comando oferece. A saída costuma ser concisa: a linha de uso (sintaxe), seguida da lista de opções com descrições curtas.

terminal
# Resumo rápido de qualquer comando
ls --help
grep --help

# Saída típica: a linha de "Usage" mostra a sintaxe
# Usage: ls [OPTION]... [FILE]...
#   -a, --all      do not ignore entries starting with .
#   -l             use a long listing format

# Se a ajuda for longa, paginar com less (Cap 6):
grep --help | less

# man: o manual completo

Para a documentação completa — não o resumo, mas a referência detalhada com cada opção explicada e notas de comportamento —, existe o man (de manual). Cada comando tem uma página de manual, e man comando a abre num paginador navegável. As páginas de man seguem uma estrutura consistente: nome e descrição curta, sinopse (a sintaxe), descrição detalhada, opções, exemplos e referências relacionadas. É a fonte autoritativa — mais completa que --help, ainda que mais densa.

terminal
# Abrir o manual completo de um comando
man ls
man grep

# Dentro do man (que usa o paginador less, Cap 6):
#   Setas / PageUp / PageDown  -> navegar
#   /palavra                   -> buscar "palavra"
#   n / N                      -> próxima / anterior ocorrência
#   q                          -> sair
Lendo a sinopse: [opcional] e <obrigatório>
A linha de sinopse de uma página de man (ou de um --help) usa uma notação convencional que vale decodificar. Colchetes [ ] indicam algo opcional — ls [OPTION]... [FILE]... significa que opções e arquivos são opcionais. Reticências ... indicam que o item pode se repetir (vários arquivos). Itens sem colchetes são obrigatórios. Texto em maiúsculas ou entre < > é um placeholder que você substitui (FILE = um nome de arquivo de verdade). Uma barra | entre opções significa "um ou outro". Decifrar essa notação — a mesma em todo o Unix — permite ler a sintaxe de qualquer comando sem adivinhação.

# As seções do manual

Um detalhe que confunde: o manual é dividido em seções numeradas, e às vezes o mesmo nome existe em mais de uma. A seção 1 é de comandos de usuário; a 5, de formatos de arquivo; a 8, de comandos de administração. Por exemplo, existe man passwd na seção 1 (o comando para trocar senha) e na seção 5 (o formato do arquivo /etc/passwd). Quando precisar de uma seção específica, passe o número antes do nome.

terminal
# Mesmo nome em seções diferentes:
man passwd        # seção 1 por padrão (o comando passwd)
man 5 passwd      # seção 5 (o FORMATO do arquivo /etc/passwd)

# Descobrir em que seções um nome aparece
man -f passwd     # (= o comando whatis)

# Descobrindo comandos: apropos

E quando você não sabe qual comando usar? O apropos (ou man -k) busca nas descrições de todas as páginas de manual por uma palavra-chave, listando os comandos relacionados. Se você precisa "comprimir um arquivo" mas não lembra o comando, apropos compress mostra os candidatos. É a ferramenta para ir do problema ao comando, em vez de só consultar um comando que você já conhece.

terminal
# "Que comando faz X?" — busca por palavra-chave nas descrições
apropos compress
# gzip (1)   - compress or expand files
# zip (1)    - package and compress (archive) files

# Equivalente:
man -k compress

# tldr: exemplos práticos

As páginas de man são completas, mas densas — às vezes você só quer ver como se usa o comando, com exemplos concretos. O tldr (uma ferramenta da comunidade, instalável à parte) preenche essa lacuna: para cada comando, mostra alguns exemplos práticos dos usos mais comuns, sem o peso da referência completa. Para "como faço X com tar de novo?", tldr tar responde em segundos com exemplos copiáveis, onde o man tar exigiria leitura.

terminal
# Exemplos práticos e diretos (precisa instalar: npm i -g tldr)

# man = referência completa; tldr = receitas rápidas. Use os dois.
A hierarquia da consulta
Na prática, há uma ordem natural de onde olhar conforme a sua dúvida. Esqueci uma opção de um comando que conheço → --help (instantâneo). Quero ver exemplos de uso → tldr. Preciso do comportamento exato, todos os detalhes, casos de borda → man. Não sei qual comando usar → apropos. Dominar essas quatro ferramentas reduz drasticamente as idas ao navegador — e, diferente de uma busca na web, elas mostram a documentação da versão exata instalada na sua máquina, sem o risco de respostas desatualizadas ou para outra versão. A documentação embutida é sempre fiel ao que você tem em mãos.

Capítulo 5

Manipulando arquivos e diretórios

Navegar (Cap 2) é saber onde as coisas estão; agora vamos mexer nelas. Criar, copiar, mover, renomear e apagar arquivos e diretórios são as operações mais básicas e mais frequentes do shell — e algumas delas, especialmente as destrutivas, exigem respeito, porque o terminal não tem lixeira nem "desfazer". Este capítulo cobre o conjunto essencial: mkdir, touch, cp, mv, rm e companhia, com atenção às opções que importam e aos perigos reais. A lição transversal — que ecoa os comandos destrutivos do Git e do Docker (Vols XIV-XV) — é que o shell faz exatamente o que você manda, instantaneamente e sem confirmação por padrão. Essa obediência literal é o seu poder e o seu perigo; usá-la com segurança é menos sobre decorar comandos e mais sobre hábitos que protegem contra o erro de um caractere.

# Criando: mkdir e touch

Para criar um diretório, mkdir (make directory). Para criar um arquivo vazio — ou atualizar a data de um existente —, touch. O mkdir tem uma opção essencial, -p (parents), que cria toda uma cadeia de diretórios aninhados de uma vez, sem reclamar se algum já existe — indispensável em scripts onde você quer garantir que uma estrutura de pastas exista.

terminal
# Criar um diretório
mkdir projeto

# -p: cria toda a cadeia de uma vez (e não falha se já existir)
mkdir -p projeto/src/componentes
# cria projeto, src e componentes em sequência, mesmo que nenhum exista

# Criar um arquivo vazio (ou atualizar a data de modificação)
touch README.md app.js .gitignore

# Copiando: cp

O cp (copy) copia arquivos e diretórios: cp origem destino. A ordem dos argumentos importa — o primeiro é a origem, o último é o destino (Cap 3). Para copiar um diretório com todo o seu conteúdo, é preciso a opção -r (recursive), que desce na árvore copiando tudo. Sem o -r, o cp recusa copiar diretórios.

terminal
# Copiar um arquivo
cp config.json config.backup.json

# Copiar para dentro de um diretório (mantém o nome)
cp app.js src/

# Copiar um DIRETÓRIO inteiro precisa de -r (recursivo)
cp -r projeto/ projeto-copia/

# Copiar vários arquivos para um destino (o último argumento)
cp a.txt b.txt c.txt destino/

# Movendo e renomeando: mv

Um ponto que surpreende: no shell, mover e renomear são o mesmo comando — mv (move). Faz sentido quando você percebe que "renomear" é só mover um arquivo para o mesmo lugar com outro nome. mv velho.txt novo.txt renomeia; mv arquivo.txt pasta/ move. Diferente do cp, o mv não precisa de -r para diretórios — mover uma pasta é mover, não copiar recursivamente.

terminal
# Renomear (mover para o mesmo lugar com outro nome)
mv rascunho.txt final.txt

# Mover para outro diretório (mantém o nome)
mv final.txt documentos/

# Mover E renomear ao mesmo tempo
mv final.txt documentos/entregue.txt

# Mover um diretório (sem -r; mover é mover)
mv projeto-velho/ arquivados/

# Apagando: rm e o perigo real

O rm (remove) apaga arquivos, e rm -r apaga diretórios com todo o conteúdo. Aqui mora o comando mais perigoso do shell, porque ele é imediato e irreversível: não há lixeira, não há "desfazer", não há reflog (ao contrário do Git, Vol XIV). O que rm apaga, some. A combinação rm -rf (recursive + force) apaga uma árvore inteira sem perguntar nada — poderosa e a origem de histórias de terror onde um espaço ou um curinga mal colocado destruiu o que não devia.

terminal
# Apagar um arquivo (imediato, sem lixeira)
rm temporario.txt

# Apagar um diretório e todo o conteúdo (-r recursivo)
rm -r build/

# -i: pede confirmação a cada item (rede de segurança)
rm -i *.log

# -f: força, sem perguntar nada (CUIDADO máximo)
rm -rf node_modules/
rm -rf: o comando que exige respeito
O rm -rf não perdoa, e os desastres vêm de detalhes minúsculos. Um espaço errado em rm -rf / pasta (espaço depois da barra) manda apagar a raiz do sistema. Um curinga amplo demais — rm -rf * no diretório errado — varre tudo ali. Uma variável vazia em rm -rf "$DIR"/* com $DIR indefinido vira rm -rf /*. Três hábitos defendem você: (1) rode ls com o mesmo padrão antes do rm, para ver o que será apagado; (2) use caminhos absolutos ou confira o pwd antes; (3) em scripts, sempre cite variáveis ("$DIR", Cap 14) e valide que não estão vazias (Cap 21). O rm faz exatamente o que você diz — a segurança está em dizer com cuidado.

# Diretórios vazios e links

Dois comandos completam o kit. rmdir remove apenas diretórios vazios — mais seguro que rm -r quando você quer garantir que não está apagando conteúdo por engano (ele recusa se houver algo dentro). E ln -s cria links simbólicos — atalhos que apontam para outro arquivo ou diretório, úteis para referenciar algo de vários lugares sem duplicar. Links simbólicos aparecem em muitas configurações de sistema e de projetos.

terminal
# Remover só se vazio (recusa se houver conteúdo — mais seguro)
rmdir pasta-vazia

# Criar um link simbólico (atalho): ln -s alvo nome-do-link
ln -s /caminho/longo/config.json config
# 'config' agora aponta para o arquivo real; mexer nele mexe no original
Aliase o rm para -i, ou use uma lixeira
Muitos preferem uma rede de segurança permanente contra o rm. Uma opção é criar um alias (Cap 20) alias rm='rm -i', que faz o rm sempre pedir confirmação — mas cuidado, isso cria o hábito de confirmar no automático e pode falhar em scripts. Outra, mais robusta, é instalar uma ferramenta de "lixeira" (como trash-cli) que move arquivos para uma lixeira recuperável em vez de apagar de vez, dando o "desfazer" que o rm não tem. Seja qual for a escolha, o princípio é reduzir o custo de um erro de digitação em algo irreversível — porque, mais cedo ou mais tarde, todo mundo digita um rm que não queria.

Capítulo 6

Visualizando e editando texto

No Unix, quase tudo é texto — código, configuração, logs, dados. Por isso o shell tem um arsenal de ferramentas para ver texto sem abrir um editor gráfico: imprimir um arquivo inteiro, paginar um grande, espiar só o começo ou o fim, acompanhar um log que cresce em tempo real. Este capítulo cobre esse arsenal de visualização — cat, less, head, tail — e dá um primeiro contato com os editores de terminal (nano e vim), para quando você precisa não só ver, mas alterar. São ferramentas que você usa dezenas de vezes por dia: conferir o conteúdo de um arquivo, achar o erro no fim de um log, ler uma configuração. Dominá-las torna o terminal um lugar onde você lê e entende, não só executa.

# cat: imprimir o arquivo inteiro

O cat (de concatenate) despeja o conteúdo de um arquivo direto no terminal. É perfeito para arquivos pequenos — uma configuração, um .env, um script curto — que cabem na tela. O nome vem da sua segunda função: concatenar vários arquivos em sequência. Mas para arquivos grandes, o cat é a ferramenta errada: ele joga tudo de uma vez, e você só vê o final rolar pela tela. Para esses, use less.

terminal
# Imprimir um arquivo pequeno inteiro
cat config.json

# Concatenar vários arquivos (a origem do nome)
cat parte1.txt parte2.txt

# -n: numerar as linhas (útil para referenciar)
cat -n app.js

# less: paginar com conforto

Para arquivos grandes, o less abre o conteúdo num paginador navegável — você rola para cima e para baixo, busca texto, e o arquivo não polui o histórico do terminal. É o mesmo paginador que o man usa (Cap 4), então a navegação já é familiar. Diferente do cat, o less não carrega o arquivo inteiro na memória de uma vez, o que o torna ágil mesmo com arquivos de gigabytes.

terminal
less arquivo-grande.log

# Dentro do less:
#   Espaço / b      próxima / página anterior
#   /palavra        buscar para frente; n = próxima ocorrência
#   G / g           ir ao fim / ao início
#   q               sair

# less também recebe a saída de outro comando por pipe (Cap 10):
cat grande.log | less

# head e tail: começo e fim

Muitas vezes você não quer o arquivo inteiro, só uma ponta. head mostra as primeiras linhas (10 por padrão); tail mostra as últimas. São ideais para espiar a estrutura de um arquivo (o cabeçalho de um CSV) ou os eventos mais recentes (o fim de um log, onde o erro geralmente está). A opção -n controla quantas linhas.

terminal
# Primeiras 10 linhas (ex.: cabeçalho de um CSV)
head dados.csv

# Últimas 20 linhas (ex.: erros recentes de um log)
tail -n 20 app.log

# head -n 5 = primeiras 5; tail -n 5 = últimas 5
head -n 5 grande.txt

# tail -f: acompanhar logs ao vivo

A opção mais valiosa do tail é -f (follow): em vez de mostrar o fim e sair, ela continua mostrando novas linhas conforme o arquivo cresce, em tempo real. É a forma clássica de acompanhar um log enquanto a aplicação roda — você vê cada requisição, cada erro, aparecer na hora. Isso conecta diretamente aos logs do Docker (Vol XV, Cap 19): o docker logs -f é, em essência, um tail -f sobre a saída do container.

terminal
# Acompanhar um log ao vivo (novas linhas aparecem em tempo real)
tail -f app.log
# Ctrl+C para parar de acompanhar

# -F continua seguindo mesmo se o arquivo for rotacionado (Vol XV, Cap 19)
tail -F /var/log/app.log

# Combinar com grep (Cap 11) para filtrar ao vivo só os erros:
tail -f app.log | grep ERROR
cat para pequeno, less para grande, tail -f para vivo
A escolha da ferramenta de visualização segue o tamanho e a situação. Arquivo pequeno que cabe na tela → cat (despeja e pronto). Arquivo grande que você quer explorar → less (pagina sem inundar o terminal). Só uma ponta → head/tail. Um log em movimento → tail -f. Usar cat num arquivo de log de gigabytes é um erro comum — ele tenta despejar tudo, trava o terminal e você perde o começo. Cada ferramenta tem seu nicho; combiná-las com as opções certas é o que torna a leitura de arquivos rápida e sem frustração.

# Editar no terminal: nano e vim

Ver é metade; às vezes você precisa editar — corrigir uma config, ajustar um script — sem sair do terminal. Há dois editores onipresentes. O nano é simples e amigável: abre, você digita, os comandos aparecem no rodapé (^X = Ctrl+X para sair). É perfeito para edições rápidas. O vim é poderoso e modal — tem uma curva de aprendizado real —, mas está em todo sistema Unix e é o que abre por padrão em muitos contextos (como a mensagem de commit do git). Você não precisa dominar o vim, mas precisa saber sair dele.

terminal
# nano: simples, comandos no rodapé. Ideal para edições rápidas.
nano config.json
#   Ctrl+O  salvar      Ctrl+X  sair      Ctrl+K  cortar linha

# vim: poderoso e modal. O essencial é saber SAIR:
vim arquivo.txt
#   i           entrar no modo de inserção (digitar)
#   Esc         voltar ao modo normal
#   :wq         salvar e sair    |    :q!  sair sem salvar
Como sair do vim (a pergunta universal)
Todo mundo já ficou "preso" no vim — é quase um rito de passagem. O motivo é que ele é modal: ao abrir, você está no modo "normal", onde as teclas são comandos, não texto. Digitar não funciona como esperado, e os atalhos óbvios (Ctrl+C, Ctrl+Q) não saem. A sequência de escape é: aperte Esc (garante o modo normal), depois digite :q! e Enter (sair sem salvar) ou :wq e Enter (salvar e sair). Memorize Esc :q! Enter — é o "botão de pânico" que sempre funciona. Vim recompensa quem investe em aprendê-lo, mas para o uso casual, saber entrar (i) e sair (Esc :wq) basta. Se preferir evitá-lo de vez, configure o git e o sistema para usar o nano como editor padrão (via a variável EDITOR, Cap 20).

Capítulo 7

Permissões e propriedade

Aquela coluna críptica que o ls -l mostra — -rwxr-xr-- — não é decoração: é o modelo de segurança do sistema de arquivos Unix, e entendê-lo resolve uma classe inteira de erros ("permission denied") e fecha vetores de segurança. Cada arquivo tem um dono, um grupo, e um conjunto de permissões que dizem quem pode ler, escrever e executar. Este capítulo decodifica essa notação, mostra como alterar permissões com chmod e propriedade com chown, e conecta tudo ao que você já viu: o +x que torna um script executável (Cap 13), o usuário não-root dos containers (Vol XV, Cap 17), e o princípio do menor privilégio do Vol XIII. Permissões são o ponto onde a segurança deixa de ser abstrata e vira três letras que você lê e ajusta — o controle de acesso na sua forma mais concreta.

# Lendo a notação de permissões

A string de 10 caracteres do ls -l se decompõe em partes legíveis. O primeiro caractere é o tipo: - para arquivo comum, d para diretório, l para link. Os nove restantes são três grupos de três, para três classes de usuário: o dono (user), o grupo, e outros (todos os demais). Cada grupo de três mostra as permissões de read (ler), write (escrever) e execute (executar), na ordem; um - no lugar significa que aquela permissão está ausente.

decodificando -rwxr-xr--
-  rwx  r-x  r--
│   │    │    │
│   │    │    └─ OUTROS: r-- (só leitura)
│   │    └────── GRUPO:  r-x (ler e executar, não escrever)
│   └─────────── DONO:   rwx (ler, escrever, executar)
└─────────────── tipo:   - (arquivo comum; d = diretório)

# r = read (ler)   w = write (escrever)   x = execute (executar)
# Cada classe (dono/grupo/outros) tem seu próprio conjunto rwx

# O que r, w, x significam (e diferem em diretórios)

Para arquivos, as três permissões são intuitivas: r permite ler o conteúdo, w permite modificá-lo, x permite executá-lo como programa. Para diretórios, o significado é sutilmente diferente e causa confusão: r permite listar os nomes dentro, w permite criar/apagar arquivos no diretório, e x permite entrar no diretório (fazer cd e acessar seu conteúdo). Sem x num diretório, você não consegue nem entrar nele, mesmo com r.

x em diretório = "atravessar", não "executar"
A maior fonte de confusão com permissões: o x num diretório não significa "executar" (diretórios não rodam), e sim "atravessar" — entrar nele e acessar o que há dentro. Isso explica comportamentos que parecem contraditórios. Você pode ter r num diretório (vê os nomes com ls) mas, sem x, não consegue acessar os arquivos listados nem fazer cd. Inversamente, com x mas sem r, você acessa um arquivo se souber o nome exato, mas não consegue listar. Na prática, diretórios quase sempre precisam de x para serem úteis, e a combinação r-x (listar e atravessar, sem modificar) é a permissão típica de um diretório de leitura.

# chmod simbólico: adicionar e remover

O chmod (change mode) altera permissões, e tem duas sintaxes. A simbólica é a mais legível para mudanças pontuais: você diz quem (user, group, others, all), a operação (+ adiciona, - remove, = define), e a permissão (r, w, x). O caso mais comum que você já encontrou: chmod +x script.sh torna um script executável (Cap 13).

terminal
# Tornar um script executável (adiciona x para todos)
chmod +x script.sh

# Adicionar permissão de escrita para o grupo
chmod g+w arquivo.txt

# Remover leitura e escrita de "outros" (privacidade)
chmod o-rw segredo.txt

# Definir exatamente: dono lê/escreve, mais ninguém vê
chmod u=rw,go= .env       # u=rw, group e others sem nada

# chmod numérico: a notação octal

A segunda sintaxe usa números, e aparece em tutoriais e configs o tempo todo — vale saber lê-la. Cada classe (dono, grupo, outros) ganha um dígito de 0 a 7, que é a soma dos valores das permissões: r=4, w=2, x=1. Então 7 = rwx (4+2+1), 6 = rw- (4+2), 5 = r-x (4+1), 4 = r--. Três dígitos definem as três classes de uma vez. chmod 755 é o clássico de scripts/executáveis (dono rwx, grupo e outros r-x); chmod 644 é o de arquivos comuns (dono rw, demais só leitura).

terminal
# r=4  w=2  x=1 ; soma por classe. Três dígitos: dono grupo outros
chmod 755 script.sh    # rwx r-x r-x  (executável: dono total, demais leem/rodam)
chmod 644 arquivo.txt  # rw- r-- r--  (arquivo: dono edita, demais leem)
chmod 600 .env         # rw- --- ---  (segredo: SÓ o dono, ninguém mais)
chmod 700 ~/.ssh       # rwx --- ---  (privado: só o dono entra)
Segredos e chaves exigem permissões restritas
Permissões são segurança concreta, e alguns arquivos exigem restrição. Uma chave SSH privada com permissões frouxas (legível por outros) é recusada pelo próprio SSH — ele se nega a usar uma chave que qualquer um pode ler, e exige 600 (só o dono). O mesmo princípio vale para o .env com segredos (Vol XIII): chmod 600 .env garante que só o dono leia, fechando o vetor de outro usuário do sistema espiá-lo. É o menor privilégio (Vol XIII, Cap 21) aplicado ao sistema de arquivos: dê a cada arquivo a permissão mínima necessária. Arquivos sensíveis com 644 (legível por todos) são um vazamento esperando acontecer num sistema multiusuário.

# chown: mudando o dono

Enquanto chmod muda o que cada classe pode fazer, chown (change owner) muda quem é o dono e o grupo de um arquivo. É uma operação de administração — geralmente requer privilégios elevados (sudo) — relevante quando arquivos acabam com o dono errado, um cenário comum ao lidar com volumes do Docker (Vol XV, Cap 11), onde arquivos criados dentro de um container podem aparecer no host pertencendo a outro usuário.

terminal
# Mudar o dono de um arquivo (geralmente precisa de sudo)
sudo chown voce arquivo.txt

# Mudar dono E grupo (dono:grupo)
sudo chown voce:devs projeto/

# Recursivo: dono de toda uma árvore (ex.: corrigir após Docker)
sudo chown -R voce:voce node_modules/

Capítulo 8

Globbing e wildcards

O Capítulo 1 estabeleceu que o shell expande antes de executar; o globbing é uma das expansões mais úteis e mais mal-entendidas. Quando você digita *.txt, não é o comando que entende o asterisco — é o shell que o expande para a lista de arquivos que combinam, antes de chamar o comando. Essa distinção, sutil mas fundamental, explica por que globbing funciona com qualquer comando (o comando só recebe nomes já expandidos) e por que às vezes ele "não funciona" como você espera. Este capítulo cobre os curingas — *, ?, [...] —, a expansão de chaves {...}, e os cuidados que separam um glob útil de um perigoso. É um capítulo curto, mas central: globbing aparece em quase todo comando que opera sobre múltiplos arquivos, e entendê-lo de verdade — como expansão do shell, não como mágica do comando — desfaz muita confusão.

# O shell expande, não o comando

A ideia que destrava o capítulo, repetindo o Capítulo 1: o globbing é feito pelo shell, antes da execução. Quando você digita rm *.log, o shell primeiro procura no diretório atual todos os arquivos que combinam com *.log, substitui o padrão pela lista real, e só então chama o rm com essa lista. O rm nunca vê o asterisco — ele recebe rm erro.log acesso.log debug.log. É por isso que globbing funciona com qualquer comando, sem o comando precisar "suportar" curingas: a expansão já aconteceu antes dele entrar em cena.

terminal
# Você digita:
$ ls *.txt

# O SHELL expande *.txt para os arquivos que combinam, ANTES de chamar ls:
#   ls notas.txt lista.txt tarefas.txt

# Prove você mesmo: echo mostra o que o shell expandiu
$ echo *.txt
notas.txt lista.txt tarefas.txt

# Os curingas: * ? [...]

Três curingas cobrem a maioria dos casos. O * (asterisco) combina qualquer sequência de caracteres, inclusive nenhum — *.txt pega todos terminados em .txt, app* todos começados em app. O ? (interrogação) combina exatamente um caractere — arquivo?.txt pega arquivo1.txt e arquivoA.txt, mas não arquivo10.txt. Os [...] (colchetes) combinam um caractere de um conjunto ou intervalo — [abc] combina a, b ou c; [0-9] combina um dígito; [a-z] uma letra minúscula.

terminal
# * : qualquer sequência (incluindo vazia)
ls *.js              # todos os .js
ls src/*            # tudo dentro de src/
ls app.*            # app.js, app.ts, app.css...

# ? : exatamente um caractere
ls log?.txt         # log1.txt, logA.txt — não log10.txt

# [...] : um caractere de um conjunto/intervalo
ls arquivo[12].txt  # arquivo1.txt ou arquivo2.txt
ls [a-c]*           # tudo começando com a, b ou c

# Expansão de chaves: {...}

A expansão de chaves {...} é parente próxima do globbing, mas com uma diferença crucial: ela não depende de arquivos existirem. Enquanto * expande para arquivos que combinam, {a,b,c} simplesmente gera as variações literais — {a,b,c}.txt vira a.txt b.txt c.txt, existindo eles ou não. É perfeita para criar múltiplos arquivos ou diretórios de uma vez, ou gerar sequências. Aceita também intervalos: {1..5} gera 1 2 3 4 5.

terminal
# Gera variações literais (não precisa que existam)
echo arquivo{1,2,3}.txt
# arquivo1.txt arquivo2.txt arquivo3.txt

# Criar uma estrutura de pastas de uma vez
mkdir -p projeto/{src,test,docs}

# Intervalos
echo {1..5}          # 1 2 3 4 5
echo {a..e}          # a b c d e

# Útil para backup: copia config.json para config.json.bak
cp config.json{,.bak}
Glob expande para arquivos; chaves geram texto
A diferença entre os dois é a fonte de confusão mais comum. O globbing (*, ?, []) é resolvido contra o sistema de arquivos — ele expande para os arquivos que de fato existem e combinam; se nenhum combina, na maioria dos shells o padrão é deixado literal. A expansão de chaves ({}) é puramente textual — ela gera todas as combinações independentemente de existirem arquivos. Por isso {} serve para criar coisas novas (arquivos, pastas, sequências) e * serve para selecionar coisas existentes. Lembrar dessa distinção — "glob seleciona o que há, chave gera o que pedi" — evita esperar que um {} filtre arquivos ou que um * crie nomes do nada.

# Arquivos ocultos e o ponto

Um detalhe que pega muita gente: por padrão, o globbing não inclui arquivos ocultos (os que começam com ., como .env e .gitignore, Vols XIII-XIV). Um * no diretório do projeto não pega o .env — o que às vezes é o desejado (não arrastar configs ocultas) e às vezes surpreende ("por que meu cp * não copiou o .gitignore?"). Para incluir ocultos, há padrões específicos ou opções do shell. É uma escolha de design deliberada: arquivos ocultos ficam fora do caminho por padrão.

terminal
# * NÃO pega arquivos ocultos (.env, .gitignore não são incluídos)
ls *               # só os visíveis

# Para incluir ocultos explicitamente:
ls .*              # só os ocultos (cuidado: inclui . e ..)

# No Bash, ativar dotglob faz * incluir ocultos também:
shopt -s dotglob
Confira o glob com ls antes de usá-lo no rm
Como o globbing expande antes da execução, um padrão amplo demais pode capturar mais do que você imagina — e com rm, isso é desastre (Cap 5). A defesa é simples e infalível: rode o padrão com echo ou ls primeiro, veja exatamente para que ele expande, e só então use o mesmo padrão no comando destrutivo. ls *.log antes de rm *.log mostra precisamente o que vai sumir. O perigo extra: um espaço acidental, como rm * .log (espaço antes do ponto), faz o * expandir para tudo no diretório, e o .log vira um segundo argumento — apagando o diretório inteiro. Ver a expansão antes de executar transforma esse risco invisível em algo que você confere com os próprios olhos.

Capítulo 9

Redirecionamento de entrada e saída

Todo programa no Unix nasce com três canais conectados: um de onde lê (entrada) e dois para onde escreve (saída normal e erros). Por padrão, a entrada vem do teclado e as saídas vão para a tela — mas o poder do shell está em redirecionar esses canais: salvar a saída num arquivo, alimentar a entrada de um arquivo, separar erros de resultados. Este capítulo cobre os três canais padrão (stdin, stdout, stderr) e os operadores que os redirecionam — >, >>, <, 2>. É a base sobre a qual os pipes (Cap 10) e quase toda automação se constroem: entender que a saída de um programa não precisa ir para a tela, e que a entrada não precisa vir do teclado, abre o caminho para compor programas e capturar resultados. É também onde mora um perigo silencioso — o > que apaga um arquivo sem avisar.

# Os três canais padrão

Cada processo tem três file descriptors abertos desde o início, numerados. O stdin (entrada padrão, descritor 0) é de onde o programa lê — por padrão, o teclado. O stdout (saída padrão, descritor 1) é para onde ele escreve o resultado normal — por padrão, a tela. O stderr (saída de erro, descritor 2) é para onde ele escreve mensagens de erro e diagnóstico — também a tela, por padrão, mas um canal separado. Essa separação entre stdout (resultado) e stderr (erros) é deliberada e poderosa: permite capturar o resultado de um comando sem capturar suas mensagens de erro, e vice-versa.

os três canais
# Todo processo nasce com três canais:
#   stdin  (0)  -- entrada   -- por padrão: teclado
#   stdout (1)  -- saída     -- por padrão: tela  (o RESULTADO)
#   stderr (2)  -- erros     -- por padrão: tela  (os ERROS, canal à parte)

# Redirecionar = mudar para onde cada canal aponta.

# Redirecionar a saída: > e >>

O operador > redireciona o stdout de um comando para um arquivo, em vez da tela. Mas atenção ao comportamento crucial: > trunca — ele apaga o conteúdo anterior do arquivo e escreve do zero. Para acrescentar ao fim sem apagar, use >>. Essa diferença de um caractere é a fronteira entre "salvar substituindo" e "salvar acrescentando", e confundi-las custa dados.

terminal
# > : redireciona stdout para um arquivo (TRUNCA: apaga o que havia)
echo "primeira linha" > arquivo.txt
echo "substitui tudo" > arquivo.txt   # a linha anterior SUMIU

# >> : ACRESCENTA ao fim, sem apagar
echo "linha 1" > log.txt
echo "linha 2" >> log.txt        # agora log.txt tem as duas

# Salvar a saída de um comando num arquivo
ls -la > listagem.txt
> apaga sem avisar — o erro de um caractere
O > trunca o arquivo de destino imediatamente, antes mesmo de o comando rodar, e sem nenhuma confirmação. Isso cria um desastre clássico: você quer adicionar uma linha a um arquivo importante e digita > em vez de >> — o arquivo é zerado na hora, conteúdo perdido (não há desfazer, Cap 5). Pior ainda, cat arquivo > arquivo (redirecionar um arquivo para ele mesmo) o destrói, porque o shell trunca o destino antes de o cat ler. Hábitos de defesa: use >> por padrão quando quiser preservar, confira duas vezes antes de > num arquivo que importa, e em scripts considere set -o noclobber (que faz o > recusar sobrescrever arquivos existentes). Um caractere separa "acrescentar" de "destruir".

# Redirecionar a entrada: <

O operador < faz o oposto de >: alimenta o stdin de um comando a partir de um arquivo, em vez do teclado. Muitos comandos que leem da entrada padrão podem assim processar um arquivo. É menos comum no dia a dia (muitos comandos aceitam o arquivo como argumento direto), mas essencial para comandos que só leem do stdin, e para os heredocs — uma forma de embutir várias linhas de entrada direto no comando.

terminal
# < : alimenta o stdin de um comando a partir de um arquivo
sort < nomes.txt        # ordena o conteúdo de nomes.txt
wc -l < arquivo.txt     # conta linhas vindas do stdin

# Heredoc (<<): embute várias linhas como entrada
cat << FIM
linha um
linha dois
FIM
# tudo entre <<FIM e FIM vira a entrada do cat

# Separando erros: 2> e 2>&1

Aqui o canal separado do stderr mostra seu valor. Como stdout (1) e stderr (2) são distintos, você pode redirecioná-los independentemente. 2> redireciona só os erros. Isso permite, por exemplo, salvar o resultado num arquivo e os erros em outro, ou descartar os erros mantendo o resultado. E quando você quer os dois juntos, há a sintaxe 2>&1 — "mande o canal 2 para onde o canal 1 está indo", que mescla erros e saída no mesmo destino.

terminal
# Redirecionar SÓ os erros (stderr) para um arquivo
comando 2> erros.txt

# Resultado num arquivo, erros em outro (canais separados)
comando > saida.txt 2> erros.txt

# 2>&1 : mandar os erros para onde a saída vai (juntar os dois)
comando > tudo.txt 2>&1
# a ORDEM importa: > tudo.txt primeiro, depois 2>&1

# &> : atalho moderno para "ambos no mesmo arquivo"
comando &> tudo.txt

# /dev/null: o buraco negro

Às vezes você quer descartar uma saída — não a tela, não um arquivo, o lixo. O /dev/null é um "dispositivo" especial que engole tudo que recebe e devolve nada: redirecionar para ele é jogar fora. O uso mais comum é silenciar mensagens de erro irrelevantes (2> /dev/null) ou rodar um comando só pelo seu efeito, descartando toda a saída. É o equivalente shell de "não me mostre isto, e não guarde".

terminal
# Descartar os erros (silenciar mensagens irrelevantes)
comando 2> /dev/null

# Descartar TODA a saída (rodar só pelo efeito/código de saída)
comando > /dev/null 2>&1

# Ex.: testar silenciosamente se um programa existe
which docker > /dev/null 2>&1 && echo "docker instalado"
stdout é o resultado; stderr é o diagnóstico
A separação entre os dois canais não é capricho — é uma convenção que torna programas componíveis. A regra que bons programas seguem: o resultado (o que outro programa consumiria) vai para o stdout; as mensagens para o humano (progresso, avisos, erros) vão para o stderr. Por isso você consegue fazer comando > resultado.txt e ainda ver os erros na tela — eles foram pelo canal 2, que não foi redirecionado. Isso conecta diretamente aos logs do Docker (Vol XV, Cap 19), onde a aplicação loga para stdout/stderr e o Docker captura ambos. Quando você escrever seus próprios scripts (Cap 13), siga a convenção: echo do resultado para stdout, echo de erros com >&2 para stderr — assim seus scripts se compõem como os comandos nativos.

Capítulo 10

Pipes e composição

Se há uma única ideia que define a cultura Unix, é esta: programas pequenos, que fazem uma coisa bem, conectados para resolver problemas grandes. O pipe (|) é o mecanismo que torna isso real — ele conecta a saída de um comando à entrada do próximo, formando uma linha de montagem onde dados fluem e são transformados a cada estágio. O Capítulo 9 mostrou como redirecionar canais para arquivos; o pipe é o passo seguinte e mais poderoso: redirecionar a saída de um programa direto para a entrada de outro, sem arquivo intermediário. Este capítulo é o coração conceitual do volume. Entender pipes não é aprender um operador — é adotar uma forma de pensar, onde você resolve problemas compondo ferramentas simples em vez de procurar uma ferramenta única que faça tudo. É a filosofia que torna o shell infinitamente mais capaz que a soma dos seus comandos.

# O pipe: conectar saída à entrada

O pipe | pega o stdout (Cap 9) do comando à esquerda e o conecta ao stdin do comando à direita. Em vez de o primeiro comando jogar o resultado na tela, ele o entrega ao segundo, que o processa como sua entrada. Você encadeia quantos quiser, formando um pipeline — uma sequência onde cada estágio recebe o resultado do anterior, transforma, e passa adiante. Os dados fluem da esquerda para a direita, lapidados a cada passo.

terminal
# A saída de ls vira a entrada de grep, sem arquivo no meio
ls -la | grep ".js"

# Um pipeline de vários estágios (dados fluem da esquerda p/ direita):
cat acesso.log | grep ERROR | wc -l
# cat lê o log -> grep filtra os ERROR -> wc -l conta as linhas
# Resultado: quantos erros há no log
A filosofia Unix: faça uma coisa bem
O pipe é a expressão de uma filosofia de design. Em vez de um programa gigante que lê arquivos, filtra, ordena, conta e formata, o Unix oferece pequenos programas especializados — um que filtra (grep), um que ordena (sort), um que conta (wc) — e o pipe para combiná-los. Cada ferramenta faz uma coisa bem e a faz sobre texto, o "formato universal" que todas compartilham. A vantagem é composicional: com N ferramentas simples, você resolve um número enorme de problemas combinando-as, em vez de precisar de uma ferramenta nova para cada problema. Pensar em pipes é pensar "qual sequência de transformações leva da entrada ao que eu quero?" — e essa é a habilidade central do shell, mais valiosa que decorar comandos.

# Construindo um pipeline incrementalmente

O segredo de construir pipelines complexos não é escrevê-los de uma vez — é montá-los estágio a estágio, vendo o resultado a cada adição. Você começa com o primeiro comando, confere a saída, adiciona um pipe e o próximo estágio, confere de novo, e assim por diante. Esse método incremental torna pipelines longos tratáveis: cada passo é uma transformação pequena e verificável, e você nunca está adivinhando o que o conjunto inteiro faz.

terminal
# Objetivo: os 5 IPs que mais aparecem num log de acesso.
# Construa um estágio de cada vez, conferindo a saída:

cat acesso.log                          # 1. ver o log
cat acesso.log | awk '{print $1}'     # 2. extrair o IP (1a coluna)
cat acesso.log | awk '{print $1}' | sort            # 3. ordenar
cat acesso.log | awk '{print $1}' | sort | uniq -c    # 4. contar repetidos
# 5. ordenar por contagem (desc) e pegar o top 5:
cat acesso.log | awk '{print $1}' | sort | uniq -c | sort -rn | head -5

Esse exemplo — extrair, ordenar, contar, ranquear — é o "olá mundo" dos pipelines, e cada estágio usa uma ferramenta que os Caps 11 e 12 detalham. O ponto aqui não são os comandos específicos, mas o método: um problema que pareceria exigir um script foi resolvido compondo cinco ferramentas simples numa linha, construída passo a passo.

# Pipe vs redirecionamento de arquivo

Vale firmar a distinção com o Capítulo 9. O > manda a saída para um arquivo; o | manda a saída para outro comando. São complementares: você usa pipes para encadear transformações em memória, sem tocar o disco, e usa > no fim para salvar o resultado final, se quiser guardá-lo. Misturar os dois é o normal — um pipeline que processa e termina salvando.

terminal
# Pipe encadeia comandos; > salva o resultado final num arquivo
cat log.txt | grep ERROR | sort > erros-ordenados.txt
#  └──── processamento em pipeline ────┘ └── salva o final ──┘

# tee: grava num arquivo E continua o pipe (bifurca o fluxo)
cat log.txt | grep ERROR | tee erros.txt | wc -l
# salva os erros em erros.txt E conta quantos são, ao mesmo tempo

# tee: bifurcar o fluxo

Um comando especial merece destaque no contexto de pipes: o tee. Normalmente um pipe leva os dados de A para B, e a saída de A não fica visível. O tee resolve quando você quer ambos — salvar a saída num arquivo e passá-la adiante no pipe. O nome vem do "T" da plomaria, que divide um cano em dois. É útil para registrar uma etapa intermediária de um pipeline sem interrompê-lo, ou para ver na tela e salvar ao mesmo tempo.

terminal
# tee grava E deixa o fluxo continuar
comando | tee saida.txt          # mostra na tela E salva em saida.txt

# Útil com sudo para escrever em arquivo protegido:
echo "config" | sudo tee /etc/app.conf

# tee -a acrescenta em vez de truncar (como >>)
comando | tee -a log.txt
Pense em transformações, não em ferramentas
A mudança de mentalidade que o pipe traz: ao enfrentar uma tarefa de processamento de texto, pare de procurar "o comando que faz isso" e pergunte "que sequência de transformações leva da entrada ao resultado?". Quero os erros únicos de um log? Entrada (o log) → filtrar erros (grep) → ordenar (sort) → remover duplicatas (uniq). Cada seta é um pipe, cada passo uma ferramenta simples. Essa decomposição é mais poderosa que qualquer ferramenta única, porque combina um vocabulário pequeno de comandos numa infinidade de soluções. E como cada estágio é independente, você depura trocando ou inspecionando um de cada vez. Dominar pipes é menos sobre saber muitos comandos e mais sobre pensar em fluxos de dados — a habilidade que carrega para os filtros (Cap 11), o sed/awk (Cap 12), e todo o scripting adiante.

Capítulo 11

Filtros de texto

Os pipes (Cap 10) só são poderosos por causa das ferramentas que conectam — e as mais usadas são os filtros de texto: programas que leem texto da entrada, transformam de alguma forma, e escrevem o resultado na saída. Cada um faz uma transformação simples — filtrar linhas, ordenar, contar, recortar colunas, remover duplicatas — e juntos, encadeados, resolvem praticamente qualquer tarefa de processamento de texto. Este capítulo cobre o vocabulário essencial: grep (filtrar por padrão), sort (ordenar), uniq (duplicatas), wc (contar), cut (recortar colunas), tr (substituir caracteres). São as peças de Lego do shell — pequenas, especializadas, combináveis. Dominá-las é o que transforma a filosofia de pipes do capítulo anterior em capacidade concreta de manipular logs, dados e saídas de comandos.

# grep: filtrar por padrão

O grep é provavelmente o filtro mais usado: ele lê linhas e imprime apenas as que combinam com um padrão. No uso básico, busca uma string literal; mas seu verdadeiro poder vem das expressões regulares (o tema do Volume XVII), que permitem padrões sofisticados. Suas opções essenciais cobrem os casos do dia a dia: ignorar maiúsculas, inverter (mostrar o que não combina), contar, e mostrar contexto.

terminal
# Filtrar linhas que contêm um padrão
grep "ERROR" app.log

# Opções essenciais:
grep -i "error" app.log    # -i: ignora maiúsculas/minúsculas
grep -v "DEBUG" app.log    # -v: inverte (linhas SEM o padrão)
grep -c "ERROR" app.log    # -c: conta as linhas que combinam
grep -n "TODO" app.js     # -n: mostra o número da linha
grep -r "funcao" src/      # -r: busca recursiva em diretórios

# sort: ordenar

O sort ordena linhas. Por padrão, ordena alfabeticamente (lexicograficamente), mas opções mudam o critério: -n ordena numericamente (essencial, porque alfabeticamente "10" vem antes de "2"), -r inverte (decrescente), -u remove duplicatas no processo. É um estágio frequente em pipelines — frequentemente antes do uniq, que exige entrada ordenada para funcionar.

terminal
sort nomes.txt          # alfabético (padrão)
sort -n numeros.txt      # numérico (10 depois de 2, não antes)
sort -rn numeros.txt     # numérico decrescente (maior primeiro)
sort -u dados.txt        # ordena E remove duplicatas

# -k ordena por uma coluna específica (campo 2):
sort -k 2 -n dados.txt
sort -n vs ordenação alfabética: a pegadinha dos números
Um erro silencioso muito comum: ordenar números sem -n. Por padrão, o sort compara linha por linha como texto, caractere a caractere — e como texto, "10" vem antes de "2" (porque o caractere "1" vem antes de "2"). O resultado é uma ordenação que parece quebrada para olhos humanos: 1, 10, 100, 2, 20, 3. A opção -n faz o sort interpretar as linhas como números, ordenando 1, 2, 3, 10, 20, 100 como se espera. Sempre que ordenar algo numérico — tamanhos, contagens, IDs —, use -n. Esquecê-lo produz resultados que parecem certos à primeira vista mas estão sutilmente errados, especialmente perigoso em pipelines que ranqueiam por contagem.

# uniq: remover duplicatas

O uniq remove linhas duplicadas consecutivas — e essa palavra, "consecutivas", é a chave. Ele só elimina duplicatas que estão lado a lado, então quase sempre vem depois de um sort (que agrupa as iguais). A opção -c (count) é especialmente útil: em vez de só remover, conta quantas vezes cada linha apareceu — a base do padrão "contar ocorrências" visto no Cap 10.

terminal
# uniq só remove duplicatas CONSECUTIVAS -> ordene antes!
sort dados.txt | uniq          # remove duplicatas (após ordenar)

# -c: conta as ocorrências de cada linha (muito usado)
sort dados.txt | uniq -c       # prefixa cada linha com sua contagem

# -d: mostra SÓ as que têm duplicatas; -u: SÓ as únicas
sort dados.txt | uniq -d       # só as repetidas

# Padrão clássico: contar e ranquear (Cap 10)
sort log.txt | uniq -c | sort -rn

# wc: contar

O wc (word count) conta — linhas, palavras e caracteres. A opção mais usada é -l (lines), que conta linhas: "quantos erros no log?", "quantos arquivos?", "quantas linhas de código?". Combinado com pipes, vira a etapa final de inúmeros pipelines de "quantos X existem?".

terminal
wc -l arquivo.txt        # número de linhas
wc -w texto.txt          # número de palavras
wc -c arquivo.bin        # número de bytes

# O uso típico: contar resultados de um filtro
grep ERROR app.log | wc -l     # quantos erros
ls | wc -l                  # quantos arquivos no diretório

# cut e tr: recortar e traduzir

Dois filtros completam o kit essencial. O cut recorta colunas de cada linha — por posição de caractere ou por campos separados por um delimitador (útil para CSVs e saídas tabulares). O tr (translate) substitui ou remove caracteres — trocar minúsculas por maiúsculas, substituir delimitadores, apagar caracteres indesejados. São transformações de baixo nível que aparecem em pipelines para ajustar o formato dos dados entre estágios.

terminal
# cut: recortar campos. -d define o delimitador, -f os campos
cut -d"," -f1,3 dados.csv    # campos 1 e 3 de um CSV
cut -d":" -f1 /etc/passwd    # primeiro campo (nomes de usuário)

# tr: traduzir/remover caracteres
echo "OLÁ" | tr 'A-Z' 'a-z'     # maiúsculas -> minúsculas
echo "a,b,c" | tr ',' '\n'      # vírgulas viram quebras de linha
cat arquivo | tr -d ' '        # -d remove (aqui, espaços)
O vocabulário que se combina sem fim
Estes seis filtros — grep, sort, uniq, wc, cut, tr — mais o head/tail (Cap 6) formam um vocabulário pequeno que se recombina numa infinidade de soluções. "As 10 extensões de arquivo mais comuns num projeto"? ls → cut (a extensão) → sort → uniq -c → sort -rn → head. "Usuários únicos num log"? cut o campo → sort -u. Não há um comando "extensões mais comuns" nem "usuários únicos" — você os constrói compondo o vocabulário. É por isso que aprender bem essas poucas ferramentas rende mais que decorar dezenas de comandos especializados: a combinação é onde mora o poder. O Cap 12 (sed e awk) adiciona duas ferramentas mais poderosas a esse kit, para quando os filtros simples não bastam.

Capítulo 12

sed e awk

Os filtros do Capítulo 11 resolvem muito, mas têm limites: eles selecionam, ordenam e contam, mas não transformam texto de forma sofisticada. Para isso existem dois programas mais poderosos, quase linguagens em si: o sed (stream editor), especialista em substituir e editar texto em fluxo, e o awk, especialista em processar dados estruturados em colunas. Eles ocupam o degrau entre os filtros simples e a escrita de um script completo — quando grep e cut não bastam mas você ainda quer uma linha, não um programa. Este capítulo apresenta o essencial de cada um: o suficiente para os usos do dia a dia — substituição com sed, extração e cálculo com awk — sem mergulhar nas suas profundezas (cada um daria um livro). É também onde as expressões regulares começam a aparecer com força, antecipando o Volume XVII.

# sed: substituir em fluxo

O uso esmagadoramente mais comum do sed é a substituição: trocar um padrão por outro, em cada linha. A sintaxe é s/padrão/substituto/ — s de substitute, com barras separando o que procurar do que colocar no lugar. Por padrão, o sed lê da entrada, aplica a transformação, e escreve o resultado na saída, sem alterar o arquivo original. É o "buscar e substituir" do shell, operando em fluxo dentro de pipelines.

terminal
# s/padrão/substituto/ : substitui a PRIMEIRA ocorrência por linha
echo "olá mundo" | sed 's/mundo/shell/'
# olá shell

# A flag g (global) substitui TODAS as ocorrências da linha
echo "a a a" | sed 's/a/b/g'
# b b b

# Substituir num arquivo (saída para a tela; original intacto)
sed 's/localhost/exemplo.com/g' config.txt
sed -i edita o arquivo no lugar — sem desfazer
Por padrão o sed não toca o arquivo — ele escreve o resultado na saída, deixando o original intacto, o que é seguro. A opção -i (in-place) muda isso: ela sobrescreve o arquivo com o resultado da transformação. É conveniente para editar arquivos em lote, mas perigoso, porque é irreversível (Cap 5) — se o padrão estava errado, você corrompeu o arquivo sem cópia. Dois hábitos protegem: (1) rode o sed sem -i primeiro e confira a saída na tela; só quando estiver certo, adicione o -i. (2) use sed -i.bak (com um sufixo) — isso cria um backup do original com extensão .bak antes de editar, dando um caminho de volta. Editar arquivos em lote com -i sem conferir antes é uma forma rápida de estragar muitos arquivos de uma vez.

# sed: além da substituição

O sed faz mais que substituir. Ele pode apagar linhas que combinam com um padrão, imprimir apenas certas linhas, ou operar em intervalos específicos. Embora a substituição domine o uso, conhecer essas outras capacidades amplia o que você resolve numa linha. A seleção por número de linha ou por padrão é particularmente útil para extrair trechos de arquivos.

terminal
# Apagar linhas que combinam com um padrão (d = delete)
sed '/^#/d' config.txt        # remove linhas de comentário (começam com #)
sed '/^$/d' texto.txt         # remove linhas em branco

# Imprimir um intervalo de linhas (5 a 10)
sed -n '5,10p' arquivo.txt    # -n silencia; p imprime as selecionadas

# Substituir só em linhas que combinam com outro padrão
sed '/ERROR/s/grave/CRÍTICO/' log.txt

# awk: pensar em colunas

Enquanto o sed pensa em linhas e padrões, o awk pensa em colunas. Ele divide automaticamente cada linha em campos (por espaços, por padrão) e dá acesso a cada um por número: $1 é o primeiro campo, $2 o segundo, $0 a linha inteira. Isso o torna perfeito para dados tabulares — logs, CSVs, saídas de comandos em colunas. O uso mais comum é extrair ou reorganizar campos, mas o awk também sabe filtrar por condição e fazer cálculos.

terminal
# $1, $2... são os campos (colunas); $0 é a linha toda
echo "alice 30 dev" | awk '{print $1}'      # alice
echo "alice 30 dev" | awk '{print $3, $1}'  # dev alice

# Extrair uma coluna de uma saída (o IP de cada linha de log)
cat acesso.log | awk '{print $1}'

# -F define o separador de campos (ex.: CSV com vírgula)
awk -F"," '{print $2}' dados.csv     # segundo campo do CSV

# awk: condições e cálculos

O awk vai além de extrair colunas: ele tem condições e aritmética, o que o aproxima de uma mini-linguagem. Você pode imprimir apenas linhas onde um campo satisfaz uma condição, somar valores de uma coluna, ou calcular médias. Esses recursos resolvem tarefas que, de outra forma, exigiriam um script — somar o tamanho de arquivos, filtrar registros por valor, agregar dados.

terminal
# Imprimir só as linhas onde o campo 2 é maior que 100
awk '$2 > 100 {print $1, $2}' dados.txt

# Somar uma coluna (END roda após processar tudo)
awk '{soma += $1} END {print soma}' numeros.txt

# Filtrar por padrão E processar (combina regex + colunas)
awk '/ERROR/ {print $4}' app.log    # campo 4 das linhas com ERROR

# Média de uma coluna
awk '{s += $1; n++} END {print s/n}' dados.txt
sed para texto, awk para colunas — e quando parar
A divisão de trabalho entre os dois: use sed quando o problema é "substituir/editar texto" (trocar uma string, remover linhas, editar configs em lote); use awk quando o problema é "processar dados em colunas" (extrair campos, filtrar por valor, somar). Mas há um limite importante de reconhecer: sed e awk brilham em transformações de uma linha dentro de pipelines. Quando a lógica fica complexa — várias condições, estruturas de dados, muitos passos —, é sinal de que você cruzou para o território de um script (Cap 13) em Bash, Python ou outra linguagem, que será mais legível e manutenível que um awk de vinte linhas espremido numa linha. A habilidade não é só saber usar sed e awk, mas saber quando eles são a ferramenta certa e quando você passou do ponto e deveria escrever um script de verdade.

Capítulo 13

Escrevendo scripts

Até aqui você usou o shell interativamente — um comando, uma resposta. Mas o Capítulo 1 plantou a ideia: comandos do shell salvos num arquivo formam um script, que se executa em lote, sempre igual. Esse é o salto da operação manual para a automação: tarefas que você faria digitando uma sequência de comandos viram um arquivo que roda com um comando só, sem erro de digitação, repetível e compartilhável. Este capítulo cobre a mecânica de transformar comandos em scripts: a linha shebang que diz como executá-los, como torná-los executáveis (o chmod +x do Cap 7), as formas de rodá-los, e a estrutura de um bom script. É a fundação dos capítulos seguintes (variáveis, condicionais, loops, funções) — eles são as ferramentas dentro dos scripts; este capítulo é o recipiente que os contém.

# Um script é só comandos num arquivo

A ideia fundamental, sem mistério: um script é um arquivo de texto contendo os mesmos comandos que você digitaria no terminal, um por linha, executados de cima para baixo. Tudo que funciona interativamente funciona num script. A diferença é o empacotamento — em vez de digitar cinco comandos cada vez, você os salva uma vez e roda o arquivo. Isso elimina erros de digitação, garante que a sequência seja sempre a mesma, e permite compartilhar a automação com outros (ou com o seu eu futuro).

backup.sh
#!/bin/bash
# Um script: os mesmos comandos do terminal, salvos num arquivo

echo "Iniciando backup..."
mkdir -p ~/backups
cp -r ~/projeto ~/backups/projeto-$(date +%Y%m%d)
echo "Backup concluído."

# O shebang: como o arquivo deve ser executado

A primeira linha de um script costuma ser estranha: #!/bin/bash. Chama-se shebang (de hash-bang, # + !), e diz ao sistema qual interpretador deve executar o arquivo. Quando você roda um script executável, o sistema lê a shebang e usa o programa indicado para interpretá-lo — /bin/bash para scripts Bash, /usr/bin/python3 para Python, e assim por diante. Sem shebang, o sistema não sabe como rodar o arquivo. A escolha entre #!/bin/bash e #!/bin/sh tem consequência de portabilidade.

shebangs comuns
# Bash: usa recursos específicos do Bash (arrays, [[ ]], etc.)
#!/bin/bash

# sh POSIX: mais portátil, roda em qualquer sistema Unix,
# mas só com recursos padrão (sem extensões do Bash)
#!/bin/sh

# Forma portátil que acha o bash via PATH (recomendada):
#!/usr/bin/env bash
#!/bin/bash vs #!/bin/sh: qual usar
A escolha da shebang define quais recursos você pode usar. #!/bin/bash dá acesso a tudo do Bash — arrays, [[ ]] para testes (Cap 15), expansões avançadas — ao custo de exigir que o Bash esteja presente. #!/bin/sh aponta para o shell POSIX padrão (que em muitos sistemas é uma versão mais enxuta), garantindo portabilidade máxima, mas sem as extensões do Bash. A regra prática: use #!/bin/bash para os seus scripts pessoais e de projeto (você controla o ambiente, e os recursos do Bash valem a pena); use #!/bin/sh só quando precisa rodar em sistemas mínimos onde o Bash pode não existir (como certas imagens Docker enxutas, Vol XV, Cap 18). A forma #!/usr/bin/env bash é a mais robusta para Bash, pois encontra o bash via PATH em vez de assumir que está exatamente em /bin/bash.

# Tornando executável e rodando

Há duas formas de rodar um script, e a diferença ilumina o papel da shebang e das permissões (Cap 7). A primeira: passar o script como argumento ao interpretador — bash script.sh — que funciona sem permissão de execução e ignora a shebang (você já disse qual interpretador). A segunda, mais idiomática: tornar o script executável com chmod +x e rodá-lo diretamente — ./script.sh —, caso em que o sistema usa a shebang para saber como interpretá-lo.

terminal
# Forma 1: passar ao interpretador (sem precisar de +x; ignora shebang)
bash backup.sh

# Forma 2: tornar executável e rodar direto (usa a shebang)
chmod +x backup.sh        # dá permissão de execução (Cap 7)
./backup.sh               # o ./ é necessário (ver callout)
Por que ./script.sh e não só script.sh
Ao rodar um script executável, você precisa do ./ na frente — ./backup.sh, não backup.sh. O motivo remete ao Capítulo 1: o shell procura comandos nos diretórios do PATH (Cap 20), e o diretório atual não está no PATH por padrão — uma proteção de segurança deliberada. Sem o ./, o shell procura backup.sh no PATH, não o encontra, e falha com "command not found". O ./ diz explicitamente "o script está aqui, neste diretório" (lembre que . é o diretório atual, Cap 2). Essa proteção existe para evitar um ataque: se o diretório atual estivesse no PATH, um arquivo malicioso chamado ls numa pasta qualquer rodaria no lugar do ls real quando você entrasse nela. Exigir o ./ torna a execução de scripts locais sempre explícita e intencional.

# Comentários e estrutura

Um bom script é legível meses depois. Comentários (linhas começando com #) explicam o porquê, como nas mensagens de commit do Git (Vol XIV, Cap 3). Uma estrutura clara — shebang, um cabeçalho explicando o propósito, configuração no topo, depois a lógica — torna o script fácil de entender e modificar. A disciplina que você aplicaria a qualquer código (toda a coleção) vale para scripts: eles são código, e tendem a viver mais e crescer mais do que se espera.

deploy.sh (estrutura)
#!/usr/bin/env bash
# deploy.sh — constrói a imagem e faz push ao registry (Vol XV)
# Uso: ./deploy.sh <versão>

# --- configuração no topo (fácil de ajustar) ---
REGISTRY="ghcr.io/org"
APP="minha-app"

# --- lógica ---
echo "Construindo $APP..."
docker build -t "$REGISTRY/$APP" .
echo "Pronto."

Capítulo 14

Variáveis e expansão

Variáveis dão a scripts a capacidade de guardar e reutilizar valores — um caminho, um nome, o resultado de um comando. Mas no shell, variáveis têm peculiaridades que são a fonte número um de bugs: a sintaxe de atribuição que não admite espaços, a distinção entre definir e usar, e — acima de tudo — a questão das aspas, que decide se o shell trata o valor como um todo ou o quebra em pedaços. Este capítulo cobre variáveis e as formas de expansão que o shell aplica sobre elas (revisitando o "expandir antes de executar" do Cap 1), com ênfase na disciplina de aspas que separa scripts robustos de scripts que quebram com o primeiro espaço num nome de arquivo. É um capítulo tão sobre uma boa prática — sempre citar variáveis — quanto sobre sintaxe.

# Definir e usar: a assimetria

Variáveis no shell têm uma assimetria que confunde: você as define sem cifrão e as usa com cifrão. Para atribuir, nome=valor — e, crucialmente, sem espaços ao redor do = (um espaço quebra tudo, porque o shell interpretaria como um comando). Para usar o valor, prefixe com $: $nome. Essa diferença — definir cru, usar com $ — é a primeira coisa a internalizar.

terminal
# Definir: nome=valor, SEM espaços ao redor do =
nome="Alice"
pasta=/home/voce/projetos

# ERRO comum: espaços quebram a atribuição
#   nome = "Alice"   -> shell tenta rodar o comando 'nome'

# Usar: prefixe com $
echo $nome            # Alice
echo "Olá, $nome"     # Olá, Alice (expande dentro de aspas duplas)
cd $pasta

# A disciplina das aspas

Esta é a seção mais importante do capítulo, e talvez do volume. Quando você usa $variavel sem aspas e o valor contém espaços, o shell o divide em múltiplas palavras (o "word splitting"), porque a expansão acontece antes da execução (Cap 1) e o resultado é re-dividido por espaços. Com "$variavel" (aspas duplas), o shell expande o valor mas o trata como uma única palavra, preservando espaços. A regra, sem exceções práticas: sempre cite suas variáveis com aspas duplas.

terminal
arquivo="meu documento.txt"   # nome com espaço

# SEM aspas: o shell divide em DUAS palavras -> rm recebe dois argumentos
rm $arquivo
#   vira: rm meu documento.txt   -> tenta apagar "meu" E "documento.txt"!

# COM aspas: tratado como UM argumento, o espaço é preservado
rm "$arquivo"
#   vira: rm "meu documento.txt"  -> correto
Sempre cite "$variavel" — é a regra de ouro do shell
Esquecer aspas em variáveis é a causa nº 1 de bugs em scripts, e os mais traiçoeiros, porque o script "funciona" nos seus testes (com nomes sem espaço) e quebra na vida real (com um nome que tem espaço, ou uma variável vazia). Os danos vão de inofensivos a catastróficos: um rm $dir/* com $dir vazio vira rm /* (Cap 5); um cp $origem $destino com espaço no nome copia para o lugar errado. A regra é mecânica e absoluta: toda expansão de variável vai entre aspas duplas — "$nome", "$dir/$arquivo", "${array[@]}". As únicas exceções são casos raros e deliberados onde você quer o word splitting. Na dúvida, cite. É o hábito que mais diferencia scripts amadores de scripts robustos, e o Cap 21 o reforça como parte da escrita defensiva.

# Aspas simples vs duplas

As duas aspas têm comportamentos diferentes, e escolher a certa importa. As aspas duplas ("...") preservam espaços mas permitem expansão — variáveis e substituições de comando dentro delas são processadas. As aspas simples ('...') são literais totais — nada dentro é expandido, o conteúdo é exatamente o que está escrito, incluindo cifrões. Use duplas quando quer expandir variáveis; simples quando quer o texto exato, sem nenhuma interpretação do shell.

terminal
nome="Alice"

# Duplas: expandem variáveis
echo "Olá, $nome"      # Olá, Alice

# Simples: tudo literal, $ não é expandido
echo 'Olá, $nome'      # Olá, $nome  (literalmente)

# Use simples quando o texto tem $ que NÃO deve expandir:
echo 'O preço é $50'   # O preço é $50

# Substituição de comando: $(...)

Uma forma de expansão especialmente poderosa: capturar a saída de um comando numa variável ou no meio de outro comando. A sintaxe $(comando) roda o comando e substitui pela sua saída. Você já viu isso nos scripts anteriores — $(date +%Y%m%d) insere a data atual num nome de arquivo. É como o shell incorpora o resultado dinâmico de comandos na composição de outros.

terminal
# $(...) roda o comando e substitui pela saída dele
hoje=$(date +%Y-%m-%d)
echo "Hoje é $hoje"          # Hoje é 2026-06-08

# Usar a saída no meio de um comando (sempre entre aspas!)
mkdir "backup-$(date +%Y%m%d)"

# Contar arquivos e guardar o número
total=$(ls | wc -l)
echo "Há $total arquivos"

# Expansões úteis de parâmetro

O Bash oferece expansões que manipulam o valor de uma variável na hora de usá-la — valores padrão para variáveis não definidas, comprimento, remoção de prefixos/sufixos. As mais úteis no dia a dia: o valor padrão (${var:-padrão}, que usa um padrão se var estiver vazia) e a remoção de extensão ou caminho. Elas evitam código extra para tarefas comuns de manipulação de strings.

terminal
# Valor padrão se a variável estiver vazia/indefinida
echo "${NOME:-anônimo}"      # usa "anônimo" se NOME não definido

arquivo="foto.jpg"
echo "${arquivo%.jpg}"       # foto   (% remove o sufixo)
echo "${#arquivo}"          # 8      (comprimento)

caminho="/home/voce/app.js"
echo "${caminho##*/}"       # app.js  (remove tudo até a última /)

Capítulo 15

Condicionais e testes

Scripts ganham inteligência quando decidem — fazer uma coisa se um arquivo existe, outra se não; prosseguir se um comando teve sucesso, parar se falhou. O if do shell viabiliza essas decisões, mas ele funciona de um jeito que surpreende quem vem de outras linguagens: a condição não é uma expressão booleana, é o código de saída de um comando. Entender isso — que if testa sucesso/falha, não verdadeiro/falso — desfaz quase toda a estranheza da sintaxe de testes. Este capítulo cobre o if, o comando de teste [[ ]] e seus operadores, os códigos de saída que governam tudo, e o case para múltiplas escolhas. É onde os scripts deixam de ser sequências lineares e passam a reagir ao ambiente — a base da automação que lida com a realidade, onde arquivos podem ou não existir e comandos podem ou não funcionar.

# Exit code: o verdadeiro/falso do shell

A chave de todo o capítulo: no shell, "sucesso" e "falha" são representados por um código de saída (exit code). Todo comando, ao terminar, retorna um número: 0 significa sucesso, qualquer outro valor significa algum tipo de falha. Note que é o oposto da intuição de muitas linguagens (onde 0 é "falso") — aqui 0 é o "deu certo". O if do shell testa exatamente isso: ele roda um comando e segue o ramo verdadeiro se o exit code for 0. A variável especial $? guarda o exit code do último comando.

terminal
# Todo comando retorna um exit code: 0 = sucesso, ≠0 = falha
ls /existe
echo $?          # 0 (deu certo)

ls /nao-existe
echo $?          # ≠0 (falhou)

# O if roda um comando e testa o exit code (0 = ramo verdadeiro)
if ls /etc > /dev/null; then
  echo "/etc existe"
fi
if testa um comando, não uma expressão
A maior fonte de confusão para quem vem de outras linguagens: o if do shell não avalia uma expressão booleana — ele roda um comando e olha o exit code. if comando; then ... significa "rode comando; se ele teve sucesso (exit 0), faça...". Por isso você pode escrever if grep -q ERRO log.txt; then — o grep retorna 0 se encontrou algo, e o if reage a isso. E por isso os testes de comparação (próxima seção) usam [[ ]], que é na verdade um comando que retorna 0 ou 1 conforme a condição. Internalizar "if testa sucesso de comando, não true/false de expressão" é o que faz toda a sintaxe de condicionais do shell — que parece arbitrária — fazer sentido.

# O comando de teste: [[ ]]

Para comparar valores e checar arquivos, o Bash oferece [[ ]] — um comando especial de teste que retorna sucesso (0) ou falha conforme a condição interna. Ele substitui o antigo [ ] (que ainda existe e é POSIX, mas tem mais armadilhas). Dentro de [[ ]] vão os operadores de teste: comparar strings, números, e — muito usado — verificar propriedades de arquivos (existe? é diretório? é executável?).

script.sh
# [[ ]] é um comando de teste; espaços internos são obrigatórios
if [[ "$nome" == "Alice" ]]; then
  echo "é a Alice"
fi

# Testes de arquivo (os mais usados):
if [[ -f "$arquivo" ]]; then echo "arquivo existe"; fi
if [[ -d "$pasta" ]];   then echo "é um diretório"; fi
if [[ -z "$var" ]];     then echo "variável vazia"; fi

# Operadores: strings, números, arquivos

Os operadores dentro de [[ ]] dividem-se por tipo, e uma peculiaridade importante: números e strings usam operadores diferentes. Para comparar números, usa-se -lt (menor), -gt (maior), -eq (igual), etc. Para comparar strings, usa-se ==, !=, <, >. Misturá-los é um erro comum — [[ 10 > 9 ]] compara como strings e dá errado (porque "1" vem antes de "9"). Para os testes de arquivo, há um conjunto de operadores unários (-f, -d, -e, -r, -w, -x).

operadores de teste
# NÚMEROS: -lt -le -gt -ge -eq -ne
if [[ $idade -ge 18 ]]; then echo "maior de idade"; fi

# STRINGS: == != (e < > para ordem alfabética)
if [[ "$resposta" == "sim" ]]; then echo "confirmado"; fi

# ARQUIVOS: -e existe, -f arquivo, -d diretório, -r/-w/-x permissões
if [[ -x "$script" ]]; then echo "é executável"; fi

# Combinar: && (e), || (ou), ! (não)
if [[ -f "$f" && -r "$f" ]]; then echo "existe e é legível"; fi
Number-as-string: o bug do -gt vs >
Uma armadilha que produz bugs silenciosos: usar o operador errado para o tipo errado. Os operadores de string (>, <) comparam alfabeticamente, então [[ 10 > 9 ]] é falso — como texto, "10" vem antes de "9" (o caractere "1" precede "9"), exatamente o problema do sort sem -n (Cap 11). Para comparar números, você precisa dos operadores numéricos: [[ 10 -gt 9 ]] é verdadeiro. O erro é traiçoeiro porque funciona para números de mesmo número de dígitos e quebra para os de tamanhos diferentes. A regra: -lt -gt -eq e companhia para números; == != < > para strings. E sempre cite as variáveis dentro do teste ("$var", Cap 14) — uma variável vazia sem aspas pode quebrar a sintaxe do teste inteiro.

# if, elif, else

A estrutura completa do condicional encadeia ramos: if para a primeira condição, elif (else-if) para alternativas, else para o caso restante, e fi (if ao contrário) para fechar. A sintaxe — com then e fi — é peculiar, mas consistente. Note o ; antes do then quando estão na mesma linha (ou o then na linha seguinte).

script.sh
if [[ $nota -ge 90 ]]; then
  echo "Excelente"
elif [[ $nota -ge 60 ]]; then
  echo "Aprovado"
else
  echo "Reprovado"
fi

# Padrão muito comum: agir conforme um comando deu certo
if npm test; then
  echo "testes passaram, prosseguindo"
else
  echo "testes falharam, abortando" >&2
  exit 1
fi

# case: múltiplas escolhas

Quando você tem muitos casos baseados no valor de uma variável, uma cadeia de elif fica pesada. O case é mais limpo: ele compara uma variável contra vários padrões (que podem usar curingas como no globbing, Cap 8) e executa o ramo correspondente. É ideal para processar argumentos, menus, ou despachar conforme um valor.

script.sh
case "$1" in
  start)
    echo "iniciando..."
    ;;
  stop)
    echo "parando..."
    ;;
  *.txt)              # padrões com curinga funcionam aqui
    echo "é um arquivo de texto"
    ;;
  *)                  # * = o caso padrão (qualquer outro)
    echo "comando desconhecido: $1"
    ;;
esac

Loops repetindo ações

Automação é, em grande parte, repetição: fazer a mesma coisa com cada arquivo de uma pasta, cada linha de uma lista, cada item de um conjunto. Os loops do shell expressam essa repetição, e o mais característico — o for — combina-se naturalmente com o globbing (Cap 8) e a substituição de comando (Cap 14) para iterar sobre arquivos e resultados. Este capítulo cobre os loops do Bash: o for (iterar sobre uma lista), o while (repetir enquanto uma condição é verdadeira), a leitura de arquivos linha a linha, e o controle de fluxo com break e continue. É onde scripts ganham a capacidade de processar conjuntos — transformar "faça isto com um arquivo" em "faça isto com todos os arquivos", a essência da automação em lote que justifica escrever um script em vez de repetir comandos à mão.

# for: iterar sobre uma lista

O for do shell percorre uma lista de itens, executando o corpo do loop uma vez para cada um, com a variável do loop assumindo cada valor. A lista pode ser escrita à mão, vir de um glob (arquivos), de uma expansão de chaves (Cap 8), ou da saída de um comando. Essa flexibilidade na fonte da lista é o que torna o for tão útil — ele itera sobre praticamente qualquer coisa que o shell saiba produzir como uma sequência de palavras.

script.sh
# Iterar sobre uma lista explícita
for nome in alice bob carol; do
  echo "Olá, $nome"
done

# Iterar sobre arquivos (o glob expande para a lista, Cap 8)
for arquivo in *.txt; do
  echo "Processando $arquivo"
done

# Iterar sobre um intervalo (expansão de chaves)
for i in {1..5}; do
  echo "iteração $i"
done
Cite a variável do loop — espaços em nomes quebram tudo
A disciplina de aspas (Cap 14) é especialmente crítica em loops sobre arquivos. Se um arquivo se chama "meu relatório.txt" e você escreve for f in *.txt; do rm $f; done sem aspas no $f, o rm recebe meu e relatório.txt como dois argumentos — apagando coisas erradas. Sempre "$f". Há uma armadilha relacionada e ainda mais sutil: iterar sobre a saída de um comando com for f in $(ls) quebra com qualquer nome que tenha espaço, porque o word splitting divide a saída do ls nos espaços. A forma robusta de processar arquivos linha a linha é o while read (adiante), não for ... in $(ls). Para o for sobre arquivos, prefira o glob direto (for f in *.txt), que preserva nomes corretamente.

# for estilo C

O Bash também oferece um for no estilo da linguagem C, com inicialização, condição e incremento — útil quando você precisa de um contador numérico com controle fino, em vez de uma lista. É menos comum no shell (a forma com lista cobre a maioria dos casos), mas aparece quando a iteração é puramente numérica.

script.sh
# for estilo C: (( inicialização; condição; incremento ))
for (( i=0; i < 5; i++ )); do
  echo "contador: $i"
done
# contador: 0, 1, 2, 3, 4

# while: repetir enquanto verdadeiro

O while repete o corpo enquanto uma condição for verdadeira — e "verdadeira" aqui é o mesmo do if (Cap 15): o exit code de um comando ser 0. Ele é a escolha quando você não tem uma lista finita conhecida de antemão, mas uma condição que controla a continuação — esperar algo acontecer, processar até acabar, repetir até um contador chegar a um limite.

script.sh
# while: repete enquanto a condição (um comando) tiver sucesso
contador=0
while [[ $contador -lt 3 ]]; do
  echo "tentativa $contador"
  contador=$(( contador + 1 ))     # aritmética com (( ))
done

# Esperar um serviço ficar disponível (padrão de espera)
while ! curl -s http://localhost:3000/health > /dev/null; do
  echo "aguardando o serviço..."
  sleep 2
done

# Lendo um arquivo linha a linha

Um padrão essencial e específico: processar um arquivo uma linha por vez. A forma correta combina while com o comando read, alimentado pelo arquivo via redirecionamento (Cap 9). Esse idioma — while read linha; do ...; done < arquivo — preserva corretamente cada linha inteira, incluindo espaços, ao contrário de iterar com for sobre a saída de cat. É a forma robusta de processar listas, CSVs, ou qualquer entrada linha a linha.

script.sh
# Ler um arquivo linha a linha (a forma ROBUSTA)
while IFS= read -r linha; do
  echo "linha: $linha"
done < arquivo.txt
# IFS= preserva espaços; -r impede interpretar barras invertidas

# Processar a saída de um comando linha a linha (via pipe)
ls -1 | while read -r arquivo; do
  echo "achei: $arquivo"
done

# break e continue

Dois comandos controlam o fluxo dentro de um loop. O break sai do loop imediatamente, abandonando as iterações restantes — útil quando você encontrou o que procurava ou uma condição de parada. O continue pula para a próxima iteração, ignorando o resto do corpo na iteração atual — útil para filtrar itens que devem ser ignorados. São os mesmos conceitos de outras linguagens (toda a coleção), com a mesma semântica.

script.sh
for arquivo in *.log; do
  # continue: pular arquivos vazios (vai para o próximo)
  if [[ ! -s "$arquivo" ]]; then
    continue
  fi

  # break: parar ao encontrar o primeiro com erro crítico
  if grep -q CRITICAL "$arquivo"; then
    echo "erro crítico em $arquivo, parando"
    break
  fi

  echo "$arquivo ok"
done
for sobre glob, while read sobre linhas
A escolha entre os loops para processar arquivos tem uma regra clara que evita os bugs de word splitting (Cap 14). Para iterar sobre arquivos, use for f in *.ext; do ... "$f"; done — o glob produz a lista corretamente, preservando cada nome. Para processar linhas de um arquivo ou da saída de um comando, use while IFS= read -r linha; do ...; done — ele lê cada linha inteira sem dividir em espaços. Evite for x in $(cat arquivo) ou for x in $(ls): ambos quebram com espaços e são a forma frágil. Lembrar "glob para arquivos, read para linhas" cobre a quase totalidade dos casos de iteração de forma robusta, e mantém seus scripts funcionando mesmo com nomes e conteúdos que contêm espaços — o tipo de dado real que sempre acaba aparecendo.

Capítulo 17

Funções organizando scripts

Quando um script cresce, a repetição e a desorganização aparecem — o mesmo bloco de comandos copiado em três lugares, uma lógica longa difícil de seguir. Funções resolvem isso no shell como em qualquer linguagem (toda a coleção): nomeiam um bloco de comandos para reutilizá-lo e dar estrutura ao código. Mas funções de shell têm peculiaridades que surpreendem — recebem argumentos como os scripts (por posição, não por nome), "retornam" via exit code ou saída de texto (não com um valor de retorno comum), e têm regras próprias de escopo de variáveis. Este capítulo cobre como definir e chamar funções, passar e usar argumentos, retornar resultados das duas formas idiomáticas, e controlar o escopo com local. É o que transforma scripts de sequências lineares em código organizado e reutilizável — a diferença entre um script descartável e um que você mantém e expande.

# Definindo e chamando

Uma função no shell é um bloco de comandos com nome. A definição usa nome() { ... }, e a chamada é simplesmente escrever o nome — sem parênteses, como se fosse um comando qualquer. Essa é a primeira surpresa: você chama uma função do mesmo jeito que chama ls ou grep, porque para o shell uma função é apenas mais um comando que você definiu. A função precisa ser definida antes de ser chamada no script (o shell lê de cima para baixo).

script.sh
# Definir: nome() { comandos }
saudar() {
  echo "Olá!"
  echo "Bem-vindo ao script."
}

# Chamar: só o nome, SEM parênteses (como qualquer comando)
saudar

# Definir uma função tem que vir ANTES de chamá-la

# Argumentos: $1, $2, $@

Funções recebem argumentos exatamente como os scripts recebem argumentos da linha de comando (Cap 18): por posição, acessados por $1 (primeiro argumento), $2 (segundo), e assim por diante. Diferente de muitas linguagens, você não declara parâmetros nomeados na definição — eles chegam posicionalmente e você os lê pelos números. $@ representa todos os argumentos, e $# a quantidade deles. A convenção idiomática é, no início da função, atribuir esses argumentos posicionais a variáveis locais com nomes significativos.

script.sh
saudar() {
  # Argumentos chegam por posição: $1, $2, ...
  local nome="$1"        # nomeie para legibilidade
  local idade="$2"
  echo "Olá $nome, você tem $idade anos"
}

# Chamar passando argumentos (como a um comando)
saudar Alice 30
# Olá Alice, você tem 30 anos

contar_args() {
  echo "Recebi $# argumentos: $@"
}
contar_args a b c       # Recebi 3 argumentos: a b c
Funções recebem argumentos como scripts, não como funções comuns
A diferença mental que confunde quem vem de outras linguagens: no shell, você não escreve function saudar(nome, idade) com parâmetros nomeados. A função recebe os argumentos posicionalmente, do mesmo jeito que um script recebe os seus (Cap 18) — $1, $2, $@. Isso é coerente com a filosofia de que funções são "comandos definidos por você": assim como você passa argumentos a cp origem destino por posição, passa a saudar Alice 30 por posição. A convenção que torna isso legível é atribuir os posicionais a variáveis nomeadas locais logo no início — local nome="$1" — para que o resto da função use nomes claros em vez de $1 espalhado. E, claro, cite sempre ("$1", Cap 14).

# "Retornando" valores: as duas formas

Aqui está a peculiaridade que mais surpreende: funções de shell não retornam valores como em outras linguagens. O comando return só devolve um exit code (0–255), usado para sinalizar sucesso/falha (como o exit code de qualquer comando, Cap 15) — não para devolver dados. Para "retornar" um valor (uma string, um número calculado), a forma idiomática é a função imprimir o resultado (com echo), e quem chama capturar essa saída com substituição de comando ($(...), Cap 14). São dois canais distintos: return para status, stdout para dados.

script.sh
# Forma 1: return devolve um EXIT CODE (status), não um valor
arquivo_existe() {
  [[ -f "$1" ]]      # o exit code do teste vira o return
}
if arquivo_existe config.txt; then echo "existe"; fi

# Forma 2: para retornar um VALOR, imprima e capture com $(...)
somar() {
  echo $(( $1 + $2 ))   # imprime o resultado
}
resultado=$(somar 3 4)         # captura a saída
echo "3 + 4 = $resultado"      # 3 + 4 = 7
return é status (0-255), não um valor
Um erro comum é tratar return como o return de outras linguagens e tentar devolver um número grande ou uma string. O return do shell só aceita um inteiro de 0 a 255, e seu propósito é sinalizar sucesso ou falha — 0 para sucesso, outro valor para erro —, exatamente como o exit code de qualquer comando (Cap 15). return "texto" ou return 1000 não fazem o que você espera. Para devolver dados, o canal é o stdout: a função echo o resultado, e o chamador captura com $(...). Manter os dois separados na cabeça — return = "deu certo?", stdout = "aqui está o resultado" — é a chave para escrever funções que se compõem bem, e espelha a separação stdout/stderr/exit-code que governa todo programa Unix (Cap 9).

# Escopo: local

Por padrão, variáveis no shell são globais — uma variável definida dentro de uma função vaza para o resto do script e pode sobrescrever outra de mesmo nome, causando bugs sutis. A palavra-chave local, usada dentro de uma função, restringe a variável àquela função: ela existe só ali e não interfere no resto. Usar local para todas as variáveis internas de uma função é uma disciplina importante — torna funções autocontidas e previsíveis, evitando que se afetem mutuamente por variáveis compartilhadas acidentalmente.

script.sh
contador=10          # variável global

processar() {
  local contador=0    # LOCAL: não afeta a global de mesmo nome
  while [[ $contador -lt 3 ]]; do
    contador=$(( contador + 1 ))
  done
  echo "local: $contador"   # local: 3
}

processar
echo "global: $contador"     # global: 10 (intacta!)
local sempre, por padrão
Adote a regra de declarar local toda variável interna de uma função, sem exceção. O custo é uma palavra a mais; o benefício é enorme — funções viram caixas-pretas autocontidas que não vazam estado nem colidem com variáveis de outras funções ou do script principal. Sem local, scripts maiores acumulam bugs traiçoeiros onde uma função sobrescreve silenciosamente uma variável que outra parte do código usava, e o sintoma aparece longe da causa. É o mesmo princípio de encapsulamento e menor escopo que vale em qualquer linguagem (toda a coleção), aqui especialmente importante porque o padrão do shell — variáveis globais — é o oposto do seguro. Funções com local e argumentos citados são a base de scripts grandes que permanecem manuteníveis.

Argumentos e entrada

Um script útil raramente faz sempre a mesma coisa fixa — ele recebe parâmetros que mudam seu comportamento: qual arquivo processar, qual versão implantar, qual modo usar. Esses parâmetros chegam como argumentos de linha de comando, e tratá-los bem é o que torna um script uma ferramenta reutilizável em vez de um trecho rígido. Este capítulo cobre como scripts recebem argumentos (os mesmos $1, $@ das funções, Cap 17), como validá-los, como ler entrada interativa do usuário, e como dar aos scripts as opções de linha de comando (-v, --help) que os fazem parecer ferramentas profissionais. É o capítulo que fecha o ciclo do scripting: das variáveis e do controle de fluxo dos capítulos anteriores para a interface que conecta o script ao mundo — a quem o invoca e ao que ele recebe.

# Argumentos posicionais

Um script acessa seus argumentos de linha de comando pelas mesmas variáveis posicionais das funções (Cap 17): $1 é o primeiro argumento, $2 o segundo, e assim por diante. $0 é o nome do próprio script. $@ são todos os argumentos, $# a quantidade. Quando você roda ./deploy.sh produção v1.2, dentro do script $1 é "produção" e $2 é "v1.2". É a interface mais básica e direta de passar informação a um script.

deploy.sh
#!/usr/bin/env bash
# Rodado como: ./deploy.sh produção v1.2

echo "Script:    $0"      # ./deploy.sh
echo "Ambiente:  $1"      # produção
echo "Versão:    $2"      # v1.2
echo "Total:     $#"      # 2
echo "Todos:     $@"      # produção v1.2

# Validando argumentos

Um script robusto não confia que recebeu o que precisa — ele verifica. O padrão essencial é checar, no início, se o número de argumentos é o esperado e se eles fazem sentido; se não, exibir uma mensagem de uso e sair com erro. Isso transforma um script que falha de forma confusa (com um erro críptico lá no meio) num que falha cedo e claro, dizendo exatamente o que esperava — a aplicação do "falhar cedo" (Cap 21) à interface do script.

deploy.sh
# Validar: o script PRECISA de 2 argumentos
if [[ $# -ne 2 ]]; then
  echo "Uso: $0 <ambiente> <versão>" >&2   # mensagem p/ stderr (Cap 9)
  exit 1                                  # sai com erro (Cap 15)
fi

ambiente="$1"
versao="$2"

# Validar valores específicos
if [[ "$ambiente" != "produção" && "$ambiente" != "staging" ]]; then
  echo "Ambiente inválido: $ambiente" >&2
  exit 1
fi
Mensagens de erro vão para stderr, e saia com código ≠0
Note dois detalhes que tornam um script um bom cidadão Unix (Cap 9). Primeiro, a mensagem de uso vai para o stderr (>&2), não para o stdout — porque é um diagnóstico para o humano, não o resultado do script; assim, se alguém canalizar a saída do script para outro comando, a mensagem de erro não polui os dados. Segundo, o script sai com exit 1 (código ≠0), sinalizando falha — para que quem o chamou (outro script, um &&, um CI) saiba que algo deu errado e possa reagir. Um script que imprime erros no stdout e sai com 0 mesmo falhando é um péssimo cidadão: ele mente sobre seu sucesso e contamina pipelines. Seguir a convenção — erros no stderr, exit code honesto — faz seus scripts se integrarem ao resto do shell como os comandos nativos.

# Lendo entrada interativa: read

Além de argumentos, um script pode pedir entrada ao usuário durante a execução, com o comando read (o mesmo do while read, Cap 16). Ele pausa, espera o usuário digitar, e guarda o que foi digitado numa variável. É útil para confirmações ("tem certeza?"), perguntas, ou entrada que não faz sentido passar como argumento. A opção -p exibe um prompt, e -s oculta a digitação (para senhas).

script.sh
# Ler entrada do usuário (-p exibe um prompt)
read -p "Qual o seu nome? " nome
echo "Olá, $nome"

# Confirmação antes de uma ação destrutiva
read -p "Apagar tudo? (s/N) " resposta
if [[ "$resposta" == "s" ]]; then
  echo "apagando..."
else
  echo "cancelado"
fi

# -s oculta a digitação (senhas)
read -s -p "Senha: " senha

# shift e processamento de opções

Para scripts que aceitam opções (como -v, --help) além de argumentos posicionais, o padrão usa shift (que descarta o primeiro argumento, deslocando os demais para baixo) dentro de um loop com case (Cap 15). Isso percorre os argumentos um a um, reconhecendo opções e seus valores. É como você dá ao seu script a mesma interface profissional dos comandos nativos — opções nomeadas, em qualquer ordem.

script.sh
verbose=0
# Percorre os argumentos reconhecendo opções (loop + case + shift)
while [[ $# -gt 0 ]]; do
  case "$1" in
    -v|--verbose)
      verbose=1
      shift                # consome esta opção
      ;;
    -h|--help)
      echo "Uso: $0 [-v] arquivo"
      exit 0
      ;;
    *)
      arquivo="$1"       # argumento posicional
      shift
      ;;
  esac
done
Para opções complexas, há getopts
O padrão while + case + shift acima cobre a maioria dos scripts e é transparente. Para scripts com muitas opções, especialmente as que recebem valores e as agrupáveis (Cap 3), o Bash oferece o builtin getopts, que automatiza o parsing seguindo as convenções padrão de opções curtas. Vale conhecer a sua existência, mas não há pressa: a maioria dos seus scripts terá poucas opções, e o loop manual com case é mais legível para esses casos. O importante é o princípio — um bom script tem uma interface: valida o que recebe, oferece um --help que explica o uso, falha com mensagem clara no stderr quando mal invocado. Essa interface é o que separa um script que só você consegue usar (lembrando a ordem mágica dos argumentos) de uma ferramenta que qualquer um — inclusive você daqui a seis meses — usa com confiança.

Processos e jobs

Todo comando que você roda vira um processo — uma instância em execução de um programa, com seu próprio identificador, dona de recursos, capaz de receber sinais. Gerenciar processos é parte essencial do trabalho no terminal: ver o que está rodando, encerrar o que travou, rodar tarefas longas em segundo plano, monitorar consumo de recursos. Este capítulo cobre os comandos de processo — ps, top, kill —, os sinais que comunicam com eles (incluindo o SIGTERM que você viu no shutdown gracioso dos containers, Vol XV, Cap 10), e o controle de jobs que permite rodar e alternar tarefas em primeiro e segundo plano. É um capítulo que conecta o shell ao sistema operacional por baixo: entender processos é entender o que de fato acontece quando você executa algo, e ganhar o controle para gerenciá-lo.

# O que é um processo

Quando você executa um programa, o sistema cria um processo: uma instância viva daquele programa, com um PID (process ID) único que o identifica, memória própria, e os canais de E/S (Cap 9). O mesmo programa pode ter vários processos simultâneos (vários node rodando), cada um com seu PID. É uma ideia que você já encontrou: no Docker (Vol XV, Cap 1), um container é um processo isolado; o PID 1 dentro dele é o seu CMD. Aqui, no host, você vê e gerencia os processos diretamente.

terminal
# ps lista processos. -e todos, -f formato completo
ps -ef

# Combinar com grep para achar um processo específico (Cap 11)
ps -ef | grep node
# UID  PID  PPID  ...  CMD
# voce 4823 1     ...  node server.js
#      ^PID ^PID do pai

# pgrep acha o PID direto pelo nome (mais limpo)
pgrep -fl node

# top e htop: monitorar ao vivo

Enquanto ps dá um retrato estático, o top mostra os processos ao vivo, atualizando continuamente, ordenados por consumo de CPU ou memória. É a ferramenta de primeira linha para diagnosticar "por que a máquina está lenta?" ou "quem está comendo toda a memória?". O htop (instalável à parte) é uma versão mais amigável, com cores e interação por mouse. Ambos conectam ao docker stats (Vol XV, Cap 19), que faz o mesmo para containers.

terminal
# Monitor ao vivo de processos (CPU, memória)
top
#   ordena por CPU por padrão; 'q' para sair
#   dentro do top: M ordena por memória, P por CPU

# htop: versão mais amigável (precisa instalar)
htop

# Uso de disco e memória rápido:
df -h           # espaço em disco (Vol XV, Cap 19 docker system df)
free -h         # memória livre/usada

# Sinais: comunicando com processos

Você se comunica com um processo enviando-lhe um sinal — uma notificação que o sistema entrega. Os dois mais importantes você já viu no Docker (Vol XV, Cap 10): o SIGTERM (sinal 15) é um pedido educado de encerramento — "termine quando puder", permitindo ao processo fazer limpeza (fechar conexões, salvar estado); o SIGKILL (sinal 9) é a morte imediata e incondicional — o processo é encerrado na hora, sem chance de limpar nada. O Ctrl+C que você aperta para interromper um comando envia um terceiro, o SIGINT (interrupção).

terminal
# kill envia SIGTERM por padrão (pedido educado de encerrar)
kill 4823           # SIGTERM ao processo de PID 4823

# SIGKILL (-9): morte imediata, só quando SIGTERM não funciona
kill -9 4823        # força (último recurso)

# Matar por nome (todos os processos chamados node)
pkill node
killall node
Tente SIGTERM antes de SIGKILL
A diferença entre os dois sinais de encerramento importa, e ecoa o shutdown gracioso dos containers (Vol XV, Cap 10). O kill sem opção envia SIGTERM, que pede ao processo para encerrar de forma limpa — um servidor bem-feito usa esse momento para terminar requisições em andamento, fechar conexões com o banco, e sair sem deixar estado corrompido. O kill -9 envia SIGKILL, que o sistema executa sem dar ao processo qualquer chance de reação — ele morre no meio do que estava fazendo, podendo deixar arquivos pela metade, locks travados, dados inconsistentes. A regra: sempre tente kill (SIGTERM) primeiro, dê alguns segundos, e só recorra a kill -9 se o processo estiver genuinamente travado e não responder. O SIGKILL é o último recurso, não o primeiro — usá-lo por reflexo é trocar a conveniência imediata por possível corrupção.

# Primeiro e segundo plano

Por padrão, um comando roda em primeiro plano (foreground): ele toma o terminal até terminar. Mas você pode rodá-lo em segundo plano (background), liberando o terminal para outros comandos enquanto ele continua. Adicionar & ao fim de um comando o inicia em background; Ctrl+Z suspende o comando em primeiro plano; bg e fg movem entre os estados; jobs lista o que está rodando. É como você gerencia múltiplas tarefas numa sessão.

terminal
# & inicia em segundo plano (libera o terminal)
npm run dev &

# jobs lista as tarefas em background da sessão
jobs
# [1]+ Running   npm run dev &

# Ctrl+Z suspende o comando em foreground; bg o retoma em background
# fg traz uma tarefa de volta ao primeiro plano
fg %1            # traz o job 1 para o foreground

# Processos que sobrevivem à sessão

Há um detalhe importante: um processo iniciado em background com & normalmente morre quando você fecha o terminal (recebe o sinal SIGHUP, de "hang up"). Para tarefas que devem continuar mesmo após você sair, há ferramentas: nohup (ignora o SIGHUP), ou — muito melhor para trabalho sério — multiplexadores de terminal como tmux e screen, que mantêm sessões inteiras vivas, das quais você "desconecta" e "reconecta" depois. São essenciais ao trabalhar em servidores remotos por SSH, onde a conexão pode cair.

terminal
# nohup: o processo ignora o SIGHUP e sobrevive ao fechar o terminal
nohup ./tarefa-longa.sh &

# tmux: sessões persistentes (essencial em servidores remotos via SSH)
tmux                  # inicia uma sessão
#   Ctrl+B d           desconecta (a sessão continua viva)
tmux attach          # reconecta a uma sessão depois
tmux: indispensável em servidores remotos
Ao trabalhar num servidor por SSH — implantar, depurar, rodar uma tarefa longa —, há um risco real: se a conexão cair (rede instável, laptop dorme), os processos da sua sessão morrem junto, possivelmente no meio de algo importante. O tmux resolve isso elegantemente: você inicia uma sessão tmux no servidor, trabalha dentro dela, e ela vive no servidor independente da sua conexão. Se o SSH cair, a sessão continua rodando lá; você reconecta e a encontra exatamente onde estava. É o seguro contra conexões instáveis, e também permite múltiplos painéis e janelas numa só conexão. Para qualquer trabalho não trivial em máquina remota, iniciar dentro de um tmux antes de começar é um hábito que evita o desastre de perder horas de trabalho por uma queda de Wi-Fi. Conecta ao Vol XV: o mesmo cuidado de processos resilientes que os containers têm, aplicado à sua sessão de trabalho.

Capítulo 20

Ambiente e configuração

O shell não é só um interpretador de comandos — é um ambiente configurável que você molda ao seu jeito. Variáveis de ambiente carregam configuração que programas leem (o PATH que decide quais comandos existem, o EDITOR que o git abre), aliases criam atalhos para comandos longos, e arquivos de configuração personalizam cada sessão. Este capítulo cobre esse ambiente: as variáveis de ambiente e como exportá-las, o PATH e como o shell encontra comandos, aliases e funções para customização, e os arquivos de inicialização (.bashrc e companhia) onde tudo isso vive. É também onde conexões importantes se fecham: as variáveis de ambiente são exatamente o mecanismo de configuração que o Docker (Vol XV, Cap 13) e a autenticação (Vol XIII) usam para injetar segredos e configuração em runtime. Entender o ambiente do shell é entender como configuração flui para os programas em todo o stack.

# Variáveis de ambiente vs variáveis de shell

Há uma distinção sutil mas importante. Uma variável de shell comum (Cap 14) existe só dentro do shell atual — programas que você executa não a veem. Uma variável de ambiente é exportada e, por isso, herdada pelos processos filhos: quando você roda um programa, ele recebe uma cópia do ambiente, e pode ler essas variáveis. O comando export promove uma variável de shell a variável de ambiente. É essa exportação que faz a configuração chegar aos programas.

terminal
# Variável de shell: só o shell atual a vê
minha_var="local"

# export: promove a variável de ambiente (filhos herdam)
export NODE_ENV="production"
# agora qualquer programa filho lê process.env.NODE_ENV (Vol VIII)

# Definir só para UM comando (sem exportar para a sessão):
NODE_ENV="test" npm test     # vale só para este npm test

# Ver todas as variáveis de ambiente
env
É o mesmo mecanismo do Docker e da autenticação
As variáveis de ambiente do shell são exatamente o mesmo conceito que você viu injetando configuração nos containers (Vol XV, Cap 13) e segredos na autenticação (Vol XIII). Quando o Docker passa -e DATABASE_URL=... ou um --env-file, ele está populando o ambiente do processo dentro do container — o mesmo ambiente que export manipula no shell. Quando a sua aplicação Node lê process.env.JWT_SECRET, ela está lendo uma variável de ambiente que alguém exportou (você no shell, o Docker no container, ou o CI no pipeline). Entender isso unifica três volumes: configuração e segredos fluem para os programas pelo ambiente, e o export do shell é a forma mais básica de colocá-los lá. A disciplina de segredos é a mesma — variáveis de ambiente com segredos não vão para arquivos versionados (Vol XIV, Cap 17).

# O PATH: como o shell acha comandos

A variável de ambiente mais importante é o PATH: uma lista de diretórios, separados por :, onde o shell procura os comandos externos (Cap 1). Quando você digita git, o shell percorre os diretórios do PATH em ordem, procurando um executável chamado git, e roda o primeiro que encontra. É por isso que comandos instalados "funcionam de qualquer lugar" — eles estão num diretório do PATH. E é por isso que ferramentas recém-instaladas às vezes "não são encontradas": elas estão num diretório que não está no PATH.

terminal
# O PATH: diretórios separados por : onde o shell busca comandos
echo $PATH
# /usr/local/bin:/usr/bin:/bin:/home/voce/.local/bin

# Adicionar um diretório ao PATH (ex.: para uma ferramenta instalada lá)
export PATH="$HOME/.local/bin:$PATH"
# o novo diretório vem PRIMEIRO (tem prioridade); cite sempre

# Onde está o executável que será rodado? (Cap 1)
which node

# Aliases: atalhos para comandos

Um alias é um apelido para um comando (ou comando com opções) que você usa muito. Em vez de digitar git status toda hora, você cria alias gs='git status' e digita gs. Aliases personalizam o shell para o seu fluxo, reduzindo digitação e codificando suas preferências (como o ls sempre colorido, ou o rm sempre interativo, Cap 5). Eles valem só na sessão atual, a menos que sejam salvos num arquivo de configuração.

terminal
# alias nome='comando' — apelidos para comandos frequentes
alias gs='git status'
alias ll='ls -lah'
alias ..='cd ..'

# Codificar uma preferência segura (Cap 5):
alias rm='rm -i'          # rm sempre pede confirmação

# Ver os aliases definidos

# Arquivos de inicialização: .bashrc

Aliases e exports definidos na linha de comando somem ao fechar a sessão. Para torná-los permanentes, você os coloca num arquivo de inicialização — um script que o shell executa toda vez que inicia. O principal é o ~/.bashrc (para shells interativos no Bash), onde vivem seus aliases, exports de PATH, funções e configurações. Editar esse arquivo é como você personaliza permanentemente o seu ambiente; após editá-lo, source ~/.bashrc aplica as mudanças sem reabrir o terminal.

~/.bashrc
# ~/.bashrc — executado a cada sessão interativa do Bash

# Configuração de ambiente
export EDITOR="nano"          # editor padrão (git, etc. — Cap 6)
export PATH="$HOME/.local/bin:$PATH"

# Aliases pessoais
alias gs='git status'
alias ll='ls -lah'

# Funções (Cap 17) também podem morar aqui
mkcd() { mkdir -p "$1" && cd "$1"; }   # cria e entra
.bashrc vs .bash_profile vs .profile
Há vários arquivos de inicialização e a distinção confunde. Em linhas gerais: o ~/.bashrc roda em shells interativos não-login (abrir um novo terminal); o ~/.bash_profile (ou ~/.profile) roda em shells de login (login via SSH, primeiro terminal). A prática comum para evitar duplicação: coloque tudo no ~/.bashrc e faça o ~/.bash_profile apenas dar source ~/.bashrc, garantindo que sua configuração se aplique em ambos os casos. No Windows com Git Bash ou WSL (Cap 1), os mesmos arquivos valem. Para o zsh (shell padrão do macOS moderno), o equivalente é ~/.zshrc. O importante: há um lugar para configuração permanente, e entender qual arquivo roda quando evita o "configurei mas não funcionou ao reabrir". Quando em dúvida, ~/.bashrc com um source a partir do .bash_profile cobre os casos.

Capítulo 21

Robustez em scripts

Um script que funciona quando tudo dá certo é fácil; um script que falha bem quando algo dá errado é o que separa um rascunho de uma ferramenta de produção. Por padrão, o Bash é perigosamente permissivo: ele continua executando mesmo depois que um comando falha, trata variáveis indefinidas como vazias (com consequências catastróficas), e ignora erros no meio de pipelines. Este capítulo reúne as práticas que tornam scripts robustos — o trio set -euo pipefail que faz o Bash falhar cedo e alto, as armadilhas (trap) que garantem limpeza mesmo em caso de erro, e a disciplina de validação e aspas que atravessa todo o volume. É o capítulo que aplica o "falhar fechado" do Vol XIII (Cap 21) ao shell: um bom script, diante de uma condição inesperada, para com um erro claro em vez de prosseguir cegamente causando estragos. É a diferença entre automação confiável e uma bomba-relógio.

# O Bash é permissivo por padrão

Antes das soluções, o problema. Por padrão, o Bash tem comportamentos que, num script, são armadilhas. Ele continua após um comando falhar — se o passo 2 de cinco falha, os passos 3, 4 e 5 rodam mesmo assim, possivelmente sobre um estado quebrado. Ele trata uma variável indefinida como string vazia — um rm -rf "$DIR/" com $DIR não definido vira rm -rf "/". E num pipeline, ele só olha o exit code do último comando — um erro no meio passa despercebido. Esses padrões são razoáveis no uso interativo, mas desastrosos em scripts.

o perigo do padrão
# SEM proteção, este script continua mesmo se o cd falhar:
cd /pasta/que/nao/existe    # falha, mas o script CONTINUA...
rm -rf *                  # ...e apaga tudo no diretório ERRADO!

# Variável indefinida vira vazia — catástrofe silenciosa:
rm -rf "$BUILD_DIR/"      # se BUILD_DIR não definida: rm -rf "/"

# O cinto de segurança: set -euo pipefail

A linha que deve abrir quase todo script de produção: set -euo pipefail. São três proteções num comando. -e (errexit): o script aborta assim que qualquer comando falha, em vez de continuar. -u (nounset): usar uma variável indefinida é um erro que para o script, em vez de virar vazio silenciosamente. -o pipefail: um pipeline falha se qualquer comando nele falhar, não só o último. Juntas, transformam o Bash permissivo num que falha cedo, alto e seguro.

script.sh
#!/usr/bin/env bash
# O "cinto de segurança" — abra quase todo script com isto:
set -euo pipefail

# -e : aborta no primeiro comando que falhar
# -u : variável indefinida é erro (não vira vazio)
# -o pipefail : pipeline falha se QUALQUER estágio falhar

# Agora um cd que falha PARA o script, evitando o desastre anterior:
cd "$BUILD_DIR"             # se falhar (ou $BUILD_DIR indefinida), aborta aqui
rm -rf ./*                 # só roda se o cd deu certo
set -euo pipefail é o falhar-fechado do shell
Esta linha é a aplicação direta do princípio "falhar fechado" do Vol XIII (Cap 21) ao scripting. Sem ela, o padrão do Bash é "falhar aberto" — diante de um erro, prosseguir mesmo assim, o que num script destrutivo é a receita do desastre. Com ela, o padrão vira "falhar fechado" — diante de qualquer condição inesperada (comando que falha, variável indefinida, erro num pipe), o script para imediatamente, em estado conhecido, antes de causar dano. O custo é que você precisa lidar explicitamente com falhas esperadas (um comando que pode falhar legitimamente recebe um || true ou um if), mas esse é exatamente o ponto: você passa a tratar falhas conscientemente, em vez de ignorá-las por omissão. Toda automação séria — um script de deploy, um entrypoint de container (Vol XV), um hook do git (Vol XIV, Cap 20) — deve começar com set -euo pipefail. É a única linha que mais aumenta a confiabilidade de um script.

# trap: limpeza garantida

Quando um script cria recursos temporários — um arquivo temporário, um diretório de trabalho, um lock —, eles precisam ser limpos ao final, inclusive se o script falhar no meio. O trap resolve isso: ele registra um comando para rodar quando o script termina (por qualquer motivo — fim normal, erro, ou interrupção). É o equivalente shell do finally de outras linguagens, garantindo que a limpeza aconteça mesmo nos caminhos de erro, em harmonia com o set -e.

script.sh
set -euo pipefail

# Criar um diretório temporário
TMPDIR=$(mktemp -d)

# trap: rode esta limpeza ao SAIR, não importa como (EXIT pega tudo)
limpar() { rm -rf "$TMPDIR"; }
trap limpar EXIT

# Mesmo que um comando abaixo falhe (e o -e aborte), o temp é limpo:
cp dados.csv "$TMPDIR/"
processar "$TMPDIR/dados.csv"      # se falhar, limpar() ainda roda

# A disciplina de aspas e validação

As proteções automáticas (set -euo pipefail, trap) se somam à disciplina manual que o volume vem construindo. Aspas em toda variável ("$var", Cap 14): impede word splitting e o desastre da variável vazia. Validar entradas cedo (Cap 18): checar argumentos e condições no início, falhando claro se algo falta. Conferir antes de destruir (Caps 5, 8): ls antes de rm. Essas práticas não são opcionais num script de produção — são o que torna a automação confiável o suficiente para você dormir tranquilo enquanto ela roda.

script defensivo (resumo)
#!/usr/bin/env bash
set -euo pipefail              # 1. falhar cedo e seguro

# 2. validar entradas cedo (Cap 18)
if [[ $# -lt 1 ]]; then
  echo "Uso: $0 <arquivo>" >&2; exit 1
fi

arquivo="$1"                  # 3. sempre entre aspas (Cap 14)

# 4. validar que o arquivo existe antes de usá-lo (Cap 15)
[[ -f "$arquivo" ]] || { echo "Não existe: $arquivo" >&2; exit 1; }

echo "Processando $arquivo com segurança"
shellcheck: o linter que pega os erros para você
Você não precisa lembrar de todas essas regras manualmente — existe uma ferramenta que as verifica. O shellcheck é um linter para scripts shell que analisa o seu código e aponta os problemas clássicos: variáveis não citadas, uso de variável indefinida, padrões frágeis, erros de sintaxe sutis. É o equivalente shell do ESLint/TypeScript (toda a coleção) — pega os bugs antes de você rodar o script. Rodá-lo nos seus scripts (e idealmente no CI, Vol XIV Cap 19, ou num hook de pre-commit, Vol XIV Cap 20) captura a esmagadora maioria dos erros de robustez automaticamente, incluindo o esquecimento de aspas que é a fonte nº 1 de bugs. A combinação de set -euo pipefail (proteção em runtime) + shellcheck (análise estática) + aspas disciplinadas é o que torna scripts shell tão confiáveis quanto código em qualquer linguagem moderna. Não escreva scripts de produção sem passá-los pelo shellcheck.

Capítulo 22

Boas práticas e encerramento

Vinte e um capítulos construíram o domínio do terminal — do modelo do shell à escrita de scripts robustos. Este último os reúne numa síntese de princípios e fecha o volume. O fio condutor foi consistente: o shell é uma linguagem, não uma lista de comandos a decorar, governada por um modelo simples — ler, expandir, executar — e por uma filosofia — programas pequenos compostos por pipes. Aqui consolidamos os hábitos que emergiram capítulo a capítulo: pensar em transformações de dados, citar variáveis religiosamente, escrever scripts que falham fechado, conferir antes de destruir. É também onde o terminal se revela como ele de fato é na coleção: não um tópico isolado, mas a interface através da qual você opera tudo o que os outros volumes construíram — o git, o docker, o deploy, a automação. Dominar o shell é dominar o lugar onde todo o resto do trabalho acontece.

# Os dois princípios que organizam tudo

Se o Git tinha "objetos imutáveis + refs móveis" e o Docker "imagem imutável + container efêmero", o shell tem um par próprio. Primeiro: o shell expande antes de executar (Cap 1) — o comando que você digita é transformado (variáveis, globs, substituições) antes de o programa rodar, e quase toda surpresa do shell se explica por essa ordem. Segundo: programas pequenos se compõem por pipes (Cap 10) — você resolve problemas grandes encadeando ferramentas simples, não procurando uma ferramenta única. O primeiro princípio explica o comportamento do shell; o segundo, a forma de pensar nele. Juntos, transformam o terminal de um conjunto de fórmulas mágicas numa linguagem que você lê, compõe e prevê.

A pergunta que resolve quase tudo
Diante de qualquer confusão no shell — "por que este comando não fez o que eu esperava?" —, volte aos princípios. O que o shell expandiu antes de executar? Rode o comando com echo na frente e veja o resultado da expansão (variáveis, globs) — quase sempre a surpresa está aí: uma variável vazia, um glob que pegou demais, aspas faltando. E para tarefas de processamento: que sequência de transformações leva da entrada ao que eu quero? — decomponha em estágios de pipe, construindo um por vez (Cap 10). Essas duas perguntas, mais a disciplina de citar variáveis, resolvem a esmagadora maioria dos problemas do dia a dia. O shell é previsível quando você raciocina com o seu modelo, em vez de tratá-lo como mágica.

# A disciplina que atravessa o volume

Alguns hábitos apareceram repetidamente porque são os que mais importam. Cite suas variáveis — "$var" sempre (Cap 14): é a fonte nº 1 de bugs, e citar elimina a categoria inteira. Confira antes de destruir — ls ou echo o padrão antes do rm (Caps 5, 8): o terminal não tem desfazer, então a checagem é a rede. Falhe fechado — set -euo pipefail em scripts (Cap 21): pare no erro em vez de prosseguir cegamente. Pense em stdout/stderr/exit code (Cap 9): escreva ferramentas que se compõem, com resultado no stdout, erros no stderr, e código de saída honesto.

os hábitos essenciais
# 1. SEMPRE cite variáveis (Cap 14)
rm "$arquivo"          # nunca rm $arquivo

# 2. Confira antes de destruir (Caps 5, 8)
ls *.tmp && rm *.tmp   # veja o que será apagado primeiro

# 3. Scripts falham fechado (Cap 21)
set -euo pipefail

# 4. Erros no stderr, exit code honesto (Cap 9)
echo "erro: arquivo não encontrado" >&2
exit 1

# Saber quando parar no shell

Uma sabedoria importante: o shell é excelente para uma classe de tarefas e ruim para outra, e reconhecer o limite evita sofrimento. Ele brilha em orquestração e automação leve — encadear comandos, processar texto, mover arquivos, rodar ferramentas em sequência. Mas quando a lógica fica complexa — estruturas de dados aninhadas, muitas condições, manipulação sofisticada, aritmética séria —, o shell vira um fardo, e é sinal de cruzar para uma linguagem de propósito geral (Python, ou o TypeScript da coleção). Um script Bash de duzentas linhas com lógica intricada quase sempre seria mais claro e manutenível reescrito em Python. A habilidade não é só usar o shell, mas saber quando ele é a ferramenta certa e quando você passou do ponto.

Shell para colar, linguagem para lógica
A heurística prática: use o shell como cola — para conectar programas, automatizar sequências de comandos, processar texto em pipelines. No momento em que você se pega implementando lógica de negócio, estruturas de dados complexas, ou parsing sofisticado em Bash, pare e pergunte se uma linguagem de verdade não seria melhor. O shell não tem tipos, suas estruturas de dados são limitadas, e o tratamento de erros é manual — coisas que linguagens modernas (toda a coleção) fazem muito melhor. Isso não diminui o shell: ele é insubstituível no que faz bem, e nenhuma linguagem orquestra comandos do sistema tão fluentemente. Mas reconhecer a fronteira — "isto virou um programa, não um script" — é o que mantém sua automação sustentável. Os melhores sistemas usam ambos: shell para a orquestração, linguagens para a lógica, cada um no que é forte.
